    LLM 应用工程：链式调用、记忆、Agent 与函数调用

    正文修订于 2026-11-13

    读完这篇，你能把一次模型调用接成有证据、能处理失败的应用流程，并区分“代码运行成功”和“回答可靠”。前提是了解基本 HTTP/JSON 和函数调用；具体 SDK 写法不在本篇固定。

    贯穿案例是一个笔记助手：先读取复习安排，生成一张卡片，再把用户确认的计划保存。最小版本用固定流程即可；模型只负责语言理解与候选生成，身份、金额、日期计算和保存结果由可信程序裁决。

    先选固定工作流，必要时才加 Agent

    链式调用（Chain）把多个步骤串起来，例如“读取笔记→生成→校验→展示”。它是一种组织方式，不等于必须使用某个框架的 LLMChain 类。前一步的输出进入下一步时，要明确数据契约和失败分支，不能将错误文本当作正常输入继续传递。

    Agent 在固定边界内根据观察决定下一步，如资料缺失时选择检索，日期含糊时追问。ReAct 是把推理和动作交替组织的一种模式；模型提出动作，执行器运行并回传 Observation（真实观察）。提示是其中一个部件，状态、授权、验证、预算与终止同样不可缺少。

    “读资料—提取—确认—保存”路径已知时，不必为每步增加自主决策。只有动态选择确实改善成功率，才比较有限 Agent 循环。循环轮次、网络重试次数、总时间与费用分别设限；max_iterations 不能独自控制全部预算。

    工具调用：提议、授权和执行是不同阶段

    Function Calling（函数调用）让模型返回结构化的工具名、参数和调用标识。执行工具的是应用，不是参数 JSON；各接口的消息字段不同，下面讨论共同机制，不把 role=tool 等具体字段当作跨厂商标准。

    1. 应用提供当前允许的工具与参数约定，工具描述写清用途、前提和失败结果。
    2. 模型提出调用；程序验证工具白名单、字段、类型、取值，再依据登录身份和真实状态检查权限。
    3. 对需要确认的动作展示真实对象和参数，由独立确认渠道授予本次授权。
    4. 执行后按调用标识回传成功、失败、取消或状态未知；模型据此解释，不得补造成功。

    JSON 可解析、Schema 合法、业务语义正确、动作得到授权是不同层。即使结构化输出限制了字段，也不能代替服务端检查。模型写 approved=true 不产生批准；同样，随机调用 ID 不自动提供业务幂等。

    一个可运行的边界示例

    下面仅模拟一项工具提议和回执，不调用真实模型、不写文件、不演示完整身份系统。确认值由程序调用方提供，而不是从模型参数取得；实际产品应将确认绑定到用户、对象、动作、参数及有效期。用 Python 3 标准库运行：

    import json


def save_plan_proposal(proposal, *, confirmed):
    if not isinstance(proposal, dict) or set(proposal) != {"name", "arguments"}:
        raise ValueError("invalid proposal fields")
    if proposal["name"] != "save_plan":
        raise ValueError("unknown tool")
    args = proposal["arguments"]
    if not isinstance(args, dict) or set(args) != {"chapter", "minutes"}:
        raise ValueError("invalid argument fields")
    # bool 在 Python 中是 int 的子类；这里必须拒绝 True 冒充时长。
    if type(args["minutes"]) is not int or not 1 <= args["minutes"] <= 120:
        raise ValueError("minutes must be an integer in 1..120")
    if type(args["chapter"]) is not str or not args["chapter"].strip():
        raise ValueError("chapter is required")
    if confirmed is not True:
        return {"status": "cancelled", "executed": False}
    # 教学模拟：实际写入需使用业务幂等键、事务及真实回执。
    return {"status": "simulated", "executed": False, "validated": args}


proposal = {"name": "save_plan", "arguments": {"chapter": "chapter-2", "minutes": 40}}
print(json.dumps(save_plan_proposal(proposal, confirmed=False), sort_keys=True))
proposal["arguments"]["minutes"] = True
try:
    save_plan_proposal(proposal, confirmed=True)
except ValueError as error:
    print(str(error))

    预期输出为 {"executed": false, "status": "cancelled"}，下一行是 minutes must be an integer in 1..120。这证明取消和类型边界能被程序检查，不证明真实模型会选择正确工具，更不证明已保存计划。

    失败后要查哪一层

    故障 动作 不能做什么
    未知工具、非法参数或鉴权失败 拒绝，解释可修正条件 原样无限重试
    临时限流、连接故障 确认可重放后有限退避 忽略 SDK 自带重试和总预算
    截断、拒答或字段不完整 保留原响应与结束状态，修复或停止 将缺字段补成“成功”
    保存请求超时 查询实际状态、幂等记录或回执 把未知当失败再创建一遍
    已保存，后续总结失败 恢复说明环节 再执行已完成的保存

    有依赖的动作串行执行；独立只读动作才适合并行。代码生成、模型输出都不是可信代码，参数不能 eval；需要执行生成代码时用受限运行环境。

    记忆：先保存哪些事实，再决定怎样取回

    对话记录、有效上下文、KV 缓存与应用长期记忆不同。滑窗保留近期原文但丢掉早期条件；摘要节省长度却可能漏例外；摘要加近期原文适合一些对话；实体或结构化字段适合日期、身份和状态，但也需来源、适用范围及修改机制。没有一种策略在所有任务下“最实用”。

    例如“今晚只有 90 分钟”是本次条件，“平时连续学习不超过 45 分钟”需用户确认后才能作为长期偏好。摘要不能把未验证方案升级为已确认事实。保存成功也不意味着每轮都已取回；发生遗忘时沿“原文→保存→检索→输入→答案”定位。

    容量规划要包含指令、历史、证据、工具定义、结果和输出余量；长工具日志先保留完整记录，再将与任务相关的部分送入模型。前缀缓存复用计算，不补回未提供的信息，也不把命中 Token 从上下文窗口中扣除。

    服务化：把模型服务和业务责任拆开

    MaaS（模型即服务）API、自部署开放权重模型或混合路线，都需检查数据留存、鉴权、限流、故障与成本。不要根据某个“6B 模型一张 24GB 卡可微调”的锚点直接配置：权重载荷、KV、中间激活、梯度和优化器状态取决于精度、训练方法、序列与批量。

    模型服务负责推理；业务层负责身份、权限、数据读取、校验与事务；网关可以负责限流、熔断和追踪。是否使用 FastAPI、Java 或某个编排框架是实现选择，不是可靠性证明。

    先完成模型加载、健康与必要预热，再声明服务可就绪；懒加载只把耗时推到首次请求，可能导致首请求超时或并发重复加载。流式响应能更早展示内容，一个传输事件不保证一个 Token；在终止前取消或断开应留下明确状态，不能先把半成品当最终结果保存。

    指标分开看首字延迟、完整请求时间、吞吐、失败率和总任务费用。低温度、种子和版本固定有助于复现，但不是跨后端的绝对保证；应用需要可审计结果时保存该次输出及来源，而不是承诺下一次完全相同。

    从修改代码走到可验证交付

    下面把开发现场接回笔记助手。开发 Agent 的登录、权限和额度不同于应用运行时的模型 Key；应用离线也不说明开发工具不联网。顺序是确认行为→限定修改→建立预期→实施→独立检查→交付，而不是装完框架就进入生产。

    一次任务怎样才算完成

    "页面多了统计、Agent 说完成"不等于完成。完成需要三件事同时成立：结果符合事先约定的行为；修改范围可解释（没换模型、没改依赖、没动数据库结构）；验证证据可复查（真实命令与退出码，不是转述）。笔记助手还需要核验卡片内容是否忠实于原文，以及保存是否得到真实回执；开发检查和应用评测不能互相替代。

    需求、规格与验收案例

    分三层：用户需求（为什么做）、行为规格（操作后应发生什么）、实现方案（代码怎么做）。"加个 SQL 查询"是实现线索，"更智能"是愿望，都不能代替规格。写规格的关键动作：

    • 先读项目事实再设计（如：历史属于当前浏览器会话、ready 状态也有问题文本），不让 AI 从想象出发。
    • 先回答最影响结果的 5 个决定（搜什么字段/谁的记录/怎样匹配/返回多少与排序/空与错误怎么办），每个选择连带改变文案、案例与实现。
    • 把含糊词收紧到"实现者不用猜"：输入长度在大小写归一化前检查、casefold 连续子串匹配、%/_ 按字面处理、先过滤后限量（不是先取最近 50 条再匹配——这条错误捷径会漏掉最旧的命中）。
    • 用反例检验规格：51 条记录中只有最旧一条命中，是区分"先限量后匹配"与"先匹配后限量"的最小案例。验收案例用"给定—当—应"格式（Gherkin 思路），规则编号（R1—R7）便于定位偏离。

    Git 检查点：让每次修改可比较、可撤回

    工作区/暂存区/提交三层分开："文件已保存"≠"版本已提交"，提交也不代表测试通过。AI 开发中的实操要点：任务开始前确认干净或归属明确的起点；有选择地暂存（git add <file> / add -p），不把多个任务捆成一包；restore --staged 只取消暂存，restore --source=HEAD --worktree 才覆盖工作区；已提交错误用 revert 留下修正记录（历史保留可审计），而不是改写历史。让 Agent 操作 Git 时按项目授权决定是否可提交；先核对真实 diff，选择性暂存，不把“可以改代码”扩展成“可以推送或发布”。

    任务拆分与架构边界

    拆分单位是"可检查的交付结果"而非时间片：A 存储查询（固定案例得到约定 ID）→ B 网页接线（HTTP 状态码与转义）→ C 集成回归（新旧功能共存）。架构从真实请求路径出发分层（路由取会话身份 → 存储方法隔离 owner 并匹配 → 模板展示），不为"看起来分层完整"提前加目录。接口约定要区分可协商部分（函数名、返回结构）与不可协商部分（行为规则：只搜问题、当前会话、先匹配再限制）。非法输入与"合法但无结果"必须区分（前者报错，后者返回空列表），否则用户无法知道该怎样修正。

    项目文档分层：约定 / 状态 / 任务

    四类信息分开存放：长期约定（AGENTS.md：入口、易破坏边界、工作方式、验证与交付要求）、当前状态（STATUS.md：做到哪了、验证范围、带日期与命令）、本次任务（任务卡）、行为规格（specs/）。判断标准："下一轮换一个任务，这句话还应该原样成立吗？"——是则入长期约定，否则入状态或任务。AGENTS.md 是上下文参考，不会把"不要越权"变成访问控制，也不能自动证明测试执行过。验收方式是让新会话做理解检查（应用用什么模型？搜索是否已实现？验证命令是什么？本轮允许改什么？），每个回答给出文件路径或函数依据。

    上下文工程：按问题逐层展开

    上下文是模型处理当前任务时能利用的信息（要求、项目指令、已加载文件、对话历史、工具返回），仓库是来源，实际提供的内容才是输入。按缺口选资料：先读现行契约与完整调用路径上的函数（不只是命中行——过滤条件可能在上面、截断在下面），需要时再读测试夹具。冲突资料按类型裁决：规格定义应有行为、源码描述当前实现、测试输出证明某次执行、历史原稿记录当时状态——不能简单按"最新日期"选。会话压缩（/compact）是对历史的整理，不能代替核对源文件；压缩提示应显式保留关键函数、案例编号和未验证范围。

    测试与反馈：独立预期先于实现

    预期从已确认规则和可数清的输入推导（0 条/恰好 50 条/51 条全命中/51 条中仅最旧命中四情形），不从被测函数输出反推——AI 同时写实现和测试时会在两边重复同一误解。测试名字不决定覆盖层次：unittest 框架 ≠ 单元测试，要看它真实调用什么（存储层用临时 SQLite、HTTP 层经测试客户端走会话与模板）。错误注入验证断言辨别力：把已知错误（先取 50 条再匹配）临时替换进被测函数，恰好两项指定 FAIL 才说明断言有效；Ran 0 tests 后的 OK 与 FAIL/ERROR 的区别都要核对。给 AI 的失败反馈要包含：脚本、失败项、输入、预期、实际、相关规则——比"又报错了，帮我修"多提供可判断的事实。

    调试与代码审查：从复现到最小修复

    稳定复现 → 比较相邻层（存储层通过、HTTP 层失败说明差异在连接处）→ 提出可检验假设 → 最小修复（每处修改有证据和任务理由）→ 先重跑失败项再跑相邻检查 → 审查真实 diff（含孤立修改行周围的上下文完整性）。不能接受的方向：改测试预期迎合错误；在展示层隐藏症状；把搜索无结果"升级"为模型语义理解（那是新需求）。审查报告回答：触发条件、为什么这行能解决、有没有改测试预期、有没有绕过身份检查、残留调试输出、未验证范围。

    AI 应用评测：代码正确 ≠ 回答可靠

    把一次回答拆成四层分别检查：检索（必要证据进入所选上下文了吗）、机械检查（格式/ID/引文位置）、语义忠实（事实断言得到资料支持吗——引用 14 天原文却回答 30 天，机械检查全部通过）、缺失判断（证据不足时承认不足了吗；已给足证据却过度拒答同样不合格）。要点：标准证据由人先读原文标注，不从候选答案倒推；"资料有答案、资料相关、资料足够"是三个不同判断；评审者能读全文而生成器只看到选中片段，二者结论可能都合理；机械指标的分母要分层（无标准证据的题不进覆盖率分母）；修改候选答案做对照实验可以验证评测工具能力边界，但不能冒充真实模型改进；保留未参与调参的题检查是否只对熟悉案例奏效。

    日志、追踪与成本

    用 operation_id / trace_id / span_id / parent_span_id 四种 ID 关联一次执行（业务 ID 与执行 ID 分开）。失败从最后一步往前找证据：校验步骤 failed 说明问题在内容层而不是检索或网络；没有 model 步骤不要说成"模型拒答"；有开始没有结束保留"不完整"状态，不能补成功。成本从逐次尝试算：校验失败不会让已生成的 Token 变成"从没消耗过"；usage 未知记 null 不记 0（把"没有证据"改成"确定没花钱"是系统性误导）；已知小计与未知次数一起展示；多次尝试看逐次 attempt，顶层 usage 只代表最后一次。开发工具额度与应用模型费用分开记账；timestamp 写时区，耗时写测量范围（本地步骤耗时不代表服务端响应，更不是端到端）。

    开发权限与应用权限分别检查

    笔记助手的提议、确认和回执流程见前面的“工具调用”。开发现场还要单独限定可读资料、可写路径和可执行命令；允许 CLI 改代码，不等于允许它把私有笔记发往外部服务。应用授权也只覆盖确认的那项操作，后续对话不能悄悄扩大对象或范围。

    Skill / 脚本 / MCP 分层

    确定的数据转换交给脚本（JSON 卡片转 Markdown，输出字节确定、可 diff）；何时做、怎样查、失败怎么办写进 Skill（可保存、可审查、失败条件随操作复用）；跨助手共享服务访问才考虑 MCP。组合不是必需：本地脚本能解决的事不因包一层协议更可靠。改哪一层的判断：输出格式变 → 改脚本与验证；交付提醒变 → 改 Skill；出现跨进程共享需求 → 改 MCP 接口。MCP 工具用逻辑 ID 而非任意路径（避免"读一份资料"扩大成"读服务器能访问的任何文件"）；输入 schema 是契约，服务端仍必须实施校验与权限检查。

    应用侧的运行环境与有限循环

    对笔记助手，Harness 至少要提供真实输入、受限动作、独立校验和可追溯回执；机械检查通过后，语义仍存疑的卡片进入 needs_review，不直接当作可靠答案。继续前先查预算，并用上轮失败证据改变候选；同候选同错误再现、越权或状态未知时停止或转交处理。任务级契约、失败签名、锁和恢复机制集中在 Coding Agent 的 Harness 与 Loop，本篇不另列一套循环部件。

    断点续做与多 Agent

    三类"接着干"不同：恢复聊天会话（找回讨论）≠ 恢复开发工作（面对代码版本与未提交修改）≠ 恢复程序执行（面对持久状态、实际产物与外部回执）。接手顺序：先确认旧进程已结束 → 只读检查现场（指纹、任务归属、产物完整性）→ 产物完整则只补核验并另存新记录（旧 interrupted 状态保留，不伪造成功历史）→ 证据不完整则交人。幂等不是命令名：读文件可重复，写动作需要业务操作 ID、唯一约束或事务支持。多 Agent 先画依赖再定人数：可并行的是共享只读输入上的独立检查；同时改同一文件、上下游字段联动都应串行或先定接口。每个工作项有明确可写目录与交付接口（result.json 含身份、指纹、命令、退出码）；两个助手结论一致不构成事实验证（可能读了同一份过时规格）；多数投票不是验证。

    交付与回滚

    交付三对象：代码与静态文件（版本标识、清单、指纹）、环境与配置（实测版本、兼容范围）、持续变化的数据（位置、备份与恢复办法）。候选构建要在展开后的包内运行检查（消除"测试对象 ≠ 交付对象"空隙），正常结束仍是 candidate，published: false 是明确字段。回滚演练的关键认知：代码回退 ≠ 数据恢复——切回旧代码时不覆盖当前数据（保留升级期间新增记录），备份验证用副本预览（暴露备份的时间边界）；数据版本不兼容时旧代码应拒绝打开，而不是改版本号强行启动。源码白名单不是秘密扫描器，写进白名单文件的密码照样会被打包。
