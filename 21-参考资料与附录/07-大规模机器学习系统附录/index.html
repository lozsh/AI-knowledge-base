    大规模机器学习系统附录：D·A·M、C³ 与集群基础

    来源：《大规模机器学习系统》（ML Systems at Scale，Vijay Janapa Reddi 著）附录 A"D·A·M 基础"、附录 B"C³ 分类法"、附录 C"集群基础"，更新于 2026-11-03。

    本页是《大规模机器学习系统》三个附录的提炼速查：附录 A 复习单节点 D·A·M 诊断，附录 B 定义集群级 C³（计算·通信·协调）诊断框架，附录 C 汇集集群工程应随身携带的参考数字与物理定律。注意：原文档在 C.3.3"通信-计算比"公式处截断，其后内容缺失；完整内容见原书。

    附录 A：D·A·M 基础（单节点诊断基线）

    D·A·M = 数据（Data）·算法（Algorithm）·机器（Machine），单节点性能诊断框架。C³ 是它向集群的扩展，但必须建立在坚实的单节点基础之上。

    A.1 维度参考

    维度 作用 物理约束 高杠杆优化
    数据（D） 信息（燃料） 带宽 BW I/O 管道优化
    算法（A） 逻辑（蓝图） 运算量 O 模型压缩
    机器（M） 物理（引擎） 吞吐 R_peak 硬件加速

    A.2 铁律与重叠

    铁律：𝑇 = 𝐷_vol/BW + 𝑂/(𝑅peak·𝜂hw) + 𝐿lat。协同设计把加法变取最大值：预取、CUDA 流、异步梯度同步、双缓冲分别让 D/M 或 M/A 重叠，将 𝑇 = a+b 变为 max(a,b)——两项平衡时延迟近似减半；严重失衡时重叠收益可忽略。延迟项 𝐿lat 通常不可重叠，只有内核融合能消除它。

    A.3 算术强度与快速筛查

    • GPU 利用率 < 80%：筛查数据/CPU/启动饥饿（看数据加载等待、CPU 饱和度、内存带宽计数器、时间线间隙）。
    • GPU 利用率 > 95%：仅当内存带宽未饱和才是机器受限。
    • 批大小为 1：LLM 解码批 1 通常受内存带宽限制，除非时间线显示调度间隙。
    • 算术强度低于脊点（H100 上约 295.2 FLOP/byte = 989 TFLOP/s ÷ 3.35 TB/s）：内存受限。

    A.4 诊断表与记分卡

    状态 主导项 有效优化 浪费的优化
    内存受限 𝐷_vol/BW 量化、剪枝、批处理、内核融合、更高内存带宽 仅加峰值 FLOP/s
    计算受限 𝑂/(𝑅peak·𝜂hw) 更好内核、张量核心、更快 GPU、低精度 更多内存带宽
    延迟受限 𝐿lat 请求批处理、内核融合、异步调度 计算与带宽都无效

    工具图：数据 → tqdm/iotop/dstat；算法 → PyTorch Profiler/DeepSpeed Flops Profiler；机器 → nvidia-smi/Nsight Compute、Nsight Systems。

    维度 指标 不合格 合格
    数据 I/O 开销（等待/总步时间） > 10% < 1%
    算法 压缩/稀疏性（有效参数比） 工作负载相关 工作负载相关
    机器 MFU < 30% > 50%

    附录 B：C³ 分类法（集群级诊断）

    C³ 不取代 D·A·M，而是扩展它。映射关系中最重要的一行：单机上可忽略的开销项 𝐿lat，在集群规模升级为独立的协调（Coordination）轴——检查点、故障恢复、流水线气泡与调度在 10K+ GPU 上可消耗 40% 以上墙钟时间。

    B.1 D·A·M → C³ 映射

    单机维度 C³ 对应 集群规模的变化
    数据（D） 通信（C²） 数据跨网络移动，不只走内存层次
    算法（A） 计算（C¹） 每 GPU MFU 仍重要，但被缩放效率侵蚀
    机器（M） 计算（C¹） 集群峰值 = N×单卡峰值，但复合损失降低有效 FLOP/s
    （无等价物） 协调（C³） 新轴：屏障、检查点、故障恢复、调度

    B.2 集群定律

    𝑇step(N) = 𝑇compute/N + 𝑇comm(N) + 𝑇sync(N) − 𝑇overlap

    • 𝑇compute/N：前向、反向、优化器步（受 MFU 支配；优化靠内核、混合精度、算子融合）。
    • 𝑇comm(N)：AllReduce/AllGather/激活传输（受带宽与集合算法支配；优化靠梯度压缩、分层集合、重叠）。
    • 𝑇sync(N)：屏障、检查点、故障检测恢复、气泡、抢占维护（受可靠性支配；优化靠异步检查点、弹性训练、更快故障检测）。
    • 𝑓_compute = (𝑇compute/N)/𝑇step(N)：低于 0.5 时集群把更多时间花在通信与协调上，而非有用算术。

    B.3 三个交叉点

    • 计算∩通信：看通信-计算比 ρ = 𝑇comm(N)/(𝑇compute/N)。ρ<1 计算受限且健康（可重叠）；ρ>1 通信受限。工程重点是重叠策略：反向传播期间发起 AllReduce、CUDA 流流水线化、加大微批次/梯度累积。
    • 通信∩协调：每个 AllReduce 既是传输又是同步屏障——掉队者把通信操作变成协调瓶颈。工程重点：异步梯度、分层 AllReduce、掉队者检测与主动缓解。
    • 计算∩协调：流水线气泡、阻塞式检查点写入、故障回滚重算——协调开销变成浪费的计算容量。工程重点：增加微批次缩小气泡分数、异步检查点、限制故障爆炸半径。

    B.4 C³ 红绿灯（快速分诊阈值）

    维度 绿色（健康） 黄色（调查） 红色（瓶颈）
    计算 MFU > 50% 30%–50% < 30%
    通信 通信分数 < 20% 20%–40% > 40%
    协调 有效吞吐比 > 90% 75%–90% < 75%
    集群状态 有效优化 浪费的优化
    计算受限 更好内核、混合精度、算子融合、下一代加速器 加网络带宽
    通信受限 梯度压缩、重叠、分层集合、InfiniBand 升级 加 GPU（只会更快地空等网络）
    协调受限 异步检查点、弹性训练、更快故障检测 加 GPU 或加带宽（时间耗在开销上）

    B.5 三个经典案例

    1. 利用不足的集群（计算）：4,096 块 H100，MFU 仅 15%，通信占比 < 10%。修复：激活 BF16/FP8 张量核心（常见罪魁是归一化层/损失计算的 FP32 回退）、torch.compile 算子融合、加大批大小。MFU 15%→50% = 3.3× 有用工作，等于不加卡扩容三倍。
    2. 通信墙（通信）：512 卡数据并行，单卡内核 MFU 45% 但全步墙钟 MFU 20.2%（AllReduce 占步时间 55%），64→512 卡仅 4× 加速（50% 缩放效率）。修复：计算-通信重叠、TopK 稀疏化/量化（降 10–100× 字节）、节点内 NVLink 分层集合（跨节点流量减 8×）。
    3. 协调税（协调）：10,000 卡，MFU 40%、通信仅 15% 都健康，但有效吞吐比仅 60%——40% 墙钟耗于故障恢复（约每 5 小时一次 GPU 故障）、气泡、检查点、调度器抢占与维护。修复：异步检查点、弹性训练（缩容续跑而非全停）、交错 1F1B 流水线调度、心跳超时 30s→5s。

    B.6 C³ 记分卡与有效 FLOP/s

    维度 指标 定义 不合格 合格
    计算 MFU O_step/(N·R_peak,device × T_step) < 30% > 50%
    通信 缩放效率 η_scaling T₁/(N × T_N) < 35% > 70%
    协调 有效吞吐比（Goodput） T_useful/T_wall < 75% > 90%

    有效 FLOP/s = 峰值 × MFU × 缩放效率 × 有效吞吐比——三个 C³ 损失相乘。

    系统视角（100,000 GPU H100 集群）：峰值 98,900 PFLOP/s × 0.50 × 0.35 × 0.60 ≈ 10,384 PFLOP/s，只交付峰值容量约 10.5% 作为有用训练工作。C³ 税 ≈ 9.5×：实现给定有效算力需要 9.5 倍原始硬件。这不是工程失败，是集群级计算的物理——C³ 分类法定量化损失发生的位置，让优化对准主导项。

    附录 C：集群基础（参考数字与物理定律）

    C.1 三个系统范式

    维度 HPC（超级计算机） WSC（Web 云） ML 集群
    哲学 最大化 FLOP/s 最大化 QPS 最大化每美元/瓦特的模型质量
    耦合 紧（MPI） 松（RPC/HTTP） 混合（NCCL + RPC）
    状态 有状态（RAM） 无状态（DB 支撑） 半有状态（检查点 + KV 缓存）
    网络 延迟优化 带宽优化 二分带宽关键
    瓶颈 计算吞吐 I/O 内存带宽（HBM）
    故障模型 检查点/重启 冗余/副本 弹性缩小/扩大
    调度 批次（Slurm） 编排（K8s） 帮派分配 + 抢占
    节点模型 宠物 牛 作业期间宠物，作业间牛

    ML 集群是混合体：训练像 HPC 一样同步且带宽饥渴，但像 WSC 一样长时间运行且必须容错；推理像 WSC 一样延迟敏感，但像 HPC 一样计算密集。把它当"纯 HPC"设计将不容忍故障；当"纯 Web 服务"设计将无法维持紧耦合同步。

    C.2 基础公式复习

    • 铁律（集群版）：数据移动项扩展为节点间通信，不止内存带宽。
    • 屋顶线：算术强度区分计算/内存受限；集群级出现第三层天花板——网络受限。
    • 阿姆达尔定律：集群级"串行分数"不仅包括顺序代码，还包括同步屏障、集合通信和流水线气泡。10% 串行开销就把加速上限钉在 10×——无论加多少硬件。出路是弱缩放（放大问题规模）。
    • 训练状态规则：混合精度 Adam 检查点状态约 14 字节/参数（2B BF16 权重 + 12B FP32 主权重和动量方差）。
    • 利特尔定律：Q_req = λ_arr × T_lat，决定负载均衡器后需要多少服务副本。

    C.3 最重要的三个集群数字

    1. 带宽差距：节点内 NVLink 每方向带宽比节点间 InfiniBand NDR 端口快约 9×。该比例决定并行边界——模型并行在节点内，数据并行跨节点。
    2. MTBF 缩放：集群 MTBF = 单组件 MTTF ÷ 组件数。100,000 块 GPU 时约 每 30 分钟一次故障。
    3. 有效利用率：经 MFU、缩放效率与开销损失复合后，1,024 卡集群交付约 19.2% 峰值 FLOP/s 作为有用工作。

    C.4 通信数字

    带宽层次（每方向）：NVLink 4.0 450 GB/s、TPU v5p ICI 1,200 GB/s、PCIe Gen5 x16 64 GB/s、IB GXDR 200 GB/s、IB XDR 100 GB/s、IB NDR 50 GB/s、IB HDR 25 GB/s、RoCE v2 12.5 GB/s。

    延迟层次（单向）：IB NDR ~5 μs、IB HDR ~7 μs、RoCE v2 ~10 μs、TCP/IP 以太网 ~50 μs（对同步训练太慢）、跨数据中心 ~40 ms（物理下限，仅异步训练）。小消息集合操作瓶颈是延迟而非带宽。

    C.5 计算与协调数字

    缩放效率（优化良好的数据并行）：

    集群规模 η_scaling
    32 GPU ~90%
    256 GPU ~70%
    1,024 GPU ~50%
    8,192 GPU ~35%

    MTBF 与 24 小时故障概率（每卡 MTTF 5 万小时 ≈ 5.7 年；Pr(≥1 故障) = 1 − e^(−T/MTBF)）：

    集群规模 仅 GPU MTBF 24h 内至少一次故障
    256 GPU 195.3 h 11.6%
    2,048 GPU 24.4 h 62.6%
    8,192 GPU 6.1 h 98%
    100,000 GPU 0.5 h ≈100%

    8,192 卡及以上，故障不再是边缘情况——容错是完成任何长时训练的前提。真实集群还有 NIC、电源、电缆、交换机故障，以上估计偏保守。

    检查点大小（14 B/参数，100 GB/s 存储带宽）：7B → 98 GB / 0.98s；70B → 980 GB / 9.8s；175B → 2,450 GB / 24.5s；1T → 14 TB / 2.3 min。

    开销预算（墙钟时间分数）：流水线气泡 ~5%、检查点 ~3%、故障恢复 ~10%、维护窗口 ~5% → 总有效吞吐比 ≈ 77%。在 10,000+ 卡上故障恢复占主导。

    C.6 功率与可持续性数字

    • 传统机架 12 kW；AI 机架 70 kW（需液冷）至 100 kW（直接芯片液冷）；空气冷却上限约 30 kW/机架。
    • PUE：液冷 AI 约 1.06（最佳）、最佳风冷约 1.12、行业平均约 1.40。
    • 经验法则：IT 负载(MW) = GPU 数 × 单卡 TDP ÷ 10⁶；设施负载 = IT 负载 × PUE。10,000 块 H100（700 W）= 7 MW IT ≈ 9.8 MW 设施负载（PUE 1.40）。

    C.8 缩放物理

    • 单加速器屋顶线：𝐼 = FLOPs/移动字节数；𝑅_attain = min(𝑅peak, 𝐼×BW)；脊点 𝐼_ridge = 𝑅peak/BW（H100 BF16 约 295.2 FLOP/byte）。自回归解码强度约 1 FLOP/byte，单流吞吐 ≈ 208.6 tokens/s——纯粹受带宽限制，批处理正是为了提高强度把解码推回计算屋顶。
    • 集群阿姆达尔：串行分数含 AllReduce 同步、流水线气泡、检查点写入、Python 级单线程操作。
    • 通信-计算比：ρ = 𝑇comm(N)/(𝑇compute/N)，决定通信能否隐藏在计算后面。（原文自此公式处截断，后续内容缺失。）
