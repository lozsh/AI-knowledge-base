    特征工程与 Embedding

    更新于 2026-11-03

    一句话概括：特征工程负责把用户/物品/场景信息变成模型可消化的数值向量（保留有用信息、剔除冗余），Embedding 是其中最高阶的手段——既是稀疏特征的救星，又能融合序列、图结构等高阶信息生成特征。

    核心概念

    • 特征的定义：对某个行为过程相关信息的抽象表达。抽象必有信息损失（存储限制 + 冗余信息会损害泛化），因此原则是：在可获得的数据上，尽量保留有用信息，摒弃冗余信息。
    • 五大类常用特征：
    • 用户行为数据：显性反馈（评分/点赞）与隐性反馈（点击/观看/购买）。隐性反馈因数据量大、更接近模型目标，是深度学习时代特征挖掘的重点。
    • 用户关系数据：强关系（关注/好友）与弱关系（互赞/同社区/同看一部电影）。可用于召回方式、构建关系图做 Graph Embedding、给用户加"好友特征"。
    • 属性、标签类数据：直接描述用户/物品，来自人工体系（如商品分类）或社交化添加（如豆瓣标签）。典型处理：Multi-hot 编码；进阶做法是纳入知识图谱做 Graph Embedding/GNN。
    • 内容类数据：大段文字/图片/视频，需先经 NLP（关键词、主题、分类）或 CV（目标检测）抽取关键要素，再按标签类特征处理。
    • 场景/上下文信息：时间、地点、推荐页面、季节、天气、是否节假日等。广义上"任何影响用户决定的因素"都是场景特征，实践中多用易获取的时间/地点/页面。
    • 特征处理的总目标：一切特征最终转为数值型向量；类别/ID 型与数值型两大类的处理路径不同。
    • Embedding：用一个数值向量"表示"一个对象，向量间距离反映对象相似性，向量运算甚至能揭示对象间关系（king−man+woman≈queen）。
    • Embedding 重要的两个原因：① 处理稀疏特征的利器——One-hot 高维稀疏向量不利于深度网络，Embedding 层将其转为稠密低维向量，几乎所有深度推荐模型标配；② 本身就是融合大量信息的特征向量——尤其是 Graph Embedding 之后，几乎可引入任何信息编码。

    关键方法/原理

    类别/ID 型特征处理

    • One-hot 编码：类别对应维度置 1 其余置 0。适用单个类别特征和 ID 特征。
    • Multi-hot 编码：一个物品多标签、用户历史行为序列（与多个物品交互）的自然延伸，多位置为 1。
    • 标签体系成熟的团队由专人维护（如电商商品分类体系）。

    数值型特征处理

    • 归一化：解决特征尺度差距（评价次数 0~10000 vs 平均评分 0~5），拉平到 [0,1]，防止大量级特征掩盖小量级特征的作用。Spark 用 MinMaxScaler。
    • 分桶（Bucketing）：解决分布不均（人们打分"中庸偏上"，评分挤在 3.5 附近，区分度低）。按特征值排序后按分位数切桶，用桶 ID 作特征。Spark 用 QuantileDiscretizer。连续特征的非线性变换（平方、开方、log）也属同类手段——YouTube 把样本年龄的平方也作为输入特征。
    • 统计型特征：对行为数据 groupBy + 聚合（count/avg/stddev）得到物品/用户的统计特征（评分均值、标准差、好评风格等）。

    训练样本处理的关键原则

    • 标签转换：拿不到评分时把行为转 CTR 二分类（如 MovieLens 中评分 ≥3.5 标 1、<3.5 标 0），把推荐问题转为 CTR 预估。
    • 警惕"未来信息"（特征穿越/泄漏）：t 时刻样本的特征不能包含 t+1 的信息。例：用户 11/1 评 3 分、11/2 评 4 分、11/3 评 5 分，则 11/2 样本的"用户历史平均评分"只能是 3 分（该用户自身当次的评分是预测目标也不能加进去）。工程解法：Spark window 函数 over(partitionBy(userId).orderBy(timestamp).rowsBetween(-100,-1))，只对当前样本之前的滑动窗口聚合。
    • 平台分工原则：让合适的平台做合适的事——Spark 管海量数据的清洗/特征/样本，Flink 管流处理，TensorFlow 管模型；TF 不擅长分布式并行数据处理。
    • 特征取舍：不人为预设特征有用与否，先加进去让模型判断，无效再剔除。
    • 线上特征存储：用户/物品特征分别以 hash（hset）形式存 Redis，key 为 userId/itemId，线上拼接成特征向量供模型推断，保证线上线下特征一致性。

    Word2vec → Item2vec

    • Word2vec（Google 2013）：把词映射为向量的模型，是深度学习时代 Embedding 技术的奠基者。两个结构：
    • CBOW：用周边词预测中心词；
    • Skip-gram：用中心词预测周边词（经验上效果更好）。
    • 样本生成：语料取长度 2c+1 的滑动窗口滑过句子，窗口内词组即样本。
    • 结构：三层神经网络。输入为 One-hot（V 维），隐层 N 维且无激活函数，输出层 softmax（V 维多分类）。词向量 = 输入层到隐层权重矩阵 W(V×N) 的行向量，可转成 Lookup Table 存线上库。为加速训练用负采样（Negative Sampling）或层次 softmax（Hierarchical Softmax）替代全量 softmax。
    • Item2vec（Microsoft 2015）：Word2vec 在任意序列数据上的推广——用户的购买序列、观看序列当"句子"喂进去，得到物品 Embedding。"万物皆 Embedding"由此成为可能；物品向量可直接算相似度或作为特征输入模型。

    Graph Embedding

    • 图结构数据的来源：社交网络、知识图谱、行为关系二部图（用户-物品交互，几乎存在于所有应用）。
    • Deep Walk（2014）：用户行为序列 → 构建物品关系图（行为先后生成有向边，重复边加权）→ 随机游走重新产生物品序列（跳转概率 = 边权重占出边权重和的比例）→ 序列喂 Word2vec → 物品 Embedding。是序列 Embedding 到图 Embedding 的过渡桥梁；随机游走还能起到降噪作用（生成比原样本更少、更精的序列往往效果更好）。
    • Node2vec（2016，斯坦福）：在跳转概率中引入参数 p、q，让 Embedding 在同质性与结构性间权衡：
    • 同质性（Homophily）：距离相近的节点 Embedding 相近（电商中同品类、常一起购买的物品）→ 游走倾向 DFS（q 越小越倾向游走到远方）；
    • 结构性（Structural Equivalence）：结构角色相似的节点 Embedding 相近（各品类爆款、凑单商品等结构属性相似的物品）→ 游走倾向 BFS（p 越小越倾向返回，微观扫描局部结构）。
    • 两种偏置的 Embedding 可以同时输入模型，保留不同图特征。
    • EGES（阿里）：在图 Embedding 中加入物品的 side information（类目、店铺、品牌等属性边），缓解冷启动并融合属性信息。

    Embedding 的三种应用方式

    1. 直接应用：用向量相似性做相似物品推荐、猜你喜欢、召回层。
    2. 预训练应用：预先训练好 Embedding，作为特征向量与其他特征拼接输入模型。优点：解耦、快、可复用、易线上服务（查库即用）；缺点：与目标函数脱节，上游重训后各维含义变化需下游重训。
    3. End2End 应用：Embedding 层与推荐模型一起端到端训练（Deep Crossing、FNN、Wide&Deep 等）。精度潜力更高，但训练慢、Embedding 难复用，新物品需扩词表重训。

    Embedding 最近邻搜索（召回的速度问题）

    • 全量遍历计算一个用户与 n 个物品向量的相似度复杂度 O(k×n)，百万千万级物品线上不可接受；问题等价于高维空间最近邻搜索（前提：用户/物品 Embedding 在同一向量空间）。
    • 聚类方案（K-means）：离线聚类、线上类内搜索。缺陷：边缘点最近邻可能落在相邻类；中心点数 k 难定。
    • 索引方案（Kd-tree）：空间切分索引。同样无法完全解决边缘点问题，结构复杂、维护成本高。
    • 局部敏感哈希 LSH：核心性质——高维点映射到低维，原本相近的点必然仍相近，原本远离的点有一定概率变得相近。用随机向量 x 与 Embedding 做内积 h(v)=v·x 映射到一维，按 \(\left\lfloor (v \cdot x + b)/w \right\rfloor\) 分桶（w 为桶宽，b 为 0~w 均匀随机数避免边界固化）。
    • 多桶策略：用 m 个哈希函数分桶。
    • "且"（AND）：同时落入 m 个桶才算候选——候选集小、效率高，但漏掉最近邻概率增大；
    • "或"（OR）：任一桶相同即候选——召回率高，后续计算开销大。
    • 调参经验：点数越多桶数越多；向量维度越大哈希函数越多、偏向"且"。
    • 桶内规模控制在常数 C 时，最近邻查找 O(C·N)（多桶 O(K·C·N)），常数级。
    • 业界超大规模方案：Facebook 的 FAISS（IVF、PQ 等索引体系）。

    术语表

    术语 英文 含义
    特征工程 Feature Engineering 从用户/物品/场景信息中提取模型可用数值特征的过程
    One-hot / Multi-hot One-hot / Multi-hot Encoding 单类别置 1 / 多类别同时置 1 的稀疏编码

    经验与常见坑

    • 特征工程最容易犯的错是特征穿越：用全量数据生成统计特征再切样本，等于把未来塞给了过去。所有历史行为类特征必须按时间滑窗生成。
    • 归一化只解决尺度不解决分布；打分类数据普遍"中庸偏上"，分桶才能拉开区分度。
    • 类别/ID 特征直接用原始数值当特征值是错的（3 不代表比 1 大三倍的偏好），必须 One-hot/Multi-hot 或 Embedding。
    • Embedding 预训练 vs 端到端没有绝对优劣：预训练快、可复用、服务简单；端到端精度上限高。物品集动态变化（频繁上新）时端到端成本高，可用预训练+side information 兜底冷启动。
    • 线上线下特征不一致是隐形事故源：线下 Spark 生成、线上 Redis 读取的必须是同一套逻辑，最好共用特征管道。
    • Deep Walk 序列样本不是越多越好：随机游走生成的序列超过原始行为序列量级反而引入噪音，相似度质量下降。
    • 用户 ID 词表过大、长尾 ID 交互太少学不好 Embedding：可用 hash 共享向量、或用属性特征补足。
    • 场景特征（时间、地点）不可预存进用户 Embedding——外卖场景中午与晚上、公司与家的用户向量本应不同；这类特征要么实时进模型，要么做场景分桶预存。
    • 预训练的多模态向量（文本/图像）直接拼进排序模型常常无效：预训练目标与排序目标不一致，需在业务数据上微调或做特征交叉。

    ⚠️ 时效性说明

    • Spark MLlib 的 OneHotEncoderEstimator 已更名为 OneHotEncoder，API 以所用 Spark 版本为准；处理思路不变。
    • 向量检索生态已远超 LSH：FAISS 的 IVF/PQ/HNSW、各厂 ANN 服务（ScaNN、HNSW 库）在精度-速度权衡上普遍优于纯 LSH，但"分桶保留距离信息"的思想一脉相承。
    • Embedding 预训练→拼接的玩法在 LLM 时代延伸为语义向量（Sentence-BERT 等）做内容召回，原理同源，Item2vec 的"序列即语料"思想依然适用。
