    推荐系统架构与分层：召回-排序-重排¶

    /> 来源：公开课程资料自学整理（整理于 2026-11-03）

    一句话概括：工业级推荐系统的通用骨架是"离线/近线/在线"三层计算架构 + "召回-排序-重排"三段模型流水线，工程实现（存储、模型服务、实时性）占了一半以上的工作量。

    核心概念¶

    • 推荐系统要解决的根本问题：在"信息过载"情况下，用户如何高效获取感兴趣的信息。形式化定义：对用户 U（User），在场景 C（Context）下，对海量候选物品 I（Item）构建函数 f(U, I, C) 预测喜好程度并排序输出推荐列表。
    • 两大类预测问题：评分预测（显式反馈，回归问题，RMSE 衡量，Netflix Prize 兴起）与行为预测（隐式反馈，CTR 预估，二分类概率）。工业界以行为预测为主——隐式反馈更稠密、更真实、与线上目标直接挂钩，解决"80% 的问题"。
    • 模型流水线三层：
    • 召回层（候选集生成）：从百万级候选快速筛到几百级。规则简单、计算快，每种离线算法对应一路召回（协同过滤、热门、标签、Embedding 近邻等），多路并行后合并。
    • 排序层（精排）：用复杂模型对几百个候选精确打分（CTR 预估），是深度学习模型的主战场。
    • 重排/补充策略层：输出前兼顾多样性、流行度、新鲜度、业务规则（运营位、去重、类目打散）。
    • 计算架构三层（Netflix 经典架构）： | 层 | 数据 | 服务 | 典型任务 | |---|---|---|---| | 离线层 Offline | 不用实时数据 | 不提供实时服务 | 全量日志（HDFS/Hadoop）上的特征工程、模型训练、批量计算推荐结果 | | 近线层 Nearline | 用实时数据 | 不保证实时服务 | 消费实时事件队列做准实时计算（剔除已消费物品、小批量更新模型参数），结果写入在线库 | | 在线层 Online | 用实时数据 | 必须实时服务（ms 级） | 模型预测、过滤调权、重排、兜底降级 |
    • 深度学习对架构的革命：模型表达能力/拟合能力大幅增强（可模拟兴趣变迁甚至决策过程）；反向推动数据部分升级——数据要"量大、流快"（Spark 离线 + Flink 流处理）；Embedding 进召回层、深度模型进排序层、强化学习进模型更新。

    关键方法/原理¶

    信息流（Feed）架构¶

    • 数据模型三要素：用户（User）、内容（Activity，Atom 规范：Time/Actor/Verb/Object/Target/Title/Summary）、关系（Connection：From/To/Type/Affinity）。Activity 产生 Connection，Connection 又喂回 Activity。
    • 内容发布的推拉模式：
    • 拉模式（Fan-out-on-load）：用户刷新时实时聚合，实现简单、实时，但连接数大时复杂度爆炸、可用性差。
    • 推模式（Fan-out-on-write）：内容产生即写入每个受众的信息流存储区，读取快、可用性高，但写放大、冗余存储、非实时、解决不了新用户。
    • 实践：活跃用户用推、低活跃用户用拉、热门生产者缓存最新 N 条；或按亲密度概率决定推不推。中小型网络纯推即可。
    • 排序：先定目标（互动率/停留时长）再选模型；起步用线性模型 + 特征工程（用户/内容/上下文三类特征），成熟后上 CTR 模型。负样本采样比例是可调参数（经验约正:负 ≈ 2:3）。

    YouTube 两段式深度学习架构（业界标杆）¶

    • 候选集生成（召回）：Embedding MLP 结构，输出层是对全量视频 ID 的 softmax 多分类（预测"点哪个视频"而非"点不点"）。取最后层 ReLU 输出为用户 Embedding，softmax 的 m×n 参数矩阵各列为视频 Embedding（与 word2vec 词向量同理）；线上不做端到端推断，而是预存两类向量后做最近邻搜索（可用 LSH 加速），百万候选毫秒级出几百个。
    • 排序模型（精排）：同为 Embedding MLP，但输入含用户+物品组合特征（候选视频 Embedding、历史观看平均、语言、time since last watch、#previous impressions 等）；输出层用 Weighted LR，正样本权重设为观看时长，使模型学到的概率与观看时长成正比，直接对齐商业目标。排序模型因用户×物品特征组合过多、无物品 Embedding 可取，必须走 TensorFlow Serving 实时推断。
    • 经验结论："模型结构只占 YouTube 方案 30% 的价值，70% 在工程细节"。

    模型服务（Model Serving）四种方式¶

    1. 预存推荐结果/Embedding：离线算好存 Redis，线上直接取或算相似度。简单快，但无法引入线上场景特征、表达能力受限，适合小规模或冷启动/热榜。
    2. 预训练 Embedding + 轻量级线上模型：复杂网络离线训出 Embedding（如阿里 MIMN 的用户兴趣向量），线上用 LR/浅层 NN 拟合。隔离了离线复杂度与线上时延，业界常用。
    3. PMML：XML 通用模型描述协议（JPMML、MLeap），跨语言部署传统 ML 模型；表达力不足以支撑复杂深度网络。
    4. TensorFlow Serving：End2End 的深度模型服务，Docker 部署，HTTP/gRPC 提供推断；不支持非 TF 框架，线上性能需调优。

    线上存储选型¶

    • 离线产出三类数据：特征（量最大，更新不频繁）、模型（KV 对，更新频繁）、推荐结果/候选集（ID 列表）。
    • 特征两种形态：正排（按 user/item ID 查特征向量，拼训练样本用）→ 列式数据库（HBase/Cassandra）；倒排（按标签/特征查物品列表，召回用）→ KV 数据库（Redis/Memcached）。稠密向量（Embedding）可存文件 + 内存映射（MMAP）。
    • 相似度矩阵也属"模型"数据（用来加权历史行为）。相似表可存 Cassandra。
    • Redis 典型用途：消息队列（List）、优先队列/有序推荐列表（Sorted Set）、模型参数（KV）。ElasticSearch 可兼做"存储+计算"的第一版推荐引擎（已有搜索的系统复用最快）。
    • API 设计要点：按场景设计（/Recommend 猜你喜欢、/Relative 相关推荐、热榜），输入含 UserID/场景/推荐位/数量/翻页偏移；输出必须带 Recommend_id（曝光 ID），用于追踪效果和日志回采。

    高并发三件套¶

    • 负载均衡：多节点分摊 QPS（Nginx 常用），是高可用与可扩展的基础。
    • 缓存：缓存同一用户短时间的推荐结果、预缓存新用户模板列表等；成熟系统可挡掉 90% 以上请求。
    • 服务降级：流量洪峰/故障时抛弃复杂模型，退化为热门榜、缓存或内存中预置的兜底列表，"不开天窗"，防止雪崩。
    • 在线时延预算参考：整个推荐接口上限约 100ms（多路召回+去重 ~25ms、排序 ~45ms、业务规则+组装 ~15ms）。

    实时推荐三个层次¶

    1. 给得及时：服务实时响应（基本要求）。
    2. 用得及时：特征实时更新（新行为立刻进用户历史/特征，影响当前用户）。
    3. 改得及时：模型实时更新（增量更新相似度/模型参数，影响全局）。
    4. 手段：消息队列（Kafka）+ 流计算（Storm/Flink；Spark Streaming 实为小批量）。
    5. 以 ItemCF 为例的增量更新：相似度公式的分子（共同用户数）、分母（各自用户数）三部分都可增量维护。
    6. 效率优化四招：剪枝（Hoeffding 不等式判定物品对相似度已收敛即停更，低相似直接剔除）、加窗（只保留最近 K 次会话或 K 条行为）、采样（热点/活跃用户的数据流采样）、缓存（活跃用户行为、热门物品特征与相似列表）。
    7. 实时结果写入在线库，定期被离线全量结果覆盖——即 Lambda 架构（批批互补）。
    8. 批流一体：Flink 在流处理基础上加"数据重播"，同一套代码既处理落盘数据也处理实时流；实践中难完全统一（复杂长跨度特征流式难算），态度是"取其所长"。

    从 0 搭建的简化建议¶

    • 舍弃近线层、避免分布式；数据量未到时单机协同过滤/矩阵分解效率往往优于 Spark 集群；在线融合用简单加权即可。架构是进化出来的，满足最低要求就好。
    • 推荐服务闭环五模块：数据收集（内容+行为）→ 特征工程 → 模型训练（按规模选规则/CF/深度模型）→ 推荐服务（速度+体验，300ms 内）→ 反馈收集（行为/评论/流程放弃点），日志回采形成闭环。
    • 推荐列表构成：推荐列表 = 运营推荐位 + 多样性排序算法位（含多路召回融合）+ 最新内容位。
    • 部署：云/本地/容器化/Serverless/分布式，常以"云或本地 + Docker/K8s 容器化"组合。

    与搜索、广告的关系¶

    • 三者本质都是信息与需求的匹配，共同骨架：过滤候选（都靠索引）→ 排序候选（目标不同）→ 个性化输出。
    • 搜索：需求明确（"已知的未知"），目标是相关性与低延迟，用户用完即走；推荐：需求模糊，可做多样性、惊喜、探索；广告：为信息找人，排序掺入出价（eCPM），目标是商业利益最大化。
    • 工程协同：基于内容的推荐本质是小搜索引擎；已有搜索（如 ES）的系统加推荐功能最快；搜索可积累即时兴趣数据，与长期兴趣互补，避免"搜什么推什么"。

    经验与常见坑¶

    • 误区一：以为算法是推荐系统的全部。工程实现才是骨架；模型训练和实现的工作量往往不到一半，大头在线上服务、特征/模型数据库的搭建维护。
    • 误区二：一开始就上分布式/完美架构。数据量不足时分布式极不划算，架构应随业务进化。
    • 误区三：信息流排序"没有目标"或"人工量化"。必须先定义目标（正/负向互动），靠数据而非运营拍脑袋加权。
    • 在线层必须设计降级：任何个性化结果都可能取不到，热门榜兜底是标配。
    • 缓存带来数据一致性问题，与业务库的实时同步是持续挑战。
    • 曝光数据必须落日志且带唯一 ID，否则后续训练样本拼接、去重、归因全部无从谈起。
    • 排序层的输出依赖召回层的质量：召回集若只覆盖单一兴趣会陷入局部最优，若什么都有则等于随机推荐——排序再好也救不回来。
    • 实时性要分层次评估投入：很多"实时推荐"实际只做到特征实时（第二层），模型实时（第三层）成本高，不是所有算法都值得实时化。

    ⚠️ 时效性说明¶

    • 流计算框架文中主推 Storm，现业界主流已是 Flink（专栏 C 亦持此观点）；Spark Streaming 的小批量模式仍是其特点。
    • 模型服务一节以 TensorFlow 生态为主；PyTorch（TorchServe、ONNX、TensorRT）已是同等主流选项，PMML 在深度模型上表达力不足的结论不变。
    • YouTube 架构为 2016 论文版（softmax 召回 + Weighted LR 排序）；其后业界更常用双塔（两塔分别产出用户/物品 Embedding 再近邻检索）做召回，见模型演化篇。
    • 具体毫秒级时延预算（25/45/15ms）为经验值，随硬件与模型复杂度浮动，量级参考即可。
