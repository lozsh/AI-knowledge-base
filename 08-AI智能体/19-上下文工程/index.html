    上下文工程

    来源：原资料（更新于 2026-11-03）

    一句话定义：上下文工程（Context Engineering）是在每次模型调用前，以可复用、可度量、可演进的方式拼装并优化输入上下文的工程方法——核心是管理 LLM 有限的"注意力预算"。

    提示工程关注"如何写出有效提示"；上下文工程是它的自然演进：在推理阶段策划与维护"最优的信息集合（tokens）"，涵盖系统指令、工具、MCP、外部数据、消息历史等一切进入上下文窗口的内容。循环运行的 Agent 会不断产生下一轮可能相关的数据，上下文工程的"艺与术"就在于：从持续扩张的候选信息宇宙中，甄别哪些内容应进入有限的上下文窗口。

    为什么重要——上下文腐蚀（context rot）：针堆找针类基准揭示，随着上下文 tokens 增加，模型准确回忆信息的能力反而下降。上下文是有限资源且边际收益递减——LLM 也有一笔"注意力预算"。根源在架构：Transformer 的两两注意力关系随长度增长被"拉薄"；训练数据中短序列远多于长序列，模型对全上下文依赖的经验更少；位置编码插值等技术可外推更长序列但牺牲位置精度。综合效果是性能梯度而非悬崖式崩溃——长上下文下依旧强大，但检索与长程推理精度下降。

    核心原理

    有效上下文的"解剖学"

    目标：用尽可能少、但高信号密度的 tokens，最大化获得期望结果的概率。三个组件的工程要点：

    • 系统提示：语言清晰直白，信息层级"刚刚好"。两个极端误区：过度硬编码（复杂脆弱的 if-else 逻辑，难维护）与过于空泛（只有宏观目标，缺具体信号）。建议分区组织（角色、工具指引、输出描述等），用 XML/Markdown 分隔；追求"最小必要信息集"（最小 ≠ 最短）。方法：先用最好的模型在最小提示上试跑，再依据失败模式增补指令与示例。
    • 工具：工具是 Agent 与信息/行动空间的契约。要求：职责单一、低重叠、接口语义清晰、对错误鲁棒、入参描述无歧义。常见失败模式是"臃肿工具集"——如果人类工程师都说不准用哪个工具，别指望 Agent 做得更好。精心甄别"最小可行工具集（MVTS）"。
    • 示例（Few-shot）：始终推荐，但精挑细选多样且典型的示例，不要罗列所有边界条件。

    上下文检索与智能体式搜索

    简洁定义：智能体 = 在循环中自主调用工具的 LLM。实践正从"推理前一次性检索"过渡到即时（Just-in-Time, JIT）上下文：不预加载所有数据，而是维护轻量引用（文件路径、存储查询、URL），运行时通过工具动态加载——模型撰写针对性查询、用 head/tail 分析大体量数据，认知模式贴近人类（不背全部信息，靠文件系统/书签按需提取）。

    引用的元数据本身也传达语义：目录层级、命名约定、时间戳暗示"目的与时效"（tests/test_utils.py 与 src/core/test_utils.py 的语义暗示不同）。这带来渐进式披露（progressive disclosure）：每步交互产生新上下文、反过来指导下一步决策，Agent 按层构建理解，工作记忆只保留"当前必要子集"。权衡：运行时探索比预计算检索慢，且需有"主见"的工具与启发式引导，否则会误用工具、追死胡同。不少场景用混合策略：前置加载少量高价值上下文（如项目约定），同时提供 glob/grep 原语让 Agent 即时检索。

    长时程任务的三大策略

    策略 思想 适用场景
    压缩整合（Compaction） 对话接近上限时高保真总结，用摘要重启新窗口；保留架构性决策、未解决的缺陷、实现细节，丢弃重复工具输出 需要长对话连续性的任务（上下文"接力"）
    结构化笔记（Structured note-taking） 以固定频率把关键信息写入上下文外的持久存储，按需拉回（TODO 列表、NOTES.md、结论/依赖/阻塞索引） 有里程碑/阶段性成果的迭代式开发与研究
    子代理架构（Sub-agent architectures） 主代理负责规划与综合，多个专长子代理在干净上下文中各自深挖，仅回传凝练摘要（约 1000-2000 tokens） 复杂研究与分析，能从并行探索中获益

    压缩整合调参：先优化召回（不遗漏关键信息），再优化精确度（剔除冗余）；安全的"轻触式"压缩是清理深历史中的工具调用与结果。即便模型能力持续提升，"在长交互中维持连贯与聚焦"仍是核心挑战。

    ContextBuilder：GSSC 流水线

    HelloAgents 框架的上下文构建器，把构建过程抽象为GSSC（Gather-Select-Structure-Compress）四阶段流水线。设计目标：统一入口（免重复模板代码）、稳定形态（固定骨架模板便于调试与 A/B 测试）、预算守护（token 超限兜底压缩）、最小规则（只用"相关性 + 新近性"评分，不引入来源/优先级等复杂维度）。

    核心数据结构：ContextPacket（候选信息包：内容、时间戳、token 数、相关性分数 0-1、元数据）与 ContextConfig（max_tokens 默认 3000、reserve_ratio 为系统指令预留比例默认 0.2、min_relevance 最低相关性阈值、recency_weight 0.3 / relevance_weight 0.7 且两者之和必须为 1）。

    四阶段：

    1. Gather 多源汇集：系统指令（relevance=1.0，最高优先级不参与评分）+ 记忆系统检索（limit 10）+ RAG 检索（limit 5）+ 最近 5 条对话历史（基础相关性 0.6）+ 自定义信息包。每个外部源调用都有 try-except 包裹——单源失败不影响整体（容错）。
    2. Select 智能选择：先扣除系统指令占用，其余信息计算综合分 = 相关性权重×相关性 + 新近性权重×新近性；过滤低于 min_relevance 的；按分数降序贪心填充至 token 上限。相关性用 Jaccard 关键词重叠（生产可换向量相似度）；新近性用指数衰减 exp(-0.1 × age_hours / 24)，24 小时内保持高分，下限 0.1。
    3. Structure 结构化输出：组装为固定分区模板——[Role & Policies]（角色与准则）→ [Task]（当前任务）→ [Evidence]（RAG 检索证据）→ [Context]（历史与记忆）→ [Output]（输出要求）。优势：可读、可调试（快速定位哪个分区有问题）、可扩展（新信息源即新分区）。
    4. Compress 兜底压缩：超限时按分区压缩——能完整保留的保留，放不下的截断并标注"[... 内容已压缩...]"，保持结构完整性。Token 估算：中文 1 字符 ≈ 1 token，英文 1 单词 ≈ 1.3 tokens（生产应换精确 tokenizer）。

    最佳实践：按任务复杂度动态调整 max_tokens；生产环境把关键词重叠换为向量相似度；对不变的系统指令与知识库做缓存；记录每次构建的统计信息（选中数量、token 使用率）；关键参数（相关性/新近性权重）用 A/B 测试定标。

    NoteTool：结构化笔记

    为长时程任务提供的外部记忆组件，填补 MemoryTool（对话式记忆）与项目式长期追踪之间的空隙：Markdown + YAML 混合格式（机器可解析 + 人类可读）、纯文本对 Git 友好、无数据库开销、type + tags 多维组织。

    • 存储格式：每条笔记一个 .md 文件，YAML 前置元数据（id、title、type、tags、created_at、updated_at）+ Markdown 正文；另维护 notes_index.json 索引（快速检索、元数据集中管理、完整性校验）。
    • 七类操作：create / read / update / search / list / summary / delete，覆盖笔记全生命周期。
    • 五种笔记类型：task_state（阶段性进展）、conclusion（关键结论）、blocker（阻塞问题，优先级最高）、action（下一步计划）、reference（参考资料）。
    • 与 ContextBuilder 集成：每轮对话前检索相关笔记转为 ContextPacket 注入上下文，按类型设不同相关性分数（blocker 0.9 > action 0.8 > task_state 0.75 > conclusion 0.7）。
    • 最佳实践：已解决的 blocker 更新为 conclusion；过时的 action 及时清理；笔记是人类可读 Markdown，支持人工审核与 Git 版本控制；可自动生成进度文档、同步到 Notion/Confluence。

    TerminalTool：即时文件系统访问

    实现 JIT 上下文理念的安全命令行工具——不预索引全部文件，按需探索。四层安全机制：

    1. 命令白名单：只允许只读命令（ls、cat、head、tail、find、grep、wc、sort、cut、awk、sed 等），禁止任何修改系统的操作。
    2. 工作目录沙箱：只能访问指定工作目录及子目录，cd .. 逃逸被路径校验拦截。
    3. 超时控制：每条命令限时（如 30 秒），防死循环与资源耗尽。
    4. 输出大小限制：超限截断（如 10MB），防内存溢出。

    典型模式：探索式导航（ls → cd → find → cat 多步探索代码库）、数据文件分析（head/wc/cut/uniq 快速了解结构）、日志分析（tail + grep + awk 定位与统计错误类型）、代码库分析（统计行数、找 TODO、定位函数定义）。实现要点：cwd 当前目录感知、合并 stderr、非零返回码标记为警告、超时与异常妥善处理不使 Agent 崩溃。

    三层信息分层设计（本章的核心收获）：即时访问（TerminalTool，按需拉取）+ 会话记忆（MemoryTool，会话内关联）+ 持久笔记（NoteTool，跨会话状态）。

    应用案例：长程代码库维护助手

    整合三大组件的 CodebaseMaintainer，面向中型 Flask 项目的跨天维护场景。三大长程挑战与对策：信息量超窗 → TerminalTool 即时按需探索；跨会话状态 → NoteTool 记录进展/待办/决策；上下文质量 → ContextBuilder 智能筛选保高信号密度。

    运行流程六步：按模式预处理（explore 探索结构 / analyze 检查质量与 TODO / plan 加载任务笔记 / auto 灵活决策）→ 检索相关笔记（优先 blocker）→ ContextBuilder 构建上下文 → 调用 LLM → 后处理（回答含"问题/bug/阻塞"自动创建 blocker 笔记，讨论含"计划/下一步"自动创建 action 笔记）→ 更新历史（限最近 10 轮）。

    实测效果体现长程智能体的四个关键特性：跨会话连贯性（第一天发现的问题第三天规划时自动纳入）；智能上下文管理（按对话模式动态调整预处理，token 预算内选最相关信息）；即时文件系统访问（无需预索引整个代码库）；自动化知识管理 + 人机协作（自动记笔记，人类可手动干预与审核）。可扩展方向：集成 RAG 语义检索代码库、拆分探索者/分析者/规划者多智能体、集成测试工具自动验证重构、Gradio 可视化。

    经验与常见坑

    • 上下文不是越大越好：context rot 意味着塞得越多、回忆越不准——筛选比堆砌重要。
    • 系统提示两极误区（过度硬编码 / 过于空泛）都常见；正确路径是"最小提示 + 按失败模式增补"。
    • JIT 上下文比预检索慢，缺少工具与启发式引导时 Agent 会迷路——混合策略（前置高价值上下文 + 按需探索）通常最优。
    • Gather 阶段的容错必不可少：单个外部源失败不应拖垮整次上下文构建。
    • 压缩先保召回再保精确；LLM 摘要不是唯一手段，简单截断/滑动窗口在部分场景更合适。
    • blocker 笔记要定期消化：已解决的更新为 conclusion，否则阻塞列表本身会变成上下文噪声。
