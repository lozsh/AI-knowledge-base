    上下文工程深入¶

    来源：《从零构建 AI Agent》课程第 2 章（wiki 化重写于 2026-11-03）

    一句话定义：上下文工程（Context Engineering）是系统性设计、组织和提供 AI 完成任务所需全部背景知识的技术——决定 Agent 在每个决策点看到什么信息、以什么结构看到，其质量才是 Agent 能力的真正上限。

    模型能力是通用的，但执行具体任务需要背景信息（产品架构、业务规则、内部约定），模型根本不知道这些。类比：天才工程师加入团队，却对产品架构、技术债务、团队规范一无所知，也难发挥价值——这恰是 AI Agent 的困境。以 Coding Agent 为例，"帮我修复这个 bug"的效果取决于三类上下文：实时代码上下文（目录结构、模块职责、代码规范——否则代码风格格格不入甚至架构冲突）、流程规范（Git 策略、提交规范、CI/CD——否则直接往主分支提交未测试代码）、环境信息（测试库、staging 部署、密钥管理——否则本地能跑的修复到测试环境就崩）。中等能力模型配精心组织的上下文，往往胜过顶级模型在信息匮乏下的摸索。

    上下文工程首先是技术问题，更根本是组织问题：多数团队关键知识是隐性的（架构决策只有老员工记得），团队本身若是信息黑洞，再好的 Agent 也无计可施。文档驱动的团队（如 Linux 内核）天然对 AI 友好。AI Agent 就像永远的新员工：给足背景它能干得很好，什么都不告诉它再聪明也白搭。翁家翌（OpenAI）："人和模型一样，最重要的是 Context"；团队合作最大的问题也是 context 不一致。

    核心原理一：API 层面的上下文结构¶

    消息的四种角色（以 OpenAI Chat Completions 为例，各厂商大同小异）¶

    角色 来源 作用
    system 开发者 系统提示词，最高优先级，通常仅一条放最前
    user 终端用户 用户输入请求
    assistant 模型 之前的回复（含工具调用请求），放回列表让模型"记住"自己说过什么
    tool Agent 框架 工具执行结果，靠 tool_call_id 关联调用

    工具定义（tools）是请求的独立字段。关键事实：每次调用都是无状态的——模型需要的所有信息必须在 messages 中完整提供，框架每次都把完整历史送回去。

    Agent 核心循环（ReAct 的 API 实现）¶

    以"温哥华现在几点、天气如何"为例：① 第一次调用发 system+user+tools，模型不直接回答而是返回 tool_calls（两个无依赖调用并行发出）；② 模型只负责决策（调什么工具、传什么参数），框架负责执行——理解 Agent 架构的关键；③ 第二次调用把完整历史（含第一次 assistant 消息原样放回 + tool 结果）重发，模型判断信息足够则返回最终文本回复，循环结束；不够则再次返回 tool_calls，如此循环。最小实现就是一个 while 循环（生产代码必须设 max_iterations 上限防死循环）：返回 tool_calls 就执行工具、追加结果、继续循环；没有就输出并退出。Agent 框架的核心工作就是管理 messages 列表——本章所有技术本质上都在优化这个列表。

    "静态前缀 + 轨迹"结构¶

    System Prompt + Tool Definitions 构成静态前缀（全程不变）；user/assistant/tool 消息构成动态增长的轨迹。由此得出"前面不能动（利于 KV Cache）、后面可以压缩"——后续一切优化的基础。

    Chat Template：从 API 消息到 Token¶

    结构化消息需经 Chat Template 转为线性 token 流（<|im_start|>/<|im_end|> 等特殊标记界定角色与边界，各模型家族格式不同；vLLM/Ollama 服务端自动处理）。理解它有两个价值：

    1. 解释为什么必须用标准 API 格式：自行拼接消息（如把工具结果当 user 消息传）破坏模型能力。典型：Qwen3 多轮工具调用中保留 <think> 思考过程（像草稿纸），但检测到新用户查询就清理重开——工具结果被误标为 user 消息会误触发清理，"草稿纸被收走"。⚠️ 历史 CoT 处理策略正快速演变：DeepSeek R1 剥离全部历史思考（历史 CoT 不在训练分布内），但对 Agent 有缺陷（中间思考承载关键状态，剥离后每轮从零推理）；DeepSeek V4 反转为强制回传全部 reasoning_content，Kimi K2、GLM-5 同样；Claude 要求工具循环中带签名回传 thinking block。行业从"剥离"转向"强制回传"证明：对 Agent，思考不是废料，而是状态。
    2. 解释 KV Cache 为何对前缀敏感：system 与工具定义转为固定 token 序列放最前，缓存跨请求复用；任何一个 token 变化（哪怕一个空格）缓存全废。

    核心原理二：KV Cache 友好的上下文设计¶

    三条核心结论（必须记住）¶

    1. 系统提示词和工具定义一旦确定就不要改——改动哪怕一个空格都导致缓存全部失效，延迟成倍增加、成本上升；
    2. 动态信息永远追加到末尾——时间戳、用户状态作为新消息追加，而非修改系统提示词；
    3. 使用标准 API 格式，不要自行拼接消息——拼接文本的关键问题不是缓存（缓存只认字节序列，拼接稳定照样命中），而是偏离模型训练时见过的结构化格式，削弱多步思考：重复执行已完成操作、忽略工具结果、该调工具时却输出文本。

    注意力机制要点¶

    注意力靠三类向量"找重点"：Query（当前词的搜索请求）、Key（每个词的标签，被匹配）、Value（词的内容，匹配后提取）；Query 与 Key 点积打分 → 归一化为权重 → 对 Value 加权求和。热力图呈三角（因果注意力，每词只能看前文）。可视化实验的关键模式：Attention Sink——序列首 token 常吸收超 70% 注意力（softmax 约束权重和为 100%，无处安放的剩余权重集中倾倒到首 token，是系统性现象非缺陷）；位置偏好——开头和结尾注意力高、中间易被忽视（"Lost in the Middle"），最关键的信息应放开头或结尾。

    代价模型与常见错误模式¶

    无缓存时 prefill 计算量随上下文长度平方级增长；有缓存时省去历史 K/V 重算，但每个新 token 的注意力仍要遍历全部缓存 K/V（线性增长）——这正是长上下文解码变慢、KV 显存成为瓶颈的原因。修改前缀为何全废：Transformer 各层串联，第 1 层输出变则逐层传导，所有层缓存重算。实测（3000 token）：缓存命中 TTFT 约 0.5s、只对新 token 计费；失效 TTFT 3-5s、全部重算计费。

    常见错误模式：动态系统提示词（嵌时间戳——案例：客服 Agent 加一行时间戳后 TTFT 0.5s→3-5s、月账单近翻倍；应追加到末尾或用工具获取）；动态用户配置嵌上下文（应用专门状态机制）；工具定义动态排序（工具定义占上下文大头，改序即缓存失效；固定顺序对工具选择几乎无影响）；滑动窗口历史（破坏前缀一致性 + 丢失关键工具结果——第 2 轮的文件内容第 15 轮还要用，Agent 会陷入循环反复调同一工具）；文本格式化拼接（主要坏在偏离训练格式，非缓存）。

    KV Cache 与 Prompt Cache：两个层级¶

    KV Cache 是模型内部优化（单次推理内）；Prompt Cache 是 API 服务层优化（跨请求缓存相同前缀），都靠前缀不变性。缓存读取成本约为正常计算的十分之一（Anthropic/DeepSeek/GPT-5 系列均约 1/10）。细节差异：Anthropic 需显式设 cache_control 断点（非自动），写入约 1.25 倍加价，有最小可缓存长度（1024 token）和 TTL（默认约 5 分钟）；OpenAI 自动前缀缓存。

    缓存作为架构约束（生产级）¶

    Prompt Cache 经济效益足够大时，缓存一致性反过来主导架构（Claude Code 实践）：提示词结构由缓存边界决定（system prompt 一分为二，边界前全局缓存、边界后放用户/会话特定信息；N 个二值运行时条件放边界前 = 2^N 种缓存键，故动态元素严格归边界后）；子 Agent 必须与父 Agent 字节级对齐（提示词、工具、模型配置、消息前缀逐字节匹配才能命中缓存）；工具结果替换字符串首次出现即冻结（保证会话恢复后与缓存字节流一致）。启示：缓存经济性不是事后优化，而是前置约束。

    前沿延伸：KV Cache 可编辑可组合（选读）¶

    研究发现（arXiv:2606.17107）：prefill 阶段模型在"做笔记"——字段推论写进下游各层 KV 状态，字段自身 KV 对决策贡献常不到 1%。由此：编辑（改字段后借 CoT 让改动顺缓存传播，约 1% 算力得到与整段重算一致的结果；无 CoT 时孤立改字段会被忽略——重要边界）；组合（预计算"技能"缓存经 RoPE 重定位拼接，O(L²) 重算降为 O(L)）。vLLM 实现后 p90 首token 延迟最高降几十到几百倍、命中率约 98.5%。仍属研究阶段，生产中上面三条结论仍是默认原则。

    核心原理三：提示工程（系统提示词设计）¶

    检验标准：大模型是聪明的新员工——如果新员工读完你的系统提示词还不知道该怎么做，Agent 也一样。设计维度：

    1. 语气风格："You MUST answer concisely with fewer than 4 lines"；失败时控制 1-2 句且不解释（避免冗长自我辩护）；大写（"NEVER do X"）比"Please avoid"更有效，但过度使用稀释效果，留给真正关键的约束。
    2. 结构化提示：XML 标签名自带语义（<working_directory> 即时告知类型）；Markdown 提供轻量层次。双层：XML 负责机器可解析的精确语义，Markdown 负责人机共读的组织。
    3. 流程驱动 vs 规则堆砌：上百条零散规则连聪明人也困惑；流程驱动是清晰 SOP（如文件处理五步：验证→分类→预处理→执行→校验，含条件分支），模型任何时刻知道自己在哪个阶段、异常按当前阶段处理。
    4. 业务规则细化（最易被忽视却最关键，是产品设计问题）：模糊规则（"按任务情况选择计费"）导致行为极不稳定——"退掉上个月买的衣服"算省钱还是取回自己的钱？规则须细化到可执行：按提成仅限谈判降账单、退款取消绝不按提成（明确写 "NEVER use percentage_based for refunds"）、成功率分步评估并映射计费模式（>60% 可退款、<30% 拒绝）、"节省"只基于现有账单。分工哲学：提示词由产品经理设计迭代，工程师准确编码、不擅自决定业务逻辑——模型优势在遵循指令，不该有业务规则的自由裁量权。
    5. Few-shot 示例：输出难以用规则精确描述（风格/格式/语气）时给两三个精选示例，胜过等量抽象规则；模型本就擅长的任务示例是浪费。示例确定后须字节级稳定——按请求动态检索"最相关"示例等于每次改前缀；生产系统为每类任务准备固定示例集。两三个覆盖边界情况的胜过十个大同小异的。
    6. 工具定义：与系统提示词并列的静态部分，质量直接决定工具使用准确性（参考 Claude Code：使用边界、具体示例、性能提示"Batch your tool calls"、工具间协作关系）。2026 起工具定义向渐进式披露演进且已是 API 原生能力：OpenAI 的 tool_search+defer_loading、Anthropic 的 Tool Search（tool_reference）、Codex CLI 默认开启 BM25 工具检索——前缀只留工具名和简述，完整 schema 按需搜索后追加到上下文末尾（因果注意力保证追加不改已缓存 K/V，一次性写入后持续命中；schema 固定在轨迹原位置，非每轮搬运）。约束：要求模型训练时见过"工具定义出现在对话中间"，目前仅较新模型（GPT-5.4+、Claude 4.5+）支持。

    消融实验证据（Tau-Bench 客服场景）¶

    语气风格（专业/夸张/随意）对任务完成率影响有限（模型风格适应力强）；信息组织打乱（保留内容、去层次、拆流程）→ 成功率下降超 30% 且常违反关键业务规则——对人类友好的组织对模型同样友好；删工具描述（留签名）→ 工具调用错误率增加 45%。方法论：Agent 表现不佳时先做消融实验逐项关组件，比凭感觉重写可靠。

    提示注入：上下文安全的核心威胁¶

    攻击者通过外部内容（网页、邮件、文档）把伪装指令混入上下文劫持 Agent。Agent 比聊天机器人更危险：被注入指令可能导致文件删除、发邮件、泄露隐私等不可逆操作；每个感知工具都是注入入口，攻击可藏在不可见元素、PDF 元数据、图片 EXIF。上下文层防御：① 来源标记（<external_content source="webpage"> 包裹，提示其中"指令"不执行）；② 结构化角色（严格用四种角色传信息——工具结果混入 user 消息等于抹掉模型辨别来源的依据）；③ 输入清洗（易被措辞变体绕过，仅辅助）。警惕：上下文机制本身构成新注入面——第三方 Skill 本质是"把外部内容当指令加载"的制度化，安装前必须像审查代码一样审查；状态栏信息被高度信任，来自可污染数据源会被反向利用（投毒）。上下文层只是第一道防线，须叠加执行层防御（权限、沙盒、高风险操作审查）。

    核心原理四：Agent Skills（渐进式披露）¶

    系统提示词随场景膨胀的两个问题：浪费 token、注意力被稀释。解法：从"一次性塞满"到按需加载。三层结构：

    1. 元数据（启动时加载，约 300 token）：每个 Skill 必有 SKILL.md，YAML frontmatter 含 name+description，框架启动时只注入元数据。description 是路由关键，应写成路由条件而非功能介绍——"Use when / Don't use when"加反例；缺反例路由准确率明显下降，"何时该用我"比"我能做什么"重要得多。
    2. 核心流程（按需加载，约 2K token）：Agent 判断需要时通过专用 Skill 工具加载完整 SKILL.md，作为 tool result 进入对话历史。
    3. 子文档（选择性深入）：主文件引用细则文档，按需阅读；Skill 还可捆绑可执行脚本和模板。

    Skill 是自包含知识模块，可独立开发/版本控制/分享——类似 pip/npm 生态，能力扩展从集中式提示词编辑转为分布式社区生态。

    三种实现方式与权衡¶

    方式 做法 优点 缺点
    一：注入 system prompt 内容追加到系统提示词 指令遵循最强 每次加载改前缀，缓存反复失效
    二：普通文件读取 内容作为 tool result 在上下文中间 不影响缓存 中间位置指令遵循打折（Claude 训练数据多表现最好，其他模型差异大）
    三：生产实现（Claude Code） 元数据以 user 角色 meta 消息注入末尾（<system-reminder> 包裹），完整内容经专用工具按需加载 不改前缀 + 末尾注意力最优 + 模型对"自己主动调用的工具的输出"执行倾向更强 —

    方式三细节：元数据增量发送（每 Skill 只发一次，稳态增量为零）；"末尾"注意力优势只在当轮成立，随会话增长滞留中部——"只发一次省缓存"与"每轮置底保注意力"的权衡。"对 KV Cache 友好"≠零成本：首次 emit 付一次缓存写入，准确含义是"一次性写入、永久受益"；对比塞 system prompt（每次更新让下游数万到数十万 token 失效重建）才是真不友好。Skills+通用执行器模式下核心工具只需七个左右，避免把大量专用工具定义塞进前缀。

    核心原理五：Agent 状态栏¶

    Agent 执行复杂任务的三类陷阱：无限循环、状态遗忘、目标偏离——根源是缺乏对环境状态和任务进展的感知。状态栏是框架在上下文末尾持续注入的状态摘要（"已打 3 次电话""TODO 还剩 2 项"），类比手机状态栏。与系统提示词的区别：后者是入职发的员工手册（不变），前者是贴屏幕边的实时仪表盘（不断更新）。

    理论基础：上下文学习更像检索而非推理¶

    模型擅长从已有内容"查找"，不擅长单次前向传播内"归纳统计"（不否定思维链，只是成本高）。上下文窗口是只有一半的检索引擎：检索半很强（内置 RAG），缺"提炼层"——任何"关于内容的结论"每次都要现算，代价随内容量上涨。案例：系统提示要求每商家最多拨 3 次电话，Agent 常数不清而打第 4 次；在工具结果中标注"本次是第 3 次呼叫"后立即遵守——把分散的隐式状态提炼为可直接使用的显式知识。放末尾还紧邻生成位置，获最高注意力权重（"强制性注意力引导"）。可视化对照：无状态栏时注意力分散、思考 token 呈现数数过程；有状态栏则锁定状态栏直接使用结论；0.6B 小模型无状态栏常违反约束，有则稳定遵守。

    大规模量化证据（上下文蒸馏 / Context Distillation）¶

    三类任务（计数、规则归纳、状态跟踪）× 11 模型 × 近 2.4 万次评测：弱模型补准确率（最弱模型涨 40-54 个百分点，2B 本地小模型追平不带状态栏的前沿大模型）；强模型省效率（思考量/延迟/花费各降约一个数量级）；最本质变化：思考量不再随上下文变长增长，变为恒定——模型只"瞥一眼"那几格状态。状态栏要写成可一眼定位的键值对（"衣物: 9 件（合格7、次品2）"），散文形式明显更差（还得解析，等于回到"扫描"）。

    三条工程经验¶

    1. 状态栏用代码维护，别拿 LLM 维护：20 行正则可达"标准答案"级准确度；让前沿 LLM 批量统计长历史反而大面积出错、比不用还糟——等于把"扫描整段上下文"的难题原样搬家。实在要用 LLM，逐条抽取、代码汇总。
    2. 删原文前确认状态栏覆盖所有会被问到的问题：状态栏是有损投影。极端测试：状态栏只存两两组合计数、问三者交叉——连 Claude 都从 100% 掉到 7.6%，一条像样却答非所问的状态栏成了带偏模型的"假权威"。把"新增问法"当改表结构对待：要么先加字段，要么别删原文。多跳推理类任务本无干净结构化摘要，别指望状态栏提准确率。
    3. 把状态栏准确率当生产指标盯：模型几乎无条件信任状态栏（写 3 次就当 3 次，不核对不重算）。容错空间：错 10% 以内收益保住大半，越线可能比不带更糟。信息越来自真实观测越好，绝不能来自可污染数据源。

    深层原理：喂进模型自己想不出来的信息¶

    让模型变强的两条老路（想得更久、采样更多）共同天花板：都在"自己脑子里"打转，变不出上下文里没有的新信息。第三条路是交互：让外部"仪器"观察真实世界（代码是否通过测试、按钮是否出屏——"跑一下、量一下"才知道的事实），把观察写回上下文让模型修正。Harness 就是那台仪器，状态栏把"闭卷考试"变成"随时查真实世界"。推论：Loop 工程的瓶颈在验证器不在模型——抽掉"把外部观测写回上下文"这步，循环只是原地重排旧信息。

    构成、位置与更新¶

    四类信息：任务规划（TODO 列表，防忘记原始诉求）、侧信道信息（精确时间、地理位置等元数据，一经添加不变、缓存友好）、环境当前状态（时间、工作目录、"该工具已被调用 N 次"）、可用能力清单（已装 Skill 元数据，增量发送）。位置：作为 user 角色消息追加到末尾（<agent_status> 包裹）而非改 system（毁缓存）——user 角色只是 API 协议层技术选择，内容来自框架而非真实用户。更新两种实现：每轮替换（替换点后缓存失效，仅限末尾几轮）vs 持久追加（Claude Code 的 <system-reminder> 方式，完全缓存友好但陈旧状态累积）。经验法则：更新频繁且轨迹长→持久追加；轨迹短或单条状态大→每轮替换。

    五种实用技术（实验框架）¶

    ① 时间戳跟踪（[2025-09-14 10:30:45] 前缀加到用户消息和工具响应，不进系统提示词）；② 工具调用计数器（"Tool call #3 for read_file"，触发模式识别：查路径→列目录→主动放弃，深层价值是成本感知）；③ TODO 列表管理（借鉴 Manus"通过复述操纵注意力"；数据：启用平均 15 次迭代完成，禁用 21 次且常遗漏子任务）；④ 详细错误信息（错误类型+参数 JSON+调用栈+修复建议，错误场景替代方案成功率 60%→95%）；⑤ 系统状态感知（时间、工作目录 cd 后自动更新、操作系统——平台相关决策）。组合产生涌现效应。

    延伸：时间感（time sense）三轴¶

    紧迫度（预算轴：力气匹配时钟，时间紧果断交付、宽裕多验证，双向——低紧迫度≠少干而是"别急着停"）；坚持度（终点轴：分清真墙——410 Gone 的接口不该重试五次——和假墙——搜两次就断言"查无此信息"是过早收手）；警觉度（监控轴：该 500ms 却跑 5 秒、1ms 就"成功"但 body 为空，都是信号）。反直觉关键发现：只给原始读数几乎无用（与什么都不给相差两三个百分点）；把通过率从一成出头拉到四五成（+19~+49 个百分点）的是配套操作手册——模型缺的不是读数而是"拿读数怎么办"的策略。计数器只靠读数就能纠偏是因为规则太显然（"到顶就停"）；节奏判断规则不显然，必须读数+策略成对给出。该缺陷跨四厂商六模型普遍存在，推理时可靠"状态栏+手册"补上。

    核心原理六：上下文压缩策略¶

    两个动机¶

    ① 长度与成本（直观）：窗口有限（如 128K），工具结果动辄数万字符，几轮撑满即任务中断；② 提升思考质量（深层易忽视）：10 次搜索结果散落上下文，模型做决策须在数万 token 中反复检索、注意力分散；先做结构化总结（"已知 A、B，还缺 C"）则可直接使用精炼表示。本质仍是"检索而非推理"：状态栏是把结论加进上下文，压缩是把原始记录换成结论——同一枚硬币的两面。直观例子：100 条宠物店记录问"黑白猫各几只"——不开思维链难答对（注意力擅长查找、不擅长统计）；开思维链能数对但每次重数；提前写入"黑猫 90、白猫 10"即可直接检索。压缩的第二个价值：把需要思考才能得到的结论变成可直接检索的知识。

    上下文腐化（Context Rot）¶

    窗口没满，Agent 却找不到关键信息、纠结已解决的问题。与"溢出"（装不下）不同，腐化是"装得下但找不到了"——更隐蔽，表面正常、决策质量悄然下降。最常见失效不是窗口不够长，而是信息密度不对：偶尔才用的知识每次都加载、稳定规则与动态状态混杂。Karpathy 洞察：模型"记忆差"某种程度上是特性——窗口有限迫使模型抽象出一般性模式。设计原则：与其期望模型从冗长上下文自动学习，不如主动显式地进行知识提炼。上下文学习本质是快速适配机制（会话结束即消失，非参数训练）——解释了 few-shot 为何有效、为何不跨会话累积。

    与 KV Cache 的关系¶

    压缩不在单次调用中改上下文，而在两次调用之间由框架预处理：System Prompt 和工具定义永远不动；压缩对象是轨迹中的 tool results，替换点之后缓存失效、之前仍有效；这是权衡——不压缩任务直接失败，压缩损失部分缓存换长度可控、密度更高。频次：接近阈值时批量压缩，而非每轮都压。

    六种策略对比（实验：追踪 OpenAI 联合创始人职业状态，128K 窗口）¶

    策略 思路 效果
    无压缩 原始结果全保留（7 次搜索约 36.7 万字符） 第 5 轮超限，失败
    个体摘要 每个结果独立摘要（压缩率约 10.9%） 能完成但信息碎片化、多页重复，24 轮迭代
    组合摘要 全部合并统一摘要（约 4.3%） 输入超长须截断，可能丢末尾信息
    上下文感知压缩 查询意图+已积累信息纳入压缩决策 最优：7 轮、4 万 token、约 3%；148K 字符压到约 2K 仍保留关键信息
    感知+引用 智能压缩+每条事实附来源 URL token 增至 22 万，但有损压缩+无损索引，可回溯
    自适应窗口 超窗口 80% 才触发+批量压缩+[COMPRESSED] 防重复 前期保留完整原始信息，初期灵活性最大

    上下文感知的关键洞察：多步任务不同阶段需要的信息密度不同——初期广泛收集、中期精确核验、后期综合整合，动态调整压缩侧重。

    生产级五层压缩机制（成本从低到高）¶

    ① 工具结果预算控制（大输出存磁盘只看预览，替换决策即冻结）；② 噪声直接删除（低价值内容不做摘要——对噪声做摘要只是浪费）；③ API 层微压缩（服务端从前缀移除指定工具结果；零本地成本但移除点后缓存失效，适合将溢出时用）；④ 归档式摘要（逐轮结构化摘要，像 git log 保留每轮记录非 squash，保留逻辑脉络）；⑤ 全量压缩（LLM 驱动的最后手段，分两阶段：先压会话记忆再全量；配连续失败熔断器——生产数据表明大量会话困在反复压缩失败循环里，熔断避免持续烧钱）。

    设计原则与保留优先级¶

    四原则：信息价值非均匀分布（决策点>支撑证据>噪声）；语义完整性（"Sutskever 于 2024 年 5 月离开 OpenAI"不能压成"Sutskever 离开"）；任务相关性（同一内容不同任务压缩结果不同）；压缩即理解（需深层语义理解，结果可审查、可跨会话复用）。压缩最易丢失的是早期架构决策、约束背后的理由、失败路径——LLM 倾向删"看起来可重新获取"的信息。保留优先级：① 架构决策和关键约束不得摘要；② 已修改文件列表和变更记录完整保留；③ 验证状态（pass/fail）必须保留；④ 未解决 TODO 和回滚笔记必须保留；⑤ 工具输出可删仅留结论。UUID、hash、IP、端口、URL、文件名等标识符必须原样保留——PR 编号错一位，后续工具调用直接失效。

    隔离优于压缩：子 Agent 上下文隔离¶

    更釜底抽薪：让大体积中间信息根本不进主上下文。主 Agent 把"读大量文件""大范围搜索"委派给子 Agent，子 Agent 在自己上下文中探索，只回传几百 token 结论。对比"找支付回调函数"：亲自搜，数万 token 原始代码进主上下文，找到后绝大部分沦为永久噪声；委派子 Agent，主上下文只增两条消息（任务描述+结论"函数在 src/payment/callbacks.py 的 handle_callback，另有两处调用点"）。本质是用隔离代替压缩：压缩是有损、需额外 LLM 调用的事后补救；隔离让噪声从一开始就绝缘，主 Agent 缓存前缀完全不受影响。代价：子 Agent 看不到主上下文，任务描述必须自包含——上下文质量决定能力上限，对子 Agent 同样成立。Claude Code 的 Task 工具、Deep Research 的检索子 Agent 都是生产实现。

    经验与常见坑¶

    • KV Cache 是最高优先级的架构约束：动态时间戳进系统提示词是最常见也最昂贵的错误（TTFT 0.5s→3-5s、月账单近翻倍）；一切动态内容追加到末尾。
    • 不要绕过 API 自行拼接消息：坏的不只是缓存，更是模型基于训练格式建立的多步思考与角色分辨能力；信息组织混乱比内容缺失更致命——打乱结构成功率降 30%+，删工具描述错误率升 45%。
    • Skill 的 description 要写成路由条件（含反例），宽泛描述=频繁误触发。
    • 状态栏三原则：代码维护（勿用 LLM 批量统计）、覆盖所有问题再删原文（防"假权威"）、准确率当生产指标盯（模型无条件信任状态栏）。
    • 读数要配操作手册：只给原始时间戳/计数不改变行为，规则不显然时必须"读数+策略"成对给出。
    • 优先隔离而非压缩：能委派子 Agent 就别让大体积中间内容进主上下文；Agent 循环必须设 max_iterations 上限防死循环。
