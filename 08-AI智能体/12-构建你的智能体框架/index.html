    构建你的智能体框架

    更新于 2026-11-03

    一句话定义：从零构建智能体框架 HelloAgents 的完整实践——以"分层解耦、职责单一、接口统一"为原则，实现统一 LLM 接口、消息/配置系统、Agent 抽象基类、四种经典范式的框架化重构，以及一套"万物皆工具"的工具系统。

    为什么自建框架

    市面框架的四类局限： 1. 过度抽象：为追求通用性引入大量抽象层与配置（如 LangChain 的链式调用），学习曲线陡峭。 2. 快速迭代的不稳定：商业化框架 API 变更频繁，版本升级后代码无法运行。 3. 黑盒化实现：核心逻辑封装过严，难深度定制，问题只能依赖文档与社区。 4. 依赖复杂：安装体积庞大，与其他项目配合时易依赖冲突。

    自建的价值是"使用者 → 构建者"的能力跃迁：深度理解 Agent 工作原理、获得完全控制权、培养系统设计能力。垂直领域（金融/医疗/教育）也常需要针对性提示词、特殊工具集成与定制安全策略的二次开发。

    HelloAgents 的设计理念

    • 轻量级与教学友好：核心代码按章节区分，任何有编程基础者可在合理时间内完全读懂；极简依赖（仅 OpenAI SDK + 必要基础库）。
    • 基于标准 API 的务实选择：OpenAI API 已是行业标准，在其上构建而非重新发明抽象——兼容性有保证、学习成本最低。
    • 渐进式学习路径：每章代码可 pip 安装为历史版本，无概念跳跃。
    • 统一的"工具"抽象（万物皆工具）：除核心 Agent 类外，Memory、RAG、MCP 等模块都统一抽象为"工具"，消除不必要的抽象层，回归"智能体调用工具"的核心逻辑。

    架构分层：core/（agent.py 基类、llm.py 统一接口、message.py、config.py、exceptions.py）+ agents/（SimpleAgent、ReActAgent、ReflectionAgent、PlanAndSolveAgent）+ tools/（base、registry、chain、async_executor、builtin）。

    核心原理

    HelloAgentsLLM：统一模型调用中枢

    三个升级目标：多提供商支持（OpenAI/ModelScope/智谱等无缝切换）、本地模型集成（VLLM/Ollama）、自动检测机制。

    扩展方式——继承而非改源码：创建 MyLLM 继承 HelloAgentsLLM，重写 __init__ 拦截 provider="modelscope" 的情况做特殊处理（解析专属环境变量 MODELSCOPE_API_KEY、默认 base_url），其他情况 super().__init__(...) 交还父类——既扩展功能又保留原有全部能力，升级库时定制不丢失。

    本地模型方案：VLLM（PagedAttention 等技术，吞吐量比标准 Transformers 高数倍，vllm.entrypoints.openai.api_server 启动后暴露 OpenAI 兼容 API）与 Ollama（一条 ollama run llama3 完成下载/配置/启动，默认 localhost:11434/v1）。两者都是 OpenAI 兼容 API，只需作为新 provider 接入，智能体核心代码零修改即可在云端 API 与本地模型间切换。

    自动检测机制（约定优于配置）三个优先级： 1. 特定服务商环境变量（MODELSCOPE_API_KEY → OPENAI_API_KEY → ZHIPU_API_KEY…）——最可靠。 2. base_url 判断：域名特征串（api-inference.modelscope.cn 等）；本地端口（:11434 → ollama，:8000 → vllm）。 3. API Key 格式辅助判断（如 ms- 前缀 → modelscope）——有模糊性，仅辅助。

    检测后由 _resolve_credentials 按 provider 解析凭证与默认 base_url。例：只配 LLM_BASE_URL="http://localhost:11434/v1" 即可零配置连 Ollama。

    框架接口三件套

    • Message 类（Pydantic BaseModel）：role 用 Literal["user","assistant","system","tool"] 严格限取值（对应 OpenAI 规范，类型安全）；含 timestamp 与 metadata 为日志与扩展预留；核心方法 to_dict() 转为 OpenAI API 字典格式——"对内丰富，对外兼容"。
    • Config 类：配置项按逻辑分组（LLM 配置/系统配置），每项有默认值保证零配置可用；from_env() 类方法支持环境变量覆盖默认配置，跨环境部署无需改代码。
    • Agent 抽象基类（ABC）：构造函数定义核心依赖（name、llm、system_prompt、config）；@abstractmethod run() 强制所有子类实现统一执行入口；通用历史管理方法（add_message/clear_history/get_history）与 Message 协同。

    四种 Agent 范式的框架化重构

    重构三目标：提示词从特定任务转向通用化设计（增强格式约束与角色定义）、接口与格式标准化（统一初始化参数、方法签名、历史管理）、高度可配置（自定义提示词模板/配置参数/执行策略）。

    • SimpleAgent：基础对话 + 可选工具调用。核心模式：增强系统提示词（把工具描述与调用格式 [TOOL_CALL:{tool_name}:{parameters}] 注入 system prompt）→ 多轮工具调用循环（正则解析 TOOL_CALL 标记 → 执行 → 把"工具执行结果"作为 user 消息追加 → 让模型基于结果继续回答 → 直到无工具调用或达 max_tool_iterations）→ 保存历史。附流式响应 stream_run 与工具管理便利方法（add_tool/remove_tool/list_tools）。参数解析要"智能"：支持 key=value 多参数、单参数直接按工具类型推断（search → {'query': ...}）。
    • ReActAgent：提示词改进强调"每次只能执行一个步骤"、明确两种 Action 格式（工具名[参数] / Finish[最终答案]）；执行循环五步：构建提示词（注入工具描述 + 执行历史）→ 调 LLM → 正则解析 Thought/Action → 检查 Finish → 执行工具并追加 Observation；max_steps 防无限循环；支持 custom_prompt 替换默认模板。
    • ReflectionAgent：三段提示词（initial/reflect/refine）通用化设计，适配文本/分析/创作多种场景；通过 custom_prompts 参数支持深度定制（如切回代码生成专用提示词）；终止条件"反馈含'无需改进'"。
    • PlanAndSolveAgent：与自由文本计划不同，强制 Planner 输出 Python 列表格式（```python 包裹），配完整异常处理，保证后续步骤稳定执行；Executor 提示词仍含原始问题/完整计划/历史结果/当前步骤四要素。
    • FunctionCallAgent（0.2.8+）：基于 OpenAI 原生函数调用机制——从工具 description 构建 function calling schema、从响应提取文本、解析 JSON 参数、转换参数类型。对比 prompt 约束方式，原生 Function Calling 鲁棒性更强。

    工具系统

    • Tool 基类：抽象接口 run(parameters: Dict) -> str（统一执行方式）+ get_parameters()（自描述参数需求——内省机制支撑自动文档生成与参数验证）；name/description 元数据提供可发现性。
    • ToolParameter（Pydantic）：name/type/description/required/default，支持类型检查与文档生成。
    • ToolRegistry：注册表管理中枢，两种注册方式——Tool 对象注册（复杂工具，完整参数定义验证）与函数直接注册 register_function(name, description, func)（简单工具快速集成）；get_tools_description() 生成格式化描述直接注入提示词；to_openai_schema() 把工具转成 OpenAI function calling schema（数组类型补 items 定义、默认值并入 description——OpenAI schema 不支持 default 字段）。
    • 自定义工具示例（计算器）：ast.parse(mode='eval') 解析表达式 + 白名单运算符/函数求值（安全优先：绝不用 eval 直接执行用户输入）；通过函数注册方式快速集成。
    • 多源搜索工具：hybrid 模式智能选择后端——优先 Tavily（AI 优化搜索），失败自动降级 SerpApi，全不可用则明确提示配置哪个环境变量（降级机制是高可用设计的核心理念）；不同引擎结果格式统一格式化（直接答案 + 编号列表 + 来源 URL）。类方式 vs 函数方式的取舍：需要维护状态（API 客户端、配置）的工具用类。
    • 工具链（ToolChain）：顺序执行多工具，add_step(tool_name, input_template, output_key) 支持模板变量替换（上一步输出 context[output_key] 可被下一步的 input_template 引用）——如"搜索 → 计算 → 总结"研究链。
    • 异步执行器（AsyncToolExecutor）：ThreadPoolExecutor + run_in_executor 包装同步工具，asyncio.gather 并行执行多个工具任务——并行收益出现在工具是 I/O 密集型（网络搜索、API 调用）时。

    工具系统设计理念：单一职责、接口统一、完善异常处理、安全优先的输入验证；性能上用异步提高并发、合理管理外部连接与资源。

    经验与常见坑

    • 扩展框架永远用继承重写而非直接改已安装库的源码——否则升级即丢定制。
    • 提示工程是多智能体/多范式系统稳定性的核心：格式约束（"每次只执行一个步骤"）、输出格式强制（Python 列表）、明确终止标志缺一不可。
    • 正则解析 LLM 输出（TOOL_CALL/Action）是教学实现；生产环境优先用原生 Function Calling（FunctionCallAgent 模式），鲁棒性更强。
    • 计算器等执行用户输入的工具必须用 AST 白名单求值，禁止 eval。
    • 所有循环式 Agent（ReAct/Reflection/工具调用循环）都要有 max_steps / max_iterations 安全阀。
    • "先体验后实现"的学习路径：pip 装框架跑通示例，再逐组件重写并跑官方测试验证。

    ⚠️ 时效性说明

    • 框架版本号（hello-agents==0.1.1 / 0.2.8 的 FunctionCallAgent）、VLLM/Ollama 启动命令与模型名（Qwen1.5-0.5B-Chat、llama3）随版本演进变化。
    • 本框架为教学用途，生产环境选型仍应参考第 11 篇的四大框架与工程化考量。
