    MLOps 大模型 智能体

    智能体框架演进与选型

    更新于 2026-11-05

    一句话定义：智能体框架的本质是提供一套经过验证的"规范"——把所有智能体共有的重复性工作（主循环、状态管理、工具调用、日志记录）抽象封装，让开发者专注业务逻辑。第一代框架（MetaGPT、AutoGPT、Swarm、DSPy、BabyAGI）各有截然不同的核心抽象——SOP 角色扮演、服务化工作流、移交原语、提示词编译、任务三代理循环——这些抽象本身比框架更耐用；第二代四大框架（AutoGen、AgentScope、CAMEL、LangGraph）分别代表"对话驱动协作、工程化平台、角色扮演、状态图控制"四条技术路径。

    从手写一次性脚本到使用框架，是软件工程式的思维跃迁。框架的核心价值：代码复用与效率（通用 Agent 基类封装核心循环）、核心组件解耦（模型层/工具层/记忆层分离，可独立替换升级）、标准化状态管理（上下文窗口限制、历史持久化、多轮状态跟踪）、可观测性（事件回调 on_llm_start / on_tool_end / on_agent_finish 自动记录轨迹，胜过手动 print）。两代框架构成一条演进线：第一代验证了核心抽象与协作范式，第二代把可靠性、工程化与生产部署补齐。

    核心概念

    MetaGPT 的两个公式（可作为理解所有多智能体系统的基座）： - 智能体 = LLM + 观察 + 思考 + 行动 + 记忆 - 多智能体 = 智能体 + 环境 + 标准流程（SOP）+ 通信 + 经济

    框架形态的两种根本路线： - MetaGPT：首先设计为库（library），装进你的 Python 进程。 - AutoGPT：首先设计为在线服务（B/S 架构，Server + Frontend 分离，RESTful API 交互），功能强但部署复杂度数量级上升。 - 选型含义：库形态适合嵌入应用，服务形态适合平台化/图形化编排/高可用场景。

    第一代框架：关键方法与模式

    MetaGPT：SOP 驱动的角色扮演（Role-Playing）

    • 三层抽象：Team（雇佣多个 Role）→ Role（执行多个 Action）→ Action（具体行动，可调工具）。
    • 一个 Agent ≈ 一个岗位（产品经理/程序员/测试员），各司其职，输出物像流水线一样传递——SOP（标准操作流程）是多智能体协作的核心粘合剂。
    • 事件驱动协作：每个 Role 注册自己可执行的 Action、订阅（watch）自己感兴趣的 Action；上游 Action 的输出累积为下游 Action 的输入 context。串行/并行组合即构成工作流。
    • 人类可以顶替任何一个 Role（传入 is_human 参数）：100% 自动化难以实现时，人担任关键决策角色，"半自动化工作流"同样有价值。
    • Role 与 LLM 的交互模式默认 ReAct，可切换为 Plan-and-Act。

    AutoGPT Platform：Agent ⊃ Workflow ⊃ Block

    • 组件三层次：Agent 基于（包含）Workflow，Workflow 基于（包含）Block；Block 代表一次行动（Action），对应 MetaGPT 的 Action；Agent 对应 Role。
    • Agent 不必只做 AI 任务：数据处理、任务调度、通知、系统集成都是合法的 Agent——"智能体本质是自动化工作流，AI 只是其中一类构建块"。
    • Block 是可复用构建块（连接外部服务、数据处理、模型调用、条件逻辑），官方认证 + 自定义扩展都容易。
    • 每个Agent 运行即一个 DAG 图执行，通过 graph_id 标识，异步执行 + 轮询取结果（保证服务可伸缩性）。

    Swarm：移交（Handoff）原语

    OpenAI 开源的极简多智能体框架，核心只有两个概念：

    • Agent = 一组指令（instructions）+ 一组函数（functions）。指令直接成为系统提示词；切换 Agent 时系统提示变、聊天记录不变。
    • Handoff：函数返回另一个 Agent 即完成执行权移交——多智能体路由被压缩成一个函数返回值。
    • run() 循环是全部核心：调 LLM → 有 tool_calls 则执行工具并追加到历史 → 必要时切换 Agent / 更新上下文变量 → 无 tool_calls 则返回。调用间不保存状态（无状态设计）。
    • Python 函数自动转 JSON Schema 传给模型：docstring → 工具描述，无默认值参数 → required，类型提示 → 参数类型。函数出错时错误信息附进聊天，让 Agent 优雅恢复。
    • 设计哲学：Agent 这个原语可以统一表示 agents / workflows / tasks——一个"由指令和函数定义的工作流或步骤"也是 Agent。
    • 底座是 Assistants API（赋予 LLM 调外部工具的能力："不奢望 LLM 自己搞定一切"）。

    DSPy：把提示工程变成机器学习问题

    针对的根本问题：提示词对模型极其敏感，换模型/换指标/改管道都要手工修补提示词——不可持续、无法快速迭代。

    • 核心思路：开发者写组合式 Python 代码（声明式签名），用优化器自动编译出高质量提示词/微调权重，而非手写脆弱提示词。
    • Signature（签名）：模块输入/输出行为的声明性规范，如 "question -> answer: float"——告诉 LM 做什么，不指定怎么做。
    • Module（模块）：每个内置模块抽象一种提示词技术（dspy.Predict、dspy.ChainOfThought、dspy.ReAct），经泛化可处理任意签名；有可学习参数；可直接借鉴 PyTorch 的 nn.Module 心智模型组合成大程序。
    • Optimizer（优化器，前身 teleprompter）：输入三样东西——你的程序、度量指标（metric 函数）、少量训练样例（5~10 个即可、可无标注）——自动调优提示词或权重。选型经验：10 个左右样例用 BootstrapFewShot；50+ 用 BootstrapFewShotWithRandomSearch；只优化指令用 MIPROv2（0-shot）；已有大模型且要高效程序用 BootstrapFinetune 微调小模型。
    • 开发三阶段循环：编程（定任务、定初始管道）→ 评估（收集开发集 + 定义 metric + 评估）→ 优化（跑优化器），不满意回到编程，渐进迭代。
    • 定位：DSPy 是机器学习框架，可嵌入任何 ChatBot/Agent 框架；手工提示词在简单场景仍有用，但不应把赌注全押在手工路线上。

    BabyAGI：任务三代理循环（目标驱动自主任务系统）

    给一个目标后无限循环的三个代理（全部由 LLM 扮演）： 1. 执行代理 execution_agent：(目标, 任务) → 任务结果字符串。 2. 任务创建代理 task_creation_agent：(目标, 上一任务结果, 任务描述, 当前任务列表) → 新任务列表——根据执行结果动态生成后续任务。 3. 优先级代理 prioritization_agent：对任务列表重新排序。

    结果存入向量库（Pinecone 等）为后续任务提供上下文。这是"目标 → 任务队列 → 执行 → 派生新任务"的经典自主循环。

    HuggingGPT：LLM 作控制器的四阶段

    任务规划（解析请求生成任务列表及依赖）→ 模型选择（按专家模型描述分配）→ 任务执行（调用专家模型）→ 响应生成（整合结果）。体现"LLM 当大脑、专家模型当四肢"的路由思想。

    第二代框架：四大技术路径

    AutoGen AgentScope CAMEL LangGraph
    设计哲学 以对话驱动协作 工程化优先的多智能体平台 角色扮演（Role-Playing）自主协作 执行流程建模为状态图
    核心机制 多"可对话"智能体组成群聊，消息传递迭代至目标达成 消息驱动架构（MsgHub + Pipeline），异步解耦、分布式支持 双智能体（AI User + AI Assistant）+ 引导性提示（Inception Prompting） 节点（Node）=计算步骤，边（Edge）=跳转逻辑，天然支持循环
    优势 贴近人类团队协作、角色专业化、UserProxy 天然支持人类在环 高并发、容错恢复、消息持久化、原生分布式、生产级运行时 轻架构重提示，代码最少，协作行为自然涌现 高度可控可预测、原生循环支持、模块化、易插入人工审核节点
    局限 对话不确定性致偏离/循环；"对话式调试"难（没有错误堆栈只有一长串对话） 异步/分布式编程门槛高，简单场景"过度工程化"；生态较新 高度依赖提示工程（调试难定位、不同 LLM 理解有差异）；大规模协作弱（缺路由、状态同步、仲裁机制） 前期代码量多（boilerplate）；缺少涌现式交互；调试需全局理解图机制
    适用 流程化协作任务、人类监督场景 大规模、高可靠生产级多智能体系统 深度协作、创造性任务（双专家模式） 需要精确流程控制、可反思修正、可审计的生产应用

    设计权衡总纲：①"涌现式协作"（AutoGen/CAMEL——定义角色与目标，让协作从对话规则中涌现，贴近人类交互但难预测调试）vs"显式控制"（LangGraph——牺牲涌现换可靠性、可控性、可观测性）；②工程化维度（AgentScope——从"能运行"到"能稳定服务"的跨越：并发、容错、分布式部署）。

    AutoGen：对话驱动协作（以 0.7.4 版为例）

    架构要点：分层设计（autogen-core 底层 + autogen-agentchat 高级接口）、异步优先（async/await，多智能体场景下网络请求为主要耗时，异步避免线程阻塞）。

    核心组件： - AssistantAgent：任务主要解决者，封装 LLM，靠不同 System Message 赋予"专家"角色。 - UserProxyAgent：双重角色——用户的"代言人"（发起任务）+ 可靠"执行器"（执行代码/调工具并反馈），清晰区分"思考"与"行动"，并负责发出 TERMINATE 结束协作。 - RoundRobinGroupChat（轮询群聊）：按预定义顺序依次发言，适合流程固定任务（需求 → 编码 → 审查 → 测试）。

    软件开发团队案例（比特币价格显示应用）：四角色 ProductManager / Engineer / CodeReviewer / UserProxy。关键实现模式： - 模型客户端：OpenAIChatCompletionClient 兼容任何 OpenAI 规范服务（含 Ollama 本地）；非 OpenAI 模型（DeepSeek 等）需传 model_info 字典声明能力边界（function_calling、max_tokens、context_length、json_output 等）。 - 系统消息设计是核心提示工程：每角色独立定义函数，消息中既写职责与流程，也写引导对话转向下一环节的明确指令（"分析完成后说'请工程师开始实现'"）。 - 协作配置三要素：participants 顺序决定发言次序；termination_condition（TextMentionTermination("TERMINATE")）；max_turns 安全阀防无限循环。 - 异步启动：await Console(team_chat.run_stream(task=task)) 流式输出协作过程。

    AgentScope：消息驱动的工业级平台

    分层架构：基础组件层（Message 统一格式 / Memory / Model API / Tool）→ 智能体基础设施层（预构建智能体、ReAct 范式、原生异步与实时控制）→ 多智能体协作层（MsgHub 消息中心 + Pipeline 工作流编排）→ 开发与部署层（Runtime 生产运行时 + Studio 可视化工具链）。

    消息驱动四优势：异步解耦（收发双方无需相互等待）、位置透明（本地/远程对开发者透明，RPC 自动处理跨节点）、可观测性（每条消息可记录追踪）、可靠性（消息持久化与重试，保证最终一致性）。

    生命周期管理：统一基类 AgentBase，开发者只需实现 reply(x: Msg) -> Msg（核心响应逻辑）与可选 observe(x)（写入记忆）——分离内部逻辑与外部通信。

    三国狼人杀案例的关键模式： - 消息驱动代替状态机：游戏流程表达为"在特定上下文中以何种模式进行消息交换"——狼人阶段用 MsgHub(werewolves, enable_auto_broadcast=True, announcement=...) 动态创建私密通信频道；白天讨论为全员广播；预言家查验为点对点请求。 - 结构化输出约束游戏规则：为不同行为定义 Pydantic 模型（DiscussionModelCN：reach_agreement/confidence_level/key_evidence；WitchActionModelCN：use_antidote/use_poison/target_name）——女巫不能对同一目标又救又毒等规则通过字段定义与验证自动执行。 - fanout_pipeline 并行收集：投票阶段并行向所有智能体发送相同消息并异步收集，模拟"同时投票"。 - 容错：单个智能体异常时创建默认响应，游戏继续。 - 双重角色建模：系统提示词融合"游戏角色（狼人）+ 三国人格（曹操）"——不同人物扮演同一游戏角色会展现不同策略风格（曹操狼人狡猾善伪装，张飞狼人直接冲动）。

    CAMEL：角色扮演自主协作

    两大核心概念： - 角色扮演：双智能体互补角色——AI User（提需求、下达指令，如"懂股票不懂编程的资深交易员"）+ AI Assistant（执行操作，如"精通编程不懂股票的程序员"）。任务解决被转化为跨领域专家的对话。 - Inception Prompting（引导性提示）：对话开始前注入的结构化初始指令，四要素——明确自身角色、告知协作者角色、定义共同目标、设定行为约束与沟通协议（AI User 一次只提一个具体步骤；AI Assistant 完成上一步前不追问；用特定标志标识完成）——确保对话不偏离、不陷入无效循环。

    电子书创作案例（心理学家 + 作家合写"拖延症心理学"）：RolePlaying(assistant_role_name="心理学家", user_role_name="作家", task_prompt=...) 封装全部提示工程；init_chat() 自动生成开场白；step() 驱动每轮交互（作家提需求 → 心理学家给内容），上一轮 assistant 输出作为下一轮输入；<CAMEL_TASK_DONE> 标志或轮次上限终止。协作自然分四个阶段：框架搭建与目标对齐（1-5 轮）→ 核心内容生成与知识转译（6-20 轮，稳定的"请求-响应"循环：心理学家供硬核知识、作家做"翻译官"转成比喻案例）→ 迭代优化与质量保证（作家审流畅性、心理学家做事实核查）→ 总结升华。

    LangGraph：状态图与循环

    三要素： 1. 全局状态（State）：共享的 TypedDict 对象（对话历史、中间结果、迭代次数），所有节点可读写；Annotated[list, add_messages] 处理消息追加。 2. 节点（Nodes）：接收当前状态、返回更新后状态的 Python 函数。 3. 边（Edges）：常规边固定流向；条件边（Conditional Edges） 用判断函数根据状态动态决定跳转目标——实现循环与分支的关键。

    组装：StateGraph(AgentState) → add_node → set_entry_point → add_edge / add_conditional_edges（返回字符串映射到目标节点或 END）→ compile(checkpointer=InMemorySaver) → app.stream(inputs)。

    三步问答助手案例：理解（understand_query_node：一个提示同时完成"意图总结 + 生成最优搜索关键词"，比直接用原始提问搜索质量显著更高）→ 搜索（tavily_search_node：try/except 包裹，失败时把 step 置为 "search_failed"）→ 回答（generate_answer_node：检查 step 值走条件逻辑——搜索失败则基于 LLM 自身知识回退回答，成功则基于搜索结果生成有据可依的回答）。

    选型建议

    • 按任务性质选型：高并发 7×24 客服等大规模高可靠系统 → AgentScope；双专家深度协作写作等创造性任务 → CAMEL；流程固定、可审计的金融风控审批等生产应用 → LangGraph；流程化协作任务、需要人类监督 → AutoGen。
    • 库形态 vs 服务形态：库形态（MetaGPT 类）适合嵌入应用，服务形态（AutoGPT Platform 类）适合平台化/图形化编排/高可用场景——评估框架时要把服务形态的部署成本（数据库、缓存、Docker 依赖链）算进选型。
    • 涌现式 vs 显式控制：要协作自然涌现选 AutoGen/CAMEL，要确定可靠可审计选 LangGraph；两者不可兼得时，生产系统优先显式控制。
    • 轻量级框架 ≠ 玩具：Swarm 几百行代码固化了一组多 Agent 编排最佳实践；警惕 Design by Buzzwords、以复杂为荣的倾向，围绕解决业务痛点选型，选"能否以最小抽象层让你专注业务逻辑"。
    • 第一代抽象仍然适用：SOP/Role-Action 分层、Handoff 原语、Signature 编译、任务三代理循环等抽象比具体框架耐用，换框架时迁移的是这些设计思想。

    术语 含义

    Inception Prompting CAMEL 的引导性提示：明确双方角色、共同目标与沟通协议的初始指令
    Handoff Swarm 中通过函数返回值把对话执行权移交给另一个 Agent

    经验与常见坑

    • 中文教程/翻译文档普遍滞后于快速演进的框架（AutoGPT 新旧版本完全不兼容），学新框架直接读英文官方文档，用翻译插件辅助。
    • 独立部署型框架（AutoGPT Platform 类）依赖链很长（数据库、缓存、Docker），评估框架时要把部署成本算进选型。
    • 轻量级框架 ≠ 玩具：Swarm 几百行代码固化了一组多 Agent 编排最佳实践；资深工程师应警惕 Design by Buzzwords、以复杂为荣的倾向，围绕解决业务痛点选型。
    • 自主循环系统（AutoGPT/BabyAGI 类）的已知顽疾：分心、陷入循环、成本失控、缺长期记忆——任何"目标驱动无限循环"的设计都要配终止条件、预算上限和记忆机制（上下文工程一篇有系统解法）。
    • MetaGPT 的 Role watch 机制提示：多智能体协作可以用"发布/订阅 + 事件"实现，不必点对点硬编码调用关系——解耦且易扩展。
    • 多智能体系统设计的第一步是角色划分：把复杂任务分解为多个领域"专家"处理的子任务；系统消息（System Message）的质量直接决定协作效率。
    • 群聊/轮询协作必须设置终止条件与最大轮次，否则对话无限循环烧钱。
    • 对话式框架的调试是"对话式调试"：得到的是一长串对话历史而非错误堆栈——需设计对话质量监控，检测偏离主题或循环时干预。
    • CAMEL 协作效果不佳时难定位：是角色定义、任务描述还是交互规则的问题；不同 LLM 对相同提示理解有差异。
    • AgentScope 的消息驱动 + 异步 + 分布式复杂度对简单场景是负担，原型开发慎用；LangGraph 强项是执行确定、可靠的流程，不是模拟开放式社会性协作——按任务性质选型。

    ⚠️ 时效性说明

    • Swarm 已被 OpenAI 官方标记为实验性项目并由 Agents SDK 接续；AutoGPT/MetaGPT/DSPy API 均大幅演进。本文只提炼架构抽象（SOP/Block/Handoff/Signature/优化器/任务循环），具体类名和版本号不要照用。
    • Assistants API 是 OpenAI 已宣布计划弃用的旧接口，理解其"工具外挂"思想即可，勿再基于它做新设计。
    • AutoGen 0.7.4 的分层架构（autogen-core / autogen-agentchat）与 AgentScope 的 API（AgentBase.reply、MsgHub 签名）随版本演进变化较快，实践前查最新文档。
    • CAMEL 已从双智能体框架扩展出多模态、工具集成、workforce 多智能体模块，与 LangChain/CrewAI/AutoGen 有互操作。
