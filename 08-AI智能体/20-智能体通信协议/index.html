    智能体通信协议

    更新于 2026-11-03

    一句话定义：智能体通信协议是标准化智能体与外部工具、智能体与智能体、以及大规模智能体网络之间交互方式的技术规范，主流代表为 MCP、A2A、ANP 三种。

    单体智能体（具备推理、工具调用、记忆能力）在走向复杂 AI 系统时面临三个根本限制：工具集成困境——每接一个新外部服务（GitHub、数据库、文件系统）都要手写专门的 Tool 类，工作量大且互不兼容；能力扩展瓶颈——智能体被锁死在预定义工具集内，无法运行时发现新服务；协作缺失——多专业智能体（研究员+撰写员+编辑）协作只能靠手动编排。通信协议的核心价值就是提供一套标准化接口规范，像 TCP/IP 之于互联网设备那样，让智能体以统一方式访问各种外部服务，并让服务方与调用方可以来自不同开发者。

    有了协议后，手写适配器的模式被"连接即获得全部能力"取代。以 MCP 为例：

    # 传统方式：每个服务手写一个 Tool 类（HTTP/认证/错误处理全要重复写）
# 协议方式：连接到 MCP 服务器，自动获得所有工具
github_mcp = MCPTool(server_command=["npx", "-y", "@modelcontextprotocol/server-github"])
database_mcp = MCPTool(server_command=["python", "database_mcp_server.py"])
agent.add_tool(github_mcp)
agent.add_tool(database_mcp)

    核心原理：三种协议的定位与理念

    MCP（Model Context Protocol）—— 智能体与工具的桥梁

    由 Anthropic 团队提出，标准化智能体与外部工具/资源的通信。设计哲学是"上下文共享"：它不只是 RPC 协议，还允许智能体与工具之间共享丰富上下文（如访问代码仓库时，服务器可同时提供文件内容、代码结构、依赖关系、提交历史），让智能体做出更智能的决策。常用类比：MCP 是智能体的"USB-C"——统一了各模型平台（Claude、GPT 等）访问工具的方式，切换模型无需重写工具代码。

    A2A（Agent-to-Agent Protocol）—— 智能体间的对话

    由 Google 团队提出，实现智能体之间的点对点通信。设计哲学是"对等通信"：每个智能体既是服务提供者也是消费者，可主动发起请求也可响应请求，避免了中心化协调器（星型拓扑）的单点故障、性能瓶颈和扩展困难。与 MCP 最大的区别在于其核心抽象是任务（Task）与工件（Artifact），并为任务定义了标准化生命周期（创建、协商、代理、执行中、完成、失败），支持任务协商、进度跟踪和异常处理。请求生命周期四步骤：代理发现 → 身份验证 → 发送消息 API → 发送消息流 API。

    ANP（Agent Network Protocol）—— 智能体网络的基础设施

    开源社区维护的概念性协议框架（生态尚不成熟）。解决的是"如何在大规模网络中发现和连接智能体"，设计哲学是"去中心化服务发现"。其整体流程三步骤：

    1. 服务发现与匹配：通过公开发现服务按语义/功能描述查询，定位符合条件的智能体；发现服务通过爬取各智能体暴露的标准端点（.well-known/agent-descriptions）建立索引。
    2. 基于 DID 的身份验证：请求方用私钥对含自身 DID（去中心化身份标识）的请求签名，接收方解析 DID 获取公钥验证签名，建立可信通信。
    3. 标准化服务执行：双方按预定义标准接口和数据格式交换数据或调用服务。

    核心是用 DID 构建去中心化信任根基 + 标准化描述协议实现动态发现，使智能体无需中央协调即可在互联网上形成协作网络。

    三协议对比与选型

    维度 MCP A2A ANP
    提出方 Anthropic Google 开源社区
    解决的问题 如何访问工具 如何与其他智能体对话 如何在大规模网络中发现/连接智能体
    设计哲学 上下文共享 对等通信 去中心化服务发现
    适用场景 单个智能体增强能力（文件/数据库/API） 小规模多智能体紧密协作、任务协商 大规模开放智能体网络、服务发现/路由/负载均衡

    选型经验：协议均处发展早期；MCP 生态相对最成熟，优先选大公司背书、维护活跃的 MCP 工具。小规模协作选 A2A，大规模网络考虑 ANP。三者可组合使用。

    关键概念

    MCP 架构与核心能力

    MCP 采用 Host / Client / Server 三层架构。以 Claude Desktop 问"我桌面上有哪些文档"为例：Host（Claude Desktop）接收用户提问、管理与模型交互；Client（Host 内置的 MCP Client）在模型需要文件信息时与对应 Server 建立连接、收发请求；Server（文件系统 MCP Server）执行实际文件扫描并返回结果。优势是关注点分离：开发者只需开发 Server，无需关心 Host/Client 细节。

    MCP 提供三大核心能力：Tools（主动，执行操作）、Resources（被动，提供数据）、Prompts（指导性，提供模板）。

    LLM 如何决定调用哪个工具——完整流程： 1. 工具发现：Client 连接 Server 后调用 list_tools() 获取工具名、描述、参数定义； 2. 上下文构建：工具列表转为 LLM 可理解格式，注入系统提示词； 3. 模型推理：LLM 根据工具描述与对话上下文决定是否/调用哪个工具； 4. 工具执行：Client 经 MCP Server 执行工具； 5. 结果整合：结果回传 LLM 生成最终回答。

    推论：工具描述的质量直接决定 LLM 是否会用、用得好不好。

    MCP 与 Function Calling 的关系

    两者不是竞争而是互补：Function Calling 是 LLM 的内在能力（理解何时调用函数、生成调用参数），MCP 是工程层的基础设施协议（标准化描述与调用工具）。类比：Function Calling 是"学会打电话"的技能，MCP 是"全球统一的电话通信标准"。传统 Function Calling 的问题：OpenAI 与 Claude 的工具定义格式、响应格式互不兼容，且工具函数要自己实现；MCP 则模型无关、可复用社区现成服务器。

    MCP 传输方式

    传输层无关（Transport Agnostic）。HelloAgents 基于 FastMCP 2.0 支持五种传输：

    传输方式 适用场景 说明
    Memory 单元测试、快速原型 内存传输，可连内置演示服务器
    Stdio 本地开发、调试 通过 stdin/stdout 与本地进程通信，最常用
    HTTP 生产环境、远程服务、微服务 用底层 MCPClient 连接远程 URL
    SSE 实时通信、流式处理、长连接 Server-Sent Events
    StreamableHTTP 需双向流式通信的 HTTP 场景 —

    注：MCPTool 包装器主要用于 Stdio 和 Memory 传输；HTTP/SSE 等远程传输建议直接用 MCPClient。

    MCP 工具自动展开机制

    将 MCPTool 添加到 Agent 时会自动把 MCP 服务器的所有工具展开为独立工具（以 name 为前缀避免多服务器冲突，如 name="fs" 展开出 fs_read_file、fs_write_file），并按工具参数 schema 自动做类型转换（如 Agent 生成的字符串 "25" 自动转为数字 25.0）。内部链路：连接服务器发现工具 → 为每个工具创建包装器并注册到 Agent 工具注册表 → Agent 调用时包装器将调用转为标准 MCP call_tool 格式。

    A2A 核心概念

    • Task（任务）：协作的基本单元，有标准化生命周期，支持协商与状态同步；
    • Artifact（工件）：任务产出物；
    • 点对点（P2P/网状拓扑）架构取代中央协调器（星型拓扑）。

    ANP 核心概念

    • 服务发现中心：注册与发现服务，可按类型查找、按元数据（负载/成本）选择；
    • DID 身份验证：去中心化信任基础；
    • Agent 网络：节点注册、按能力匹配建立连接、网络统计。

    分类/类型：HelloAgents 框架的协议集成

    HelloAgents 采用三层架构集成三种协议：

    1. 协议实现层：MCP 基于 FastMCP 库（客户端+服务器）；A2A 基于 Google 官方 a2a-sdk（可选依赖，安装 pip install a2a-sdk）；ANP 为自研轻量级概念实现（服务发现/注册）。
    2. 工具封装层：MCPTool、A2ATool、ANPTool 均继承 BaseTool，提供一致的 run() 接口——所有协议统一抽象为 Tool。
    3. 智能体集成层：ReActAgent、SimpleAgent 等通过 Tool System 使用协议工具，不感知底层协议细节。

    经验与常见坑

    • 多 MCP 服务器必须指定不同的 name：name 作为展开工具名的前缀，重名会冲突。
    • 工具描述质量决定调用效果：LLM 完全依据描述决定是否使用工具，描述要清晰、准确。
    • A2A 生态不成熟：现有实现多为 Sample Code，Python 实现繁琐，实战可用 SDK 封装模拟协议思想。
    • 协议早期不必造轮子：优先复用社区现成 MCP 服务器（文件系统、GitHub、数据库等），减少重复开发。
    • 工具调用要有异常处理：读取不存在的文件等操作应 try/except 后重试、降级或报告用户。
    • Stdio 是本地开发首选：npx 可自动下载并运行社区 npm 包形式的 MCP 服务器，零配置上手。

    • MCP Servers Website（mcpservers.org）：官方目录网站，可搜索筛选；

    典型应用方向：Playwright 自动化网页测试（开浏览器/填表单/截图验证）、Obsidian+Perplexity 智能笔记、Jira+GitHub 项目管理自动化、YouTube+Notion 内容创作工作流。

    构建与发布自定义 MCP 服务器

    自建 MCP 服务器的动机：封装企业内部业务逻辑、安全访问私有数据（内网数据库/API）、针对高频调用做性能优化、实现标准服务未覆盖的定制功能。

    构建模式（以天气查询服务器为例）：

    from hello_agents.protocols import MCPServer

weather_server = MCPServer(name="weather-server", description="真实天气查询服务")

def get_weather(city: str) -> str:
    """获取指定城市的当前天气（工具的 docstring 即工具描述）"""
    ...

# 注册工具并运行
weather_server.add_tool(get_weather)
weather_server.run()

    客户端测试与 Agent 集成：MCPClient(["python", "weather_mcp_server.py"]) 逐个 call_tool 验证；或 MCPTool(server_command=[...]) 添加到 Agent，工具自动展开（如 mcp_get_weather）供 LLM 直接调用。

    发布到 Smithery（MCP 服务器的发布平台，类比 PyPI/npm，可发现、一键安装、看使用统计、自动更新）：

    • 标准发布目录：README.md、LICENSE、Dockerfile（推荐）、pyproject.toml（必需）、requirements.txt、smithery.yaml（必需）、server.py；
    • smithery.yaml 关键字段：name（唯一标识）、displayName、description、version、categories/tags、runtime（container）、startCommand（tools 列表声明各工具名与描述）；
    • pyproject.toml 为必需的 Python 标准配置（元数据、依赖、Python 版本要求）；
    • Dockerfile 建议：python:3.12-slim 基础镜像、EXPOSE 8081（Smithery 标准端口）、启动命令 python server.py；
    • 发布流程：Fork/建 GitHub 仓库 → 登录 smithery.ai → Publish Server 填仓库 URL；发布后可用 Smithery CLI 安装（smithery install xxx）、在 Claude Desktop 中配置（{"mcpServers": {"weather": {"command": "smithery", "args": ["run", "weather-mcp-server"]}}}）、或在 HelloAgents 中作为 MCPTool 使用。

    实战模式速记

    • 多 Agent 流水线（MCP）：Agent1（GitHub 搜索专家，挂 gh MCP 工具）→ 结果传给 Agent2（文档生成专家，挂文件系统 MCP 工具）→ 保存报告。
    • A2A Agent 网络：多个 A2AServer 各注册 skill（researcher/writer/editor），后台线程启动在不同端口，客户端依次 execute_skill 串联协作；或用 A2ATool 把远端 Agent 挂到协调者 Agent 上（如智能客服：接待员 Agent 挂技术专家与销售顾问两个 A2ATool，自动路由问题）。
    • A2A 协商：Agent 间可交换提案（proposal）与反提案（counter_proposal），按约束（如最短工期）接受或拒绝。
    • ANP 负载均衡：注册多个同类型服务（metadata 含 load），每次请求选负载最低者并递增其负载——分布式任务调度系统即按此让调度 Agent 结合 CPU/内存/GPU 元数据智能选节点。

    ⚠️ 时效性说明

    • 三种协议均处于发展早期（原文写作时），生态与 SDK 更新快；A2A 当时实现多为示例代码，ANP 尚无成熟生态，HelloAgents 的 ANP 实现为概念性模拟。
    • MCP 社区工具的可用性取决于维护者，建议优先选用大公司背书、维护活跃的服务器。
    • 原文引用的 HelloAgents 框架版本（hello-agents 0.2.2）与 Smithery 发布流程细节可能随平台演进变化。
