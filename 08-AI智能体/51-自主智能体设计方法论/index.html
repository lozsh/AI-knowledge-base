    自主智能体设计方法论

    /> 来源：公开课程资料自学整理（更新于 2026-11-03）

    一句话概括：自主型智能体 = AI 应用 + 复杂业务应用的结合体，设计它需要"机器教学"思维 + DDD 战略层方法 + 明确的运行环境约束，而不是上来就堆框架和提示词。

    核心概念

    自主性 ≠ 自动化（这是全课程的立论基础） - 自动化：传统应用也可以高度自动化，流程硬编码，编码完成后行为不再改变。 - 自主性：系统是"柔性的"，由 AI 算法驱动，编码完成后仍能接收反馈、自动调优。 - 自主型智能体的本质区别：能从"所见所闻"中学习并制定管理决策。 - 自主型智能体（LLM 驱动）被视为更广义"自主型 AI 应用"的子集。

    构建是团队行为：AI 专家（懂算法）+ 应用开发专家（懂编程和领域建模）+ 领域专家（懂业务流程），三者缺一不可。AI 技术专家不等于领域解决方案专家，需保持"空杯心态"。

    复杂自主智能体的两大组成部分 1. 与 AI 直接相关的部分：LLM 交互、AI 算法（可用深度强化学习 DRL 概念建模）。 2. 不与 AI 直接相关的部分：普通业务逻辑——这部分照常用 DDD/OOD 等成熟软件方法设计。 - 结论：学了 LLM 开发不等于可以抛弃 DDD、OOD；没有它们指导，LLM 生成的代码和架构质量照样低。

    关键方法/模式

    1. 运行环境决定设计（脱离环境谈架构 = 耍流氓）

    三类典型运行环境的约束推导：

    环境 关键约束 设计推论
    边缘云（工业场景） 实时性、4个9高可用、资源有限、网络不稳、供电不稳、安全防护弱 服务完全无状态（可水平扩展的前提）；轻量级集群代替 K8s；只能部署小模型（约 14B 以下）；断点恢复；多网络通道冗余；严格认证授权 + 传输加密 + 入侵检测
    企业私有云/局域网 条件更好的边缘云 同上，可适当放宽
    客户端设备（PC/手机） 资源最少、最易受攻击 不建议把复杂智能体做成纯客户端应用

    2. 机器教学（Machine Teaching）三步法

    来自《自主 AI 设计》（Kence Anderson）：把构建智能体看成"教师训练学生"。

    1. 确定要教的技能清单：每个模块（感知、行动、监控、选择）命名并标记为技能；明确教的技能越多，学习成功越快（指数级差异）；约见领域专家面谈确保清单完整。
    2. 设计技能如何协同：画出技能间关系（"连连看"），记录在架构设计中。
    3. 为每项技能选择最合适的决策技术：LLM 交互、机器学习、决策表、启发式等按优劣选型，不必事事上 LLM。

    配套思想：搭建机器教学平台 + 模拟器——智能体需要一个能安全试错、可加速时间、可并行多实例的"虚拟练习室"。

    能力成长五阶段（类比人类）：初学者（专家规则）→ 高级初学者（识别规则例外）→ 胜任者（行动抽象为策略并权衡）→ 精通者（编写并随机应变）→ 专家（直觉化、形成风格）。

    3. 提示词工程的结构化与技巧

    • 结构化两模板：role-context-task 三段；或 ICDO 四段（instruction-context-input data-output indicator）。
    • 四种手工技巧（从简到繁）：
    • 少样本学习（FSL）——示例的重点是背后逻辑，不是复杂性；
    • 少样本思维链（CoT）——复杂问题引导逐步思考；
    • 思维树（ToT）——中间思维可评估、保留最优分支，适合需要探索/预判的任务；
    • 自洽性思维链（CoT with Self-consistency）——多推理路径采样取多数答案，"一题多解选最优"。

    4. 与 LLM 交互的九种设计模式

    本质：都是把人类思维/管理模式结构化为提示词，让 LLM 规划并调用工具迭代执行。没有最好的模式，只有最适合的模式，从用户需求出发选。

    • ReAct：思考 → 行动 → 观察
    • Plan and Solve / Plan and Execute：计划 → 任务列表 → 再计划
    • REWOO（Reason without Observation）：计划（含依赖关系）→ 行动（全程无观察介入，节省 token）
    • LLMCompiler：计划 → 并行行动 → 合并结果
    • Basic Reflection：从步骤中反省学习
    • Reflexion：通过强化学习式反思增强下一步规划
    • LATS：ToT + 强化学习式反思
    • Self-Discover：任务中自发现推理结构
    • Storm：搜索大纲 → 逐主题搜索 → 汇总生成长文

    工程含义：ReAct 和 Plan-and-Solve 适合任务执行型智能体；若能用 DSPy 这类自动提示词框架实现，优先用框架，避免手工提示词的维护泥潭。

    5. DDD 战略层指导架构

    • 分层架构：层间单向依赖，禁止循环依赖；复杂系统可用六边形架构（端口与适配器），领域模型居中，外围功能各接端口。
    • 限界上下文：划分 Agent 工作组的依据（同层内多 Agent 怎么分组），也是组件化/微服务边界。
    • 参考分层范例——AI 驱动的 DevOps 系统四层：
    • 数据输入和监测（传感器/日志/遥测，提供系统状态全貌）
    • 决策引擎（可配置，为每个 Agent 配 AI/ML 或启发式算法）
    • 执行和控制（API/自动化工具执行扩容、负载均衡、故障恢复）
    • 反馈回路和持续学习（决策结果回流，长期适应性的关键）

    6. 企业级应用的工程流程（以"企业员工 AI 助理"为例）

    1. 产品需求层：需求文档（详细用例）不可省——没有它 UED/测试/运维无法高效协作。
    2. UI 设计与技术架构设计并行开展，架构师参与 UI 讨论（UI 影响架构决策）；AI 应用的 UI = 一半传统 GUI + 一半 NUI（自然语言界面，含语音 VUI）。
    3. 架构文档内容：领域模型设计（最重要）、ER 设计、对外 API 设计、安全设计、高可用设计，AI 专属策略另立章节；文档随迭代持续更新。
    4. 领域建模次序：先名词（实体）后动词（操作）；类图雏形（只有实体名）先团队讨论达成共识，再补属性、操作，再补活动图/序列图。
    5. 防止"设计瘫痪"：识别出足以启动一轮迭代的实体就动手，带着开发反馈进入下一轮。
    6. 开发前"扫雷"：先解决最难的两个技术不确定点（如多模态输入输出、与 Agent 平台的 API 集成），为后续开发铺路。

    经验与常见坑

    • 陷阱一：解决方案与问题混为一谈。现有方案只是业务问题的一种解法，别拿着锤子看什么都是钉子。
    • 陷阱二：过于关注局部而忽视全局。看到完整端到端流程前，很难识别关键技能并做权衡；过早局部优化事倍功半。
    • 陷阱三（两个对立极端）：
    • 追求完美设计走瀑布式，忽略迭代——智能体是学习系统，教之前永远不知道它学到什么；
    • 完全忽略设计规划、盲目敏捷——复杂自主智能体更像钢铁厂而非普通软件，需要预先完整设计，但实现反馈后及时修改设计（增量 + 迭代，而非一次性瀑布）。
    • 手工提示词工程的不可持续性：换模型、换指标、改管道都要修补提示词；提示词专家离职即断档，提示词越积越复杂。能自动优化就自动优化。
    • 语音方案选型：传统链路 ASR→NLU→业务→NLG→TTS；Web Speech API 依赖浏览器厂商云端（中文差、延迟大），可改配私有化 ASR/TTS；多模态 LLM 直接收语音延迟更低但硬件/成本门槛高——架构上要为未来切换留灵活性。
