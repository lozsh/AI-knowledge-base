    流处理与消息系统经典设计：从 Storm 到 Dataflow

    更新于 2026-11-03

    流式系统三代进化：S4 迈出第一步 → Storm 用异或做到"至少一次" → MillWheel 解决"正好一次"与状态持久化 → Dataflow 把一切抽象成窗口+触发器+增量策略的统一模型，从此流批一体。

    核心概念

    为什么需要流式系统：MapReduce 为高吞吐设计、无低延迟考虑，且输入是边界明确的数据；每分钟跑一次 MapReduce 会遭遇双重灾难——任务固定开销占比畸高 + 输入文件极度碎片化丧失顺序读优势。广告点击率、热搜这类"分钟级反馈"需求催生了流式计算。

    三代系统的关键一跃：

    系统 年份 架构 消息保障 关键贡献/短板
    S4 2010 (Yahoo) 无中心完全对称，PE 对象 基本没有 首创 DAG 模型；无时间窗口、容错丢状态、不支持动态扩容
    Storm 2011 (Twitter) Nimbus+Supervisor+Worker 至少一次（Acker 异或追踪） 逻辑与并行度解耦；仍无状态持久化、无事件时间窗口
    MillWheel 2013 (Google) Computation+Key 分段 正好一次 低水位、状态/Checkpoint 持久化、租约防僵尸进程
    Dataflow 2015 (Google) 编程模型（非系统） 正好一次 窗口分配/合并 + 触发器 + 累积/撤回，流批一体的统一抽象

    流批一体的本质：批/流的核心差异不是数据集大小或框架，而是有界 vs 无界。有界数据可以用流式引擎重放处理；无界数据也可以微批处理（Spark Streaming 就是微批）。把批的记录数限制到每批一条，就是流——MapReduce 的有界数据集只是 Dataflow 无界数据集的特例。

    关键设计/原理

    Kafka：大数据的传输层

    • 诞生背景：日志从应用服务器进 Hadoop，要么 cronjob 定时上传（故障窗口丢数据），要么直写 HDFS（百级客户端 7x24 高并发压垮系统 + 小文件灾难 + 同文件多客户端在 primary chunkserver 排队竞争）。Scribe/Flume 类日志收集器用多层树状汇集解决了传输，但与下游靠文件名等隐式协议耦合，且不定时 Dump 之间数据不可见。
    • 模型：Producer → Broker（Topic 按业务分组 + Partition 按数据分区）→ Consumer。Consumer Group 双层语义：不同 Group 各自消费全量（不同用途），同 Group 内多个 Consumer 分摊分区（并行扩容）。
    • 两个反直觉设计：
    • 拉而非推，进度由消费者自持：传统消息队列/推送模式必须维护"每条消息被哪些下游处理完"的状态，消息没被全部确认就不能删，内存与复杂度爆炸。Kafka 让 Consumer 自己维护在分区日志中的 offset，Broker 不存任何消费状态。
    • 裸用顺序文件当消息队列：无 message-id、无复杂内存结构；Partition 逻辑上是一个日志，物理上拆成等大 Segment 顺序追加。读写全是磁盘顺序 IO。
    • 性能三板斧：依赖 Linux 页缓存（读写时间局部性极强，刚写即被读；还避开 JVM GC 开销与缓存冷启动抖动）、mmap 写入、sendfile 零拷贝网络传输。
    • 分布式协调：无 Master，Broker/Consumer 全注册到 ZooKeeper（类似 Chubby 的粗粒度锁），所有权注册表记录"分区→消费者"映射，Broker/Consumer 增减时触发再平衡（简单平均分配，offset 已持久化故接手容易）。
    • 高可用（0.8 后）：每分区 3 副本，Producer 只写 Leader，Follower 拉取并 Ack；acks 参数在可用性与性能间滑动（acks=0 到 all）。顺序性只保证分区内有序，跨分区无全局顺序；只有 Offset 语义使单条消息级事务很难做。
    • ⚠️ 2011 论文时期分区没有副本，高可用是后来补的。

    Lambda 与 Kappa 架构

    • 共同的抽象：View = Query(Data)。原始日志是不可变的主数据，报表/看板都是对它的一次查询产生的视图；程序 Bug 改的是 Query 而非 Data——把"开发人员会写错代码"纳入架构设计，重算即可修复，这是 Lambda 思想最耐用的部分。
    • Lambda：批处理层（MapReduce，准确、易重算）+ 实时处理层（Storm，低延迟）+ 服务层（数据库，批结果不断覆盖实时结果）。用户只查服务层。缺点：一切做两遍——双倍计算资源、双套代码，且两套逻辑对同一视图的理解可能不一致引入新 Bug。
    • Kappa（Jay Kreps, 2014）：利用"日志全在 Kafka 本地盘、重放只是改 Offset"这一特性，去掉批处理层——程序要改时部署新版 Topology，重放历史日志生成视图新版本，追上进度后切换查询、下线旧版。代价是需要按"重放 N 天日志"的规模预留 Kafka 保留期与算力。

    MillWheel：第二代流式系统的三件套

    • 模型：消息 =（Key, Value, Timestamp）三元组；Computation 订阅/输出 Stream，通过 key_extractor 提取 Key——同一流可被多个 Computation 用不同 Key 维度复用。Key 按 Bigtable Tablet 式分段调度（Computation+一段 Key），既保留"Key 级状态绑定"的好处又避免 S4 海量 PE 对象问题。
    • 低水位（Low Watermark）：每个 Computation 未处理完消息的最早时间戳，取 min(自身 oldest work, 各上游低水位)，由 Injector 模块全局收集分发。系统据此判断"某时间点前的数据都到齐了没"。实测仅 0.001% 的日志晚到水位之后，且因数据全持久化仍可纠正。
    • 正好一次：收到消息先 BloomFilter 分段去重 → 执行业务逻辑 → 所有状态变更（State/Timer/待发送记录）一次性提交 Bigtable/Spanner → 回 Ack → 下游发送前先写 Checkpoint（类 WAL）。Checkpoint 必须在发送前落盘的原因：同一时间窗口内先发消息 X 再发值不同的 Y 时，网络乱序会让下游无法去重——只有"先持久化再重放"能保证一致。
    • Strong vs Weak Production：去重与 Checkpoint 有开销，无状态/幂等计算（过滤、max/min）可降级为 Weak，只需下游做 Strong。
    • 租约防僵尸进程：Master 网络分区时会在新节点重启 Computation，旧进程可能还活着并持有 Timer——每个进程持租约 Token，写入必须带 Token，新进程启动即作废旧租约。这是所有分布式系统保证 Single-Writer 的通用机制（GFS/Bigtable 同款）。

    Dataflow：统一的编程模型

    • 基础算子只有两个：ParDo（并行处理，≈Map）与 GroupByKey（按 Key 分组，≈Shuffle），可像串联多个 MapReduce 一样多层组合。
    • 三大抽象：
    • 窗口模型（What/Where）：事件按事件时间而非处理时间归属窗口。固定窗口、滑动窗口（窗口大小+滑动周期两个参数）、会话窗口（超时时间定义）。核心是 AssignWindows（事件→(key,value,event_time,window)，一个事件可进多个窗口）+ MergeWindows（窗口重叠则合并）——会话统计、乱序数据都靠这对组合，数据乱序到达结果不变。
    • 触发器模型（When）：决定"何时把窗口结果发往下游"。低水位方案有两个天然缺陷——水位后仍有迟到数据（结果不准）、单条迟到数据把水位拖得极低（结果迟迟不发）。Dataflow 借 Lambda 思想：先尽快发一版，再用可组合的触发器（基于水位/处理时间/记录数/自定义）不断修正。
    • 增量处理策略（How）：触发后旧结果怎么办——抛弃（空间省，适合监控告警）、累积（新结果覆盖旧结果，主流统计的首选）、累积并撤回（还能撤回已发的错误结果；会话合并场景必需，实现最难，连 Apache Beam 都长期未支持）。
    • 影响：Apache Beam 即 Dataflow 模型的开源接口实现；Flink 同样向该模型对齐。

    术语表

    术语 含义
    Spout / Bolt / Topology Storm 的数据源 / 处理单元 / 整体 DAG 任务
    Acker + XOR 校验码 Storm 用异或追踪 Tuple 树是否全部处理完，每树仅 16 字节状态
    至少一次 / 正好一次 可能重复处理 / 恰好处理一次（需去重或幂等）
    Offset 消费者在分区日志中的位置，消费进度的唯一持久化状态
    Consumer Group 同用途消费者分摊分区，跨组各自全量消费
    acks / ISR 写入确认级别 / 与 Leader 保持同步的副本集合
    低水位 未处理完消息的最早事件时间，判断"数据到齐没有"
    AssignWindows / MergeWindows 事件归属窗口 / 重叠窗口合并（会话统计的核心）
    触发器 / 水位线 何时输出结果 / "数据是否到齐"的进度估计
    累积并撤回 输出新结果的同时撤回旧结果，保证最终正确性

    经验与常见坑

    • 设计约束来自业务假设：Kafka vs 传统 MQ vs Scribe 的差异本质是对需求的假设不同——海量日志可容忍丢几条但要吞吐，交易消息一条不能丢但量小。选型先写清楚"我们能容忍什么"。
    • 至少一次 + 消费端幂等 = 正好一次：去重可用 BloomFilter 按时间窗切片（固定内存覆盖 N 分钟重复）。注意 BloomFilter 有小概率误判，计费级场景需更强的去重（唯一键/状态存储）。
    • 事件时间 ≠ 处理时间：用消息到达时间替代事件发生时间，重放日志时统计结果会完全错误（几天数据挤进几分钟）；预算类、对账类业务必须用事件时间窗口。
    • 把故障恢复要用的状态持久化，是一切容错的地基：Storm 的进步（异或追踪）止步于"知道丢了要重发"，MillWheel 的进步在于状态+Checkpoint 落盘后"重发也能续上"且支持在线扩容迁移。
    • 批处理与流式代码分开写是 bug 工厂：Lambda 架构最大隐性成本是两套逻辑对同一业务口径的理解偏差；能 Kappa 就 Kappa，能流批一体就流批一体。
    • 异或追踪、租约、WAL 式 Checkpoint 都是可移植的小巧思：每树 16 字节追踪全拓扑消息生命周期、写入带租约 Token、发送前先落日志——这些模式在任何自研流式/任务系统里都能复用。

    ⚠️ 时效性说明

    • Storm/S4 已基本退出主流（S4 于 2014 年从 Apache 退役），现实中的流式引擎是 Flink 与 Kafka Streams；本文价值在于设计思想的演化脉络而非选型指南。
    • Kafka：早期 Offset/所有权存 ZooKeeper，新版已由内部协议（KRaft）管理；Exactly-Once 已由事务 + 幂等 Producer 原生支持，不再只靠消费端幂等。
    • "累积并撤回"在 Flink 中已原生支持（Retraction/Changelog 语义）；课程写作时（2021）Beam 仍未支持，现状已变化。
    • Dataflow 论文的窗口/触发器/水位线模型本身是稳定耐用的抽象；MillWheel 是 Google 内部系统，无开源对应物。
