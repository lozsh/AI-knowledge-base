    大数据体系与架构演进

    更新于 2026-11-03

    一句话概括：大数据技术史是一条"Google 论文 → 开源复刻 → 抽象升级"的主线，架构演进从 MapReduce 两阶段走向 DAG 批流统一，数据架构从批处理走向 Lambda/Kappa 双轨。

    核心概念

    • 大数据 4V：Volume（量大）、Variety（类型杂）、Velocity（产生速度快）、Value（价值密度低——正因为价值密度低，才需要专门技术从海量数据中提炼）。
    • 第一性原理：移动计算比移动数据更划算。PB 级数据不可能搬给单机程序；数据大、程序小（几十 KB 的 JAR），所以把程序分发到数据所在节点执行。实现机制：文件分块存储 → 各节点起任务进程 → 程序包分发 + 反射热加载 → 按数据分片就地读取。
    • 物理 backing：机械盘延迟主要来自寻址，顺序写远快于随机写；N 盘并发写达不到 N 倍提速。
    • 垂直伸缩 vs 水平伸缩：垂直（scaling up，升级单机）受物理上限与成本约束；水平（scaling out，加机器）理论上无止境（工业集群已达数万台）。Hadoop 的核心思想突破就是放弃"买更贵的机器"。
    • 与互联网高并发的区别：网站分布式处理互不关联的高并发请求；大数据处理互相关联的存量数据（统计规律、关联关系）。
    • 大数据应用演进四阶段：搜索引擎时代 → 数据仓库时代（Hive 让人人可分析）→ 数据挖掘时代（关联分析、用户画像）→ 机器学习/AI 时代。主线一脉相承：发现数据中的规律并为我所用。

    技术史：Google 三驾马车与开源复刻

    • 2003-2006 Google 发表三篇论文：GFS（分布式文件系统）、MapReduce（分布式计算）、BigTable（NoSQL 数据库），分别解决搜索引擎"网页抓取 + 索引构建"的存储、计算、数据管理问题。
    • 开源演化链：Lucene（搜索库）→ Nutch（Doug Cutting 依论文实现类 GFS/MR）→ 2006 年 Hadoop 独立（HDFS + MapReduce）→ 2008 年成为 Apache 顶级项目。
    • 生态组件动机链（每个组件都为解决前一环的痛点而生）：
    • Pig（Yahoo，类 SQL 脚本）→ Hive（Facebook，直接写 SQL，2011 年占其平台 90% 作业）
    • YARN（2012 独立，资源调度与执行引擎分离，集群可共享给多框架）
    • Spark（伯克利 AMP Lab，针对 MR 迭代慢 + 中间结果落盘改用内存计算 + DAG）
    • HBase（Bigtable 开源实现）、Sqoop（关系库同步）、Flume（日志采集）、Oozie（工作流调度）
    • 技术史三期论：石器时代（2003 前，各家自造工具无统一抽象）→ 青铜时代（2004 MapReduce 论文，Hadoop 开源复刻三驾马车）→ 蒸汽机时代（2008 FlumeJava、2015 Dataflow Model 论文，批流统一；开源对应物即 Apache Beam）。2014 年前后 Google 内部几乎无人新写 MapReduce。
    • 判断技术更替的标志：2014 年 Spark 登顶排序基准后，"MapReduce 慢"才成为共识——常常意识不到问题存在，直到有人解决它。

    数据架构：Lambda 与 Kappa

    • Lambda 架构（Nathan Marz，Twitter）：三层。
    • 批处理层：存储不可变主数据集 + 预计算全量视图（T+1），重算可修复任何错误，准确性高、延迟高。
    • 速度层：实时处理新数据，补上批处理窗口的滞后，近可用但不完全准确。
    • 服务层：合并两路视图响应查询。
    • 典型案例：广告投放（历史行为批 + 新行为流）；Twitter 热门话题（Kafka → Spark 双路 → Cassandra 服务）。
    • 优点：灵活、容错（逻辑错了重跑批处理层即可纠正）。
    • 根本缺点：同一业务逻辑要在两套系统里各实现并维护一遍，且要保证输出一致（如 Java Storm + Python MR 双写）。这是催生批流统一框架的直接动因。
    • Kappa 架构（Jay Kreps，Kafka 作者）：砍掉批处理层只留流处理层，靠 Kafka 日志保留期（Retention Period，可设 1 年或永久）重放历史。
    • 逻辑变更四步：新起一个流作业实例从 Offset=0 重算 → 输出新视图 → 追上旧视图后切换 → 停旧删旧（可保留旧视图支持回滚与 A/B 测试）。纽约时报内容管理系统是经典案例。
    • 局限：速度层重放海量历史慢；Kafka 作唯一存储容量成本高（一年数据 × 3 副本）；批处理重的场景不适合。
    • 选型口诀：稳健的机器学习预测、重准确性 → Lambda；高实时、事件驱动响应 → Kappa。
    • ⚠️ 演进现状：Flink 流批一体、实时数仓（ClickHouse/StarRocks/Doris）与湖仓一体（Iceberg/Hudi/Paimon）大幅压缩了 T+1 依赖；新系统设计上"流批一体"优先于"两套管道"。

    大数据平台架构

    • 在线应用需毫秒响应，大数据计算分钟级，平台是两者的"粘合剂"。通用三层：
    • 数据采集：Sqoop 同步库表、Flume 收日志、埋点经 Kafka 进来。
    • 数据处理：离线全量存 HDFS 用 MR/Hive/Spark 跑；当天数据用流计算。
    • 输出：结果导回数据库供在线读取与报表。
    • 任务调度系统是平台核心：简单用 Crontab，复杂用 DAG 工作流（Oozie，实践中大厂多自研）。
    • 大厂平台模式高度趋同（淘宝调度"天网"、美团 Canal+Kafka 双消费、滴滴实时+离线+HBase 三平台）——同一类问题的有效解法重复出现即"模式"。
    • 数据来源四类：
    • 关系库业务数据：Sqoop 批量同步；Canal 伪装 MySQL 从库读 binlog 实现实时同步（CDC 思想）。
    • 日志：Flume 管道（Source → Channel → Sink），可级联路由。
    • 前端埋点：手工/全埋点/可视化三类，采集"无后端请求"的行为（停留时长等）。埋点常是糊涂账，需专门数据产品经理规划。
    • 爬虫与公共数据。
    • 中小企业四类商业方案：解决方案商（CDH 类四层栈）、云服务（交付方式变为 API）、SaaS（嵌 SDK 零开发）、数据开放平台——买通常比自建总成本低。
    • 物联网"端-云-端"分层：传感器 → 智能网关（边缘计算，本地初算）→ 云端流计算三路处理（清洗入库 / 触发控制指令 / 实时统计）+ 离线分析更新模型。设备 7×24 在线，物联网比互联网更需要大数据。远程热加载网关上的执行代码 = FaaS/Serverless 思想。

    贯穿性架构模式

    • 一主多从（集中管理 + 分布执行）是大数据最主要的架构模式：HDFS（NameNode/DataNode）、YARN（RM/NM）、HBase（Master/RegionServer）、Storm、Spark 同构。互联网在线应用则相反——要避免全局单点管理者。
    • 依赖倒转原则的框架化应用：YARN 依赖 ApplicationMaster 抽象规范而不依赖具体计算框架（类比 Tomcat 与 J2EE 规范）；Beam 依赖 PTransform 抽象而不依赖 Runner。上层逻辑与底层引擎解耦是框架设计的通用手法。

    经验与常见坑

    • "加强监控"类需求错位：老板指运营监控，技术做成运维监控——先确认给谁看、看什么指标。
    • 新技术必须比旧技术有量级提升（~70% 级别）才值得付出迁移代价；选型先从问题独立思考（忘掉具体开源产品），再看开源对答案。
    • Lambda 双写一致性是长期税：实时与历史结果不一致需靠历史覆盖兜底，能上流批一体就不要双写。
    • 埋点缺规划 = 要的没采、没用的狂采，事后无法补采。

    ⚠️ 时效性说明

    • MapReduce 编程已基本淘汰（被 Spark/Flink 取代）；JobTracker/TaskTracker 架构早被 YARN 取代。学习价值在理解分布式计算与 shuffle 本质。
    • Sqoop/Flume/Oozie/CDH：Sqoop 已归档（2021），现行方案为 DataX/Flink CDC/SeaTunnel 与 Airflow/DolphinScheduler；CDH 闭源收费，主流转向云托管与湖仓一体。
    • YARN 地位：云原生时代 Kubernetes 在容器化/流式场景大量替代。
    • HDFS"存储王者"：存算分离 + 对象存储（S3/OSS）作数仓底座正弱化自建 HDFS 的必要性；其原理仍是理解分布式存储的教科书级经典设计。
    • Google Cloud IoT Core 已于 2023 年停服，物联网接入层当下更多是 AWS IoT Core/Azure IoT Hub 或私有方案。
    • "啤酒与尿布"关联分析故事真实性存疑（多考证为营销传说），引用需标注。
