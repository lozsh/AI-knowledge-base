# 基准测试

<p class="note-date">更新于 2026-11-03</p>

**一句话定义**：机器学习基准测试 = 用标准化的工作量、度量与运行规则，实测系统在真实负载下的**持续性能**（而非厂商峰值指标），并沿"系统（硬件）—模型（压缩质量）—数据（代表性）"三个维度验证优化承诺是否兑现。

每个优化都带着一个承诺：数据选择承诺更省的训练、压缩承诺更小更快、加速承诺更高吞吐。基准测试就是让这些承诺面对经验现实的"说真话"环节。峰值与持续性能的差距是**结构性的**：A100 峰值 312 TFLOP/s（BF16），实际 Transformer 训练典型只持续 30–50% MFU——内存停顿、流水线气泡、内核启动开销所致。基准测试量化这个差距，规格书不会。

## 三个核心心法

1. **基准是代理，不是真相**：关键问题永远是"这个基准没测什么"。Offline 模式（全量输入、无延迟约束）吞吐可比 Server 模式（延迟约束下按需到达）高 2–3 倍。
2. **古德哈特定律**："当度量成为目标，它就不再是好度量。"为榜单优化常牺牲鲁棒性、校准、能效。例：BLEU +0.5 的代价是推理 4 倍变慢（beam search 10 倍候选）——正确姿势是"约束优化：在延迟 <100ms 下最大化准确率"。
3. **端到端压倒组件指标**：厂商报的 5–10ms 是模型推理，生产总延迟含预处理/排队/后处理（50–100ms）。推理环节 3× 提速对整条管线可能只有 ~1.2×。**Amdahl 定律封顶一切优化声明**：预处理占 44% 延迟时，把模型优化到无穷快也只能换来 ~2.25× 整体提速。

## 历史演进与教训

| 基准 | 年份 | 教训 |
|------|------|------|
| Whetstone / LINPACK | 1976/1979 | 单一合成操作可被编译器针对性"作弊"，数字漂亮但预测不了真实负载 |
| SPEC CPU | 1989 | 用真实应用套件才能反映部署性能 |
| SPEC Power / Green500 | 2007 | 能效需多负载点评估（部分负载下高效才是真高效）；FLOP/s per watt 补充裸性能 |
| MLPerf | 2018 | 集大成：代表性负载 + 多目标 + 全系统测量 + 开放提交 |

ML 特有的额外难度是**概率性波动**（随机种子、热节流、系统负载），要求统计纪律：每个基准跑 5–10 次，报标准差/95% 置信区间。注意**统计置信陷阱**：1000 张测试集在 95% 精度下的误差波动约 ±7 张（~±1.4pp），根本无法可靠检测 1 个百分点的精度回退——测试集要按想检测的精度配容量。

## MLPerf 套件与执行场景

| 变体 | 目标域 | 关键约束 | 主要指标 |
|------|--------|---------|---------|
| Training | 数据中心训练 | 多机扩展、互连带宽 | time-to-quality、samples/sec |
| Inference | 服务器/边缘 | 延迟 SLA、吞吐 | QPS、p99 延迟、精度保持 |
| Mobile / Client | 手机 / PC 本地推理 | 功耗、内存 | 实时性、本地 LLM 的 token 延迟 |
| Tiny | 微控制器/IoT | KB 级内存、mW 级功耗 | 延迟、每次推理能耗 |
| Power | 横切 | 能耗预算 | perf/W、energy/query |

**四个执行场景**决定同一硬件的数字差异：

- **SingleStream**（batch=1，逐个请求）：移动/嵌入式，只看单请求延迟与功耗；
- **MultiStream**（多路同步流）：自动驾驶多摄融合，看抖动与硬截止期；
- **Server**（泊松到达、动态 batching）：云 API，看吞吐与 p99 的权衡；实际生产流量常违反泊松假设（突发尖峰），纯泊松基准会低估尾延迟；
- **Offline**（全部输入 upfront、最大 batch）：批处理，纯吞吐。

**防作弊机制**：Reference vs Submission 双轨——提交者必须用完全相同的模型结构达到可验证的精度目标（如 ResNet-50 ImageNet top-1 75.9%），否则取消资格。这直接封杀三种常见作弊：偷偷降精度（FP32→BF16）、删除对 top-1 无影响的算子、把权重硬编码进片上 SRAM 绕过内存墙。

## 测量粒度：微 / 宏 / 端到端

| 层级 | 范围 | 回答的问题 | 典型用途 |
|------|------|-----------|---------|
| 微基准 | 单内核/单层/激活函数 | 问题*在哪个*组件 | 硬件选型、算子优化（DeepBench、cuDNN 版本敏感） |
| 宏基准 | 完整模型（ResNet-50 on ImageNet） | *什么*问题存在 | 架构选型、标准化比较 |
| 端到端 | ETL+推理+后处理+基础设施 | 系统*是否可用* | 生产评估（多由组织内部自建） |

粒度选择是**诊断精度 vs 现实代表性**的权衡：微基准精确但漏交互效应（单内核 3× 提速可能被数据管线吞掉），端到端真实但难归因。有效评估需要三层叠加。

微基准测量四规则：**预热**（丢弃冷启动迭代，DVFS/缓存需热身）、**变异系数**（CV = σ/μ > 5% 即噪声过大）、**SOL 检查**（对照 roofline 看利用率，低利用率先查小内核过多导致启动开销）、**刷缓存**（测内存带宽须清 L2，否则测的是缓存速度）。诊断映射到性能公式的三项：DRAM 带宽≈峰值 → 内存受限，优化算力无用；算力与带宽都远低于峰值 → "利用率陷阱"（延迟受限/线程不足）；时间线上的锯齿状空隙 → 软件开销主导（解法：算子融合、CUDA Graphs）。工具链：先用框架 profiler（PyTorch Profiler）找慢层，再用内核 profiler（Nsight Systems/Compute）诊断物理瓶颈。

## 训练基准 vs 推理基准

**训练**测"多快学会"：

- 核心指标 **time-to-accuracy**：$T_{train}$（达到目标精度的最短训练时间）。吞吐必须相对精度目标解读——跑得快但不达标的结果无效。⚠️ 混合精度与全精度结果不可直接比（可行 batch、收敛动态都变了），MLPerf 靠固定精度目标保证可比。
- **扩展效率** = T(1)/(N·T(N))。8 卡把 24 小时压到 4 小时 = 75% 效率；损失的 25% 可归因：梯度同步 10–15%、主机搬运 3–5%、负载不均与 batch 效应各 2–5%。小规模近线性不能外推到集群（4096 芯 TPU pod 上同步是主导因素）。
- **checkpoint 开销**：百亿参数级单次 checkpoint 要写数百 GB，生产系统用异步 checkpoint/并行文件系统把它与下一步计算重叠。
- 复现性要覆盖"整个运行包络"：模型 commit、数据校验和、预处理管线、种子方案、框架/编译器版本、精度策略、硬件拓扑、checkpoint 行为，并报告可接受运行的**分布**而非单次最佳。

**推理**测"多稳地服务"：

- **尾延迟是运营指标**：p95/p99 而非均值。扇出架构下 1% 的慢分片会复合——100 个后端分片的请求有 63% 概率至少碰到一个慢分片，p99 实际成了"平均体验"。经典案例：Discord 的 Go GC 停顿造成每两分钟一次的延迟尖峰，换 Rust（无 GC）后毫秒级降到微秒级——语言运行时为尾延迟设了下限，调参无法突破。SLO（内部目标，须严于外部承诺留误差预算）vs SLA（违约赔钱的合同线）要区分。
- **端到端延迟分解**：网络往返 10–100ms、预处理 1–50ms、排队 0–1000+ms、模型推理 5–100ms、后处理/序列化各 <10ms——厂商报的"基准"只是其中一小段。JSON/HTTP 文本协议的解析开销可能超过小模型推理本身（Clipper 的教训），高性能 serving 用 gRPC/Protobuf 或共享内存格式（Arrow）。
- **场景与指标优先级**：实时应用以延迟为首（p95<50ms），云服务以吞吐/成本为首，边缘移动端功耗优先，医疗科研精度不可妥协。
- **冷启动**：7B 模型 FP16（~14GB）从 PCIe 4.0 装载仅权重传输就要 ~560ms——缓存、模型常驻、投机加载是系统设计要求；serverless 场景下排除冷启动的基准会系统性低估真实延迟。

## 功耗测量

- **边界决定"高效"**：MLPerf Power 明确测量边界（TinyML 整 SoC 入内；推理节点含本地存储/加速器、排除远程存储；训练只测选定计算节点与交换机，不含制冷）。边界不清的能效数字不可比。
- **INT8 为什么省电**：能耗主要由数据搬运决定（DRAM 每字节 ~160pJ，是寄存器的 16000 倍）。INT8 乘加 ~0.2pJ vs FP32 ~3.7pJ（18 倍差）；MobileNetV2 实测 INT8 使模型加载能耗降 4×、计算能耗降 ~18.5×、总计 ~5.4×。
- **瞬时功耗高速波动**：Transformer 前向中 FFN 层（计算密集、峰值功耗）与注意力层（带宽受限、低功耗）交替，低采样率会混叠出失真的平均值；batch 大小与功耗是非线性关系；间歇负载（唤醒词检测）里**空闲功耗**才是主导。
- **峰值 ≠ 持续**：被动散热设备持续推理会热节流，"45 TOPS 峰值"的芯片持续可能只有 ~20 TOPS。边缘基准必须跑 30 秒以上的持续负载，报告热稳态吞吐。TOPS 数字还混着不同算子类型/精度/稀疏假设，跨厂商比较基本无意义。

## 模型与数据评估

**模型维度**——压缩验证不能只看 top-1 精度：

- Top-1 与 Top-5 的差距暴露模型不确定性；精度/召回暴露类别失衡下的失败（99% 准确率的欺诈模型可能只召回 10% 真欺诈）；**聚合指标掩盖子群体失败**（Gender Shades：整体准确，深肤色女性错误率畸高）。
- **校准**：量化可保精度却破坏置信度可靠性。ECE（期望校准误差）<0.05 可靠、0.05–0.10 慎用、>0.10 不可信。MobileNetV2 INT8 案例：top-1 只掉 0.9pp 合格，但 ECE 0.031→0.089、边缘样本精度掉 6.8pp——依赖置信度阈值或常遇边缘输入的场景不应部署，修复方案是温度缩放 + 把边缘样本加进测试集。
- **Pareto 前沿**：画精度-效率散点，前沿上的模型才是有效权衡；不同压缩技术的失败模式不同（量化毁校准、剪枝毁尾部特征、蒸馏毁软性质）。
- **LLM 特有**：MMLU（多选识别）≠ 会生成有依据的回答；HEM 展示单准确率榜单如何掩盖校准/毒性差异；perplexity 只测语料内下一词预测；响应性要拆 time-to-first-token 与 inter-token latency（25 tok/s 生成 750 token 要 30 秒，吞吐数字掩盖"感觉慢"）；**基准污染**（预训练语料见过考题）需用训练截止后的时间盲测、动态题库、复述检测来排查。

**数据维度**——最晚暴露、最难诊断：

- **覆盖**：类失衡（99/1 欺诈数据训出"全预测正常"的 99% 准确模型）、子群体失衡、特征覆盖缺口（白天图片训的模型过不了夜间）；涉人场景需人口学代表性。
- **标签质量**：主流数据集 3–6% 标签错误率；随机错训练中部分自消，**系统性错会被当成真值学会**（雪地里的狼全标成狗 → 模型学会"雪地狼=狗"）。用 confident learning 找可疑标签、用标注者间一致性（Cohen's kappa）评标注质量。
- **分布对齐**：i.i.d. 假设在生产中例行失效。WILDS 基准显示：分布内 90%+ 精度的模型在真实偏移下可掉到 60–70%。生产需漂移检测（KS 检验、MMD、置信度分布监控）。
- **数据为中心的 AI**：DataComp 证明精心筛的 30% 子集胜过 10 倍量未滤数据——修数据比修模型更划算。

**三维联动**：系统过 + 模型挂（压缩毁了精度）、系统过 + 数据挂（训练偏差害子群体）、模型过 + 系统挂（负载下延迟违 SLA）、模型过 + 数据挂（分布漂移静默退化）——单独过任何一维都不够。

## 基准 → 生产的桥

实验室基准系统性违反的生产条件及对策：均匀到达 vs 突发流量（用生产 trace 回放压测）、干净输入 vs 变质输入（生产数据抽样验证）、热系统 vs 冷启动（测冷启动）、隔离运行 vs 资源竞争（真实负载下测）、固定模型 vs A/B 灰度。上线后，监控就是**持续化的基准**：沿用同一套指标基线，用影子评估、分阶段发布、回滚阈值把"一次性测量"变成"滚动对照"。

## 经验与常见坑

- 拒绝任何无法还原"工作负载边界、精度、排除成本"的厂商声明；有效声明长这样："ResNet-50、batch 32、INT8、76% top-1、含 JPEG 解码、H100、700W TDP 下 10,000 inf/s"。
- 报告均值而不报 p99 = 给系统开脱；测量不含预处理 = 给优化开脱。
- 短基准捕捉的是 boost 频率性能，持续训练会因热节流掉到更低稳态频率。
- 饱和基准（MNIST、已停赛的 ImageNet）继续刷已无部署意义；基准要随部署场景更新（稳定性与适应性权衡）。
- "硬件彩票"：Transformer 恰好契合 GPU Tensor Core；榜单系统性偏袒与硬件对齐的架构，换硬件平台重测（多硬件验证）才排除对齐假象。
- 研究基准不能当生产发布门禁——发布门禁 = 负载测试 + 尾延迟 + 数据质量检查 + 故障演练 + 回滚标准。

## ⚠️ 时效性说明

数值锚点（A100 312 TFLOP/s、H100 ~989 TFLOP/s FP16、GPT-3 训练 ~1287 MWh、各代 MLPerf 榜单）反映写作时点；MLPerf 版本间结果不可跨版本比较（工作量与硬件都在演进）。榜单结构（Training/Inference/Mobile/Client/Tiny/Power）与测量方法论稳定，具体数字请查当期 MLCommons 结果。
