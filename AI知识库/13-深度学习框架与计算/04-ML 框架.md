# ML 框架

<p class="note-date">更新于 2026-11-03</p>

**一句话定义**：机器学习框架是位于"数学"与"硬件"之间的编译层——把高层模型定义翻译成硬件优化的执行计划，统一解决三个问题：怎么执行（execution）、怎么求导（differentiation）、怎么跨硬件抽象（abstraction）。

框架之于 ML，如同编译器之于传统编程：模型架构是"源代码"，框架把它编译成一系列硬件内核调用。选框架不是选 API 封装，而是选编译器——它决定了模型能触达哪些硬件、能做哪些优化、能部署到哪些目标。这套选择同时带来能力和锁定（lock-in）：一旦项目积累了 checkpoint、数据管线、自定义模块和团队专长，框架就成了系统架构的一部分，迁移以"工程师月"计价。

## 三个框架问题

1. **执行问题**：操作是立即执行（eager）还是先记录成计算图再优化执行（graph）。这决定调试体验、优化空间和部署灵活性。
2. **求导问题**：对数百万到数千亿参数自动求梯度。手写微分在玩具网络之外不可行。
3. **抽象问题**：同一份模型定义跑在 CPU/GPU/TPU/手机/微控制器上，各硬件内存约束与最优执行模式不同。

三者互相制约：执行模型决定求导发生在何时、哪些优化可行；抽象层要同时支持两种执行风格。

## 抽象阶梯

框架的每个能力都是对上一代工具瓶颈的回应：

| 时期 | 层 | 解决的问题 |
|------|-----|-----------|
| 1979–1992 | BLAS / LAPACK | 硬件原语：标准化线性代数接口，让上层委托给厂商调优的 GEMM 实现（GPU 上是 cuBLAS） |
| 2006 | NumPy | 开发效率：Python 写逻辑、C/Fortran 跑循环的"矢量化"契约，成为后来所有 ML 框架的设计模板 |
| 2007–今 | 深度学习框架（Theano → TensorFlow / PyTorch → JAX） | 自动微分：把链式法则变成软件原语，定义前向即免费获得反向 |

每上爬一层都换来生产力、牺牲透明度；每层抽象靠"shape/dtype/device 的隐式契约"粘合——契约一旦含糊，各自正确的组件也能组合成错误系统（NASA 火星气候探测器因磅-秒/牛-秒单位契约断裂坠毁，是经典案例）。

## 执行模型：Eager、静态图与混合 JIT

### 为什么执行策略重要：内存墙

现代加速器算力增长远快于内存带宽。ReLU 等逐元素操作的算术强度极低（如 0.125 FLOP/byte），是**内存受限**的；大矩阵乘法才是**计算受限**的。关键优化是**内核融合**（kernel fusion）：把多个操作合成一个 GPU kernel，省掉中间结果写回显存的往返——融合 MatMul+Bias+ReLU 可减少 2–3 倍数据搬运；FlashAttention 类融合注意力内核可把 HBM 流量降 10–20 倍、端到端提速 2–4 倍。而框架只能融合它"看得见在一起"的操作——这就是执行策略的意义。

### 三种策略对比

| 维度 | Eager + 动态图（PyTorch 默认） | 静态图（TF 1.x） | 混合 JIT（torch.compile） |
|------|------|------|------|
| 图构建 | 前向时逐步记录 | 执行前完整定义 | 首次执行时捕获并缓存 |
| 优化 | 无（逐操作） | 提前（AOT） | JIT 编译捕获区域 |
| 动态控制流 | 完全支持 | 有限（专用原语） | 部分（图断点回退 eager） |
| 调试 | 简单（标准 Python） | 困难（符号节点） | 中等 |
| 性能 | 基线 | 高 | 高（编译区域） |

- **Eager 的代价 = 派发税**：每个操作付 ~10–15μs 的 Python 查找/类型检查/内核启动开销。小操作（kernel 仅 1μs）时派发税占比 94%，GPU 在等 Python；大矩阵乘（100μs）时降到 13%。小模型/多小层模型"比 FLOP 数预言的慢得多"就是 overhead-bound。
- **静态图的全局优化**：内核融合、常量折叠、死代码消除（大 Transformer 图可裁 5–15% 节点）、内存预分配与 buffer 复用、布局变换（NCHW↔NHWC）。代价是控制流要用专用语法、调试栈指向建图代码。
- **混合 JIT**：`torch.jit.trace` 跑一遍示例输入记录路径（简单但**数据依赖分支会被静默丢掉**，只 trace 到的分支生效——危险的无报错错误）；`torch.jit.script` 分析源码保留全部分支（但只支持受限 Python 子集）；`torch.compile`（PyTorch 2.0）自动捕获 eager 区域、加 guard 条件、编译缓存，不支持的代码形成图断点回退 eager。

### 编译的经济学

编译收益 ≈ [N_prod·(T_eager − T_compiled)] / [T_compile + N_dev·T_compile]，>1 才值得编译。三种工况：

- **研究原型**（频繁改架构）：留在 eager。1 万张图、改 10 次代码的实验，编译重编译开销可使总耗时反而慢 40+ 倍。
- **长训练**：编译 30s 成本摊到百万步上可忽略；ResNet-50 上 torch.compile 提速约 1.4–1.5×，第一个 epoch 内回本。
- **生产推理**：最大化编译，激进 autotuning 也值得；专用引擎（TensorRT/TVM）在转换干净时可比未调优 eager 快 2–10×。

规律：**越窄的目标 + 越稳定的图，编译器能做的优化越多**。稀疏散乱负载（如推荐 DLRM 的不规则 embedding 查找）几乎没有可编译收益；微控制器（TinyML）则彻底去掉 Python 运行时，用固定内存 arena + 小 C 解释器（TFLM）。

## 自动微分

### 前向模式 vs 反向模式

- **前向模式**：每个数附带导数（对偶数）随计算传播，内存恒定，但**每个输入要一遍前向**——P 个参数需要 P 遍。只适合少输入多输出场景（敏感度分析、特征重要性）。
- **反向模式**：一次反向传播算出**全部** P 个参数的梯度，代价是必须保存前向中间激活。训练神经网络只有这一个可行选择：1 亿次前向 vs 1 次反向。

### Autograd 的系统实现（PyTorch）

前向时构建**反向链图**：每个张量带 `grad_fn` 指向生成它的 Function，Function 经 `next_functions` 链到叶节点的 AccumulateGrad。`loss.backward()` 按逆拓扑序遍历、逐节点用链式法则累积 `.grad`、用完即释放保存的张量。

**内存是主要代价**。训练显存 = 权重 + 梯度（≈权重）+ 优化器状态（Adam ≈4× FP16 权重）+ 激活（随深度线性增长）。ResNet-50 推理只需 ~102MB 权重，训练峰值要 10–15GB——**训练/推理内存比近百倍**。7B 模型 FP16 权重 14GB，加 Adam 状态约 70GB。应对手段：

1. **激活检查点（gradient checkpointing）**：只存段边界激活，反向时重算中间层，用计算换内存；
2. **梯度累积**：大 batch 拆成多个小 batch 顺序 backward，只累积梯度，用 64 样本的显存模拟 4096 的有效 batch；
3. **算子融合**：中间量留在寄存器，省 HBM 往返；
4. **`.detach()`/`requires_grad=False`**：切断不需要的梯度路径（迁移学习冻结底层）。

扩展机制：`retain_graph=True`（多次 backward，代价约双倍图内存）、`torch.autograd.Function` 自定义 forward/backward（自己负责保存什么）、hook（中途检查/修改梯度）、`zero_grad()`（忘掉会让梯度静默跨步混合）。⚠️ 原地操作（`x += 1`）可能破坏反向所需的原始值——PyTorch 用张量版本号检测并报错。

### 混合精度

FP16/BF16 矩阵乘跑 Tensor Core 更快、激活显存减半——同时改善计算与搬运两项。FP16 指数位少，梯度易下溢，需要 **loss scaling**（放大 loss 再反向，之后同倍缩回）；**BF16 保留 FP32 的指数范围，通常免 loss scaling**（代价是尾数精度 7 位 vs 10 位）。TF32 是 NVIDIA 的折中格式。

### 内存分配器

直接 `cudaMalloc` 是同步操作（10–100μs），框架用**缓存分配器**：整块申请、按 2 的幂分箱复用。`nvidia-smi` 显示有空闲内存却 OOM，多半是碎片化——找不到足够大的连续块。

## 张量与设备抽象

- **张量元数据**：shape、dtype、device、stride。stride 编译内存布局（行主序 [3,1] vs 列主序 [1,2]），转置/reshape 常是零拷贝的元数据操作；布局与硬件访问模式错配可损失过半带宽。非连续张量可能要先 `.contiguous()`。
- **带宽层级决定放置纪律**：GPU 显存内 ~2TB/s，NVLink 600GB/s，PCIe 4.0 x16 32GB/s——CPU↔GPU 与 GPU 内部差约 60 倍，一次错位的传输就能吞掉 GPU 加速的全部收益。跨设备张量混合运算直接报错，是刻意的保护。
- **流与事件**：把传输和计算放不同 CUDA stream，延迟从 sum 变成 max；事件提供细粒度生产者-消费者同步（`event.wait()` 只阻塞依赖流），`torch.cuda.synchronize()` 全设备同步会把流水线打回串行——调试代码常把它忘在热路径里。
- **pinned memory**：页锁定内存才能 DMA 直传；`non_blocking=True` 只对 pinned 源真正异步（约 2–3× 传输提速）。
- **DataLoader 三旋钮**：`num_workers`（并行加载/预处理）、`prefetch_factor`（流水深度）、`pin_memory`（DMA）；数据管线要跟上加速器消费速度（如 1000 img/s ≈ 150MB/s 原始吞吐），否则 GPU 空转。多 worker 注意各自 RNG 播种（`worker_init_fn`）。
- **核心操作栈**：硬件抽象层（内核选择：cuBLAS/oneMKL/MPS/XLA；内存搬运与布局；执行控制）+ 数值层（GEMM 绝对主力——ResNet-50 前向 4.1 GFLOP 几乎全是 GEMM；卷积经 im2col 化为 GEMM）+ 系统层（调度独立分支并行、缓存分配、算法变体选择）。

## nn.Module 抽象

模块抽象解决"组织"问题，三条原则跨框架通用（Keras layers、Flax、tf.Module 同构）：

1. **自动参数发现**：给 `nn.Parameter` 赋属性即注册进模块树，`.parameters()` 递归遍历供优化器一次性更新。参数 vs 缓冲：`register_buffer` 的张量（如 BN 的 running_mean）随模型迁移设备但不参与梯度。
2. **模式行为**：`.train()`/`.eval()` 递归传播 `training` 标志——dropout 训练随机置零/推理恒等，BN 训练用批统计/推理用滑动统计。忘切模式是静默错误的生产事故来源。
3. **层级组合与序列化**：`state_dict()` 把模块树摊平成点路径键值（`blocks.0.conv1.weight`），支持整树序列化与恢复；`.named_modules()` 支持批量替换层、统一初始化等遍历操作。

配套模式：迁移学习冻结（全模型 `requires_grad=False` + 换新头，优化器只收可训练参数）；hook（`register_forward_hook` 查激活、`register_full_backward_hook` 查梯度，用完 `remove()`）。

## 框架对比与选型

| 维度 | TensorFlow | PyTorch | JAX |
|------|-----------|---------|-----|
| 设计重心 | 抽象/部署生态（TPU→手机→浏览器全谱） | 执行/研究体验（eager + 动态图） | 求导/函数式变换 |
| 编程模型 | 命令式前端 + tf.function 捕图 | 命令式（面向对象、可变状态） | 函数式（纯函数、不可变数组） |
| 求导 | 捕获图上反向模式 | 动态 tape 反向模式 | `grad/vmap/jit` 可组合变换（支持前向+反向） |
| 优化风险 | 算子覆盖、捕获完整性 | 图断点、eager 派发 | 纯度、shape 稳定性 |

JAX 的要点：`grad` 返回**函数**而非值，`jit(grad(vmap(f)))` 把分布式、编译、批量化的梯度计算表达成一个组合式；函数纯度（无副作用）是编译器能安全重排/融合的前提——任何 print/随机数副作用在首次 trace 后静默消失。

**选型方法**：不是问"哪个框架最好"，而是先用硬约束（部署目标、算子需求、编译路径、团队栈）排除不可行者，再用软偏好（性能、生态、招人）排序。部署谱系逐级收紧：全功能框架（~1400 算子、MB 级）→ 移动端 TFLite（~130 算子、百 KB 级、量化/委托）→ 微控制器 TFLM（~50 算子、~10KB、固定内存 arena、无 OS）。ONNX 作为交换格式缓解"训练框架 ≠ 部署运行时"的碎片化，但不消除自定义算子/动态 shape 的兼容工作。

## 一次训练步的解剖

七行代码（前向两矩阵乘 + ReLU + 交叉熵，`loss.backward()`，`optimizer.step()`）触发全栈：

1. **前向**：Python 派发（μs 级）→ cuBLAS 选 GEMM 内核 → 异步入队 → GPU 执行（HBM→L2→张量核）→ autograd 同时记录节点并保存张量引用；
2. **反向**：逆拓扑遍历 → 各节点调 backward 函数 → 梯度累积进 `.grad` → 释放已用中间量；
3. **物理核算**：示例小 MLP 一步 ~39 MFLOP、~4.2MB 流量——GPU 计算仅 0.1μs、访存 2.1μs，而 6 次派发开销 ~30μs，**overhead-bound**。小模型的解法都是压派发项：torch.compile 融合、加大 batch 摊薄、或换更大模型让计算主导。

## 经验与常见坑

- "数学相同性能就相同"是谬论：编译路径差 1.2–3×，专用推理引擎差 2–10×，转换不干净则全无。
- 追热度选框架不如先查部署目标——微控制器上 GB 级运行时根本装不下。
- 高层 API 不豁免系统知识：不懂内存墙会闲置 80–90% 硬件算力，推理成本高 5–10 倍。
- 盲目加大 batch：激活内存随 batch 线性涨，触发重算反而降吞吐 20–30%。
- 探索期用 eager、生产期编译——同一执行策略通吃两阶段，要么拖慢迭代要么浪费吞吐。
- `.data` 绕过 autograd 会静默污染梯度，用 `.detach()`。
- 恢复训练必须同时加载模型与优化器 `state_dict`，否则动量/自适应学习率全丢。

## ⚠️ 时效性说明

`torch.jit.trace/script`（TorchScript）是 PyTorch 1.x 时代的部署路径，2.0 起官方主推 `torch.compile`/`torch.export`；TF 1.x 静态图已成为历史。数值锚点（A100 312 TFLOP/s、PCIe/NVLink 带宽、编译耗时 15–90s）反映写作时的硬件与软件版本，量级可用、具体值会漂移。
