# 开发原则（Development Principles）

<p class="note-date">更新于 2026-11-03</p>

**一句话定义**：构建机器学习系统不只是组装模型组件，而是管理信息与能量在硅芯片中的流动；本篇给出支配模型与硬件协同设计的两条不变量——铁律（时间核算方程）与硅契约（对哪种资源先饱和的赌注）。

## 概述

数据既是机器学习系统的程序（数据即代码），也是其物理锚点（数据引力）。确立这一锚点后，开发的中心问题转向**算法与机器的交互**：如何围绕模型必须执行的硬件之物理限制，对数学模型进行协同设计（co-design）。有些架构在大规模下成功、另一些失败，根源可以追溯到下面两条原则的核算。

## 原则 3：机器学习系统的铁律（The Iron Law）

**不变量**：任何机器学习操作的总时间 T 由三部分决定——数据移动、计算、固定系统开销：

```
T = D_vol / BW + O / (R_peak · η_hw) + L_lat
```

| 符号 | 含义 |
|---|---|
| $D_{\text{vol}}$ | 数据量（需要移动的字节数） |
| BW | 内存/互连带宽 |
| $O$ | 总浮点运算次数 |
| $R_{\text{peak}}$ | 峰值计算速率 |
| $\eta_{\text{hw}}$ | 硬件利用效率 |
| $L_{\text{lat}}$ | 固定延迟开销（内核启动、网络往返等） |

**关键教训是"主导性"而非"求和"**：当各阶段在现代硬件上重叠执行时，挂钟时间由**最大的那一项**主导——耗时最长的项设定了性能下限。

**含义：优化几乎没有免费午餐。** 减少一项通常会把瓶颈转移到另一项。典型例子：非结构化剪枝减少了计算量 O，但引入不规则的内存访问模式，可能反而增加数据移动项 $D_{\text{vol}}/BW$。只有当"更快"的算法减少了**目标硬件上的主导项**时，它在现实中才真正更快。

铁律明确了优化目标，但没有说明如何优化；架构在实现开始之前就决定了如何优化——这是第四条原则的角色。

## 原则 4：硅契约（The Silicon Contract）

**不变量**：每种模型架构和工作负载模式都对硬件做出隐性承诺——即对"哪种资源将首先饱和"下的赌注。

| 架构 | 隐性承诺 | 典型瓶颈项 |
|---|---|---|
| ResNet-50（CNN） | 高密度浮点计算 | 计算受限：$O/(R_{\text{peak}}\cdot\eta_{\text{hw}})$ |
| Llama 3 8B（自回归解码、小批量） | 高带宽内存访问 | 带宽受限：$D_{\text{vol}}/BW$ |
| DLRM（推荐） | 大规模嵌入表 + 稀疏查找 | 存储容量 + 稀疏访问带宽共同决定 |

（⚠️ 具体瓶颈归属依赖批量大小与部署方式：上述是各自最典型场景下的判断。）

**含义**：设计模型时不知道它将饱和哪种硬件资源，就像设计桥梁时不知道钢材的强度一样。**设计必须针对瓶颈进行**——先弄清工作负载会饱和哪类资源，再决定优化方向（是加算力、加带宽，还是重排数据布局）。

## 经验与常见坑

- 优化前先用铁律估算当前主导项，再动手；"最显眼的组件"（模型本身）未必是"最昂贵的组件"。
- 把 A 硬件上的优化经验照搬到 B 硬件：主导项变了，结论可能整个反转。
- 剪枝/量化等压缩手段要评估其对 $D_{\text{vol}}/BW$ 的影响（稀疏性破坏向量化访问），不是"计算少了就一定快"。

## 扩展：为 AI 编码补上工程知识层

### 知识丢失、随机漂移与路径不透明

让 AI 长期参与工程后，三个问题反复出现：知识丢失（上周解释过的系统约定，下周还要重讲）；随机漂移（同样的任务今天与明天处理方式不同，甚至出现"自称已调用工具、实际自行编造结果"的情况）；路径不透明（出问题时不知道卡在哪一步，只能反复调提示词）。这些看似是模型问题，但首先要回到工程自身：如果人都无法从代码库中找到准确知识，AI 同样不可能稳定理解系统。

### CDD：从注释开始，而不是从大文档开始

CDD（Comment-Driven Development）的切入点是让 AI 补注释——注释距离代码最近，能在编码时随代码一起被读取，也更容易随代码变化更新。但注释只能解决局部问题，需要组织成三层知识体系：**L1** 是整个研发过程的硬约束（例如"改动必须配单元测试"），任何任务都不能突破；**L2** 是模块级设计知识（为什么这样设计、关键依赖是什么），由架构师与技术负责人维护，更新频率低（可能半年一次），在跨模块任务时提供必要背景；**L3** 是与代码直接关联的注释（这个常量是什么意思、这段逻辑为什么这样处理），随代码变化更新。执行时 L1 全程生效，AI 处理具体任务先结合代码读 L3，不够再启用 L2。一套内部验证（作者自述、未经独立对照）显示：补齐注释前，AI 回答代码库问题的整体准确率约 52%；补齐后达 90% 以上，且追问次数与总 Token 消耗下降——单次上下文变大，但减少了无效尝试。

### 已知问题代码化：Story 与 Skill 的区别

对高频已知问题，比"给 AI 一份说明"更可靠的做法是把已验证的处理过程固化为代码：意图路由识别出已知问题时直接执行确定性逻辑，而不是让模型每次重新规划。这套思路（某企业实践中称为 Highway/ATV 双路径）的关键沉淀机制是 **Story**：长尾问题经 AI 与人协作解决后，把排查路径转化为可编码、可重复执行的方案，人工按检查单校验后并入确定性路径。Story 与 Skill 的区别在于：Skill 是等待 AI 下次重新理解的能力说明，只要存在重新理解就存在新的随机性；Story 是经过实际问题验证并被固化为代码的执行经验。经验是：代码无法预先解决所有未知问题，但已解决并验证过的问题，应尽量从"可参考"变成"可重复执行"。

### 适用与不适用

这套做法适用于长期演进、多人维护的代码库；对一次性脚本、原型验证则投入产出比偏低。注意 L1/L2 的比例应由团队真实约束决定，不是越多越好——把易变的细节写进 L1 会让硬约束迅速过期。上述准确率等数字为该团队内部自述，引用时应标注来源性质。

### 自测

1. 把你们仓库的 AI 相关约定按 L1/L2/L3 重新归类，找出放错层的条目。
2. 选一个重复出现过的排障问题，写出它的 Story 版本，并说明它比一份文档多了什么保障。
3. 设计一个检查：如何发现"AI 声称调用了工具但实际没有"？
