# 开发原则（Development Principles）

> 来源：《机器学习系统》教材第二部分导言（更新于 2026-11-03）

**一句话定义**：构建机器学习系统不只是组装模型组件，而是管理信息与能量在硅芯片中的流动；本篇给出支配模型与硬件协同设计的两条不变量——铁律（时间核算方程）与硅契约（对哪种资源先饱和的赌注）。

## 概述

数据既是机器学习系统的程序（数据即代码），也是其物理锚点（数据引力）。确立这一锚点后，开发的中心问题转向**算法与机器的交互**：如何围绕模型必须执行的硬件之物理限制，对数学模型进行协同设计（co-design）。有些架构在大规模下成功、另一些失败，根源可以追溯到下面两条原则的核算。

## 原则 3：机器学习系统的铁律（The Iron Law）

**不变量**：任何机器学习操作的总时间 T 由三部分决定——数据移动、计算、固定系统开销：

```
T = D_vol / BW + O / (R_peak · η_hw) + L_lat
```

| 符号 | 含义 |
|---|---|
| D_vol | 数据量（需要移动的字节数） |
| BW | 内存/互连带宽 |
| O | 总浮点运算次数 |
| R_peak | 峰值计算速率 |
| η_hw | 硬件利用效率 |
| L_lat | 固定延迟开销（内核启动、网络往返等） |

**关键教训是"主导性"而非"求和"**：当各阶段在现代硬件上重叠执行时，挂钟时间由**最大的那一项**主导——耗时最长的项设定了性能下限。

**含义：优化几乎没有免费午餐。** 减少一项通常会把瓶颈转移到另一项。典型例子：非结构化剪枝减少了计算量 O，但引入不规则的内存访问模式，可能反而增加数据移动项 D_vol/BW。只有当"更快"的算法减少了**目标硬件上的主导项**时，它在现实中才真正更快。

铁律明确了优化目标，但没有说明如何优化；架构在实现开始之前就决定了如何优化——这是第四条原则的角色。

## 原则 4：硅契约（The Silicon Contract）

**不变量**：每种模型架构和工作负载模式都对硬件做出隐性承诺——即对"哪种资源将首先饱和"下的赌注。

| 架构 | 隐性承诺 | 典型瓶颈项 |
|---|---|---|
| ResNet-50（CNN） | 高密度浮点计算 | 计算受限：O/(R_peak·η_hw) |
| Llama 3 8B（自回归解码、小批量） | 高带宽内存访问 | 带宽受限：D_vol/BW |
| DLRM（推荐） | 大规模嵌入表 + 稀疏查找 | 存储容量 + 稀疏访问带宽共同决定 |

（⚠️ 具体瓶颈归属依赖批量大小与部署方式：上述是各自最典型场景下的判断。）

**含义**：设计模型时不知道它将饱和哪种硬件资源，就像设计桥梁时不知道钢材的强度一样。**设计必须针对瓶颈进行**——先弄清工作负载会饱和哪类资源，再决定优化方向（是加算力、加带宽，还是重排数据布局）。

## 经验与常见坑

- 优化前先用铁律估算当前主导项，再动手；"最显眼的组件"（模型本身）未必是"最昂贵的组件"。
- 把 A 硬件上的优化经验照搬到 B 硬件：主导项变了，结论可能整个反转。
- 剪枝/量化等压缩手段要评估其对 D_vol/BW 的影响（稀疏性破坏向量化访问），不是"计算少了就一定快"。
