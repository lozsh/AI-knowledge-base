# 基础原则（Foundation Principles）

> 来源：《机器学习系统》教材第一部分导言（更新于 2026-11-03）

**一句话定义**：机器学习系统遵循"复杂性守恒"——复杂性无法被消灭，只能在数据（Data）、算法（Algorithm）、机器（Machine）三个领域之间转移；本篇给出支配这种转移的两条基础不变量：数据即代码、数据引力。

## 核心原理：复杂性守恒

复杂性在 D·A·M 分类法的三个领域中流动：

| 领域 | 承载内容 | 复杂性形态 |
|---|---|---|
| 数据（Data） | 信息 | 分布、质量、标注、版本 |
| 算法（Algorithm） | 逻辑 | 模型结构、特征、超参数 |
| 机器（Machine） | 物理 | 硬件、带宽、延迟、能耗 |

简化一个领域必然加重其他领域的负担。典型例子：

- 手工设计特征流水线 → 降低算法复杂性，但把负担转给数据工程；
- 更大的模型 → 可以"吸收"混乱的数据，但把复杂性转给必须训练和服务它的硬件。

这条**复杂性守恒（Conservation of Complexity）**是整门学科的元原则：后续所有定量不变量都是它的可测量实例化——每一个不变量都在量化"复杂性现在落在何处、由此产生了什么约束"。

架构、框架和优化只有在与硬件、数学、信息论施加的不变量保持一致时才能成功。正如土木工程师不能忽视重力，机器学习工程师也不能忽视管理数据、计算和吞吐量的物理定律。这些不变量不是随框架演变的最佳实践，也不是团队间见仁见智的观点，而是"机器学习工程的物理学"。

## 原则 1：数据即代码不变量（Data as Code Invariant）

**不变量**：数据是机器学习系统的源代码。对训练数据集的更改，在功能上等同于对可执行逻辑的更改（ΔProgram）。

```
System Behavior ≈ f(Data)
```

**含义**：数据工程需要与软件工程同等的严格性。具体对应关系：

| 软件工程实践 | 数据侧等价物 |
|---|---|
| 版本控制（Git） | 数据集版本控制 |
| 单元测试 | 数据质量检查 |
| 调试 | 数据调试 / 血缘追踪 |
| 修改一行代码 | 删除/修改一行训练数据 |
| 重新编译 | 重新训练 |

删除一行训练数据在工程上等价于删除一行代码；重新训练只是从更改后的"源材料"重建学习产物。

但如果数据是源代码，它就不仅是逻辑产物——它还有约束系统架构的**物理属性**。代码可以自由复制分发，数据却"抵抗移动"，其规模决定了计算应该发生在哪里。这就引出第二条不变量。

## 原则 2：数据引力不变量（Data Gravity Invariant）

**不变量**：数据具有"质量"。随着数据量 D_vol 增大，移动数据的成本（延迟、带宽、能量）会超过移动计算的成本。

```
C_move(D_vol) ≫ C_move(Compute)
```

**含义**：大型数据集成为架构的**引力中心**。系统应当把计算移向数据——将查询或代码下发到存储层执行——而不是通过反复下载大数据集把数据移向计算。这一不变量是 Data Lakehouse 等存算一体架构的物理根源。

## 两条不变量的合取

- 数据即代码 → 数据是每个 ML 系统的**逻辑程序**（决定行为）；
- 数据引力 → 数据是每个 ML 系统的**物理锚点**（决定架构）。

在这两块基石之上，可以进一步展开：机器学习工作流（生命周期）、数据工程的工程化实践（见 05-数据工程）、以及性能核算的铁律（见 06-开发原则）。

## 经验与常见坑

- 试图"彻底消除"复杂性（如追求零特征工程的端到端大模型）不会成功，只会把复杂性转移到数据规模或算力成本上；正确做法是**有意识地选择复杂性落在哪个领域**。
- 把数据变更当"小事"处理（随手改训练集不记录版本）是最常见的违约行为——它等价于在不通知的情况下改生产代码。
