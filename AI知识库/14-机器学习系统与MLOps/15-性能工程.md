# 性能工程

<p class="note-date">更新于 2026-11-05</p>

**一句话定义**：性能工程通过重塑计算本身（数据移动、精度、编译、算法变换）使其匹配硬件物理特性，把"理论上快"的模型变成"实际快"的生产系统，通常可带来一个数量级的提升。

性能工程与模型压缩的分工：压缩（剪枝、量化、蒸馏）缩小模型的内在工作量；性能工程则让剩余工作量与硬件的物理特性对齐——把数据留在快速内存、把每次传输打包得更密、消除软件开销。二者互补：把量化后的模型直接加载到加速器上，若每个权重仍从片外内存读取，量化的带宽收益就被浪费了。

本篇内容属于舰队栈中服务层内的优化学科：从内存层次结构出发，依次讨论算子融合、精度工程、图编译、算法性能变换（推测解码、稀疏专家路由）、通信-计算重叠与系统性能分析，最后以 70B LLM 优化案例收束。所有手段都属于 C³ 分类法中的"计算"项——从舰队已有的周期中榨取更多有用工作。

## 核心原理

### ML 性能铁律

执行时间可分解为三个竞争项：

```
T ≈ max(计算项, 数据项) + 开销项
   = max(FLOPs / (Peak × η_hw), D_vol / BW) + T_overhead
```

- **计算项**：总浮点运算数 ÷ 实际达到的硬件吞吐。
- **数据项**：总传输字节 ÷ 内存带宽。
- **开销项**：其余一切——内核启动延迟、同步、通信、软件栈低效。PyTorch 训练循环中，每次内核启动都要穿越 Python GIL 和框架调度器，每个操作耗费数十微秒后才进入 GPU 命令队列；`torch.compile(mode="reduce-overhead")` 和 CUDA Graphs 正是为此而生：把重复的 GPU 提交变成原生重放，绕过 GIL 与调度器。

Roofline 近似则进一步问：在给定工作点上哪个暴露项占主导。**诊断主导项，再应用针对该项的技术**——把优化用在非主导项上是浪费工程努力。

### 手段与铁律项的映射

| 铁律项 | 攻击手段 |
|---|---|
| 数据项（字节/BW） | 算子融合、分块（消除中间 HBM 往返，注意力场景可降 10-30 倍片外访问）；精度工程 FP8/INT4/KV 缓存压缩（同带宽携带更多有用状态） |
| 开销项 | 图编译（torch.compile、XLA、TensorRT）：消除启动间隙、融合算子、优化内存分配 |
| 计算项 | 通信-计算重叠（当 $T_{\text{comm}}(N) - T_{\text{overlap}} \leq T_{\text{compute}}/N$ 时通信退出关键路径）；算法创新：推测解码、MoE 稀疏路由（改变计算本身） |

### 诊断先于优化

标准排障流程：训练慢/GPU 利用率低 → 先排除 I/O 受限（DataLoader 停滞）、CPU 受限（预处理）、通信开销 → 再用 Roofline 分类为计算受限或内存受限 → 前者走精度工程与算法优化，后者走算子融合与图编译 → 改后重新分析。误诊不只是浪费：盲目的性能改动可能把系统推到错误的工作点。

## 核心概念

### 效率前沿

吞吐、延迟、成本、质量、内存五个维度构成的帕累托前沿：

| 维度 | 测量 | 典型张力 |
|---|---|---|
| 吞吐量 | tokens/s 或 requests/s | 大批量提升吞吐但退化延迟 |
| 延迟 | TTFT 与逐 token 延迟 | 低延迟需要小批量、更高单价 |
| 成本 | 每 token 成本 | 最便宜的配置可能错过延迟/质量目标 |
| 质量 | 困惑度/基准准确率/人类偏好 | 降精度与投机解码需质量护栏 |
| 内存 | 峰值 GPU 内存 | 大上下文与大批量消耗容量 |

实例——同一个 70B 模型的两个部署点：配置 A 延迟优化（FP16、batch=1、投机解码，8×H100 服务单用户，约 50 tokens/s，token 间 20ms，约 $0.12/千 token）；配置 B 吞吐优化（INT4、batch=64，每 H100 聚合约 4000 tokens/s，token 间 120ms，约 $0.002/千 token）。B 单成本低 60 倍、延迟高 6 倍，没有客观上"更好"的配置，只有匹配应用的点。

### 内存墙

处理器不缺算术能力，缺数据。H100 提供 1979 TFLOP/s（FP8）但仅 3.35 TB/s 带宽：**若每字节加载的内存执行的算术少于约 590.7 FLOP，计算单元就在挨饿**。这是物理约束而非工程限制——片上 SRAM 访问约 0.5 pJ，片外 HBM 约 640 pJ，相差约 1280 倍；模型需要 GB 级参数，物理只允许 KB 级数据靠近计算单元。

GPU 内存层次结构（H100）：

| 层级 | 规模 | 访问成本 | 优化约束 |
|---|---|---|---|
| 寄存器 | 256 KB/SM（共约 33 MB） | 1 周期，~0.01 pJ | 线程私有；FP32 累加器会强制溢出 |
| 共享内存（SRAM） | 最多 228 KB/SM | 20-30 周期，~0.5 pJ | 线程块共享；中间结果留在此时融合有利 |
| L2 缓存 | 50 MB | ~200 周期 | 跨 SM 自动捕获重用，不可显式管理 |
| HBM | 80 GB，3.35 TB/s | ~300 ns，640 pJ | 读全部带宽需约 24 ms，远超实时推理目标 |

数据中心的能源账：1000 张 H100 在内存受限负载下每张每秒约 10¹² 次内存访问，仅 HBM 访问（640 pJ/次）就消耗约 640 W/GPU——内存子系统能耗与算力同量级。

### Roofline 模型

```
可实现 FLOP/s = min(Peak, BW × I)        I 为算术强度（FLOP/字节）
脊点 I_ridge = Peak / BW
```

$I < I_{\text{ridge}}$ 为内存受限，$I > I_{\text{ridge}}$ 为计算受限。各代 GPU 的 FP16 脊点：V100 ≈139、A100 ≈153、H100 ≈295（FP8 约 590.7）、B200 ≈281 FLOP/字节。计算逐代增长快于带宽，脊点趋势性抬升（约 7 年翻倍），越来越多工作负载落入内存受限区；且同一内核可跨硬件代际改变 regime，升级硬件时必须重新分析。

### 常见 ML 操作落在哪

| 操作 | 算术强度 | 区域 | 瓶颈 |
|---|---|---|---|
| GEMM（4096×4096 大批量） | ~1365 FLOP/字节 | 计算受限 | 张量核心吞吐 |
| 自注意力（seq=2048） | ~50-200 | 内存受限 | HBM 带宽 |
| 逐元素（GELU、LayerNorm） | ~1-3 | 内存受限 | HBM 带宽 |
| LLM 解码（batch=1） | ~1-2 | 内存受限 | HBM 带宽 |

Transformer 推理管线的大多数操作是内存受限的。推论：**比较 LLM 推理 GPU 的正确指标不是 FLOP/s，而是内存带宽（决定 token 生成速率）与内存容量（决定最大批量）的组合**；batch=1 时两块 TFLOP/s 不同但带宽相同的 GPU 解码吞吐几乎一样。

## 服务机制：批量大小与 Prefill-Decode 分离

### 批量大小是第一旋钮

解码算术强度随批量近似线性放大：$I_{\text{decode}}(B) \approx 2B / (s_{\text{param}} \cdot P + s_{\text{elem}} \cdot B \cdot d_{\text{model}})$（$s_{\text{param}}$ 每参数存储字节数、$s_{\text{elem}}$ 每元素存储字节数、$d_{\text{model}}$ 隐藏维度）。batch=1 时约 1 FLOP/字节（深内存受限）；batch=256 时约 256 FLOP/字节，逼近计算受限。H100 上 batch=1 约 5% 利用率，大批量可达 40%，每 token 成本可降约 8 倍。

约束是内存：每个请求需要自己的 KV 缓存，总 KV 缓存必须与权重共存于 GPU 内存。PagedAttention 把 KV 缓存按固定大小块（页）按需分配，消除碎片（传统预分配在最大 4096/平均 500 的场景浪费约 88%），使有效批量增大 2-4 倍；与 KV 缓存量化叠加可达 8-16 倍，根本改变服务经济学。

### Prefill 与 Decode 是两种负载

- **Prefill**：并行处理整个提示，n 个 token 的 GEMM 算术强度约 2n（1024 token 约 1024 FLOP/字节），计算受限，受张量核心吞吐限制。
- **Decode**：自回归一次一个 token，batch=1 时约 1 FLOP/字节，深内存受限。

 Napkin math（70B @ 8×H100，TP=8，batch=1）：每 GPU 每步读 17.5 GB 权重产生 17.5 GFLOP，I=1 FLOP/字节；17.5 GB ÷ 3.35 TB/s ≈ 5.2 ms/token，约 191 tokens/s，仅用了 0.3% 的 FP16 峰值算力（实际还会被 KV 读取与 NVLink 同步进一步拉低）。改进路径都攻击同一权重流成本：更大批量摊销、量化减字节、投机解码一次权重传递换多个 token。

分解服务（disaggregated serving）把两阶段放到不同硬件池：prefill 池要高 FLOP/s，decode 池要大带宽大容量，KV 缓存在池间传送。FlashAttention 在 prefill 收益最大；KV 量化与投机解码只作用于 decode；FP8/INT4 对两者都受益但机制不同（prefill 得双倍算力，decode 得双倍有效带宽）。

## 算子融合与内核工程

朴素执行 `y = LayerNorm(GELU(xW + b))` 需要三次 HBM 往返：每个非融合内核都把中间张量实体化到 HBM。对隐藏维 4096、批量 2048（FP16），每个中间张量 16.8 MB，非融合执行产生 67.1 MB 中间 HBM 流量；融合内核把中间量留在 SM 内的寄存器/共享内存里，直接消除。类比：非融合是三个厨师共用一台冰箱来回取放，融合是一个厨师在案板（SRAM）上连续完成三步。

内核启动本身也有开销：CPU 备参、派遣命令队列、跨 SM 调度线程块，小型逐元素操作约 5-20 μs——Transformer 层由几十个小操作组成时累积可观。这解释了融合与 CUDA Graphs 为何常一起使用。

## 精度工程

融合减少穿过 HBM 的次数，精度工程减少每次携带的字节：权重从 2 字节降到 1 字节，权重读取流量近似减半、等效带宽翻倍。工程决策的本质是判断哪里能容忍数值噪声、哪里必须为质量保留精度。第一个决策是如何在压缩权重的同时保护携带稀有但关键信号的通道——大模型会涌现"离群维度"：约 0.1% 的特征激活值比典型值大 3-20 倍（Dettmers 等 2022）。均匀按张量量化要么裁掉离群值摧毁推理能力，要么为迁就它们浪费多数近零权重的精度。块级量化把权重张量切成互不重叠的组，每组独立算缩放因子，把最坏量化误差锁在组内：

$$s_i = \frac{x_{\max,i} - x_{\min,i}}{2^b - 1}$$

块大小 $G_{\text{block}}=64$、$b=4$ 时：权重 16 bit → 4 bit（4× 压缩），每权重摊上 FP16 scale 的 16/64 = 0.25 bit，有效位宽 4.25 bit——INT4 净荷仅 6.25% 开销。块大小不是免费超参：G=32 元数据开销翻倍，G=16 时 scale 占 1 bit/权重（25% 开销）。

四条主流方法保护同一批敏感信息，但把代价放在流水线的不同位置：

| 方法 | 代价位置 | 机制 | 适用 |
|---|---|---|---|
| LLM.int8() | 运行时 | 按幅值阈值（典型 6.0）把离群维路由给 FP16 GEMM，其余走 INT8 GEMM，结果合并 | 近无损 INT8，压缩上限 8 bit |
| GPTQ | 校准（小时级） | 用校准激活的近似 Hessian 逆逐层重构，借层内相关权重补偿量化误差 | 激进 INT4 权重压缩 |
| AWQ | 校准（分钟级） | 按激活幅值识别显著权重，逐通道缩放保护后做均匀分组量化 | 校准时间敏感的 INT4 |
| SmoothQuant | 预处理 | 数学等价变换把激活离群迁移到权重上，得 W8A8 | 要同时吃 INT8 Tensor Core 的带宽与算力收益 |

### PTQ 还是 QAT

PTQ 用小校准集（典型 128-1024 样本）逐层最小化重构误差，70B 模型小时级完成；INT8 通常稳健，但 INT4/INT3 若不保护敏感层与离群通道，困惑度退化、MMLU 可掉数个点。QAT 在前向模拟低精度舍入、反向用直通估计器（STE：舍入函数梯度几乎处处为零，把上游梯度原样穿过舍入步作代理）绕过，等于一次完整微调——70B 要数百 GPU 小时的多天分布式作业。Adapter 式量化微调冻结低精度底座、只训低秩适配器，用小硬件换回部分质量，是任务适配补救而非通用替代。实用工作流：先 PTQ，不达标再上 QAT/adapter。

### 作用范围：权重、激活与 KV 缓存

Weight-only（GPTQ/AWQ）：权重 INT4、激活保持 FP16，GEMM 时在线反量化走 FP16 Tensor Core——只省权重存储与读取带宽，最适合 batch=1 这类权重读取主导的内存受限 decode。Weight-activation（SmoothQuant/FP8）：两者都降，GEMM 本身用低精度算力，带宽算力双赚，但激活分布动态、更难压。高性能服务栈常混用：低批量走 INT4 weight-only 保延迟，高批量走 FP8 weight-activation 保吞吐。而 KV 缓存决定权重节省能否变成更大批量。70B @ 8×H100：FP16 权重占 17.5 GB/GPU，80 GB 里剩 62.5 GB 给 KV（每请求 1.34 GB，约 0.17 GB/GPU），最大批量约 372；权重 INT4（4.4 GB/GPU）+ KV INT8（每请求 0.67 GB）后，可用 75.6 GB、每请求约 0.08 GB/GPU，最大批量约 901。批量扩约 2.4 倍直接转为吞吐：大批量摊薄固定的权重加载成本，把工作点从内存受限推向计算受限。KV 还有第二条路：数值压缩减每条缓存字节数，GQA 减每层要缓存的 KV 头数；调度器按"权重+活跃缓存"总占用准入请求，只压权重不动缓存可能根本挪不动瓶颈。

精度减每次传输的字节，融合减传输次数，二者相乘：FlashAttention 消掉二次方注意力中间量后，INT8 KV 压缩再把剩余 KV 字节减半，组合收益超过各自之和。极限在另一端：512 KB SRAM 的微控制器上，量化不是优化而是可行性测试——二值网络（权重 ±1）比 FP16 省 16× 内存、每操作能耗最多降 100 倍，智能才可能在收集能量（微瓦级）的设备上运行。

## 图编译

为每种层组合手写融合 CUDA 内核是不可能完成的任务；图编译器分析计算图、自动生成硬件感知指令——前提是形状稳定、重放次数够多，摊得平编译成本。管线以 `LayerNorm(Linear(GELU(Linear(x))))` 为例，eager 模式触发 4 次独立内核启动、各读写一次 HBM。编译器依次做：**图捕获**（trace 出 DAG，动态 Python 控制流需走代表路径或标注动态维度）→ **图级优化**（偏置折进 GEMM、代数化简，图尺寸先减 10-30%）→ **算子融合**（GELU 并入 Linear 尾部或与 LayerNorm 合成单内核，HBM 访问减 30-50%）→ **内存规划**（分析张量生命周期复用物理地址，推理时峰值临时内存从各层缓冲之和降到最大活跃工作集；训练侧为反向保存的激活需重算/checkpointing，普通复用消不掉）→ **内核选择**（重投影用 cuBLAS/CUTLASS，融合序列生成 Triton 内核）——4 个内核变 2 个。

### 三种编译器画像

| 编译器 | 定位 | 优势 | 代价 |
|---|---|---|---|
| torch.compile | PyTorch 最小侵入 | TorchDynamo 在字节码层捕获（免改模型代码），TorchInductor 生成 Triton/C++，AOTAutograd 编译反向；单次调用典型 10-40% 加速 | graph break 拆碎子图（50 个 break = 50 个小区域，融合失效）；动态形状触发重编译 |
| XLA（JAX/TF） | 整程序静态编译 | GSPMD 按少量标注自动跨数千核分片并插入通信原语；TPU 上对齐 128×128 脉动阵列；大规模 LLM 训练 MFU 报告 55-65% | 编译分钟级、形状一变全量重编译，适合数天周级稳定负载 |
| TensorRT | 推理专用 | 校准定数值范围支持混合精度、逐算子在真实硬件上 benchmark 数十种内核配置择优 | 编译 30-60 分钟（70B），引擎绑定 GPU 架构与形状范围 |

torch.compile 的模式选择是摊销决策：default 是开发基线；reduce-overhead 叠加 CUDA Graphs 治启动受限；max-autotune 逐算子自动调优（10-30 分钟编译），只有稳定部署才回得了本。Napkin：13B 模型 eager 120 tokens/s（8.33 ms/token），剖析显示逐元素内核占 35%、启动开销占 15%；compile 后逐元素时间 -70%、启动 -80%，新耗时 4.17+0.87+0.25 = 5.29 ms ≈ 189 tokens/s——**1.58× 加速没动 GEMM 一根手指**，此时 GEMM 占 79%，下一步只能靠精度或批量。

Triton 以 tile（而非线程）为编程抽象：程序员定分块与融合策略，线程调度、访存合并、共享内存管理交给编译器。一个 `y = LayerNorm(GELU(x))` 融合内核把 3 次 HBM 往返压成 1 次，内存受限下直接 3× 提速；TorchInductor 遇到编译器启发式覆盖不到的融合点时也生成 Triton 代码，所以很多融合收益来自一次 `torch.compile` 调用而无需手写内核。

## 算法性能变换

### 推测解码

用小 draft 模型一次提出 K 个候选 token，目标模型用一次并行前向验证——权重流成本与生成一个 token 近似相同，decode 算术强度提升最多 K 倍，把工作点从内存受限斜坡推向脊点。接受检验保证输出分布与目标模型完全一致：第 i 个草稿以概率 \(\min(1, p_\theta/q_\phi)\) 接受，拒绝时从归一化正残差 \((p_\theta - q_\phi)^+\) 重采样修正。期望接受轮长度（几何接受模型）：$$E[\text{tokens}] = \frac{1 - p_{acc}^{k+1}}{1 - p_{acc}}$$ 生效条件苛刻：draft 不够准则拒绝率吃掉收益，draft 不够便宜则验证变计算受限，大批量下 decode 本就接近计算受限、投机收益缩水。

### 混合专家（MoE）

万亿参数稠密模型服务不起；MoE 训练大模型但每 token 只激活相关的一小片，切断模型规模与推理成本的铁链。性能问题随之从稠密矩阵吞吐转移到路由、内存驻留与负载均衡：专家并行把不同专家放上不同 GPU，AllToAll 交换把每个 token 的隐状态搬到其专家再搬回——**只有路由通信与专家不均衡的代价小于被替换的稠密计算时，稀疏激活才真正改善铁律预算**。

## 通信-计算重叠

融合、精度、编译、推测、稀疏路由之后，铁律中下一个暴露项往往是通信；重叠是暴露时间测试，只有有用计算能盖住通信时才有效。两个工作点看清批量为何是万能旋钮（70B TP=8，每层 2 次 AllReduce，$2 \times d_{\text{model}} \times B \times 2$ 字节，$d_{\text{model}}=8192$）：batch=1 时每次 AllReduce 32.8 KB，900 GB/s NVLink 下传输仅 36.4 ns，而约 5 μs 的启动开销主导 100 倍——重叠无从谈起；batch=64 时 2.1 MB、传输 2.3 μs，注意力+FFN 计算约 20 μs，计算比通信宽 9 倍，重叠高度有效。

训练梯度同步是同一条不等式的大载荷版：7B 模型 8×H100，16.1 GB FP16 梯度，ring AllReduce 传 \(2(N-1)/N = 1.75\) 倍体积约 62.5 ms，backward 按 40% MFU 约 166.3 ms；无重叠步时 311.9 ms，全隐藏后 249.4 ms，**1.25× 改善**。但规模是敌人：集群从 8 扩到 1024 GPU，重叠效率从约 90% 跌到约 18%（跨节点延迟与带宽），小模型或慢互联（PCIe 64 GB/s）下 AllReduce 直接超过 backward，怎么盖都盖不住。

机制是 CUDA streams：计算流跑 GEMM、通信流跑 NCCL，硬件调度器交错执行。代价是物理资源争用：重度 NCCL 操作要占 132 个 SM 中的 4-8 个做协议处理与内存拷贝，计算吞吐降 3-6%（干扰效应）——若计算内核本就打满 SM，重叠反而变慢；不过 3-6% 通常远小于被隐藏的通信时间，稳赚。PyTorch DDP 用参数级 backward 钩子在独立 NCCL 流上异步 AllReduce，按 bucket 就绪即启动以藏住启动延迟，backward 结束前同步保证优化器读到完整梯度。自写 side stream 的两个隐雷：跨流消费张量必须显式 `event.record()/wait()` 否则数据竞争且框架无报错；拷贝不加 `non_blocking=True` 会插入隐式同步点，把想重叠的流串回 serial。

## 系统性能分析

没有测量的性能工程是昂贵的猜测。经典教训：工程师花两周把模块重写成快 5 倍的 CUDA 内核，端到端延迟纹丝不动——系统整体 I/O 受限。而观测本身又改变被观测系统（海森堡效应）：记录每次内核启动与分配消耗 PCIe 带宽和 CPU 周期；PyTorch profiler 为记录分配元数据会延长激活张量生命周期，阻止缓冲复用，虚增峰值 HBM 甚至诱发不存在的 OOM；torch.compile 检测到张量观测会保守禁用部分复用融合，剖析执行走的是比生产更慢的路径。全量 trace 开销约 10-20%。策略：生产用低开销采样遥测，高保真同步 trace 只在隔离诊断环境开，剖析数字用于定性结构、绝对值需打折。

### 四层剖析与下钻

从症状到根因逐层下钻，跳层就会优化错瓶颈：

| 层级 | 回答的问题 | 工具 |
|---|---|---|
| 应用 | tokens/s、TTFT、P99、MFU 是否达标 | 自建面板、Prometheus/Grafana |
| 框架/分布式 | 集合通信与计算是否重叠、是否有 straggler 与负载不均 | PyTorch Profiler + NVTX、TensorBoard |
| 内核/trace | 时间线上内核、空闲间隙、CPU-GPU 同步、NCCL 事件 | Nsight Systems、PyTorch Profiler |
| 硬件计数器 | 单内核带宽、占用率、指令混合 | Nsight Compute、perf |

指令混合计数器能抓到最隐蔽的静默 bug：tile 维度不满足 Tensor Core 对齐（FP16 倍数 8、INT8 倍数 16）时，GEMM 静默退回 CUDA Core 标量指令，吞吐只剩零头。

### 指标与时间线判读

MFU 40-60% 为调优良好的 LLM 训练、>60% 优秀；HFU−MFU 的差值即重算等浪费算力的估计。TTFT <500 ms 可接受、<200 ms 流畅；ITL <50 ms 支持舒适阅读、实时语音要 <25 ms。**MBU 与 MFU 要配对读**：H100 上一次 decode 步可以只有 2% MFU 却有 85% MBU——这不是差，是内存饱和且路径优化良好的标志。Roofline 诊断三步：Nsight Compute 测实际 FLOP/s 与带宽 → 从算法算算术强度 → 对照 ceiling 定位。实例：LayerNorm 内核 15 TFLOP/s、2.8 TB/s，\(I = 15/2.8 \approx 5.4\) FLOP/字节远低于脊点 295，而 2.8 TB/s 已达峰值带宽 83.6%——铁证内存受限，继续优化算术毫无意义，只能融合或降精度。

Nsight Systems 时间线看四个关键行：CUDA HW（内核执行，条间空隙即 GPU 浪费）、CUDA API（CPU 侧调用，明显宽于 HW 行即 CPU 喂不动 → CUDA Graphs/compile）、NCCL（与 CUDA HW 重叠为好、落在空隙即通信串行）、NVTX（把神秘内核名映射回模型模块）。PyTorch profiler 用 `schedule(wait=1, warmup=2, active=3)` 留足预热——不预热会把 JIT 编译、CUDA 上下文初始化等一次性成本算进测量。

### 侦探案例与规模化剖析

7B @ 单 H100 实测 45 tokens/s，全 decode 带宽上限约 96。排查：主 GEMM 内核 2.8 TB/s（84% 峰值带宽）近乎最优——直觉指向的元凶无罪；trace 显示它只占步时 42%，其余 58% 分散在：注意力含 KV 读取 28%（KV 内核因不规则访存只有 1.9 TB/s → INT8 KV + 布局优化）、LayerNorm/激活 12%（未融合 → Triton 融合内核）、softmax 与 top-k 采样 8%、启动间隙 10%（每层 120+ 次启动 → compile 后约 30 个）。**瓶颈不在最大的内核，而在许多小操作的累积开销。** 单 GPU 之外的剖析另有一套账：5 秒 trace 单 GPU 约 500 MB，1000 GPU 就是 500 GB——不可存也不可析。生产用层级剖析：全量 GPU 持续低开销采集 MFU/吞吐/步时，指标劣化时才对代表性子集（每流水线阶段、每 DP 组一台）做短窗口定向 trace；或统计剖析，每 GPU 随机采样一小部分内核，聚合成分布。最难抓的是间歇 straggler（热节流、内存错误、网络拥塞，短窗口看不见却吞掉 10-20% 长时吞吐），只能靠持续步时监控加统计异常检测。

## 大规模测量

### MFU 与扩展税

单节点优化是前提，舰队规模才是终考。MFU 度量有用的模型 FLOPs 而非"忙碌"：系统可以硬件利用率 90% 而 MFU 只有 30%（通信气泡、低效内核）。舰队级 MFU 恒低于单节点：通信、负载不均、流水线气泡逐级复合。万卡集群上 MFU 提升 1% 等于白捡 100 张 GPU。$$\mathrm{MFU} = \frac{\mathrm{FLOPs}_{useful}}{N \times R_{peak} \times t_{step}}$$ 扩展税 = \(1 - \mathrm{MFU}_{fleet}/\mathrm{MFU}_{local}\)：70B 模型单 8-GPU 节点 65% MFU，扩到 128 GPU 步时涨到 245 ms、MFU 跌到 48%，税 26.2%——这是 InfiniBand 延迟与同步屏障的价格。健康舰队里该税率应稳定，**税率突增即扩展回退信号**，典型病因是并行化策略错配或网络 fabric 灰故障。

### 缩放回归与英雄运行税

系统在规模上是非线性的：单 GPU 上无碍的小内存增量，到 1000 GPU 可因 GC 停顿或 InfiniBand credit 耗尽演成性能崩塌。三层测试拦截：小规模金丝雀（8/64 GPU 建标度效率曲线）、舰队基线比对（每次生产运行对参考基线查 MFU）、灰故障检测（一个慢 10% 的节点能把同步数据并行的 MFU 拖低 10%）。基准数字别直接抄进容量规划：MLPerf 类"英雄运行"关日志、跳安全检查、刚重启硬件，生产 MFU 通常低 10-20%——可观测性、可靠性（checkpoint/心跳）与熵（热节流、碎片、多租户网络噪声）吃掉差额。基准说训练 30 天，生产计划按 35-40 天排。

## 优化剧本：70B 服务优化案例

按瓶颈类别走有序路径，每步之后重新剖析确认瓶颈已移动：内存受限 → 降精度提有效带宽 → 融合消中间流量 → 编译兜剩余融合 → 仍不动则上推测解码/MoE；计算受限 → 确认 Tensor Core 在用 → 编译选核与内存规划 → FP8 双倍算力 → 重叠通信；通信受限 → 梯度重叠 → 降精度通信/压缩 → 重排流水线让通信藏进计算 → 拓扑感知摆放减跨节点流量。排序原则：**被动优化（编译器、换库）先于主动优化（算法改动、新组件）**。

实战：8×H100（NVLink）服务 70B 实时聊天，目标 TTFT <500 ms、ITL <50 ms、吞吐 ≥1000 tokens/s。

**基线**：FP16、eager、TP=8。TTFT 1200 ms、ITL 85 ms、吞吐 280 tokens/s、最大 batch 仅 4（KV 缓存卡死）。decode 步时间分解：GEMM 38%、注意力含 KV 读取 24%、逐元素 14%、AllReduce 12%、启动间隙 12%；Roofline 确认 batch=1 时 I≈1 FLOP/字节、深度内存受限（实测带宽 2.7 TB/s，80% 峰值——内核已不差，是算法性限制）。

**第 1 轮·精度**：AWQ INT4 权重（17.5 → 4.4 GB/GPU，含在线反量化的有效读取带宽约翻倍）+ INT8 KV 缓存（每请求减半）。可用 KV 空间 62.5 → 75.6 GB，服务策略为长上下文与尾延迟预留后，最大批量 4 → 32。结果：batch=1 ITL 48 ms（达标），batch=32 吞吐 720 tokens/s（未达标）；GEMM 时间降约 45%，注意力与逐元素原封不动——瓶颈部分转移。

**第 2 轮·融合**：torch.compile max-autotune 把逐元素从 14% 压到约 4%；FlashAttention-2 使 prefill 注意力 HBM 流量降约 16×（decode 中收益温和——decode 注意力被 KV 读取而非 S×S 矩阵主导，但叠加 INT8 KV + PagedAttention 后 decode 注意力时间降约 30%）；reduce-overhead 模式用 CUDA Graph 消掉几乎全部 12% 启动开销。结果：TTFT 380 ms、ITL 32 ms、吞吐 1050 tokens/s——三项全达标。

**第 3 轮·推测解码**：吞吐达标后压 ITL。1.5B draft（AWQ INT4 仅 0.75 GB）4 ms 出 5 个候选，目标模型约 32 ms 验证一轮；$p_{\text{acc}}=0.78$（单个草稿的接受概率）时按几何模型每轮期望约 3.5 个 token，有效 ITL \(\approx 4 + 32/3.5 \approx 10.3\) ms，**较 32 ms 再提 3.1×**。但它与大批量冲突：batch=32 时验证不再"免费"，故只在小批量（<16）启用、高负载回退标准解码的自适应策略。

三轮的元教训：**每次优化都移动瓶颈**——纯带宽受限 → 批量化后部分计算受限 → 融合后回到 decode 的本质带宽极限。最终系统是 INT4 权重 + INT8 KV + FlashAttention-2 + CUDA Graphs + 自适应推测解码五种技术的乘积，且互相纠缠：INT4 腾出的批量空间决定推测解码是否划算，FlashAttention 的收益随生成过程中的序列长度变化。每一步都必须重新剖析后再决策。

## 经验与常见坑

- **先诊断后优化**：对计算受限负载做融合、对开销受限负载做精度工程，都不会有改进。
- **量化的收益要靠局部性兑现**：量化模型若每个权重仍走片外读取，带宽节省归零。
- **开销量与长尾都要管**：Python 调度路径的每步数十微秒足以吞掉小内核收益，用编译/CUDA Graphs 消除；GEMM 近最优后，LayerNorm/激活/采样/启动开销的长尾可占一半以上时间，系统融合比继续磨 GEMM 有效。
- **通信重叠是有条件的**：只有有用计算能覆盖通信（不等式成立）时才有帮助，它是暴露时间测试而非新定律；集群扩到 1024 GPU 重叠效率可从 90% 跌到 18%。
- **峰值 FLOP/s 预测不了推理速度**：A100→H100 按规格表期望 3× 只见 15% 的教训——batch=1 解码由带宽决定，选型看带宽+容量；硬件升级后重新做 Roofline 分析。
- **降精度不是自动减半**：FP8 只加速精度敏感的受限项——逐元素操作受启动开销限制、通信受限负载梯度体积不缩就白降；实际加速取决于花在精度敏感操作上的时间占比。
- **推测解码与 MoE 都有隐藏账单**：推测解码在大批量下验证变真成本且扰乱连续批处理；MoE 专家数超过约 64-256 后，内存、AllToAll 流量、负载均衡与训练不稳定的系统成本压过容量收益。
- **精度与质量必须同报**：困惑度变化 <1% 也可能在罕见语言与复杂推理上可见退化；定向量化——最激进给 KV 缓存等不敏感组件，首末层与注意力 logits 保守；优化目标是吞吐-质量帕累托前沿。
- **单次剖析不充分**：热节流可降 10-15% 时钟、内存碎片数小时累积、网络拥塞随集群波动——性能非平稳，要在持续生产条件下多次采样。
- **平均值好不等于尾延迟好**：平均 ITL 30 ms 配 P99 500 ms 的交互体验由最差情况主导；预分配内存池、CUDA Graph 重放（消分配抖动）、延迟敏感请求优先调度。
- **编译器自动化已知优化，人负责发现新优化**：FlashAttention 的分块在线 softmax、推测解码、MoE 路由都是编译器改写规则之外的算法洞察；编译覆盖越广，系统设计能力越值钱。

## ⚠️ 时效性说明

- 硬件数字（H100 3.35 TB/s、1979 TFLOP/s FP8、脊点 295/590.7）基于 2023-2024 年代硬件；新硬件（如 Blackwell 的 FP4）会改变具体数值，但 Roofline 方法论不变。
