# 模型服务（Model Serving）

<p class="note-date">更新于 2026-11-05</p>

**一句话定义**：模型服务是在严格延迟约束下为终端用户或下游系统提供模型预测的**操作阶段**——它是分布式系统问题，模型执行只是包含请求路由、负载均衡和数据转换的栈中的一个组件。

## 概述：服务反转（Serving Inversion）

**为什么服务会颠覆训练成功的每一个优化优先级？** 训练与服务遵循相反的物理规律：

| 维度 | 训练 | 服务 |
|---|---|---|
| 目标 | 最大化吞吐量（样本/秒），大批量、长周期 | 最小化每请求延迟（毫秒），单次慢响应即故障 |
| 成本观 | 在数十亿示例上分摊硬件成本 | 对每个请求"征税"，低效累积为运营债务 |
| D·A·M 数据 | 容量优先 | **新鲜度**优先（实时请求） |
| D·A·M 算法 | 权重可变（反向传播） | **冻结**（固定前向传播） |
| D·A·M 机器 | 利用率优先 | **余量**优先（40%–60% 利用率吸收峰值，饱和会把小波动变成尾部延迟故障） |

铁律因此发生决定性转变：延迟项 L_lat 从舍入误差变为主导约束。服务优化的不是"占满的硬件"，而是**延迟承诺下的有用完成工作**。

**定义（定义 13.1）**：模型服务 = 在严格延迟约束下为终端用户或下游系统提供模型预测的操作阶段。常见误区："服务只是前向传播"——实际上模型执行只是更长流水线（预处理→推理→后处理）中的一环。

## 关键概念

### 排队与尾部延迟

生产系统面向**百分位延迟**（p50/p95/p99）而非平均值：平均 50ms 但 p99 2 秒，意味着每 100 个用户有 1 个比平均值多等 40 倍；谷歌/亚马逊的研究表明延迟增加 100ms 约损失 1% 销售额。

**「黑色星期五」案例**：1,000 QPS 下 50ms 舒适运行；流量 10 倍至 10,000 QPS 时系统不是慢 10 倍而是崩溃——利用率趋近 100% 时队列长度非线性发散，服务器忙于管理队列（上下文切换、抖动）而非有用工作，有效吞吐量趋近零。修复三件套：**减载**（立即拒绝多余请求保队列短）、**自动扩展**（在利用率到达排队"拐点"前扩容）、**降级**（改用更便宜的模型）。简单 M/M/1 近似下拐点约在 70% 利用率，p99 ≈ 4.6× 平均值（说明性数字）。

SLO 是内部目标（如 p99 < 50ms），SLA 是带经济处罚的外部合同承诺；SLO 应设得比 SLA 更严以留安全余量。

### 智能通缩与杰文斯悖论

API token 价格 2020–2025 年下降多个数量级（趋势约每 18 个月便宜 5.8×：GPT-4 原版、Claude 3 Opus 在 $10–100/M token 档，GPT-4o-mini、Gemini 1.5 Flash、DeepSeek-V3 在 $0.01–1 档）。⚠️ 供应商价格频繁变动，此为趋势快照而非采购指南。杰文斯悖论：每降 10 倍成本会打开此前经济上不可行的应用类别，总需求增长超过效率提升——**更便宜的推理可能增加而非减少总 GPU 舰队需求**。

**Facebook 的推理税**（Hazelwood et al. 2018）：动态消息排序、广告排名、搜索、图像理解（Lumos）、翻译（每天 45 亿条、2000+ 语言对）——机器学习最昂贵的部分已转移到推理（每天数万亿次操作、严格尾部延迟目标、实时到达限制批量、模型一小时不更新就降质）。结论：推理是一类数据中心基础设施问题，须与模型、加速器、内存系统共同设计。**训练创建模型，服务支付经常账单。**

### 静态推理 vs 动态推理

- **静态/离线/批量推理**：为预期输入预计算并存储（如每晚为所有用户-物品对生成推荐），请求时查表。把计算移出请求路径、可离线质检，但遇到意外输入需回退在线路径。
- **动态/在线/实时推理**：请求到达时按需计算，可处理任意输入、立即反映模型更新，代价是严格延迟约束。
- 生产常用**混合**：高频查询命中批量推理填充的缓存，长尾请求触发动态计算。

**延迟的成本估算**：$4/小时的 GPU 服务器，batch=1：延迟 5ms、吞吐 200 QPS、$5.56/百万查询；batch=8：延迟 10ms、吞吐 800 QPS、$1.39/百万查询。**把延迟从 10ms 降到 5ms，硬件账单增加 300%**——须量化提速的业务价值。另一反向趋势（推理时计算系统如推理链/搜索）故意花更多每查询计算换答案质量，把类训练级预算带入服务阶段。

## 服务架构

### 部署频谱：云 / 移动 / TinyML

| 特性 | 云/数据中心 | 移动端/边缘 | TinyML |
|---|---|---|---|
| 延迟目标 | 10–100 ms | 20–50 ms | 1–100 ms |
| 批量大小 | 1–128（动态） | 1（固定） | 1（固定） |
| 内存 | 16–80 GB 显存 | 2–8 GB 共享 | 256 KB–2 MB SRAM |
| 功率 | 300–700 W | 1–10 W | 1–100 mW |
| 更新 | 容器部署 | 应用商店 | 固件 OTA |
| 故障模式 | 重试/故障转移 | 优雅降级 | 静默或重置 |
| 监控 | 全遥测 | 有限分析 | 仅心跳 |

**同一个 ResNet-50 在三层级是三种不同的优化**：云端 TensorRT FP16 引擎（51.2 MB、batch-1 1.4ms、1143 张/秒批量）；移动端 TFLite INT8（25.6 MB、NPU 12ms / 0.8 mJ）；TinyML 根本跑不动 ResNet-50，须换 MobileNetV2-0.35 INT8（3.5 MB、120ms、320 KB 张量区适配 512 KB SRAM）。云与移动共享同一计算图但精度/运行时/内存相差 3–4 个数量级。

移动端独有优势是**零拷贝推理**：相机直接把像素写入 NPU 读取的缓冲区，消除云服务中多达 4 次的内存复制（每次复制都耗 CPU 周期与带宽）；需要相机/CPU/NPU 统一内存架构（苹果 M 系列、高通骁龙 SoC）。

### 负载均衡器与资源隔离

负载均衡器三大功能：**请求分发**（轮询/最少连接；避开慢副本可改善尾部延迟）、**健康监控**（ML 系统须验证进程活跃 + 模型就绪：权重已加载、预热完成）、**部署支持**（逐步切换流量而非全有全无）。

单机确定性延迟需对抗"嘈杂的邻居"（日志代理、监控、系统中断窃取 CPU 周期造成延迟抖动）：**CPU 亲和性绑定**（限制线程迁移与缓存局部性损失）、**mlock 内存锁定**（防止权重/KV 缓存被换出页导致毫秒级 DMA 停滞）、**中断屏蔽**（把网络/存储中断引导到非推理核心）。Clockwork 等系统证明仔细控制调度与执行可满足严格请求级 SLO。

### 推理服务器内部

推理服务器（NVIDIA Triton、TensorFlow Serving、TorchServe）是管理并发、内存与数据移动的高性能调度器，典型六阶段流水线：客户端 → 网络入口(HTTP/gRPC) → 请求队列 → 调度器/动态批处理 → 执行优化 → 加速器推理运行器(TensorRT/ONNX)。三大职责：**并发管理**（异步事件循环/线程池避免网络 I/O 闲置加速器）、**请求转换**（JSON/Protobuf → 张量格式；NCHW 利于 GPU 卷积——PyTorch/TensorRT 首选，NHWC 利于 CPU SIMD——TensorFlow 默认；布局不匹配会产生形状看似有效但错误的张量）、**模型管理**（权重加载、版本活动、预热）。

调度器体现核心权衡：**批量窗口**参数——0ms 优化纯延迟（无批量），小的有界窗口用可控等待换更高加速器利用率。

### 接口协议与序列化

ML 载荷是多维浮点数组，文本格式代价高：JSON 把 4 字节浮点膨胀为 10–15 字符，二进制需 Base64（+33% 体积）。估算：1,000 个浮点的载荷，JSON ≈ 9 KB / 50µs 解析，Protobuf ≈ 4 KB / 5µs——每请求省 45µs，10,000 QPS 下释放 45% 的一个核心。REST（HTTP/1.1+JSON）通用、可读、无状态，但无状态迫使每次重发上下文（LLM 对话上下文可超 10KB token）；gRPC（HTTP/2+Protobuf）单连接多路复用、类型化二进制序列化，适合内部高 QPS 张量流量。FlatBuffers 支持零拷贝读取（缓冲区即数据结构）。

## 请求生命周期与延迟预算

**延迟预算（定义 13.2）**：分配给推理请求的时间资本，受端到端 SLO 硬约束。它是零和约束——序列化或网络开销耗掉的毫秒直接减少模型可用预算。常见误区："模型"拥有整个预算——实际上**模型通常不到总预算的 50%**，其余被 DNS/TLS/负载均衡/序列化消耗。

**ResNet-50 预算分解**（10.1ms 总计）：JPEG 解码 3ms(30%) + resize 1ms(10%) + 归一化 0.5ms(5%) + CPU→GPU 复制 0.5ms(5%) = 预处理侧 44.6%；前向传播 5ms(50%)；Softmax 后处理 0.1ms。若用 TensorRT 把推理压到 2ms，预处理将占 63.4%——**更快的硬件不自动等于更快的服务**。

**DLRM 服务分解**（10ms p99 预算，实际 9ms）：请求解析 0.5ms(CPU)、嵌入查找 6ms（内存带宽，取 100+ 个 128 维向量）、MLP 前向 1.5ms（计算）、排序过滤 1ms(CPU)——"推理" MLP 只占约 17%。**阿姆达尔定律**：预处理+复制占 49.5% 时，模型优化 10 倍只带来 1.8 倍端到端加速（10.1→5.6ms）。通用方法论：**先测量每阶段，再按时间占比分配优化精力**；模型占总延迟不到一半时，只优化模型收益必然递减。

**服务税单**（非推理开销的代表性范围）：网络 I/O 1–5ms（线性于载荷；对策：压缩、区域共置）、序列化 50–500µs（对策：gRPC/Protobuf）、排队 0.1–10ms（随负载指数增长；对策：动态批量、自动扩展）、分派 10–50µs（对策：内核融合）、数据复制 100–500µs（对策：零拷贝/共享内存）。**致命微秒问题**（Barroso/Patterson）：微秒级操作对 OS 调度太短、对自旋等待太长；单个都小，合计在 5ms 推理服务中消耗约 3%–21% 延迟预算，共同决定能否满足 SLO。

### 分辨率权衡与流水线

计算受限时吞吐量与分辨率平方成反比：`Throughput(r₂)/Throughput(r₁) = (r₁/r₂)²`（224→448 理论慢 4 倍，实测 3.6 倍因固定开销摊薄）。ResNet-50 的算术强度随分辨率升高（224²:32.2 → 640²:109.2 FLOP/字节，均高于 V100 拐点 ~15.6），更高分辨率把工作负载推入更深的计算受限区。**自适应分辨率**：轻量分类器（128²）先判内容类型再选主模型分辨率（文档 512²、风景 224²、人脸 384²）→ 1.4× 吞吐量、保持 99.2% 准确率。

**请求流水线**：串行执行时 GPU 在网络 I/O 和 CPU 预处理期间闲置超 50%；用异步 I/O 让 CPU 预处理第 N+1 个请求的同时 GPU 推理第 N 个，占空比可接近 100%，**不改模型即提升同硬件吞吐 2–3 倍**。

## 排队理论形式化

**Little's Law**：任何稳定系统中，系统内平均请求数 \(Q_{req} = \lambda_{arr} \cdot T_{lat}\)（到达率 × 每请求在系统时间），与到达分布、服务分布、调度策略无关。它把可观测指标直接翻译成容量需求：1,000 QPS、50ms SLO 意味着必须同时持有 50 个并发请求槽（批状态+队列状态的硬下限）——GPU 内存放不下 batch 32，物理上就不可能同时达到 1,000 QPS 和 50ms，唯一出路是降 \(T_{lat}\) 或加显存撑更大的驻留 \(Q_{req}\)。反向用法：10ms 平均延迟下观测到 50 并发 → 实际到达率 5,000 QPS；显存限制并发 10、服务 10ms → 最多 1,000 QPS。

**批处理税**：批量引入两类延迟——批成形等待（批内第一个请求等最后一个到达）与推理膨胀 \(T_{inf}(B)\)。批大小 B、到达率 \(\lambda_{arr}\) 下的总延迟：

$$L_{lat,total} \approx \frac{B-1}{2\lambda_{arr}} + T_{inf}(B)$$

500 QPS 下从 batch-1 到 batch-32，等待 0ms → 31ms，总延迟 2ms → 46ms（23 倍惩罚）。批大小是经济效率的主调节阀：在不违反 SLO 的前提下最大化吞吐。

**利用率-延迟非线性**（M/M/1，\(\rho_{serv} = \lambda_{arr}/\mu\) 为利用率）：

$$T_{lat} = \frac{1}{\mu - \lambda_{arr}} = \frac{\text{服务时间}}{1-\rho_{serv}}$$

| 利用率 | 延迟倍数 | 5ms 服务的实际延迟 |
|---|---|---|
| 50% | 2× | 10 ms |
| 70% | 3.3× | 17 ms |
| 80% | 5× | 25 ms |
| 90% | 10× | 50 ms |
| 95% | 20× | 100 ms |

从 80% 到 90% 利用率延迟翻倍——这就是"温和的流量增长导致 SLO 违约"的数学根源。ML 推理固定批大小下服务时间近常数，M/D/1 更精确（平均等待约为 M/M/1 的一半）；用 M/M/1 是因为它闭式可解且保守——按它规划会轻微超额配置，宁可多买机器也不违约。

**尾部延迟**：M/M/1 的 p99 近似

$$T_{lat,p99} \approx \frac{4.6 \times \text{服务时间}}{1-\rho_{serv}}$$

70% 利用率时 p99 ≈ 15.3× 服务时间，均值却只有 3.3×——平均延迟健康的系统尾部可以不可接受。多机 fan-out 再放大这一点（tail-at-scale）：请求扇出到多台服务器时，至少遇上一台慢响应的概率随台数快速增长，整体尾延迟由最大值决定。

**容量规划实战**（ResNet-50，p99 50ms、峰值 5,000 QPS、TensorRT FP16 服务 5ms）：① 由 p99 公式反推安全利用率 \(\rho \le 1 - 4.6{\times}5/50 = 0.54\)；② 需要服务率 5,000/0.54 ≈ 9,259 req/s；③ V100 batch-16 吞吐 1,143 img/s → 8.1 → 9 块 GPU；④ 加 30% 余量抗流量方差 → 12 块；⑤ 验证容错：坏 1 块剩 11 块，利用率 39.8%，仍低于 54%，N+1 冗余成立。吞吐数字只有在请求仍满足百分位 SLO 时才是"真的"（MLPerf 只统计满足 SLO 的有效 QPS）。

**尾部容忍技术**（按失效模式选择）：慢副本→**竞速**（hedging：超时即向其他副本发重复请求、取先返回者；在 p95 触发仅增加 5% 负载即可大幅压尾。GPU 内核一旦启动难以廉价取消，须预算重复计算）；**绑定请求**（tied：同时发多台、他台开算即取消，免去检测等待，适合模型加载开销大的服务）；fan-out→**金丝雀请求**（先发 1–2 台探路，慢则重试或用缓存，再全量扇出，把尾部放大问题变成预警信号）；过载→**优雅降级**（返回近似结果：相似输入的缓存预测、更短输出、削减 ensemble 成员——缩短服务时间 \(\mu\) 上升、利用率被拉回拐点以下，用可控精度损失换 SLO 存活）与**准入控制**（队列超阈值立即 503，起点取 worker 数的 2–3 倍，如 4 worker → 阈值 8–12；ML 推理服务时间近确定，准入控制器比通用 Web 服务的粗启发式精确得多）；重试放大→**协同减载**（副本间共享负载信息，全局过载时各副本拒绝同一比例，避免被拒请求互相重试引发雪崩）。生产还常用 deadline 感知/最短作业优先等优先级调度进一步压尾。

## 模型生命周期管理

### 训练-服务偏斜

权重相同，服务准确率却可能静默下降——预处理分歧使 \(f_{train}(x) \neq f_{serve}(x)\)。与数据漂移（外部环境变化）不同，这是工程栈的内部缺陷，且**对异常监控和延迟看板完全不可见**：系统运行完美、延迟很低，预测在统计上是错的。ResNet-50 三个典型分歧点：resize 插值（训练 PIL.BILINEAR vs OpenCV 默认 cv2.INTER_LINEAR，像素级差异即可移动 0.5–1 个百分点准确率）、色彩通道（RGB 训练 BGR 服务 = 预测近乎随机）、归一化常数（mean=[0.5,0.5,0.5] vs [0.485,0.456,0.406]）。最稳做法：直接导出训练用的预处理代码在服务端原样运行，或用 NVIDIA DALI 统一两侧管线。

### 冷启动

冷启动是**每副本**的固定成本（推理延迟是每请求成本），包含权重加载、图编译、显存分配、预热四阶段。ResNet-50 时间线：本地 SSD 加载 98MB 权重 0.5s（S3 走网络 3–5s）、CUDA 上下文 0.3–0.5s、TensorRT 编译 15–30s、预热 0.2s、运行时开销 0.4s——预编译引擎的热容器共 ~1.5s，云上首次部署含编译 ~35s。没有预热时第一个真实请求会触发编译与分配，平时 5ms 的请求要 500ms。**预编译并存储优化引擎**可消除后续部署的 30 秒编译。

加载策略三选：**全量加载**（推理最快、冷启动最长、模型受限于显存）；**内存映射 mmap**（按需分页、启动快，但初期请求有缺页延迟尖刺）；**惰性初始化+合成预热请求**（启动最快，初始化成本转嫁给真实流量到达之前）。缓存基建按更新频率选：模型少更新→打进容器镜像（单镜像 10–50GB）；频繁更新→共享文件系统（EFS/GCS FUSE，网络延迟影响冷启动）；性能关键→节点本地 SSD（NVMe ≥500MB/s）+后台刷新。

### 多模型共置

GPU 显存是约束。三种策略：时间多路复用（一次一个模型、按路由换入换出，有 swap 延迟）、显存分区共享（更多模型常驻但限并发）、模型虚拟化（Triton 的模型仓库+加载/卸载/版本控制 API，把模型生命周期与应用代码解耦）。流量均匀选并发加载，突发且按模型分布选时分复用+显式预加载。硬件隔离用 **MIG**：A100 最多切 7 个独立实例（A30 4 个），H100/H200 延续；老卡（V100/T4）用 CUDA 流时分复用。CUDA MPS 允许多进程 GPU 工作重叠、降低上下文切换开销，代价是故障隔离变弱。模型总量超显存需在主存与显存间换页：10GB 模型走 PCIe Gen4 x16（32GB/s 理论带宽）至少 312.5ms（未计反序列化/图构建/预热）；**pinned memory**（页锁定）让 GPU DMA 免去 pageable→pinned 的 staging 拷贝，代价是这块 RAM 不可回收——权重和常用输入缓冲值得 pin，其余留给可换页内存。

## 吞吐量优化与批处理

同一块 V100：batch-1 只有 15% 利用率、200 img/s；batch-32 达 95%、1,280 img/s——**6.4× 提升来自摊销固定成本**，不改模型不改硬件。两个固定成本：内核启动（每层 5–20μs、与批大小无关；ResNet-50 约 50 层即 250–1000μs，batch-1 时超过计算本身）、权重读取（batch-1 每张图读一遍全部权重，batch-32 读一次用 32 次）。

| 批大小 | 推理时间 | 每图计算 | 吞吐 | GPU 利用率 |
|---|---|---|---|---|
| 1 | 5 ms | 5 ms | 200 img/s | 15% |
| 4 | 7.2 ms | 1.8 ms | 556 img/s | 42% |
| 8 | 9.1 ms | 1.1 ms | 879 img/s | 65% |
| 16 | 14 ms | 0.9 ms | 1,143 img/s | 85% |
| 32 | 25 ms | 0.8 ms | 1,280 img/s | 95% |

用户感知延迟 = 等待 + 计算：$$L_{lat} = L_{lat,wait} + L_{lat,compute}(B)$$ 批处理窗口 \(T_{window}\) 约束等待上限，泊松到达下平均等待恰为窗口一半：

$$E[L_{lat,wait}] = T_{window}/2$$

20ms 窗口 = 平均白等 10ms（50ms 均值 SLO、5ms 推理时，等待先吃掉 20% 预算；尾部 SLO 要按满窗口预算）。窗口内收集的请求数服从泊松分布，均值 \(\lambda_{arr} T_{window}\)、方差=均值：50 QPS + 10ms 窗口 → 平均批 0.5，61% 的窗口是空的（浪费 GPU 周期）；1,000 QPS → 平均批 10，波动大幅收敛。**尾部分析**：λ=500 QPS、10ms 窗口时平均批 5（均值延迟 5+8=13ms），p99 批 11（10ms 满窗 + 11.6ms 服务 = 21.6ms），p99 是均值的 1.66×——按均值配置必然违约。

**Pareto 前沿**（ResNet-50/V100 代表值）：窗口 2ms → 890 img/s / p99 18ms；5ms → 1,140 / 22ms；10ms → 1,240 / 35ms；20ms → 1,310 / 52ms；50ms → 1,350 / 98ms。窗口从 2ms 拉到 50ms，吞吐只多 52%，p99 涨 5.4 倍——拐点之后批量性价比急剧恶化。工程法则：把 SLO 的 20–30% 分给批处理等待（\(T_{max} = 0.3 \times L_{lat,SLO}\)），流量估算用 p95 到达率而非均值（尖峰时恰是最需要余量的时刻），并监控生产批大小分布——高方差说明窗口该做成自适应。窗口经验式：

$$T_{window} \approx \min\left(L_{lat,SLO} - T_{svc},\ \sqrt{T_{svc}/\lambda_{arr}}\right)$$

反直觉结论：**流量越大，最优窗口越短**，同时批次反而更大（100 QPS→15.8ms 窗/均批 1.6；5,000 QPS→2.24ms 窗/均批 11.2）——高流量下批自然形成，无需长等。自适应窗口（按队列深度：够目标批立即关窗、低流量用剩余 SLO 预算攒批）比固定 10ms 窗口平均延迟降 27%（15ms→11ms）、吞吐 +5%（650→680 img/s）。批处理不是普适药方：p99 <10ms 的超低延迟、输入尺寸差异大（padding 白烧算力）、显存吃紧时都不该批。会话亲和（sticky routing）与批量冲突：多轮对话复用 KV 缓存、按用户加载 adapter 都要求路由回同一副本，生产常用**软亲和**——优先回原副本、过载时溢出，兼顾亲和收益与负载均衡。

### 流量模式决定批策略

MLPerf 四场景即四种到达模式：**Server**（云 API，泊松到达）→ 动态批+超时，调窗口与利用率-延迟曲线；**MultiStream**（自动驾驶/视频分析，多传感器同步）→ 批大小和 deadline 由外部定死：六相机 30FPS 的 33ms 硬截止中留 12ms 作抖动容差，20ms 未到的帧用上一帧顶替——优化点是同步策略而非窗口；**SingleStream**（移动/嵌入式，单用户）→ 无批可做，目标转为每请求能耗：手机端 ResNet-50 全管线 45ms / 2.98mJ（JPEG 解码吃掉 1.5mJ 居首；NPU 推理 12ms/0.8mJ 且利用率 82%——移动 NPU 容量匹配单图负载，与数据中心 GPU batch-1 只有 15% 形成对照），2.98mJ 意味 10Wh 电池约 1,210 万次推理、66mW 持续功耗不触温控；温度到 45°C 结温时 NPU 降频 30–50%，所以允许散热的突发型负载跑赢持续满载；模型被系统逐出后重载要 200–500ms，内存映射加载可缓解；**Offline**（批量处理）→ 最大化批大小，只看吞吐。

### 连续批处理与 PagedAttention

LLM 输出长度未知：批内 8 序列若一个 10 token 就结束、其余要 100 token，该槽位 90% 算力浪费。**连续批处理**（iteration-level / in-flight batching）在每个解码步之间允许新请求加入、完成序列退出，序列长度差 100× 仍保持高占用（vLLM、TensorRT-LLM；Sarathi-Serve 再用 chunked prefill 减少 prefill 与 decode 相互干扰）。随之而来的 KV 缓存动态分配产生碎片：100 token 序列释放的空间放不进 150 token 新序列，碎隙累积——朴素实现的碎片+超量预留浪费 40–50% 显存（静态批设计下浪费 60–80%）。**PagedAttention**（vLLM）借操作系统虚拟内存思想把 KV 缓存切成固定大小页（典型 16 token），序列持有非连续页指针，完成后页回自由列表，浪费压到 4% 以下，同硬件吞吐提升 2–4×，代价只是注意力计算中一次页表查找。

## LLM 服务

LLM 服务新增三个性质：**自回归**（每 token 依赖此前全部 token，串行生成）、**变长输出**（请求时不知道答案多长，固定批假设失效）、**有状态记忆**（KV 缓存随每 token 增长，动态内存压力）。指标随之分相：**TTFT**（首 token 时间，白屏预算，由计算受限的 prefill 决定）与 **TPOT**（每输出 token 时间，阅读流畅度，由内存带宽受限的 decode 决定）。参考目标：1,000 token 提示下 TTFT < 500ms，TPOT < 50ms（≈20 token/s，快过人读），集群聚合吞吐 > 1,000 token/s。快 TTFT 配慢 TPOT 是最糟体验——答案出得快但后面卡顿。

解码策略是质量-成本旋钮：**贪心**每 token 一次前向但易复读、无法从早期错误恢复；**beam search** 宽度 5 即约 5× 每 token 计算，交互场景基本不用；**温度/top-k/top-p 采样**几乎零额外算力，代价在输出长度方差——它拉宽连续批处理要吸收的序列长度分布。生产必做**流式输出**（chunked HTTP + 客户端增量渲染）：同样 2 秒总时长，token 连续流出是"流畅"，盯着白屏 2 秒是"坏了"。

**KV 缓存是第一内存约束**：70B 级 GQA 模型 FP16 约 0.31MB/token/序列，batch-32 × 8k 上下文仅 KV 就要 ~80GB——70B 场景下 batch-32 在 8k 上下文就进 OOM 区，上下文长度（能力）与批大小（吞吐）此消彼长。对策：**前缀缓存**（共享系统提示/RAG 上下文的 KV 只算一次，N 个请求共享 S token 前缀省约 (N−1)·S 次 token 步；多轮对话每轮只处理新增 token）；**KV 卸载**（不活跃上下文溢出到主存/NVMe，重载成本 ≥ 字节数÷PCIe/NVMe 带宽，换来更大上下文但引入亲和、失效与热解码延迟风险，须显式预算）。

**能量账**：H100（700W + 300W 主机）跑 114 并发 × 8 token/s ≈ 912 token/s → 约 1.1 J/token；500 token 回答约 548 J（对比：手机充满电约 40,000 J、烧一杯水约 100,000 J）。若批处理差导致利用率仅 10%，空闲功耗仍 ~300W，涨到 >3.3 J/token。降 J/token 的主路是提高利用率 + 前缀缓存跳过重复 prefill。

## 运行时选择与节点级优化

同一 ResNet-50（V100，batch-1）在不同运行时：PyTorch eager 8.5ms（1× 基线）→ TorchScript 6.2ms（1.4×）→ ONNX Runtime 5.1ms（1.7×，跨平台）→ TensorRT FP32 2.8ms（3×）→ FP16 1.4ms（6.1×）→ INT8 0.9ms（9.4×，需校准，准确率损失 <1pp）。每往下一档都是用可移植性换速度。专用引擎的武器：**算子融合**（conv+BN+ReLU 三内核合一，省一次 HBM 往返 15–60μs/融合、内存流量降 2–3×；ResNet-50 约 50 内核 → 15）、**内核自动调优**（同一卷积有直接/FFT/Winograd 等几十种算法，逐一 benchmark 缓存赢家，用编译时间换运行时性能）。

**精度即基础设施经济学**：带宽受限算子上降精度近线性提吞吐，理论上限 INT8/FP32 = 4×，实际受 Tensor Core 对齐限制在 2.5–3.5×。ResNet-50/V100：FP32 2.8ms/76.13% → FP16 1.4ms/76.13%（近免费的 2×）→ INT8 PTQ 0.9ms/75.80%（3.1×，需 1,000 样本校准）→ INT8 QAT 0.9ms/76.05%（恢复精度但要重训）。层敏感度 \(\epsilon_{quant} \propto \kappa_{quant} \cdot \|W\|_2 \cdot 2^{-b}\) 解释经验规律：首层与末层敏感（留 FP16），中层容忍 INT8。校准集必须代表真实服务流量：ImageNet 校准的模型上线野生动物相机图像，76.1% → 72.9%（−3.2pp）。30 卡 FP32 集群换 INT8 = 同硬件 3× 吞吐 = 账单砍 2/3。进阶做法是把精度做成运行时策略：SLO 余量足用高精度、低置信度回退 FP16 重算、按客户分级定精度。

**节点级优化补最后 2–5×**。图编译：服务图是静态的，可在部署时完成算子融合、常量折叠、内存预规划（缓冲区复用，消除分配器停顿）；JIT 灵活但首个请求付编译尖刺，AOT 无启动尖刺但须穷举所有 shape 档。CPU 推理：标量 Python 循环只能用 ~1% 峰值，SIMD 内核（AVX-512/AMX）可到 80–90%；NUMA 错配（线程与内存在不同 socket）带来 ~60% 延迟惩罚（远程 ~130ns vs 本地 ~80ns），且因权重远超 L3 每个 pass 都发生——线程绑核 + 权重就近分配。小模型（<50MB）batch-1 时 CPU 常反超 GPU：省掉 ~10μs 内核启动 + ~50μs 传输。序列化格式直接决定扩容速度：5GB Stable Diffusion 权重，pickle 加载 15s，Safetensors（裸字节+最小 JSON 头，零拷贝 mmap，且反序列化不执行任意代码）1.5s——10× 差距决定新副本能否在 SLO 破坏前吸收尖峰。最后一切靠 timeline 剖析闭环（PyTorch Profiler / Nsight Systems）：GPU 条空白 = 等 CPU 预处理或 IO，海量微小内核 = 该融合，MemcpyHtoD = 看传输是否与计算重叠；每次只改一处，下一份 trace 必须朝预期方向变化。按目标指标选技术：算子融合 2–5×（延迟+吞吐）、INT8 3–4×（吞吐，成本在校准）、图编译 1.5–3×（延迟，一行配置）、零拷贝加载 10–50×（启动时间）、CPU 绑核降 20–50% p99。

## 经济学与容量规划

每推理成本四分量：计算、显存、数据传输、编排开销。利用率决定主导项——高利用率时计算主导，低利用率时显存主导（GPU 闲置也在计费）：提吞吐降的是计算成本，提利用率降的是闲置浪费。AWS 按需价格对比（ResNet-50）：c5.xlarge CPU $0.17/时、50 img/s → $0.94/百万张；T4 $0.53/时、400 img/s → $0.37/百万张；V100 $3.06/时、1,200 img/s → $0.71/百万张。**时薪更高不等于更贵**：T4 单位成本最低；V100 只在持续高流量下划算。GPU 与 CPU 的取舍不止稳态：CPU 实例 30–60s 启动，GPU 2–5 分钟（驱动+加载+预热）——尖峰来得比 GPU 扩容快时，容量最终够也照样违约。CPU 适合响应式扩容，GPU 需要预测式扩容；突发型负载用混合架构：GPU 保底 + CPU 溢出承接尖峰。容量规划三输入（流量模式、延迟 SLO、各批大小下的推理时间分布）→ 安全利用率阈值 → 副本数 + 30% 余量（见排队理论一节的 12 块 V100 实战）。

**案例：8B Llama 3 单卡 H100**（4-bit AWQ 权重 4.1GB，HBM3 3.35TB/s；1,000 token 输入、256 token 输出；SLO TTFT < 200ms、TPOT < 20ms）：prefill 并行处理 1,000 token ÷ 10k token/s = 100ms + 20ms 系统开销 → TTFT 120ms 达标。decode 是纯带宽问题：算术强度 ≈1 FLOP/字节，每生成一个 token 都要读完整个 4.1GB 权重，$$T_{token} \approx D_{vol}/BW_{memory}$$ = 1.2ms 理论下限、1.53ms 实际（含内核开销与保守余量），256 token 共 0.39s，TPOT 远优于 20ms。内存：4-bit KV 约 0.033MB/token（GQA 相对全多头注意力省 KV 头），~75GB 余量 ≈ 220 万 token 容量 → 理论并发 ~1,749 请求；但 prefill 吞吐限定准入 10 req/s → 每小时约 4,520 万 token，$3/小时 ≈ **$0.066/百万 token**。结论：KV 容量决定最大并发驻留，prefill 算力与 decode 带宽决定实际吞吐，**带宽决定 decode 延迟**——加计算核心对 token 延迟无效，只有更快内存、更小模型或更好批处理能改变约束。

## 经验与常见坑

- 用训练思维做服务：追求加速器饱和会把小流量峰值放大为尾部延迟崩溃；留 40–60% 余量是特性不是浪费。
- 优化最显眼的（模型量化/剪枝）而非最昂贵的（JPEG 解码、嵌入查找带宽）——先分析后优化。
- "推理时间 = 服务时间"：模型只占预算一部分；序列化这类"税"合计可能吃掉一半预算。
- 高平均吞吐量不能防崩溃：利用率须控制在排队拐点以下。
- 把"同一个模型"跨端部署当成同一件事：每个部署上下文都是独立的优化（甚至换架构）。
- 批量窗口调 0 追求极限延迟或调大追求吞吐而不看 SLO：这是调度器最关键的显式权衡点。
- "降低模型推理延迟就能等比例降低用户延迟"：排队延迟与利用率耦合。80% 利用率下把推理 5ms→2ms，利用率降到 32%，排队等待从 20ms→0.9ms——系统级 8.5×（25ms→2.9ms）远超模型级 2.5×；反之高利用率下 20% 的模型优化用户几乎无感。要在真实负载下分析完整延迟预算，而非孤立剖析推理。
- "训练/验证准确率保证服务准确率"：权重相同也会因预处理偏斜从 95% 掉到 90%，且对延迟与异常监控不可见；须复用同一预处理代码或做输入分布统计监控。
- 用平均延迟评估服务质量：70% 利用率下均值 16.7ms、p99 76.7ms（4.6×），平均看板看不到决定体验的尾——SLO 用百分位正是为此。
- "加大批总是提升吞吐不伤 SLO"：批 16→32 吞吐只 +12%，批推理 14ms→25ms 近翻倍，变长输入的 padding 还白烧算力；批大小、超时、并发须联合对着 p99 调。
- 用训练数据而非真实流量校准量化：ImageNet 校准的模型上线野生动物相机图像 76.1%→72.9%；量化是数据-算法协同设计，校准集必须采自实际服务流量。
- "冷启动只影响第一个请求"：尖峰需 10 个新副本 = 300 副本-秒的冷启动工作；冷实例上请求 500ms vs 稳态 5ms，恰在流量最高、部署与故障恢复窗口违约。扩容预算必须含 warm pool（预初始化副本）、分级加载与编译/健康检查时间，否则扩容是在给尾部延迟添堵。

## ⚠️ 时效性说明

- API token 价格、硬件型号（V100/A100/H100、TPUv4）与具体延迟/能耗数字为 2018–2025 年快照，会随硬件与定价迭代过时；方法论（排队拐点、延迟预算、阿姆达尔、余量设计）不随其过时。
