# 大规模推理

<p class="note-date">更新于 2026-11-03</p>

**一句话定义**：大规模推理研究如何把训练好的模型变成全球规模的低延迟服务——在严格的尾部延迟（P99）预算内，用批处理、内存管理、模型分片、路由、多租户隔离与自动扩展，压低持续服务成本。

训练是一次性资本支出，服务是随用户增长的持续运营支出：一个训练费数百万美元的模型，生命周期推理开销可超训练成本几个数量级，省下的每一毫秒、每一页内存都会在数十亿次请求上复利。性能工程提供单机工具（融合、精度、编译、推测解码），本篇把这些工具放到服务规模下，叠加批处理、分片、路由、扩展与隔离。

## 核心原理

### 服务成本主导定律

`C_total = C_training + C_serving × T_deployment × Q_rate`。服务/训练成本比：推荐与搜索排序类高 QPS 应用为 100-1000 倍，LLM API 为 10-100 倍。实例：训练 $200 万的 70B 模型服务 100 万 DAU（每人每天 50 请求、每请求约 $0.001），一年服务成本 $1825 万，仅第一年就是训练的 9.1 倍；高流量推荐系统几天内服务成本即超训练，高流量 LLM 约 6 周。

### 分布式推理的三个触发条件

| 约束类型 | 单机限制 | 示例 | 分布策略 |
|---|---|---|---|
| 内存 | 80 GB（H100 HBM） | GPT-4 级约 1.8T 参数（FP16 约 3.5 TB）；DLRM 嵌入表数 TB | 张量/流水线并行、嵌入分片 |
| 吞吐 | 约 10K QPS（视觉） | 10 万 QPS 推荐系统 | 水平复制 |
| 延迟 | 模型执行时间超预算 | LLM TTFT 需 <500ms | 分片或复制，视瓶颈而定 |

### 训练 vs 推理的根本转变与服务税

训练优化吞吐（样本/小时）、维护检查点状态、可从检查点重启；推理优化 P99 延迟、维护持续性会话状态（KV 缓存）、故障必须对用户无感（重定向/降级而非重启）。分布开销即"服务税"：`T_total = T_compute + T_network + T_serialization + T_coordination + T_queuing`，通常吃掉延迟预算的 10-30%——数据中心网络往返 50-500 μs/次，传统序列化器（JSON/protobuf/pickle）对 1 GB 激活约 100 ms（零拷贝格式 FlatBuffers/Cap'n Proto 可规避大部分但布局约束严），负载均衡器 100-500 μs。延迟预算必须显式为服务税留份。

### 推理全景与服务层次

LLM 不是全部：消费平台中推荐/排序常占推理量大头，各负载瓶颈不同——推荐在嵌入查找（<10ms P99）、视觉在批效率（20-100ms）、LLM 在内存带宽（100ms-10s）、语音在顺序解码（实时）。优化按四级层次组织，每级换不同的指标：请求级（单请求延迟：批处理/缓存/预取）→ 副本级（吞吐/利用率：内存优化/内核融合）→ 服务级（聚合容量：负载均衡/路由/自动扩展）→ 平台级（资源效率：多租户/调度/放置），优化错层级就改变错误的指标。部署栈三层：CDN/边缘（SLA <10ms）→ 网关/路由（<50ms）→ 模型服务集群（<2s，GPU 冷启动约 60s）。

## 服务架构五维度

选服务系统 = 按工作负载约束在五个维度上选设计点，而非逐特性比框架：

| 维度 | 视觉/嵌入 | LLM（自回归） | 推荐 |
|---|---|---|---|
| 批处理 | 静态/动态（输入均匀） | 连续（输出长度可变） | 特征并行（分片输入） |
| 内存 | 预分配（可预测） | 分页（KV 缓存可变） | 分布式（嵌入表） |
| 调度 | FCFS（成本均匀） | 抢占式（方差大） | 优先级（SLO 分层） |
| 拓扑 | 单卡副本 | 张量/流水线并行 | CPU-GPU 混合分片 |
| 状态 | 无状态 | 有状态（KV 缓存） | 无状态（特征存储） |

关键区分：无状态服务横向扩展是平凡问题（加副本+负载均衡，故障即时切换）；有状态的 LLM 服务需要粘性路由、排水式缩容、昂贵的故障恢复——这是模型架构的后果，不是框架特性。

## 批处理策略

### 效率曲线与 Little 定律

延迟 `T_lat(B) = T_fixed + B × T_variable`，吞吐 `X(B) = B / T_lat(B)`：小 B 时开销受限（超线性增长），大 B 时逼近硬件上限 1/T_variable，膝点在交界。视觉模型 T_fixed 小（简化模型膝点 B≈2，实际硬件饱和要到 32-64）；LLM 解码因权重加载（140 GB）T_fixed 巨大，膝点约 B≈80——**LLM 必须靠连续批处理+分页内存把数百并发用户塞进一个批，才能喂饱带宽**。Little 定律 `Q_req = λ_arr × T_lat` 做容量规划：目标 1000 req/s、SLO 100ms → 需 100 并发；单副本 batch=8、80ms → 吞吐下限 10 副本，按 SLO 留余量应配 13 副本（利用率约 77%，给排队波动留头部空间）。

### 连续批处理（Continuous Batching）

静态批处理要求整批等到最长序列完成，输出长度方差大时浪费超 50% GPU 计算。Orca（2022）引入迭代级调度：批成员与迭代边界解耦，每个解码步允许新请求进入、已完成请求退出并立即复用其 KV 槽位。量化：浪费率 `W = 1 − S̄/S_max`，吞吐增益 ≈ 1 + CV²/2（CV 为输出长度变异系数），CV≈1 的典型聊天约 1.5 倍、RAG 类高方差可达 3.5 倍；实测（Llama-2 70B @ 8×A100）静态 400 tokens/s（利用率 45%）→ 动态 580（65%）→ 连续 1200（92%）。示例：4 个请求输出 50/200/100/150 token，静态批平均延迟 4000ms、连续批 2500ms（-37.5%，恰等于浪费率）——连续批处理不会让最长请求变快，只是防止短请求占着已完成的槽位陪跑。它不是"纯调度器改动"：需要动态内存管理（PagedAttention）、变长序列内核，调度开销从每批 O(1) 升到每迭代 O(B)。

### 其他批处理模式

- **推荐系统特征并行**：瓶颈是分布式嵌入查找而非稠密矩阵乘，按特征类型（用户/物品/上下文）分组并行查找再拼接进稠密排序塔。Meta 规模：1000 万 QPS、每请求约 5000 次查找、100 TB 表 1000 分片 → 每分片 5000 万次查找/秒，用 1ms 攒批窗口得每批约 5 万次查找；单请求延迟：路由 0.2 + 攒批 0.5 + 查找 2 + 特征处理 1 + 排序 1.5 ≈ 5.2ms（10ms SLO 内）。
- **流式推理**（语音/视频/机器人）：批处理本身就是错误响应，逐帧处理（语音 10-20ms 帧、端到端约 100ms 预算），GPU 利用率刻意降到 30-50% 换延迟保证；约束是帧间 deadline，不是吞吐。
- **自适应批处理**：流量自适应（`T_window = min(T_max, B_target/λ)`）、SLO 自适应（P99 > 0.9×SLO 砍批量/窗口，< 0.5× 放大）、请求感知（按预期输出/提示长度分组）；Triton 三旋钮 max_batch_size / batching_timeout_ms / preferred_batch_size，按 `argmin_q(wait_q + exec(|q|+1))` 选队列。
- **Test-time compute（逻辑墙）**：推理模型让"每请求工作量"从可观察量变成调度器要决定的量——128 个思考 token 的证明延迟约 12.8 秒（vs 单 token 回答 100ms）；系统从吞吐工厂变成搜索引擎，需要"推理 SLO"：难题可容忍十几秒，简单问候不行。

### 调试实例：P99 尖刺

P50 100ms / P95 180ms 达标但 P99 500ms（目标 200ms），GPU 利用率"健康"的 85%。根因不是硬件（PCIe 代替 NVLink 使 100MB 同步从 0.17ms 变 3.1ms 只是放大因素），而是 FIFO 批处理队头阻塞：长序列堵住短请求。修复：按预期输出长度分类请求、差异化批上限（短 8/中 16/长 32）、短请求在 P99 逼近 SLO 时可抢占长序列；改后 P99 185ms。教训：高平均利用率可以掩盖只影响 5% 请求却决定 P99 的队头阻塞。

## KV 缓存与内存管理

### KV 缓存墙

KV 缓存是每请求的注意力键值缓存，把逐 token 注意力从 O(n²) 降到 O(n)，但占用随上下文长度和批量线性增长，长上下文下常超过权重本身。每 token 字节 `M_KV = 2 × N_L × H_KV × d_head × s_elem`：Llama-3-70B（80 层、GQA 8 KV 头、d_head=128、FP16）约 0.33 MB/token，128K 上下文单请求约 42.9 GB；8×H100 节点（640 GB，扣除权重 141 GB 与系统 20 GB）最多约 11 个 128K 并发请求。**量化了权重的 70B 在长上下文下依然可能容量受限——KV 缓存把"减少模型内存"和"减少服务内存"区分开。**

### 碎片与 PagedAttention

按最大长度预分配造成内部碎片（最大 4096/实际平均 100 → 97.5% 浪费）与外部碎片（空闲总量够但无连续大块，新请求被拒），生产系统碎片浪费 60-80%。PagedAttention（vLLM，Kwon 2023）把虚拟内存思想搬进 KV 缓存：固定大小块（默认 16 token/页）+ 块表把逻辑位置映射到非连续物理页，按需分配、完成即回收。收益：缓存池利用率从连续分配的 30-40% 升到近 100%，同硬件 2.5-4 倍吞吐——注意它是**容量优化**，不加速单 token 数学，只靠装下更多并发请求起作用。

### Prefix Caching

系统提示、few-shot 示例、共享文档等公共前缀的 KV 页可跨请求共享（copy-on-write）。实例：2000-token 系统提示 + 1000 并发用户，无共享 6.6 TB → 共享后 1.3 TB（省 79.9%），可支撑 5 倍并发。命中率决定收益：固定系统提示的聊天 95%+（省 70-80%）、文档 QA 80-90%、通用 API 仅 20-40%。

### KV 压缩、GQA 与精度红利

KV 量化：K/V 存 INT8/FP8/INT4（KIVI：键有通道级离群值故按通道量化，值按 token 量化）；70B @ 4K 上下文从 10.7 GB（MHA FP16）降到约 2.7 GB（INT4）。GQA 把 KV 头从 64 减到 8，缓存缩 8 倍（10.7 → 1.3 GB），与 INT8 叠加可达每请求亚 GB。精度红利（napkin math）：4×H100 服务 70B，全 FP16（权重 35 GB/卡、KV 2.7 GB/卡/请求）最大批 16；换 INT4 权重（8.75 GB/卡）+ INT8 KV（1.3 GB/卡/请求）最大批 53——精度工程通过扩大批量改变服务经济学。

### 内存层次、换页与分布式 KV

`KV 池 = 0.9 × (总内存 − 权重 − 激活 − 开销)`，满载时按 LRU/尺寸/优先级驱逐，高优先级请求可触发受害者换出。三层层次：GPU HBM（80 GB，0ms）→ CPU DRAM（1 TB，1-5ms）→ NVMe（10 TB，10-50ms）；GPU+CPU 换页实测把并发从 50 提到 500（10 倍，平均换页 3ms）——是非性能关键流量的吞吐杠杆，不能替代延迟关键路径上的 HBM。分布式下 KV 按注意力头分片（8 路 TP 每卡存 1/8）；会话迁移时重建（长上下文 500ms+）vs 传输（1.3 GB @ 100Gbps 约 100ms），决策阈值 `cache_size/bandwidth < prefill_time 则传输`——带宽够时传输通常更优。

## 解码时优化：投机解码与分解服务

### 投机解码作为服务策略

小草稿模型一次提 K 个 token，目标模型一次并行前向验证，拒绝采样保证输出分布与目标完全一致（无损）；每轮期望产出 `(1−α^(K+1))/(1−α)` token。K=5、草稿快 20 倍时：α=0.9 → 4.69 token/轮、3.7 倍加速；α=0.7 → 2.4 倍；α=0.5 → 1.6 倍。**接受率是工作负载属性**：可预测文本 >0.9，创作/代码可能 <0.5，配套好的模型对常见 0.6-0.8。服务视角三约束：① 投机税——草稿模型占权重内存（7B 草稿约 14 GB/副本）加每请求草稿缓存，挤占 KV 准入预算、压低并发上限；② SLA 取向——延迟 bound 端点（交互聊天）受益，吞吐 bound 端点（批量摘要）受损；③ 动态开关——高负载时 decode 逼近计算受限、投机收益缩水而内存税不变，须按实测负载与接受率运行时开关。变体：self-speculative（早退出做草稿，省内存但接受率低）、Medusa（目标模型加轻量预测头）、Lookahead（Jacobi 迭代免草稿模型）。

### 分解服务与 Chunked Prefill

Prefill（计算受限、O(n²) 注意力、高算术强度）与 decode（带宽受限、1-10 FLOP/字节）硬件诉求相反，混批要么浪费算力要么浪费带宽。两层次解法：① **Chunked prefill**（Sarathi-Serve）——把长提示切成与解码迭代时间匹配的块（如 20ms 调度量子、10000 prefill tokens/s → 每块约 200 token），块与解码步交错，把长 prompt 从"整段阻塞"变为有界；实测 128K prompt 下静态批与纯连续批 TTFT 都是 30s 且 decode 被阻塞，连续+chunked 利用率 85% 且 decode 停顿有界（约 3s）。② **Prefill-Decode 分解**——prefill 池用高 FLOP/s 节点、decode 池用大 HBM/带宽节点，KV 经 RDMA/InfiniBand 迁移（<10ms SLO），两池独立扩展（prefill 随输入量、decode 随输出量）；注意低利用率 decode 流量仍是能耗大户。

### Adapter 局部性

多租户 LoRA 引入第二类驻留状态：KV 缓存是每 token 注意力状态，LoRA 是每租户权重增量，两者都必须在解码步执行那一刻就位。基础模型常驻 HBM、adapter 按需调入片上——若换入延迟超过单步计算时间，GPU 停顿，类似操作系统上下文切换；因此要按活跃 adapter 攒批，并让 adapter 放置与 KV 分页协同。

## 模型分片

内存公式 `Memory = P × b/8` 字节：70B FP16 = 140 GB > 单卡 80 GB → 至少 2 路。分片延迟收益 `T = T_compute/N + T_comm(N) + T_sync(N) − T_overlap`，只有非重叠开销小于并行节省时才有收益。

- **张量并行（TP）**：注意力按头分片、FFN 列-行切分，每 transformer 层 2 次 AllReduce：`T = T_compute/t + 2×T_allreduce`。Llama-70B 8 路 TP（8×H100 NVLink）每层 30ms → 4.35ms（6.9 倍，通信税约 0.6ms/层），1024-token prefill TTFT 约 400ms。**TP 用通信买延迟，只在互连扛得住集体通信时成立。**
- **流水线并行（PP）**：按层切阶段，层内无同步只需点对点传递；单请求零延迟收益（须顺序走完全部阶段），多请求填满流水线后吞吐 ×p。适合内存受限但延迟宽松、只有点对点带宽的场景。
- **专家并行（EP/MoE）**：经济悖论——总参数定硬件（内存），激活参数定每 token 算力。DeepSeek-V3（671B 总/37B 激活）解码每步只读约 74 GB（FP16），vs 等效稠密 400B 的 800 GB（省 10.8 倍），但全部权重必须驻留（FP16 约 1342 GB）。容量实例：FP8 权重 671 GB → 2 个 8-GPU 节点；每步 37 GB 分摊 16 卡各约 2.3 GB，读约 0.69ms + AllToAll 约 0.3ms → 约 1ms/token（batch=1 约 1000 tokens/s）。通信是 AllToAll（不同数据到不同设备）而非 AllReduce。负载均衡三机制：辅助损失、容量因子（约 1.25× 公平份额，超限丢弃/重路由）、专家缓冲。失败模式：专家坍缩（训练期）、路由不稳定、分布偏移热点（口语数据打爆"语法专家"）、token 丢弃靠残差兜底而质量降。Mixtral-8x7B（46.7B 总/12.9B 激活）每 MoE 层约 1.5ms（等效稠密约 4ms）；路由失衡 20% → 利用率降 17%，50% → 降 33%。
- **嵌入分片（推荐）**：行分片（按实体 ID 哈希，单设备存完整向量 + AllToAll 收集，适合均匀访问）、列分片（向量切到所有设备 + AllGather，适合热点）、混合（热 top 1% 全复制、温 10% 列分片、冷 89% 行分片+SSD）。Meta 规模：100+ TB、10+ 万亿实体、1000+ 分片，每请求约 5000 次查找经攒批+去重+分片感知分发，往返 5000 次 → 1 次、延迟 50ms → 2ms。注意生产系统靠压缩/分层/冷存储实现，不是单张全量稠密大表；**DLRM 服务由稀疏嵌入放置与查找协调主导，与稠密 FLOP/s 关系不大**。
- **混合分片**：TP+PP（8 卡 = 2 stage × 4 路 TP：4 倍延迟改善 + 扛 8 路内存分片）；EP+TP（每专家再切 2 卡，Mixtral 共 16 卡）；嵌入（CPU 1000 分片）+稠密（GPU 8 路 TP）。

### 通信开销与互连

`AllReduce ≈ 2(N−1)α + 2(N−1)/N × M/β`；`P2P = α + n/β`；`AllToAll = (N−1)(α + M/(N·β))`。

| 互连 | 带宽 | 延迟 | 用途 |
|---|---|---|---|
| NVLink | 900 GB/s | 500 ns | 节点内 TP（H100；Blackwell 达 1.8 TB/s） |
| PCIe Gen5 | 64 GB/s | 1 μs | 无 NVLink 节点内 |
| InfiniBand HDR | 25 GB/s | 7 μs | 跨节点 |
| 100G Ethernet | 12.5 GB/s | 50 μs | 跨节点（商品化） |

8MB 激活 AllReduce 占 30ms 层预算：NVLink 0.03ms（0.1%）、IB 0.56ms（1.9%）、100GE 1.12ms（3.7%）。工程边界：NVLink 让节点内 TP 高效，IB 让精选负载的跨节点 TP 可接受，商品以太网对延迟敏感推理通常太慢。

## 负载均衡与请求路由

- **两选择幂（Power-of-Two-Choices）**：随机放置最大队列 O(logR/loglogR)（1000 台约 4-5 个），采样两台取低者降为 O(loglogR)（约 2 个）——概率从 m/R 变 (m/R)²，超指数衰减；两探针+一次状态更新即 O(1) 协调，P99 约减半。负载信号要匹配负载：LLM 用活跃 token/预计解码工作量/KV 占用，而非请求计数（否则 10-token 请求藏在一个 500-token 请求后面）。
- **加权与自适应**：异构集群按容量加权（10×H100@1000QPS + 20×A100@600QPS 承 15000 QPS：加权后两类都跑 68% 利用率；均分则 A100 83% 而 H100 闲置 50%）；自适应用逆延迟加权 `weight = 1/EMA(latency)`。
- **最少连接**：LLM 请求时长差 50 倍（500ms vs 25s），按在处理工作路由远优于轮询；实测（高方差 LLM 负载）轮询 P99 45s → 最少连接 28s（-38%）→ 两选择+最少连接 26s。
- **一致性哈希**：会话亲和保 KV 复用（无亲和时每轮重建缓存 500ms，10 轮对话浪费 4.5 秒）；虚拟节点（每物理机 100 个）保均衡，节点增删只重映射 K/N 的键。
- **分级健康检查**：liveness（进程活着，10s）/ readiness（模型已载、显存可分配、预热完成，5s）/ deep health（真实跑测试请求、校验输出无 NaN/Inf、logit 熵合理，30s）。**深度检查是唯一能抓到"静默硬件退化"的手段**——降级 HBM 的 GPU 会通过所有进程探针同时输出垃圾。
- **断路器与背压**：慢副本（温控降频 50ms→500ms）继续接流会因重试风暴拖垮全局。三态断路器（closed → 错误率>50% 或 2× 基线延迟时 open 30s → half-open 放 5 个探针）把爆炸半径约束在单副本。LLM 舰队 KV 压力的三个专用泄压阀：驱逐旧对话上下文、关投机解码回收草稿内存、路由到更小的量化 fallback 模型。
- **战例**：2023-03-20 ChatGPT 因 redis-py 异步连接复用 bug 出现跨用户缓存泄漏（可见他人对话标题），停服修复。教训：有状态推理基础设施中缓存是正确性边界的一部分，不只是优化。

## 多租户与隔离

共享提利用率（30-50% → 70-90%）但引入吵闹邻居：一个租户长上下文突发可把 60 GB KV 池吃到 45 GB，其他租户并发从 200 掉到 75（-62%）；无配额全员 SLO 违约，配额后只有突发者被限流。工具箱：

- **资源配额**：准入时检查并发数/KV 内存/QPS/批 token 上限，"先拒绝，不干扰"；软配额+公平共享（低载可突发 2 倍，90% 饱和时强制）。公平分配单位用 token 生成速率而非请求数（等量请求≠等量负载）；max-min fairness 例：30K/20K/80K 需求抢 100K 池 → 分得 30K/20K/50K。
- **优先级调度**：critical（营收相关，100% 预留，可抢占一切）/ standard（加权份额，可抢 best-effort）/ best-effort（剩余容量，无保证）；抢占用 KV 换出+断点续跑，不丢已生成 token。
- **舱壁（Bulkhead）**：部署级（金级租户独占副本池，完全隔离）+ 请求级（输入 ≤8000 token、输出 ≤2000 token、执行 ≤30s 硬帽）。分层 API 典型：企业级独占池 99.9% SLO / 专业级共享池 70% 配额可抢免费级 / 免费级 30% 尽力而为 10 QPS 限速。
- **模型隔离**：显存分区（80GB 分 40+30+10 共享池）；MIG 硬件分区（单卡切最多 7 个隔离实例，避免时间片 2-5 倍延迟方差）；模型加载 fail-closed——内存不足只驱逐更低优先级且可驱逐的模型，否则拒绝加载而非破坏隔离。
- **可观测性**：每租户的请求量/延迟分布、GPU/KV 占用、限流与抢占事件、错误分类；告警阈值：P99 超目标 10% 持续 5 分钟、配额用到 90%、租户吃 2 倍公平份额持续 5 分钟；计费归因（GPU 秒、KV GB-小时、出网）到租户。

## 自动扩展与全球基础设施

### 冷启动是主要约束

`T_cold = T_provision + T_load + T_warmup`：GPU 实例供给 30s-数分钟；权重加载取决于存储层（本地 SSD 约 6 GB/s vs S3 约 0.5 GB/s：175B 模型 1 分钟 vs 12 分钟）；预热需 10-30 次哑推理跑 JIT 编译/CUDA 上下文/内存池。Llama-70B 全时间线约 7 分钟（实例 60s + 容器 10s + S3 下载 300s + 装载 25s + 预热 15s 等）。**GPU 推理冷启动比无服务器函数慢 100 倍，纯响应式扩展不可能应对突发。**三种旋钮：水平加副本（延迟不变、线性成本、分钟级）、批量大小（延迟换吞吐、即时，突发时先拧它买时间）、垂直换卡（极慢需重部署）。实例：1000→3000 QPS 无预热时 10 副本跑到 210% 利用率、P99 500ms+；有 20 个热备则 0 秒到位、70% 利用率、P99 80ms——热备把冷启动延迟换成空闲容量成本。

### 预测式扩展与热池

时间序列预测（日/周季节性+趋势）+ 事件驱动排程（发布前 30 分钟 ramp up）+ 响应式兜底：`Target = max(Predicted, Reactive) + Buffer`。LLM 特有：必须预测请求类型组合——长上下文摘要对 KV 的消耗远超同数量短对话。预测式按真实峰值配机（30 副本 vs 响应式需约 45），省约 33% GPU 开销。分层热池：hot（模型已载，即时，100% 成本）/ warm（GPU 已分配，30s 激活，60%）/ cold（0 成本，5 分钟+），典型 2 hot + 5 warm + 无限 cold。Spot 实例（60-90% 折扣，30s-2 分钟终止通知）承载 best-effort 流量，终止时停收新请求 → 90s 排空在途 → 保存 KV 状态 → 注销 LB；70% on-demand + 30% spot 混合约省 18-27%。

### 多区域

单区域三重限制：RTT 地板（伦敦 75ms/东京 150ms/悉尼 200ms vs 本地 10ms，多模型调用复利放大）、区域级单点故障、数据驻留合规。三模式：① **区域副本+全球负载均衡**（默认）——各区域完整部署，anycast/按 RTT 路由，模型注册中心同步权重（推/拉/混合），版本锁定滚动发布，区域故障切次近健康区域；② **边缘缓存+中心推理**——命中 <10ms，命中率取决于请求重复性：自动补全 60-80%（优秀）、FAQ 40-60%、代码生成 20-40%、开放聊天 5-15%（几乎无收益），语义缓存（嵌入相似度）可提 2-3 倍命中率，代价是每次 1-5ms 向量查询和查准/查全权衡；③ **跨区域模型分片**（最后手段）——跨区 RTT 75-150ms vs 每阶段算力 1-5ms，慢 10-100 倍，仅当无单一区域装得下完整模型才考虑。成本路由：区域差价约 20% 远小于延迟差，只把延迟不敏感的批处理发往最便宜区域（时段路由省 20-40%）。

## 服务权重量化

量化是**瓶颈选择决策**：FP16 70B（140 GB 需 2 卡）→ INT4（35 GB 单卡候选），内存与带宽需求降 4 倍。方法按所解绑的瓶颈选择：

| 绑定约束 | 方法族 | 要点与风险 |
|---|---|---|
| 装不下 | GPTQ、AWQ（W4A16） | 校准集失配与质量回退 |
| 解码带宽受限 | W4A16 减每 token 字节 | 内核支持与 KV 余量 |
| Prefill 算力受限 | SmoothQuant W8A8 | 激活离群值与硬件路径 |
| 离群值挡住低精度 | QuaRot/SpinQuant 旋转法 | 变换开销与运行时支持 |

- **LLM 特有困难——激活离群值**：少数通道产生比典型值大数量级的激活，对称 INT8 无两全 scale（区间宽则常规值坍缩、窄则截断离群值）。
- **GPTQ**：逐层逐列量化，用校准激活（128-256 条，须匹配生产流量）估计二阶敏感度（Hessian），舍入残差补偿到未量化列。Llama 4-bit 困惑度增幅：7B +0.3（15 分钟）、13B +0.2、70B +0.15（3 小时）——**越大越耐量化**。
- **AWQ**：校准测每通道激活幅度，放大喂给高幅通道的权重再量化（尺度折进下一层）。比 GPTQ 校准更轻（约 128 条、无需参考输出）、4-bit 质量更好（约低 0.5-1% 困惑度损失），风险是缩放必须融进部署图否则多一个 kernel 吃掉收益。
- **SmoothQuant**：激活除以每通道尺度、权重乘同一尺度（代数等价），把难量化的动态范围从激活迁到宽容的权重，W8A8 跑标准 INT8 路径近零开销。W8A8 vs W8A16：prefill 加速 1.8-2 倍 vs 1.3 倍，decode 仅 1.3-1.5 倍 vs 1.8 倍——decode 主导的 LLM 实际吞吐收益常为 1.3-1.7 倍而非理论 2 倍。
- **QuaRot**：离群值是坐标基伪影；Hadamard 正交旋转把极端值摊匀（[1000,1,1,1] → 约 [502,500,500,500]），正交性保证层输出不变、免校准，可达 W4A4，代价是每次前向内联旋转约 3% 开销。LLaMA-2-70B 困惑度：FP16 3.12 / SmoothQuant W8A8 3.18 / GPTQ W4A16 3.24 / QuaRot W4A4 3.31。SpinQuant 用短微调学最优旋转矩阵再提质量。
- **硬件协同设计**：A100/H100 张量核心原生支持 FP16/BF16（1×）、INT8（2×）、FP8（Hopper 2×）；INT4 靠软件/CUTLASS，原生 FP4 是 Blackwell 特性。解码吞吐 ∝ 带宽/模型字节数，实际收益取决于内核支持、反量化开销、KV 精度与批形状，须在目标负载验证。
- **运行时契约**（缺一不可）：加载量化产物不静默反量化；选到支持低精度路径的 kernel（否则回退高精度）；围绕缩小后的权重重规划 KV 预算（让省出的内存变成批量余量）；质量与延迟一起验证。成本：FP16 @ 8×A100 约 $2.40/百万 token → AWQ 4-bit @ 4× $1.20 → @ 2× $0.60，节省几乎全部来自省卡而非单卡吞吐。

## 案例研究

| 系统 | 绑定约束 | 核心技术 | 关键创新 |
|---|---|---|---|
| Meta 推荐服务 | 嵌入规模（100+ TB，<10ms P99） | 混合嵌入分片 + CPU/SSD 稀疏查找（2ms）+ GPU 稠密排序（1.5ms） | 特征级并行批处理，查找 50ms→2ms |
| OpenAI 风格 API | 请求方差（TTFT <2s，128K 上下文） | 连续批处理 + chunked prefill + 多级限流（key 速率/token/组织/全局）+ 会话一致性哈希 | 长提示不阻塞所有人的解码 |
| Google 搜索排序 | 级联成本（<200ms，数十模型/查询） | 排序级联 L0 检索（百万→万）→ L1 线性 → L2 小网络 → L3 大集成（100→10），各阶段带 deadline 的投机并行执行 | 昂贵模型只看缩到万倍的候选集，模型工作量约省 5600 倍 |
| TikTok 多模态推荐 | 新鲜度（<50ms P99，日百万新视频） | 双塔：视频塔离线小时级预计算缓存、用户塔在线实时（5ms）；多模态后期融合；摄入分级 SLA（大 V 5 分钟/常规 30 分钟/批量 2 小时） | 把视觉推理从关键路径摘除 |

共性模式：专业化而非通用服务栈——嵌入/检索与排序/生成分离、CPU-GPU 混合匹配负载、多层缓存并接受陈旧性、候选集渐进精化、deadline 传播让质量/延迟权衡显式化。

## 经验与常见坑（谬误与陷阱）

1. **谬误：大规模推理 = LLM 服务**——推荐系统常占消费平台推理量大头，只懂连续批处理和 KV 管理做不好特征并行与嵌入分片。
2. **陷阱：用训练基础设施做生产服务**——训练要吞吐不要延迟、千级批量、检查点恢复；服务要 P99、个位数批量、无感故障切换。
3. **谬误：连续批处理解决一切**——长上下文 prefill 瓶颈、KV 内存上限、分片间网络都可能主导；必要非充分。
4. **陷阱：按平均吞吐配容量**——80% 平均利用率遇 25% 尖峰即过 100%，队列无限增长；按峰值+余量规划。
5. **谬误：负载均衡无关紧要**——两选择幂是指数级改善（最大队列 4-5 → 2），在 P99 尺度是第一性差异。
6. **陷阱：忽略服务税**——单机 70ms 的模型上线端到端 100ms，差的 30% 是网络/序列化/协调。
7. **谬误：显存越大吞吐越高**——LLM 解码绑定约束是带宽不是容量，HBM 带宽饱和后加显存不涨 token/s。
8. **陷阱：上线后才发现没做隔离**——配额、优先级、舱壁必须从第一天设计进去，不能等生产事故后补救。
