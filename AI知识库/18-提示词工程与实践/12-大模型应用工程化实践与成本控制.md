# 大模型应用工程化：RAG 模式、微调选型、成本控制与安全

/> 来源：公开课程资料自学整理（整理于 2026-11-03）
> 一句话概括：应用开发四大工程板块的耐用模式——RAG 设计模式、PEFT/LoRA 微调选型、Function Calling、以及错误处理/成本/安全的工程化清单。

## 核心概念

- **RAG**：检索增强生成，把外部知识放进上下文再回答，解决知识时效与幻觉。
- **PEFT**：参数高效微调，只训练极小部分新增参数，缓解灾难性遗忘。
- **Function Calling**：模型只输出"调用意图 JSON"，函数实现与执行永远在开发者侧。
- **托管型 Agent 运行时**（以 Assistants 类产品为原型）：平台托管对话状态、工具执行沙箱、运行生命周期。

## 关键方法/模式

### RAG 设计模式
- **托管式 RAG**：喂文件即得，平台自动分块/索引/检索。适合 MVP 与原型；代价是分块策略不可控。引用脚注（citation）机制能显著提升可信度，自建 RAG 值得模仿。
- **读图 PDF RAG**：纯文本提取会丢图表。模式 = **视觉内容文本化 + 图文配对重建 chunk**：整页转图 → 多模态模型逐页生成结构化描述 → 按标题匹配图文配对成 chunk → 向量检索。回答提示词写明"先判检索相关性，不相关则用自身知识或承认不知道"，防噪声污染。
- **Embedding 推荐**：把特征工程换成"LLM 生成受控关键词（限定维度、只提取明确提及的，防幻觉标签）→ 拼接 embedding → 余弦 top-k"。天然缓解冷启动（只需内容不需行为数据），可解释但个性化弱。查询与文档必须同模型同向量空间。
- **长文档总结评估三板斧**：①找权威摘要当 ground truth；②ROUGE/BERTScore——**坑：字面指标奖励照抄、惩罚高质量改写**，结论可能反直觉；③LLM-as-judge 多维打分才与人类一致，且换模型交叉评避免自评偏置。三层组合使用，单层结论可能错。

### PEFT 微调选型（三层）
| 层次 | 代表方法 | 特点 |
|---|---|---|
| 基于提示 | Prompt / Prefix / P-Tuning | 不动原参数，最防遗忘 |
| 低秩分解 | LoRA 系（新增参数占原模型 0.1%~3%） | 默认解：可挂多适配器共享基座、可组合、效果近全参 |
| 其他 | Adapter 插模块 / BitFit 只调 bias / IA3 | 特定场景 |

- LoRA 原理：冻结权重，旁挂低秩增量矩阵，训练参数量从 d² 降到 2dr 量级。
- QLoRA = 4bit 量化加载基座 + 高精度 LoRA 增量，解决"基座装不进显存"。
- 微调决策序：**知识缺口先 RAG → 行为/格式问题先调提示词 → 都到顶才微调**（目标是稳定风格/格式/函数调用）。微调无法可靠注入实时知识。
- 坑：微调前必测基线否则无法归因；产物只有十几 MB 是正常的；数据质量 > 数量（几十到百条级别即可起步）；冷启动技巧 = 强模型生成弱模型的微调数据（需清洗客套废料）。

### Function Calling 模式
- 函数元数据（JSON Schema）与实现分离；参数带 description 与枚举示例，描述含糊则模型选择"随缘"。
- 确定性/涉钱逻辑放本地函数，模型只做意图解析。
- **为什么要微调 FC**（提示词做不到的三件事）：①函数多/任务复杂时调用准确率下降，微调把函数知识焊进权重；②省去每次携带全量函数定义的 token；③防幻觉出无效 JSON，定义不全也稳定输出合规结构。

### 托管型 Agent 运行时模式
- 四对象模型：Assistant（配置+工具）/ Thread（会话，与 Assistant 多对多解耦可路由多专家）/ Run（一次执行，状态机：排队→执行中→完成/等待本地函数回传/失败/取消/过期）/ Message。
- 典型坑：轮询须先判状态再取动作；Run 有生命周期会过期，过期须新建重放；"代码能跑 ≠ 逻辑正确"，结果须抽样校验；模型会偷懒（复杂任务口头承诺不真做，要拆成独立消息驱动）。
- 多步自主任务套路（自动出商业报告六步）：数据探索（报错自愈）→ 约束字数出洞察 → **由洞察派生标题（标题=结论）** → 配图 → 模板组装 → 下载。跨步复用同一会话让上下文自动串联。

### 错误处理与可观测
- 错误分类对策：4xx 查请求参数、401 查密钥、429 降频退避、5xx 查服务状态页、超时重试。
- try/except 只是体面失败，根因常在请求构造——异常处理不替代修复。
- **Tracing 必记字段**：每次调用的输入输出、模型名、token 数、花费、延迟；批量任务逐条记，出错可定位到单条。

### 成本控制清单
- 输出 token 单价更高 → 压输出比压输入更省；用 tokenizer 预估成本。
- 长对话定期总结压缩历史；相似查询做缓存；分段生成逐段校验。
- **模型级联**：便宜模型做粗活（抽取、分类），贵模型做精炼/审核/复杂推理，还可用贵模型当裁判建质量基准。
- 限流：RPM/TPM 多维同时生效；指数退避（带随机化）；读响应头剩余额度主动调度；非实时任务走批处理通道；小任务合并请求。

### 内容安全（Moderation）
- **双端审核**：输入、输出都过审。工程技巧：审核与生成并发跑，审核先出且违规则取消生成（关键路径短路）。
- 开源模型对齐不完善必须外挂审核；完整体系还包括数据清洗、人工复核、红队测试。

## 术语表

| 术语 | 含义 |
|---|---|
| RAG | 检索增强生成：先检索外部知识再放入上下文回答 |
| Chunk | 文档切分后的检索单元 |
| Embedding | 文本的向量表示，用于语义相似度计算 |
| PEFT | 参数高效微调技术总称 |
| LoRA | 低秩分解微调：冻结原权重、旁挂低秩增量 |
| QLoRA | 量化基座 + LoRA 增量的省显存组合 |
| Function Calling | 模型输出结构化调用意图、开发者侧执行的模式 |
| Thread / Run | 托管运行时中的会话对象 / 一次执行对象 |
| Moderation | 输入输出内容安全审核 |
| LLM-as-judge | 用更强模型按多维标准给输出打分 |
| BERTScore | 基于语义向量的文本相似度指标 |

## 经验与常见坑

- 字面评估指标（ROUGE 类）会系统性低估改写型好答案，别单看它下结论。
- 弱模型没有 RAG 时会幻觉编造；接了 RAG 也要防检索噪声污染回答。
- 微调最大的浪费是"用微调补知识"——知识问题永远先 RAG。
- 托管运行时省事但是黑盒，出问题难排查；自研运行时相反。
