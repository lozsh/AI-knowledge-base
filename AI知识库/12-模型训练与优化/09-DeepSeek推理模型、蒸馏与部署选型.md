# DeepSeek 推理模型特性、蒸馏方法与部署选型

<p class="note-date">更新于 2026-11-03</p>
**一句话定义**：推理模型与对话模型要分工使用；蒸馏教的是能力而非知识；部署从单卡到集群有一条清晰的决策链。

## 核心概念

- **对话模型 vs 推理模型**（以 DeepSeek V3 / R1 为例）：V3 类 = 聊天、翻译、常规代码；R1 = 同基座经强化学习训练出的推理模型，输出含思维链。API 中推理内容与最终答案分字段返回，程序要分开处理。
- **分工铁律**：R1 慢且（早期版本）工具调用弱、与 Agent 编排有冲突——**单点深度任务用 R1，Agent 调度层用 V3 类"听话"模型**；简单查询用对话模型即可。
- **蒸馏版** = 把 R1 的推理能力灌进小底座（如 Qwen 系）；底座素质越高，蒸馏效果越好。

## 核心原理

### 蒸馏：教能力，不教知识
- 与普通微调的唯一差别 = **教学数据带思考过程**（think + 答案）。
- 流程：原始输入数据 → 用 prompt 喂给满血教师模型生成"思考+答案"教学数据 → 对小模型做 SFT。
- 核心 in prompt 设计（占工作量 50-70%）：任务说明 + 输出格式 + 逼真示例；示例须符合教师模型口吻。

### 微调三法与分类器流程
- 三法选型：全参微调（耗资源）/ 冻结微调（简单分类任务）/ LoRA（低秩增量，默认选择）；QLoRA = 先量化再 LoRA。
- 训练分类器的模式：对话格式数据（输入加任务前缀，输出保留思维链 + 标签）→ 数百条量级即可教会 7B 级模型。
- 评估三件套：测试集离线推理对比预设答案 + 人工抽检 + **训前先测原模型基线**（否则无法归因）。
- 坑：本地大模型文件下载常不完整；WebUI 找不到模型多半是挂载路径没对上容器内缓存路径；超参没有统一参考值，必须实验。

### 部署策略决策链
显存估算：参数量 × 精度字节数（如 7B FP16 ≈ 14GB），量化近似线性压缩。

| 情形 | 方案 |
|---|---|
| 单卡装得下 | 直跑 |
| 单机多卡 | 张量并行 TP（吃卡间带宽，TP 不能跨节点） |
| 单机不够 | 多节点 TP + 流水线并行 PP（需高速互联网络） |
| 无 GPU | CPU 量化推理（GGUF 格式，内存换显存）——但"能跑"≠可用，**必须实测 tokens/s** |

工具选型：
- Ollama = 易用性封装（量化损精度），适合个人体验，生产几乎不用。
- 生产推理引擎用 vLLM 一类高吞吐方案（与 CUDA 版本强耦合 → 用官方 Docker 镜像最稳）。
- K8s 解决生产四大问题：单点故障、弹性伸缩、GPU 调度、服务发现；百 G 级模型文件放对象存储用 PV/PVC 挂载，不塞镜像。
- **AI 网关**（Higress/Kong 类）：多后端分流、故障转移、限流防打爆、API Key 二次分租（每用户独立 Key 控额度）、token 用量观测。注意：多实例负载均衡不解决会话上下文共享问题。

### RAG 进阶
- **数据清洗是第一生产力**：按业务重组文档再入库（如题干与答案合并成一个块），优先 Markdown；切片目标是"一个语义单元一个 chunk"，分段不理想先改源文档格式，而不是硬调参数。
- 检索方式三选：向量 / 全文 / 混合 + 重排序，配相似度阈值过滤。
- **Agentic RAG 五段式**（对抗检索四大失效）：query 改写（拆多角度）→ 意图判断（能直接答就不检索）→ 路由（联网/查库/工具）→ 执行 → 校验（不解决问题循环重来）。代价：费 token、慢。
- **GraphRAG**：向量 RAG 只会相似度、无法沿关系扩展（搜不到别名、拿不到关联结构）。GraphRAG = LLM 抽取（实体，关系，实体）三元组建图 + 图遍历多跳检索。代码场景关键预处理：先用 LLM 把每个文件抽成结构化描述（签名/引用/功能）再建图，避免直接切片拆散函数。

## 术语表

| 术语 | 含义 |
|---|---|
| 推理模型 | 经强化学习训练、输出含思维链的模型（如 R1） |
| 蒸馏 | 用教师模型的"思考+答案"数据教小模型学会能力 |
| SFT | 监督微调 |
| LoRA / QLoRA | 低秩增量微调 / 量化基座 + LoRA |
| TP / PP | 张量并行 / 流水线并行 |
| GGUF | CPU 量化推理常用模型格式 |
| vLLM | 高吞吐生产级推理引擎 |
| AI 网关 | 多模型后端的统一入口：分流/限流/计量/鉴权 |
| GraphRAG | 知识图谱 + 多跳检索的 RAG 变体 |
| Agentic RAG | 用 Agent 循环（改写/路由/校验）增强的 RAG |

## 经验与常见坑

- 推理模型不适合直接当 Agent 的调度大脑：慢、贵、与多轮工具调用编排冲突。
- CPU 量化部署"能跑"与"可用"之间差一个吞吐实测。
- K8s 编排训练/推理集群时，Head 节点占位导致 Worker 数 = GPU 节点数 − 1；容器内访问宿主机不能用 localhost，要用网桥 IP。
- Docker 里用 GPU 需要装容器运行时工具包，报"找不到 GPU"先查这个。

## ⚠️ 时效性说明

DeepSeek V3/R1 版本划分、SSE→Streamable HTTP 的传输层演进、各引擎与 CUDA 版本耦合关系随时间变化；推理/对话分工、蒸馏方法论、部署决策链为耐用结论。
