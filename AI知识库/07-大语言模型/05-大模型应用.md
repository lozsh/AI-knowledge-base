# 大模型应用

<p class="note-date">更新于 2026-11-03</p>

**一句话定义**：围绕大模型的三大应用支柱——评测（如何量化模型好坏）、RAG（检索增强生成）、Agent（智能体）——的概念框架与动手实现。

大模型要落地，先要能**测**（评测数据集与榜单给出选型依据），再要能**接外部知识**（RAG 缓解幻觉与知识过时），最终要能**自主办事**（Agent 具备规划、记忆、工具使用能力）。本文按"评测 → RAG → Agent"递进，每部分附一个可运行的最小实现（Tiny-RAG、Tiny-Agent）。

## 评测体系

### 评测数据集分类

| 类别 | 代表评测集 | 考察点 |
|---|---|---|
| 通用 | MMLU | 历史/数学/物理/生物/法律等多学科知识理解 |
| 工具使用 | BFCL V2、Nexus | 多步骤工具调用的正确性与任务协调管理 |
| 数学 | GSM8K、MATH | 小学数学推理；代数几何等更复杂数学 |
| 推理 | ARC Challenge、GPQA、HellaSwag | 科学推理；零样本开放问答；复杂语境逻辑选择 |
| 长文本 | InfiniteBench/En.MC、NIH/Multi-needle | 长文档阅读理解与多样本总结 |
| 多语言 | MGSM | 多语言下的数学解题能力 |

### 主流榜单

- **Open LLM Leaderboard**（Hugging Face）：开源模型汇总评测，多标准化测试集、持续更新。
- **Lmsys Chatbot Arena**：真实用户盲测对比投票，考察对话生成、上下文理解与用户满意度。
- **OpenCompass**（司南，国内）：覆盖中文理解与多语言能力，侧重本土化准确性、鲁棒性。

评测的意义：大模型开发成本高，评测既判断模型适用性与可靠性，也暴露偏见、鲁棒性等弱点，还为行业提供统一比较标准。

## RAG：检索增强生成

### 为什么需要 RAG

LLM 三大痛点：**幻觉**（生成不准确/误导内容）、**知识过时**（训练数据有截止日期）、**领域知识浅**（垂直专业问题处理差）。RAG 的解法是生成前先从外部文档库检索相关片段，把检索结果作为上下文喂给模型——答案建立在真实文档之上，可追溯、可信、可及时更新。

### Tiny-RAG：五个模块

1. **向量化模块**：`BaseEmbeddings` 基类定义 `get_embedding` 与 `cosine_similarity`（点积/模长，零模长返回 0）；子类如 `OpenAIEmbedding` 只需实现 `get_embedding`，API 模型标记 `is_api=True`。
2. **文档加载与切分**：按扩展名分派 pdf/md/txt 读取函数；`get_chunk` 按行累切到 `max_token_len=600`，切下一块时带上前一块末尾 `cover_content=150` 字符作重叠，保证语义连贯、提高检索召回。
3. **向量数据库**：`VectorStore` 四个能力——`get_vector`（批量向量化文档）、`persist`/`load_vector`（持久化与本地加载）、`query`（问题向量化后与全库算余弦相似度，`argsorts` 取 Top-k 文档）。
4. **检索模块**：即 query 方法，k 可调，返回最相关片段。
5. **大模型模块**：`BaseModel` 基类（`chat` + `load_model`，本地模型才需 load_model）；子类如 `InternLMChat`（InternLM2-chat-7B）用 PROMPT_TEMPLATE 拼接问题与上下文，模板里明确指示"上下文无法回答就说数据库中没有这个内容"，进一步压制幻觉。

### Demo 流程

```python
docs = ReadFiles('./data').get_content(max_token_len=600, cover_content=150)
vector = VectorStore(docs); vector.get_vector(ZhipuEmbedding()); vector.persist('storage')
content = vector.query(question, embedding, k=1)[0]
print(InternLMChat(path).chat(question, [], content))
```

第二次使用直接 `load_vector('./storage')` 免去重复向量化。

## Agent：大模型智能体

### 定义与五大能力

LLM Agent 是以 LLM 为核心"大脑"，赋予**自主规划、记忆、工具使用**能力的系统，从被动响应 Prompt 变为主动完成任务：

1. **理解目标**：接收高层次目标（如"规划北京周末行并订机票酒店"）。
2. **自主规划**：拆解为可执行小步骤（搜景点→查天气→比价→调预订 API）。
3. **记忆**：短期（当前任务上下文）+ 长期（从历史交互或外部知识库检索）。
4. **工具使用**：调用外部 API/插件/代码环境来获取信息、执行操作、做计算。
5. **反思与迭代**：评估自身行为结果，调整后续计划（更高级的 Agent）。

类比：传统 LLM 是"知识渊博但只能纸上谈兵的图书馆员"，Agent 是"全能私人助理"。

### Agent 的四种类型

| 类型 | 特点 | 典型例子 |
|---|---|---|
| 任务导向型 | 特定领域、预设流程 + 固定工具集，理解意图/填槽/调用工具 | 订餐机器人、代码助手（GitHub Copilot） |
| 规划与推理型 | 分解复杂任务、多步计划、按环境反馈调整；常用 ReAct（先 Reason 后 Act 循环）、CoT | 整合搜索+计算器+数据库的研究型 Agent |
| 多 Agent 系统 | 多角色协作/辩论/竞争（规划者、执行者、审查者） | AutoGen、ChatDev 模拟软件团队 |
| 探索与学习型 | 在交互中主动学新技能、优化策略，含记忆与反思机制 | 未知软件环境自主操作、游戏策略进化 |

### Tiny-Agent 实现（基于 OpenAI tool_calls）

技术栈：`openai` 库指向兼容端点（如 SiliconFlow），模型 `Qwen/Qwen2.5-32B-Instruct`。三步：

1. **工具函数**：普通 Python 函数（获取当前时间、加法、比较大小、统计字符出现次数），必须有清晰的 docstring 和类型注解。
2. **Schema 转换**：`function_to_json` 用 `inspect` 把函数名、docstring、参数签名转成 OpenAI tool 的 JSON Schema。
3. **Agent 类**：维护 `self.messages`（含 system prompt），核心循环：

```
get_completion(prompt):
  messages.append(user 消息)
  响应 = chat.completions.create(model, messages, tools=schema)
  若响应含 tool_calls:
    对每个 tool_call：解析函数名+参数 → 执行 Python 函数 → 以 role=tool 消息附结果回 messages
    再次调用模型（带工具结果）得到最终回答
  返回最终回答
```

工作流程六步：用户输入 → 带工具 Schema 调模型 → 模型决定调用则解析并执行函数 → 结果返回模型 → 模型生成最终回复 → 返回用户。

### 实测效果与启示

示例交互中，模型把"9.12 和 9.2 哪个大""strawberry 里有几个 r"这类 LLM 易错的数值/字符计数问题自动转给 `compare`、`count_letter_in_string` 工具，答对后再由模型生成解释——**工具弥补了 LLM 的弱项，LLM 负责理解意图与组织语言**。这正体现了 Agent 的价值分工。
