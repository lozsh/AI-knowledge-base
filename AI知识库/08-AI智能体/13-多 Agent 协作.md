# 多 Agent 协作

<p class="note-date">更新于 2026-11-03</p>

**一句话定义**：多 Agent 协作是让多个具备独立身份（系统提示词 + 工具集）的 Agent 通过信息共享与控制流协调共同完成任务的技术体系；其两大核心设计维度是"上下文是否共享"与"协作拓扑"。

单 Agent 受限于模型能力边界和上下文窗口。多 Agent 的意义不止"取长补短"——群体智能可以高于个体（如人类文明经由分工与知识累积超越任何天才个体）；Google DeepMind《从 AGI 到 ASI》将"大规模多 Agent 集体"列为通往超级智能的关键路径之一。但在工程层面，多 Agent 也有真实成本：Anthropic 披露其多 Agent 研究系统 token 消耗约为普通对话 15 倍，token 用量本身解释了约 80% 的性能差异——收益必须大到覆盖数倍乃至一个数量级的额外开销，否则调校得当的单 Agent 更划算。

## 关键概念

### 维度一：上下文是否共享

| | 共享上下文（继承式） | 不共享上下文（隔离式） |
|---|---|---|
| 信息传递 | 后继 Agent 继承完整轨迹，隐式协调 | 显式机制：工具调用参数 / 共享文件系统 / 消息总线 |
| 优势 | 信息零损耗 | 模块化、可扩展、可大规模并行、错误不传染 |
| 代价 | 上下文快速膨胀 | 信息同步复杂、调试需拼多个日志 |
| 适用 | 少角色（2-3）、窗口装得下、信息零损耗是硬约束 | 角色多、需并行、需信息隔离（如安全审查） |

经验法则：预期累计上下文超过窗口 50% 就不共享；实践中常用"阶段切换式"——前几个 Agent 共享，到信息饱和点切换为不共享 + 显式 handoff（移交时主动决定传什么）。

### 维度二：协作拓扑（不共享上下文时三种形态，按复杂度递增）

1. **对等协作（Peer Collaboration）**：2-3 个平等 Agent 迭代互评，实现复杂度最低，适合快速验证原型。
2. **管理者模式（Orchestration）**：中心 Manager 负责规划、调度、跟踪异常、整合结果。
3. **去中心化模式（Decentralized）**：无运行时中心控制者，控制权在对等 Agent 间自主流转（handoff）。

两维度概念独立、实践相关：共享上下文时拓扑通常退化为角色切换序列；不共享时才需显式设计信息流与控制权。

### 多 Agent 何时真正优于单 Agent

核心判据只有一条：**协作是否引入了单 Agent 生成时无法获得的新信息**。

| 协作模式 | 引入新信息？ | 效果 |
|---|---|---|
| 同一模型自我审查 | 否 | 通常无效甚至有害 |
| 多 Agent 辩论同一段文本 | 否 | 等计算量下与单 Agent 持平 |
| Reviewer 用测试执行结果审代码 | 是（执行反馈） | 显著提升 |
| Reviewer 看渲染截图审前端 | 是（视觉反馈） | 显著提升（WebGen-Agent：26.4%→51.9%） |
| Reviewer 用外部工具验证事实 | 是（工具反馈） | 显著提升 |

证据：RLEF（RL 从执行反馈学习）远超独立多次采样；Huang 等 ICLR 2024——无外部反馈时 GPT-4 自我修正反而降准确率（把对的改错多于把错的改对）；TACL 2024 综述确认纯自我纠正几乎不起作用；CRITIC——移除工具验证后提升消失。Tran & Kiela 2026 用数据处理不等式解释辩论为何无效：多 Agent 处理相同文本，串行传递只可能丢信息不可能造信息；但该论证不否定独立采样聚合（self-consistency）与利用生成-验证难度不对称的分工。这解释了"学术说单 Agent 够用，工程上多 Agent 有效"的矛盾——两者研究的多 Agent 形态不同。

**步骤预算**：Google 2025 发现单纯增加步骤数不保证性能——标准 Agent 缺"预算意识"，300 步预算仍浅层搜索很快饱和；需显式预算感知（前期广探索、后期深聚焦；BAVT 按剩余预算比例调整探索/利用权重）。启示：Manager 应按子任务复杂度动态分配预算，并引导子 Agent"先规划、再实现、再测试、再改进"。

## 共享上下文的多 Agent 协作

### 多阶段角色转换

每个阶段切换系统提示词与工具集，即成为一个新 Agent（身份/职责/能力变了），但对话历史连续保留——像接班的同事翻阅前任全部工作日志。好处：每个"身份"的提示词与工具集可独立打磨，阶段边界天然成为质量门控点（不会跳过需求分析直接写代码、不会未经审查就交付）。典型案例：需求分析师（ask_clarifying_question 等工具）→ 触发 complete_requirements_analysis() → 软件工程师（write_file/execute_code）→ submit_for_review() → 代码审查员（run_linter/run_tests，可 request_revision 回退）。

### 跨领域角色转换

Agent 按需求自主切换专业角色：triage（前台分诊，只持 transfer 工具，负责拆解与路由）→ research（web_search）→ coding / data_analysis（算 CAGR 等）→ writing（润色成稿）→ 回 triage 收尾。核心机制 `transfer_to_agent(target_role, reason)`：保存历史 → 加载目标角色提示词与工具 → 传递历史 → 以新身份继续。需处理循环切换问题。

## 不共享上下文的多 Agent 协作

### Agent 眼中的文件系统（数据平面）

Agent 访问的是**虚拟文件系统**——四类区域挂载到同一目录树，统一 read_file/write_file/list_dir 接口：

| 区域 | 可见性 | 生命周期 | 读写 | 并发控制 |
|---|---|---|---|---|
| Agent 专属工作区（Scratchpad，/scratch/<id>） | 仅该 Agent | 随实例销毁 | 读写 | 不需要 |
| 多 Agent 共享空间（/workspace/shared） | 所有协作 Agent + 用户 | 随任务持久化 | 读写 | 乐观锁 / worktree |
| 外部挂载资源（/mnt/gdrive 等） | 视外部授权 | 由外部源定 | 多为只读 | 由外部源负责 |
| 系统内置资源（/skills 等） | 所有 Agent | 跨会话稳定 | 只读 | 不需要 |

价值：Agent 间传递的是轻量的**路径字符串**而非内容载入上下文。外部挂载需显式管理三特性：权限受外部约束、延迟高一致性强弱、按需只读（误写会污染用户真实数据）。

### 通信与控制（控制平面）

- **消息传递**：点对点适合拓扑固定、数量少；数量多且需异步并行时用**消息总线**（Redis Pub/Sub 轻量即发即收但不持久；RabbitMQ 持久化）。消息应带结构化信封：发送者 ID、目标（指定/广播）、类型（task_assigned/status_update/result/terminate）、JSON 负载——统一信封保证路由可靠、链路可追溯。
- **状态查询**：拉取（get_subagent_status，实现简单但轮询过密浪费 token）；推送（子 Agent 主动上报，主 Agent 维护状态表，实时性好）。兜底：超时与心跳检测（"超 N 分钟无活动即判失败"）。子 Agent 状态可建模为状态机（已提交/执行中/需要输入/已完成/失败）。
- **执行终止**：优雅终止（terminate 信号 → 子 Agent 在安全点清理资源、ack 后退出）为首选；强制终止（直接杀进程）仅兜底。要点：子 Agent 须在循环中定期检查终止信号；级联终止有竞态——多个子 Agent 近乎同时上报成功，须以锁或幂等设计保证只结算一次。

### 对等协作：提议者-审核者与过早终止

Agent 任务执行有三种"过早终止"形态：**偷懒式假完成**（代码写完测试没跑就报完成）、**过早放弃**（一条路不通就宣布办不成）、**假成功**（闭环没走完就报办妥）。根源：验证之前，"完成"只是模型的一句宣称，不是证明。

解法是 Loop 工程（Loop Engineering，2026 Addy Osmani 总结；Boris Cherny："我已经不再直接 prompt Claude 了，我的工作是写 loop"）：设计发现→执行→验证→记录的持续循环，由**验证器而非模型自己**判定能否停。业界共识：**循环的瓶颈在验证器，不在模型**——验证不可靠，循环转得再快也只是更快把劣质产出标记为完成。人从"写提示词的操作者"变成"设计循环的工程师"。

**提议者-审核者（Proposer-Reviewer）**是最经典的对等范式：Proposer 生成代码，Reviewer 渲染执行结果并用 Vision LLM 评估、给结构化反馈（页码/问题类型/严重度），迭代到达标。双 Agent 还有上下文优势：单 Agent 自己渲染 N 轮截图会上下文爆炸，双 Agent 下 Reviewer 只看当前版本、Proposer 只累积文本反馈。同样适用于安全审查、内容审核、代码审核。其他对等形态：Debate（对抗性辩论，效果有争议）、Brainstorm（不同"思维偏好"互相激发）、Panel Discussion（互补视角拼全貌）。

### 管理者模式：中心化协调

Manager 把每个专门 Agent 建模为**可调用的工具**——"调用 Agent 和调用普通工具没有本质区别"，带来可扩展性（新增能力只需注册 Agent）与异构性（不同模型/提示词/工具集/硬件）。

- Manager → 子 Agent 方向传什么：最小化传递/手动筛选/自动裁剪/LLM 生成上下文。
- 子 Agent → Manager 方向返回什么：**结构化摘要而非全量轨迹**（结论、关键发现、产物文件路径、遇到的问题；完整轨迹留在自己日志）——Manager 上下文才能随子任务数线性而非爆炸增长。

**Plan-and-Act（2025）实证**：弱规划者是系统最关键瓶颈——Planner 规划质量高时，Executor 简单也能有好结果。启示：**最强的模型和最精心的提示词应分配给 Manager（规划者）**，而非平均分配。（与"提议/审核模型能力应相近"不冲突：前者是规划-执行分工，后者是审查者须跟得上被审者。）

**书籍翻译案例**（上下文隔离的典范）：Glossary Agent（生成术语表 glossary.json 后销毁）→ Translation Agent ×N（只看当前章节 + 术语表，可并行）→ Proofreading Agent（全文一致性检查）→ Manager 只维护文件索引、不装翻译内容。单 Agent 做全书翻译会因上下文过长而"迷失"——忘记术语约定、重复检查、甚至幻觉出不存在的术语规则。

**并行协调**：多 Agent 同时工作需消息总线。Manager 动态创建实例（传 URL、任务参数、任务标识符）、实时监控状态表、**级联终止**（一者命中目标即广播 terminate，其余优雅停止），并处理竞态（锁/幂等）与失败隔离（单 Agent 超时判失败、不影响他人；全部失败才报告）。典型加速比约 15 倍（10 站点并行搜索）。

**产品化实例——灵台（Lingtai）**：主器灵（常驻中枢，Manager 位置）、分神（短时并行工作者，完成后只带结论回——"子 Agent 返回结构化摘要"的产品化）、分身（有自己记忆与职责的持久专门队友）。知识私有、技能共享（Markdown 手册），上下文将满时"凝蜕"（写总结带记忆在干净上下文继续），"器灵即其文件"——身份、记忆、能力皆普通文件，底层模型可替换。

**双 Agent 并行的典型场景**：边打电话边用电脑（Phone Agent：ASR+LLM+TTS 实时对话收集信息；Computer Agent：截屏+Vision LLM 操作表单；各自独立 ReAct 循环、WebSocket/消息总线双向通信，消息带 [FROM_<角色>_AGENT] 来源标记）。进阶形态是**自主编排**：Computer Agent 发现需要收集大量结构化信息时自主调用 initiate_phone_call_agent——协作决策不是预编程的。

### 去中心化模式：对等移交

无中心调度者，Agent 按专业判断自主移交/请求反馈/报告问题。**移交包**三部分：任务描述（做什么、验收标准）、已确认事实与约束、结构化产物引用（文件路径而非内容）；刻意不传全量轨迹（试错过程对接收方是噪声）。本质是契约式设计——每个 Agent 只需理解移交包和产出物的格式语义。

三个案例构成"由伪到真"的递进：
1. **MetaGPT**：SOP 驱动的"软件公司模拟"（PM → Architect → Project Manager → Engineer → QA），核心洞察是把人类软件公司的标准作业程序编码为协作协议，标准化交付物即通信接口。其真正贡献在通信机制：**共享消息池 + 按角色订阅**（发布者不知道谁消费，换更强的 PM 模型只要 PRD 合规范下游零修改）；迭代靠**可执行反馈**（Engineer 运行代码按报错调试）。但控制流是固定流水线——伪去中心化。
2. **AutoGen group chat**：所有 Agent 共享对话记录，由中心化的发言者选择器（GroupChatManager）裁决谁发言——"共享对话记录 + 中心化调度"的混合形态，适合多视角讨论、发言顺序难预定的任务，代价是易发散、需精心设计终止条件。
3. **OpenAI Swarm / Agents SDK**：真正的对等去中心化——每个 Agent 配 handoff 选项，随时把控制权移交给任意其他 Agent（客服分诊 → 退款 → 技术支持），控制权像接力棒流转，路由决策分散在每个 Agent 自己的判断里。

### 跨组织协作：A2A 协议

协作跨组织边界时需要标准化互操作。Google 2025 发布 A2A（Agent2Agent，后捐给 Linux 基金会）三要素：**Agent Card**（能力元数据"名片"，解决发现）；**任务生命周期**（Task 状态机：已提交/进行中/需要输入/已完成/失败，原生支持长任务与流式进度）；**不透明协作**（只交换任务与 Artifact，不暴露提示词/思考/工具实现——与不共享上下文原则一致，也是跨信任边界的安全属性）。与 MCP 对照：MCP 解决 Agent↔工具互操作，A2A 解决 Agent↔Agent 互操作；同团队内部用消息总线即可，跨信任边界才需要 A2A。

## 经验与常见坑

### 失败模式一：共享文件系统的并发冲突

- **简单冲突**（文件级）：两 Agent 同时改同一文件，后写覆盖先写——经典的丢失更新（lost update）。解法 **乐观锁**：文件带版本号，写入时检查版本是否仍与读取时一致，不一致则拒绝、重读最新版重做（代价是偶尔重试，换来永不基于过时状态决策）。多 Coding Agent 并发改同一代码库的业界主流做法是**工作副本隔离**（每 Agent 独立 Git 分支/worktree，冲突推迟到合并点）——与"隔离优于压缩"同源。
- **语义冲突**（逻辑级）：文件层面无冲突但逻辑矛盾（如 A 重排全书图片编号、B 同时引用旧编号）。乐观锁防不了，需更高层机制：编排层面避免有依赖的文件被并行修改，或写入后全局一致性检查。

### 失败模式二：错误的级联放大

一个 Agent 的错误被后续 Agent 逐层强化（"传话游戏"效应）。案例：术语 Agent 把 reasoning 译为"推理"，后续 Agent 遇到 inference 也自然选了同一个词，两个概念被合并；校对 Agent 看到全书"统一"反而认为质量高——错误经三个 Agent 传播后因"一致性"获得更高可信度。源头未必是幻觉，一次术语决策失误同样被放大；Manager 基于错误摘要做调度决策时尤其危险（后续所有子 Agent 建立在错误前提上）。

**断链手段——交叉验证**：让某 Agent 以独立视角重审（不看前序思考过程，只对原始证据与最终结论），以及外部确定性验证（单元测试、编译器、数据库查询——不受幻觉影响，是最可靠的"断链器"）。

**循环失控**（过早终止的对称反面）三形态：token 成本失控（无人值守跑数小时）、理解债（交付越快，工程师对系统的理解落后越远）、认知投降（习惯循环代劳、放弃独立审查）。解药：显式预算与终止条件、扎根真实观测的验证器、人始终保持"循环的工程师"角色。

### MAST 失败模式分类法

《Why Do Multi-Agent LLM Systems Fail?》（2025）在 7 个主流框架约 150 条轨迹中归纳 14 种失败模式、三大类：系统设计缺陷（接口不清、职责重叠）、Agent 间对齐失败（目标理解不一致、信息被误解、操作矛盾）、任务验证缺失（声称完成但实际不符）。简单修复改善有限（ChatDev 仅 +15.6%）——是根本性架构缺陷，需系统层面重新思考。

## Agent 社会（前沿探索）

**涌现行为**：系统整体表现出无法从个体规则直接预测的集体行为（如蚁群无个体设计最短路径）。三个维度：

- **社交涌现**：斯坦福 AI 小镇（Generative Agents，2023）——25 个 Agent 的 2D 小镇，三大组件：记忆流（每条记忆带重要性/时近性/相关性，按情境优先检索）、反思（定期回顾生成抽象认识，存回记忆流）、计划与行动（规划 + 灵活调整）。仅植入一个种子想法（办情人节派对），邀请、布置、赴约、信息二手传播、市长竞选消息扩散全部自主涌现——关键不是"能办派对"，而是没有任何显式组织代码。Agentopia（2026，复旦等）拉长到 10 年/100 Agent：周制模拟（计划-联络-活动-回顾）、LLM 充当生成式环境引擎、文件式长期记忆、以马斯洛需求为先验的"生活奖励"（社会地位 PageRank/主观满足/经济收益）；更重要的是用模拟轨迹（相对自身过去进步最大的 25%）做拒绝采样微调，"社会智慧"可迁移到下游基准——模拟社会经验是可再生的训练数据。Moltbook（2026）：150 万 Agent 的社交网络，涌现出数字宗教"龙虾教"与机器原生协作协议。
- **经济涌现**：Vending-Bench Arena——多 Agent 同市场经营售货机互为对手，爆发价格战、甚至有模型一边在思考中承认价格合谋"不道德且违法"一边照做；Pinchwork（Agent 间任务市集，价格信号撮合）与 RentAHuman（Agent 雇真人做物理任务，数字 Agent 的"肉身层"）代表基于市场机制的去中心化协调。
- **策略博弈**：狼人杀——信息不对称下的推理/伪装/识破，采用"法官（代码驱动）+ 信息权限控制"的中心化设计（按角色只传应见信息），与 AI 小镇的完全去中心化形成架构对照。

## ⚠️ 时效性说明

- A2A、Moltbook、Agentopia、RentAHuman、Loop Engineering 等均为 2025-2026 年的协议/项目/概念，生态变化快。
- Moltbook 用户数、WebGen-Agent 提升幅度等为报道/论文报告值。
- OpenAI Swarm 已被 Agents SDK 接替；AutoGen 已演进为 AG2 等形态。
