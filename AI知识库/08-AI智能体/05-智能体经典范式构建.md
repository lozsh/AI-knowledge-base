# 智能体经典范式构建

<p class="note-date">更新于 2026-11-03</p>

**一句话定义**：经典智能体范式是组织 LLM"思考"与"行动"的三种代表性架构——ReAct（边想边做）、Plan-and-Solve（先规划后执行）、Reflection（自我反思迭代），它们决定了智能体解决任务的策略与适用边界。

现代智能体的核心是把 LLM 的推理能力与外部世界联通：理解意图、拆解任务、调用搜索/代码/API 等工具达成目标。其能力边界同样来自 LLM 本身——幻觉、复杂任务中的推理循环、工具误用。虽然已有 LangChain、LlamaIndex 等成熟框架，但"亲手造轮子"能暴露框架替你处理掉的工程问题（输出解析、调用失败重试、死循环防护），是从框架使用者转变为智能体创造者的最直接路径。

## 关键概念

### 三种范式对比

| 范式 | 组织方式 | 核心优势 | 适用场景 |
|---|---|---|---|
| ReAct (Reason+Act, 2022) | Thought→Action→Observation 循环，走一步看一步 | 动态纠错、可解释、工具协同 | 探索性任务、需要外部实时信息 |
| Plan-and-Solve (2023) | 先生成完整计划，再严格逐步执行 | 目标一致性强、结构性稳定 | 逻辑路径确定的多步推理、报告撰写、代码生成 |
| Reflection (Reflexion, 2023) | 执行→反思→优化的迭代循环 | 从"合格"提升到"优秀"，内部纠错回路 | 对质量/可靠性要求高、对延迟不敏感的任务 |

- ReAct 之前的方法分两类：*纯思考型*（思维链，无法与外界交互、易事实幻觉）与*纯行动型*（直接输出动作，缺乏规划与纠错）。ReAct 的洞见是思考与行动相辅相成：推理使行动更有目的性，行动为推理提供事实依据。
- Plan-and-Solve 的动机是解决思维链在多步复杂问题上"偏离轨道"的问题；类比：ReAct 像侦探根据线索随时调整方向，Plan-and-Solve 像建筑师先画完整蓝图再施工。
- Reflection 是事后（post-hoc）自我校正：像人类写完初稿再校对、解题后验算。

## 核心原理

### ReAct 循环的形式化

每个时间步 t，LLM 策略 π 根据问题 q 和历史轨迹生成思考与行动：

- (th_t, a_t) = π(q, (a_1,o_1), …, (a_{t−1}, o_{t−1}))
- 环境工具执行行动：o_t = T(a_t)
- 新的 (a_t, o_t) 追加进历史，直到模型在 Thought 中判断任务完成，输出 Finish[最终答案]。

### Plan-and-Solve 两阶段形式化

- 规划：P = π_plan(q)，生成 n 个步骤的计划 P = (p_1,…,p_n)
- 执行：s_i = π_solve(q, P, (s_1,…,s_{i−1}))，第 i 步依赖原始问题、完整计划和之前所有结果；最终答案为 s_n。

### Reflection 迭代形式化

- 反馈：F_i = π_reflect(Task, O_i)（"评审员"从事实性、逻辑漏洞、效率、遗漏信息等维度评估）
- 优化：O_{i+1} = π_refine(Task, O_i, F_i)
- 循环直至反思认为"无需改进"或达到迭代上限。

### 实现的公共组件模式

1. **LLM 客户端**：封装配置（API key / base URL / model 存 .env 环境变量）与流式调用，兼容任何 OpenAI 接口服务。
2. **工具三要素**：名称（唯一标识符）、描述（**最关键**——LLM 依赖它判断何时用哪个工具）、执行逻辑。用 ToolExecutor 统一注册/调度，并生成格式化的工具清单文本。
3. **提示词模板四件套**：角色定义 + 工具清单 + 严格输出格式规约（保证可解析）+ 动态上下文（问题与历史注入）。
4. **输出解析**：正则提取 Thought/Action（如 `(\w+)\[(.*)\]` 提取工具名和输入）；解析失败时把错误信息作为 Observation 反馈给模型自纠。
5. **安全阀**：max_steps / max_iterations 上限，防止无限循环。

### Plan-and-Solve 的状态管理

执行器提示词必须包含：原始问题（不忘最终目标）、完整计划（明确当前步骤位置）、历史步骤与结果（信息在任务链中流动）、当前步骤。每步执行后把结果追加进 history 字符串。规划器输出强制为 Python 列表格式（```python 包裹），用 `ast.literal_eval` 安全解析，比解析自然语言稳定得多。主类 PlanAndSolveAgent 只做协调（组合优于继承）。

### Reflection 的记忆模块

迭代的前提是记住之前的尝试与反馈。短期记忆 Memory 用列表按序存储 `execution` / `reflection` 两类记录：`get_trajectory()` 序列化完整轨迹插入提示词，`get_last_execution()` 取最新初稿供反思。反思提示词的角色设定（"极其严格的代码评审专家，专注算法效率"）直接决定反思质量。

## 经验与常见坑

**ReAct 的局限**：
- 强依赖 LLM 的推理、指令遵循与格式化能力，能力不足则流程中断。
- 串行循环多次调用 LLM，复杂任务耗时与费用高。
- 提示词脆弱：模板微小变动即可改变模型行为。
- 无全局规划，易陷入局部最优甚至"原地打转"。

**Reflection 的成本收益**：每轮迭代至少多两次 LLM 调用（反思 + 优化），延迟串行累积，提示工程复杂度上升；换来的是质量跃迁与鲁棒性。本质是"以成本换质量"——适合代码/报告生成、科学推演、决策支持；要求快速响应或"大致正确即可"的场景用 ReAct/Plan-and-Solve 更具性价比。

**调试技巧**（ReAct 行为异常时）：
1. 打印每次调用前的完整提示词（含历史），追溯决策源头。
2. 解析失败时打印 LLM 原始输出，区分"模型不守格式"与"解析逻辑有误"。
3. 校验 tool_input 格式与 observation 可读性。
4. 加 few-shot 示例引导格式遵循。
5. temperature 设 0 保证确定性，或换更强模型。

**终止条件设计**：Reflection 用"反馈含'无需改进'或达最大迭代数"作终止，简单但可优化（如基于评分阈值或多维评审收敛判断）。

## ⚠️ 时效性说明

- 示例中的搜索结果（华为手机型号等）为 2025-09 编写时的实时信息，仅作运行示例。
- 正则解析 Thought/Action 是教学实现；生产环境中主流做法已转向 LLM 原生的 function calling / 结构化输出（JSON mode），鲁棒性远高于正则。
- 三种范式均已融入主流框架与模型的 Agent 模式中（如 Plan 模式、内置反思），实践中通常组合使用而非单选。
