# 智能旅行助手（多 Agent 全栈应用）

<p class="note-date">更新于 2026-11-05</p>

**一句话定义**：一个基于多 Agent 协作 + MCP 工具集成 + 前后端分离架构的完整旅行规划应用——用户输入目的地/日期/偏好/预算，系统自动生成含景点、餐饮、酒店、预算的完整行程，支持地图可视化、行程编辑与导出。

传统旅行规划的三大痛点：**信息分散**（景点/天气/酒店分属不同网站，需手动整合）、**缺少个性化**（通用攻略不考虑偏好、预算、时间）、**难以调整**（景点顺序、时间、预算相互关联，改一处要重排全部）。智能旅行助手针对这三点：一次输入生成完整计划、按个人偏好定制、编辑后地图与预算实时更新。

## 系统架构

前后端分离四层：

| 层 | 技术 | 职责 |
|---|---|---|
| 前端层 | Vue3 + TypeScript + Vite + Ant Design Vue + 高德 JS API | 表单输入、结果展示、地图可视化 |
| 后端层 | Python + FastAPI | API 路由、数据验证、业务逻辑 |
| 智能体层 | HelloAgents 框架 | 任务分解、工具调用、结果整合（4 个专门 Agent） |
| 外部服务层 | 高德地图 API（MCP）、Unsplash API、LLM API | 提供数据与能力 |

数据流转：前端表单 → 后端验证 → 多 Agent 依次执行（景点搜索 → 天气查询 → 酒店推荐 → 行程规划）→ Agent 经 MCP 协议调用外部 API → 整合返回 → 前端渲染。

## 关键概念

### 数据模型：从字典到 Pydantic

Web 应用中数据多次转换（前端表单 → HTTP → Python 对象 → 外部 API 响应 → …），字典表示有三个问题：字段名不统一（高德返回"116.397128,39.916527"字符串，Unsplash 用 longitude/latitude）、类型不安全（price 写成"60"只在运行时暴露）、维护性差（加字段要改多处）。

Pydantic 解决方案的核心概念：
- `Field(...)` 标必填；`Field(default=0.0, ge=0, le=5)` 做范围验证；`Optional` 可选字段。
- **嵌套模型**：Location 嵌入 Attraction/Meal/Hotel，`List[Attraction]` 组成 DayPlan。
- **自定义验证器** `field_validator(mode='before')`：高德返回温度是"16°C"字符串，验证器在建模前自动剥离单位转 int（含容错，解析失败返回 0）。

模型层次（自底向上）：`Location`（经度 -180~180 / 纬度 -90~90 范围验证）→ `Attraction` / `Meal` / `Hotel` / `Budget`（四类费用汇总）→ `DayPlan`（日期、交通、住宿、景点列表、餐饮列表）→ `TripPlan`（城市、日期、days、weather_info、总体建议、预算）。

FastAPI 中模型直接作请求/响应类型：自动数据验证（格式错误自动 400 并指明原因）、序列化、OpenAPI 文档生成。前端定义对应的 TypeScript interface（`?` 对应 Optional），前后端统一数据格式，类型检查在两端都生效。

### 多 Agent 协作设计

**为什么不用单 Agent**：SimpleAgent 每次 run 只执行一个工具，多工具需多次调用且要手动传递中间结果；ReActAgent 虽能多轮调用但每轮思考都是一次 LLM 调用且串行，耗时长；且单 Agent 的巨型提示词（同时描述四个任务的执行逻辑）难以维护、容易出错（LLM 搞混不同任务的格式参数）、难以调试（不知哪个环节出问题）。类比旅行社：景点顾问、酒店顾问、行程规划师各司其职。

**四个 Agent 角色**：

| Agent | 职责 | 输入 | 工具 |
|---|---|---|---|
| AttractionSearchAgent | 按偏好搜景点 | 城市 + 偏好 | amap_maps_text_search |
| WeatherQueryAgent | 查天气 | 城市 | amap_maps_weather |
| HotelAgent | 搜酒店 | 城市 + 住宿类型 | amap_maps_text_search |
| PlannerAgent | 整合生成完整计划 | 用户需求 + 前三个 Agent 输出 | 无（纯整合） |

提示词设计要点：简洁但信息完备——明确工具调用格式（`[TOOL_CALL:amap_maps_text_search:keywords=景点,city=北京]`）、给出示例、强调"必须使用工具搜索，不要编造信息"；PlannerAgent 则严格规定 JSON 输出格式与七条规划要求（每天 2-3 个景点、考虑距离与游览时间、含三餐、温度纯数字等）。

协作流程（TripPlannerAgent 编排）：顺序执行三个搜索 Agent → `_build_planner_query` 把用户需求与三个输出组织成清晰有序的规划查询 → PlannerAgent 生成 JSON → 解析为 TripPlan。结构化分解也为未来扩展（餐厅推荐 Agent、交通规划 Agent）打好基础。

## 核心原理

### MCP 工具集成

**为什么不直接调 API**：Agent 无法自主调用（变成简单函数调用，失去决策能力）；参数传递复杂（高德 API 十几个参数都要写进提示词）；响应解析困难（JSON 结构变化要改解析代码）；工具管理混乱（每个 API 手写一个函数再手动注册）。

**MCP 集成方式**（amap-mcp-server，Node.js 实现）：

```python
mcp_tool = MCPTool(
    name="amap_mcp",
    command="npx", args=["-y", "@sugarforever/amap-mcp-server"],   # 或 uvx（Python 生态，理念相同）
    env={"AMAP_API_KEY": settings.amap_api_key},
    auto_expand=True,
)
```

关键机制：
- MCPTool 在后台启动 MCP 服务器进程，经 **stdin/stdout**（而非 HTTP）以 JSON-RPC 通信——更高效易管理。
- **auto_expand=True**：自动查询 MCP 服务器提供的工具清单，为每个工具创建独立 Tool 对象——创建一个 MCPTool，Agent 即获得高德的全部工具（POI 搜索、天气、路线规划、静态地图等）。
- 调用链路：Agent 生成 `[TOOL_CALL:...]` 标记 → 框架解析 → Tool 对象构造 JSON-RPC `tools/call` 消息经 stdin 发给 MCP 服务器 → 服务器调高德 HTTP API → 解析结果经 stdout 返回 → Agent 拿到 Observation。Agent 只需知道"有个叫 amap_maps_text_search 的工具"，底层细节全被封装。

**共享 MCP 实例**：三个 Agent 都需高德工具，若各自创建 MCPTool 会有三个服务器进程（超 API 速率限制风险、资源浪费）。正确做法是在 TripPlannerAgent 构造函数中创建一个 MCPTool 实例，add_tool 共享给每个子 Agent——一个进程服务全部调用。

### Unsplash 图片服务

封装为 UnsplashService 类（search_photos / get_photo_url），**不封装成 Tool 或 MCP 工具**，直接在 API 路由中调用——图片搜索不需要 Agent 的智能决策，只是数据增强步骤；若要让 Agent 自主决定是否取图才需要封装成 Tool。注意 Unsplash 为国外免费服务，搜索准确性有限；商用可考虑必应/百度/高德 POI 图片 API（付费）。

### 前端要点

- **API 服务封装**：Axios 实例（baseURL、**超时 2 分钟**——多 Agent 各调 LLM 与外部 API 全程 10-30 秒，超时太短会中断）；请求/响应拦截器做日志与错误处理；API 函数用 TypeScript 类型签名（`Promise<TripPlan>`）保证调用正确性。
- **加载进度条**：生成耗时长，无反馈用户会以为卡死。用 setInterval 模拟进度（每 500ms +10%，分段切换状态文案"搜索景点→查天气→推酒店→生成计划"），完成后跳结果页。是模拟进度而非真实进度。
- **地图可视化**：AMapLoader 加载高德 JS SDK → 遍历行程中的景点创建 Marker（经纬度来自后端 Attraction 对象）。
- **行程编辑**：核心是状态管理——进入编辑模式时用 `JSON.parse(JSON.stringify(...))` **深拷贝**原始计划（JS 对象是引用类型，直接赋值会互相影响）；取消恢复副本，保存则重新初始化地图。移动景点用 ES6 解构交换 `[a,b]=[b,a]`，删除用 splice。
- **导出**：html2canvas（DOM → Canvas，scale:2 高清、useCORS 允许跨域加载 Unsplash 图片）+ jsPDF（A4 宽 210mm，按宽高比算高度）。**已知坑**：地图是 Canvas 渲染，html2canvas 处理嵌套 Canvas 有兼容性问题（高德渲染机制 + 跨域限制）；替代方案：高德静态地图 API、地图与内容分开导出后端合并、Puppeteer 服务端截图、导出时隐藏地图只导文字（当前采用的简化方案）。
- **预算计算**：在后端 PlannerAgent 中实现（LLM 生成行程时已掌握门票/酒店/餐饮信息，前端重算会重复逻辑且不准）；前端用 a-statistic 组件展示，`v-if="tripPlan.budget"` 条件渲染体现对可选数据的容错。
- **侧边导航**：Menu 组件 + `scrollIntoView({behavior:'smooth'})` 锚点平滑跳转，各区块加对应 id。

## 经验与常见坑

- 前后端数据模型必须两端同步定义（Pydantic ↔ TypeScript interface），任何一端改字段都要同步，否则类型检查会兜底报错。
- 提示词要求 LLM 输出严格 JSON 时，要在提示词中穷举格式细节（如"温度为纯数字不带°C"），并配合 Pydantic 验证器做最后防线。
- 多 Agent 共享外部服务实例（MCP 服务器、LLM 客户端）是资源与速率控制的基本功。
- Agent 任务提示词中"必须使用工具搜索，不要编造信息"是防幻觉的关键约束。
- 全栈集成类项目的调试难度随层次增加（前端 → 后端 → Agent → MCP → 外部 API），每层都要有独立可验证的入口（如 FastAPI 自带 /docs）。
- 导出含第三方 Canvas 地图的页面是已知难点，选型时优先考虑静态地图或服务端截图。
- **批量与即时分工是大量 AI 调用场景的通用优化思路**：不要求实时性的内容（背景生成、预计算）离线批量生成省钱，用户交互必须即时个性化，二者混合可大幅降低成本；并发场景下被共享的 Agent/资源要有忙碌保护（拒绝重入、结束后在 finally 中释放）。

## ⚠️ 时效性说明

- 依赖服务（高德 MCP server 包名 @sugarforever/amap-mcp-server、Unsplash 免费额度、Vite/Ant Design Vue 版本）随时间变化。
- 模拟进度条是权宜方案，生产环境应改为 SSE/WebSocket 推送真实进度。
- 导出功能当前采用"隐藏地图"的简化方案，文中列出的四种替代方案值得在正式项目中评估。
