# 构建赛博小镇

<p class="note-date">更新于 2026-11-03</p>

**一句话定义**：一个「游戏引擎 + LLM 后端」结合的 AI 小镇项目——Godot 像素办公室里的每个 NPC 都是一个有角色设定、双层记忆和好感度的智能体，能与玩家自然语言对话并随关系变化改变态度。

传统游戏 NPC 只能说编剧预写的固定台词或走对话树，可控但没有"生命感"。赛博小镇探索的是：用大语言模型驱动 NPC，让它能理解任意自然语言、记住过去的互动、根据好感度做出不同反应。应用场景不止游戏——教育游戏中扮演历史人物互动教学、虚拟办公室里扮演同事导师、心理健康领域的情感陪伴。

项目五大核心功能：智能 NPC 对话系统（按角色设定和记忆回应）、记忆系统（短期+长期）、好感度系统（态度随互动从陌生到挚友）、游戏化交互（2D 像素办公室自由移动）、实时日志系统（所有对话可追溯）。

## 核心原理：系统架构

游戏引擎 + 后端服务分离的四层架构：

| 层 | 技术 | 职责 |
|---|---|---|
| 前端层 | Godot 4.5 游戏引擎 | 游戏渲染、玩家控制、NPC 显示、对话 UI |
| 后端层 | FastAPI | API 路由、NPC 状态管理、对话处理、日志 |
| 智能体层 | HelloAgents | NPC 智能（每个 NPC 一个 SimpleAgent 实例）、记忆管理、好感度计算 |
| 外部服务层 | LLM API、Qdrant 向量库、SQLite | 模型推理、向量存储、数据持久化 |

一次交互的数据流：玩家在 Godot 按 E 键 → HTTP API 发对话请求到 FastAPI → 调用 NPC 的 SimpleAgent → Agent 从记忆系统检索相关历史 → LLM 生成回复 → 更新 NPC 状态与好感度、写日志 → 返回 Godot 显示。

## 关键概念

### NPC 智能体（SimpleAgent + 角色设定）

每个 NPC 一个独立 SimpleAgent，系统提示词由 `名字 + 职业 + 性格` 模板生成。三个示例 NPC：

| NPC | 职业 | 性格 |
|---|---|---|
| 张三 | Python 工程师 | 严谨、直接、爱分享技术、注重代码质量 |
| 李四 | 产品经理 | 外向、善沟通、从用户角度思考、爱问"为什么" |
| 王五 | UI 设计师 | 温和、有创意、审美独特 |

```python
# NPC Agent 创建模式（骨架）
memory_manager = MemoryManager(
    working_memory=WorkingMemory(capacity=10, ttl_minutes=120),   # 短期记忆
    episodic_memory=EpisodicMemory(db_path=..., collection_name=...)  # 长期记忆
)
agent = SimpleAgent(name=name, llm=llm, system_prompt=system_prompt,
                    memory_manager=memory_manager)
```

### 双层记忆系统

- **短期记忆（WorkingMemory）**：容量 10 条、保留 120 分钟，自动清理。作用是保持对话连贯——理解"它是什么颜色的？"中"它"指什么。
- **长期记忆（EpisodicMemory）**：SQLite + Qdrant 向量库存全部对话历史，语义检索。作用是回忆——回答"还记得我们上次讨论的项目吗"。

对话处理流程：取短期记忆最近 5 条 → 长期记忆按玩家消息检索 top-3 相关历史 → 组合上下文交给 LLM → 交互写回记忆。

### 批量对话生成与混合模式（成本优化的关键设计）

问题：多玩家并发对话时每个请求都调 LLM API，成本高且受并发限制。解法是「批量生成 + 即时响应」的混合模式：

- **批量生成（背景对话）**：把所有 NPC 的对话请求合并成一次 LLM 调用，Prompt 要求按 `{"张三": "...", "李四": "...", "王五": "..."}` 的 JSON 格式一次生成全部回复，成本降到约 1/3。附加收益：同一上下文生成的 NPC 对话彼此有关联（张三调试 bug，李四会提到帮忙），氛围更真实。适用场景：NPC 背景自言自语、定时更新、按时间（早/午/晚）生成氛围对话。后台任务每 5 分钟批量刷新一次。
- **即时响应（玩家交互）**：玩家按 E 发起对话时切到该 NPC 的专属 Agent，基于消息、记忆、好感度实时生成个性化回复。

| 批量生成 | 即时响应 |
|---|---|
| 背景对话、氛围营造 | 玩家直接交互 |
| 一次调用生成全部，成本低 | 逐个生成，个性化质量高 |
| 后台定时运行（5 分钟） | 实时触发 |

### 好感度系统

五级好感度（0-100 分），量化 NPC 与玩家的关系：

| 等级 | 分数 | 行为表现 |
|---|---|---|
| 陌生 | 0-20 | 礼貌但疏远，回复简短，不主动分享 |
| 熟悉 | 21-40 | 记住玩家，交流自然，偶尔聊工作 |
| 友好 | 41-60 | 当作朋友，回复详细，主动询问玩家 |
| 亲密 | 61-80 | 非常信任，聊私人话题，热情给建议 |
| 挚友 | 81-100 | 无话不谈，分享内心想法 |

计算逻辑不用固定加分（那样机械），而是让 LLM 分析每轮对话中玩家的态度：友好 +5、中立 +2、不友好 -3（结果钳制在 [-3, 5]，解析失败默认 +2），再累加进分数并映射等级。好感度反过来影响对话：**动态改写系统提示词**——每个等级对应一段关系描述（如"陌生：保持礼貌但不要过于热情，回复简短专业"），拼进 Agent 的 system prompt，NPC 的语气随之变化。这个设计还可扩展为门控：达到一定好感度才解锁特殊信息或任务。

### 后端服务（FastAPI）

- 模块化结构：`agents.py`（NPC Agent 系统）、`relationship_manager.py`（好感度）、`state_manager.py`（状态）、`logger.py`（日志）、`config.py`、`models.py`。
- 核心 API：
  - `GET /npcs/status`、`GET /npcs/{npc_id}/status`——NPC 状态；
  - `POST /dialogue`——对话主流程：验证 NPC 存在 → 检查忙碌（409）→ 标记忙碌 → 取好感度 → 按等级取 Agent 生成回复 → 更新好感度 → 记日志 → finally 释放忙碌状态；
  - `GET /affinity/{npc_id}/{player_name}`——查好感度。
- **状态管理器**：跟踪每个 NPC 的位置、忙碌、当前动作，防止一个 NPC 同时与多个玩家对话的并发问题。
- **日志系统**：控制台 + 按日期文件（`logs/dialogue_YYYY-MM-DD.log`）双输出，记录消息、回复、好感度值与变化量、情感分析结果，可用 `view_logs.py` 实时查看。

### Godot 场景系统（游戏前端基础）

- **节点（Node）**：Godot 最小构建块，如 Sprite2D（图片）、AudioStreamPlayer（音频）、CharacterBody2D（物理移动），父子树状结构，父节点操作影响所有子节点。
- **场景（Scene）**：一组节点的集合，存为 `.scn` 文件，相当于"预制件"，可嵌套实例化、可复用。三个 NPC 是同一个 `NPC.tscn` 的三个实例，改一次场景全部生效。

选 Godot 的四个理由：2D 开发优势明显（TileMap、AnimatedSprite2D 等专用节点）；MIT 开源免费无分成；GDScript 类似 Python 学习成本低；HTTPRequest 节点与 Python 后端集成简单。局限：3D 能力弱于 Unreal/Unity，不适合大型 3D 游戏。

四个核心场景：

| 场景 | 根节点 | 内容 |
|---|---|---|
| Player | CharacterBody2D | AnimatedSprite2D、CollisionShape2D、Camera2D、两个音效节点 |
| NPC | CharacterBody2D | 碰撞、动画、InteractionArea（Area2D 交互检测）、NameLabel、DialogueLabel |
| DialogueUI | CanvasLayer | Panel + NPCName、NPCTitle、DialogueText（RichTextLabel）、PlayerInput（LineEdit）、发送/关闭按钮 |
| Main | Node2D | 背景、Player 实例、3 个 NPC 实例、DialogueUI 实例、墙体、背景音乐 |

### 前后端通信（GDScript 侧）

- **api_client.gd**：设为 AutoLoad 单例，封装三类请求（`send_chat` 对话、`get_npc_status` 状态、`get_npc_list` 列表）。每个 API 独立 HTTPRequest 节点避免互相干扰；异步请求通过**信号**（`chat_response_received`、`npc_status_received`）通知多个监听者，而非 await 阻塞，保证游戏流畅。
- **player.gd**：WASD 移动 + 4 方向动画（walk_up/down/left/right）、按 E 交互（NPC 通过 `set_nearby_npc` 注册自己为可交互对象）、交互时禁用移动、走路音效自动启停。加入 "player" 组供 NPC 识别。
- **npc.gd**：在出生点 wander_range 范围内随机巡逻（3-8 秒间隔选新目标）、Area2D 检测玩家进出交互范围、`update_dialogue` 显示对话气泡 10 秒后隐藏、对话中停止巡逻。
- **dialogue_ui.gd**：RichTextLabel `append_text` 富文本显示对话（玩家消息青色、NPC 回复黄色）；等待响应时禁用输入防重复发送；打开对话框即通知玩家进入交互态。
- **main.gd**：定时器每 30 秒调一次 `get_npc_status`，收到状态信号后遍历更新各 NPC 的对话气泡——玩家不交互也能看到 NPC 的"自主对话"。

## 经验与常见坑

- **并发状态保护**：NPC 必须有忙碌标记（409 拒绝），对话结束在 `finally` 中释放，异常也不能漏。
- **LLM 输出必须约束格式**：批量生成靠"严格 JSON + 示例输出 + 只返回 JSON"的 Prompt 约束；好感度分析靠"只返回数字"并对解析失败设默认值（+2）。
- **好感度别用固定加分**：让 LLM 做情感判断再动态调分，玩家正常交流即可，系统才显得自然。
- **批量与即时分工**：背景对话批量生成省钱，玩家交互必须即时个性化，二者混合是大量 AI 调用场景的通用优化思路。
- **Godot 信号而非轮询**：API 响应用信号广播，多脚本可同时监听，组件松耦合。

## 挑战与扩展方向

三大现实挑战：**成本**（每句对话都调 API，大型多人游戏费用高）、**延迟**（LLM 推理需时，网络差时玩家要等几秒）、**内容控制**（生成内容不完全可控，需提示词约束 + 内容过滤）。

七个扩展方向：多人在线（WebSocket + 数据库持久化，NPC 对每个玩家独立好感度）、任务系统（好感度门控解锁 NPC 任务）、NPC 之间互动（后台自动对话让世界更生动）、情感系统（开心/难过等情绪状态影响回复）、动态事件（团队会议、生日派对、紧急任务）、更大的世界（咖啡厅、图书馆、公园等多场景）、个性化学习（NPC 记住玩家偏好与活跃时段）。

## ⚠️ 时效性说明

- 原文基于 Godot 4.5、FastAPI、HelloAgents 框架的 2024-2025 年技术栈；文中提到 Unity 2024 年"运行时费用政策"争议属于当时事件，政策后续有调整。
- 批量生成成本"降到 1/3"是按当时 3 个 NPC 估算的相对值，非普适结论。
- 本项目 NPC 对话为单轮请求-响应（HTTP REST），未用流式/长连接；"NPC 自主对话"实为定时批量生成后推送，不是 NPC 间实时协商。
- 好感度情感分析由通用 LLM 充任，未用专门的情感分析模型。
