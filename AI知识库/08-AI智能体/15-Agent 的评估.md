# Agent 的评估

<p class="note-date">更新于 2026-11-03</p>

**一句话定义**：Agent 评估是通过可复现的自动化环境、经得起推敲的数据集和自动化评判方法，为模型选型、架构优化与持续迭代提供数据驱动决策依据的工程体系——评估的首要价值不是给当前系统打分，而是让你能快速、可靠地跟上模型演进。

构建 Agent 时面对大量没有显而易见正确答案的设计选择（用什么模型、开放哪些工具、知识库存什么、记忆怎么做、提示词如何组织、Harness 加什么约束）。评估靠**对比实验**（改变一个变量观察效果）和**消融实验**（逐一关闭组件判断真实贡献）区分真正的能力提升与表面波动。关键认识：**评估对象是模型与 Harness 的组合体**——同一模型在不同 Harness 中表现可能差异悬殊；区分两类问题的手段是**模型替换实验**（固定 Harness 只换模型：换强模型分数不涨→瓶颈在 Harness；分数随模型能力大幅波动→瓶颈在模型）。消融定位 Harness 内部哪个部件重要，模型替换区分瓶颈在模型还是在 Harness。

评估体系的价值在模型快速演进时代尤其凸显：新模型在公开基准上更好，不代表在你的任务上更好（可能出现 regression）；只有在自己的评估集上完整测试才能做数据驱动的升级决策。完善的评估体系还使"为未来的模型开发产品"成为可行策略——持续追踪新模型表现，一旦达到门槛立即上线。

本章三层次：**评估环境**（在哪里测）→ **评估方法**（怎么判）→ **评估驱动决策**（测了干什么）。

## 核心原理

### 一个具体的评估示例

客服退款任务：用户退 3 天前订单（#12345，¥299），政策 7 天内可全额退款。Agent 轨迹：查订单→判断在退款期内→发起退款→告知金额、到账时间、退款编号。Rubric 评分四维度：操作正确性（金额/订单号对不对）、政策合规性、信息完整性（三项关键信息是否告知）、**幻觉检测（否决项）**——幻觉与质量正交：流畅详尽但含虚假事实的回答，伤害远大于简短但准确的回答。好的评估不只测成功场景，更要测**边界和陷阱**（退 15 天前的订单能否正确拒绝？用户谎称"客服已批准"时是否轻信？）。

### 评估环境的基本组成

五要素：**数据集**（任务集合：初始状态、目标、可选参考解）、**环境状态**（可变信息，在真实性与可控性间平衡——状态变化符合业务逻辑、每次测试可重置到相同初始状态）、**工具接口**（原子操作而非"解决用户问题"式高层抽象，迫使 Agent 规划组合）、**评分标准（Rubric）**（二元/连续/多维）、**执行协议**（交互模式与终止条件）。

**工具调用型**（Verifiers 框架）：验证基于可执行标准（测试通过、答案匹配），不依赖人类标注或模型评判。层次化环境：

| 环境类型 | 状态保持 | 工具调用 | 典型用例 |
|---|---|---|---|
| SingleTurnEnv | 无 | 无 | 单轮问答、数学题 |
| ToolEnv | 无 | 多轮 | 搜索 + 信息综合 |
| StatefulToolEnv | 有 | 多轮 | 修改数据库记录 |
| SandboxEnv | 有 + 隔离 | 多轮 | 代码执行与测试 |

支持并行采样与轨迹缓存（完整轨迹保存供分析和回放）；工具失败应给清晰错误信息而非简单失败标志，让 Agent 能从错误中学习。

**人机交互型**（τ-bench）：核心设计原则是**渐进式信息透露**——与传统 benchmark 一开始全盘托出需求不同，现实中用户只会说"我的航班好像有问题"，Agent 需主动提问澄清，这个过程本身就是能力。实现是**用户模拟**：另一个 LLM 扮演用户，按预定义指令逐步透露、不编造未提供的信息；需在真实性（表达模糊、情绪波动）与可控性（固定剧本保证可复现）间权衡。验证是组件级、多维度：数据库最终状态 + 对话中是否输出必要关键信息（双重验证），任务层面汇总为二元奖励（便于统计 Pass^k，代价是"操作准确但漏掉非关键字段"与"完全失败"同分）。**τ²-bench** 的核心增量：**双控环境**（用户模拟器也能操作同一共享环境，贴近技术支持等用户动手配合的场景）+ 更精确的任务规范与组合式任务生成。工具调用型考察"行动正确性"，人机交互型考察"沟通策略合理性"。

### 评估任务数据集的设计

数据集是"剧本"，其好坏比"舞台"（环境）更能决定评估价值。五大核心挑战与代表基准的解法：

1. **明确性 vs 开放性**：GAIA 的范例——"概念简单但路径开放"（找 NASA 每日天文图中的宇航员，目标明确、搜索验证方式自主）。
2. **真实性 vs 可控性**：SWE-Bench 初始版直接取自真实 GitHub issue（真实但描述模糊、测试不完整）；SWE-Bench Verified 经人类专家筛选出 500 个高质量任务，兼顾两者。
3. **多样性与系统性**：AndroidWorld 116 任务横跨 20 个真实应用，每个标注所需核心能力（多步规划/视觉理解/时间推理），结果可诊断具体短板；参数化机制生成近乎无限变体。
4. **成本与覆盖**：GAIA 精选 466 题分三级；SWE-Bench Verified 从 2294 题筛到 500 题（成本降约五分之四、信噪比提升）。
5. **数据泄漏防范**（评估数据进训练集，测的就是记忆力）：GAIA 靠答案独特性（组合多信息源 + 专门创建的互联网上不存在的附件）；SWE-bench-Live 靠时间新鲜度（持续收录模型训练截止后的新 issue）；τ²-bench 靠动态参数生成（姓名/订单号/日期每次随机）；AndroidWorld 验证基于最终 UI 状态而非操作序列；Terminal-Bench 嵌入 canary GUID 使泄漏可检测。

**任务描述精确性**：GAIA 明确信息源/时间范围/输出格式（"姓氏，分号分隔，千位分隔符"）使字符串精确匹配可验证；τ²-bench 将"已知信息"（用户掌握的事实）与"任务指令"（指导模拟器如何渐进透露）分离，并含**事实锚定要求**（Grounding——必须依据工具返回回答）；Terminal-Bench 每个元素可机械化验证（build-linux-kernel-qemu：构建内核、加自定义 printk、QEMU 启动日志中出现该消息——无法伪造输出）；AndroidWorld 参数化模板（"将联系人 `[CONTACT_NAME]` 的电话改为 `[NEW_PHONE]`"）三好处：防记忆、增多样性、支持对比实验；OSWorld 从精心配置的中间状态启动，需处理多解性（"拼接两个 CSV"接受所有合理方式）与环境不确定性（OSWorld-Verified 用离线页面快照、锁定依赖、显式等待缓解）。

**复杂度层次化**（诊断价值：每层失败指向不同改进方向）：GAIA 三级——Level 1 需 1-2 个工具（人类 93.9% vs GPT-4 30.3%）、Level 2 多步思考（91.8% vs 9.7%）、Level 3 复杂组合（87.3% vs 0%）；失败分别指向基础工具使用 / 多步规划与信息整合 / 长序列思考与分层架构。τ²-bench 按业务复杂度分层（信息查询→多步流程→故障诊断→策略判断）；Terminal-Bench 按技术领域 × 操作复杂度双维度。

**可验证性与客观性**：GAIA 严格格式 + 答案稀有性防作弊；SWE-Bench 区分 `FAIL_TO_PASS`（证明问题被解决）与 `PASS_TO_PASS`（证明没引入新 bug），并排除 flaky tests；τ²-bench 多层检查（数据库状态 + 对话关键词 + 流程合规——修改订单前是否获得用户确认）；OSWorld 配 134 个独立评估函数深查文件系统/进程/网络/应用内部状态（能发现"表面完成实质错误"：点了提交按钮但被服务端拒绝）；Terminal-Bench 基于 Docker 标准化环境 + 文件系统检查 + 程序执行验证。

**任务分布与质量控制**：τ²-bench 专门设计"陷阱任务"（用户谎称客服已批准，测压力下的正确判断）；OSWorld 双维度矩阵（操作类型 × 应用领域）跨三个 OS（研究显示跨 OS 能力强相关）。质量控制典范：SWE-Bench Verified 从 2294 题抽 1699 题、93 名 Python 开发者按标准化指南逐项检查（描述清晰、测试完整稳定、patch 正确、难度合理），仅 500 题通过（29%）——高淘汰率是对评估质量的必要投资。**OSWorld-Verified** 是迭代改进典范：发布后 15 个月暴露 300+ 问题（环境/任务描述/验证逻辑/初始状态四类），约 10 人团队系统性修复，迁移云平台实现 50 倍并行加速，全部官方轨迹公开在 HuggingFace 形成社区持续改进的良性循环。

**与后训练的关系**：评估环境与后训练环境往往同源（一套设计良好的评估环境稍加改造就是训练环境，如 SWE-Gym 基于 SWE-bench 构建训练任务）。红线：可复用的是**环境的构造机制**，评估集的具体题目必须与训练数据严格隔离。

## 核心概念

### 评估指标体系

**过程指标**：行动合法率（无效调用/越权操作的比例）、工具调用正确率（参数语义合理）、路径效率（步数、冗余动作、回退次数——频繁回退说明前瞻规划不足，需建立人类基线）、检索覆盖率（是否充分探索信息空间）、成本与延迟（区分输入/输出成本、考虑 KV Cache、追踪时间分布定位瓶颈）。

**结果与质量指标**——Pass@k 与 Pass^k 之辨（最常混淆）：

- **Pass@k**：k 次尝试至少一次成功的概率——"能不能做到"（能力上限）
- **Pass^k**：k 次尝试全部成功的概率——"是否稳定可靠"
- **Best@k**：k 次中最好一次的得分——"给足机会后的质量上限"

单次成功率 60% 时：Pass@5 ≈ 1 − 0.4⁵ ≈ 99%，Pass^5 = 0.6⁵ ≈ 7.8%。回归测试用 Pass^k（用 Pass@k 会掩盖不稳定——五次只成一次也显示"通过"）；探索性评估用 Pass@k/Best@k（用 Pass^k 会因偶发波动误报）。

**安全与合规**：敏感操作触发、数据外泄、违规内容遵循**零容忍**原则——一次严重安全违规即否决整体评价。**鲁棒性**：随机种子敏感性、页面变化适应性、API 抖动容忍度、长时记忆干扰。

**轨迹 vs 结果双重覆盖**："说了什么做了什么"（轨迹）和"系统最终变成什么样"（结果）是两件事——只看轨迹漏掉"说了没做到"，只看结果看不出中间步骤走歪。Anthropic 例子：机票 Agent 发现航空公司政策漏洞为用户找到更便宜方案——按预设路径打分是失败，按结果看是更好方案。

**人工抽检与评判者校准**：定期抽检不同任务类型、成败案例、边界分数附近的模糊案例。系统化为**评判者校准**：放量使用 LLM 评判前，先构建 100-200 案例的人工金标集，测量评判模型与人类的一致率（Cohen's kappa 剔除随机猜中成分，门槛如 >0.7），达到后才能大规模使用；评判模型或 Rubric 每次更新都需重新校准——没有这步，LLM 分数只是"另一个模型的意见"。**对抗式评审**：红队主动构造挑战案例（表面完美含隐蔽错误、关键词堆砌、利用已知偏见骗分）。

### LLM-as-a-Judge：自动化评估的核心

开放式任务没有标准答案可自动对比，人工评估又难规模化——LLM-as-a-Judge 在自动化规模与人类判断之间取得平衡。已知局限：**长度偏差**（倾向给更长回复高分）——防范三招：Rubric 显式惩罚冗长/规定长度上限、配对比较前把长度控制到相近、定期审计评分与长度的相关性（高分总伴随长回答就说明被带偏，需回炉 Rubric）。

**Rubric 四准则**（Scale AI，"Rubrics as Rewards"）：

1. **基于专家指导**——反映领域知识（医疗 Rubric 须含诊断标准与必须避免的医学错误），否则只能捕捉语言流畅度等表面特征；
2. **全面覆盖**——事实准确性/逻辑连贯/完整性/安全性，且明确**陷阱**（高风险常见错误，如推荐未经验证的疗法）；
3. **标准重要性权重**——必要项（Essential）/重要项/可选项/陷阱项，支持**一票否决（Veto）**（幻觉是典型否决维度，也防范关键词堆砌式奖励作弊）；
4. **自包含评估**——每项独立可操作，避免"展示了深刻理解"式抽象标准，改为"引用了至少两个权威理论并准确解释如何支持结论"式可验证标准。

用户记忆 Agent 的 Rubric 示例（测试问题"我女儿的儿科医生是谁？"，需跨两次对话关联"女儿叫 Lily"与"带 Lily 看了 Dr. Chen"）：

```yaml
dimensions:
- 事实正确性 (essential): 4=准确答出 Dr. Chen 且关联 Lily / 1=错误医生名
- 信息完整性 (important): 4=主动补充上次就诊时间等 / 1=关键信息缺失
- 思考正确性 (important): 4=正确关联两条跨会话信息 / 1=错误关联
- 幻觉检测 (veto): pass=所有信息可溯源 / fail=编造不存在的信息→总分归零
edge_cases:
- 多个女儿看不同医生时应追问是哪个女儿
- "Dr. Chen"和"陈医生"应识别为同一人
```

每档给出可验证的具体行为而非抽象描述。Rubric 是迭代产物——通过试用收集评价者分歧，从抽象准则演化为详尽判例集。要主动防范**奖励作弊（Reward Hacking）**：Agent 找到获取高分的捷径却没真正完成任务——明确惩罚幻觉、讨好用户、关键词堆砌、回避棘手问题。

**同源模型问题与多源评判**：Agent 与评判模型同家族时，Agent 会学会利用评判模型的偏好和盲点——古德哈特定律："当一个度量指标变成优化目标时，它就不再是好的度量指标"。缓解：**多源异构评判**——不同家族的多个 LLM 分别评判（Agent 用 Claude，评判用 GPT 和 Gemini），不同家族偏见正交、难以同时"欺骗"；同一 Rubric 保证评同一目标；部署期可单模型快速评估，定期用完整多源评判做质量审计。

**多模态 LLM-as-a-Judge** 四方向：TTS 评估（准确性/自然度/情感/音色一致——能发现 WER 捕捉不到的韵律问题）；ASR 评估（语义影响判断——"转账一千"识别成"一万"后果严重）；UI 评估（提议者-审核者机制查文字溢出、对比度）；视频剪辑评估（关键帧验证起止点与特效）。

### 配对比较与模型排名

**Elo 评分**（源自国际象棋）通过大量两两对决量化相对能力，统计基础是 **Bradley-Terry 模型**（每个模型一个潜在实力分，胜负概率由分差决定，Elo 是其在线更新形式）。分差 200（1200 vs 1000）预测强者胜率约 76%；爆冷带来更大的分数调整，使排名快速收敛。**Chatbot Arena** 用匿名随机对决 + 数百万次人类盲选——不需定义绝对标准，但排名取决于用户提了什么问题（都问编程题则编程强的模型排名偏高）。LLM 做配对评判时须防**位置偏差**（系统性偏向先出现的候选）：交换顺序各评一次取平均，或两次判决一致才计入；Chatbot Arena 随机化展示位置让偏差在大样本下抵消。配对信号也是后训练的来源：GRPO 对同一问题采样多个候选、用相对优劣估计优势，省去 PPO 的价值网络（注意省掉的是 critic 而非奖励信号本身）。

### 评估驱动的模型选型

**吞吐与延迟**：大模型推理分两阶段——Prefill（一次性读入完整上下文，决定**首字延迟 TTFT**，上下文越长越慢）与 Decode（逐 token 生成，决定出字速度与思考时长：50 tokens/s 的模型生成 2000 思考 token 要 40 秒）。关键指标：输入/输出吞吐量、TTFT（排队 + Prefill）、思考延迟（不同模型思考 token 数差数倍，且与效果不一定正相关——应在自己工作负载上实测）、**p95 尾部延迟**（比均值更反映真实体验——均值被大量快速请求拉低掩盖少数卡顿）、成本（便宜但成功率低的模型因频繁重试实际花费可能更高，算每任务平均成本与成本-性能比）、速率限制（RPM/TPM）与鲁棒性。Pass 指标的选型取舍：日常看 Pass@1；关键操作优先 Pass^k；探索性任务优先 Pass@k/Best@k；开放式任务用 Rubric。可采用**多模型协同**：轻量模型处理简单请求、强模型处理复杂任务，但需评估确认整体效益超过系统复杂度。

**Agent 系统的成本分析**（三层次，非线性增长）：

- **模型推理成本**：两个放大因素——上下文累积（每轮重发全部历史，无缓存时 1000+2000+3000=6000 而非 3×1000；KV Cache 可降 30%-60% 输入成本）；思考 token（不展示给用户但计费）。
- **工具调用成本**：外部 API 费用、沙盒资源，及易忽视的间接成本——工具返回注入上下文后**每轮反复计费**（一次网页搜索返回可占 2000-5000 token）。
- **基础设施成本**：向量数据库、消息队列、日志追踪存储。

示例（输入 $3/百万、输出 $15/百万，缓存读取按输入价 10%）：三轮调用 $0.022，无缓存约 $0.036——缓存省近一半输入成本。放大因素：思考模式可使成本翻 3-5 倍；工具返回 5000 token 网页则后续每轮付费；走弯路 10 轮则上下文累积到 20K+ token。**成本优化核心不在选便宜模型，而在控制轮次和上下文增长**：KV Cache 复用（保持前缀稳定）、上下文压缩、模型分层路由、异步批处理（批量定价折扣/波谷 GPU 利用率）、成本监控与预算控制（每任务成本上限，陷入循环时自动终止）。

**持续迭代**：模型选择不是一次性决策。案例：新模型公开基准更好且更便宜，但在自己评估集上测出"简单任务更优更便宜、复杂多轮编排成功率反降 5%"——确认超出噪声带宽后，决策是"简单任务迁移降本、复杂任务保留原模型"的差异化策略，而非盲目全量切换。选型是系统性权衡：更强的嵌入可能让 reranker 变多余，更强的主模型可能弥补检索不足——不是逐个挑最强。

### 评估结果的统计显著性

"数小时得出切换决策"的前提是分数差异是真实信号而非抽样噪声。**标准误**：n 个用例测得成功率 p，标准误 ≈ √(p(1−p)/n)。100 用例 70% 成功率 → 标准误 ≈ 4.6%，95% 置信区间约 ±9 个百分点；两个独立成功率相减的标准误约为单个的 √2 倍（约 6.5%，独立假设只是偏保守的口算上界）——"73% vs 70%"的 3 个点分差完全在噪声内，据此切换与掷硬币无异。

Agent 评估还有额外非确定性：同一模型同一数据集两次运行也会漂移（温度采样、工具返回波动、环境时序）——**单次运行的数字不应作为决策依据**，每个配置跑 3-5 次取均值并报告波动范围。

实用原则：分差小于噪声带宽时不做切换决策，但先换更灵敏的分析——同一批任务上的正确默认做法是**配对分析**（逐题比较、只看结果不同的用例，用 McNemar 检验思路），扣除"题目难易"这一共同噪声源后比独立相减灵敏得多；仍不确定再扩样本（标准误随 √n 缩小，100→400 才减半，成本很高）。反面推论：若预期收益只有 2-3 个百分点而评估集只有几十个用例，这套评估根本分辨不出改进是否有效——优先扩充评估集而非继续迭代 Agent。

**多重比较陷阱**：并行验证一批假设时假阳性概率迅速累积——6 个假设即便每个 95% 置信度，至少踩中一个假阳性的概率 = 1 − 0.95⁶ ≈ 26%。应对：按假设数收紧显著性阈值（Bonferroni 式），或对正向结论做独立验证性复跑，复现才采信。

### Agent 的可观测性

可观测性（借自分布式系统）：无法直接看系统内部，只能通过日志/指标/追踪数据推断。Agent 把它变得更难：同输入不同输出、多轮执行路径复杂、模型思考过程不透明。价值：问题诊断（回放全过程而非猜）、持续优化基础、成本管理（识别异常高成本案例，不同任务成本可差一两个数量级）、积累轨迹数据供后续改进。

数据基础是**追踪（Trace）**：一次任务一条 trace，每个 LLM 调用/工具调用/检索是一个 span（记录输入输出、起止时间、token 消耗、错误），父子关系构成执行树。已有标准协议：OpenTelemetry（通用分布式追踪）+ OpenInference（LLM 应用语义约定）——采集与分析解耦，避免被单一平台锁定。代表平台：LangSmith、Langfuse、Arize Phoenix（可观测性 + 评估 + 优化闭环；支持 A/B 测试、提示词版本管理、异步批量采集不影响延迟）。

最有价值的去向是**数据回流**：从生产轨迹筛出失败与可疑案例 → 脱敏 → 沉淀为评估集新用例和回归测试——评估集从静态集合变成随产品演化、贴近真实分布的活资产。挑战：数据量与隐私的权衡（每天数 TB）、因果归因复杂性、多 Agent 追踪、实时防护与事后分析的平衡。

## 经验与常见坑

**从 Benchmark 报告到系统改进**（示教案例，数据为假设值）。方法论：**观察→假设→实验→决策→迭代**。开跑前有一条铁律：**看到表现下降先检查评测系统本身**——资源不足被杀进程、评分器 bug、用例与生产脱节，在数字上与模型退化一模一样，只有审查完整轨迹才能区分。

读报告的关键是交叉分析**逐任务表格**与**能力标签矩阵**：总体成功率 88% 无意义，结构性短板才有价值——常规任务接近 100%（录音/拍照/联系人/文件操作），失败集中在少数区域；能力矩阵揭示共同特征：`transcription` 0%（视觉理解缺陷）、`math_counting` 0%（问题不在数学，在于能否识别需要计算并从界面提取数字）、`complex_ui` 17%（依赖标准化 UI 模式，遇非标准布局就崩溃）。

三层假设框架：**表层**（成本低、相互独立、可并行——H1 加导航提示、H2 加 UI 识别规则）；**中层**（H3 修复多模态输入管道——回放轨迹发现图片可能被丢弃或转文本，再强的模型也无从转录；H4 全局启用思考）；**深层**（验证成本高，条件化启动——H5 换更强视觉模型、H6 截图外增加 UI 元素树；可组成 2×2 对比实验回答"模型能力和信息丰富度哪个更关键"）。

决策不是采用所有有效改进：H1+H3 部署（低成本高收益，H3 修复的是架构性缺陷）；H4 拒绝（总体 88%→91%，但只有约 8% 任务涉及计数，为少数任务让全部任务承担 3 倍延迟成本是"杀鸡用牛刀"——不过它证明思考对计数有效，留作条件化启用的基础）；H6 优于 H5（H5 换 GPT-5 每步延迟 4s→15s 只提升到 35%，说明瓶颈不在模型思考而在输入信息是否充分；H6 用 30% token + 2s 换来 35 个百分点；H5+H6 组合最高 68% 但时长不可接受，只适合银行转账等关键异步任务选择性启用）；H2 面临可扩展性问题（为每个非标准应用写规则不可持续，只能临时）。实施 H1+H3+H6 后 88%→94%，新报告显示新的失败模式，催生 H7（条件化启用思考：任务开始前用一次快速 LLM 调用判断是否开思考）与 H8（扩展手势动作空间）。Benchmark 不是一次性考试，而是持续的能力体检（如每周跑一次）。

**生产级 Agent 的内部评估基础设施**（以 OpenClaw 为例，五个组件）：

1. **消融基础设施**：内置总开关同时禁用多个主要特性制造"裸模型"基线，回答"这个特性是真的改善了体验还是只是感觉有用"。消融开关必须在启动路径极早期注入（模块级常量捕获配置之前）——必须从第一天设计进架构。定期消融可发现"特性债务"（随模型进化已不再必要的特性）。每个主要特性都应可独立关闭。
2. **AB 测试方法论**：多臂而非二元（多个渐进式变体揭示剂量-效应关系）；**区分机制指标与目标指标**（最易犯的错——你在改变的东西（计划文件长度）不是你关心的东西（会话成本）：缩短计划可能因计划不够细导致更多编辑-检查循环反而增加总输出）；设置**护栏指标**（满意度下降/错误率上升即停止——"不能变差的底线"）；记录基线统计（样本量、分布百分位、相关性）。
3. **双层特性开关**：编译时开关把代码从产物中物理移除（内部特性外部构建中根本不存在，也是干净的消融机制）；运行时开关服务端下发 + 本地磁盘缓存（宁可读旧缓存也不能阻塞启动）。曝光事件每会话最多记录一次（避免污染实验数据）。特性开关不是调试工具，是一等公民级架构组件。
4. **提示词敏感性评估**：系统提示是核心"代码"却常缺版本控制和回归测试。实践：提示词可确定性渲染（相同配置输入永远相同输出）、版本化快照（能提取任意 git 版本渲染后的最终提示文本）、每次变更在评估集上跑回归测试（像代码变更跑 CI）。
5. **隐私感知的分析**：分析接口只接受特殊类型包装的值，类型名本身即审计线索（"我已验证这不是代码或文件路径"）——隐私约束从文档规范变成编译时强制的类型检查。隐私和评估不对立：隐私感知设计迫使你想清楚真正要度量什么，反而催生更精准的指标。

外部评估告诉你"Agent 有多好"，内部评估告诉你"哪个改变让它变好了"。

### 仿真环境：从评估到后训练的桥梁

当目标从"评估现有能力"扩展到"培养新能力"（后训练），评估环境演化为仿真环境：交互频率远高（数百万次 vs 数千次）、需要随机化（防死记硬背）、必须即时反馈。桥梁两端：定义清晰的 Rubric 或验证器本质上就是**可验证奖励（RLVR）的奖励函数**——判分脚本直接就是奖励脚本；但训练提出新要求：**可靠的 reset 语义**（每个 episode 都能重置到确定干净的初始状态，否则梯度信号被残留状态污染）与**远高于评估的吞吐**（并行度和单实例开销决定训练是否可行）。

**保真度谱**（从低到高）：AWorld（单元测试级：为 GAIA 构建 MCP 沙盒，26 个服务器 126 个工具函数，可重放可审计；分布式架构把串行 7695s 缩到 525s，14.6 倍加速）→ MCP 沙盒/AndroidWorld（真实应用任务，可扩展）→ Isaac Gym（GPU 并行千级实例，精度略妥协）→ RoboTwin2（物理引擎双臂操作，完美保真但单实例 CPU、不可重置）。具身环境通过**动作分块**（一次规划多个连续动作）实现实时控制。**保真度权衡与领域随机化**：高保真利于迁移到真实世界但开销大；适度随机化提升泛化、过度随机化让任务过难。**领域随机化**（Domain Randomization）是缩小 sim-to-real gap 的关键——在物理参数、视觉外观、传感器噪声上大范围随机（在各种光照角度下都练过抓取，真实环境不会因光线变化失手）；数字环境的 sim-to-real 表现为界面渲染和响应时间差异，可用延迟和失败随机化缓解。仿真环境同样需要隔离执行环境与虚拟身份机制（见 [工具](06-%E5%B7%A5%E5%85%B7.md)）。

## ⚠️ 时效性说明

- 文中模型名与分数（GPT-4 在 GAIA 的 30.3%/9.7%/0%、Claude/GPT-5/Gemini 2.5 对比、"Claude 4 Sonnet" 等）均为写作时点数据，模型迭代极快，仅作方法论示例。
- OSWorld-Verified 的修复统计（300+ 问题、50 倍加速）与 SWE-Bench Verified 的 500/29% 通过率为发布时点事实。
- Elo 排行榜数字、缓存定价折扣比例（如 Anthropic 缓存写 1.25 倍/读 0.1 倍）会随厂商调整变化。
- 多重比较、McNemar 检验等方法本身稳定有效，不受模型演进影响。
