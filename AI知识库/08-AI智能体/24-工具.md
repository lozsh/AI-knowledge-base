# 工具

<p class="note-date">更新于 2026-11-03</p>

**一句话定义**：工具是连接 Agent 语言"大脑"与真实数字世界的"手脚和感官"——工具设计的质量决定 Agent 的能力上限，而事件驱动的异步架构决定 Agent 能否在真实世界中可靠运行。

本章（原课程第 4 章）围绕两个核心挑战展开：**工具选择**——当数千个工具的说明文档足以撑爆上下文窗口时，Agent 如何准确高效地找到所需的那一个，如何从被动"选择"进化为主动"发现"；**异步与事件**——Agent 如何管理耗时任务、处理随时到来的中断、响应多渠道外部事件而不陷入同步等待。工具设计与异步架构也是 Agent 自我进化（[51-自主智能体设计方法论](51-自主智能体设计方法论.md)）的前提。

## 分类/类型

五类工具按调用方向与作用对象定位（两列不构成交叉分类，仅助记）：

| 工具类型 | 调用方向 | 作用对象 | 例子 | 设计关键 |
|---|---|---|---|---|
| 感知工具 | Agent 主动调用 | 获取信息 | web_search、read_file、grep_file | 粒度权衡、输出信息量控制 |
| 执行工具 | Agent 主动调用 | 改变世界 | shell_exec、write_file、send_email | 安全约束（错误代价极高） |
| 协作工具 | Agent 主动调用 | 驱动其他 Agent 或人类 | spawn_subagent、request_human_approval | 上下文管理、HITL |
| 事件触发工具 | Agent 注册、外部触发 | 驱动 Agent 开始执行 | set_timer、monitor_shell、connect_channel | 触发条件过滤、载荷上下文 |
| 用户沟通工具 | Agent 主动调用 | 向用户传递信息 | reply_to_user、send_card_to_user | 异步消息、多渠道召回 |

## 核心原理

### 能力表达形式：专用工具还是 Skill + 通用执行器

Agent 能力有两种基本形态：**专用代码工具**（结构化函数调用，确定性高可测试，但每个占数百 token、数量膨胀破坏 KV Cache）；**Skill + 通用执行器**（自然语言文档描述流程，经终端/代码解释器执行，少量通用工具覆盖大量场景——如"部署应用"Skill 写三步命令，Agent 用 bash 逐步执行）。选择看三个维度：

- **参数复杂度**：嵌套对象、多字段联合校验的操作适合专用工具的 schema 引导；参数简单用 CLI 同样可靠。
- **变更频率**：频繁变化的能力用 Skill 维护（改文本远比改代码轻松）；稳定底层操作做专用工具。
- **模型能力**：SOTA 模型可用 Skill + 通用执行器表达更多能力；弱模型需要结构化 schema 引导。

### 工具粒度与通用性

- **粒度**：过细导致数量激增增加选择负担（超 100 个工具时最先进的模型也易选错），过粗使单工具过于复杂。整合标准是功能相似性与场景重叠度——extract_pdf_text/extract_docx_content/extract_pptx_content 应统一为 read_document（file_type 参数区分），降低认知负担、便于扩展；但参数形态和延迟特性差异大的（图片 OCR vs 视频关键帧）不应强行合并。
- **通用性**：通用优于专用，除非有明确的安全/权限/性能理由。一个沙盒中的 code_interpreter 可代替数十个特定工具（如四则运算计算器），还能处理未预料的边缘场景——LLM 有代码生成能力，应利用而非限制。例外：跨平台语法不一致的 grep、需精细权限控制的生产数据库写操作，仍需专用工具。

### 工具描述的艺术

核心是让 LLM 知道"**什么时候用**"而非只"能做什么"（"当需要获取实时信息或查找未知事实时使用" 优于 "搜索相关内容"）。**边界同样重要**：明确列出做不到什么、不接受什么——大多数调用失败的根因不是模型不知道工具能做什么，而是不知道它不能做什么。参数描述用具体例子代替抽象规范（"timestamp：RFC3339 格式，例如 2024-03-15T14:30:00Z"；"phone：E.164 格式，如 +8613888888888"）——复杂任务中确认参数格式只占注意力一小部分，例子可直接套用。返回值说明结构（"返回 JSON 数组，含 title/url/snippet"）；耗时工具注明代价（"大型网站 5-10 秒；只需元信息请用 get_page_metadata"）。更进一步为每个工具附 1-5 个真实调用示例——JSON Schema 表达不了调用方式和典型参数组合（时间戳是秒还是毫秒），示例可让调用准确率从约 72% 提升到 90%（因任务而异）。**调试原则**：Agent 频繁选错工具时优先检查描述而非怀疑模型——修正描述的投入产出比通常远高于换更强的模型。

### 参数传递的保真性（底线原则）

两种比功能缺失更隐蔽的反模式：

- **静默输入转换**：工具悄悄"修正"模型输入。案例：某版 Cursor 的编辑工具把中文弯引号静默转换为直引号——模型读文件看到弯引号、原样传入 old_string，参数层已转换导致"未找到匹配"，模型反复失败且无法自行诊断；写方向同理，写入内容被篡改。
- **静默参数注入**：工具在模型不知情时追加参数。案例：某 IDE 的 bash 工具给所有 git commit 自动附加标记参数，旧版 Git 不支持导致报错，模型改措辞、改参数都无效。

底线：**模型感知到的世界与工具操作的世界之间不能存在系统性偏差**。确需规范化处理必须在描述中说明并在返回中告知。

### 工具设计的演进三阶段

第一代：直接 API 封装（每个端点一个工具，粒度过细）。第二代：**ACI（Agent-Computer Interface）原则**——工具应对应 Agent 的目标而非底层 API 操作（对标 HCI，核心是让工具对 Agent 而非对人友好），前述粒度/通用性/描述规范属此。第三代：优化工具被调用、串联和发现的方式——"如何被准确调用"靠示例驱动，"如何被发现"靠动态工具发现，"如何被串联"靠**代码编排执行**：LLM 一次性生成脚本，中间变量留在执行环境，只有最终结果返回上下文（比喻：传统方式每做一步就"写邮件汇报"等领导回复；代码编排是领导一次写好操作手册，照做即可）。抓多网页批量提取字段时整页内容不进上下文，token 消耗可降约两个数量级。

## 关键概念

### MCP 协议与工具生态

Model Context Protocol（Anthropic 2024 年底发布）统一 AI 模型与外部工具/数据源的通信协议——好比给工具生态制定通用"插座标准"（此前 OpenAI function calling、Anthropic tool use、LangChain Tool 各不相同，开发者需重复适配）。架构与要点：

- **客户端-服务器**：MCP 服务器暴露工具，客户端（Agent 框架/IDE）经标准协议通信。工具用 JSON Schema 描述输入参数。
- **传输层**：本地 stdio、远程 Streamable HTTP（⚠️ 早期 SSE 方案已弃用）。
- **三类原语**：工具（模型可执行的操作）、资源（应用可读取的只读数据——区分"获取信息"与"执行操作"）、提示模板（用户可选用的模板）。
- **生态价值**：一次开发处处可用，一个服务器可被 Cursor、Claude Desktop 等任何兼容客户端使用。

MCP 实践中的三个递进挑战：

1. **同步调用的限制**：工具调用主体仍是请求-响应式。协议已有扩展原语——资源更新通知（notifications）、执行进度（progress）、采样（sampling，服务器反向请求客户端模型）、征询（elicitation，执行中向用户补要输入）——但都作用于保持连接的单个会话内，无法唤醒未运行的 Agent。跨会话、多事件源、离线唤醒的事件驱动架构需在协议之上分层构建（MCP 管单次调用标准化，框架管调度/并发/事件源）。
2. **上下文开销**：仅 5 个 MCP 服务器就可能引入约 55,000 token 的工具定义开销（200K 窗口近三成）。Cursor 的缓解方案：工具描述同步到文件夹，Agent 默认只见工具名索引、需要时再查定义——A/B 测试总 token 消耗减少 46.9%。层次化组织也有效（按信息源性质分搜索/读取/解析/查询四类，系统提示词显式说明分类）；更进一步是动态工具发现——Anthropic 实验显示按需检索使 Opus 4 工具基准准确率从 49% 升到 74%。MCP 解决互操作，Skills 解决选择过载——把"工具选择"转化为"知识检索"。
3. **信任模型与安全风险**：每接入一个 MCP 服务器 = 把一段不受控文本注入上下文 + 交出一份凭证。四类风险：**工具描述投毒**（description 原样进上下文夹带指令，是提示注入的变种、每次会话生效）；**恶意/被劫持服务器**（供应链攻击，更新引入恶意行为）；**同名工具遮蔽**（恶意服务器诱导 Agent 把发给可信服务器的调用连敏感参数路由到攻击者）；**凭证管理**（OAuth token/API key 被诱导滥用）。缓解：接入前把 description 当不可信输入审计、锁定版本拒绝静默更新、每服务器最小权限凭证；运行时由 Sidecar 作最后防线。评估整体风险可用 Simon Willison 的**致命三要素**：访问私有数据 + 暴露于不可信内容 + 对外通信能力，三者齐备即成完整攻击闭环；持久记忆会进一步放大跨会话影响。

### 感知工具设计

常见挑战是返回信息量远超处理能力（一次搜索数万字符、PDF 上百页）——在工具层集成上下文感知压缩（超阈值如 10000 字符时基于查询意图自动压缩）。各项要点：

- **搜索类**：返回结构化候选列表（标题、位置、摘要）而非全文拼接，让 Agent 先浏览再决定深入；结果多时提供分页/游标，注明总数与获取下一页的方式。
- **读取类**：支持 offset/limit 按需读片段；截断必须显式可见（"已显示第 1-200 行，共 5000 行，可用 offset 继续"）——**静默截断是危险的**，Agent 会误以为看到全部。
- **只读红利**：结果可安全缓存，多个感知调用可放心并行；执行工具无此自由。
- **多模态输出形态**：直接返图像（保留布局细节、耗 token）vs 转文本（精简、丢空间结构如表格行列关系）。按内容选择：纯文字用提取，布局敏感内容（UI、复杂表格、设计稿）保留图像。

### 执行工具设计

执行工具错误代价极高（误删不可恢复、错误命令致服务中断、API 调用产生真实财务损失），设计核心是在能力开放与安全约束间平衡。

**层次化安全防护**：① 输入验证——检查路径遍历（../../etc/passwd）、命令注入（分号/管道拼接）、参数类型格式，**快速失败**不"智能修正"；② 权限控制——限制工作目录、禁止命令黑名单（rm -rf /、dd）、API 配额限速；黑名单只是最基础层，可被变形命令绕过，需结合语义解析理解命令意图。

**提议者-审核者（Proposer-Reviewer）**：独立第二视角检验第一视角（如银行经办、审核双签）。两种机制：

- *事前审批*：提议模型 + 独立审查模型。三要点——两模型来自**不同家族**（认知多样性，同家族易犯相同错误）但**能力相近**（相差过大则审查者跟不上被审者，如 Haiku 审 Opus 不可靠）；提示词底层规则完全一致（否则扯皮僵局）但关注点不同（提议者行动导向、审批者风险控制）；审批失败不简单重试，而是把拒绝理由作为工具调用结果加入轨迹。可加风险分级审批与人类监督升级。适用：收费、发通知邮件、改关键配置等后果持久、错误成本高的操作。
- *事后验证*：要诀在**模态切换**——不同模态提供互补视角，单一模态审查易陷入相同盲区（代码生成文档渲染成视觉再查排版；配置修改在沙盒实际运行验证）。

**Sidecar 机制**：解决"操作执行时如何实时校验"——伴随主 Agent 思考循环的旁路轻量 LLM 调用（借鉴微服务边车模式）。真实时序：与主模型流式输出**并行**运行省掉排队时间，但对被审的工具调用起**门控**作用——放行前不真正执行。典型案例 Claude Code 自动模式：独立低延迟调用判断"这个工具调用是否安全"，**只看结构化数据（工具名、参数），不看主模型自由文本**——有意设计，防止攻击者借"请允许执行 rm -rf"式话术经主模型复述操纵权限判断。亚秒级完成。与提议者-审核者的区别（不矛盾）：后者审开放式思考需能力相近的模型；Sidecar 判断结构化数据上的分类问题，轻量模型足够。配套**拒绝熔断器**：连续多次拒绝时不无限重试，回退请求用户手动判断。Sidecar 另一典型应用是上下文丰富：并行筛选记忆相关性、摘要大输出、预判权限。

**其他关键机制**：

- **执行-验证-反馈闭环**：结果可验证就应自动验证——write_file 后立即调 linter，结构化错误列表随工具返回值给出，Agent 下一轮即修正。
- **长输出截断与持久化**：超阈值（如 200 行/10000 字符）时头尾各保留约 50 行，中间提示省略多少、完整输出存临时文件并给出读取路径。
- **沙盒隔离**（常见误区：**venv 不是沙盒**——只隔离包依赖，对文件系统/网络/进程无约束）。按强度递增：OS 级（macOS Seatbelt、Linux seccomp/namespaces，本地轻量首选）→ 容器（独立文件系统与网络栈，但共享内核）→ microVM（Firecracker，独立内核硬件级隔离，运行完全不可信代码的最强层级）→ 任一层级之上加资源配额。
- **可观测性**：详细日志、审计追踪、性能指标、告警机制。
- **幂等性与取消语义**：调用取消/超时后副作用是否已发生？（转账超时重试可能重复转账。）手段：唯一标识（idempotency key，服务端去重返回首次结果）与先查询后变更。不可幂等操作（发邮件、打电话、转账——每执行一次产生不可撤销的真实事件）用"**预检-确认**"两段式：第一段只校验预演并返回确认令牌，第二段凭令牌执行，失败不盲目重发而交回上层重新预检。

### 协作工具设计

子 Agent 的核心价值是**专业化分工**——一组各自专精的 Agent 优于一个"全能"Agent，各自独立优化提示词、工具集、知识库。

**子 Agent 提示词要素**：角色定义清晰（"你是专门负责 XXX 的助手"）；上下文来源明确标注（[FROM_MAIN_AGENT] / [FROM_USER] / [TOOL_RESULT]——防混淆来源、防提示注入）；任务边界明确（什么转交或上报）；输出格式标准化（统一 JSON 降低主 Agent 解析负担）。

**上下文传递四策略**（按复杂度递进选择）：

| 策略 | 做法 | 优劣 | 适用 |
|---|---|---|---|
| 最小化传递 | 只传调用参数 | 零上下文、保护隐私，但可能信息不足 | 简单高频（查天气、计算器） |
| 手动筛选 | 主 Agent 显式指定共享内容 | 可控，但设计复杂 | — |
| 自动裁剪 | 规则自动筛选（用户信息+最近3轮+相关工具结果） | 平衡，需预定义规则 | 中等复杂度（默认方案） |
| LLM 生成 | 额外一次调用动态生成结构化上下文（可含隐私规则"不传支付信息"） | 最智能，多一次调用开销 | 复杂任务（报告、客服） |

在 spawn/send_message/cancel 原语之上可承载：同步调用、异步调用（返回任务 ID，完成时事件通知）、流式协作、多轮交互。

**HITL（Human-In-The-Loop）**：关键决策点仍需人类介入。需要超时阈值与默认行为（"5 分钟无响应采用保守策略"）、优先级队列（紧急多渠道通知、普通只发邮件）。HITL 应形成**学习循环**：记录批准/拒绝及理由——后训练（构建监督数据集内化决策模式）或外部化学习（决策案例结构化入库，新决策时检索相似案例，优势是可解释——可引用"根据类似情况（案例 ID 123）的决策"）。

### 事件驱动的异步 Agent

**为什么需要异步**：同步架构像只会排队的柜台，真实助理场景需要：异步执行常态（长任务不阻塞交互）、事件优先级动态判断（取消/入队/并行三种策略）、中断恢复流畅性。根本矛盾：**LLM 训练范式假设同步**（发出工具调用后下一条必须是工具结果），**真实部署要求异步**（用户随时打断、任务并发、事件提前到达）——"训练同步/部署异步"贯穿本节所有工程取舍。

**从 OpenClaw 看现实需求**：OpenClaw 的 Gateway 提供三种内置自动化——Hooks（生命周期事件钩子，类似 GitHub Actions 触发器）、Cron（定时调度，如 0 9 * * 5 每周五 9 点）、Heartbeat（每隔 N 分钟唤醒检查）。但三者都是**时间驱动**，对内置渠道之外的第三方事件源（新邮件、API 回调）缺乏即时接入通道。案例 PineClaw（代用户打真实电话的 AI 助手：协商账单、取消订阅、保险理赔）：通话中随时需要用户介入（OTP 验证码、三方通话、降价方案确认），5 分钟心跳轮询会导致客服挂断通话；秒级轮询又浪费资源。解法是 **Channel 机制**——Gateway 与 Pine API 之间建实时事件通道，关键事件即时推送，响应从分钟级降到秒级。启示：真正的"主动服务"不仅需要 Agent 能定时检查世界，更需要**世界能主动通知 Agent**。

**事件触发工具**三类：set_timer（一次性——"下周一上午 10:00 致电 DMV"；循环——每小时查服务器健康；外部服务只支持主动查询时用循环定时器反复查询，Heartbeat 即其系统化）；monitor_shell（监控后台长任务的新增输出或特定关键词，避免反复轮询耗 token 或卡死无法介入）；connect_channel（新邮件/API 回调/IM 消息实时推送）。设计要点：触发条件与过滤规则清晰（避免无关事件浪费算力），载荷含足够上下文（减少唤醒后额外查询）。

**用户沟通工具**：传统 Agent 的 assistant 消息直发用户、须打开指定 session 对话；OpenClaw 让 session 对用户透明，双方随时互发消息（"活人感"，像秘书异步沟通），消息经专门工具发送、可带附件和推送提醒。还有结构化卡片、生成式 UI（HTML 交互界面）。类别边界：通知审批者/协作者归**协作工具**，通知最终用户本人才是**用户沟通工具**——区别不在渠道在"通知谁、为什么"。通知机制同时是**用户召回机制**：按紧急程度、用户状态、内容性质、偏好综合选渠道（IM/短信/邮件/电话/推送），长任务完成时主动召回注意力，定期任务帮用户建立交互习惯。

**虚拟身份与隔离执行环境**：直接管理用户个人账号一旦出错/被攻破则全部数字身份暴露；更稳妥是给 Agent 独立虚拟身份（专属通讯账号、存储空间、计算环境——如秘书有自己的办公电话）。落地在虚拟电脑（VM/容器）与虚拟手机（Android 模拟器）：OS 级隔离、操作可追溯可审计——沙盒思想在"数字身份"维度的延伸（沙盒隔离代码执行，虚拟电脑隔离整个数字身份）。两个现实挑战：反自动化机制（CAPTCHA、IP 信誉检测——常需住宅代理）；必须以用户本人身份登录时用 **HITL 认证**——VNC/RDP 远程桌面让用户亲见 Agent 操作界面并亲自登录，会话令牌有效期内复用。主 Agent 与虚拟环境经共享文件系统交换数据：卷挂载 + 路径引用传递而非内容拷贝（避免占上下文窗口）。

**事件处理机制**。结构化事件建模四维度：来源（用户/联系人/陌生人/系统）、渠道（电话/短信/IM/邮件/定时器/工具结果）、内容（文本/情感/紧急度/是否需回复）、上下文（回复还是新沟通、与当前任务关联）。只有维度清晰建模，Agent 才能在多方通信中不把用户输入误当工具结果、不把藏指令的工具结果误当用户指令（提示注入防线）。基于紧急度的三种动态策略：

- **取消式**（紧急事件，如用户喊停）：停当前操作（取消流式响应/发取消信号）→ 清空队列 → 队列事件与紧急事件一起追加轨迹 → 立即以完整轨迹重调 LLM。
- **队列式**（常规事件）：入队不打断 → 当前操作完成后一次性批量追加 → LLM 综合处理（如搜索等待期间用户补充"只看最近一个月"，与搜索结果一起呈现，避免往返）。
- **并行处理**（独立的轻量查询，如分析大数据时问天气）：与主任务无关、需快速响应、成本低——在并行推理会话中独立执行后立即返回，结果追加主轨迹并标记"与主任务并行"。

紧急度判定：紧急 = user.interrupt、supervisor.instruction、agent.interrupt、标记紧急的外部触发；非紧急 = 常规输入、工具结果、定时器、常规外部触发。硬编码规则有局限（语义决定策略），建议用轻量分类 LLM 作事件路由器。

**工程实现：让同步模型支持异步打断**。核心思想：常态下让 LLM 看到标准同步轨迹，只在打断时插入占位符修复格式。五条规则：① LLM 输出时立即记录 assistant message；② 工具完成时才记录 tool result；③ 工具执行中被打断 → 为未完成工具生成占位符响应（"工具正在后台执行，请优先处理新事件"）再追加打断事件重调 LLM——LLM 视角里配对完好；④ LLM 思考中被打断 → 直接丢弃当前思考不写轨迹；⑤ 非打断事件入队等待批处理。**风险**：占位符可能加剧幻觉——模型从未学过"结果还没回来"的情况，可能编造工具结果并基于虚构数据决策，因此实践中只在真正紧急时打断。**配套**：异步工具接口设计——把"启动"与"完成"解耦（initiate_phone_call 立即返回任务 ID，进展经 phone_call_connected/ended 事件通知），名称和描述本身传达异步语义；队列式批处理的**注意力分散**问题（模型只关注最后一个事件）——状态栏标记 [未处理事件 1/4] + 末尾汇总提醒覆盖全部。

**深层矛盾与未来方向**：占位符、异步接口、状态栏都是用提示工程弥补训练不足的过渡方案。根本解法是下一代模型在异步环境中经强化学习获得三种能力：理解轨迹中事件的异步穿插（哪些调用还在等结果、哪些思考是未完成片段）、恢复被打断的任务和思考（不幻觉以为工具已完成）、批量事件综合处理。方向参照：机器人 VLA 模型已面对感知-动作延迟问题。近期进展（NeverStop Thinking，2026 待发表）：用约两百行薄编排就能让现成思考模型变成"持续思考"Agent——随时合上正在写的 think 块、把新观察作为普通消息注入接着解码，利用"等待"这段白赚的算力长出**边等边想**（不等工具返回就基于半截信息提前思考甚至抢先调用下一步工具）与**边做边想**；但训练信号是关键——用"LLM 当裁判"式奖励训练，模型学会把思考藏起来换好评、客观指标反而更差，只有可验证、保信息覆盖度的目标才带来实收。一句话：编排让行为成为可能，训练让行为变好。

### 主动工具发现

工具从十几个增长到成百上千后，全量注入 schema 迅速失效（上下文被"工具说明书"塞满，选择精度下降）。检索预筛选按初始查询做一次性匹配，但 "Debug the file" 这类请求实际牵出多步骤跨领域工具链，任务开始时无法预见所有需求。

**主动发现**：Agent 在执行中意识到能力缺口时，主动用自然语言声明"我需要什么能力"，系统动态匹配注入。代表工作 MCP-Zero（arXiv:2506.01056）：系统提示词不预置工具 schema，Agent 生成结构化请求块，两层语义路由（服务器级→工具级）从数千候选匹配，约 2800 个工具上比全量注入节省约 98% token。工程等价方案：系统提示词只留少数基础工具（web_search、code_interpreter）+ 一个"工具搜索工具"（如 Anthropic 的 Tool Search Tool）。层次化匹配：先按能力描述定位服务器（手机 App 比喻），再在服务器内匹配具体工具，把搜索空间从"数千工具"缩为"数十服务器 × 每个数十工具"；候选相似度低于阈值应明确返回"未找到"，让 Agent 改写需求、用基础工具手工实现或创造新工具。

**KV Cache 优化**：动态加载工具会破坏 KV Cache——若全部工具定义在静态前缀，每加载一个新工具整段缓存失效。破解：把变动的部分（新工具完整 schema）追加到上下文末尾，静态前缀保持稳定，Agent 状态栏维护简短工具名列表（朴素方案缓存命中率约 0% vs 优化后约 95%，首 token 延迟从重算 50K token 降为增量约 200 token）。现已是主流 API 原生能力：OpenAI Responses API 的 tool_search + defer_loading:true（schema 以 tool_search_output 追加）、Claude Code 的 MCP 工具默认延迟加载（tool_reference blocks）、Codex CLI 的 tool_search（BM25）默认开启。**易误解点澄清**："追加到末尾"只发生在工具被发现的那一轮——此后 schema 块固定在轨迹原位置成为普通历史消息，后续轮次命中缓存；真正导致重算的只有 Prompt Cache TTL 过期和修改/移除/重排已加载工具集。代价是"工具定义必须在上下文最前面"不再成立，模型须在后训练中学会理解散落各处的工具定义（弱模型需强化学习专门训练）。

**Skills：把工具发现变成"按需查阅"**。Skills 机制（渐进式披露）换了一种更轻的思路——不需要嵌入索引 + 语义匹配的基础设施。Agent 启动只见薄目录（每个 skill 的 name + description，合计数百 token），上下文真需要某能力时才读 sub-skill、顺引用再往下一层。像查工具书或维基百科：没人整本通读，而是顺索引按需查词条。Agent 靠通用文件阅读能力（grep、read_file）翻目录即可。KV Cache 方面：加载 sub-skill 同样可放末尾复用前缀；但 Skills 会被跨会话、跨用户反复加载，"可编辑、可组合的 KV Cache"（arXiv:2606.17107）把每个 skill 的 KV 表示预编译缓存一次，用 RoPE 重定位"粘贴"到任意位置（O(L) 而非 O(L²) 拼接），小改动可"勘误笔记"式增量修正——skill 从"每次重新 prefill 的文本"升级为"可复用可组合的缓存对象"。

**实验结论**：用 Qwen3-4B 访问 120+ 工具的对比——全量注入（超 50K token）时 4B 模型指令遵循严重退化（查股价错选 Web Search、"忘记"列表中的工具）；主动发现方案（基础工具 + discover_tools 元工具 + schema 追加 + 状态栏）准确率和完成率显著提升。主动发现不仅帮大模型应对数千工具，更让小模型在上百工具场景保持可用。

## 经验与常见坑

- Agent 频繁选错工具：先查工具描述（边界不清、缺反例、参数模糊），别急着换模型。
- 静默截断、静默转换、静默注入是三类"工具好心办坏事"的反模式——一切对模型不可见的处理都会制造无法自行诊断的故障。
- venv 不是沙盒；黑名单可被变形命令绕过；同家族模型互审易犯相同错误——三条都指向"表面防护不可靠"。
- 非紧急事件不要打断（占位符有幻觉风险），入队批量处理；只在真正紧急时打断。
- 工具定义别放静态前缀再动态改——追加到末尾保 KV Cache。
