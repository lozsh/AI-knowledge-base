# 智能体性能评估

> 来源：HelloAgents 课程第十二章（更新于 2026-11-03）

**一句话定义**：智能体性能评估是用标准化基准（Benchmark）、指标和评分方法，客观量化智能体在工具调用、通用任务、数据生成等维度上能力的工程实践。

构建智能体系统后必须回答三个问题：它是否具备预期能力？在不同任务上表现如何？与其他智能体相比处于什么水平？评估的价值在于：用具体数字量化表现、客观比较不同设计方案（如优化提示词或更换 LLM 后是否真的有改进）、及时发现特定场景弱点、向用户证明可靠性。

与传统软件测试不同，智能体评估有三大独特挑战：

1. **输出不确定性**：同一问题可能有多个正确答案，难以用简单对错判断；
2. **评估标准多样性**：不同任务需不同方法——工具调用查函数签名，问答任务评语义相似度；
3. **评估成本高昂**：每次评估需大量 API 调用，成本可达数百元甚至更多。

应对方案是使用学术界/工业界提供的标准化基准：统一的数据集、评估指标和评分方法，使不同智能体系统可在相同标准下对比。

## 关键概念：主流评估基准与指标

### 基准概览

**工具调用能力**：
- **BFCL**（Berkeley Function Calling Leaderboard，UC Berkeley）：1120+ 测试样本，覆盖 simple / multiple / parallel / irrelevance 四类，用 AST 匹配算法评估，规模适中、社区活跃；
- **ToolBench**（清华）：16000+ 真实 API 调用场景；
- **API-Bank**（Microsoft Research）：53 个常用 API 工具，专注 API 文档理解与调用。

**通用能力**：
- **GAIA**（General AI Assistants，Meta AI + Hugging Face）：466 个真实世界问题，分 Level 1/2/3 三档难度，评估多步推理、工具使用、文件处理、网页浏览，用准精确匹配（Quasi Exact Match）；
- **AgentBench**（清华）：8 个不同领域任务；
- **WebArena**（CMU）：真实网页环境中的任务完成与交互能力。

**多智能体协作**：ChatEval（多智能体对话质量）、SOTOPIA（社交场景互动）、以及按应用场景自定义的协作评估。

### 常用评估指标

| 类别 | 指标 | 衡量内容 |
|---|---|---|
| 准确性 | Accuracy / Exact Match / F1 Score | 答案正确性 |
| 效率 | Response Time / Token Usage | 执行效率 |
| 鲁棒性 | Error Rate / Failure Recovery | 容错能力 |
| 协作 | Communication Efficiency / Task Completion | 协作效果 |

## 核心原理一：BFCL 与 AST 匹配

BFCL 评估智能体完成四类任务的能力：理解任务需求（从自然语言提取关键信息）、选择合适工具、正确构造函数调用（函数名+参数）、处理复杂场景（多函数/并行调用）。四个评估类别难度递增：Simple（单函数）→ Multiple（多函数）→ Parallel（并行调用）→ Irrelevance（判断是否根本不需要调用函数）。

### AST 匹配算法

核心思想：把函数调用解析为抽象语法树，比较树的结构与节点值，而非简单字符串匹配。形式化定义：预测 P 与标准答案 G 匹配，当且仅当 `AST(P) ≡ AST(G)`，匹配结果记 1，否则记 0。

两个语法树等价需满足三个条件：
1. **函数名精确匹配**（`get_weather` ≠ `get_temperature`）；
2. **参数键值对集合相等**（忽略顺序：`f(a=1, b=2)` ≡ `f(b=2, a=1)`）；
3. **参数值语义等价**（`f(x=2+3)` ≡ `f(x=5)`；`f(s="hello")` ≡ `f(s='hello')`）。

多函数场景：函数数量必须相同、每个调用都必须匹配，但调用顺序可以不同（集合匹配）。

```python
def _ast_match(self, pred_call, true_call) -> bool:
    # 1. 函数名必须完全匹配
    if pred_call.get("name") != true_call.get("name"):
        return False
    # 2. 参数字典 → 构造虚拟函数调用 → 解析为 AST Call 节点
    pred_args = self._args_to_ast(pred_call.get("arguments", {}))
    true_args = self._args_to_ast(true_call.get("arguments", {}))
    # 3. 比较 AST 序列化结果
    return ast.dump(pred_args) == ast.dump(true_args)
```

### BFCL 评估指标

- **准确率（Accuracy）**：核心指标，= AST 匹配成功样本数 / 总样本数；
- **AST 匹配率**：与准确率同值，强调使用 AST 算法；
- **分类准确率**：每个类别单独计算；
- **加权准确率**：按类别难度加权（权重和为 1）；
- **错误率** = 1 − Accuracy。

例：simple 95%、multiple 82%、parallel 68%，等权加权准确率 = 0.817。

### 数据集与评估流程

BFCL 数据集为 JSON 格式，每个样本含 `question`（自然语言请求）、`function`（可用函数签名与描述）、`ground_truth`（期望的函数调用）。评估流程：加载数据集选类别 → 运行智能体获取预测 → 预测解析为 AST → AST 匹配判分 → 汇总指标生成报告。

数据获取推荐从官方 GitHub 仓库克隆（gorilla 仓库的 berkeley-function-call-leaderboard 目录，含完整 ground truth，可直接用官方脚本，支持 v4 最新版本）。

### HelloAgents 三种使用方式与官方工具集成

1. **BFCLEvaluationTool 一键评估**（推荐）：自动完成加载、评估、导出、官方评估、报告；
2. **命令行脚本**：适合批量评估/CI/CD 集成（参数 `--category` / `--samples` / `--model-name`）；
3. **Dataset + Evaluator 直用**：最大灵活性，适合深度定制。

与官方评估集成的四步流程保证结果与排行榜一致：HelloAgents 评估取预测 → 导出 BFCL 官方格式（JSONL）→ 复制结果到 `result/{model_name}/` → 运行 `bfcl evaluate --model xxx --test-category xxx --partial-eval`。

### 组件实现模式（可复用的评估系统三层架构）

- **Dataset（数据层）**：加载数据，本地优先、找不到再从 HuggingFace 加载；
- **Evaluator（评估层）**：核心 `evaluate()` 循环——构造提示词 → 调用智能体 → 从响应提取函数调用（支持 JSON / Python 代码块 / 纯文本多种格式）→ 与 ground truth 做 AST 对比；
- **Metrics（指标层）**：计算 accuracy、ast_match_rate、parameter_accuracy、f1、分类统计；
- **Tool 封装**：继承 Tool 基类，严格参数校验，返回 JSON——可被智能体直接调用。

### 提分方向与实践建议

当前 SimpleAgent 实现的局限：自定义 `[TOOL_CALL:...]` 格式需要 LLM 主动学习使用，复杂场景不如原生 Function Calling；只测了 simple_python 等基础类别。提分方向：改用支持原生函数调用的 LLM、优化提示词、按数据集特点扩充工具库、针对类别设计策略（multiple 规划多步调用序列、parallel 识别可并行调用、irrelevance 学会拒绝）。实践路径：先从 simple 类别稳住 → 逐步测复杂类别并分析失败案例 → 参考排行榜高分模型 → 用官方工具验证。评估策略上建议**渐进式评估**：5 样本快测（>80% 才继续）→ 50 样本 → 全量；并做多类别、多配置（不同提示词）对比。

## 核心原理二：GAIA 与准精确匹配

GAIA（Meta AI + Hugging Face）评估真实世界任务的综合能力，设计理念是优秀 AI 助手需要：多步推理（分解复杂问题）、知识运用（内置+外部知识库）、多模态理解（文本/图片/文件）、网页浏览、文件操作。

### 数据集结构

466 个真实问题，按复杂度分 Level 1/2/3。样本字段：`Question`、`Level`（难度）、`Final answer`（标准答案，可为数字/文本/文件）、`file_name/file_path`（附件）、`Annotator Metadata`（标注者提供的推理步骤数、耗时、所需工具——可用于计算平均推理步骤数）。validation 集共 165 题（Level 1: 53 / Level 2: 62 / Level 3: 50）。

GAIA 是**受限数据集（Gated Dataset）**：需在 HuggingFace 数据集页申请访问权限（通常数秒批准），配置 `HF_TOKEN` 后用 `snapshot_download` 下载（约 114 个文件，含图片/PDF/CSV 等附件），首次下载后缓存本地。

### 准精确匹配（Quasi Exact Match）

先归一化、再精确匹配：`Quasi_Exact_Match(A_pred, A_true) = 1` 当且仅当 `N(A_pred) = N(A_true)`。归一化规则 `N(·)` 按答案类型：

- **数字**：移除逗号分隔符（1,000→1000）和单位符号（$100→100，50%→50）；如 "$1,234.56" → "1234.56"；
- **字符串**：转小写、移除冠词（the/a/an）、合并多余空格、移除末尾标点；如 "The United States" → "united states"；
- **列表**：按逗号分隔，逐元素做字符串归一化，**按字母顺序排序**后重新连接；如 "Paris, London, Berlin" → "berlin,london,paris"。

### GAIA 评估指标

1. **精确匹配率（Exact Match Rate）**：准精确匹配成功样本比例，核心指标；
2. **分级准确率（Level-wise Accuracy）**：各难度级别分别计算；
3. **难度递进下降率（Drop Rate）**：`DropRate(l→l+1) = (Acc_l − Acc_{l+1}) / Acc_l`，衡量难度增加时的性能衰减——下降率越大，复杂任务能力衰减越明显；
4. **平均推理步骤数**：正确样本的推理步骤均值。

示例分析：整体 70%，Level 1/2/3 分别 100%/67%/50%，Drop Rate 1→2 为 33%、2→3 为 25%——说明中等难度已有明显衰减、复杂任务仍有提升空间。

### 官方系统提示词与答案格式

GAIA 要求答案以 `FINAL ANSWER: [YOUR FINAL ANSWER]` 模板给出：数字不加逗号分隔符和单位符号；字符串不用冠词、不用缩写、数字用纯文本；列表用逗号分隔并按字母顺序。系统提示词需在评估时原样使用（这是能否正确解析答案的关键）。答案提取实现：正则匹配 `FINAL ANSWER:` 行并剥离方括号，失败时依次尝试中文"答案：/最终答案："等标记，兜底取最后一个非空行。

### 评估产出与排行榜提交

GAIAEvaluationTool 一键评估产出三类文件：GAIA 格式结果（JSONL，每行 `{"task_id", "model_answer", "reasoning_trace"}`，可直接提交排行榜）、提交说明（SUBMISSION_GUIDE_*.md）、Markdown 评估报告。提交入口：huggingface.co/spaces/gaia-benchmark/leaderboard。

## 核心原理三：数据生成质量评估（AIME 案例）

高质量训练数据是 AI 系统性能的基础。以 AIME（美国数学邀请赛）风格数学题生成为例：AIME 题目答案是 0-999 的整数（格式统一便于自动评估）、覆盖代数/几何/数论/组合/概率、需多步推理但不涉高深理论、难度适中（相当 AIME 第 6-9 题水平）——是生成质量评估的理想基准。生成参考用 TianHongZXY/aime-1983-2024（900+ 真题，1983-2025），质量对比用 AIME 2025 真题（math-ai/aime25，JSONL，30 题足够）。

### 三种互补评估方法

**1. LLM Judge（绝对质量评估）**：LLM 当评委，从四个维度给 1-5 分——正确性（数学逻辑与答案准确）、清晰度（表述易懂）、难度匹配（符合 AIME 标准）、完整性（解答步骤完整）。汇总指标：

- 平均分 Average Score = 各题四维均分的总平均，反映整体水平；
- 及格率 Pass Rate = 平均分 ≥ 3.5 的题目比例，保证基本质量；
- 优秀率 Excellent Rate = 平均分 ≥ 4.5 的比例，衡量高质量产出。

优点：快速、一致、可给评分理由和改进建议；成本远低于人工。

**2. Win Rate（相对质量对比）**：成对比较生成题与真题，LLM 判 A/B/Tie。三指标满足 Win Rate + Loss Rate + Tie Rate = 100%。**理想结果：Win Rate ≈ 50%**（生成质量接近真题）；显著低于 50% 需优化生成策略；显著高于 50% 可能是生成超真题或评估标准有偏差。相对比较比绝对评分更符合人类判断习惯。

**3. 人工验证（最终把关）**：对数学内容，逻辑严密性、创新性等仍需人类专家。基于 Gradio 的 Web 界面：阅读题目/答案/解答 → 四维评分（1-5）→ 标注状态（approved / rejected / needs_revision）→ 评论，结果存为 `<data_path>_verifications.json`。

### 题目生成器要点

- 生成提示词含**参考样例**（从真题集随机选一题做风格参考，要求生成完全不同的题）、AIME 特征约束（整数答案 0-999、主题、难度）、固定 JSON 输出格式（problem/answer/solution/topic）；
- 用英文生成：与真题一致、评估公平（英文 vs 英文）、便于国际化、免翻译失真；
- **LaTeX 与 JSON 的坑**：`\frac`、`\sqrt` 中的反斜杠是非法 JSON 转义，解析失败；修复方式是正则把未转义的反斜杠替换为双反斜杠：`re.sub(r'(?<!\\)\\(?!["\\/bfnrtu])', r'\\\\', json_str)`；
- 批量生成要控制 API 延迟（2-3 秒/题避速率限制）、检查点保存防中断损失、先小批量（10 个）验证再放量。

### 质量标准与流程整合

完整流程：生成题目 → LLM Judge + Win Rate 并行评估 → 综合报告 → 人工验证。建议的质量门槛：

| 指标 | 建议标准 |
|---|---|
| LLM Judge 平均分 | ≥ 4.0/5.0 |
| Win Rate | ≥ 45%（接近 50%） |
| LLM Judge 通过率 | ≥ 80% |
| 人工验证通过率 | ≥ 90% |

迭代优化：按评估结果调整生成提示词、分析低分题共性问题、参考高分题优点。

## 经验与常见坑

- **评估结果不理想是正常现象**：即使 GAIA Level 1（一步推理）也需要工具调用能力（搜索、计算器），演示用 SimpleAgent 的工具能力有限——先区分"评估流程问题"与"被测智能体能力问题"。
- **bfcl-eval 官方包依赖冲突**：强制 numpy<=2.0.0，与主框架冲突，需单独 `pip install "numpy==1.26.4" bfcl-eval`。
- **AST 匹配比字符串匹配准，但非万能**：能识别参数顺序、等价表达式、格式差异；理论上仍可能误判（如语义等价但语法不同的写法）。
- **LLM Judge 的固有局限**：可能对回答风格有偏好、对长度敏感；重要场景必须人工验证兜底。
- **评估成本控制**：渐进式评估（小样本先行）、延迟控制、缓存数据集本地化。
