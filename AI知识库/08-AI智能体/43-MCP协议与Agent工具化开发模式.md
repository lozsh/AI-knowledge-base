# MCP 协议与 Agent 工具化开发模式

<p class="note-date">更新于 2026-11-03</p>
> 一句话概括：MCP 用统一协议解决"M 个应用 × N 个工具"的适配爆炸；Agent 开发的元方法是 FC/ReAct/计划模式/校验机制的组合，LLM 只做调度与解读，执行与计算交给工具。

## 核心概念

- **MCP（模型上下文协议）**：解决 M×N 问题——M 个 AI 应用 × N 个工具各自适配改为统一协议，工具供应与消费分离，工具可复用、可独立部署。
- 架构：Host（AI 应用）内嵌 Client（与 Server 1:1 连接），Server 负责执行工具。
- 三大能力与选用原则：**Tool**（模型自主选择调用，全自动，主流）/ **Resource**（资源，用户手动选用）/ **Prompt**（预置提示词）。原则：模型自主决策的做 Tool，给人用的做 Resource/Prompt。
- 传输方式：stdio（本地子进程）vs HTTP 类（远程、长连接、多客户端，产品化首选）。
- **A2A 与 MCP 互补不竞争**：MCP 管 Agent↔工具，A2A 管 Agent↔Agent。A2A 哲学：单 Agent 不做万金油，跨域问题转介给对应专家；核心概念 Agent Card（JSON 名片：能力/地址/输入输出类型）与 Task 状态机。

## 关键方法/模式

### Function Calling 的本质
- **FC 本质是 Function Selecting**：模型只负责选工具 + 提炼参数，执行永远在人类程序侧。流程：消息 + 工具清单 → 模型回调用意图 → 程序执行 → 以 tool 角色回填结果 → 重发对话。
- 坑：模型决定调工具时正文为空是正常的；**工具描述本身也消耗 token，描述质量直接决定选择准确率**。

### ReAct
- 公式：**ReAct = CoT + 工具调用**，Thought → Action → Observation 循环到 Final Answer。与 FC 本质相同，区别在模板约束使过程可控、可纠错。
- 坑：模型会**杜撰 Observation**，须在模板中明确"此处等待工具/人类回复"。很多框架的 react agent 底层其实是 FC 实现。

### 计划模式（Plan mode）
- 先用纯提示词节点制定计划（计划存入共享状态字段），再逐步执行；通盘考虑防跑偏，可加人工审核计划环节。
- 退出条件不能用"是否调过工具"判断，改用输出末尾固定标记（如 Final Answer）。
- 铁律：**制定计划的 prompt 必须包含全部工具描述，并约束"步骤必须贴合工具能返回的内容"**——否则执行必崩。

### 校验机制（双模型互查）
- 第二个模型独立重算 + 批改；错误输出固定哨兵词 → 条件分支 → 人工兜底（消息通知）或回流重试。
- 本质是拿 token 和延迟换准确率，适合高价值低频场景。

### LangGraph 核心抽象
- 适用时机：需要分支 + 循环的控制流（Agentic RAG、多步 Agent），线性 chain 搞不定时。
- 抽象类比低代码工作流：State = 中央变量，Node = 函数，条件边 = if-else。
- **关键坑：节点收到的是上一节点的输出而非全量 State，跨节点存续的数据必须每步显式回写**；累积字段用列表累加返回。

### 工具开发套路（零代码平台与代码通用）
- 工具 = 入参 Schema + 执行逻辑 + 出参 + 鉴权；接口标准规范是 OpenAPI。产品化趋势：厂商从提供 OpenAPI 转向直接提供 MCP Server。
- MCP Server 开发：用轻量框架时 docstring 即工具描述、类型注解即 Schema，描述与实现合一；Client 套路固定（连接 → 握手 → 列工具 → 调工具），精力应放在工具设计上。

### 代码生成与数据类 Agent 的通用模式
- **数据表文档 → 实体代码**：终态 = RAG 版工具（数据字典切片入库 → 工具内按关键字检索字段 → LLM 生成结构体）；top-k 要大于最长表的字段数加切片碎片冗余；文档写成数据库表风格（类型/主键）红利大。
- **老代码库 → 新代码**：按函数切分老代码入库 → 需求关键字向量匹配 → 最相关历史代码作 few-shot。**前提：每个函数前有清晰注释，注释质量决定命中率**。
- **按结构拆节点生成**：把目标代码的固定结构拆成多个节点，每节点一段专属 prompt，靠共享状态传依赖——比整段生成稳定得多。
- **数据类 Agent 心法**：把大模型当人看——把人的流程拆成工具链，前一工具输出即后一工具入参，LLM 只做调度与解读。**数值计算必须封装成工具**（LLM 直接算会幻觉）；产出必须人工核对（LLM 会杜撰补全）。
- 爬虫类工具选型：官方 API > HTTP 爬虫 > 无头浏览器（仅 JS 动态渲染 + 反爬时用）；等待元素而非固定延时；爬虫是易腐代码，页面结构变了要重新定位。

| 术语 | 含义 |
|---|---|
| MCP | 模型上下文协议，统一 AI 应用与工具的连接标准 |
| Host / Client / Server | MCP 中 AI 应用 / 协议连接器 / 工具执行端 |
| Tool / Resource / Prompt | MCP 三能力：模型自选工具 / 资源 / 预置提示词 |
| A2A | Agent 间协作协议，与 MCP 互补 |
| Agent Card | A2A 中描述 Agent 能力与接口的 JSON 名片 |
| FC | Function Calling，模型选工具、程序执行的机制 |
| ReAct | 思考-行动-观察循环的 Agent 模式 |
| Plan mode | 先制定计划再执行、可人工审计划的模式 |
| State / Node / 条件边 | LangGraph 的共享状态 / 节点函数 / 分支控制 |

## 经验与常见坑

- 工具描述是"写给模型的 prompt"：描述含糊模型就选错工具，值得花与业务提示词同等的功夫打磨。
- 校验模型与生成模型不要是同一个上下文，独立重算才有检出力。
- 简历匹配、文档检索类应用的质量上限取决于**输入物的质量**（简历本身就是 prompt 的一部分）。
- 上游 SDK 升级破坏插件生态是平台类工具的常态故障源，降级是合法解法。
