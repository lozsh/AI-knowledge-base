# 低代码平台智能体搭建

<p class="note-date">更新于 2026-11-03</p>

**一句话定义**：低代码平台用图形化、模块化的"节点/编排"方式封装智能体的技术细节（API 调用、状态管理、并发控制），让开发者把重心从"实现细节"转向"业务逻辑"——正如建站从手写 HTML 演进到 WordPress/Wix。

纯代码"造轮子"对深入学习至关重要，但业务逻辑复杂后维护成本和开发周期急剧上升。低代码平台的核心价值：**降低技术门槛**（产品经理、业务专家也能参与构建）、**提升开发效率**（数分钟到数小时完成原型）、**可视化可观测**（端到端看到数据流动、哪个节点耗时/失败）、**沉淀最佳实践**（预设 ReAct 模板、标准化的知识库检索与工具接入规范）。它不是取代代码，而是更高层次的抽象；最佳实践是"混合开发"——平台快速验证想法、代码做精细化控制。

## 分类/类型

### 四大代表平台对比

| | Coze（扣子） | Dify | FastGPT | n8n |
|---|---|---|---|---|
| 定位 | 零代码/低代码 Agent 构建，生态集成最强 | 开源 LLM 应用开发与运营平台（BaaS + LLMOps） | 开源知识库问答平台，"企业级 AI 生产力引擎" | 通用工作流自动化工具（LLM 只是其中一种节点） |
| 强项 | 插件库丰富、可视化编排、一键发布到微信/飞书/豆包等多平台、提示词管理与模板 | 全栈式（RAG Pipeline、Agent 工作流、模型运营、微调）、Marketplace 插件 8000+、本地/云端双部署 | RAG 链路极致打磨（导入→分块→索引→检索全流程精细配置）、原生 MCP 支持、模型中立 | "连接"能力：数百预置节点串联 SaaS/数据库/API，AI Agent 节点整合模型/记忆/工具，可私有化部署 |
| 弱项 | 当时（写作时点）不支持 MCP；复杂插件配置仍需技术背景；导出导入仅限自家 zip 格式（可复制编排绕过） | 学习曲线较陡；Python 实现的高并发性能瓶颈；多模态支持有限；企业版成本高；API 格式不兼容 OpenAI | 模板生态薄弱；免费版额度紧（100 积分/30 QPM）；社区与文档仍完善中 | 调试逐节点排查繁琐；Simple Memory/Vector Store 基于内存、重启即失（生产须换 Redis/Pinecone）；版本控制与协作不如 git；超高并发性能开销 |
| 适用 | 非技术用户、快速验证创意、个人创作者 | 企业级应用、复杂业务逻辑、专业团队 | 基于私有知识库的问答/智能客服/垂直咨询 | 深度业务集成、通用自动化流程、数据不出内网 |

**选型速记**：快速原型/非技术用户 → Coze；企业级/复杂逻辑/多模态 → Dify；私有知识库问答 → FastGPT；深度业务集成/通用自动化 → n8n。

## 核心原理（各平台关键模式）

### Coze：插件驱动的多源聚合

界面结构：项目开发（智能体 + AI 应用两类，智能体分单智能体自主规划/对话流/多智能体三种模式）、资源库（工作流、知识库、卡片、提示词库——"模型决定下限，资源库给上限"）、插件商店、智能体社区、发布渠道管理。

"每日 AI 简报"案例三步：
1. **信息源插件配置**：RSS 插件（36氪/虎嗅/it之家/infoq 的 RSS 链接）、GitHub 插件（关键词 q:AI、per_page、sort:updated）、arXiv 插件（领域关键词 + 数量 + 排序），作为数据输入节点接入大模型模块。
2. **角色与提示词**：系统提示定义长期行为准则与输出格式（角色 = 资深科技媒体编辑；日报格式：标注日期、每条目配 Emoji、附原始链接、每条一句话概况）；用户提示定义具体任务（从 `{{articles}}` 等变量提取"AI 技术新闻"、从 `{{arxiv}}` 整理"AI 学术论文"、从 `{{GitHub}}` 筛 5 个开源项目）。
3. **测试调试 → 多渠道发布**：预览检查内容/格式/风格，不合规回改提示词或插件参数；一键发布到微信/豆包/飞书等。

### Dify：问题分类器路由的多模块智能体

分层模块化架构（数据层/开发层/编排层/基础层），模型高度中立（数百种 LLM 统一接口接入）。MCP 配置：魔搭社区 MCP 市场选 hosted 类型，SSE 模式（在 Dify 中比其他模式流畅稳定）生成配置 JSON。

"超级智能体个人助手"架构：**问题分类器做智能路由**，分发到各子模块——
- 日常问答（大模型 + 时间工具兜底）
- 文案优化（高频场景；提示词结构：角色人设/背景/任务目标/限制提示/输出格式要求）
- 多模态生成（即梦插件，seedream 生图 / seedance 生视频；用循环 + 条件判断获取视频任务结果）
- 数据查询与分析（rookie-text2data 插件；关键是为大模型提供清晰的表结构——DDL 语句或表名字段说明，让模型生成准确 SQL；查询结果经大模型整理为自然语言；可视化由 generate_pie_chart / generate_column_chart / generate_line_chart 等 BI 图表工具完成）
- MCP 工具集成（智能体策略选 ReAct 模式，配置 MCP 服务时注意删除 mcp-server 前缀）

### FastGPT：知识库第一等公民

核心链路"数据导入 → 智能分块 → 向量化存储 → 智能检索 → 对话生成"深度优化。知识库精细化配置：分块存储 vs 问答对提取两种处理方式；分块条件（如原文 >1000 字符触发）；索引增强选项（标题入索引、自动补充索引、**图片自动索引**——图文混排文档让模型理解视觉信息）；分块内容与元数据（文件大小、原文长度、处理模式）透明可查。

"智能投顾助手"案例工作流：意图识别节点分流（金融概念咨询 → 知识库检索；股票查询 → MCP 工具调用；投资诊断 → 风险问卷收集）→ 投资知识教育专员（检索金融知识库）→ 风险评估分析师（表单收集年龄/经验/收入/最大亏损/目标 → 大模型生成结构化投资策略报告：风险等级 + 资产配置饼图 + 市场分析 + 再平衡策略）→ 市场新闻情报专员（实时股票 MCP、图表生成 MCP）→ 通用咨询专员。金融知识库的 RAG 检索降低概念问答的幻觉风险。

MCP 生态来源：魔搭社区（ModelScope）MCP 市场、阿里云百炼平台官方 MCP 服务。

### n8n：节点 + 工作流的自动化

两个基本概念：**节点**（最小操作单元；触发节点启动流程——Gmail 收信/定时/Webhook，一个工作流有且仅有一个触发节点；常规节点处理数据——读写数据库/调 API/调 LLM）与**工作流**（节点连成的流程图，数据以 JSON 结构化传递）。**AI Agent 节点**把 Chat Model（思考核心）、Memory（记住同一邮件线程的对话历史）、Tools 整合在一个界面，实现"思考 → 决策 → 工具调用"的自主决策，比传统多节点手动路由优雅得多。

"智能邮件助手"案例（接收 → AI Agent 思考 → 回复）：
1. **构建私有知识库**（独立流程，更新知识时跑一次）：Code 节点存知识 JSON → Embeddings Google Gemini 向量化 → Simple Vector Store 写入模式（Memory Key 如 `my-dailytime`，相当于"表名"）。
2. **主工作流**：Gmail 触发器（Message Received；OAuth 凭证配置：Web 应用类型、添加重定向 URI、目标对象加用户邮箱）→ AI Agent 节点：
   - Chat Model：Gemini Chat Model
   - Memory：Simple Memory，Key 用邮件线程 ID（`threadId`）保证唯一
   - Tools：SerpAPI（上网搜公开信息，**主要信息来源**）+ Simple Vector Store 读取模式（**Memory Key 与 Embeddings 模型必须与建库时完全一致**——"用正确的钥匙和语言访问知识库"）
   - System Message 要点：角色（全天候 AI 邮件助手）、可用工具及各自用途、执行步骤（并行搜集：SerpAPI 查答案 + Vector Store 查工作时间 → 对比当前时间判断是否非工作时间 → 非工作时间在回复开头附状态提醒前缀并附上具体工作时间）、严格的 JSON 输出格式（`{"shouldReply", "subject", "body"}`，换行用 `<br>` 标签）
   - 工具的 Description 字段是 Agent 决策的依据（"用来查询我的工作时间和邮件回复策略，判断是否为工作时间时必须使用"）
3. **发送回复**：Gmail Send 节点，用 n8n 表达式关联收件人/主题/正文（`{{ $json.output }}`）。

扩展性：向 AI Agent 节点继续添加工具（日历、数据库、CRM），只需在 Prompt 中教会 Agent 使用。

## 经验与常见坑

- 提示词在各平台都是核心：结构化模板（角色/背景/任务/限制/输出格式）普遍适用；对输出长度的硬性要求（"超过 500 字"）应视场景取舍。
- n8n 的 Simple Memory / Simple Vector Store 是内存存储，服务重启即丢——生产环境必须替换为 Redis、Pinecone 等持久化方案。
- n8n 案例的"Memory Key + Embeddings 模型一致性"是向量库检索失败的最常见原因。
- 数据查询场景给模型表结构：表多字段多时直接塞全部 DDL 会撑爆上下文，需要更智能的表筛选/检索方案。
- 低代码工作流的调试：数据格式错误需逐节点检查输入输出，不如代码断点直接。
- 平台选型要综合：技术可行性、上线速度、开发/运营成本、可维护性、可扩展性、数据安全与合规（如涉敏数据的合同审核系统必须私有化部署——Dify 本地部署或 n8n 私有化）。

## ⚠️ 时效性说明

- 各平台功能、插件数量（Dify 8000+、Marketplace 8677 个）、免费额度、模型版本（seedream/seedance、gemini-embedding 型号）均为教程编写时点（2025 年）数据，迭代极快。
- Coze 对 MCP 的支持状态在写作时点为"路线图中未实现"，现状请查官方；导出导入功能付费版可用。
- 即梦、豆包、魔搭 MCP 市场、阿里云百炼等服务细节可能变化。
