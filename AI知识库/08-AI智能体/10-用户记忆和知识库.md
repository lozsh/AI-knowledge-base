# 用户记忆和知识库

<p class="note-date">更新于 2026-11-03</p>

**一句话定义**：用户记忆是 Agent 针对单个用户跨会话积累的个性化知识模型；知识库是面向所有用户共享的集体知识（经 RAG 检索）；两者尺度不同（个体 vs 群体），共用向量检索、分块、知识压缩等同一套底层技术，最终汇合为"双层记忆架构"。

上下文工程（见 [上下文工程](08-%E4%B8%8A%E4%B8%8B%E6%96%87%E5%B7%A5%E7%A8%8B.md)）解决的是单次会话内的上下文管理；本文处理更难的问题：对话结束后如何仍然记住用户、记住知识。用户记忆让 Agent 成为"懂你的助手"——在与每位用户的交互中逐渐提炼其偏好、习惯和需求；知识库让 Agent 成为"领域专家"——承载行业法规、公司流程、专业文档。两者面临同样的麻烦：信息冲突、知识过期、检索不准。

## 核心原理

### 用户记忆的本质

记忆不是记录用户说过的每一句话，而是一个主动的、持续的学习过程：投入额外算力（专门的 LLM 调用），把分散在冗长对话中的关键信息**显式提取、压缩、结构化**。例如订机票对话结束后，框架调用一次 LLM 提取出"偏好靠窗座位（偏好）、素食需特殊餐（饮食限制）、美联航常旅客号 12345678（账号）、有东京行程（近期活动）"。提取的三个关键特征：

- **选择性**：只保留对未来有用的事实，不记"搜索返回了 3 个选项"这类临时信息；
- **抽象化**："I prefer window seats" 被提炼为通用偏好，不绑定具体航班；
- **结构化**：每条记忆标记类型（偏好/限制/账号），便于后续检索。

它与上下文学习（ICL）相对：用户记忆持久、可审查；ICL 临时、会话结束即消失。

### 记忆能力的评估：三层次框架

学术界代表性基准是 LoCoMo（Maharana 等，2024，arXiv:2402.17753）：平均约 300 轮、最多 35 个会话的超长多轮对话，考查询答（单跳/多跳/时间推理/开放域/对抗性）、事件摘要和多模态生成。综合各基准与商业产品实践，记忆能力可归纳为八项：个人信息保留、偏好追踪、上下文切换、记忆更新、多会话连续性、复杂思考（如花生过敏者订泰国菜时主动提醒）、时间感知、冲突解决。

三层次评估框架（配套 user-memory 项目，每层 20 用例，用 LLM-as-a-judge 评分）：

1. **基础回忆**：准确存取用户直接给出的无歧义信息（"我的会员号是 12345"）。
2. **多会话检索**：跨多个会话检索全部相关信息并推理——用户有两辆车时"为我的车预约保养"要主动问哪辆；取消"洛杉矶之旅"要关联机票和酒店全部预订。
3. **主动服务**（试金石）：综合久远会话信息提供预见性帮助——订国际航班时发现数月前存的护照即将过期并预警；手机损坏时整合自带保修、信用卡附加保修、运营商保险给出完整方案；报税季汇总全年税务文件。

### 记忆的层次结构（放哪里）

- **轨迹（Trajectory）**：单次 Agent 运行的完整历史（用户消息 + 回复 + 工具结果），按时间追加、只增不改（append-only），是决策的即时上下文——流水账。
- **用户长期记忆**：跨会话持久化存储，通常键值对绑定用户 ID，会被反复改写、合并、淘汰——档案。
- **业务状态**：开发者定义的任务逻辑阶段抽象（"需要澄清""等待付款"），在事件驱动架构中尤为重要。

分层设计同时保证当前任务效率（依赖轨迹）与长期个性化（依赖长期记忆）。

## 分类/类型

### 四种存储格式（怎么存）——简单性与表达力的张力

| 格式 | 形态 | 优势 | 代价 |
|---|---|---|---|
| Simple Notes | 原子事实（"用户邮箱：john@x.com"） | 开销极低，O(1) 操作 | 关联性丢失，长文难检索 |
| Enhanced Notes | 整段叙事（保留完整上下文） | 语义完整，适合细微理解 | 冗余、难更新、段落长导致嵌入稀释 |
| JSON Cards | 三层嵌套（类别→子类→键值，如 work.position.title） | 支持部分更新，可预测可扩展 | 刚性分类，多维信息被迫归入单一类别 |
| Advanced JSON Cards | 卡片 + backstory（来源背景）+ person + relationship + 时间戳 | 消歧与知识管理（区分"我的牙医张医生"与"我父亲的心脏科张医生"） | 生成维护成本高 |

四种格式递进代表记忆粒度与结构复杂度的升级，没有绝对优劣。实验结论：Simple Notes 以最低成本通过第一层多数用例，但在综合多条信息、消歧的第二三层频繁失分；Advanced JSON Cards 在消歧和跨会话关联上最好，代价是记忆维护调用更贵更慢。**实践标准**：关键少量数据（偏好、关键人物关系）用 Advanced JSON Cards；大量非关键对话事实用 Simple Notes；多数生产系统混合使用。

### 认知科学基础（存什么）

工作记忆 ↔ Agent 的上下文窗口（轨迹是其核心内容）；长期记忆分三类：

- **情景记忆**（具体事件）："用户订了下周五去东京的 ANA 航班"。
- **语义记忆**（抽象的一般知识）："用户是素食者"、"偏好靠窗座位"。
- **程序记忆**（行为流程）：从反复订票学到的"先搜直飞→确认座位→用常旅客号→订餐"。

三套分类体系正交、可自由组合：记忆层次回答"存在哪里"、存储格式回答"怎么存"、认知类型回答"存什么"。

### 表示介质的进阶：由外及内的连续谱

- **User as Code（可执行代码）**：把用户模型建成活的软件工程——带类型的 Python 对象保存状态、普通函数编码约束。更新拆两阶段：会话后 LLM 把事实追加进只增不删的事实日志；周期性地从日志重新生成整份带类型代码（类比数据库"预写日志 + 周期检查点"）。纯文本记忆最吃力的三件事由此变成确定性代码：聚合统计（"去年出国几次"一行表达式，检索式记忆正确率仅 6%–43%，代码形态接近 99%）、冲突发现（用药与过敏史交叉比对）、约束执行（出国行程距护照到期不足 180 天自动报警）。代价：需要代码生成与执行的工程支撑，杂项事实仍保留 notes 文本字段。
- **User as Engram（写进局部参数）**：不训练每用户 LoRA（fact-LoRA 能复述事实却无法在其上做间接推理——冻结骨干没学过"何时查阅"适配器），而是把用户事实外科手术式写入 Engram 模型的空闲哈希 N-gram 槽位；该类模型预训练时已学会哈希查表调取记忆、由上下文感知门控决定何时调取，不同用户事实落在互不相交的槽位上互不干扰。
- **参数化多模态记忆**：存下无法言说的感知（脸、嗓音、画风——转写成文字恰恰丢掉区分性细节）。为冻结模型外挂记忆库，键是编码器（ArcFace/CLIP）算出的感知向量，值是标记词嵌入；生成时以当前感知做注意力查询，不经由文字。注册新身份只需添一行。效果上反超直接向量检索——因为在语言模型自身表示空间里比对感知，尺子更锐利。

外侧（文本/代码）易更新、可审查、可迁移；内侧（参数/感知）更紧凑、擅长即时推理、能承载文字无法转写的内容。

## 关键概念

### 记忆框架案例

**Mem0**（Chhikara 等，2025，arXiv:2504.19413）：核心是"提取—对比—决策"两阶段流水线。提取阶段：新对话结束后 LLM 结合近期对话与已有记忆摘要提取候选记忆；更新阶段：向量检索找出语义相近的已有记忆，LLM 对比后四选一——ADD（全新入库）/ UPDATE（如"搬到上海"修正"住在北京"）/ DELETE（新信息否定旧记忆）/ NOOP（重复不操作）。这把选择性提取与冲突解决统一在"每条记录与既有记忆显式对账"的机制里。工程上嵌入与存储分离、插件化多后端；图记忆变体 Mem0-g 用实体-关系图显式捕捉记忆关联，改善多跳、时序问题。

**Memobase**：聚焦"用户画像"形态。用户画像（Profile）是开发者可配置的主题-子主题两级槽位（`basic_info`→姓名、`interest`→游戏偏好），精确控制范围和粒度；事件记忆（Event）按时间线记录经历，回答"我们上次讨论预算是什么时候"。采用缓冲批处理：对话累积到一定规模再统一触发一次提取，摊薄 LLM 成本，查询侧只读整理好的画像和事件，保证低延迟。

两个框架都只覆盖设计空间一部分（事实条目≈语义记忆、事件≈情景记忆）。多类型记忆协同的参考架构（设计概括而非具体实现）：情景记忆带多维元数据（时间戳、情感标记、任务标识）可组合检索；与工作记忆动态交互——重要信息选择性写入长期记忆，相关长期记忆按需激活加载。注意轨迹与工作记忆的区别：轨迹是不可变的完整事件序列，工作记忆是按相关性筛选激活的动态子集。实际框架往往只实现一两种类型，按业务取舍优于"大而全"。

### 记忆压缩与整理机制

累积式存储导致记忆爆炸，降低检索准确性。多层次压缩：

1. **重要性评分筛选**：综合访问频率、时间衰减、情感强度、信息独特性四因素，低于阈值标记可压缩/删除；
2. **聚类压缩**：相似记忆分组生成代表性摘要（多次天气对话→"用户经常询问天气，特别关心降雨"），原始记忆存档二级存储；
3. **抽象泛化**：从情景记忆提取一般规律转化为语义/程序记忆（多次购物对话→"偏好性价比高、重视用户评价"）。

冲突检测用版本化方法：保留历史版本并标记最新版；当前地址只留最新版，工作经历保留完整历史。注意边界：这里是记忆存储层的整理算法，单次会话内的窗口压缩属上下文工程（[上下文工程](08-%E4%B8%8A%E4%B8%8B%E6%96%87%E5%B7%A5%E7%A8%8B.md)）；离线整合的触发机制属 Agent 架构层。

### 隐私保护：日志脱敏

核心挑战是既利用用户信息提供个性化服务，又不让敏感数据暴露在 LLM 上下文和日志中。配套 log-sanitization 项目用 Ollama 跑本地 Qwen3 0.6B 小模型做 PII 检测——**必须本地部署**：日志本身含敏感信息，发云端脱敏就违背了初衷。可识别结构化信息（身份证、银行卡号）、半结构化（地址）、自然语言敏感内容（"我的密码是 abc123"），JSON Schema 结构化输出类型/位置/置信度。基于 LLM 的脱敏召回率 95% 以上、假阳性显著低于正则；超高吞吐场景可用混合策略：正则快速过滤 + LLM 深度分析剩余文本。

### RAG 基础：知识获取管道

RAG（检索增强生成）= 检索器（从知识库找相关片段）+ 生成器（LLM 以片段为上下文生成答案）。核心价值：让 LLM 利用训练时没见过的知识（最新维基内容、公司内部文档），无需重新训练。查询流程：检索→增强（注入上下文）→生成。

**文档分块（Chunking）**：嵌入模型输入长度有限、整篇文档压成一个向量无法精确表达多主题（与 Enhanced Notes 的问题同源）；检索只需注入相关部分。三类策略：固定大小切分（如 512 token + 50-100 重叠，简单可预测但无视结构）；递归/结构感知切分（按章节/段落/句子边界递归，生产系统最常用默认选择）；语义切分（相邻句嵌入相似度骤降处下刀，质量高但需额外嵌入计算）。块大小权衡：太小语义模糊（"该公司收入增长了 3%"——哪家公司？），太大主题混杂、嵌入稀释。常见起点 256-1024 token、重叠 10%-20%。固有缺陷：分块切断片段与原始上下文的联系（后文"上下文感知检索"解决）。

**稠密嵌入**：文本映射到向量空间，语义相近则向量距离近。余弦相似度度量方向一致性而非长度（两篇内容相同长度不同的文档方向一致）。演进：Word2Vec/GloVe（2013-14，静态词向量，一词一向量，有 "king-man+woman≈queen" 的线性语义规律，但无法处理一词多义）→ BERT（2018，自注意力上下文感知，"苹果"在不同语境向量不同）→ Sentence-BERT（2019，对比学习句子级嵌入）→ BGE-M3（2024，多语言长文本，实际同时输出稠密/稀疏/多向量三种表示）。海量向量检索用 ANN（近似最近邻）索引，两种代表：

| 特性 | ANNOY（基于树） | HNSW（基于图） |
|---|---|---|
| 构建速度 | 快 | 较慢 |
| 内存占用 | 低 | 较高 |
| 增量更新 | 不支持（需完全重建） | 支持（长期增量插入后建议定期重建） |
| 查询精度 | 较高 | 极高 |
| 适用场景 | 数据不常变的静态库 | 需实时索引新信息的动态场景 |

**稀疏嵌入**：根植于传统信息检索，极高维向量、绝大多数维度为零，核心是精确关键词匹配。理论基石是词袋模型（忽略词序——"猫追狗"与"狗追猫"相同），演进到 TF-IDF（词频高且文档频率低的词更重要）再到 BM25，后者引入 k1（词频饱和：出现 20 次与 10 次相关度并非差一倍）与 b（文档长度归一化）两个参数，至今是搜索引擎核心组件。倒排索引（Inverted Index）是"词→文档"的反向映射，如书后术语索引页。稀疏检索已进入学习型阶段：SPLADE、BGE-M3 稀疏分支用神经网络为词项打权重，甚至为原文未出现的语义相关词补非零权重（术语扩展），保留精确匹配与可解释性又获得语义泛化。BM25 评分公式：

```
Score(Q,D) = Σ IDF(qi) × TF(qi,D)×(k1+1) / (TF + k1×(1−b+b×|D|/avgdl))
```

**混合检索**：稠密懂语义但可能漏关键词（搜"HTTP-403"返回泛泛的"服务器错误"），稀疏精确但读不懂同义（搜"kitty"找不到只写"cat"的文档）。三阶段流水线：① 并行检索（两路各自召回）；② 结果融合——两路得分尺度迥异（余弦 0-1 vs BM25 0-几十）不可直接比较，常用归一化加权求和，或**倒数排名融合 RRF**：得分 = Σ 1/(k + rank)，k 常取 60，只看排名不看原始得分，简单鲁棒但丢失得分信号；③ 神经重排序——用**跨编码器（Cross-Encoder）**把查询与候选文档拼接送入模型逐词深度交互打分（如 BAAI/bge-reranker-v2-m3），精度远高于检索阶段**双编码器（Bi-Encoder）**各自独立编码再比向量（比喻：猎头按简历特征快速初筛 vs 面试官与候选人深谈）。重排序不是为补救 RRF 而存在——无论怎么融合它都值得加，因为换用了更强的匹配范式；但它不替代融合（没有候选池它不知道该对谁打分）。

**检索质量指标**（在带标注的测试查询集上计算）：recall@k（正确文档进前 k 的查询比例——"该找的找到了吗"，最贴近 RAG 需求）；MRR（第一个相关文档排名倒数的均值——"够不够靠前"）；nDCG（全列表质量，排名越靠后折扣越大）。工业报告的"检索失败率"通常指 1 − recall@20，比较时先弄清指标与 k 值。

**多模态信息提取**（知识库流水线最前端的摄取索引阶段），三条路、核心取舍是保真度 vs 成本：① 原生多模态处理——ViT 把图像切成图像块当"视觉单词"进 Transformer，与文本共存于统一语义空间，直接"看到"PDF 版式与图表，保真最高（Qwen-VL、LLaVA 等架构公开；GPT-4o、Gemini 未公开但思路类似）；② 提取为文本——OCR/音频转录后进 LLM，模块化低成本、可缓存复用，但版式图表信息全部丢弃；③ 工具化分析——文本提取起步，赋予 Agent `analyze_image`/`analyze_pdf` 工具按需深入。实验结论：原生模式分析图表最佳；提取为文本处理纯文本主导文档成本效益最高但无法处理视觉查询；工具模式在交互式场景灵活，端到端深度理解不如原生。没有万能答案。

## 经验与常见坑

**扁平化 RAG 的根本限制**——简单切块入库，统计类与规则类问题都会失败：

- **计数问题**：100 个独立案例（90 黑猫 10 白猫）问"比例多少？"——top-k 截断漏掉大部分案例、检索分数参差、统计需要"数遍所有"而检索只"找最相关的几个"，天然矛盾。模型基于不完整样本得出错误结论。解法：预先生成统计摘要并索引。
- **规则推理错误**：三个孤立案例（退伍军人 John 获优惠、医生 Sarah 获折扣、教师 Mike 不符），护士询问时检索器因"护士"与"医生"语义相近只召回案例 B，错误推断护士可享优惠，漏掉案例 C 的反面证据。解法：预先提炼明确规则并索引。

根因：注意力机制本质是基于相似度的软检索，不是能主动总结归纳的思考引擎——**必须在索引阶段投入算力，主动提炼、抽象、结构化**。

**结构化索引**——索引前先用 LLM 把知识整理一遍，两条路：

- **RAPTOR**：自下而上递归抽象——文本块作叶子，聚类语义相近的块，LLM 为每组生成父节点摘要，递归成"细节→主题→全局概览"的知识树，检索可在多个抽象层次穿梭（适合"从概念逐步钻进细节"）。
- **GraphRAG**：LLM 提取实体与关系构成知识图谱（三元组"主语-关系-宾语"，如（张三, 就职于, 腾讯）），社区发现算法生成主题聚类摘要。核心优势：多跳关系推理（"我的医生所在医院的地址"沿关系边逐跳遍历）与实体消歧（两个同名"张医生"是图中不同节点，靠关系边区分——注意与"bank 一词多义"的词义消歧不同，后者靠上下文感知嵌入即可）。局限：自然语言转三元组导致语义降级（条件判断和时间依赖在分解中丢失），提取错误会污染知识。推荐分层互补：核心信息用完整自然语言保存 + 结构化元数据索引；多跳推理和精确消歧的垂直场景（医疗、法律、家族关系）将图谱作专项索引。
- **何时需要**：混合检索已覆盖大多数需求。查询主要是"找包含某信息的片段"（退款政策）时混合检索就够；经常需要跨文档综合或多层次导航时才值得投入——结构化索引的索引构建需要大量 LLM 调用，成本显著，简单方案不够用时再升级。

**文件系统范式（OpenViking，火山引擎开源）**：第三种知识组织哲学——把记忆、资源、技能映射为虚拟文件系统的目录和文件，每条目有唯一 URI（viking://resources/、user/memories/、agent/skills/）。核心设计 L0/L1/L2 三层按需加载：L0 摘要约 100 token（判断目录相关性）、L1 概览约 2000 token（规划决策）、L2 全文（深入时才加载）——大部分查询到 L1 即可完成决策，与渐进式披露（progressive disclosure）思路一致。选 Markdown 纯文本而非专用数据库：用户可直接阅读修正、可 Git 版本控制、Agent 可用 `write_file` 自主记录知识（会话结束时自动把偏好写入 user/memories/、经验写入 agent/memories/，形成记忆自演化循环）。**极易忽视的前提**：文件之间必须建立链接与索引——若知识只是孤立平铺的文本文件，知识越多越难检索；正确做法是像 Wikipedia，每个条目提及其他条目时以链接指向，辅以入口页和索引页，形成双向可达的引用网络（相当于用轻量文件链接实现 GraphRAG 的部分导航能力）。不同模型主动建链的意愿差异很大，写入侧提示词必须明确要求：新增条目先检索并链接相关已有条目、更新索引页。

**知识库的时效与治理**：

- **增量更新**：公司政策改版、法规更新后应增量更新索引而非推倒重建——索引结构选择有现实后果（ANNOY 需完全重建适合静态库，HNSW 支持增量插入适合动态场景）。
- **失效内容下线**：旧政策留在库里会与新版一起被召回，给出自相矛盾的答案。给每个分块附加版本号、生效/失效时间等元数据，在检索阶段过滤，或提炼摘要时标注"此条已于某日废止"（与用户记忆的版本化冲突检测同思路，搬到共享库尺度）。
- **权限与租户隔离**：检索必须按调用者权限过滤，且要**下推到检索层**——一旦敏感内容进入 LLM 上下文，很难保证不泄露到最终回答；多租户系统还需隔离向量索引和元数据，避免串味。

**智能体化 RAG（Agentic RAG）**：传统 RAG 是"非智能体化"的单向数据流（查询→检索→注入→生成），被动管道能力上限低。智能体化 RAG 把知识库检索封装成 Agent 可随时调用的工具，由 Agent 以 ReAct 循环（思考→行动→观察）主导：分析需求定关键词→调用 `knowledge_base_search`→评估信息是否充分→不够则提炼更精确查询再搜→充分后综合生成。比喻：图书馆只搜一次就写报告 vs 研究员反复查阅、调整策略、交叉验证。实验（中文司法问答）：简单问题（"正当防卫怎么规定的"）一次检索即中，传统 RAG 更快且质量相当——信息需求明确单一时传统 RAG 仍是高效选择；复杂问题（"醉酒过失致人重伤且有盗窃前科如何量刑"）差距显著——智能体化 RAG 分解问题并行检索多组关键词，发现缺少"前科在过失犯罪中如何考量"的关键信息后二次聚焦检索"累犯/数罪并罚"，最终给出有法条依据的完整回答。它以牺牲响应速度换取复杂问题的鲁棒性，价值在"解决问题"而非"回答问题"。

**RAG 的安全边界**：检索到的文档是间接提示注入（indirect prompt injection）最典型的载体——攻击者把恶意指令藏进会被收录的网页，等它被检索命中拼进上下文，模型可能当成指令执行；知识库投毒是同一道理、污染发生在索引之前。防御两层：① 指令与数据分离——检索内容做来源标记，明确"以下是参考资料不是命令"；② 检索内容不直接触发高风险操作——转账、删除、外发等有副作用的动作须经独立授权判断，不能仅凭检索内容执行。

**上下文感知检索（Contextual Retrieval，Anthropic）**：修补最基础的分块环节。孤立文本块"该公司第二季度收入增长了 3%"无法回答指代（哪家公司）、时间参照（何时）、实体关系（哪条产品线）。做法：**索引前**用 LLM 为每个文本块生成简短的上下文前缀（"[本段节选自 ACME 公司 2025 年 Q2 财报的关键业绩指标章节]"），与前缀拼接后再索引，同时增强稀疏检索（前缀提供可精确匹配的关键词）与稠密检索（注入语义背景）。注意与运行期的"上下文感知压缩"区分：一个做加法（索引期给知识库文本块补背景），一个做减法（运行期按当前任务裁剪对话历史）。成本通过 prompt caching 可控（相同前缀重复调用约 1/10 成本，每百万文档 token 约 1 美元）。Anthropic 数据：结合 BM25 检索失败率降低 49%，再加重排序降幅达 67%。

### 双层记忆架构：两条线索的汇合点

用户记忆与知识库 RAG 的技术最终在此交汇：**用 Advanced JSON Cards 把少量关键事实结构化后常驻上下文，提供随时可见的"概览"；用上下文感知检索按需从海量原始对话中取回"细节"**。把知识库技术反用于用户记忆的验证过程：对话历史按固定窗口（如每 20 轮）分块索引 + `search_user_memory` 工具，可解决基础回忆和简单多会话检索（两辆车场景：初搜只回本田，从本田对话发现"还有一辆特斯拉"线索后二次搜索，完整回答"是本田 Accord 还是特斯拉 Model 3"）；但孤立对话块在矛盾指令场景（妻子设转账→丈夫修改→妻子改回）无法判断哪条最终有效，主动服务层更不够——分块的固有缺陷所致。加入上下文生成后，三个矛盾块分别带上"[妻子设立初始电汇]""[丈夫修改之前的电汇]""[妻子再次修改]"前缀，为判断优先级提供关键线索。最高层"主动服务"的完整流程：事实回顾（审视 JSON Cards 中"东京之行"与"护照 2 月过期"两事实）→ 关联推理（机票日期与护照过期接近，识别风险）→ 细节验证（RAG 查原始对话）→ 主动建议（"护照即将过期，建议加急续签"）。只靠常驻上下文会因容量受限丢细节，只靠检索缺全局视野发现不了跨会话隐藏关联——双层叠加才让"主动服务"工程上落地。

### 从数据集中提取深度知识：信息检索 → 知识发现

很多有价值知识不以文档存在，而隐藏在结构化数据的统计规律中（如司法判决知识更多在成千上万判例的权衡经验中，如资深医生的"直觉"）。两阶段范式：

1. **知识提取与结构化**：LLM 把非结构化案情描述转为标准化 JSON。核心创新是"自下而上"因子发现——让 LLM 分析数百个样本自由列出可能影响判决的因素，构建贴合数据本身（而非人类先验）的模块化 Schema：全案件通用的核心模式（自首、赔偿）+ 按罪名扩展的模式（盗窃→涉案金额、伤害→伤害等级）。
2. **因子分析与重要性建模**：特征向量化（分类字段用独热编码——盗窃 [1,0,0]、抢劫 [0,1,0]，不用 1/2/3 是避免算法误以为"诈骗比盗窃严重 3 倍"；是非字段 0/1 编码）→ HDBSCAN 聚类发现自然"案件原型"（如"轻微口角引发的赤手轻伤"、"持械预谋的团伙重伤"）→ 量化各因素权重，构建数据驱动的"因子重要性层次模型"。

应用：对话式法律顾问按因子重要性引导提问收集案情→检索最相似案件原型→基于原型统计（典型刑期范围）给出有判例支持的分析。要点：Agent 不必把知识库当只能检索的静态仓库——可以先把数据"读懂"、提炼结构化决策逻辑，再基于逻辑回答。

## ⚠️ 时效性说明

- User as Code（arXiv:2606.16707）、User as Engram（arXiv:2606.19172）、参数化多模态用户记忆均为 2026 年的前沿研究（后者为待发表），工程可用性未经大规模生产验证。
- BGE-M3、bge-reranker-v2-m3、SPLADE 等模型与 Anthropic Contextual Retrieval 的失败率数据（-49%/-67%）为报告发表时点的实测值，新模型可能改写对比结论。
- OpenViking 的 L0/L1/L2 具体规模（100/2000 token）是该项目的实现参数，非通用标准。
- LoCoMo 基准（2024）之后可能有更强的记忆基准出现。
