# 应用型智能体架构与落地模式

<p class="note-date">更新于 2026-11-05</p>
**一句话定义**：智能体的可靠性按"感知→决策→规划→执行"依次递减，落地范式是大模型 + 传统程序融合 + 人工干预接口，程序控制逻辑才是 AI 应用的核心；设计自主型智能体则需要"机器教学"思维 + DDD 战略层方法 + 明确的运行环境约束，而不是上来就堆框架和提示词。

## 核心概念

- **Agent 四要素与可靠性递减律**：感知 / 决策 / 规划 / 执行，大模型的可靠性依次递减——
  - 感知（意图识别、上下文抽取）最可靠，可直接交给大模型；
  - 决策与规划需提示词 + 微调引导，半可靠；
  - 执行必须交给传统程序。
- **开发范式**：大模型 + 传统程序融合 + 人工辅助决策。这不是过渡方案，而是长期形态，本质原因是成本与可靠性。
- **Agent = 大模型的代理人**：助理、工作流、插件、知识库四层，分别类比界面、函数、系统库、数据库。
- **自主性 ≠ 自动化**：自动化是流程硬编码，编码完成后行为不再改变；自主性系统是"柔性的"，由 AI 算法驱动，编码完成后仍能接收反馈、自动调优。自主型智能体的本质区别是**能从"所见所闻"中学习并制定管理决策**，它是更广义"自主型 AI 应用"的子集。
- **构建是团队行为**：AI 专家（懂算法）+ 应用开发专家（懂编程和领域建模）+ 领域专家（懂业务流程），三者缺一不可；AI 技术专家不等于领域解决方案专家，需保持"空杯心态"。
- **复杂自主智能体的两大组成部分**：与 AI 直接相关的部分（LLM 交互、AI 算法，可用深度强化学习 DRL 概念建模）；不与 AI 直接相关的部分（普通业务逻辑——照常用 DDD/OOD 等成熟软件方法设计）。结论：学了 LLM 开发不等于可以抛弃 DDD、OOD；没有它们指导，LLM 生成的代码和架构质量照样低。

## 关键方法/模式

### "程序控制逻辑为主"模式（判题系统案例）
核心论断：**程序控制逻辑才是 AI 应用的核心，提示词只占一半工作量**。大模型是"文科生"（有创造性但不可靠），程序是"理科生"（可靠），程序给大模型"兜底"才达到商用级。

落地流程：
1. 梳理原有人工流程，逐步评估哪些环节能用 AI；
2. 每个 AI 节点对应一个提示词（= 接口，定义输入输出职责），交互设计与提示词一一对应到函数级；
3. 能确定性的环节绝不用 AI（如编译验证直接用编译器）；
4. AI 能力不足以完成整个任务时，**降级为子任务**：不做代码转换、只识别参数，替换由程序完成。

可靠性兜底手段：
- 输出格式程序校验（分隔符 / JSON 合法性检测）；
- 二次判题程序修正 AI 误判（结果完全一致不得判错）；
- 业务规则可注入提示词（用户自定义判题规则）；
- 全流程保留人工干预接口；
- 结果缓存。

实战结果：10 倍效率提升，而客户最满意的恰是**人工干预空间**——不要追求全自动化，让 AI 嵌入原有工作流。

### 自研 Agent 底层的最小内核
- 核心就是两个能力，都用 LLM 实现：**意图识别 + 参数识别**。
- 输出协议设计：`to_sys`（调系统）/ `to_user`（答用户）二分 + 反例约束。
- 工作流用 YAML 编排，节点支持单步调试。
- 托管平台的局限：数据私有化难、存量功能需重写、双重成本 → 有存量系统的企业倾向自研。

### 内容生成类应用的标准范式
**人工定框架 + AI 填细节**。某营销文章项目三代演进：
- V1 微调灌产品信息 → 失败（输出泛化、更新成本高）；
- V2 规则引擎：人工模板限定结构 + LLM 填变量（复用原营销模板）；
- V3 再按用户画像做个性化改写。
辅助手段：分词提取实体 → 向量库语义召回 → 拼进提示词。

### 智能客服分层方案
简单问题走规则库/提示词；知识查询走 RAG；复杂意图识别与信息抽取才微调；用工作流编排意图分类 + ReAct。先覆盖 80% 高频问题，再逐步提高覆盖率。坏例专项收集回流语料（行业新概念、模型答错的问题）。

### RPA 型集成模式（微信 AI 案例）
RPA 操作客户端 + LLM 处理消息，消息按前缀路由意图。坑：轮询效率（置顶 + 读到首个有消息的会话即停）、消息无 ID 需时间戳 + 哈希比对增量、正式对外要用官方接口而非 RPA。

### 机器教学（Machine Teaching）三步法

把构建智能体看成"教师训练学生"，三步：

1. **确定要教的技能清单**：每个模块（感知、行动、监控、选择）命名并标记为技能；教的技能越多，学习成功越快（指数级差异）；约见领域专家面谈确保清单完整。
2. **设计技能如何协同**：画出技能间关系（"连连看"），记录在架构设计中。
3. **为每项技能选择最合适的决策技术**：LLM 交互、机器学习、决策表、启发式等按优劣选型，不必事事上 LLM。

配套思想：**搭建机器教学平台 + 模拟器**——智能体需要一个能安全试错、可加速时间、可并行多实例的"虚拟练习室"。能力成长五阶段（类比人类）：初学者（专家规则）→ 高级初学者（识别规则例外）→ 胜任者（行动抽象为策略并权衡）→ 精通者（编写并随机应变）→ 专家（直觉化、形成风格）。

### 运行环境决定设计

脱离环境谈架构没有意义。三类典型运行环境的约束推导：

| 环境 | 关键约束 | 设计推论 |
|---|---|---|
| 边缘云（工业场景） | 实时性、4个9高可用、资源有限、网络不稳、供电不稳、安全防护弱 | 服务完全无状态（可水平扩展的前提）；轻量级集群代替 K8s；只能部署小模型（约 14B 以下）；断点恢复；多网络通道冗余；严格认证授权 + 传输加密 + 入侵检测 |
| 企业私有云/局域网 | 条件更好的边缘云 | 同上，可适当放宽 |
| 客户端设备（PC/手机） | 资源最少、最易受攻击 | 不建议把复杂智能体做成纯客户端应用 |

### DDD 战略层指导架构

- **分层架构**：层间单向依赖，禁止循环依赖；复杂系统可用六边形架构（端口与适配器），领域模型居中，外围功能各接端口。
- **限界上下文**：划分 Agent 工作组的依据（同层内多 Agent 怎么分组），也是组件化/微服务边界。
- 参考分层范例——AI 驱动的 DevOps 系统四层：
  1. 数据输入和监测（传感器/日志/遥测，提供系统状态全貌）
  2. 决策引擎（可配置，为每个 Agent 配 AI/ML 或启发式算法）
  3. 执行和控制（API/自动化工具执行扩容、负载均衡、故障恢复）
  4. 反馈回路和持续学习（决策结果回流，长期适应性的关键）

### 与 LLM 交互的九种设计模式

本质：都是把人类思维/管理模式结构化为提示词，让 LLM 规划并调用工具迭代执行。没有最好的模式，只有最适合的模式，从用户需求出发选。

- ReAct：思考 → 行动 → 观察
- Plan and Solve / Plan and Execute：计划 → 任务列表 → 再计划
- REWOO（Reason without Observation）：计划（含依赖关系）→ 行动（全程无观察介入，节省 token）
- LLMCompiler：计划 → 并行行动 → 合并结果
- Basic Reflection：从步骤中反省学习
- Reflexion：通过强化学习式反思增强下一步规划
- LATS：ToT + 强化学习式反思
- Self-Discover：任务中自发现推理结构
- Storm：搜索大纲 → 逐主题搜索 → 汇总生成长文

工程含义：ReAct 和 Plan-and-Solve 适合任务执行型智能体；若能用 DSPy 这类自动提示词框架实现，优先用框架，避免手工提示词的维护泥潭。

### 企业级应用的工程流程（以"企业员工 AI 助理"为例）

1. 产品需求层：需求文档（详细用例）不可省——没有它 UED/测试/运维无法高效协作。
2. UI 设计与技术架构设计**并行**开展，架构师参与 UI 讨论（UI 影响架构决策）；AI 应用的 UI = 一半传统 GUI + 一半 NUI（自然语言界面，含语音 VUI）。
3. 架构文档内容：领域模型设计（最重要）、ER 设计、对外 API 设计、安全设计、高可用设计，AI 专属策略另立章节；文档随迭代持续更新。
4. 领域建模次序：**先名词（实体）后动词（操作）**；类图雏形（只有实体名）先团队讨论达成共识，再补属性、操作，再补活动图/序列图。
5. 防止"设计瘫痪"：识别出足以启动一轮迭代的实体就动手，带着开发反馈进入下一轮。
6. 开发前"扫雷"：先解决最难的两个技术不确定点（如多模态输入输出、与 Agent 平台的 API 集成），为后续开发铺路。

## 经验与常见坑

- **视频 AIGC 的几十万成本教训**：用传统控制思维做创意型任务必败；控制方式无法保证画面语义连贯；文生视频模型只生成单镜头，替换的是"逐帧绘画"环节，成片仍需人工；不要与巨头拼底层模型，做应用创新。
- 复杂智能体要**分而治之**为多个 Chain/工作流，模块复用降成本；每增加一分自主性就增加一分不可靠与成本。
- 聊天交互界面统一使界面开发成本趋零——这是低代码 Agent 平台成立的根本。
- 数据更新要有机制：行业出现新概念、模型答错的问题，都要有通道回流为语料或知识库更新。
- **陷阱一：解决方案与问题混为一谈**——现有方案只是业务问题的一种解法，别拿着锤子看什么都是钉子。
- **陷阱二：过于关注局部而忽视全局**——看到完整端到端流程前，很难识别关键技能并做权衡；过早局部优化事倍功半。
- **陷阱三（两个对立极端）**：追求完美设计走瀑布式，忽略迭代——智能体是学习系统，教之前永远不知道它学到什么；完全忽略设计规划、盲目敏捷——复杂自主智能体更像钢铁厂而非普通软件，**需要预先完整设计，但实现反馈后及时修改设计**（增量 + 迭代，而非一次性瀑布）。
- **手工提示词工程不可持续**：换模型、换指标、改管道都要修补提示词；提示词专家离职即断档，提示词越积越复杂。能自动优化就自动优化。
- 语音方案选型：传统链路 ASR→NLU→业务→NLG→TTS；Web Speech API 依赖浏览器厂商云端（中文差、延迟大），可改配私有化 ASR/TTS；多模态 LLM 直接收语音延迟更低但硬件/成本门槛高——架构上要为未来切换留灵活性。

## 术语表

| 术语 | 含义 |
|---|---|
| 意图识别 | 判断用户话语要干什么，Agent 感知层核心 |
| 参数识别/抽取 | 从话语中提取结构化参数，供程序调用 |
| 工作流编排 | 用配置（YAML 等）定义节点执行顺序与分支 |
| ReAct | 推理-行动交替的 Agent 循环模式 |
| RAG | 检索增强生成，知识查询层标配 |
| RPA | 用程序模拟人操作软件界面 |
| 人工干预接口 | AI 结果可被人审查修改的出口 |
| 机器教学 | 把构建智能体看成"教师训练学生"的设计方法论：列技能清单、设计协同、按技能选决策技术 |
| DDD | 领域驱动设计，用限界上下文与分层架构约束业务复杂度 |
| 限界上下文 | DDD 中业务边界的划分单位，用作 Agent 分组与微服务边界依据 |

## ⚠️ 时效性说明

- wxauto、Dify Chatflow、讯飞星火等为 2024 年产品示例；
- "14B 以下算小语言模型"是个人口径，非业界共识；
- 四要素可靠性递减、程序兜底、人工定框架 AI 填细节、机器教学三步法、DDD 战略层等模式为耐用结论。
