# 数据仓库与 SQL 引擎：Hive、Spark SQL 与流式 SQL

<p class="note-date">更新于 2026-11-03</p>
> 一句话概括：数据仓库让大数据人人可查——Hive 靠"SQL 嫁接 MapReduce"零创新却极大降低门槛，此后所有 SQL on Hadoop 引擎都在回答同一问题：如何在分布式数据上高效执行关系代数。

## 核心概念

- **数据仓库**：面向分析的只读数据集合，与面向事务的业务库分离；大数据平台的输出端（结果导回数据库供报表与在线读取）。
- **Hive 原理**：HiveQL → Compiler（生成算子 DAG，封装进 map/reduce）→ MapReduce 执行。**Metastore** 用关系库存元数据（表 ↔ HDFS 路径映射）——Hive 本质是"元数据 + SQL 翻译层"，自己不存数据。
- **方法论精华**：Hive 技术上无创新，**把数据库技术与 MapReduce 嫁接**才是创新，极大降低大数据分析门槛。判断一个中间件的价值，看它连接了哪两个已有世界。
- **SQL 与关系代数**：SQL 建立在关系代数五种基本操作上（并、差、积、选择、投影）；分布式 SQL 引擎的核心工程难题是**消除嵌套子查询**——嵌套子查询可等价转换为 join。
- **MapReduce 上实现 join 的思路**：map 阶段给 Value 打表标记（标明来自哪张表），相同 join Key 聚到同一 reduce，在 reduce 内做笛卡尔积。小表场景用 MapJoin（全量 Cache 小表，免 shuffle）。
- **批处理 vs 流处理的数据二分**（SQL 语义的前提）：**有界数据**（Bounded，如表/CSV，是时间窗提取后的子集）vs **无界数据**（Unbounded，传感器/支付流）；**事件时间**（数据实际产生时刻）vs **处理时间**（系统接收时刻）。传统 SQL 处理的是有界数据 + 事件时间。

## SQL 引擎谱系与原理

- **Spark SQL 血统**：Hive（HQL → MapReduce）→ Shark（改造 Hive 内存管理，快 10-100 倍，但对 Hive 的依赖阻碍 Spark 发展）→ **2014 年 Spark SQL 自研执行引擎**。
- **Catalyst 优化器**：利用 schema 信息做逻辑计划 → 物理计划优化（如把 Filter 提到 GroupBy 之前、谓词下推）。schema 元数据是优化器工作的燃料。
- **三代 API 对比**：
  - **RDD**：编译期类型安全、无 schema、需手工优化，适合非结构化数据与底层操作。
  - **DataFrame**：有 schema 但列不带类型（= DataSet[Row]），运行时才报列名错误。
  - **DataSet**（Spark 1.6+）：每列带类型，编译期类型检查，可 `people.name` 直接访问；Java 中 DataFrame 并入 DataSet。
  - 选型口诀：schema 静态且完全掌控用 DataSet；类型不确定、适配性强的通用函数用 DataFrame。
- **自研 SQL 引擎方法论（Panthera 案例）**：Hive 流程为 HiveQL → AST → 语义分析 → MR 计划；只替换语法解析器（标准 SQL → SQL AST → 自研转换器 → Hive AST），工程上装饰器模式串联 Transformer、组合模式遍历 AST。⚠️ 当今自研 SQL 引擎几乎都基于 **Apache Calcite**，不再手写 AST 转换链。
- **MPP 引擎 vs 批引擎**：Impala（MPP、全内存）实测聚合快但 join 慢甚至失败——不支持 spill（溢写）时大数据量直接崩；MapReduce 类批引擎本质对内存需求小，是"正餐兜底"。启示：**内存换速度有边界，spill 能力决定引擎处理数据量的上限**。

## 流式 SQL（Streaming SQL）

- 对象是"底部不断追加新行的表"——把无界流纳入 SQL 心智模型。
- 无统一语法规范，但算子高度同构：SELECT/WHERE/GROUP BY 直接继承 SQL；流特有三种：
  1. **窗口**：时间/长度 × 滑动/固定四组合，另有会话窗口；时间窗还可选处理时间/事件时间。
  2. **Join**：至少一方要附加窗口——任一时刻流都不完整（与 watermark 思想同源）。
  3. **Pattern 模式检测**：SQL 没有的独有算子，检测事件先后顺序模式（如"10 分钟内温度上升超 5 度"），即 CEP（复杂事件处理）。
- 优点：学习成本低、继承 SQL 优化器成果、代码简洁。趋势判断成立：让流处理像写 SQL 一样简单。

## 数据运营指标体系（数仓的"消费者"）

- 核心指标定义（务必准确）：新增用户数；**留存率 = 留存用户 / 当期新增**（3 日留存 40% 以上不错，流失率 = 1 − 留存率）；活跃用户 DAU/MAU；PV；GMV（配订单量、客单价）；**转化率 = 购买用户 / 总访问用户**。
- **漏斗图是运营最重要图表**——营收异常沿漏斗逐环节排查。
- **数据分析金字塔法**：任一问题拆 3-5 个原因、再各拆 3-5 个子原因逐层排查；凭经验锁定主链路——互联网产品主链路就在转化漏斗上。
  - 经典案例链：订单连跌 → 排除外部因素 → 查新增（渠道）→ 查日活 → 确认转化率下降 → 逐环节算环节转化率 → 定位到新用户咨询量为 0 → 查发布记录发现 SDK 更新引入 bug。
- **A/B 测试**：设计是主观的、数据是客观的。按用户 ID Hash 随机分组（大网站每特性只分约 1% 流量仍具统计代表性）。系统三件套：实验管理（分组+百分比）、流量分配（Hash）、**数据上报必须带实验 ID + 分组 ID**。
- **灰度发布**解决"A/B 通过但全量冲突"问题（特性正交假设失效）：逐批放量 + 持续监控，可直接复用 A/B 系统——把全部新特性当一个灰度实验放大到 100%。

## 术语表

| 术语 | 一句话定义 |
|---|---|
| Metastore | 存表结构与 HDFS 路径映射元数据的关系库 |
| Catalyst | Spark SQL 基于 schema 做逻辑/物理计划优化的查询优化器 |
| 谓词下推 | 把过滤条件尽量提前到数据源附近，减少参与计算的数据量 |
| DataFrame / DataSet | 带 schema 的分布式表 / 在其上增加每列编译期类型 |
| MPP | 大规模并行处理架构：各节点独立执行查询片段再汇总 |
| spill（溢写） | 内存装不下时把中间数据写到磁盘的能力，决定引擎数据量上限 |
| Streaming SQL | 用类 SQL 语法查询无界数据流的语言统称 |
| CEP / Pattern | 复杂事件处理：检测流中事件按时间先后构成的模式 |
| 留存率 | 当期新增用户在若干天后仍活跃的比例 |
| 转化漏斗 | 从访问到成交逐环节转化率的可视化，异常排查主链路 |
| A/B 测试 | 按用户 ID 随机分组的对照实验，用数据决策特性去留 |
| 灰度发布 | 逐批放量 + 持续监控的渐进式上线 |

## 经验与常见坑

- "大数据 SQL 引擎不支持嵌套子查询"已成历史，但**复杂 SQL 生成的执行计划仍需人工审视**——引擎优化不是银弹。
- 内存型 MPP 引擎做大数据量 join 前先确认 spill 能力，否则作业直接失败。
- A/B 各特性独立测试通过，全量同版本可能互相冲突——灰度发布是最后的兜底。
- 数据上报漏带实验 ID/分组 ID，整个 A/B 实验白做——埋点设计先于实验上线。
- "啤酒与尿布"式关联分析故事多考证为营销传说，引用需标注。

## ⚠️ 时效性说明

- **Hive on MapReduce 已普遍被 Hive on Tez/Spark 替代**；Hive 现定位更多是数仓元数据与 SQL 标准层。
- **交互式查询主流已是 Trino/StarRocks/ClickHouse/Doris**（Apache Doris 即原 Palo，MPP 分析库）；Impala 已边缘化（后续版本也补了溢写）。
- **Streaming SQL 事实载体已收敛**：Flink SQL 是国内实时数仓主力；Siddhi 生态萎缩，KSQL（现 ksqlDB）社区趋冷。模式检测实用入口是 Flink CEP。
- "Flink Table API/SQL 与 Spark SQL 差距明显"的判断已过期：Flink SQL 1.11 后飞速成熟，与 Spark SQL 的对比结论需反转理解。
- 阿里 Panthera 是 2010 年代内部项目，方法论（等价变换消除嵌套子查询）仍耐用，工程载体已换代（Calcite）。
