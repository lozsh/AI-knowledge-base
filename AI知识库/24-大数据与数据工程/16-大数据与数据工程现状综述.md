# 大数据与数据工程：现状综述（2026）

<p class="note-date">更新于 2026-11-06</p>

**一句话定义**：数据基建的重心已从"自建 Hadoop 时代的计算存储体系"转移到"以开放表格式为核心的湖仓一体 + 面向 AI 的新型数据需求"，表格式之争基本尘埃落定，流计算与 AI 数据管道成为两条最活跃的战线。

经典大数据体系的组件——HDFS、MapReduce、Hive、Spark、Flink、Kafka——在十年间形成了稳定的架构范式。2024–2026 年的格局变化不在于推翻这套体系，而在于三个结构性迁移：存储层收敛到少数开放表格式、云厂商围绕这些格式重新划分商业版图、以及大模型带来了"数据用于训练"这一全新的第一等需求。本文聚焦这些"现在格局"，经典原理不再复述。

## 湖仓一体：表格式之争尘埃落定

### 三种表格式与一个目录层

开放表格式（Open Table Format）在 Parquet 之上提供 ACID 事务、schema 演进与时间旅行，是湖仓一体的技术支点。当前格局：Apache Iceberg 事实胜出，Delta Lake 与 Apache Hudi 并存，Apache Paimon 主打流式场景。

| 格式 | 主导方 | 现状要点 |
|---|---|---|
| Apache Iceberg | Netflix 发起，现为 Apache 项目 | 最新版 1.12；REST Catalog 已成为标准协议，Spark/Trino/Flink/DuckDB/ClickHouse/Snowflake/BigQuery 等几乎全部主流引擎接入 |
| Delta Lake | Databricks 主导，Linux Foundation 治理 | 最新版 4.4 配套 Spark 4.2；通过 UniForm 让 Iceberg/Hudi 客户端直接读 Delta 表；70+ 组织 190+ 开发者 |
| Apache Hudi | Uber 发起 | 存量用户集中于增量摄取与 CDC 场景，社区活跃度弱于前两者 |
| Apache Paimon | Flink 社区孵化的流式数据湖格式 | 与 Flink 深度绑定，主打高频更新与流读 |

Iceberg 胜出的关键不是单点技术，而是"中立性"：在 Databricks 与 Snowflake 两强对峙的市场里，厂商中立且引擎覆盖最广的格式成为所有人的公共选择，连 Delta 也以 UniForm 主动兼容 Iceberg 读取。

### 目录（Catalog）成为新的竞争高地

表格式统一之后，竞争上移到元数据目录层。Snowflake 将其 Polaris 目录以 Apache 2.0 开源并于 2025 年捐赠给 Apache 基金会（即 Apache Polaris，实现 Iceberg REST API，支持 Spark、Trino、Flink、Doris、StarRocks 等引擎）；Databricks 则把 Unity Catalog 开源，并在 2024 年收购 Iceberg 商业公司 Tabular。至此"开放表格式 + 开放目录"成为两大厂商共同承认的公共层，差异化竞争转向其上的治理、AI 与性能服务。

### 近三年关键节点

| 时间 | 事件 |
|---|---|
| 2024-06 | Databricks 收购 Iceberg 商业公司 Tabular，湖仓商业化格局重排 |
| 2024-11 | Databricks 开源 Unity Catalog；收购并开源流式湖仓引擎 Convoy |
| 2025 上半年 | Kafka 4.0 发布，ZooKeeper 模式正式退出；Flink 发布 2.0 主线 |
| 2025 年中 | Snowflake 开源 Polaris 目录并宣布捐赠 Apache 软件基金会 |
| 2025–2026 | Iceberg REST Catalog 生态成熟，各引擎与云厂商陆续原生接入 |
| 2026 | Flink Agents 与 Flink CDC 引入 AI 处理能力，流式管道向智能体场景延伸 |

## 流计算：从 Flink 单核到多元格局

### Flink 生态

Flink 已进入 2.x 主线（当前稳定版 2.3，另维护 1.20 LTS），流批一体的 SQL 接口成为默认用法。围绕 Flink 的三个子项目构成其生态纵深：Flink CDC（3.7 稳定）承担从数据库到湖仓的实时同步，2026 年起引入可插拔模型 API 做 AI 驱动处理；Flink Agents（0.4）把 AI 智能体引入流式管道，让事件驱动的 LLM 调用成为一等公民；流式存储层则由 Apache Fluss 补位——这个源自阿里巴巴的流式存储为湖仓提供亚秒级新鲜度的实时层，基于 Arrow 列式流并内置 changelog，与 Paimon 组成"流式湖仓"组合。

### Kafka 的演进

Kafka 已完成向 KRaft 架构的迁移（4.0 起 ZooKeeper 模式退出，当前最新版 4.4），新特性集中在三处：分层存储把历史数据卸载到对象存储以降低成本；队列语义（Queues for Kafka / 共享组）补上"一条消息只被一个消费者处理"的传统队列能力，回应与云厂商队列服务的竞争；Kafka Streams 引入新的再均衡协议以减少扩缩容时的分区抖动。定位上，Kafka 愈发收缩为"事件流骨干"，其上的处理逻辑越来越多地让位给 Flink 与下述流式数据库。

### 流式数据库：把"管道 + 服务库"压成一个系统

Materialize 与 RisingWave 代表另一条路线：以增量维护的物化视图为核心，用 Postgres 线协议直接服务查询，替代"Debezium + Kafka + Flink + 服务数据库"的四件套。RisingWave（约 9.4 千 star，Apache 2.0）状态存于对象存储、内置 Iceberg REST catalog 与自动表维护，2026 年其定位进一步转向"面向智能体 AI 的事件流平台"，提供 MCP server 让 AI 智能体直接订阅与查询流数据。这一流派尚未撼动 Flink 在超大规模场景的地位，但在"实时应用 + 中等规模"场景中显著降低了架构复杂度。

## AI 时代数据基建新需求

### 向量检索的"去专用化"

2023 年专用向量数据库（Pinecone、Milvus、Weaviate、Qdrant）经历爆发，随后格局快速变化：向量索引成为通用数据库的标配功能——pgvector 让 Postgres 覆盖绝大多数中小场景，Elasticsearch、Redis、MongoDB、各家云数仓相继内建向量检索，Databricks 与 Snowflake 亦在自有平台提供向量检索服务。独立向量数据库的生存空间收缩到超大规模与专职场景；对多数团队而言，"为向量检索单独引入一套存储系统"已不再是默认决策。

### 数据用于训练 vs 用于查询

LLM 让"数据集"第一次与"数据表"平起平坐，两种用途对基建的要求截然不同。一个直观的对照是：同一家公司的数据平台上，BI 数仓里的核心表不过数千张、由 ETL 管道严格加工；而训练语料动辄数万亿 token、来自全网抓取，处理逻辑是"去重、过滤、打分"而非"建模、建模口径"。

| 维度 | 用于查询（BI/分析） | 用于训练（LLM 语料） |
|---|---|---|
| 核心操作 | SQL 聚合、join、行级更新 | 抓取、清洗、去重、过滤、分词 |
| 质量标准 | 一致性、及时性、口径正确 | 多样性、毒性过滤、去重率、许可合规 |
| 典型形态 | 表格式湖仓 + 数仓建模 | 文档级语料管道（如 FineWeb 类的大规模清洗流程） |
| 消费者 | 分析师、BI 工具、Text-to-SQL | 训练框架、评测集 |
| 版本管理 | 快照/时间旅行 | 数据集版本卡、训练数据溯源 |

这促使数据工程栈向两侧延伸：向上承接网页级抓取与非结构化解析，向下服务评测与数据溯源。"数据工程"与"模型工程"的边界正被这条语料管道重新划分。

### 数据质量与治理：从"报表可信"到"模型可信"

LLM 时代给数据治理增加了一层新语义：训练语料的许可合规与污染检测、RAG 知识库的新鲜度与权限继承、以及模型生成内容的可溯源。传统的元数据管理、血缘与质量监控体系仍是地基，但消费方从分析师扩展到了模型——坏数据不再只产出错误报表，而是直接固化为模型能力缺陷或泄露风险。

### Text-to-SQL 与数据对话

自然语言查数是"数据对话"最被寄予厚望的入口，但基准数据揭示了理想与现实的落差：在 Spider 1.0 这类学术数据集上前沿模型可达 86% 以上，而 2024 年末发布、ICLR 2025 Oral 的企业级基准 Spider 2.0（632 个真实工作流，数据库常超千列、托管于 BigQuery/Snowflake）上，发布时 o1-preview 仅解决 17.0%、GPT-4o 仅 10.1%。落差来自企业真实环境的长尾 schema、方言差异与多步任务。当前的主流做法是转向 agent 化方案——schema 检索、语义层/指标层约束、执行结果校验与多轮自我修正——而非追求端到端直译。

## 云厂商格局与开源商业化

| 厂商 | 关键动作 | 战略意图 |
|---|---|---|
| Databricks | 收购 Tabular（2024）；开源 Unity Catalog（2024）；收购 Neon（2025）；开源流式湖仓引擎 Convoy（2024 末） | 拥抱 Iceberg 以消除迁移壁垒，把控制点从存储格式上移到目录与 AI 平台 |
| Snowflake | 开源并捐赠 Polaris 至 Apache（2025）；收购 Postgres 公司 Crunchy Data（2025） | 以开放目录换取多引擎互操作，补齐事务型 Postgres 能力 |
| 云上自研 | AWS/S3 + Athena/Glue、Google BigLake 均原生拥抱 Iceberg | 云厂商以存储与托管服务承接开放格式，而非与开放格式对抗 |
| 国内生态 | 阿里开源 Fluss 并捐赠 Apache；StarRocks/Doris/SelectDB 深度兼容 Iceberg/Paimon | 湖仓 + 实时分析的一体化栈竞争 |

开源商业化的整体逻辑与数据库历史上的剧本一致：存储与表格式充分开源以建立事实标准，商业价值沉淀在托管服务、目录治理、安全与 AI 集成层。

## 趋势判断

- **Iceberg 成为最大公约数**：表格式战争实质结束，未来的分歧点在目录层与计算引擎，数据可迁移性大幅提升将进一步压低存储层利润、抬升服务层价值。
- **湖仓的"实时层"补齐**：Fluss 类流式存储 + Paimon/Iceberg + Flink/StarRocks 的组合，正在把"秒级新鲜的湖"从愿景变成默认架构，批流界限继续消融。
- **数据平台为 AI 重写需求清单**：语料管道、评测数据集管理、向量检索、MCP 式数据访问接口会逐步成为数据平台的标配模块，而非独立于数仓之外的外挂。
- **Text-to-SQL 走 agent + 语义层路线**：自然语言不会直接替换 SQL，而是"语义层定义业务口径、agent 负责编排与校验"的混合形态率先在内部数据对话场景落地。
- **数据平台与智能体直接对接**：MCP 等协议让智能体成为数据平台的新一类"用户"，流式平台与湖仓正在为其提供订阅、查询与工具化访问接口，"数据即工具"是继"数据即服务"之后的下一层抽象。
- **开放格式红利转向治理与 AI 层**：当存储与表格式充分开放，厂商竞争将集中于目录治理、权限血缘、语料管道与模型集成，数据工程师的技能重心亦随之从"调 Spark"上移到"定义语义层与数据契约"。
