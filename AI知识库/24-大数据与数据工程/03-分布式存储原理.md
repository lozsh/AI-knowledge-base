# 分布式存储原理：从 RAID 到 HDFS、HBase

<p class="note-date">更新于 2026-11-03</p>
> 一句话概括：分布式存储 = 把 RAID 的"分片并行 + 冗余容错"从单机放大到集群（HDFS），再叠加 LSM 写优化与列族模型（HBase/Bigtable），一致性难题则交给 CAP 取舍与多数派协议（ZooKeeper）。

## 核心概念

- **RAID：单机内解决存储三问题（容量/速度/可靠）**
  - RAID 0：分片并发写（快但零冗余）；RAID 1：镜像（利用率 50%）；RAID 10：先镜像再分片；RAID 5：校验螺旋分散（最常用）；RAID 6：双校验容忍坏两块。
  - **RAID = 单机内垂直伸缩；HDFS = 集群级水平伸缩**——把分片并行 + 冗余容错思想放大到集群。
- **HDFS 定位**：管理数千服务器、数万块磁盘的 PB 级存储。**不是最好的存储，却是最重要的存储**——数据是最难替代的资产，新技术必须兼容它才能获取数据。
- **Bigtable/HBase 哲学**：数据库只管存数据，业务逻辑交给应用。（对应链：GFS→HDFS、MapReduce→Hadoop、Bigtable→HBase。）

## HDFS 架构与原理

- 组件分工：**DataNode** 存数据块；**NameNode** 管元数据（路径、BlockID、块位置），角色类似文件分配表。
- **Block 设计**：缺省 128MB 大块（减少寻址开销占比）、**3 副本**、跨服务器/机架分布（机架感知：2 副本同机架 + 1 副本异机架）。
- **四层容错**（由内向外）：
  1. 数据块校验和（CheckSum）：读取时重算，失败自动换副本；
  2. 坏盘上报，自动补齐副本数；
  3. DataNode 心跳超时判死，NameNode 指挥复制其数据块；
  4. NameNode 自身故障最致命——主从热备 + ZooKeeper 选主 + shared edits 同步元数据；DataNode 向双 NameNode 发心跳但只受主控制。
- **脑裂（Split-Brain）**：主从切换中误判主宕机、从节点接管，导致双主同时写——失效转移的核心难题。
- **可用性三策略**（通用）：冗余备份、失效转移（难点在失效鉴定与选主）、降级限流（降级应对可预知场景如大促关评价保下单；限流应对突发流量）。

## HBase / Bigtable：宽表与列族

- **Region 分片**：数据按 RowKey 区间切 **HRegion**，RegionServer 承载多 Region；Region 超阈值自动分裂迁移，实现负载均衡与线性伸缩。
- **关键设计：HMaster 不走数据路径**——客户端经 ZooKeeper 定位 Region 位置后**直连 RegionServer** 读写；Master 只负责元数据管理与调度。Master 宕机不影响读写。
- **列族（Column Family）模型**：建表只定义列族，字段在写入时才指定——"字段名+值"作为 KV 存储，天然支持百万级字段、schema 随需演化。
  - 代价：只能按 RowKey 查、二级索引难、无跨行事务。
- **LSM 树（Log-Structured Merge Tree）**：针对机械盘随机写慢——写入全部进内存排序树（删除写墓碑标记），超阈值后异步与磁盘逐层合并，**以连续写代替随机写**。适合写多读近期场景；是 RocksDB、Cassandra、HBase 的共同内核。
- **RowKey 设计直接决定性能**：散列防热点、前缀利扫描；设计不当则数据倾斜到个别 RegionServer。

## ZooKeeper 与分布式一致性

- 要解决的根本问题：主从切换时各节点判断不一致导致**脑裂**。
- **CAP 定理**（Brewer 2000 提出，Gilbert & Lynch 2002 证明）：一致性 C（线性一致性：后发操作必须看到更新后的状态）、可用性 A（任意非故障节点必须响应）、分区容错 P（容忍网络丢消息）三者不可兼得。**现代网络下 P 基本是必选项，实际在 C/A 之间取舍**。
  - CP：Bigtable/HBase/MongoDB/Redis；AP：Dynamo/Cassandra；ZooKeeper 属 CP。
  - ⚠️ 陷阱：系统宣称的"强一致"未必是论文定义的线性一致性；Kafka（同机房 replication、分区时踢出失联副本）在分区场景可能丢数据，是否算 CA/P 长期有争论。
- **ZAB 协议**：Paxos 多数派表决的工程简化——集群选 Leader，写请求全部经 Leader Propose → 多数 ACK → Commit；读可由任意 Follower 直接返回。
- **数据模型**：树状 ZNode + watch 监听 + **EPHEMERAL 临时节点**（会话断即删——选主的基石）。
- **四大应用场景**：选主（抢临时节点 + watch 前任）、配置中心、分布式锁、心跳检测。HDFS HA、HBase、Storm、Kafka 均依赖它。
- **反直觉性能特性**：全量数据 + 每写必多数表决，**写性能随节点数增加而下降**——集群宜 3/5 台奇数小规模，不要为了"高可用"盲目加节点。
- 拜占庭（恶意节点）场景 Paxos 类协议失效，需区块链式工作量证明（>51% 算力防线）——这是另一类问题域。

## 分布式系统的四项 SLA 指标（衡量存储/服务质量的标尺）

- **可用性**：99.9% = 每天 86.4 秒中断；四个 9（高可用）= 每天约 8.64 秒；五个 9 = 每年约 5 分钟。
- **准确性**：错误率 = 内部错误请求数 / 有效请求总数。
- **系统容量**：QPS/RPS。测算三法：限流上限推测（阈值过高会堆积请求致 OOM）、性能测试（⚠️ 同参数请求命中缓存可虚高 10 倍）、日志峰值分析（只能给下限）。
- **延迟**：p95/p99 百分位。缓存命中率 90% 时，p99 就是回源数据库的长尾时间——优化长尾靠缓存策略与索引。
- 配套三指标：**可扩展性**（水平扩展提升可用性但增加通信/一致性复杂度）、**一致性**（强一致牺牲延迟；**最终一致性 = 弱一致的特例**，无新更新则最终读到最新值——银行转账、12306 购票实际都是最终一致）、**持久性**（靠数据复制；消息持久性 = 节点故障恢复后消息不丢、仍被处理）。

## 术语表

| 术语 | 一句话定义 |
|---|---|
| Block | HDFS 存储单元，缺省 128MB、3 副本、机架感知分布 |
| NameNode / DataNode | HDFS 元数据管理节点 / 数据存储节点 |
| 心跳 | 从节点定期上报存活，超时判死触发故障转移 |
| 脑裂 | 主从切换中误判导致双主同时写 |
| HRegion / RegionServer | HBase 按 RowKey 区间的分片 / 承载分片的物理节点 |
| 列族 | 建表单位，字段动态写入，支持 schema 演化 |
| LSM 树 | 写入先进内存排序树再异步合并落盘，以连续写代替随机写 |
| 墓碑标记 | LSM 中删除的实现方式：先记删除标记，合并时真正清除 |
| ZooKeeper / ZAB | 分布式协调服务（选主/锁/配置）；其简化的 Paxos 原子广播协议 |
| EPHEMERAL 节点 | 会话断开即自动删除的临时节点，选主机制基石 |
| CAP | 一致性/可用性/分区容错三者不可兼得，P 必选 |
| 线性一致性 | 后发操作必须看到先发更新效果的最强单机序语义 |
| 最终一致性 | 无新更新则最终全部读到最新值（弱一致特例） |
| SLA | 服务承诺，常用可用性/准确性/容量/延迟四指标度量 |
| p95/p99 | 95%/99% 的请求响应时间低于该值的百分位延迟 |

## 经验与常见坑

- 可用性三板斧中失效转移最难——难在"失效鉴定"：网络分区时无法区分"对方死了"和"网络断了"，靠多数派表决 + 临时节点化解。
- ZooKeeper 不是数据库也不是消息队列，只做小体量元数据协调；塞业务数据进去会拖垮写性能。
- HBase 二级索引难是列族模型的固有代价——查询模式要先想清楚再设计 RowKey，而不是建完表再想怎么查。
- 性能测试的缓存陷阱：压测用同一类参数会大量命中缓存，QPS 虚高可达 10 倍；日志分析只能给容量下限，两者要结合。
- 限流阈值不是越大越好：过高会让请求堆积，把服务器拖垮。

## ⚠️ 时效性说明

- Kafka 用 ZooKeeper 选举 leader 的描述已过时：Kafka 2.8 起用 **KRaft** 模式逐步移除 ZooKeeper。
- RAID 在云环境已被分布式三副本/纠删码大量替代；HDD 时代经验值（盘寿命约一年等）在 SSD + 高带宽网络下大幅改善。
- "HDFS 是存储王者"的判断弱化中：存算分离架构下对象存储成为数仓底座，但 HDFS 的原理设计（分块、副本、心跳、元数据分离）仍是分布式存储的教科书级经典设计。
