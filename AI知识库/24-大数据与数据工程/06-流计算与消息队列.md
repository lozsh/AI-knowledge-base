# 流计算与消息队列：Kafka、窗口模型与 Exactly-Once

<p class="note-date">更新于 2026-11-05</p>
> 一句话概括：流计算的全部难点浓缩为三件事——用发布-订阅解耦生产消费（Kafka）、用事件时间 + 窗口 + 水位线对抗乱序与迟到（Dataflow Model）、在完整性与延迟之间做取舍。

## 核心概念

- **流处理的定义**：持续处理无界数据（Unbounded Data），毫秒级（实时）或分钟级（准实时）响应。**"能否在毫秒间隔内产出逻辑正确结果"是实时与准实时的分界**。批处理则处理有界数据、关心事件时间、延迟小时~天级。
- **事件时间 vs 处理时间**：数据实际产生时刻 vs 系统接收时刻。两者之差就是流处理乱序与迟到问题的根源（典型例子：地下车库没信号，12:05 付款 12:15 才同步成功）。离线管道里二者通常视为相等，流处理必须区分。
- **流处理的本质权衡：数据完整性与延迟性不可兼得**——等得越久结果越完整，出结果越快遗漏越多。所有窗口/水位线/触发器机制都是这个权衡的具体化。

## 消息队列与发布-订阅模式

- **发布-订阅（Pub/Sub）模式**：消息（任意格式）+ 消息队列（持久化缓冲 Durable Buffer，确认收到才删除）；发布者与订阅者互不知晓对方存在，松耦合、高伸缩（LinkedIn 2016 年维护近 1400 个消息队列）。
- **对照组：观察者模式**——组件间同步 API 直接调用、紧耦合，每接入一个新消费方都要改发布方代码、延迟递增。这是"为什么要上消息队列"的最短答案。
- **Kafka 核心机制**：Producer/Consumer/Topic；用 **Log offset** 确认消费（收到 offset 10001 即认为 ≤10001 全部收到，之后可重发）——**可重放性**是 Kafka 区别于传统 MQ 的关键，也是 Kappa 架构的基石。
- **适用四场景**：广播给大量接收方；组件与多个异构组件通信；发送后无需实时响应；只需最终一致性。**需实时同步响应的场景不要用**。
- ⚠️ Kafka 早期靠 ZooKeeper 管理，2.8 起用 KRaft 模式逐步移除 ZooKeeper。

## 流计算框架谱系

| 框架 | 模型 | 延迟 | 现状 |
|---|---|---|---|
| Storm | 逐事件真流 | 毫秒级 | ⚠️ 已被 Flink 基本淘汰 |
| Spark Streaming (DStream) | 微批：把流按 batch interval 切成 RDD 序列 | 秒级 | ⚠️ 已废弃，官方转 Structured Streaming |
| Spark Structured Streaming | 把流建模为无限增长的关系表，复用 DataFrame/SQL 引擎 | 约 100ms（Continuous 模式毫秒级但算子受限） | Spark 官方流方案 |
| Flink | 逐事件连续流（Stream + Operator 构成 Dataflow DAG） | 毫秒级 | ⭐ 国内实时计算事实标准 |

- **DStream 关键参数**：滑动窗口两参数——窗口长度、滑动间隔，都必须是 batch interval 的整数倍。
- **Structured Streaming 三种输出模式**：Complete（全量更新）/ Append（只写新增行）/ Update（只写被更新的行）；不存输入数据，只存更新输出表所需状态；事件时间即表中的一列，`window(ts, "1 minute", "10 seconds")` 直接做窗口聚合；支持端到端 exactly-once。
- **Spark Streaming vs Flink 的理念差异**：Spark"用批模拟流"（流是批的特例）vs Flink"用流模拟批"（批是流的特例）——后者模型扩展性更好，能原生支持运行时有环数据流（ML 迭代友好）。
- **投递语义三档**：at-most-once / at-least-once（可重复）/ exactly-once（恰好一次）。实现思路：结果写入支持幂等/事务的存储 + 检查点恢复重放；Flink 用分布式快照做端到端 exactly-once。这是三框架对比的核心维度。

## 历史源流：从 S4、Storm 到 MillWheel

现代流引擎的概念都有历史出处。为什么需要专门的流式系统：MapReduce 为高吞吐设计、无低延迟考虑，且输入是边界明确的数据；每分钟跑一次 MapReduce 会遭遇双重灾难——任务固定开销占比畸高 + 输入文件极度碎片化丧失顺序读优势。广告点击率、热搜这类"分钟级反馈"需求催生了流式计算。

| 系统 | 年份 | 架构 | 消息保障 | 关键贡献/短板 |
|---|---|---|---|---|
| S4 | 2010 (Yahoo) | 无中心完全对称，PE 对象 | 基本没有 | 首创 DAG 模型；无时间窗口、容错丢状态、不支持动态扩容 |
| Storm | 2011 (Twitter) | Nimbus+Supervisor+Worker | 至少一次（Acker 异或追踪） | 逻辑与并行度解耦；仍无状态持久化、无事件时间窗口 |
| MillWheel | 2013 (Google) | Computation+Key 分段 | 正好一次 | 低水位、状态/Checkpoint 持久化、租约防僵尸进程 |

- **Storm 的关键一跃**：用 Acker 异或校验码追踪 Tuple 树是否全部处理完（每树仅 16 字节状态），做到"至少一次"——但它的进步止步于"知道丢了要重发"，没有状态持久化，重发也续不上。
- **MillWheel 的三件套**（第二代流式系统的台阶）：
  - 模型：消息 =（Key, Value, Timestamp）三元组；Key 按 Bigtable Tablet 式**分段**调度，保留"Key 级状态绑定"又避免 S4 海量 PE 对象问题。
  - **低水位（Low Watermark）**：每个 Computation 未处理完消息的最早时间戳，取 min(自身 oldest work, 各上游低水位)，由 Injector 模块全局收集分发，系统据此判断"某时间点前的数据都到齐了没"——水位线概念的直系祖先。实测仅 0.001% 的日志晚到水位之后，且因数据全持久化仍可纠正。
  - **正好一次**：收到消息先 BloomFilter 分段去重 → 执行业务逻辑 → 所有状态变更一次性提交 Bigtable/Spanner → 回 Ack → 下游发送前先写 **Checkpoint**（类 WAL）。Checkpoint 必须在发送前落盘：同一时间窗口内先发消息 X 再发值不同的 Y 时，网络乱序会让下游无法去重——只有"先持久化再重放"能保证一致。无状态/幂等计算可降级为弱保障，只需下游做强保障。
  - **租约防僵尸进程**：Master 网络分区时在新节点重启 Computation，旧进程可能还活着并持有 Timer——每个进程持租约 Token，写入必须带 Token，新进程启动即作废旧租约。这是所有分布式系统保证 **Single-Writer** 的通用机制（GFS/Bigtable 同款）。
- 承前启后的两条通用经验：**至少一次 + 消费端幂等 = 正好一次**（去重可用 BloomFilter 按时间窗切片，计费级场景需唯一键/状态存储级去重）；**把故障恢复要用的状态持久化，是一切容错的地基**。异或追踪、租约、WAL 式 Checkpoint 都是可移植的小巧思，在任何自研流式/任务系统里都能复用。

## Dataflow Model：窗口、水位线与触发器（最耐用的思想）

Google 2015 年 Dataflow Model 论文提出的 **WWWH 四问**，是所有现代流引擎（Flink/Beam/Structured Streaming）的概念底座：

- **What**：做什么计算 → Transform 回答。
- **Where**：事件时间的什么范围 → **窗口**回答。
- **When**：处理时间的何时输出 → **水位线 + 触发器**回答。
- **How**：后续结果如何修正先前结果 → **累加模式**回答。

配套概念：

- **窗口（Window）**：按事件时间把无界数据切成有限集合。三种：
  1. **固定窗口**（Tumbling）：定长、不重叠，元素只落一个窗口。
  2. **滑动窗口**（Sliding）：长度 + 滑动周期；周期 < 长度时元素可落多窗，周期 = 长度退化为固定窗口。
  3. **会话窗口**（Sessions）：无固定长度，按 Gap Duration 动态成组（相邻元素时间戳差 ≤ gap 归同一会话），适合用户活跃行为分析。
  - 批处理 = 全局窗口（无穷大到无穷大）的特例；**处理无界数据必须显式设非全局窗口**。
- **水位线（Watermark）**：声明"事件时间 < X 的数据已收齐"的**输入完整性度量**。有了它才有依据判定迟到数据与触发输出。
- **触发器（Trigger）**：何时真正物化窗口结果。四种：事件时间触发（watermark 过窗尾）、处理时间触发（定时）、数据驱动触发（元素计数，如每 100 条）、复合触发器（早触发 + 迟到补充）。
- **累加模式与窗格（Pane）**：一次触发产生的结果叫窗格；多次触发间**丢弃**（discarding，各窗格独立）或**累积**（accumulating，后窗格含此前全部）。
- 实战参数化示例（Facebook 游戏周榜）：一周固定窗口 + watermark 过窗尾后早触发（每 5 分钟刷新）+ 允许迟到 20 小时（按业务物理上界估算，作者以最长直飞航班 19 小时为参照）+ 丢弃式窗格。

## 经验与常见坑

- **迟到数据上界要按业务物理约束估算**，不能拍脑袋：物流数据按运输时长、游戏数据按跨时区飞行时长。
- 触发越频繁延迟越小，但迟到数据遗漏越多——完整性/延迟的权衡要显式配置，不要用引擎默认值糊弄。
- Spark 流处理修改业务逻辑要删 checkpoint 从头算；慢节点会卡住整个 batch（微批模式的固有缺陷）。
- 有界数据源读入时所有元素默认同一时间戳 + 全局窗口；无界数据不设窗口运行时直接抛异常。
- 流数据的时间戳要显式声明来源（如 Kafka 的 LogAppendTime vs 自带事件时间），两种时间混用是排查乱序问题的第一现场。
- 消息队列不是数据库：Kafka 作唯一存储（Kappa）时，一年数据 × 3 副本容量巨大，重放从 earliest offset 耗时长。
- 大规模系统 90% 的时间花在异常处理上——数据就是钱，每一步要记录数据条数与操作者，监控先行。

## 术语表

| 术语 | 一句话定义 |
|---|---|
| Pub/Sub | 发布者与订阅者经消息队列异步解耦通信，互不知晓 |
| Log offset | Kafka 用连续编号确认消费进度、支持重放的机制 |
| DStream | Spark Streaming 中按时间片切分的 RDD 序列抽象 |
| 微批（Micro-batch） | 把流切成小批依次批处理的流处理实现思想 |
| Exactly-Once | 每条消息恰好被处理一次的效果（幂等/事务 + 重放实现） |
| 窗口（固定/滑动/会话） | 按事件时间切分无界数据的三种方式 |
| Watermark | 声明"事件时间 < X 的数据已收齐"的完整性度量 |
| Trigger | 决定窗口结果何时被物化计算的信号 |
| Pane / 累加模式 | 一次触发产生的窗口结果 / 多窗格间丢弃或累积的策略 |
| CEP / Pattern | 复杂事件处理：检测流中事件的先后模式 |
| 边缘计算 | 在离设备最近的网关上先做简单实时计算再上云 |

## ⚠️ 时效性说明

- **Storm 已被 Flink 基本淘汰**；Spark Streaming（DStream）官方废弃，学 Spark 流处理直接学 Structured Streaming。
- Spark 2.3 的 Continuous Processing 至今仅支持 map 类有限算子，毫秒级真流场景实际选择是 Flink。
- 国内实时计算事实标准是 **Flink**（阿里 Blink 已回归社区并主导演进）；"Spark SQL 更成熟"的对比结论已反转。
- Google Cloud IoT Core 已于 2023 年停服；物联网接入层现以 AWS IoT Core/Azure IoT Hub 或私有方案为主。
- Apache Beam 在生产中未成主流（活跃于 Google Cloud Dataflow 用户群），但其窗口/水位线/触发器概念已被 Flink 完整吸收——**学思想比学 SDK 更耐用**。
