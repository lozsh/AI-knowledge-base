# 分布式计算范式：MapReduce、Spark RDD 与数据倾斜

<p class="note-date">更新于 2026-11-03</p>
> 一句话概括：分布式计算的范式演进 = MapReduce 两阶段（教会世界分而治之）→ DAG + 内存计算（Spark）→ 流批一体（Flink/Beam），不变的核心是 shuffle 与数据倾斜治理。

## 核心概念

- **MapReduce 既是编程模型又是计算框架**：模型定义怎么写（map 输入 `<k,v>` 输出 `<k',v'>`，框架按键合并成 `<k', v列表>` 交给 reduce）；框架负责集群执行。WordCount 与 SQL 的 GROUP BY 同构（map 输出 `<分组键, 1>`，reduce 求和）。
- **Shuffle 的本质**：**把分布在不同服务器上的相关数据合并到一起做下一步计算**。map 输出写本地盘，Partitioner 按 `hash(key) % numReduceTasks` 决定去向，相同 Key 必到同一 Reduce，Reduce 端排序合并。**shuffle 是批处理最关键也最耗性能的环节**，也是所有引擎（MR/Spark/Flink）共同的核心。
- **掉队者问题（Straggler）**：分片函数选择不当引发机器负载不均（如按年龄分片导致 20-30 岁热点堆积），拖慢整个作业。解法：profiling 定位 + 动态分片（dynamic sharding）。
- **为何 MapReduce 被淘汰（两大根因）**：
  1. **维护成本高**：真实商用流程动辄 10 个子任务，每步都可能出错，需紧耦合状态机编排（orchestration）；
  2. **时间性能难调**：Google 2007-2012 年把 1PB 排序从 12 小时优化到 0.5 小时花了 5 年。
- **下一代技术五条设计思路**（FlumeJava/Beam 的设计源头）：① 用 **DAG** 抽象多步骤处理（节点=数据集，边=变换）；② 自动性能优化（合并重复子图、剪除无关分支、弹性分配资源）；③ 描述语言与运行引擎解耦（client-server，类比 TF 计算图与 runtime）；④ 统一批流编程模型；⑤ 架构级异常处理与数据监控（Google 内部调研：**大规模数据处理系统 90% 的时间花在异常处理上**）。

## YARN：资源调度与执行解耦

- 动因：Hadoop 1 中资源调度与 MR 执行耦合，无法把集群共享给 Spark/Storm。
- 架构：**ResourceManager**（全局调度，含 Fair/Capacity 调度器）+ **NodeManager**（节点级管理）；资源单位 **Container**（一定量内存 + CPU）。
- 流程：提交应用 → RM 分配首容器启动 **ApplicationMaster** → AM 申请容器 → AM 与 NodeManager 通信跑任务 → 完成注销。各计算框架各写各的 AM 即可共享同一集群。
- 设计精髓：**依赖倒转**——YARN 依赖 AM 抽象规范而非具体框架（类比 Tomcat 与 J2EE）。
- ⚠️ 云原生时代 Kubernetes 在容器化/流式场景大量替代 YARN。

## Spark：RDD 与 DAG

- **因果洞察**：不是 MR 慢催生了 Spark，而是 Spark 出现后人们才意识到 MR 慢。公开数据：Databricks 排序 100TB 用 23 分钟 vs Hadoop 72 分钟，只用 1/10 计算资源。
- **RDD（弹性分布式数据集）** = 已被分区、不可变、可并行操作的数据集合。三特性皆有分布式动机：
  1. **分区**：逻辑上是"大数组"（元素=分区），物理上每分区指向某节点的数据块；内存不够才落盘。
  2. **不可变**：只能通过 Transformation 产生新 RDD；只需记录**血缘（依赖关系）**而非数据本身，故障时从上一步重算——"弹性"的来源。
  3. **并行操作**：分区天然支持分布式并行。
- **窄依赖 vs 宽依赖**（判断依据：父分区是否被多个子分区使用）：
  - 窄依赖（map/filter/union）：可链式**流水线执行**；故障恢复只需重算丢失的父分区。
  - 宽依赖（groupBy/普通 join）：需全部父分区就绪、跨节点 shuffle，恢复代价高。
- **Stage 划分依据是 shuffle（宽依赖）而非转换函数**：窄依赖连成一个 stage，宽依赖切出新 stage；每 stage 按分片数生成 task；遇到 action 生成 job。
- **惰性求值**：Transformation 只记依赖不计算，遇 Action（collect/reduce/count/first）才从链条末端回溯执行。写 N 个 transform 不执行 N 次计算。
- **Checkpoint vs persist/cache**：checkpoint 把耗时 RDD 落盘并**切断血缘**（容错恢复用）；persist 保留血缘（避免重复计算，分区丢失可自动重算）。
- **Spark 更高效三因**：① DAG 多阶段替代 MR 僵化两阶段，减少 HDFS 访问与调度次数；② 中间结果优先内存；③ 编程模型面向数据（想 RDD 如何逐步变换）而非面向过程。**本质仍是 MapReduce 模型的更优雅实现**。
- 执行模型差异：Spark **task 级多线程**（同节点任务跑在一个 JVM）vs MapReduce 多进程——启动快、CPU 利用率高。
- 定位澄清：Spark 只是 MapReduce 的替代，仍依赖 HDFS/HBase 存数据、YARN 管资源。
- RDD 转换/行动算子、血缘与内存管理的执行心智模型细节见 08 篇《Spark 核心原理与心智模型》；倾斜定位与 Join 调优的完整方法论见 10 篇《Spark 数据倾斜与 Join 调优》。

## Spark vs Flink（批流两条路线）

| 维度 | Spark | Flink |
|---|---|---|
| 流处理思想 | 微批（用批模拟流），秒级延迟 | 逐事件真流（用流模拟批），毫秒级 |
| 窗口 | 只支持时间窗口 | 时间/数据驱动/自定义，极灵活 |
| 迭代计算 | 无环 DAG 表达（不佳） | 原生支持运行时有环数据流（ML 友好） |
| SQL | 传统上更成熟 | 后来快速成熟（见 04 篇时效说明） |
| 生态 | 社区最大最全 | 阿里收购 Data Artisans 后国内主导 |

- 理念差异：Flink"批是流的特例"的模型扩展性优于 Spark"流是批的特例"。
- 选型：超大规模复杂批处理 + 秒级流 → Spark 一站式；毫秒级实时 → Flink。
- Flink 数据传输两形态与 RDD 依赖对应：one-to-one = 窄依赖；redistributing = 宽依赖。

## Apache Beam：引擎无关的编程模型

- 血统：FlumeJava（2008，批）+ MillWheel（2013，流）→ **Dataflow Model 论文（2015）** → Apache Beam（2016，Google 联合多家捐给 Apache）。Beam = Batch + StrEAM，**本身不是执行引擎**，是统一编程模型 + SDK，经 Runner 跑在 Spark/Flink/Dataflow 等后端（类比 SQL 之于数据库、ONNX 之于推理框架）。
- **核心抽象**：
  - **PCollection**：唯一数据抽象（≈RDD 但天生统一有界/无界）；无序、不可变、延迟执行（写 N 个 Transform 只构建执行计划 DAG）；自定义类型必须注册 **Coder**（序列化器）。
  - **Transform**：DAG 节点（可多输入多输出），PCollection 是边；最常用 **ParDo**（单元素进、0/1/多元素出，实战约 80% 流水线只需它）+ GroupByKey。
  - **Pipeline**：读 → N 步转换 → 写的逻辑封装；执行时数据切 **Bundle**，单元素失败整个 Bundle 重算（含关联上游）。
- **不要在一个 DoFn 里塞所有逻辑**——分步表达，交给优化器合并（MSCR Fusion）；有状态 DoFn 被并行到几千实例时，会把下游数据库 QPS 放大数千倍。
- Beam 的价值在思想而非 SDK：WWWH 模型与窗口/水位线已被 Flink 完整吸收（详见 05 篇）。

## 数据倾斜与性能优化方法论

- **数据倾斜是所有分布式计算引擎的通病**：热点 Key（空值、爆款商品）被 shuffle 到同一节点。经典案例：`user_id=null` 的几亿条记录 shuffle 到同一 reduce 跑了两天，一条 `where` 过滤解决。治理手段：空值单独处理、热点 Key 打散加盐、MapJoin 小表广播。
- **两条铁律**：不能优化没经过性能测试的软件；不能优化不了解架构的软件。闭环 = 测试 → 定位瓶颈 → 找根因 → 修改 → 对比。
- **优化五层次**（由高到低）：SQL 写法 → 数据倾斜 → 代码 → 参数 → 源码/硬件。
- 瓶颈可能在最不起眼的层：千兆网卡（125MB/s）可碾压整个集群吞吐；OS 的 transparent huge pages 可把 CPU sys 态推到 80%；JAR 包 120 进程重复下载 17MB 耗 14 秒，本地缓存后 1 秒内。

## 经验与常见坑

- `collect()` 慎用：把全部数据载入 Driver 内存必 OOM，取样本用 `take()`。
- 复用型 RDD 不 persist，则每个 action 都从头重算整条血缘。
- 分片/分区键要选分布均匀的字段；电商长尾数据（少量 item 占大半销量）要专门设计 hash。
- 分而治之的正确性陷阱：各机器只取本地 Top K 再汇总时，"总量第一但很少进各时段 Top K"的元素会漏——**局部聚合的口径必须审视**。
- 选型思维：先从问题独立思考框架应有什么，再看开源对答案；框架会过时，抽象（DAG、批流统一、WWWH）不会。

## ⚠️ 时效性说明

- MapReduce 编程已淘汰，JobTracker/TaskTracker 被 YARN 取代；学习价值在理解 shuffle 与分而治之本质。
- "Spark 快 100 倍"是 2014 年迭代场景宣传数字，只具历史意义；"Spark SQL 全面领先 Flink SQL"的结论已反转——Flink SQL 现为国内实时数仓主力。
- Spark Streaming（DStream）已废弃，官方转向 Structured Streaming；Continuous Processing 模式至今算子受限，毫秒级真流场景实际选 Flink。
- Apache Beam 未成为主流生产选择（活跃用户集中在 Google Cloud Dataflow），国内批流统一事实标准是 Flink；学 Beam 的价值是 Dataflow Model 思想。
- Google 内部 2016 年"新人改教 FlumeJava"的口径已成历史脉络，现在主推 Dataflow/BigQuery 体系。
