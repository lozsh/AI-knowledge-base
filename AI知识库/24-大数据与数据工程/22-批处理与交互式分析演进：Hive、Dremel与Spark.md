# 批处理与交互式分析演进：Hive、Dremel 与 Spark

/> 来源：公开课程资料自学整理（更新于 2026-11-03）
> MapReduce 之后的三条进化线：Hive 给它穿上 SQL 的皮（更好写）、Dremel 换掉执行引擎（更快查）、Spark 换掉磁盘为内存（更快算）。

## 核心概念

围绕 MapReduce 的三大短板，三条进化路径：

| 短板 | 进化者 | 核心手段 |
|---|---|---|
| 写 MapReduce 门槛高 | Hive (2009, Facebook) | HQL ≈ SQL，编译成 MapReduce 任务 |
| 交互式查询延迟小时级 | Dremel (2010, Google) | 嵌套数据列式存储 + 多层查询执行树 |
| 每轮迭代必落盘、多轮迭代极慢 | Spark/RDD (2010, Berkeley) | 只读分布式内存数据集 + 血缘容错 |

共同背景：批处理的数据是**边界明确（bounded）**的——数据在计算前已就位，这是与流式处理（unbounded）的分水岭。

## 关键设计/原理

### Hive：SQL 永生不死

- 动机：Facebook 数据仓库原在商用 RDBMS 上，日批作业超 24 小时跑不完；搬 Hadoop 后降到小时级，但分析师写 MapReduce 太痛苦。引入分析师已掌握的**表/分区**概念，把写脚本从几小时缩到几分钟。
- 数据模型：宽表优先——把一个对象所有字段放一张表，**避免昂贵的跨服务器 Join**。天然支持数组/字典/结构体等复杂类型。
- **分区 vs 分桶**：分区按字段值划目录（通常按日期），查询只扫对应分区；分桶按哈希拆固定个数文件，用于采样分析。注意与 Bigtable 动态分区的区别不是"高低级"而是场景：Bigtable 处理随机读写需动态分区分散热点，Hive 批处理要整扫过滤条件下的全部数据，静态分区即可。
- 存储：表对应 HDFS 目录，分区是子目录，分桶是文件拆分；SerDe 定义应用模型↔存储模型的转换，文件格式决定文本/二进制/列式。
- 架构三件套：对外接口（CLI/Web/Thrift/JDBC/ODBC）、驱动器（编译器+优化器生成执行计划）、**Metastore**（元数据中枢）。元数据在生成执行计划时就写入计划文件，Mapper/Reducer 不必反复请求 Metastore。
- 优化器自动选 Join 策略：大表 Join 小表用**广播哈希 Join**（小表拷到每个分区任务），大表 Join 大表用**分区哈希 Join**（两表按 Join 键同法分区后分区间 Join）。声明式语言让这类优化对用户免费。
- 关键伏笔：Hive 对 MapReduce **没有强依赖**——所以后来能有 Hive on Spark：Spark 内存管中间数据 + 数据流引擎（上游有一点点输出下游就能开跑）。

### Dremel：嵌套数据的列式存储 + 查询树

- 定位是 MapReduce 的**补充**而非替代：Dremel 几秒出近似结果供快速验证想法，精确分析仍要写 FlumeJava/MapReduce。它处在"分析师探索"环节。
- 列存的好处：只加载查询涉及的列 + 压缩更廉价省 CPU。论文实测同一查询 MapReduce-on-records 读 87TB 花数小时，MapReduce-on-columns 只读 0.5TB 缩到几分钟——光是把 MapReduce 跑在列存上就提升一个数量级。
- **难点是嵌套数据怎么还原**。Dremel 给每个字段值附加两个整数：
  - **Repetition Level**：字段路径上，第几个可重复字段最近发生了重复（0 表示新记录开始）。用于知道"这条记录里该字段出现了几条"。
  - **Definition Level**：字段路径上，那些"可以不定义"的子字段（可选/可重复）实际出现了几个。用于区分 NULL 是"字段不存在"还是"哪一级不存在"。
  - 两者让每个值**自描述嵌套结构信息**，配合状态机（Record Assembly）即可从列数据重建原始记录。这套编码就是 Parquet 的内核。
- **多层查询执行树**：根服务器接收请求、分解查询计划、聚合最终结果；中间服务器（可多层）进一步分解与聚合；叶子服务器在各数据分片上执行。分析查询逐层聚合后数据量递减，所以网络开销不随层数爆炸，层数越多并行度越高、延迟越低。
- Dremel 2020 回顾论文补充的降延迟手段：服务池化（避免冷启动）、投机执行（快机器多干）、只解析查询涉及列的 Schema、轻量压缩、近似结果（处理完 98% 就返回可降 2-3 倍延迟）、查询延迟层（小查询不被大查询阻塞）、文件元信息复用、重要作业容量保障、自适应执行树层数。

### Spark/RDD：内存计算与血缘容错

- RDD（弹性分布式数据集）= **只读的、已分区的记录集合**，只能从稳定存储或其他 RDD 经明确的粗粒度转换（map/filter/join...）创建。接口这样设计全为容错：分区丢了就按上游重算该分区，无需复制数据。
- "弹性"三层含义：数据可在内存/磁盘间换入换出；可选择把高成本中间 RDD 持久化到磁盘；故障恢复靠血缘重算。
- 编程接口：**Transformation**（惰性求值，只记录不执行）与 **Action**（count/collect...，触发计算）。全部操作构成拓扑图（Lineage graph）。
- **窄依赖 vs 宽依赖**是调度与恢复的核心依据：
  - 窄依赖（map）：上游一分区只影响下游一分区 → 可同节点流水线执行、计算靠近存储、恢复快（只需重算少数分区）。
  - 宽依赖（groupByKey）：一分区影响下游多分区 → 恢复代价高，实践上应把宽依赖产出的 RDD 持久化，故障时从磁盘恢复。
- 性能实测：逻辑回归/K-means 上 Spark 比 Hadoop 快 20 倍以上，甚至比"数据放内存的 Hadoop"（HadoopBinMem）还快——差距不在内存而在软件栈开销：初始化/清理、每 Block 多次内存拷贝与校验和、二进制↔Java 对象转换。

## 术语表

| 术语 | 含义 |
|---|---|
| 宽表 | 反范式地把对象所有字段放一张表，牺牲存储换掉 Join |
| 分区 / 分桶 | Hive 按字段值划目录 / 按哈希拆固定数量文件（采样用） |
| Metastore | Hive 元数据中枢（表结构、位置），后被独立为通用组件 |
| Repetition / Definition Level | Dremel 列存编码，自描述嵌套结构的两个整数 |
| 查询执行树 | 根-中间-叶子分层分解与聚合查询的树状执行结构 |
| RDD / Lineage | 只读分区集合 / 记录"数据从哪算来"的 DAG，容错依据 |
| 窄依赖 / 宽依赖 | 上游分区 1:1 / 1:N 影响下游分区 |
| Transformation / Action | 惰性转换算子 / 触发执行的动作算子 |

## 经验与常见坑

- **DSL 来来去去，SQL 永生不死**：Sawzall、Pig 都曾与 Hive 同台，最终胜出的是最接近 SQL 的 Hive——降低门槛的最优解往往是"不发明新语言，用行业已有的共同语言"。
- **列式存储是分析查询最大的单点杠杆**：先想清楚查询只碰几列，再把"减少扫描量"作为存储格式设计的第一原则；嵌套数据列存的复杂度全压在 Repetition/Definition Level 这套编码上，理解了它就读懂了 Parquet。
- **惰性求值 + 依赖分类是通用模式**：先构建执行图再优化调度（窄依赖流水线、宽依赖物化），MapReduce 的 Map/Shuffle/Reduce 与 Dataflow 的 ParDo/GroupByKey 都是同一件事。
- **性能问题常不在"算法"而在"软件栈开销"**：Spark 赢 Hadoop 的大头是初始化、内存拷贝、序列化转换——做性能优化先量这些边角开销，别急着换数据结构。
- **近似是有价值的工程取舍**：允许 98% 数据就返回，延迟降 2-3 倍；探索性分析要快，精确计算留给批处理——按用途分流，而不是让一个系统满足所有延迟要求。

## ⚠️ 时效性说明

- Hive 默认执行引擎早已不是 MapReduce（Hive on Tez/Spark）；Spark 成为事实上的批处理标准后自身也在持续演进（结构化流、自适应执行）。
- Dremel 论文中的 2010 版架构（多层固定执行树）已被 2020 回顾论文描述的自适应系统大幅修订；开源对应物是 Presto/Trino、ClickHouse、Apache Doris 等。
- 课程基于 2021 年认知；Metastore 已演化为独立的 Hive Metastore Service，被 Spark/Trino/Flink 等广泛复用。
