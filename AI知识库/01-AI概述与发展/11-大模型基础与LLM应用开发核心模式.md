# 大模型基础与 LLM 应用开发核心模式

/> 来源：公开课程资料自学整理（更新于 2026-11-03）
> 一句话概括：理解"大模型就是一次添加一个 Token"这一个原理，就能推演出提示词、RAG、Agent、记忆、缓存、网关全部应用模式的设计动机与权衡。

## 核心概念

- **LLM 的工作本质**：针对已有文本预测下一个 Token 的概率分布，循环生成。计费按 Token、上下文窗口限制、流式输出、"幻觉"，全部源于此。
- **Token**：可整词、子词或词片段（所以模型能"造新词"）。上下文窗口 = 可处理 Token 数上限。
- **温度（Temperature）**：控制采样随机性。低 = 确定性（推理、Agent 场景）；高 = 创造性（文案）。top_p 是另一种采样方式，与温度二选一调节即可。
- **Embedding**：文本 → 稠密向量。一切输入转成向量是 AI 算法的前提，也是多模态的前提；语义相似度 = 向量距离（余弦/内积/欧氏）。
- **幻觉的根源是机制性的**：训练数据有错漏、语言歧义、概率生成本质——"一本正经胡说八道"不是 bug，是缺陷，只能靠外挂知识（RAG）和工程手段缓解。
- **把 AI 当人看**：GPT 知识丰富、知人晓事（角色设定有效的根源）、知错就改（多轮反馈有效）、知法守法。

## 关键方法/原理

### 提示词与提示工程
- 用户级公式：**提示词 = 定义角色 + 背景信息 + 任务目标 + 输出要求**。本质都是给模型充足上下文让它推断你要什么。
- 用法三步：定目标 → 下命令 → 按结果迭代调整（改提示词或人工润色）；结果不满意往往意味着信息缺失，补信息重新生成。
- 提示工程四级技术：
  1. 零样本（Zero-Shot）：通用任务直接问。
  2. 少样本（Few-Shot）：给例子；应用开发中作为固定模板与用户输入拼接（PromptTemplate 的由来）。
  3. 思维链（CoT）：样例中给出推导过程，或加 "Let's think step by step"，大幅提升推理正确率。⚠️ 推理模型（o 系、DeepSeek-R1 等）已把 CoT 内置化。
  4. ReAct（Thought→Action→Observation 循环）：行动环节嵌入外部工具，是 Agent 的基础。⚠️ 靠正则解析文本输出的老实现已被原生 Function Calling 取代。
- 铁律：提示词效果必须基于特定模型实测，模型迭代后重新验证。

### RAG（检索增强生成）
- 解决"模型不知道你的业务数据"。知识进模型（微调）vs 知识进提示词（RAG）：RAG 更便宜更灵活，首选。
- 流程 = 索引（加载→分块 chunk→Embedding→入向量库）+ 检索生成（问题向量化→语义检索→拼进提示词）。
- 要点：分块大小是权衡（太小漏信息，太大浪费上下文）；向量库管语义匹配，人名/ID 类精确匹配靠传统搜索 → 混合搜索；Rerank 重排序提升相关性；知识图谱 RAG 补足关系型问题。
- RAG 提示词关键句："根据上下文回答，不知道就说不知道。"

### Agent
- Agent = 规划（LLM 任务分解）+ 记忆（短期=聊天历史，长期=向量库）+ 工具（外部 API）。执行本质是循环：模型决定做什么 → 代码执行工具 → 结果回传 → 再循环，直到模型说结束。
- **必须设 max_turns 上限**，否则可能不收敛、成本失控。
- 工具信息（名称/描述/参数）可由 docstring 自动提取传给模型；不是所有 Agent 都要全组件（流程固定的写作 Agent 不需要规划）。

### 记忆与缓存
- HTTP API 无状态，"记忆" = 把历史塞回提示词。短期记忆 = 聊天历史 + 按 Token 裁剪（保留 system、从后保留）；长期记忆 = 向量库存"事实" + 检索注入（从对话中用 LLM 提取事实再入库）。
- 缓存两类：精确缓存（提示词完全相同）对自然语言场景基本失效；**语义缓存**（向量化匹配相似问题）实用价值更大。⚠️ 2026 年厂商原生 Prompt Caching（前缀缓存计费折扣）已部分替代应用层语义缓存。

### 集中接入（网关）
- 把接入复杂度移到代理层：多账号号池解限流、多供应商屏蔽差异、统一 OpenAI 兼容接口、模型重定向（贵模型映射到便宜模型）、渠道优先级与故障禁用。
- 有了 OpenAI 兼容网关，LangChain 的模型抽象价值大减。

### 选型权衡：微调 vs RAG vs 纯提示词
- 本质是业务知识放模型里还是提示词里。微调：准确性高，但需要高质量大数据（垃圾进垃圾出，数据要懂业务的人把关）+ 成本。RAG：灵活新鲜，风险是检索不到恰当数据时幻觉。
- 工程实践常组合：RAG 处理新数据，积累后定期微调固化。

## 术语表

| 术语 | 英文 | 含义 |
|---|---|---|
| Token | Token | 模型处理文本的最小单位，计费与上下文窗口的度量 |
| 温度 | Temperature | 采样随机性参数，低确定高发散 |
| 向量嵌入 | Embedding | 文本的稠密向量表示，语义相似度的基础 |
| 幻觉 | Hallucination | 模型生成貌似合理实则错误内容，机制性缺陷 |
| 零样本/少样本 | Zero/Few-Shot | 不给例子/给少量例子让模型执行任务 |
| 思维链 | CoT (Chain of Thought) | 让模型显式输出推理步骤提升正确率 |
| ReAct | Reasoning + Acting | 思考→行动→观察循环，Agent 执行的基本模式 |
| 检索增强生成 | RAG | 检索外部知识拼入提示词再生成 |
| 分块 | Chunking | 文档切分为适合向量检索的片段 |
| 混合搜索 | Hybrid Search | 语义检索 + 关键词精确检索结合 |
| 语义缓存 | Semantic Cache | 按语义相似度命中缓存的问答复用 |
| 模型网关 | LLM Gateway/Router | 统一多模型接入与路由的代理层 |

## 经验与常见坑

- 上下文历史无限膨胀会撑爆窗口且费钱，必须裁剪。
- Agent 循环不限次 = 成本失控的定时炸弹；教程示例代码（历史消息无限增长）不能直接上生产。
- 大模型编程中 API 层面的东西影响很低，功夫全在与模型的交互（提示词）上。
- 用框架（LangChain 等）要能下钻排查：框架内部实现问题（如把整个消息对象 JSON 化作缓存键导致语义缓存乱命中）会渗透到所有下游实现。有些项目用 LangChain 只为集成生态，不用其抽象。
- 面对模型迭代的应对方法论（全书最耐用）：① 区分变与不变——OpenAI 兼容 API 和"基础能力底线不断抬高"是不变的；② 用不变的部分把系统做稳定；③ 引入 LLM Router 按用途路由（简单任务给小模型省钱，复杂任务给大模型）；④ 关注"变"的三个信号——新能力创造新场景、性能跃升、成本下降；⑤ 核心结论：**AI 应用的核心是业务，不是选模型**。
