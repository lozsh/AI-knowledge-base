# RAG 基础架构与核心流程

/> 来源：公开课程资料自学整理（整理于 2026-11-03）
> 一句话概括：RAG = 索引（解析→分块→嵌入→入库）+ 检索（查询向量化→相似匹配）+ 生成（Prompt 组合→LLM 作答）；分块和解析质量决定上限，模型只是最后一步。

## 核心概念

- **RAG（Retrieval-Augmented Generation，检索增强生成）**：结合检索与生成的 NLP 架构（Facebook AI 2022 年提出）。生成前先从外部知识库检索相关信息，注入 Prompt 再作答。
- **解决的四个 LLM 固有缺陷**：
  1. **领域知识缺乏**——训练数据来自公开语料，覆盖不了企业内部/专业领域知识；
  2. **信息过时**——训练周期长，模型完成后无法感知新信息；
  3. **幻觉**——按概率生成，会输出看似合理实则错误的答案；
  4. **数据安全**——企业要求数据不外流，RAG 让私有数据留在自己的检索侧。
- **为什么不全量塞给大模型**：token 窗口有限、成本高；更关键的是**少量高相关的关键信息能带来更优质的回答**（信噪比）。
- **RAG vs 微调的选择**：
  - RAG：外部知识需求高、信息频繁更新、回答需可解释/可溯源——企业知识库、客服、实时资讯场景。
  - 微调：领域固定、知识不常更新、看重领域推理能力与输出风格（如固定故障诊断流程）。
  - 两者可结合：微调管"能力"，RAG 管"知识"。
- 应用场景：企业知识管理问答、智能客服、医疗/金融等高准确性高时效领域；内部系统（MIS）智能问答等。

## 关键方法/原理

### 标准三阶段流程

1. **索引（Indexing）**——RAG 的地基：
   - **文档解析**：把多源多格式（PDF/Word/PPT/Excel/CSV/Markdown/HTML/XML/TXT）统一解析为文本；复杂格式建议输出为 **Markdown**（关注内容而非排版，LLM 理解好）。
   - **分块（Chunking）**：切分为语义完整的小块。
   - **嵌入（Embedding）**：分块向量化（归一化）。
   - **入库**：向量 + 原文 + 元数据存入向量数据库并建索引。
2. **检索（Retrieval）**：查询用**同一个嵌入模型**向量化（保证同一向量空间），相似度匹配取 Top K 文本块。
3. **生成（Generation）**：查询 + 检索块组合成增强 Prompt，LLM 生成回答。大模型是系统的"大脑中枢"，但**输入质量决定其发挥**。

### 文档解析（Quality in, Quality out）

- 文档解析的本质：把**格式各异、版式多样、元素多种**（段落/表格/标题/公式/多栏/图片）的文档，转为**阅读顺序正确**的字符串。"Quality in, Quality out"——解析质量对最终效果起决定性作用。
- **PDF 是重点与难点**：PDF 本质是一串显示/打印指令，对计算机是非结构化的，模型训练数据里也没有直接 PDF。分两类处理：
  - **电子版**：规则解析库即可提取文本/表格。选型经验：pdfplumber 中文支持好、表格强但双栏差；pdfminer/PyMuPDF 中文好但表格弱；pyPDF2 英文好中文差；papermage 适合论文。
  - **扫描版**：需 OCR + 表格识别 + **版面分析 + 阅读顺序还原**，规则库做不到，要用深度学习开源库（MinerU、marker、PP-StructureV2、PDF-Extract-Kit、pix2text、Layout-parser 等），有 GPU 部署成本；生产高精度高吞吐场景可考虑商业库（TextIn、Doc2x、mathpix、PDFlux、腾讯云文档识别等）。
  - 图片中的图表（折线图/柱状图）理解需要端到端多模态大模型（GPT-4o/Gemini 类），效率成本仍是挑战。
- LangChain Document Loaders：BaseLoader/Document 统一抽象 + 160+ 加载器，是"封装好的解析库 SDK"；真实项目仍需按业务写文档后处理逻辑。

### 分块 Chunking（最耐用的调参面）

- **分块的目标**：每个片段既**保留核心语义**，又**相对独立、语义完整**，不依赖大范围上下文即可被理解和命中。
- **三大组成要素**：**大小**（块最大字符/token 数）、**重叠**（相邻块重叠量）、**拆分依据**（段落/分隔符/语义边界）。
- 块大小的权衡：**过大**→向量抓不住细节、检索命中不精准、成本高；**过小**→上下文丢失、语义碎片化。细粒度任务（情感分析）用小块；摘要/主题类任务用大块。
- 六种策略：

| 策略 | 做法 | 适用 | 缺点 |
|---|---|---|---|
| 固定大小 Fixed | 按固定长度切 | 同质数据集、基准线 | 切断词句，无语义 |
| 重叠 Overlap | 滑动窗口，块间重叠 | 法律/技术手册等需保上下文 | 冗余存储、成本升 |
| 递归 Recursive | 按 \n\n→\n→句→词 分隔符逐级递归切 | 长文档通用首选 | 边界处仍可能切散语义 |
| 文档特定 Specific | 按 Markdown 标题/代码函数等结构切 | 结构化格式文档 | 格式依赖强，不通用 |
| 语义 Semantic | NLP 按句子/主题边界切（spaCy/NLTK） | 上下文敏感的精细任务 | 计算资源开销大 |
| 混合 Mix | 先固定快速粗分，再语义细分 | 多格式、动态数据集 | 实现与调优复杂 |

- 实战基线：RecursiveCharacterTextSplitter，chunk_size=512、chunk_overlap=128（字符数非 token）——课程反复验证的稳健起点。

### 生成环节与 Prompt 模式

- 生成 = **指令组合**（查询 + 检索块 + 约束）→ LLM。提示词工程贯穿始终。
- 生成侧的三个成熟模式（LLM 小册案例归纳）：
  1. **私域问答**：企业知识入库 → 检索 → 引用回答，可要求答案标注出处（可溯源）。
  2. **结构化输出**：让 LLM 输出 JSON/Markdown 等机器可用结构（如思维导图的层级大纲再转格式），是"LLM 接入传统工作流"的关键模式。
  3. **个性化记忆**：多轮对话的记忆分两层——**短期记忆**（最近 N 条对话原文，保连续性）+ **长期记忆**（用 LLM 从历史中提炼关键信息入库、随新对话更新），三者拼成"有记忆的 LLM"。可复用开源记忆框架 **Mem0**：相比静态 RAG，它有实体关系理解、时效性/衰减（优先新交互、遗忘过时信息）、跨会话连续性、自适应学习、动态更新五大优势——RAG 检索静态文档，记忆系统检索"关于这个用户"的动态知识。＼�
- 选模型维度：开源 vs 闭源（数据敏感/合规→开源私有化）；参数规模（简单任务 7B 足够、响应快成本低；复杂推理才上大参数）；部署地域与合规（国内场景注意网络稳定性与数据法规）。

### RAG 应用的两条业务"核心密码"（系统实战课归纳）

- **对话模式**：多轮对话中维护上下文（把历史问答纳入查询理解），是 RAG 应用可用的前提——用户不会永远单轮提问。
- **返回结构化数据**：RAG 不只回答自然语言，还能让 LLM 把用户问题翻译成对结构化数据（数据库/元数据字段）的查询条件，返回表格/列表——这让 RAG 从"文档问答"扩展到"业务系统问答"（MIS 提效的本质）。

## 术语表

| 术语 | 一句话解释 |
|---|---|
| RAG | 检索增强生成：先检索外部知识再生成回答 |
| Naive RAG | 索引→检索→生成的最朴素链路（MVP 起点见 05 篇范式演进） |
| Chunk / Chunking | 文本块 / 把文档切成小块的过程 |
| Chunk Overlap | 相邻块重叠部分，防止边界信息丢失 |
| 文档解析 | 多格式文档→阅读顺序正确的纯文本/Markdown |
| 版面分析 | 识别标题/段落/表格/图等区块及其阅读顺序 |
| 增强提示词 | 查询 + 检索内容组合后的 Prompt |
| 幻觉 | LLM 生成看似合理实则错误的内容 |
| 溯源 | 回答标注所引用的文档出处，提升可信度 |

## 经验与常见坑

- **效果差先查数据侧，别先怪模型**：检索不准的根因大多在解析和分块——表格被切碎、双栏 PDF 阅读顺序错乱、扫描件没做 OCR，都会直接毁掉召回。（RAG快速弉
- 块大小没有行业标准答案，**必须结合场景实测**；512/128 是稳健起点而非真理。（RAG快速弉
- 固定大小分块会把"大模/型"这类词拦腰切断——至少要上递归分块按分隔符切。（RAG快速弉
- 实战线的切割经验（知识库问答助手）：**优先按段落切，段落超长再按固定长度切**；固定长度切时在截断点前后设 buffer（如长度 50、buffer 10），在窗口内探测句号等自然边界再截，"尽量而非彻底"避免生硬截断。怎么切都有特例，所以段落优先是铁律。＼�
- 查询和文档必须用**同一个嵌入模型**向量化，否则不在同一语义空间。（RAG快速弉
- 冗余模板内容（重复法律条款、页眉页脚、版权声明）会污染向量库、拉低信噪比——入库前要做数据清洗。（RAG快速弉
- 系统实战课的教训：RAG 项目门槛在"把业务问题翻译成检索问题"（对话管理 + 结构化返回 + 元数据条件），而不在调大模型 API。
- 多文档跨年度/跨实体的复杂问题，Naive RAG 会召回重复章节、混淆时间范围、漏掉实体——需要 Advanced RAG 手段（见 04 篇）。（RAG快速弉

## ⚠️ 时效性说明

- chunk 512/overlap 128 的经验值基于 2024 年嵌入模型（max tokens 512）与qwen 类模型的实践；长上下文模型与长文嵌入模型普及后可重新调优。
- 文中模型名（qwen/GLM/Baichuan、GPT-4o）为 2024 年快照，选型思路（开源/闭源、参数规模、合规）不变，具体型号过时。
