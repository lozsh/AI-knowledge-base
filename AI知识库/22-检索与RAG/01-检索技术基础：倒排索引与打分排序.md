# 检索技术基础：倒排索引与打分排序

/> 来源：公开课程资料自学整理（整理于 2026-11-03）
> 一句话概括：一切大规模检索系统的底座是"倒排索引 + 打分排序 + 分层加速"，这套 2020 年前定型的架构至今仍是 Elasticsearch/Lucene 和 RAG 稀疏检索通道的内核。

## 核心概念

- **正排索引（Forward Index）**：以文档唯一 ID 为 key 的哈希索引（ID → 内容）。适合"给 ID 查内容"，不适合"给关键词查文档"（需全量遍历，O(n·k)）。
- **倒排索引（Inverted Index）**：反过来以**内容/属性（关键词）为 key**，value 是包含该关键词的文档列表。O(1) 定位。是搜索引擎、广告引擎、推荐引擎、数据库全文索引的共同核心。
  - **词典（Dictionary）**：所有 key 的集合（工业级可达千万级词项，每个词有全局唯一编号）。
  - **记录列表（Posting List）**：每个 key 对应的文档 ID 列表，工业实现中每个节点还存词频、每个出现位置等信息。
- **构建流程**：文档编号排序 → 逐篇解析生成〈关键词, 文档ID, 位置〉对 → 以关键词为 key 插入哈希表（追加 posting 节点）→ 全部处理完。位置信息用于短语查询和"关键词是否邻近"判断。
- **联合查询**：多关键词取交集/并集/差集。有序 posting list 用**归并法**求交集，代价 O(m+n)；无序则 O(m·n)。多关键词用**多路归并**。

## 关键方法/原理

### 打分排序：从 TF-IDF 到 BM25

- **TF-IDF**：相关性 = TF × IDF。TF（词频）代表词在文档内的重要性；DF（文档频率）代表词的普遍程度，取倒数得 IDF（逆文档频率），值越大区分度越高。TF、IDF 都要用对数平滑。多词查询 = 各词相关性累加。
- **BM25**（概率模型，TF-IDF 的升级，Lucene/ES 默认）：核心洞察是**词频与相关性非线性**——词频增加时相关性增益递减且有上限。
  - 文档词项权重 = tf·(k1+1) / (tf + k1·(1 - b + b·l/L))，其中 l 为当前文档长度、L 为平均文档长度。
  - **参数**：k1 控制词频上限与收敛速度（经验值 1.2）；b 控制文档长度惩罚强度，0~1（经验值 0.75）；k2 控制查询词内词频的作用（0~10，查询词短，可放大词频）。
  - 完整打分 score(q,d) = Σ IDF(变体) × 文档词项权重 × 查询词词项权重。四个因子：IDF、文档长度、文档内词频、查询词内词频。
- **机器学习打分（LTR）**：主流搜索引擎有数百个打分因子，人工公式不够用。做法：Score = Σ wi·xi 加权求和，离线从训练数据学出权重，再用 Sigmoid 压到 (0,1)（即逻辑回归模型）；还有 SVM、GBDT、DNN 等。BM25 在机器学习排序时代退化为其中一个因子或召回手段。

### Top K 检索：精准与非精准分层

- **精准 Top K**：全量打分后不排序全部（O(n log n) 太贵），用**堆**选前 K 个：O(n) + O(k log n)。
- **非精准 Top K（召回）**：核心思想是**把计算从在线移到离线**，用简单机制先筛出 k1 个，再对这 k1 个做精准打分选 k2 个。工业界标配 = 非精准召回 + 精准排序（类比"简历筛选 + 面试"）。三种实现：
  1. **静态质量得分截断**：只按文档自身质量分（如 PageRank）离线排序，posting list 按分数降序排列（同分按文档 ID 二次排序），在线直接截断、可归并。
  2. **胜者表（Winner List）**：每个 posting list 先按权重（如词频+静态分）取前 r 个，再按文档 ID 排序以便归并。风险：提前截断可能丢失联合查询结果。
  3. **分层索引**：离线把得分最高的 m 篇单独建高质量索引；查询先查高质量层，不足 K 个再去普通层补。最通用，可与文档拆分叠加。
- "非精准/精准"是相对的：精排用 DNN，粗排就可用 LR；精排用 LR，粗排就可用 BM25。原则只有一个——用更小的代价快速缩小范围。

### 索引工程：构建、更新、分布式

- **大规模构建（MapReduce 式）**：文档均分为小批 → 每批内存建倒排 → 按关键词字符串排序写出**临时倒排文件**（有序、不存局部编号）→ 多路归并所有临时文件，归并时赋予全局词编号。可直接迁移到 MapReduce 框架（构建倒排索引是 MapReduce 最早最成功的应用之一）。
- **磁盘索引的检索原则**：内存远快于磁盘，能进内存的尽量进内存。典型分层：词典（哈希表/FST 压缩前缀树）驻内存 + posting list 留磁盘；词典太大则用 B+ 树查词典；超长 posting list 用分层跳表分块加载；热点 posting list 用 LRU 缓存。
- **实时更新**：
  - 小规模（内存装得下）：**Double Buffer 双缓冲**——内存存两份索引，指针原子切换，一读一写无锁交替，批量更新降低切换频率。代价是内存翻倍。
  - 大规模：**全量索引（只读，可落盘）+ 增量索引（内存，可用 Double Buffer）+ 删除列表**。查询时两边结果合并、再按删除列表过滤。
  - 增量合并三法：**完全重建法**（小系统，简单）；**再合并法**（全量与增量直接归并，避免重头处理文档）；**滚动合并法**（量级差距悬殊时，设天级/周级索引逐层向上合并，避免海量无谓复制——搜索引擎用此法）。
  - 贯穿思想：**读写分离**——检索压力放在只读组件上，天然免锁。
- **分布式索引拆分**：
  - **水平拆分（按文档拆）**：文档随机均分，每片词典完整、posting list 不完整；查询扇出到所有分片再合并。负载均匀、易运维，是主流方案。分片不宜过多（网络开销与合并瓶颈）。
  - **垂直拆分（按关键词拆）**：词典切分，每片词典不完整但 posting list 完整。查询词少时可只查一台，省请求复制；但热词倾斜、多词跨片、新增文档管理复杂，仅少数高性能场景使用。

### 倒排检索加速（工业实现）

- **跳表法**：posting list 用跳表实现（Lucene/ES 即如此），长链上查元素从 O(n) 降到 O(log n)；两边互相跳的"**相互二分查找**"进一步加速交集。内存中变化不频繁时可用可变长数组代替链表（利用 CPU 局部性）。
- **哈希表法**：一大一小两个集合求交，把大集合预转哈希表，拿小集合逐个 O(1) 查。前提：预判哪些 posting list 常被求交；且要保留原始 posting list 指针（两个哈希表无法互并）。
- **位图法**：posting list 改为位图，交集 = AND 位运算，代价固定且极快。局限：只适合纯 ID、元素稠密、且 ID 空间不能太大（int32 全量位图约 512MB/个）。
- **Roaring Bitmap（压缩位图）**：32 位拆高 16 位（有序数组做桶）+ 低 16 位（桶内容器）。桶内元素 >4096 用位图容器，≤4096 用 short 有序数组容器，动态转换。Lucene、Druid、数据库广泛使用。"倒排 + Roaring Bitmap"是用户标签系统的高性能组合。

### 状态检索：位图与布隆过滤器

- **位图**：ID 直接作数组下标置 1，O(1) 判存在，比哈希表省去算哈希环节；用 bit 为单位存储（char 数组 + 位运算定位）。
- **布隆过滤器**：用 k 个哈希函数把一个对象映射到 k 个 bit，降低冲突误判。特点：**判"不存在"一定准确，判"存在"可能误判**（错误率）。最优哈希函数个数 k = (m/n)·ln2（m 为 bit 数、n 为元素数）。适用场景：注册 ID 查重、爬虫 URL 去重、缓存穿透防护——允许极小误判换巨大空间节省。位图可视为"单个哈希函数、不压缩长度"的布隆过滤器。

### B+ 树 vs LSM 树（读写权衡）

- **B+ 树**：数据在叶子节点，支持随机写，适合读多写少的关系型数据库；每条插入都要随机写磁盘，高频写入场景性能骤降。
- **LSM 树**：写优化。内存 C0 树（平衡树/跳表）承接写入，攒到阈值后以**多页块**为单位批量顺序写磁盘 C1 树（叶子写满不留空位）；用 **WAL 预写日志**保证崩溃可恢复（顺序追加 log + 检查点）；C0→C1 的**滚动合并**视为两个有序链表归并。查询先查 C0 再查 C1（新版更新）。
- 选择逻辑：读多写少 → B+ 树；持续大量写入的日志/监控系统 → LSM 树。LevelDB/RocksDB/HBase 等 NoSQL 均基于 LSM。

### 搜索引擎整体架构与查询理解

- 三大子系统：**爬虫系统**（抓取，存 LSM 系存储如 HBase）→ **索引系统**（预处理去重/质量分析/分词/反作弊 → 分层+分片 → MapReduce 构建 → 全量+增量更新）→ **检索系统**。
- 检索流程：**查询分析**（分词粒度分析、属性/需求分析）→ **查询纠错**（错误判断→候选召回→打分排序；拼音相同/字形相似/编辑距离召回；语言模型置信度判断）→ **查询推荐**（搜索日志/点击图挖掘相关词，结果不足时补充召回）→ 倒排检索 → 打分排序选 Top K。
- **中文分词粒度**：混合粒度策略——标准分词 + 整个短语一起作为检索词（如"机器学习"→【机器、学习、机器学习】），结果不足再降级到单字细粒度。
- **短语检索 / 位置信息索引法**：拆词检索后用**位置信息**判断关键词邻近度；多关键词用"**最小窗口**"（同时覆盖所有关键词的最短片段）衡量相关性，窗口越短越相关。
- 通用抽象：几乎所有检索业务（含纠错、广告、推荐）都可抽象为**候选召回 + 打分排序**两阶段。

## 术语表

| 术语 | 一句话解释 |
|---|---|
| 正排索引 | 文档 ID → 内容的哈希索引，适合按 ID 取详情 |
| 倒排索引 | 关键词 → 文档列表的索引，检索系统的核心 |
| 词典 / Posting List | 倒排索引的 key 集合 / 每个 key 对应的文档列表 |
| TF-IDF | 词频 × 逆文档频率，经典相关性打分 |
| BM25 | TF-IDF 的概率模型升级，词频影响有上限，Lucene/ES 默认 |
| Top K 检索 | 只返回得分最高的 K 个结果而非全排序 |
| 召回 / 精排 | 非精准快速筛选阶段 / 对少量候选精准打分阶段 |
| 静态质量得分 | 与查询词无关、离线计算的文档质量分（如 PageRank） |
| 胜者表 | posting list 按权重预截前 r 个再按 ID 排序的加速结构 |
| 分层索引 | 高质量文档单独建索引、优先查询的方案 |
| Double Buffer | 双缓冲双索引 + 指针原子切换的无锁更新机制 |
| 全量/增量索引 | 只读大索引 + 内存实时小索引的更新方案 |
| 滚动合并法 | 天级→周级→全量逐层合并，避免大量无谓复制 |
| 水平/垂直拆分 | 按文档切分（片片词典全、posting 不全）/ 按关键词切分 |
| 跳表 | 可二分跳跃的有序链表，工业 posting list 标配 |
| Roaring Bitmap | 高 16 位分桶 + 低 16 位数组/位图容器的压缩位图 |
| 位图 / 布隆过滤器 | 1 bit 表示存在 / k 个哈希位降冲突的存在性判断结构 |
| LSM 树 | 内存树攒写 + 批量顺序落盘的写优化结构（配 WAL） |
| WAL | 预写日志：先顺序写 log 备份再驻内存，崩溃后按检查点恢复 |
| SimHash | 保留关键词权重的局部敏感哈希，Google 用于网页去重 |
| 海明距离 | 两个等长比特串中不同位的个数 |
| 局部敏感哈希（LSH） | 相似输入哈希值也相近的哈希函数族 |
| 乘积量化（PQ） | 高维向量切段、每段聚成 256 类用 1 字节编码的压缩方法 |
| 最小窗口 | 同时覆盖所有查询关键词的最短文本片段，用于相关性判断 |

## 经验与常见坑

- 无序链表求交集是 O(m·n)；posting list 必须有序（文档 ID 序或分数序）才能归并加速。＼�
- 胜者表提前截断有丢结果风险：文档可能不在任何关键词的前 r 名里，联合查询结果可能为空——分层索引更通用。＼�
- 简单分布式（每台全量索引、负载均衡轮询）只提升吞吐量，**不缩短单次查询耗时**；要缩短单查时间必须做索引拆分。＼�
- 哈希表法加速交集时必须保留原始 posting list 指针，否则两个都转哈希表的集合无法求交。（加餐一）
- 位图法只适用稠密、纯 ID 场景；稀疏时空间和运算反而更贵。（加餐一）
- 布隆过滤器哈希函数个数不是越多越好，按 k=(m/n)·ln2 取最优。＼�
- 大规模场景不要用原地更新法改全量索引：超多零散小文件 + 读写锁，两头都低效；用滚动合并。＼�
- 热门词 posting list 可达亿级节点，必须设计成分块可部分加载的结构，不能假设整条链能进内存。＼�
- LSH/SimHash 擅长**字面相似**，不擅长语义相似（字面差异大但主题相近的文章抓不到）——这正是后来 embedding 语义检索要解决的问题。＼�
