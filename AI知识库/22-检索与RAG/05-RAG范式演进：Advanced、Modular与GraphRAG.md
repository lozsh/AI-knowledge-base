# RAG 范式演进：Advanced、Modular 与 GraphRAG 等新范式

/> 来源：公开课程资料自学整理（整理于 2026-11-03）
> 一句话概括：RAG 从 Naive（朴素链路）到 Advanced（检索前/中/后系统优化）再到 Modular（模块自由组合+编排路由），GraphRAG 则用 LLM 生成的知识图谱解决跨文档多跳与全局归纳两大顽疾。

## 核心概念

- **三代范式的继承关系**：Naive RAG ⊂ Advanced RAG ⊂ Modular RAG（Advanced 是 Modular 的特例，Naive 是 Advanced 的基础特例）。演变方向：从固定链路 → 分环节优化 → 模块化+动态编排。
- **Naive RAG 的典型失败模式**（以"比较 Nvidia 与 Apple 近三年财务表现"为例）：召回不同年度报告的同一章节、时间范围混淆、单实体内容缺失、缺乏处理复杂问题所需的上下文——根因是"切块+向量匹配"只重**局部文本匹配**，没有全局理解。
- 传统 RAG（向量路线）的两大结构性短板（微软 GraphRAG 论文归纳）：
  1. **跨片段连接能力弱**：需要跨多个信息片段建立联系（多跳推理）的复杂查询表现差；
  2. **全局归纳总结能力不足**：对大型数据集/长文档做整体性总结极其困难。

## 关键方法/原理

### Advanced RAG：检索前 / 检索中 / 检索后三段优化

**检索前（Pre-Retrieval）**——提升索引质量与查询质量：
- 滑动窗口分块（块间重叠保上下文）
- 元数据添加（日期/章节/类型，供检索时过滤）
- 分层索引（句子/段落/文档多层级嵌入，按查询粒度选层）
- 句子窗口检索（句子级精确命中，返回时扩窗口）
- 查询重写、查询扩展
- 长短内容分别向量化（短句聚焦细节、段落覆盖全局）

**检索中（Retrieval）**：
- 动态嵌入（上下文敏感的词表示，如 bank 在河岸/银行语境不同）
- 领域嵌入微调（医学/法律等专业术语场景）
- HyDE 假设文档嵌入
- 混合检索（向量+关键词）
- 小到大检索、递归块合并（小块检索、逐级合并父块供生成）

**检索后（Post-Retrieval）**：
- 重排序、提示压缩
- 上下文重构（多片段整合成连贯文本，消除重复与冲突）
- 内容过滤（规则/相似度阈值剔除低相关）
- 多跳推理（多步检索-推理链，回答"某技术演化历程"类问题）
- 知识注入（检索后补充外部知识库/领域规则，高准确性场景）

### Modular RAG：编排是灵魂

把 RAG 拆成可自由组合的模块，核心增量是 **Orchestration（编排）**：
- **Routing 路由**：查询分析（判断类型与难度）→ 管道选择（简单问题直接用模型自身知识答，省检索；复杂领域问题走完整检索链）。
- **Scheduling 调度**：判断**是否需要检索**（不是每个问题都要检索！）、是否需要多轮检索。
- **Knowledge Guide 知识引导**：调用知识图谱辅助实体关系推理；设计推理路径（Reasoning Path）处理强逻辑问题。
- 意义：不同场景定制不同管道；对简单问题跳过重流程，效率大幅提升。

### GraphRAG（微软，2024 开源）

- **思想**：用 LLM 从文本中抽取实体与关系，构建知识图谱，检索时以**实体为入口**、沿关系扩展，把结构化图谱信息与非结构化原文片段一起注入上下文。
- **解决什么**：跨文档多跳关系问题与全局归纳问题。经典例子（西游记）：菩提祖师与唐僧从未同段出现，传统 RAG 只能分别召回两人的内容而无法答出关系；GraphRAG 在入库时抽取出"两人都是孙悟空的师傅"，即可推理作答。
- **构建流程**：实体识别 → 关系抽取 → 三元组（主体,关系,客体）生成 → 图数据库存储；查询时本地搜索定位相关实体→ 提取关联实体/关系/原文片段 → 按上下文窗口筛选 → 生成。
- **优点**：准确度与完整性高（微软论文称复杂问题 LLM 响应准确度平均提升 3 倍以上）；多跳推理自然；可解释可追溯（结论在图上有路径）；图结构直观便于理解数据。
- **代价与坑（最关键的现实判断）**：
  - 门槛、算力、时间、人力成本都高。有公司做出月入几千万的 GraphRAG 产品，但花了 8 个月与大量人力——"RAG 里的专业马拉松"。
  - 构图成本示例：200 页文本用 GPT-4 构图约需 449 次调用、约 11 美元（2024 年价格），知识更新还要重复此过程。
  - **最大难点是"知识正确入库"**：实体消歧——两处"土地公公"是不同的实体，如何识别？
  - **适用判据**：关系本身已有结构化数据（如社交关系风控）→ 很适合；自由文本关系密集（小说、研报）→ 值得但贵；知识简单平铺 → 不必上 GraphRAG。

### 其他 12 种 RAG 技术（实践清单）

**入库侧**：①语义分块入库（自然断点切分保语义连贯）②按树入库（像书的章-节-小节-段组织知识）③分层入库（摘要层+详情层，两层元数据指向同一数据位置）④信息压缩入库（入库前用 LLM 剔除与业务无关/次要信息）。
**检索侧**：⑤综合多种过滤（元数据+相似度+关键词+内容过滤+多样性过滤）⑥投票与加权检索（多方法结果投票定最终知识）⑦分解子查询再整合 ⑧多轮检索（检索→LLM 分析→生成后续查询，循环；只适合非实时场景）⑨AI 智能体检索（多智能体各角色多提示语检索的工作流；同样只适合非实时）⑩预生成问答（离线用高级方法生成 QA 对入库，线上只需检索问题返回答案——用离线时间换在线延迟）。
**排序与回答侧**：⑪重排序五种手段（专用重排模型 / LLM 逐块评分 / 查询+文档共同重编码 / 元数据纳入评分 / 结合用户反馈）⑫用户反馈作为知识参与回答生成（ChatGPT 采用）。

**方法论**：RAG 技术会不断增多，学习姿势是固定套路——弄清一种技术的**原理、优点、缺点、适用场景、注意事项**，再整合进自己项目。

### 框架借鉴：不整体用，但"取长补短"（系统实漉

- 现实观察：RAG 项目做得越久，框架定制化比例越高；作者实际项目中 LangChain 占比极低，没有一个框架能满足 20% 以上的真实需求。
- 不直接调框架类的原因：①框架一两天一版、兼容性差，升级即坏；②功能不完善（尤其中文场景），且不可定制；③拖入大量不需要的依赖，高并发内存可多两三倍。
- **正确姿势（四步法）**：明确自己项目的问题与目标 → 浏览各框架文档找到解决思路（如 LlamaIndex 的 SentenceWindowNodeParser 句子窗口分割）→ 找到对应**源代码** → 整合进自己项目（并针对中文标点等细节打补丁）。
- 思想："授人以鱼不如授人以渔"——框架会过时，"看源码借鉴实现"的方法不会。

## 术语表

| 术语 | 一句话解释 |
|---|---|
| Naive / Advanced / Modular RAG | 朴素链路 / 三段式系统优化 / 模块化+编排的三代范式 |
| Orchestration | 编排：路由+调度+知识引导的动态流程控制 |
| Routing / Scheduling | 按查询特点选管道 / 判断是否与如何执行检索 |
| GraphRAG | 用 LLM 构建知识图谱增强检索的 RAG 范式（微软开源） |
| 实体消歧 | 判断文本中同名实体是否为同一对象，构图最大难点 |
| 三元组 | (主体, 关系, 客体) 的知识图谱最小存储单元 |
| 按树入库 | 按章-节-小节-段的层级结构组织知识库 |
| 预生成问答 | 离线生成 QA 对入库、在线只查不生成的换时策略 |
| 多跳推理 | 需要跨多个信息片段串联才能回答的推理 |

## 经验与常见坑

- Naive RAG 能跑通 ≠ 能上线：跨年份、跨实体、需要比较归纳的问题，朴素链路必败，要按 Advanced 清单逐项排查补强。（RAG快速弉
- 不是每个问题都需要检索：Modular RAG 的调度思想提醒——简单寒暄/常识问题直接让模型答，省时省钱；检索需求判断应成为管道中的显式节点。（RAG快速弉
- GraphRAG 不是默认选项：先问"我的问题需要跨文档多跳或全局归纳吗""关系数据是否已结构化""预算能覆盖构图与更新的 LLM 调用吗"。三者有一否，先用分层入库/预生成问答等便宜手段。（系统实漉
- 实体消歧做不好，图谱会安静地给出错误关系——比"检索不到"更危险。（系统实漉
- 多轮检索、多智能体检索每轮都是 LLM 调用，延迟秒级起步，只能用于离线/非实时场景（如每日简报）。（系统实漉
- 别把框架当依赖：借鉴 LlamaIndex/LangChain 的实现思路并吸收源码，比引入整框架更可控（中文支持、并发内存、版本兼容）。（系统实漉
- 用用户好评/差评数据作为知识反哺回答，是几乎所有成熟产品的共同选择，从第一天就该收集。（系统实漉
