    Fleet 编排

    更新于 2026-11-05

    一句话定义：编排是从共享基础设施中提取有用工作的学科——决定哪些作业在哪些节点上运行、抢占何时服务更大利益、如何在团队间平衡公平性与利用率、以及如何防止协调机制本身成为瓶颈。

    概述

    一千个空闲等待调度决策的加速器与一千个正在计算有用工作的加速器成本相同。规模上的限制因素从"拥有足够硬件"转移到"有效利用它"。用 C³ 术语说，编排是有意支付的协调税：用一部分理论峰值利用率，换取 Fleet 共享资源在负载下不死锁、不碎片化。

    经济账说明了杠杆之大：10,000 GPU 集群按 $2/GPU·小时计每天运营 48 万美元，GPU 空闲与否照付。调度低效导致 30% 空闲 = 每天浪费 14.4 万美元、每年约 5,260 万美元；利用率从 50% 提到 80% 等效于白得 3,000 个满载 GPU（对 50% 利用率的旧集群相当于购置 6,000 个新 GPU）。利用率每提升 1 个百分点，年价值超过实现它的工程师工资——调度是 ML 基础设施中最高杠杆的工程投资之一。

    关键概念：ML 调度为什么难

    四个 ML 特有约束

    1. 组调度（Gang Scheduling）：同步分布式训练的阶跃函数效用——1,024 GPU 的作业拿 512 个 GPU 完成的训练步数为零（每个 AllReduce 停滞到最后一个 worker 到达）。调度器不能像传统装箱那样"紧密包装"，必须做原子多资源分配。
    2. 拓扑感知放置：张量并行要求 GPU 在同一 NVLink 域内。节点内 450 GB/s/方向 vs 节点间 50 GB/s/端口，差一个数量级；跨节点拼凑的"4 GPU"对张量并行毫无意义。放置组（Placement Group）是云上的拓扑合同。
    3. GPU 异构性：A100/H100 混合池中，H100 对 transformer 吞吐约 2× 但成本成比例更高。调度器须按实际需求（而非用户习惯）匹配硬件，否则首选池排队溢出、另一池空闲。
    4. 作业时长不可预测：提前收敛、硬件故障、超参搜索自愿终止——调度器在深度不确定性下运行，传统科学计算"可预测运行时间"的奢侈不存在。

    分布式调度的四个基本难题

    单机调度器拥有三样集群调度器没有的奢侈：一致的全局状态视图、立即生效的原子决策、二元故障模型。集群调度全部放弃：

    • 部分故障：分配与作业启动之间节点故障，已放置的其他作业可能占了次优资源。
    • 网络分区：调度器看不见的节点可能仍在正常干活。重新分配有双重分配风险，干等又浪费——任何固定超时都是对网络行为的猜测。
    • 状态不一致："空闲" GPU 可能还在清理上个作业（僵尸进程、CUDA 重置），"使用中"的可能已释放；视图陈旧度随节点而异。
    • 无全局时钟：分配顺序需共识协议保障，否则分区恢复时两个作业可能各自"拥有"同一 GPU。

    这呼应 CAP 定理（用作设计类比而非字面定理）：控制平面必须在分配前选择接受多少陈旧状态。三种取法：Slurm 式集中批量控制（作业开始前强调权威视图）、Kubernetes 式协调（持续驱动实际状态向声明状态自愈）、自定义 ML 调度器（接受有界不一致换调度吞吐，乐观并发、事后解冲突）。调度器与 ML 框架的协调平面交互也有张力，TorchElastic 类 rendezvous 机制（心跳 + 重新 rendezvous）给调度器比"集体超时"更清晰的恢复信号。

    规模故障率：故障是常态

    以 99.9% GPU 年度可靠性计，4,096 GPU 集群纯硬件期望约 0.01 次故障/天——但这严重低估：加上驱动崩溃、CUDA 上下文损坏、热事件、网络/OS/容器错误，大型集群经验值约 每 1,000 GPU 每天 1–4 次组件故障，即 10,000 GPU 集群每天 10–40 次。多周训练必然多次遇障。调度器因此必须：预测资源在执行期消失、保留备用容量或快速重调度、区分瞬态故障（几分钟内自愈，不值得昂贵的重分配）与永久故障（需新分配 + checkpoint 恢复）。节点失联时的三选一（等待恢复 / 立即重分配 / 标记可疑并预热替代资源）没有普适答案，取决于该集群的故障模式分布。

    核心原理：调度目标与死锁

    四目标冲突

    目标 偏好行为 代价
    吞吐量 大型长作业填满集群 其他用户等待数周
    公平性 跨用户分割资源（DRF 均衡最大归一化份额） 留下大作业装不下的小空隙
    延迟 短作业快速完成（类 SJF、激进抢占） 大型训练饥饿
    成本 现货实例、非高峰、紧包装 故障率↑、完成时间↑

    四者同时最优不可能；典型零和案例：64 GPU 微调作业是吞吐视角的理想负载（高利用跑数天），却是延迟视角的巨石（为调度它可能要排空数百小作业；若让小作业抢占/碎片填充，它可能永远凑不齐启动资源）。

    排队论：利用率墙

    把集群建模为 M/G/1 队列，Pollaczek–Khinchine 公式给出等待时间：

    W_q = [ρ/(1−ρ)] × (1/μ)(1+C_s²)/2

    Web 请求服务时间近似指数分布（C_s ≈ 1）；ML 作业时长重尾（几分钟调试作业混数周训练，C_s ≈ 3）。在 ρ=0.8 时：C_s=1 → 等待 4× 平均作业时长；C_s=3 → 20×。这解释了"利用率墙"：Web 集群 80% 负载感觉正常，ML 集群同样利用率感觉坏了。运维推论：ML 集群通常压在 60–70% 利用率运行以保住交互响应性；约 70% 以上队列等待爆炸。

    装箱与碎片化

    装箱一般形式 NP 难（ML 再加 GPU/CPU/内存/网络/拓扑四到五个维度），但 FFD/BFD 启发式对"多数小作业+少数大作业"的重尾分布近优。真正的次优性不是包装而是碎片化：示例中 8 节点×8 GPU 集群有 19 个 GPU（约 30%）空闲，却没有任何一个节点有 8 个连续槽位——需要整节点的作业被阻塞。缓解策略：回填（小作业填空隙）、周期性碎片整理（迁移/抢占低优先级作业整合连续块，类似 OS 内存压缩）、超订用（依赖统计复用）。注意多维约束：4 GPU + 32 CPU + 256 GB 的作业在"有空 GPU 但 CPU 被别人预处理吃光"的节点上放不下——任一维度瓶颈可让其余维度容量全部滞留。

    死锁与优先级反转

    组调度从构造上消除了 Coffman 四条件中的"保持并等待"（两个作业各持 512 个 GPU 互相等待 → 1,024 GPU 全分配、零进展、$2,048/小时纯烧钱），但死锁仍可从优先级规则、抢占策略与辅助资源依赖的交互中涌现：

    • 优先级反转：高优先级 175B 训练要 64 GPU，60 个空闲、4 个被低优先级数据处理作业持有；而中优先级负载占住 CPU/带宽使低优先级作业饥饿到无法完成退出——它不能释放 GPU 因为它退不出去。结果是 60 GPU 持续闲置直到人工干预。教训：不做整体抢占（为受害者保留退出所需的全部资源），单纯增加优先级级别反而制造更复杂的依赖链、提高反转概率。
    • 大规模下的死锁处理：10,000 GPU + 500 待处理作业的状态空间超 10¹⁵，精确检测不可行，生产系统近似活性而非证明它：基于租约的 TTL 回收、进度监控（GPU 利用率/步计数器/心跳识别僵尸分配）、抢占时整体预留退出资源。接受非零假阳性换集群活性。

    异构组调度

    RLHF 类管道中一个逻辑作业含多种角色（生成 rollout 的推理节点 + 算策略更新的训练节点），资源配置各不相同。调度器必须原子分配"资源星座"并持续平衡两侧吞吐——任何一侧失衡，整个集群失去同步。这是编排从静态拓扑装箱走向动态路由的标志。

    编排范式：Slurm vs Kubernetes

    Slurm（HPC 传统，命令式）

    用户声明确切资源（sbatch --gres=gpu:8 --nodes=4 → 保证跨 4 节点精确 32 GPU），架构为中央控制器 slurmctld + 每节点 slurmd（集中权威分配，主动-被动故障转移）。ML 关键配置：

    • 分区按加速器/互连切分（如 dgx-a100：8×A100 NVLink+IB NDR 跑大模型训练；infer：2×A10G 跑服务；debug 隔离开发负载）。
    • 公平份额：Priority_eff = Priority_base × F_target/(F_actual + ε)——多用者优先级自动折半，闲置者回归时快速拿回资源。历史用半衰期衰减（生产常见 3–14 天：太短振荡、太长惩罚刚完成大项目的合法重用户）。
    • 抢占：SIGTERM + GraceTime（60–300 秒做 checkpoint）再 SIGKILL；PreemptMode=REQUEUE。抢占可行性的前提是可靠的 checkpoint 基础设施（参见容错一篇）。
    • ML 高级配置：作业数组（--array=0-99 把超参 sweep 变成一个可调度对象）；异构作业（GPU 节点 + 纯 CPU 数据标注节点分 het-group 提交）；prolog/epilog 脚本作为"免疫系统"（作业前验 NVLink 拓扑、ECC 计数器、IB 链路宽度，失败则排出节点；作业后杀孤儿进程、清共享内存、记录利用率）；TRES 计费权重（按加速器经济价值而非裸核数算公平份额——100 个旧 GPU 不该和 100 个 H100 等价）。

    Kubernetes（云原生，声明式）

    用户声明期望状态，控制循环持续协调（级别触发：控制器崩溃重启后重读状态自愈；代价是多控制器涌现行为难顺序调试）。ML 生态拼图：

    • 设备插件把 GPU 暴露为扩展资源（nvidia.com/gpu: 4）；但二元整卡分配对碎片化推理负载低效 → MIG 硬件隔离切分（1g.10gb/14 SM 小推理 … 7g.80gb/98 SM 训练）。
    • 组语义靠外挂：Volcano / Coscheduling 的 PodGroup（最小成员数原子评估）、Kueue（准入控制与放置分离，ClusterQueue 提供公平份额）；PriorityClass 定抢占序（生产典型：推理高、训练中、开发低）。
    • 训练算子：Kubeflow Training Operator 的 PyTorchJob/TFJob/MPIJob 自动注入 MASTER_ADDR/PORT、WORLD_SIZE、RANK。
    • 高性能网络：hostNetwork: true 绕过 CNI 直取 RDMA；NVIDIA Network Operator 管理 SR-IOV/GPUDirect RDMA。
    • checkpoint 风暴：1,024 GPU 同时写 2 TB checkpoint 需带 QoS 的存储类 + 客户端限速，否则饿死其他作业甚至压垮存储元数据服务器。

    选型与混合架构

    维度 Slurm Kubernetes
    模型 命令式：确切资源、精确保证 声明式：期望状态、持续自愈
    组调度 原子分配 + 回填原生 需 Volcano/Kueue/Coscheduling 外挂
    故障处理 配置依赖的重排队 控制循环自愈
    服务负载 无原生支持 Deployment/滚动更新/健康检查原生
    开销 无容器开销 容器网络损失约 1–5% 带宽 + 启动时间

    经验法则：纯训练集群选 Slurm（可预测分配、裸机性能），训练+服务混合选 Kubernetes（单一控制平面）。生产中常见三种混合：Kubernetes-over-Slurm（K8s 做外层编排/可观测/CI-CD，TrainingJob CRD 翻译成 sbatch，兼得两者）；Slurm-alongside-Kubernetes（共享节点池上的独立集群 + 元调度器仲裁，模式切换成本 5–15 分钟，只适合日/周粒度弹性）；统一平台如 Ray（编排灵活但调度成熟度不及两者）。典型 175B 生命周期：训练在 Slurm（NVLink 拓扑效率 + 组调度可靠性），服务移交 Kubernetes（滚动更新 + 自动扩展），桥梁是监控训练进度、验证损失平台期自动触发量化并部署的 K8s 算子。趋势是两者互相吸收对方能力（K8s 经 Volcano/Kueue 获得批量能力），边界正迅速模糊。

    拓扑感知调度

    把 GPU 当作可互换槽位是昂贵错觉：同样 64 个 GPU，随机撒进数据中心比打包进单个机架慢 15–30%。调度器须把集群建模为带带宽悬崖的层次图（GPU→Node→Rack→Pod），每次边界跨越都意味着数量级的带宽下降，spine 层还常配 2:1–4:1 收敛比。

    通信层次与局部性成本

    层级 互连 适配的并行
    节点内 NVLink（A100 600 / H100 900 GB/s） 张量并行：每层交换激活，可近理想吞吐
    机架内 InfiniBand NDR 400 Gb/s ≈ 50 GB/s/链路 流水线并行 + 数据并行 AllReduce（可掩盖）
    跨机架 经 spine 多一跳：有效带宽再降 10–30%，P99 尖刺制造 straggler 仅数据并行

    局部性成本函数：$\(\mathrm{Cost}_{\mathrm{locality}}=\sum_{i<j} w\bigl(d(g_i,g_j)\bigr)\)$ \(d\) 为拓扑距离（同节点 0 / 同机架 1 / 跨机架 2），权重编码性能悬崖：\(w(0)=0,\ w(1)=1,\ w(2)=10\)——同机架到跨机架的十倍权重差反映 spine 边界的不成比例代价。三级放置与三级并行一一对应：张量并行组锁进单节点 NVLink 域、流水线相邻 stage 放同一 leaf 下、数据并行副本撒跨机架吃满 bisection 带宽；无可行整块放置就让作业排队（组调度原子性），绝不零散占用。

    放置即性能：数字

    64 GPU 同步 1 GB 梯度 AllReduce 的延迟阶梯：随机放置 120 ms（8.3 GB/s）→ 机架感知 85 ms → rail 优化 40 ms → 拓扑最优 25 ms（40 GB/s），4.8× 差距纯靠调度获得，模型代码零改动。注意这是通信-only 度量：同步训练掩盖部分通信，落到端到端是 15–30% 吞吐差——但张量并行每层（大模型 80+ 层）都通信，残余暴露逐层复利。3D 并行示例（256 GPU = 8 TP × 4 PP × 8 DP）：1 GB 激活走 NVLink（450 GB/s/方向）约 2.2 ms，落到 IB（50 GB/s）约 20 ms，单个映射错误 9× 放缓。

    Rail 优化与运行时拓扑发现

    Rail 优化拓扑中每节点 GPU i 接 rail i 交换机；调度器把数据并行 rank r 放到各节点 GPU \(r \bmod 8\)，使每组 AllReduce 只走单一 rail 树、消除跨 rail 争用。三个目标（NVLink 局部性、机架局部性、rail 对齐）部分冲突，生产调度器用加权评分消解：3D 并行大作业权重 TP 局部性 > rail 对齐 > 机架局部性；纯 DP 作业 rail 优先；单节点作业只管装箱效率。

    静态配置（Slurm topology.conf、K8s node label）描述"意图拓扑"，NCCL 类库运行时解析 /sys/class/infiniband 才得到"有效拓扑"——验证过的链路图。交换机可能"活着但瘸了"：高 CRC 错误、丢包、重传，二元健康检查全绿而集合通信性能全红；需要性能感知监控 + 动态隔离（K8s taints / Slurm drain），把降级机架对通信密集作业标记为不合格。若选择迁移而非带伤硬跑：协调 checkpoint + 重调度 + 预热约 5–15 分钟；20% 吞吐损失下 10 分钟迁移的盈亏平衡点不到一小时训练，多周训练通常值得迁。

    弹性调度

    刚性分配下调度器只有二元动作 {继续，整体抢占}；弹性训练（依托检查点恢复机制，参见容错一篇）把它变成连续资源谱：128 GPU 起步、有货扩到 256、高优先级到来缩回 192，训练进度不断。

    调度器-框架契约

    三参数：弹性范围 \([N_{\min}, N_{\max}]\)；转换成本（rendezvous 周期 10–60 秒，限定重定规模频率）；扩展效率曲线（决定新增 worker 值不值）。有效 batch 随 worker 数变化 \(B_{\mathrm{effective}}=B_{\mathrm{per\text{-}worker}}\times N\)，恒定全局 batch 保收敛但低 worker 数可能爆显存，自适应学习率好管理但在快速伸缩期有收敛风险。TorchElastic 的 --nnodes=4:16 即在声明此范围。硬约束：弹性本质是数据并行操作——175B 用 8 路张量并行时只能整节点伸缩（改 DP 度）；从 TP 组抽走一个 GPU 等于重切分权重 = 完整 checkpoint-restart。

    三项调度优化与算账

    • 快速启动：32 GPU 可用即开工，不等 128 个连续槽位；调度器动态选启动时刻与初始规模，最小化期望总时间。
    • 机会扩展：弹性作业成为吸收利用率波动的缓冲垫，双向伸缩抹平"已分配"与"在产出"的差。
    • 优雅抢占：先缩到最小规模再 checkpoint-preempt，把抢占从"回滚事件"变"暂停-恢复"。

    队列算账：128 GPU 作业排队 8 小时等全 gang——刚性 8+24=32 小时；弹性 32 起步（25% 吞吐）、2h 后 64、4h 后 128，等待期白赚 5.5 小时等效满载工作，总墙钟约 26.5 小时（省 17%）。另一面（24h 窗口、目标 512 GPU、resize 税 10 分钟）：立即小跑 24 epochs，死等 4 小时再满载 64 epochs，弹性阶梯 39.7 epochs——比死守小规模多 1.7×，但仍落后 gang 约 38%；队列更久或峰值更稀缺时差距收窄，转换税涨到 2 小时则进一步落后。

    扩展策略：边际效用而非空位

    扩展效率 \(\eta_{\mathrm{scaling}}(k)\)（实测吞吐 / 理想线性）呈三阶段：线性（计算主导）→ 次线性（梯度同步开始吃掉计算）→ 饱和（AllReduce 环成为瓶颈）。175B 实测 64–512 线性、512–1,024 次线性、超过 1,024 递减 → 调度器强制范围 [256, 1024]：有空位也不再给（5% 边际收益不值饿死排队 gang 作业）；只有 128 可用时宁可排队（每 GPU 训练强度太低藏不住通信延迟）。resize 税必须摊销到后续运行时长——每空出一个节点就缩放一次的策略因进程组持续重建而净进度为负。

    成本优化

    单作业效率之上是舰队经济学：10,000 GPU ≈ 3 亿美元资本支出；20% 因碎片/等数据闲置 = 6,000 万美元搁置资本 + 年烧约 3,500 万美元运营。按 $2/GPU·小时，10K GPU @ 50% 利用率年浪费 8,760 万美元；提到 70% 年省超 3,500 万美元、不购一卡。实测佐证：Microsoft Philly 集群平均 GPU 利用率约 52%；Perlmutter 上 50% 的作业用不到所分配显存的 25%。

    Spot/抢占式实例

    60–90% 折扣（$0.70 vs $2/GPU·小时）能把多周预训练从数十万美元压到十万美元以内，代价是回收通知窗口：AWS 2 分钟、GCP 30 秒——大模型 checkpoint 要 3–5 分钟。有效成本 $\(C_{\mathrm{effective}}=C_{\mathrm{spot}}\times \frac{T_{\mathrm{total}}}{T_{\mathrm{productive}}}\)$ 中断 <1 次/天且 checkpoint 开销 <5% 时接近 spot 价；中断每几小时一次 + 大模型慢重启时可逼近甚至超过按需价，名义折扣变隐性溢价。容错基础设施的双重回报：既防硬件故障（统计性、难量化的收益），又解锁 spot（具体、可量化的节省）——常是容错投资过审的真正理由。

    策略组合：AZ 多样化（池级回收能一次拿走数百 GPU，须按弹性收缩/故障转移处理而非孤立故障）；实例类型多样化（多 SKU = 多个独立 spot 市场，按优先序列回退）；中断预测（Spot Placement Score 类数据，>4 次/天即迁按需或换区，防"恢复时间超过训练时间"的抖动）；双层 checkpoint——Young-Daly 周期 checkpoint 防硬崩溃 + 收到终止通知立即打"恐慌 checkpoint"，把抢占从回滚变暂停-恢复。容量三档：预留（1–3 年承诺，30–60% 折扣 → 24/7 推理、SLA 作业）、按需（全价即时 → 紧急重训、调试）、spot（可中断 → 超参 sweep、消融、探索）。算例：70B、512 GPU、14 天——按需 \(344,064；spot（65% 折扣、5% checkpoint 开销、14 次/天中断 × 30 分钟重启）\)161,567，省 53% 换 34.2% 更长墙钟。没有 checkpoint 基础设施时一次中断即从头再来，全部节省归零。

    成本感知调度与 TCO

    三类日常决策：现在跑预留 A100 vs 等 2 小时后的 spot H100（3× 快、半价）；抢占低优先级 sweep 腾位 vs 给高优先级训练买按需；spot 被回收后迁按需保吞吐 vs 弹性缩容保成本。按负载类固化成本策略：推理钉死预留（宕机损失远超预留溢价）、大训练 = 预留打底 + spot 弹性扩张 + 期限内在场回退、探索类纯 spot。ML FinOps 用作业级标签支撑 showback→chargeback，指标从"GPU 小时"换成"每模型版本成本 / 每实验成本 / 每百万次预测成本"，让成本成为产品决策输入。TCO 提醒：计算硅片只占高性能集群总成本 40–60%，其余是 IB 交换机/光模块/布线、并行文件系统、供电散热——单 H100 机架可拉 40 kW（标准 Web 机架 10 倍）倒逼液冷；自购硬件只有保持繁忙才能摊销，调度器 reclaim 的每个利用率点都在把舰队推向 build-vs-buy 盈亏平衡点。

    自定义 ML 调度器

    通用调度器把训练作业当黑盒，分不清陡峭前期与收益递减尾部，只能优化完成时间而非 time-to-accuracy。四个研究系统的分野在于信任哪种内部信号：已消耗服务、迭代边界、完成价值、实测 goodput。

    系统 关键洞察 信号 优化目标 实测收益
    Tiresias 已消耗服务量预测剩余时间 GPU 时分箱 最小化平均 JCT JCT 降 40–60%
    Gandiva 迭代边界是天然抢占点 迭代计时 最大化利用率 100 GPU 托管 120 并发作业
    Themis 沉没成本影响公平 完成百分比 最小化最大减速 近完成作业优先
    Pollux batch 与分配耦合 goodput 最大化集群 goodput JCT 改善 37–50%
    • Tiresias：按已消耗 GPU 时降优先级（<1 / 1–10 / 10–100 / >100 GPU 时分箱），不需要用户给不出的时长估计；重尾分布下"年轻作业大概率是短作业"，近似理论最优 SRPT 而无需预知未来。Microsoft/Alibaba 生产 trace 上平均 JCT 降 40–60%，代价是长作业被系统性降级——但短作业多数的收益大于长作业少数的损失。
    • Gandiva：迭代间只有权重 + 优化器状态驻留 GPU，上下文切换以秒计（迭代中抢占则全量激活在显存）；作业 20% 迭代时间在等数据 → 超订交错装箱。附带基于迭代画像的细粒度 grow-shrink：高优先级到来时缩编低优先级作业而非杀掉。
    • Themis：90% 完成只差 10 GPU 时的作业优先于 10% 完成需 90 GPU 时的作业——延迟前者一小时浪费 900 GPU 时的沉没投资（这些投入只在完成时产生价值）；经拍卖机制实现，作业按边际价值（每 GPU 时能改善多少完成时间）竞标。
    • Pollux：同时改 GPU 数和 batch size 最大化集群 goodput（统计效率 × 系统吞吐折成一个数）；但错误的 goodput 模型可能伤模型收敛——最脆的失败模式，多数生产团队不愿为 15% 效率冒此险。

    复杂度梯度决定失败模式：Tiresias 假设错了优雅退化为 fair-share；Gandiva 画像错了表现为装箱干扰抖动；Pollux 错改训练语义本身。生产路径多为"先 Tiresias 式政策解堵队列，再考虑 Pollux 式深集成"；且无人整体安装研究调度器——都是把算法移植成 K8s operator / Slurm 插件，应对异构硬件代际（V100/A100/H100 混部）与谎报需求的作业。自研账：3–5 个系统工程师生 6–12 个月；10K H100 舰队（约 $25,000/小时折旧+电费）利用率 +10% ≈ 年省约 2,200 万美元——这是每个大 AI 实验室都自研调度平台的理由。War story：OpenAI 7,500 节点 K8s 集群（GPT-3/CLIP/DALL-E）遭遇经典 gang 死锁——默认调度不保证整组同放，两个各要全集群的作业各被放一半，集群看似忙实则零实验进展。教训：对 MPI 式训练，"部分 pod 已调度"不是部分进展，是纯浪费的分配。

    服务资源管理

    目标函数翻转：训练求吞吐，服务保毫秒级尾延迟下的突发流量。推理容量是围绕用户流量的"活包络"，而非围绕训练作业的批量分配。

    自动扩展的指标问题

    GPU 利用率是坏信号：高不等于在处理请求（后台维护/预热也算），且利用率-延迟关系在 70–80% 处非线性跳变，基于它的扩展是事后反应。有效指标：请求队列深度（10–50，领先指标）、P99 对 SLO 的余量（滞后指标）、LLM 的 pending tokens 与 KV cache 占用。LLM 瓶颈是双资源的：70B 长上下文仅 KV cache 可超 80 GB——突发长上下文请求会在低计算利用率下耗尽显存（算力看着闲、请求却 stall），只看利用率的扩展器对此全盲；组合指标取 max(归一化算力利用率， 归一化内存压力)。VPA 对 GPU 无用（改请求须重启 pod 重初始化 CUDA 上下文），但适合推理管道的 CPU 前后处理组件。

    冷启动与预测扩展

    70B FP16 权重约 140 GB：PCIe Gen4 x16（32 GB/s）裸传输超 4 秒，加上初始化/图编译/安全检查实际 60–120 秒；NVMe（7 GB/s）约 20 秒，网络存储可超 2 分钟。反应式 HPA 的致命窗口：175B 加载 3 分钟，流量 30 秒翻倍（产品发布/病毒事件）时新副本就绪前全是降级窗口。连续批处理（vLLM/TensorRT-LLM）当缓冲垫——把新请求插进进行中的 decode 步骤、以内存压力换延迟，直到 KV cache 页全占满才必须排队/丢载；调好最小副本与扩容阈值保住这个窗口是防 SLO 违约的主杠杆。因此 SLO 驱动策略："P99 超 400 ms（500 ms 目标的 80%）即扩"，配不对称滞回：扩容无稳定窗（保 SLO），缩容 15 分钟冷却（防抖动）——多余扩容的代价远小于错失扩容。三件冷启动缓解互补：最小副本（>0 消灭首波冷启动）、预测扩展（按昼夜/周模式提前上量）、预热（备用副本常驻显存，激活从分钟级降到秒级）。

    算账（10 副本 × 5 QPS = 50 QPS 容量，流量 60 秒内 40→80 QPS，加载 180 秒）：反应式 t=15s 触发、t=195s 就绪，约 4,725 个请求排队/丢弃违约；预测式提前 180 秒下令、ramp 开始时容量已 100 QPS，零违约。

    隔离与共享经济

    干扰四通道：HBM 内存带宽、L2 cache 逐出、PCIe 争用、热节流。隔离谱：MIG 硬件隔离最强，但切分固定、改 profile 要排空 GPU、粒度不匹配浪费（需 15 GB 的负载在 20 GB 切片上废 5 GB）；MPS 允许多进程 kernel 并发，消除 time-slicing 的 10–20 ms 上下文切换税、只加 5–10 μs/kernel，但无内存隔离——一个进程爆显存团灭同卡负载，适合同团队可信负载、危险于多租户；time-slicing 灵活但 10–20 ms 延迟惩罚 + 无隔离。CPU 侧 core pinning + isolcpus + NUMA 亲和（本地 ~100 ns vs 远端 150–200 ns，错域使亚毫秒推理 P99 膨胀 10–30%）是常被 K8s 默认调度忽略的低垂果实。信任边界定选型：多租户外部客户必 MIG（共享 GPU 侧信道有文档化攻击），同团队内部模型可 MPS。

    共享算账：80 GB A100 跑 7B 模型（FP16 权重 14 GB、运行足迹 26 GB）独占浪费 67% 显存；MPS 双租到 52 GB、浪费降到 35%。100 个 7B + 10 个 175B（各 8 GPU TP）舰队：独占 180 GPU vs 混合共享 130 GPU，省 27.8% ≈ 年省约 87.6 万美元，纯调度政策。互补装箱是关键：算力密集与内存密集（decode 重）同卡只互拖 ~5%，两个算力密集互拖 15–20%——调度成为找互补负载的多维装箱。

    路由与训练-服务边界

    服务单元是"TP 组"（8 GPU 逻辑整体）而非容器。round-robin 对生成负载必崩（输出长度差数量级，新请求总被发给背着长生成任务的副本）；LOR 改善；记忆感知路由按各副本 KV 占用分流——长上下文去宽裕副本、短请求去近满副本，有效 batch +30–40%。模型上线走影子流量阶梯 1% → 5% → 25% → 100%，v1 只在 v2 统计验证后逐级排空。延迟感知装箱把严格 SLO 模型与可秒级节流的批任务（embedding 生成）同节点，利用率与 SLO 兼得。

    训练/服务共享池的切换成本：checkpoint（1–5 分钟）+ 杀容器 + 起服务 + 加载权重（2–10 分钟）+ 预热查询 = 5–20 分钟——GPU 只能跟昼夜曲线而非秒级突发：预测提前 30 分钟，7:30 抢占低优先级训练（超参 sweep）预热推理副本，22:30 排空归还训练侧。1,024 GPU 算例：静态分区（服务池按峰值留 400、均值只用 150）舰队利用率 75%；动态共享按需取用 + 训练回收 + 117 GPU 安全垫，每日两次按预测迁移约 133 GPU → 88%，年价值约 230 万美元。

    多租户与配额

    没有治理的共享集群退化成公地悲剧：提交最凶、作业最大、重投脚本最顽的团队吃掉一切；慢节奏但可能高价值的项目永远排队，摩擦升级到管理层。

    层次公平共享与借用

    固定配额（A 500 / B 300 / C 200 GPU）在负载错峰时系统性闲置：A 的一半闲着，B 的队列溢出，250 GPU 被配额禁锢。层次配额允许向下借用：$\(Q_{\mathrm{effective}}=\min\Bigl(Q_{\mathrm{team}},\ Q_{\mathrm{department}}-\sum_{\mathrm{other}} U_{\mathrm{allocated}}\Bigr)\)$ 借来的容量抢占优先级低于自有：所有者回来时经抢占收回。没有借用，组织只能在"按峰值配额（保低利用率）"与"配额不足（保阻塞）"二选一；峰值很少同时发生，静态峰值配额浪费 25–40% 容量。突发容量更进一步：保证 64 GPU 秒取、上限 512 GPU 视集群松弛——超订比 1.2–1.5× 可行当实际利用率低于申请（申请 100% 实跑 70% 时，1.3× 超订总需求 91% 仍低于物理容量）；比例必须按集群遥测经验校准，真打满的作业超订只会全员降速。四级优先级骨架：P0 生产服务不可抢占；P1 生产训练仅服务中断可抢；P2 交互/调试高 precedence 短时限；P3 batch/研究全可抢占——超参 sweep 填满缝隙，关键重训一到即刻蒸发。

    计量、抢占税与治理

    三层计量区别"要了/忙了/干成了"：allocated（调度器保留、他人不可用）→ compute utilization（kernel 活跃时间，nvidia-smi 口径）→ productive utilization（真在推进模型状态，扣除等数据/通信/checkpoint）。500 allocated → 350 compute（70%）→ 280 productive（56%）的 44% 缺口是纯烧钱，只有最后一层关联价值。治理抓手：作业级标签 + "no tag, no schedule" 准入拒绝；仪表盘含碎片指数（因拓扑约束无法分配的空闲 GPU）、按优先级的队列深度与"混乱成本"（抢占率、spot 中断频率、恢复开销）；异常检测抓失控脚本（消费冲到 3× 历史基线）与净增长队列、以及功耗骤降（常先于存储故障引发的大面积作业失败）。

    抢占税是非线性的：64 GPU 175B 微调被抢 = 丢上次 checkpoint 后 15 分钟工作 + 20 分钟重载优化器状态 + 10 分钟预热（prefetch 回填、JIT 重编译、cache 预热），45 分钟窗口 GPU 通电零产出，$96/次；无限制则 12 次/天 = 576 GPU 时/天纯损耗。更隐蔽的是数据管道状态：shuffle 种子、epoch 内置换序、shard 字节偏移若不精确恢复，要么重读样本毒化梯度统计、要么打乱 epoch 间统计独立——恢复 PB 级管道需跨所有 loader worker 重放元数据日志；紧凑数据加载器 checkpoint（种子 + 置换索引 + shard 偏移）能显著降低此成本。缓解靠抢占预算：限频（如 ≤1 次/小时）与集群 churn 上限（任意 10 分钟窗口 ≤5% 容量），迫使调度器等自然完成而非触发级联。抢占级联本身也要防：紧包装集群里逐出一个中优先级作业，它立刻去挤低优先级，一次紧急服务上线波及几十个训练作业、checkpoint 重载风暴打满存储带宽。

    霍德问题两个 ML 特有放大器：RLHF 评测期等人工标注时策略模型节点占用可低于 10%（团队抱着预留防"还了拿不回"）；预处理管道慢于预估时 GPU 空占等数据。反制是利用率回收（"use it or lose it"：预留组连续 72 小时 <20% 利用率自动回收转 spot 池，赎回需 VP 批准）+ showback→chargeback 演进（chargeback 立竿见影但定价过猛会扼杀探索性研究）。算例：500 GPU 空置三周 ≈ 50.4 万美元资本浪费。安全侧：namespace/RBAC 隔离可见性；网络策略命名空间内 AllReduce 全通（环通信要求）、跨命名空间 ingress 全断、egress 限外联防数据外带。

    调试集群利用率

    仪表盘 60% 利用率 + 小作业排 3 天队可以同时为真——队列满和加速器空闲共存，因为调度器在执行仪表盘聚合掉之外的约束。诊断法：先比硬件能力，再看调度政策，最后测政策-基础设施错配。

    案例：三层诊断

    1,024 GPU 集群（400 A100-80GB + 424 A100-40GB + 200 V100，三代采购积累）报告 60% 利用率、50+ 作业排队。硬件层：A100 走 NVLink 可张量并行，V100 只有 PCIe 15.8 GB/s 限数据并行。分布层：15 个大作业全点名"≥64 GPU A100-80GB"（合计需求 1,200 GPU），8 个中作业要 A100-40GB，V100 零作业。病理叠加：过度指定（实测峰值显存仅 35 GB，80GB 模板照抄不重算）、池碎片（严格同构匹配使 153 个空闲 40GB 不可用）、搁浅资源（V100 被"legacy"偏见零分配、照付电费）、原子分配饥饿（大作业等完整兼容块，政策禁止替换与回填）。诊断：政策-基础设施错配——调度器正确执行了为同构 A100-80GB 集群写的政策，而集群已经异构。最贵的调度 bug 往往不是软件缺陷，而是没跟着基础设施更新的旧政策。修复是分层能力匹配 + 回填：表达能力需求而非 SKU、NVLink 节点留给 TP 作业、回填兼容小作业、低成本核算引流到旧卡、让正确的资源请求比抄模板更容易。两周验证：A100-80GB 有效利用率 72%→94%，A100-40GB 分配 64%→88%，V100 0%→71%，全集群 60%→84%（+24pp） ≈ 246 个满载 GPU ≈ 年回收约 700 万美元，零新增硬件。

    四个反模式签名

    • 僵尸作业：显存高占（>300 GB）+ SM 利用率 <5% 持续超心跳超时（~10 分钟）——rank 崩溃后 CUDA 上下文损坏/驱动死锁使清理失败，128 GPU 挂着空转，需节点级强制清理。
    • 数据饥饿：利用率 100%↔0% 高频锯齿，均值 60–70% 似健康、实则三分之一生命在等数据（CV 的 JPEG 解码/增强打满 CPU 是典型）；标准差 >30% 为诊断指标，处方是预取/加载器并行/NVMe 缓存。
    • 通信瓶颈：所有 rank SM 周期性同步下探；步时比 >1.5× 纯计算时间（前向+反向）即网络成为主导约束，处方是拓扑感知放置或梯度积累提高算通比。
    • 内存碎片陷阱：KV cache 占 80% HBM 却接不了新请求（空闲内存碎成非连续小块）；"请求 token 槽/分配字节"比值暴露它，分页分配器靠解耦逻辑连续与物理布局把服务吞吐提 2–4×。

    经验与常见坑

    • 别把调度当运营开销：它是年化数千万美元级的杠杆，任何"提高 1% 利用率"的工程投入都值得认真算账。
    • 优先级/配额不能替代组调度的原子性：只要原子性只落在 GPU 粒度，死锁会在互连域、网络容量等下层资源重现——原子性必须覆盖作业进展需要的每个协同调度资源。OpenAI 7,500 节点的教训："部分已调度"对 MPI 训练不是进展。
    • 回填依赖运行时间估计，而用户恰恰给不准；组合拳是"组调度保安全 + 回填提利用 + 租约/进度监控兜底活性"。
    • 排队论给运营的红线：重尾负载下别把集群推过 ~70% 利用率再谈响应性；准入队列长度要按 C_s 而非指数假设校准。反过来，高利用率也不等于健康：ρ=90% 时平均等待 9× 服务时间、95% 时 19×；训练集群健康目标 70–85%，推理集群更低（50–70%）。
    • 先审计政策再升级算法：FIFO + 正确政策（能力匹配、带回填、合理 gang 约束）常胜高级调度器 + 错误政策；异构硬件到位后旧作业模板不更新，是最常见的利用率黑洞。
    • 单一利用率数字掩盖一切：必须拆 allocated / compute / productive 三层，只有 productive 关联真实价值。
    • gang 调度不是永远必需：异步或弹性训练可放宽原子性约束，换取大幅缩短排队——代价是陈旧梯度/batch 波动的收敛风险，超参 sweep 与微调类负载通常划算。
    • spot 不是永远便宜：15 分钟 checkpoint + 30 分钟重启 + 每 2 小时中断，会把名义 65% 折扣的实际节省压到约 52%；100B+ 模型在抖动市场里按需可能反而更省。
    • 弹性训练补充而非替代 gang 调度：TP 组的 8 GPU 是不可放松的原子约束，弹性只作用于数据并行副本数。
    • 调度器不是装完就忘的家电：gang 超时、拓扑权重、抢占宽限期、fair-share 衰减率的 ML 特定调优可提 15–25% 利用率，且须随负载结构漂移（训练主导→推理主导）持续重调。

    ⚠️ 时效性说明

    文中具体价格与硬件数字（$2/GPU·小时、A100/H100 带宽与对比、MIG 配置、spot 折扣率、Philly 52% 利用率等）均为写作时点的参考值，实际采购与云定价会随时间变化；引用的研究调度器收益（40–60% JCT 改善等）来自各自论文的实验环境，落地收益取决于集群负载结构。
