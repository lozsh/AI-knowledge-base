    性能工程¶

    来源：《机器学习系统》教材第 9 章（PDF 提取原文，wiki 化重写于 2026-11-03）

    一句话定义：性能工程通过重塑计算本身（数据移动、精度、编译、算法变换）使其匹配硬件物理特性，把"理论上快"的模型变成"实际快"的生产系统，通常可带来一个数量级的提升。

    性能工程与模型压缩的分工：压缩（剪枝、量化、蒸馏）缩小模型的内在工作量；性能工程则让剩余工作量与硬件的物理特性对齐——把数据留在快速内存、把每次传输打包得更密、消除软件开销。二者互补：把量化后的模型直接加载到加速器上，若每个权重仍从片外内存读取，量化的带宽收益就被浪费了。

    本章内容属于舰队栈中服务层内的优化学科：从内存层次结构出发，依次讨论算子融合、精度工程、图编译、算法性能变换（推测解码、稀疏专家路由）、通信-计算重叠与系统性能分析，最后以 70B LLM 优化案例收束。所有手段都属于 C³ 分类法中的"计算"项——从舰队已有的周期中榨取更多有用工作。

    核心原理¶

    ML 性能铁律¶

    执行时间可分解为三个竞争项：

    T ≈ max(计算项, 数据项) + 开销项
   = max(FLOPs / (Peak × η_hw), D_vol / BW) + T_overhead
    • 计算项：总浮点运算数 ÷ 实际达到的硬件吞吐。
    • 数据项：总传输字节 ÷ 内存带宽。
    • 开销项：其余一切——内核启动延迟、同步、通信、软件栈低效。PyTorch 训练循环中，每次内核启动都要穿越 Python GIL 和框架调度器，每个操作耗费数十微秒后才进入 GPU 命令队列；torch.compile(mode="reduce-overhead") 和 CUDA Graphs 正是为此而生：把重复的 GPU 提交变成原生重放，绕过 GIL 与调度器。

    Roofline 近似则进一步问：在给定工作点上哪个暴露项占主导。诊断主导项，再应用针对该项的技术——把优化用在非主导项上是浪费工程努力。

    手段与铁律项的映射¶

    铁律项 攻击手段
    数据项（字节/BW） 算子融合、分块（消除中间 HBM 往返，注意力场景可降 10-30 倍片外访问）；精度工程 FP8/INT4/KV 缓存压缩（同带宽携带更多有用状态）
    开销项 图编译（torch.compile、XLA、TensorRT）：消除启动间隙、融合算子、优化内存分配
    计算项 通信-计算重叠（当 T_comm(N) − T_overlap ≤ T_compute/N 时通信退出关键路径）；算法创新：推测解码、MoE 稀疏路由（改变计算本身）

    诊断先于优化¶

    标准排障流程：训练慢/GPU 利用率低 → 先排除 I/O 受限（DataLoader 停滞）、CPU 受限（预处理）、通信开销 → 再用 Roofline 分类为计算受限或内存受限 → 前者走精度工程与算法优化，后者走算子融合与图编译 → 改后重新分析。误诊不只是浪费：盲目的性能改动可能把系统推到错误的工作点。

    关键概念¶

    效率前沿¶

    吞吐、延迟、成本、质量、内存五个维度构成的帕累托前沿：

    维度 测量 典型张力
    吞吐量 tokens/s 或 requests/s 大批量提升吞吐但退化延迟
    延迟 TTFT 与逐 token 延迟 低延迟需要小批量、更高单价
    成本 每 token 成本 最便宜的配置可能错过延迟/质量目标
    质量 困惑度/基准准确率/人类偏好 降精度与投机解码需质量护栏
    内存 峰值 GPU 内存 大上下文与大批量消耗容量

    实例——同一个 70B 模型的两个部署点：配置 A 延迟优化（FP16、batch=1、投机解码，8×H100 服务单用户，约 50 tokens/s，token 间 20ms，约 $0.12/千 token）；配置 B 吞吐优化（INT4、batch=64，每 H100 聚合约 4000 tokens/s，token 间 120ms，约 $0.002/千 token）。B 单成本低 60 倍、延迟高 6 倍，没有客观上"更好"的配置，只有匹配应用的点。

    内存墙¶

    处理器不缺算术能力，缺数据。H100 提供 1979 TFLOP/s（FP8）但仅 3.35 TB/s 带宽：若每字节加载的内存执行的算术少于约 590.7 FLOP，计算单元就在挨饿。这是物理约束而非工程限制——片上 SRAM 访问约 0.5 pJ，片外 HBM 约 640 pJ，相差约 1280 倍；模型需要 GB 级参数，物理只允许 KB 级数据靠近计算单元。

    GPU 内存层次结构（H100）：

    层级 规模 访问成本 优化约束
    寄存器 256 KB/SM（共约 33 MB） 1 周期，~0.01 pJ 线程私有；FP32 累加器会强制溢出
    共享内存（SRAM） 最多 228 KB/SM 20-30 周期，~0.5 pJ 线程块共享；中间结果留在此时融合有利
    L2 缓存 50 MB ~200 周期 跨 SM 自动捕获重用，不可显式管理
    HBM 80 GB，3.35 TB/s ~300 ns，640 pJ 读全部带宽需约 24 ms，远超实时推理目标

    数据中心的能源账：1000 张 H100 在内存受限负载下每张每秒约 10¹² 次内存访问，仅 HBM 访问（640 pJ/次）就消耗约 640 W/GPU——内存子系统能耗与算力同量级。

    Roofline 模型¶

    可实现 FLOP/s = min(Peak, BW × I)        I 为算术强度（FLOP/字节）
脊点 I_ridge = Peak / BW

    I < I_ridge 为内存受限，I > I_ridge 为计算受限。各代 GPU 的 FP16 脊点：V100 ≈139、A100 ≈153、H100 ≈295（FP8 约 590.7）、B200 ≈281 FLOP/字节。计算逐代增长快于带宽，脊点趋势性抬升（约 7 年翻倍），越来越多工作负载落入内存受限区；且同一内核可跨硬件代际改变 regime，升级硬件时必须重新分析。

    常见 ML 操作落在哪¶

    操作 算术强度 区域 瓶颈
    GEMM（4096×4096 大批量） ~1365 FLOP/字节 计算受限 张量核心吞吐
    自注意力（seq=2048） ~50-200 内存受限 HBM 带宽
    逐元素（GELU、LayerNorm） ~1-3 内存受限 HBM 带宽
    LLM 解码（batch=1） ~1-2 内存受限 HBM 带宽

    Transformer 推理管线的大多数操作是内存受限的。推论：比较 LLM 推理 GPU 的正确指标不是 FLOP/s，而是内存带宽（决定 token 生成速率）与内存容量（决定最大批量）的组合；batch=1 时两块 TFLOP/s 不同但带宽相同的 GPU 解码吞吐几乎一样。

    服务机制：批量大小与 Prefill-Decode 分离¶

    批量大小是第一旋钮¶

    解码算术强度随批量近似线性放大：I_decode(B) ≈ 2B/(s_param·P + s_elem·B·d_model)。batch=1 时约 1 FLOP/字节（深内存受限）；batch=256 时约 256 FLOP/字节，逼近计算受限。H100 上 batch=1 约 5% 利用率，大批量可达 40%，每 token 成本可降约 8 倍。

    约束是内存：每个请求需要自己的 KV 缓存，总 KV 缓存必须与权重共存于 GPU 内存。PagedAttention 把 KV 缓存按固定大小块（页）按需分配，消除碎片（传统预分配在最大 4096/平均 500 的场景浪费约 88%），使有效批量增大 2-4 倍；与 KV 缓存量化叠加可达 8-16 倍，根本改变服务经济学。

    Prefill 与 Decode 是两种负载¶

    • Prefill：并行处理整个提示，n 个 token 的 GEMM 算术强度约 2n（1024 token 约 1024 FLOP/字节），计算受限，受张量核心吞吐限制。
    • Decode：自回归一次一个 token，batch=1 时约 1 FLOP/字节，深内存受限。

    Napkin math（70B @ 8×H100，TP=8，batch=1）：每 GPU 每步读 17.5 GB 权重产生 17.5 GFLOP，I=1 FLOP/字节；17.5 GB ÷ 3.35 TB/s ≈ 5.2 ms/token，约 191 tokens/s，仅用了 0.3% 的 FP16 峰值算力（实际还会被 KV 读取与 NVLink 同步进一步拉低）。改进路径都攻击同一权重流成本：更大批量摊销、量化减字节、投机解码一次权重传递换多个 token。

    分解服务（disaggregated serving）把两阶段放到不同硬件池：prefill 池要高 FLOP/s，decode 池要大带宽大容量，KV 缓存在池间传送。FlashAttention 在 prefill 收益最大；KV 量化与投机解码只作用于 decode；FP8/INT4 对两者都受益但机制不同（prefill 得双倍算力，decode 得双倍有效带宽）。

    算子融合与内核工程¶

    朴素执行 y = LayerNorm(GELU(xW + b)) 需要三次 HBM 往返：每个非融合内核都把中间张量实体化到 HBM。对隐藏维 4096、批量 2048（FP16），每个中间张量 16.8 MB，非融合执行产生 67.1 MB 中间 HBM 流量；融合内核把中间量留在 SM 内的寄存器/共享内存里，直接消除。类比：非融合是三个厨师共用一台冰箱来回取放，融合是一个厨师在案板（SRAM）上连续完成三步。

    内核启动本身也有开销：CPU 备参、派遣命令队列、跨 SM 调度线程块，小型逐元素操作约 5-20 μs——Transformer 层由几十个小操作组成时累积可观。这解释了融合与 CUDA Graphs 为何常一起使用。

    经验与常见坑¶

    • 先诊断后优化：对计算受限负载做融合、对开销受限负载做精度工程，都不会有改进。
    • 量化的收益要靠局部性兑现：量化模型若每个权重仍走片外读取，带宽节省归零。
    • 开销量不可忽略：Python 调度路径的每步数十微秒足以吞掉小内核的全部收益，用编译/CUDA Graphs 消除。
    • 通信重叠是有条件的：只有有用计算能覆盖通信（不等式成立）时才有帮助，它是暴露时间测试而非新定律。
    • 硬件升级后重新做 Roofline 分析：脊点逐代移动，同一内核可能改变受限区域。
    • GPU 选型看带宽+容量：报峰值 TFLOP/s 的基准无法预测 batch=1 的推理性能。
