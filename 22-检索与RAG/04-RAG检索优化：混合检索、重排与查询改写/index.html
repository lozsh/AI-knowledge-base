    RAG 检索优化：混合检索、重排与查询改写

    /> 来源：公开课程资料自学整理（更新于 2026-11-03）

    一句话概括：单路向量检索不够用时的标准武器库——混合检索（多路召回）+ RRF 融合 + 重排精排，再配合查询扩展/改写与元数据过滤，把模糊检索尽量转化为精确检索。

    核心概念

    • 混合检索（Hybrid Search / 融合检索 / 多路召回）：同时用多种检索方式（典型为向量语义检索 + BM25 关键词检索），结果融合。不限定必须是哪几种（如知识图谱检索实体关系也可作为一路）。
    • 为什么需要：向量检索的弱项恰是关键词检索的强项——
    • 精确匹配：订单号、产品名、人名、品牌名（向量容易匹配错）；
    • 超短查询：缩写词（RAG、LLM）语义信号太少；
    • 低频关键词：低频词承载关键信息（"喝咖啡"比"你吗"重要）。
    • 反之，关键词检索给不了语义上下文扩展。
    • 重排序（Reranking / 精排）：混合检索解决"相关结果在不在候选里"（召回），重排解决"最相关的排最前"（排序）。微软 Azure AI 实验证实：混合检索 + 重排序的组合在多个数据集上均为最佳，显著优于任一单路。

    关键方法/原理

    粗排与精排的分工

    • 粗排（向量/BM25）：快，能召回但不保证强相关。
    • 精排（重排模型）：慢，只在粗排的少量候选上运行。
    • 这正是传统搜索"召回→排序"分层架构（见 01 篇）在 RAG 中的重现：用更小的代价快速缩小范围，把贵计算留给少量候选。

    重排序模型（Reranking Model）

    • 与嵌入模型的本质区别：嵌入模型（Bi-encoder）把查询和文档各自独立编码成向量（可离线建库，快但粗）；重排模型把查询和文档一起输入（Cross-encoder 交互式），直接输出相关度分数（细粒度交互，准但慢、无法预计算）。
    • 可用模型：商用 Cohere；开源 BGE-reranker 系列（如 bge-reranker-v2-m3）、Sentence、Mixedbread、T5-Reranker；甚至直接用提示词让大模型对候选块排序（输出"1,2,3,4"式序号）。
    • 代价：参数量大、计算资源消耗高、推理慢——必须控制精排候选数量（对粗排 Top 2×K 个重排取前 K）。

    RRF 融合

    • Reciprocal Rank Fusion（倒数排名融合，课程译"递归折减融合"）：不比较各路的分数（不同检索器分数量纲不同），只看排名——文档在越多路的结果里排得越靠前，综合排名越高。
    • 定位：比重排模型简单得多、零成本，适合快速融合多路结果的场景；重排模型可在其后再做一层精排。

    查询侧优化

    • 查询扩展（Multi-Query）：让 LLM 从原始问题生成多个不同角度的子问题，各自检索、结果合并重排——克服"单个向量只能覆盖向量空间一个有限区域"的局限。
    • 查询重写（Query Rewrite）：把模糊/口语化的提问改写为清晰、具体、与检索任务匹配的查询。
    • 自查询（Self-Query）：让 LLM 从问题中抽取业务关键的元数据字段（标签、作者、类别、编号），用元数据过滤 + 向量/关键词检索结合，避免这些关键信息在向量里被稀释。
    • HyDE（假设文档嵌入）：让 LLM 先生成一个"假设性答案"，把假设答案向量化去检索——答案与文档的语义分布比问题与文档更接近，命中更准。
    • 分解子查询：复杂问题拆成多个简单子问题分别检索再整合（多跳问题的基本解法）。

    索引/数据侧优化

    • 数据清洗预处理（解析后、分块前）：去重复模板内容（合同里重复的法律条款）、去多余空白与格式不一致、去页眉页脚/脚注/版权声明——提升文本块语义密度，减少向量库噪声。
    • 元数据过滤：分块时附加元数据（日期、章节、文档类型、模块），检索时先按元数据缩小范围再做语义匹配。一种已验证的落地形态：UI 标签栏让用户点选模块，精确信息直接传后台过滤，不让大模型猜（又快又准、prompt 还更短）。
    • 多层/多粒度索引：句子级+段落级+文档级分层嵌入，按查询长短选层；小到大检索（small-to-big）：用小块做精准检索命中，返回时附其父块/大块做生成上下文；句子窗口检索：命中句子后扩展前后 N 句作为窗口。

    混合检索实践的总原则

    尽量将模糊检索转化为精确检索——"尽量"而非绝对，从多个层面提高转化率： 1. 用户交互层面：标签栏/表单让用户主动提供精确信息（模块、类别）； 2. 业务逻辑层面：识别必须精确匹配的关键词（股票代码 300498、配件型号 sh-d32），走精确检索通道而非语义相似——模糊检索可能返回 300497/300499，是事故。 - 综合过滤技术栈：元数据过滤 + 相似度阈值 + 关键词 + 内容过滤（不合标准剔除）+ 多样性过滤（去近似重复，避免 Top10 全是同一篇的不同块）。 - 投票与加权：多路/多法检索后用投票+加权机制决定最终入选知识。

    术语表

    术语 一句话解释
    混合检索 多种检索方式（向量+关键词等）并行召回再融合
    RRF 倒数排名融合：按各路排名（而非分数）合并多路结果
    重排 / Reranker 对候选块精细打分重排的精排模型（Cross-encoder 类）
    Bi-encoder vs Cross-encoder 查询文档分别独立编码（快粗）/ 拼接一起编码打分（慢准）
    查询扩展 LLM 生成多角度子问题分别检索
    HyDE 生成假设答案、用答案向量去检索的技巧
    自查询 LLM 抽取查询中的元数据字段做结构化过滤
    提示压缩 检索后剔除无关内容、只留高相关信息再送 LLM
    小到大检索 小块检索、大块生成的多粒度策略
    句子窗口检索 以句为检索单元、返回时扩展前后文窗口
    多样性过滤 过滤近似重复条目，保证结果多样性

    经验与常见坑

    • 只做向量检索不做混合，遇到编号/型号/缩写类查询必然翻车；反之只用关键词检索则丢失语义扩展。默认配置应是混合检索 + 重排。（RAG快速弉
    • 各检索器的分数不可直接比较，跨路融合要么用 RRF 这类排名法，要么统一交给重排模型重打分。
    • 重排模型是全链路最贵的一环：候选给太多会拖垮延迟；生产环境在精度与效率间做平衡（控制候选数、用 fp16、轻量模型）。（RAG快速弉
    • 让大模型"猜"用户在哪个业务模块查询，既慢又可能猜错——能用 UI/业务规则拿到的精确信息就不要让模型猜。（系统实漉
    • 股票代码、型号、订单号这类标识符必须走精确检索，语义检索返回相近编号是事故级错误。（系统实漉
    • 查询扩展召回的候选与原查询召回的候选混在一起重排时，注意融合策略（各查各的再合并重排 vs 组成新查询），并在评估集上验证扩展是否真的带来增益。
    • 检索结果不缺"相关"而缺"多样"：近似重复的块会挤占上下文窗口，多样性过滤常被忽略但收益明显。（系统实漉

    ⚠️ 时效性说明
