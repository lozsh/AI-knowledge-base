    多模态与实时交互

    来源：原资料（更新于 2026-11-03）

    一句话定义：多模态实时交互研究 Agent 如何在语音对话、GUI 操作、机器人控制等输入持续流动、输出受严格时间预算约束的场景中，同时处理多种模态信息并实时响应——这是 Agent 跳出"对话框"的关键一步。

    多模态指同时处理文字、语音、图像、视频、动作等多种信息形式。静态的"一次输入、一次理解"类任务（看截图、读图表、解析 PDF）对今天的多模态大模型已相对成熟；本章聚焦的是实时性把问题变难的三个场景：语音对话、Computer Use（GUI 操作）、机器人控制。三者卡住的地方高度相似：都要同时处理多种模态、都对延迟极度敏感（语音停顿超两秒让人焦躁，机器人毫秒级抖动可能导致碰撞）。这两个约束把三个场景推向同一个架构方向：从串行流水线走向端到端模型。

    边界说明：多模态生成（生图、生视频）在 Agent 框架中只是普通的工具调用，不涉及实时交互难题，不在主线之内。

    一、语音：三种架构范式

    语音是带宽最高、最自然的人机接口：说话速度约为打字四倍，且不占双手视线。产品形态两类：语音输入法（如 Typeless，口述转文字，替换键盘）与语音 Agent（如 ChatGPT Voice、Pine，语音既是输入也是交互本身）。进阶用法是 whisper coding——以口述指挥编程/研究 Agent。同一套技术也服务于 Agent 代替用户对外说话（如打电话协商）。

    按 OpenAI 2026 年发布 GPT-Live 时的三分法（对应 ChatGPT 语音三代架构）：

    范式 架构 轮次假设 代表
    级联（Cascaded） ASR→LLM→TTS 流水线 依赖 VAD 划分轮次 最早的 ChatGPT Voice、智能音箱、客服机器人
    端到端全模态（Omni） 单模型直接"听音频、想回复、说出来" 仍靠 VAD 判断轮次切换 ChatGPT 高级语音模式、Qwen3-Omni
    全双工（Full-Duplex / Interactive） 边听边说，每秒多次决策"该说/听/停/打断/调工具" 彻底取消轮次 Moshi（2024）、GPT-Live（2026）

    贯穿三代的主线：如何摆脱"轮流说话"假设、摆脱 VAD（语音活动检测）对轮次的猜测。三种范式是不同延迟与成本约束下的取舍，2026 年的生产系统中长期并存。

    范式一：级联流水线

    四阶段串行：VAD 判断用户说完 → ASR 转文字 → LLM 生成回复 → TTS 合成。各环节延迟：VAD 等待 500–800ms（静音阈值）+ ASR 50–200ms + LLM 首字 100–500ms + TTS 200–500ms，总计约 0.9–2.3 秒——还是空载理想情况。

    两个关键问题：

    • VAD 结束点检测两难：静音阈值太短，思考停顿被误判为说完、句子截断；太长，说完后干等大半秒。
    • 排队延迟非线性飙升：排队论给出总延迟 ≈ 空载延迟 × 1/(1−利用率)。利用率 50% 延迟翻倍，80% 变 5 倍——生产环境利用率通常控制在 0.5–0.8。

    全链路流式化：2025 年后的主流做法不是抛弃模块化，而是保留分工、让各级流式重叠——ASR 边听边转、LLM 按句切分输出、TTS 句级流式合成，端到端延迟可压到 600–800ms（LiveKit Agents、Pipecat 走的路线）。但 VAD 的静默等待压不掉——它无法预知未来，只能靠"等一等"区分"说完了"和"停顿想想"。

    流式语音感知（替代 VAD+ASR）：传统级联的三个根本问题——延迟累积、信息丢失（VAD 只输出二值信号，情绪、语气、犹豫全部丢失，"嗯"无法判断是打断还是附和）、准确率下降（切碎片段破坏上下文，报邮箱时"smith"缺上下文被误识别为"miss"）。新路线是以开源 LLM 为骨干后训练的音频感知模型（Ultravox、Qwen2-Audio、Qwen2.5-Omni），把"识别"和"理解"合并：基于从对话开始的连续音频流做上下文学习，且继承 LLM 的世界知识（"苹果"+"发布会"→Apple）。注意"流式"的技术含义：编码器因果/分块 + 解码增量；Whisper 不能流式是因为其编码器需完整 30 秒音频段，而非解码方式。更轻的路线是把轮次判断做进识别器（Deepgram Flux、AssemblyAI Universal-Streaming）：小流式识别模型加 LoRA，边转写边综合语义与静音判断"是否说完"——因为轮内停顿（报电话号码时顿一下）常比轮间间隔还长。一个深刻教训：模型在"该不该收话"上摇摆，根源常不在架构而在训练标签用了"上帝视角"（标注时用到决策点之后的音频）；把标签改成"只用决策当下能拿到的信息"，摇摆就消失了——数据比架构更关键。

    模型输出除文字外还有声学事件标记：<speak_start/end>（语义+声学综合的起止判断）、<interrupt>（真打断 vs 附和 vs 噪音）、<emotion:...>、<laugh>/<sigh>、<music>/<noise>，与文字 token 形成统一事件流送入思考层。

    范式二：端到端全模态（Omni）

    单模型直接听、想、说，隐空间在文本之外保留副语言信息（情绪、语调、环境声）：延迟更低、韵律情感保留。代价：训练数据需求更大、可解释性更差、每段无法独立调优。

    准确率维度上端到端并不必然占优——自级联（self-cascade）（同一模型先转结构化文本再推理）在答案主要由语义决定时相当乃至更优；答案依赖语调情绪等非语言线索时端到端才显优势。设计原则：关键不在有无中间表示瓶颈，而在瓶颈承载的信息——把中间文本升级为附带副语言标记的结构化表示，端到端的准确率优势往往收窄。

    但 Omni 本质上只是三模型合一，没有取消"轮流说话"：用户报数字中途停顿仍会被强行插话。代表系统：

    • OpenAI Realtime API：模型层接近端到端，控制层仍靠服务端 VAD，属过渡方案；2025 年 GA 后用专用模型 gpt-realtime；支持打断、异步函数调用（等工具返回时继续说话）。
    • Gemini Live API：类似思路，VAD 敏感度可配，打断时保留已发信息。
    • Qwen3-Omni：Thinker-Talker 架构（思考与表达分模块）；Talker 以多码本自回归生成音频 token、因果 codec 增量解码，冷启动首包延迟约 234ms，36 项音视频基准 22 项领先。
    • Step-Audio 2：直接处理原始音频，感知副语言信息（StepEval-Audio-Paralinguistic 基准 83.09%，大幅领先 Qwen2.5-Omni 的 44.18%、GPT-4o Audio 的 43.45%），集成 RAG 与工具调用、强化学习生成富有表现力的回复。

    范式三：全双工（Full-Duplex）

    有些场景不是"你一句我一句"：同声传译边听边译，节奏游戏甚至无所谓"一轮"——输入是永不停歇的连续流。全双工把"摆脱 VAD"走到逻辑终点：取消轮流假设，同时持续地听和说。

    • Moshi（Kyutai，2024）：并行建模两条音频流（用户声音 + 模型自己的声音）+ 一条"内心独白"文本流。任一时刻都在收听，重叠说话、随时打断是天然行为，无需打断检测逻辑，端到端延迟约 200ms。
    • 交互模型（Thinking Machines Lab，2026）：主张交互性应内建于模型自身而非外挂 harness。微轮次（micro-turn）：以约 200ms 为一段持续"读入 200ms、生成 200ms"，音频/视频/文本多路流交织——足够细使静音、重叠、打断都作为连续流保留在上下文里，又足够粗能把多路模态成块并发处理。TML-Interaction-Small（276B MoE、激活 12B）轮次切换延迟约 0.40 秒。
    • GPT-Live（OpenAI，2026）：全双工到生产规模（1.5 亿用户），持续输入持续输出，每秒多次交互决策：用户思考时安静等待、用"嗯""对"附和、胜任实时翻译。同时把"实时交互"与"深度思考"解耦——遇到需要搜索/复杂推理的任务委派给后台前沿模型（发布时 GPT-5.5），自己继续维持对话。

    二、思考架构：实时响应 vs 深度思考

    核心矛盾：用户期待毫秒级回应，复杂问题需要秒级思考。三种方案不是线性迭代而是并存的设计取舍（方案一、二是"两个独立模型并发"，可套在级联流水线上；只有方案三把思考内化进单一模型）。

    到 2026 年，"快慢解耦"已是前沿语音产品的主流：Thinking Machines Lab 称之为"交互模型"，xAI Grok Voice "Think Fast"、Pine AI、GPT-Live 委派走的都是同一条路线。不解耦、非训练一个全能模型的务实理由：前沿推理模型每隔几个月迭代一次，实时交互能力需要专门数据与训练目标——塞进同一个模型等于追移动靶子，还稀释推理能力；解耦则后台可随时换用当下最强的大脑。

    方案一：快慢并行，各自回答

    快思考 500ms 内给应付性回答（"让我想想"式），慢思考后台 5–10 秒深度思考（test-time scaling：多步推导换更高质量）后给完整回答。两大问题：简单问题过度思考（"今天星期几"答完 10 秒后被重复回答打断节奏）；快慢不一致（独立思考路径得出相反结论，用户几秒内听到自相矛盾，信任崩塌）。

    方案二：快思考交互，慢思考当"军师"

    慢思考能看到快思考的输出，通过 Agent 状态栏（动态元信息注入）提供建议而非直接对用户说话。GPT-Live 委派、Pine AI 是生产实例。仍有本质局限：沟通间接模糊（"价格需要重新确认"可能被理解成"问用户能否接受"）；看不到中间思考结果（递纸条合作却看不到草稿纸）；且无法实现"边想边说"——只能说填充词干等结果。

    方案三：思考内化，边想边说（Step-Audio R1）

    双机制解决两个问题：

    • MGRD（模态锚定思考蒸馏）解决"想得对不对"。反直觉现象：现有音频模型的思考链越长性能越差。根因是文本代理思考——模型基于文本转录而非声学特征思考（判断歌曲情绪时分析"歌词提到悲伤"而非"小调旋律+下行音高"），因为 CoT 数据多由文本模型生成。MGRD 迭代自我改进：采样多条思考链→筛选真正基于声学特征的（"语速快 40%、音量升高、声调变尖"）→重新训练→RLVR 防止跳过思考直接猜答案。多轮迭代后思考根基从文本抽象迁移到声学分析。
    • MPS 双脑架构（Mind-Paced Speaking）解决"说得及不及时"。灵感来自人脑思考区与语言区并行：构思脑持续思考产出思考片段，表达脑每收到一段就转化为语音，流水线并行——t=0 构思脑开始，t=200ms 输出第一段思考，t=350ms 用户听到第一个音节。

    实验数据（Spoken-MQA 语音数学推理）：不思考 70.6%；MPS Speak-First（零延迟）92.8%；Think-First（约 80 token 延迟）93.9%；完整先想后说 93.0%。有趣发现：零延迟几乎不损准确率（CoT 开头通常在复述问题、还没进入真正推理）；Think-First 甚至略高于无延迟约束的完整 TBS（分段产出思考起了类似分步监督的作用，差距在评测误差内，不宜过度解读）。

    产业分野：方案三最优雅但代价是"移动靶子"（两种能力都快速演进、需反复重训）；追求"可换大脑"的前沿产品（GPT-Live、Grok Voice、Pine AI）多押注方案二。两者是"可换的大脑"与"更紧的边想边说"之间的取舍。

    快慢之间的接口：Latent Bridge（潜空间桥）

    方案二用文本通道"递话"，是慢思考中间状态的一根细吸管。在实时游戏场景中走得通的路子：快慢两模型都冻结，只训练之间几千万参数的小"桥"，把慢模型隐层结论直接投影成几个"潜 token"拼进快模型输入，绕开"想法→文字→再理解"的往返。多个 Atari 游戏上比文本通道高出一截（部分游戏 +26% 到 +82%），每步只多约 5ms。诚实边界：快慢协作有没有用取决于任务瓶颈在"想不想得到"还是"来不来得及反应"（相关性跨游戏 r≈0.9）——纯拼反应速度的任务，再好的桥也无济于事。

    三、更像人的语音合成

    传统 TTS 的"完美"（过于流畅、零停顿、无填充词）恰恰暴露机器身份——人类的停顿、"嗯"、"呃"是思考过程的自然外化。解决方案：把"哪里停顿、用什么语气"的决策权交给主 LLM，输出控制标记：[THINKING]（1–2 秒思考停顿+填充音）、[SEARCHING]（短停顿+搜索性填充词）、[EMO:happy]（语气韵律）、[SPEED:0.8x]（语速）、[SIGH]/[LAUGH]/[BREATH]。只有 LLM 知道当前该停顿、该加快语速还是该活泼。实现路径：自研 TTS 原生支持（灵活但需专业团队），或 voice cloning 多参考语音库（同一音色备数十条不同情绪/语速/风格的参考语音，按标记选择，用 ElevenLabs、Fish Audio 等几周可部署）。

    四、Computer Use：GUI 自动化 Agent

    让 AI 像人一样观察屏幕、操作鼠标键盘。核心是感知-思考-行动循环：截图 → 多模态模型输出思考+动作 → 执行（点击、输入）→ 等界面响应再截图。三个关键设计维度：

    动作空间

    Anthropic 定义三类工具：computer（鼠标移动/点击/拖拽/按下松开、滚动、逐字符输入 type（12ms 间隔模拟打字）、组合键、长按、截图、光标位置、wait）；bash（持久终端会话，120 秒超时，哨兵字符串检测命令完成，跨调用保持环境状态）；str_replace_editor（字符串匹配的安全文件编辑：查看/创建/替换/插入/撤销）。典型速度：每个动作间隔 2–5 秒（截图-识别-思考-点击串行），约为人类的 1/3 到 1/5。

    视觉定位（Grounding）

    模型如何在截图中找到目标元素，两大思路三条路线：

    路线 做法 适用 特点
    结构化元素索引 从 DOM/Accessibility Tree 枚举可交互元素并编号（SoM 思想的 Web 结构化实现，browser-use 为代表） 网页、有 Accessibility 接口的桌面应用 定位最精确稳定，免分割漏检；不省 token
    视觉标注（Set-of-Mark） 分割模型（SAM/SEEM）在像素上切候选区并叠编号，模型报编号 原生桌面软件、游戏界面（无 DOM 可用时） 把开放坐标预测变成封闭 ID 选择，对通用模型友好
    纯坐标预测 海量 GUI 截图-坐标配对数据训练，模型直接报坐标（SeeClick、Claude computer use） 任何界面 省标注步骤；小元素和密集界面精度仍有差距

    坐标预测的工程关键——分辨率匹配与双向坐标缩放：模型对坐标的理解依赖训练分辨率（Claude 用 XGA 1024×768、WXGA 1280×800、FWXGA 1366×768）。截图先按宽高比选最接近的目标分辨率等比缩小送入模型（如 2560×1440 的 16:9 屏幕选 FWXGA），模型输出坐标后按比例放大回真实分辨率执行；非等比拉伸会把画面压扁、坐标系统性偏移。

    观察接口：能看动画、能听声音

    现有 Computer Use 假设屏幕静止——每 3–5 秒睁一次眼且没有耳朵，对"两帧之间发生的事"（视频、转瞬即逝的通知、会议人声）是禁区。AOI（Agent–电脑观察接口）：把连续、自适应、多模态的观察从离散动作里解耦，做成插在环境与现成模型之间、无需重训的感知中间件，三个"按需开闸"部件：像素门+小模型判断的帧间关键帧捕获（静止画面近零成本）；音量门控的语音转写；以及最关键的把帧叙述成持久文字——原图被清理出上下文后，"刚弹出的提示说发布日期改到 4 月 28 号"这句话仍留在记忆里。反直觉发现：起作用的不是"选哪几帧"而是"叙述成文字"——文字才是 LLM Agent 最擅长的模态。7B 到前沿规模八个模型上无需重训带来 +17 到 +48 个百分点，语音类任务提升最悬殊；但部件要按模型逐个挑选（某些新模型塞太多图像 token 反而拖累推理）。

    移动端与实时性挑战

    移动端技术差异：动作空间改用系统无障碍服务 API（Android AccessibilityService），触摸手势使坐标语义改变（单击/长按/滑动起点需额外界定），AndroidWorld 等基准在此动作空间上评测。但真正卡住移动端的是生态壁垒而非技术：有厂商集成 AI 助手自动操作微信、淘宝、支付宝即遭平台封杀。根本原因是商业模式冲突——Agent 直奔目标完成任务，绕过了广告和流量变现链路。这是结构性利益冲突，比 CAPTCHA 等技术对抗更棘手。

    实时性：OSWorld 基准上早期模型成功率约两成，截至写作时已逐步接近人类水平，但 OSWorld-Human 效率研究揭示：即使成功，操作步骤明显多于人类，且每步推理延迟随上下文增长——人类几十秒的文档调整 Agent 要数分钟。根源与语音类似：串行循环不会"提前想"（理想是等页面加载时就想好下一步，把思考和执行重叠——"边想边操作"）。Computer Use 循环本身的提速尚无系统性方案，但快慢解耦已跑通：小模型（快）实时语音对话 + 前沿 VLM（慢）操作浏览器，之间只靠一份极简"纯文本契约"——慢 Agent 每次操作附带滚动更新的状态摘要，快 Agent 据此实时回应用户、并把用户口头信息转达给慢 Agent，且摘要确认完成前绝不说"办好了"。效果：语音回应快约 15 倍（中位 0.58s vs 8.64s）而成功率不降；抽掉文本通道成功率立刻塌到 0（用户口头信息传不到浏览器）。这份契约本质上就是 Agent 状态栏。

    五、机器人操作：从实时控制到训练与泛化

    当 Agent 控制物理世界，延迟与多模态挑战被进一步放大——动作后果不可逆，一次碰撞可能损坏物体或机器人。

    硬件不是瓶颈（有边界），算法才是

    XLeRobot 的反证：成本不到 1000 美元的双臂轮式机器人，人类通过 VR 遥操作（延迟约 100–200ms）已能流畅完成大量家庭任务；宇树机器人人类遥操作下也能完成需灵巧手的任务。传感器、执行器、控制频率在低成本平台已足以支撑实用任务。⚠️ 边界：这只说明"低成本硬件+人类智能足以完成以视觉反馈为主的家庭操作任务"；触觉传感缺失、灵巧手可靠性与成本仍是公认硬件短板，重度依赖力控与触觉的任务硬件仍可能是瓶颈。

    双层架构：规划与控制分离

    • 长程规划（0.1–1Hz）："做什么"——把"打扫厨房"拆解为子目标序列，需理解环境语义、推理任务依赖。通用 VLM 已具备不错的具身思考能力：Gemini Robotics-ER 1.5 专门优化具身思考，15 个学术基准平均 62.8%（超 GPT-4o 的 60.6%），支持空间理解、时序推理（"推倒杯子会怎样"）、任务编排。
    • VLA 控制（1–10Hz）："怎么做"——Vision-Language-Action 模型根据画面和指令实时输出控制信号。结构上这就是语音场景"快慢思考"的翻版，但注意切分维度不同：这里拆的是"谋划全局/实时执行"，不是 MPS 的"思考/表达"。

    实时性矛盾被下推到 VLA 层靠动作分块（Action Chunking）摊薄：VLA 单次推理只有 1–10Hz，传统控制要求 50–1000Hz（差两个数量级）。分块让模型一次推理生成未来一段动作序列（π₀ 典型配置：0.5–1 秒的动作块、50Hz 下 25–50 个动作），控制线程高频回放、后台异步生成下一批——像视频缓冲，推理时间小于执行时间就不卡顿。权衡：块越长越平滑，但对突发变化（物体被挪走）越迟钝——拿反应性换平滑性。

    VLA 的两条动作表示路线

    模型 路线 要点
    RT-2 离散动作 token 在大规模 VLM 上微调，连续动作离散化为 token 自回归输出，借预训练泛化能力零样本迁移新物体/新指令；Google 内部
    OpenVLA 离散动作 token 开源（Llama 2 骨干 + DINOv2/SigLIP 视觉编码器）；先在 Open X-Embodiment（20 多种机器人平台的演示）预训练再按平台微调；原版单步自回归约 6Hz，动作卡顿是主要短板
    π₀ 连续轨迹生成 flow matching（与扩散模型同源）从噪声多步去噪，直接生成平滑连续动作轨迹，天然配合动作分块，灵巧操作流畅度更优

    训练方式：当前 VLA 控制层主要通过模仿学习（行为克隆）——从人类演示学"看到什么就做什么"；强化学习是其上的补充，但 RL 训练的 VLA 往往泛化不足（SimpleVLA-RL 在 LIBERO 上的高分是每任务分别 RL 训练的，非统一模型零样本泛化）。机器人场景当前的主要矛盾已从实时性转移到训练与泛化——数据怎么来、如何跨任务跨平台迁移。

    Sim2Real：从仿真到现实

    仿真无法完全还原真实物理/视觉/硬件特性。Domain Randomization：训练时把关键参数大范围随机打乱（摩擦系数、物体质量、光照、摄像头位置、控制延迟、噪声水平……），逼策略学出对各种变化都稳的通用表征——真实世界只是训练分布中的"一个样本"。成功案例：OpenAI Dactyl（手内方块重定向，后续用自动域随机化 ADR 单手解魔方）、ETH ANYmal（四足机器人复杂野外地形行走）。落地时两个工程环节：

    1. 随机化范围标定：先从真实环境实测标定参数分布，真机明显掉点再逐步扩大范围——太窄盖不住真实变化，太宽学出"什么都能应付但什么都不精"的次优策略。
    2. 视觉对齐：精确校准仿真与真实的摄像头位姿；把真实拍摄的背景随机替换进仿真渲染（greenscreen）。

    零样本 RGB Sim2Real 抓取的五步流程（LeRobot + ManiSkill → 真实 SO100 机械臂，纯 RGB 不依赖深度/力传感器）：环境对齐 → 背景替换 → 域随机化（颜色/纹理/光照/FOV）→ PPO 大规模并行仿真训练（成功率 >90%，单张 4090 约 1 小时）→ 真机零样本部署。成功三要素缺一不可：精确环境对齐 + 视觉域随机化 + 物理参数随机化。局限：真实物体形状/大小/材质超出训练分布时成功率显著下降。

    经验与常见坑

    • 延迟账要算排队：空载延迟好看没用，利用率 80% 时实际延迟是空载的 5 倍。
    • VAD 的静音阈值必然两头不讨好——轮内停顿常比轮间间隔长，根治要么语义级轮次判断、要么全双工取消轮次。
    • 训练标签的"上帝视角"是隐蔽坑：标注时用到决策点之后的音频，线上模型却看不到未来——很多"模型不行"其实是"标签不行"。
    • 端到端 vs 级联的准确率优劣可依任务性质事先判定（答案靠语义还是靠非语言线索），别简单归因于"端到端更先进"。
    • t-SNE/UMAP 式的"显微镜 vs 法官"原则在评估各处通用：能看局部，别过度解读全局。
    • Computer Use 的感知方案没有银弹：结构化索引、SoM、坐标预测、AOI 部件都要顺着模型的脾气来配。
    • 机器人域随机化范围别拍脑袋：实测标定起步、真机掉点再扩。
