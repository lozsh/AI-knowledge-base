阶段 1：领域逻辑

发送：

实施 PLAN.md 的阶段 1，只创建：
- mealcraft/__init__.py
- mealcraft/scaling.py
- mealcraft/recipes.py

严格实现 tests/test_scaling.py 和 tests/test_recipes.py 已定义的公开接口。

要求：
- 使用 Fraction 或等价的精确方法，避免浮点噪声；
- 数字显示尽量简洁，整数不带 .0；
- 不可解析文字保持原样；
- 数据错误只包含安全摘要，不泄露绝对路径或 Traceback；
- load_recipes 返回稳定顺序并拒绝重复 id；
- scaled_recipe 深复制，不改输入对象；
- 不修改 tests、scripts、REQUIREMENTS.md 和 data；
- 完成后运行 13 个 unittest，然后停下来汇报。

出现权限确认时，只批准创建三个领域文件和运行 unittest。拒绝安装包、修改固定菜谱或放宽断言。

预期测试结果结尾为：

Ran 13 tests

OK

测试数量如果不是 13，先检查是否从项目根目录运行，以及固定测试是否被改动。

在 Claude Code 外再运行同一命令。这个第二次运行用于区分“Claude 说跑过”与磁盘上的当前代码确实通过。

阶段 2：本地 HTTP API

发送：

实施 PLAN.md 的阶段 2，只新增 app.py。

必须满足 REQUIREMENTS.md 的固定路由，并支持：
python app.py --host 127.0.0.1 --port 8000

约束：
- 只允许 host 为 127.0.0.1；
- 使用 Python 标准库 HTTP 服务器；
- 查询参数错误返回 HTTP 400 和 error=invalid_request；
- 未知菜谱返回 HTTP 404 和 error=not_found；
- 数据损坏返回结构化 JSON，不向浏览器发送 Traceback；
- 暂时不要创建前端和 README；
- 不修改固定测试、检查器、需求和菜谱。

完成后运行 unittest，并实际启动服务器验证 /api/recipes 和一条带 servings 的详情请求，然后停下来。

如果 Claude 要启动服务器，确认绑定地址是 127.0.0.1 而不是 0.0.0.0。服务启动后，在另一个终端执行真实请求。

macOS、Linux 或 WSL2：

python3 -c "import json,urllib.request; data=json.load(urllib.request.urlopen('http://127.0.0.1:8000/api/recipes')); assert len(data)==6; print('PASS: API 返回 6 份菜谱')"

Windows PowerShell：

py -c "import json,urllib.request; data=json.load(urllib.request.urlopen('http://127.0.0.1:8000/api/recipes')); assert len(data)==6; print('PASS: API 返回 6 份菜谱')"

预期打印 PASS: API 返回 6 份菜谱。停止服务器后再继续；如果端口被占用，临时改用 --port 8010，并同步修改检查 URL。

阶段 3：浏览器界面与 README

发送：

实施 PLAN.md 的阶段 3，新增：
- static/index.html
- static/app.js
- static/style.css
- README.md

页面必须从真实 API 读取数据，完成菜系、标签、最长时间的交集筛选；点击卡片显示详情；份数下拉框为 1～6，并使用 API 返回的 display_amount。

只做本地个人菜谱界面：不使用框架、CDN、图片、外部字体、账号、数据库或遥测。README 必须包含四类平台的测试、发布检查、启动和停止方式。不要修改固定验收文件和菜谱。

完成后运行 unittest 和 scripts/verify_release.py，再停下来汇报真实命令、退出状态和关键结果。

verify_release.py 会选择一个临时本地端口，启动真实 app.py，请求列表、组合筛选、份数换算、404、400 和首页，最后比较 6 份菜谱的 SHA-256。通过时应看到：

PASS: MealCraft 1.0 发布检查通过，源菜谱哈希未变化

如果系统询问是否允许 Python 监听本机端口，只允许当前 MealCraft 的 127.0.0.1 临时测试。不要为此开放公网地址或长期防火墙规则。

第 1 层：单元测试

macOS、Linux 或 WSL2：

py -m unittest discover -s tests -v

第 3 层：浏览器人工操作

启动：

macOS、Linux 或 WSL2：

python3 app.py --host 127.0.0.1 --port 8000

Windows PowerShell：

py app.py --host 127.0.0.1 --port 8000

浏览器打开 http://127.0.0.1:8000/，逐项检查：

  1. 初始显示 6 张菜谱卡片；
  2. 菜系选“家常菜”只剩“番茄炒蛋”和“清蒸鱼片”；
  3. 清除菜系，标签选“快手”、最长时间选“20 分钟”，只剩两份菜谱；
  4. 打开“香菇拌面”，从 2 人份切到 4 人份，生抽从 1/2 勺 变为 1 勺；
  5. 打开“番茄炒蛋”，盐在任意份数下仍显示“适量”；
  6. 刷新页面后功能仍正常，终端没有 Traceback。

按 Ctrl+C 停止服务器。人工检查发现问题时，记录“选择了什么、预期什么、实际什么”，再交给 Claude 复现；不要只说“页面不对”。

审查 Diff 与固定文件

在 Claude Code 中输入 /diff，再在外部终端运行：

git status --short

  • API Key、账号、个人绝对路径；
  • 计划外的数据库、部署或外部服务代码。

关键排错

测试一开始就通过：确认你没有误在 mealcraft-reference 或旧项目中运行；主项目在复制实现验收包后、编写代码前应因模块缺失而失败。

Claude 修改固定测试：拒绝该修改并用 Git Diff 恢复到课程复制后的内容。测试与需求真的冲突时应先停止并核对，不应由被测实现自行放宽标准。

发布检查提示连接失败：先手工运行 app.py，确认没有语法错误、绑定 127.0.0.1 且接受 --host、--port。安全软件拦截时只允许本机回环测试。

unittest 通过但网页没有菜谱：这是为什么还要真实 HTTP 和浏览器验收。打开终端日志及浏览器开发者工具的 Network/Console，记录失败 URL 和状态码，再让 Claude 复现。

源 JSON 哈希变化：停止提交，查看 git diff -- data/recipes。换算必须基于深复制或新结构，不能把 display_amount 写回源文件。

MealCraft 1.0 的完成证据不是一段总结，而是固定的 13 个测试、真实服务器检查、源数据哈希和六项人工操作。分阶段停下来验证，让 Claude 的编码能力服务于已经确认的个人项目范围。

补齐输入与浏览器边界验收

参考快照已补齐以下边界，生成自己的实现时也应满足：

  • JSON 的 true 不能作为整数份数或分钟数；食材名不能只含空白。
  • 菜谱文件损坏属于服务端 500 recipe_data_error；非法参数为 400 invalid_request，不存在的菜谱为 404，分别验收。
  • 菜谱内容只按文本显示。把测试菜谱名设为 <img src=x onerror=alert(1)>，页面应显示原样文字，不创建图片或执行脚本。
  • API 错误或服务器停止时显示可见错误，并清空旧结果；恢复服务后重新筛选可重试。
  • 连续改变筛选、快速切换详情时，最终界面对应最后一次选择，较早请求不能覆盖新结果。

复制 implementation-kit 后，在项目根目录运行 python -m unittest discover -s tests -v（macOS/Linux 可用已验证的 python3）。新增 test_revision_boundaries.py 验证输入和 HTTP 边界。浏览器三项仍需亲自操作；单元测试通过不能代替页面验收。

可选自动检查：安装 Node.js 后在合并好的项目根目录运行 node tests/test-browser-boundaries.cjs。它使用最小 DOM 替身检查文本渲染、请求乱序及 HTTP 错误，不代替真实浏览器的布局与交互验收。
