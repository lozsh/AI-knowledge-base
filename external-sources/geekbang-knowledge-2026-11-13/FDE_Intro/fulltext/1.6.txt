这份术语表不需要背诵。开营前先浏览一遍，课程中遇到不熟悉的词，再回来查即可。

每个术语分成两层。「正式定义」尽量说明它通常指什么；「这门课里的理解」则说明它为什么会出现在 FDE 项目里。两层并不互相替代，前者帮助我们使用同一种语言，后者帮助我们把术语落到具体工作中。

这份表只收录训练营中反复使用、容易误解，或者会直接影响作业与客户沟通的术语。案例公司、产品名称和普通开发工具不在这里逐一解释。

FDE 与 To B 交付
术语	正式定义	这门课里的理解
FDE	Forward Deployed Engineer，本课程统一称为前沿部署工程师。FDE 嵌入客户环境，用工程能力解决真实问题并交付可衡量的结果。	进入现场只是起点。真正完整的闭环，还包括把现场认知沉淀回产品，让后续客户更容易被服务。
Delta / Dev	Palantir 对两类工程角色的称呼。Delta 围绕一个客户调动多种能力，Dev 用一种能力服务多个客户。	这组对照用于说明 FDE 与普通产品研发的工作重心不同。术语表保留训练营会使用的 Delta / Dev，不扩展其他内部角色称呼。
To B / B To B	Business to Business，企业向其他企业提供产品或服务的业务模式。	企业项目不仅有使用者，还有决策者、评估者、采购、IT、安全等多方角色。技术正确，不代表项目就能推进。
甲方 / 乙方	企业项目中，甲方通常指采购或使用产品与服务的客户，乙方通常指提供产品、方案或交付服务的供应商。	甲乙方只是合同关系中的位置，不代表谁更专业。FDE 需要同时理解客户目标和供应商边界。
售前 / SA / 实施	售前帮助销售识别需求并推动签约；解决方案架构师（Solution Architect，SA）负责方案与架构设计；实施负责把已经约定的产品或方案部署到客户环境。	三类角色都可能与 FDE 协作，也可能在实际岗位中重叠。FDE 的区别在于还要进入现场编写生产代码，并对业务结果与产品认知回流负责。
干系人	能影响项目、受到项目影响，或掌握项目所需资源与信息的个人或群体。	不能只访谈职位最高的人。需要判断谁有业务目标、谁掌握数据、谁承担风险、谁拥有否决权。
POC	Proof of Concept，概念验证，用较小范围验证某个技术或方案是否可行。	POC 只回答“这条路是否可能走通”，不能直接证明系统已经达到生产要求，更不能代替业务效果验收。
试点	在受控的用户、数据、时间或业务范围内运行一套接近正式使用的方案。	POC 主要验证技术可行性，试点则进一步验证系统进入真实工作流后是否有效、稳定，组织是否愿意采用。
MVP	Minimum Viable Product，最小可行产品，用最小范围验证核心价值假设。	MVP 要形成一个能够进入真实工作流、产生证据并支持下一轮判断的最小闭环，不能只把 demo 的功能删减一遍。
SOW	Statement of Work，工作说明书，用来约定项目范围、交付物、双方责任、时间计划和验收方式。	SOW 要提前说清楚“做什么、做到什么程度、用什么证据验收、哪些事情不在范围内”，避免双方到了验收阶段再解释边界。
里程碑与里程碑付款	里程碑是项目中可以确认的阶段性成果；里程碑付款是达到约定成果并完成确认后触发的付款安排。	里程碑不能只写日期，还需要绑定交付物、通过条件和确认人，否则付款节点仍然会产生争议。
SOP	Standard Operating Procedure，标准作业程序，用来规定一项重复工作按照什么步骤完成。	FDE 需要先理解客户真实 SOP，再判断哪些环节应该保留、改变或交给 AI，不能只把现有流程原样自动化。
人天	以一个人工作一天作为工作量或报价单位。	人天适合估算投入，但不能直接代表客户价值。FDE 如果只靠增加人天获得收入，很容易失去沉淀产品能力的动力。
变更单 / 需求蔓延	变更单是对原范围、成本、排期或验收标准作出的正式修改；需求蔓延是新增要求不断进入项目，却没有同步调整这些约束。	客户提出新要求并不等于团队必须免费完成。需要先判断它属于原范围内澄清，还是需要重新确认的项目变更。
SLA	Service Level Agreement，服务级别协议，用来约定可用性、响应时间、恢复时间等服务标准。	SLA 管的是服务质量，不直接等于业务结果。模型供应商或外部系统达不到 SLA，也会成为 FDE 项目的供应商风险。
验收	依据事先约定的范围、指标和证据，判断交付是否达到要求。	训练营里的验收同时看技术结果和交付结果：系统是否正确运行，客户是否基于证据确认项目价值。
回款 / 应收账款	回款是客户按照合同支付款项；应收账款是已经形成收款权利、但尚未收到的款项。	项目完成技术工作并不代表已经回款。范围、验收证据和付款条件没有提前对齐，都会让应收账款长期挂账。
客户成功 / CSM	客户成功是帮助客户持续获得预期价值的一组工作与职责；CSM 是 Customer Success Manager，客户成功经理。	FDE 会与客户成功团队协作，也会关注长期业务结果，但 FDE 不等同于客户成功岗位，更不以续约本身代替价值判断。
续约 / 增购 / NRR	续约是客户继续购买原服务，增购是扩大产品、席位或服务范围。NRR 是 Net Revenue Retention，净收入留存率，用来衡量同一批客户在流失、降购和增购之后保留下来的收入。	这些指标反映客户经营结果，但不能代替对单个 FDE 项目的业务价值判断。
SaaS / 私有化 / 混合部署	SaaS 由供应商统一托管并通过网络提供；私有化部署运行在客户控制的环境中；混合部署把两种方式组合使用。	部署形态会改变数据边界、升级方式、运维责任和模型选择。不能只把它看成安装位置不同。
项目定义与交付方法
术语	正式定义	这门课里的理解
北极星指标	能够集中反映一项业务是否持续创造核心价值的关键指标。	课程要求它同时满足三个条件：与商业价值强相关、客户能够通过自身行动影响、能够被继续拆解和归因。选场景、做验收和谈结果付费，要尽量使用同一把尺子。
基线	在方案实施前，用统一口径记录的比较起点。	只写“上线前的数据”还不够，需要固定对象、时间窗、计算方法和数据来源，后续才能判断变化是否真实发生。
Demo-driven / demo 内循环	用可以运行的系统持续获得真实反馈，并据此迭代产品和方案的开发方式。	demo 不是每周汇报。它要端到端跑通一条窄链路，把客户的模糊意见变成具体工单、责任人和下一步行动。
MVA	Minimum Viable Architecture，最小可行架构，用最少工程投入验证架构中的关键风险。	MVP 主要验证价值，MVA 先验证“承重柱”：真实数据和长尾问题、数据与工具能否接通，以及真实规模下的延迟、并发、成本和失败兜底。
gap	现有产品或方案能力与客户真实需求之间的差距。	先判断 gap 是通用还是客户特有、阻塞还是增强，再决定做进平台、放进隔离层、进入产品需求池，还是明确延后。
负债区 / 隔离区 / 资产区	对客户项目代码按长期复用和维护方式划分的三个区域。负债区把特殊逻辑写死在客户实例；隔离区把特殊逻辑放入统一代码库并通过开关或配置隔离；资产区把需求抽象成通用平台能力。	代码写在哪里，决定它最终是长期负债还是可复用资产。既不要把特殊逻辑留在客户实例里，也不要把伪装成通用需求的特殊逻辑硬塞进平台。
内环 / 外环	内环围绕单个客户发现问题、构建方案并交付结果；外环把多个现场的共性认知沉淀为可复用的产品、工具和方法。	内环保证这次项目做成，外环降低下一个项目的边际成本。只做内环，团队容易陷入持续定制；只有外环，没有现场证据，也容易闭门造车。
平台提交 / 前后方握手	平台提交是把现场学习结构化地转交给产品或平台团队，形成有负责人、有评审节奏的路线图条目；前后方握手是双方共同管理这些提交的固定协作机制。	一份有效的平台提交要写清现象、根因、建议和受益面，不能只转发客户原话。AI 可以缩短交接链路，但不能省掉产品化决策。
第二客户时间 / 单位经济 / 平台提交率 / 产品化速度	第二客户时间衡量同类模式第二次交付比第一次快多少。单位经济观察单次交付的收入与成本结构。平台提交率衡量现场学习进入正式产品路线图的比例。产品化速度衡量共性需求转成可复用能力的速度。	这组指标用来检查外环是否真的转动。项目数量增加，不代表产生了复利；下一次交付更快、更轻，现场学习持续进入平台，才说明沉淀正在发生。
私有知识	在具体项目中形成、与客户环境和决策过程密切相关，尚未公开或结构化的知识。	被否决的方案、客户的真实约束和现场判断都可能成为私有知识。FDE 要先处理保密边界，再把可复用部分沉淀为评估集、模板、规则或产品能力。
服务陷阱	服务收入增长依赖人员和定制工作近似同比增长，单个项目经验又难以复用的经营状态。	FDE 不是拒绝服务，而是通过外环沉淀，避免团队只能靠增加人天服务更多客户。
双向筛选	FDE 模式需要同时判断团队是否适合深入现场，也判断客户是否具备支持这种工作方式的组织条件。	不能只问“我们能不能做”。还要检查客户是否有关键负责人、数据与权限、及时反馈，以及是否愿意为探索阶段投入资源。
一纵、一横、一软	一纵指在某个技术或业务方向上的深度，一横指跨技术、产品与业务的广度，一软指现场沟通、推动和判断能力。	这是课程用来理解 FDE 能力结构的简化模型。AI 时代还需要补上一项：把业务世界建模为人和系统都能使用的 Ontology。
业务语义与数据
术语	正式定义	这门课里的理解
Ontology	对一个领域中的实体、属性、关系、动作和约束进行明确表达的形式化模型，中文通常译为本体。	把客户业务里的名词和动词建成一套人和系统都能理解、能够继续落进数据与程序的业务模型。
Object / Link / Action	Object 表示业务对象，Link 表示对象之间的关系，Action 表示可以对对象执行的业务动作。	这三个基本元素把“会员与订单是什么、它们如何关联、系统允许做什么”放进同一套业务模型，让 Agent 不只会回答，还能在明确边界内行动。
业务实体	业务世界中需要被识别、记录和处理的对象，例如会员、订单、门店和优惠券。	先把对象及其关系说清楚，后面才能统一数据、定义指标，并让 Agent 在正确的业务边界里行动。
实体解析	判断多条记录是否代表同一个现实对象，并进行关联、合并或区分的过程。	新旧系统中的两个会员 ID 可能属于同一个人。实体解析要给出可以复现的匹配规则，而不是凭经验手工合并。
主数据	在多个系统之间作为核心业务对象权威记录的数据，例如统一的客户、商品或组织信息。	主数据不是把所有字段堆进一张大表，而是先确定权威来源、唯一标识、冲突处理和更新责任。
数据口径	对一个字段或指标的业务含义、计算范围和使用边界作出的明确约定。	“会员数”“复购率”都不能只写一个名称，需要继续说明分子、分母、时间窗、去重方式和剔除规则。
语义层	位于底层数据和上层应用之间，对业务概念、指标、维度及其关系进行统一定义的一层。	语义层让报表、程序和 Agent 使用同一套业务含义，避免每个系统各自猜测“复购率”或“活跃会员”是什么意思。
数据血缘	描述数据从哪里来、经过哪些处理、最后被哪些结果使用的关系。	当客户质疑一个数字时，需要能够从结论追溯到计算逻辑、源表和原始字段，而不是只给出最终结果。
数据脱敏	通过掩码、替换、泛化等方式降低数据中的身份识别或敏感信息暴露，同时保留必要的使用价值。	脱敏后还要验证权限边界和模型效果，不能因为数据“看起来不像真的”，就默认它已经安全或仍然可用。
遗留系统	已经长期运行、难以直接替换，但仍承载关键数据、接口或流程的旧系统。	接入遗留系统不是顺手配一个接口。文档过时、数据不一致、网络隔离和迁移回退，都要作为正式项目工作管理。
MCP	Model Context Protocol，一种让 AI 应用以较统一的方式连接外部数据源和工具的协议。	在课程沙盘里，MCP 是 Agent 与业务能力之间的一层适配。真正进入客户环境时，还要补齐鉴权、权限、数据边界、日志和失败处理。
AI 工程与生产治理
术语	正式定义	这门课里的理解
LLM API	通过程序接口调用大语言模型能力的方式。	入营前只要求能够完成一次基本调用。课程重点不在背模型接口，而在把模型能力接入可验证、可治理的生产链路。
Agent	能够基于目标和上下文进行判断，并调用工具或执行动作的 AI 系统。	W1 在标准样例上验证、W5 在青禾客户场景验收一条完整行为链：接收自然语言业务目标，结合上下文、本体和指标语义判断下一步，在许可范围内选择工具，再根据工具结果给出可以追溯的结论、理由或证据。Agent 不只是能够对话，也不是按照写死流程调用接口。
工具调用	模型按照约定的接口请求外部程序执行查询或动作。	查询会员和给会员发券是两类风险完全不同的工具调用。会调接口只是第一步，还需要处理鉴权、白名单、确认、幂等和失败。
Workflow	按照预先定义的步骤、条件和分支执行任务的工作流。	确定性强的环节不必全部交给模型判断。固定工作流可以成为 Agent 的工具或护栏，但不能替代 Agent 对业务目标的理解、判断和工具选择。
RAG	Retrieval-Augmented Generation，检索增强生成，在模型生成答案前，从外部知识源检索相关内容并加入上下文。	RAG 是一种常见实现方式，不是所有企业 AI 问题的默认答案。课程不会把向量库选型和 RAG 基础作为主线。
评估驱动开发	在实现和迭代系统的同时，先定义什么叫“好”，并用可重复的评估持续约束每次修改。	评估不是开发完成后的最后一道验收。模型、提示词、数据或架构一变，都要重新跑评估，发现退化就不能直接发布。
评估集	用一组有代表性的输入、预期结果和判定标准，衡量系统表现的数据集合。	评估集相当于 AI 系统的测试样本，需要覆盖正常情况、异常情况和安全对抗情况，并随着真实问题持续补充。
黄金集 / 异常场景集 / 安全对抗集	黄金集覆盖核心业务及其预期结果；异常场景集覆盖长尾、缺失和失败情况；安全对抗集覆盖越权、注入和其他攻击性输入。	三类集合分别守住效果、韧性和安全。安全失败不能被其他样本的平均分掩盖，必要时应直接阻断发布。
评测 Harness / Eval Harness	能够重复运行评估集、调用被测系统、计算结果并记录版本差异的评测执行框架。	评估集是“拿什么测”，Harness 是“怎样反复测”。只有两者结合，修改模型、提示词或架构之后，才能知道系统是进步还是退化。
Agent Harness	围绕模型组织上下文、工具执行、任务状态、恢复和约束的运行机制。	FDE 可以调整上下文组织、工具结果和执行策略，并用评估证明变化；不要求重新开发通用框架。
Agent 效果调优	为实际模型、客户业态和业务目标改进 Agent 行为的工程工作。	从 W1 模型基线开始，持续做失败归因、实际修改、前后对照、保留集验证与回归，和数据清洗、系统集成、安全、评估并列。
棘轮原则	一项能力达到新的可靠水平后，就把这个水平设为后续版本不能跌破的下限。	真实故障和客户反馈要补回评估集。修复过的问题再次出现，属于明确的回归。
护栏	对输入、输出和系统动作设置约束、检测与拦截机制，以降低越权、注入、错误内容和高风险操作造成的影响。	护栏不能保证系统永远不犯错。输入侧要防注入与越界，输出侧要做事实核验与风险拦截，动作侧还要限制权限并保留人工确认。
最小权限 / 动作白名单	最小权限要求主体只拥有完成任务所必需的权限；动作白名单只允许执行事先明确批准的操作。	Agent 能读取数据，不代表它应该修改数据。权限要按数据、工具、动作和环境拆开，并为高风险动作设置更严格的确认条件。
审计日志	为追溯、复核与问责而保留的系统访问、决策和操作记录。	至少要能回答谁在什么时间触发了什么请求，系统依据什么作出判断，调用了什么工具，改动前后是什么状态，以及能否撤销。
可观测性	通过日志、指标和调用轨迹了解系统内部状态，并定位问题的能力。	AI 系统出错时，不能只看到最终一句错误答案，还需要知道使用了什么上下文、调用了哪个工具、在哪一步开始偏离。
Trace	一次请求在多个模型、程序和工具之间流转时形成的完整调用轨迹。	Trace 要能回答谁在什么时间、用什么输入、调用了什么能力、得到什么结果，为调试、审计和责任判断提供证据。
HITL	Human in the Loop，人参与系统的关键判断或执行环节。	风险越高的动作，越不能让 Agent 自动完成。是否需要人工确认，要根据错误成本、权限范围和可逆性分层设计。
幂等	同一个请求重复执行一次或多次，产生的最终业务效果与执行一次相同。	网络重试不能导致一张优惠券被发放多次。涉及外部动作时，幂等是 Agent 能否进入生产环境的基本要求。
生产就绪六维度	课程用来判断 AI 系统能否进入生产环境的六项检查：评估过线、真实规模下的性能与成本、安全与权限、全链路留痕与决策可追溯、应急与回滚预案、运营与交接流程。	上生产需要逐项拿出证据，不能只在某个时刻按下开关。六项中任何一项缺失，都可能让一个好用的 demo 无法成为企业可用的系统。
硬化阶段	demo 通过后、正式上线前，对系统进行边界处理、监控、压测、降级和回滚加固的阶段。	这段工作不增加显眼的新功能，却决定系统遇到真实规模和异常情况时能不能扛住，因此不能为了赶上线而省略。
模型网关	对多个模型服务提供统一接入、路由、鉴权、配额、日志和策略控制的基础设施。	它帮助项目管理模型切换、供应商风险和使用成本，但网关本身不能代替应用层的权限、评估和安全设计。
成本工程	把系统成本当作可观测、可预算和可优化的工程指标，持续管理其构成与变化。	AI 项目需要核算真实规模下的 token、模型调用、检索、存储和人工复核成本，再通过模型分层、缓存、路由和流程设计优化，而不是上线后才看账单。
灰度发布	先让一小部分用户、流量或场景使用新版本，观察结果后再逐步扩大范围。	AI 系统的不确定性较高，不能从 demo 直接全量上线。灰度需要同时定义观察指标、停止条件和扩大范围的依据。
回滚	新版本出现问题时，将系统恢复到之前稳定状态的机制。	回滚不能只写在方案里，需要提前准备版本、数据和操作路径，并验证出现异常时是否真的能够恢复。
效果衡量与商业结果
术语	正式定义	这门课里的理解
ROI	Return on Investment，投资回报率，常用收益减去成本后再除以成本来衡量投入产出。	公式只是起点。项目还要约定收益和成本各包含什么、使用哪个时间窗、数据来自哪里，以及哪些变化可以归因于本次交付。
GMV	Gross Merchandise Value，商品交易总额，表示一定时间内成交商品的总金额。	GMV 不等同于收入或利润。用它衡量项目时，还要说明退款、取消、口径周期以及系统实际影响的是交易额中的哪一部分。
归因分析	判断一个结果的变化由哪些因素造成，以及各因素贡献多少的分析过程。	业务指标上涨，不等于全是系统的功劳。要区分系统作用、客户配合、外部变化和随机波动，并提前约定双方认可的归因方法。
对照组 / 差分分析	对照组是不接受某项干预、用于比较的群体；差分分析通过比较干预组与对照组在干预前后的变化，减少共同趋势带来的误判。	这是一种常用的效果验证办法，但前提是两组具有可比性，干预边界清楚，期间没有被其他重大变化污染。
OLA	Outcome-Level Agreement，本课程所说的结果级协议，用书面方式约定交付结果、衡量方法、衡量责任和审核节奏。	OLA 不是通行的行业标准缩写，而是课程用来把结果责任落到合同和协作过程中的工具。它既要写供应商承诺，也要写客户需要提供的数据、权限、反馈和流程配合。
RaaS	Result as a Service，按结果付费的服务模式。	它不是一句“没效果就不付费”。要先用基线、归因和 OLA 说清楚结果怎么计算、双方各承担什么责任，以及基础费用与结果分成如何组合。
训练营工程与教学工具
术语	正式定义	这门课里的理解
Starter Repo	课程提供的标准 Agent 产品底座、客户交付仓库和配套工具。	它不是一个等待学员从头填满的空项目。12 周都在同一个客户交付仓库上持续演进，标准产品底座默认不直接修改，客户化代码、连接器、评估和产品补丁需要保持清楚的责任边界。
标准 Agent 产品底座	具备明确业务能力、执行机制和扩展接口的可运行 Agent 产品。	W1 已能在独立样例上澄清条件、筛选会员、比较消费、给出建议和证据，并通过独立标签 API 演示受控动作。青禾的数据、语义和系统需要学员后续适配。
客户交付扩展层	围绕具体客户的数据、业务语义、系统接口和生产约束进行开发的工程层。	这是学员主要写代码的区域，包括数据适配、本体与指标语义、Agent 业务工具、连接器、权限、评估和上线配置。客户专属逻辑不能直接写进标准产品核心。
产品扩展或补丁	标准产品现有扩展点无法承接客户需求时，对产品通用能力作出的补充。	先证明问题不能只在客户层解决，再说明它会影响哪些客户、是否值得回到产品主线。不能为了展示开发量而重复实现底座已有能力，也不能为了满足作业要求强行修改产品核心。
Delivery Manifest / 交付清单	记录本周新增代码、所属责任层、依赖版本和测试证据的结构化清单。	不同技术栈可以采用不同的内部目录，但需要通过交付清单说明哪些属于标准产品、客户化开发、连接器、评估或产品改进。
产出物契约	对文件位置、字段、类型、统计口径和跨周引用方式作出的明确约定。	课程不按框架或代码目录判分，而是检查交付结果是否符合契约，因此不同技术栈可以完成同一项作业。
Checker	对可确定验证的产出物进行自动检查的工具。	Checker 检查格式、字段、关键结果、权限用例和回滚结果等内容；架构取舍和沟通判断仍由助教与答辩评估。
Checkpoint	在一个阶段结束后提供的标准中间状态或参考产出物。	某一周掉队时，可以从 checkpoint 继续后面的项目。它不会覆盖个人实现，也不会提前透露未来剧情。
Mock 服务	按照固定接口模拟真实外部系统行为的服务。	W1 提供有状态的样例标签 Mock，W8 提供青禾发券、标签 Mock API，均通过真实 HTTP 调用。它只覆盖课程任务需要的最小能力，不是完整 CRM 或营销平台。
Rubric	对作品从哪些维度、按照什么标准进行评价的评分规则。	Rubric 负责判断架构、沟通和交付质量；能够完全确定的格式与结果交给 Checker。学员提交前可以据此自查，而不是等答辩时才知道标准。
技术门槛 / 交付门槛	技术门槛判断系统能否正确、安全、稳定地工作；交付门槛判断需求、证据、沟通、验收和责任边界是否成立。	两道门槛不能互相抵消。W1 标准样例与 W5 客户任务中，Agent 的理解、判断、工具选择和结果解释也属于技术门槛。代码写得再好，如果只有固定 SQL、固定规则、固定流程或按钮直连 API，仍然不能通过 Agent 相关门槛；同样，如果没有客户认可的价值证据，也不算完成一次 FDE 交付。
三档尺度	课程对同一能力设置的三个递进层级：在演示环境中跑通、达到生产可用要求、能够迁移到陌生客户环境。	第一档看“能不能跑”，第二档补错误处理、监控与回滚，第三档看面对新数据、新系统和新干系人时能否重新完成闭环。
AI 模拟客户系统	按角色、信息边界和事件规则模拟客户反馈与项目变化的训练系统。	它是课程方提供的客户 Agent，不是学员要交付的业务 Agent，也不负责给代码判分。角色只透露自己应当知道的信息，关键剧情由确定性规则控制，用来训练访谈、澄清和项目判断。
使用时的一个提醒

术语的目的，是让我们更准确地讨论问题，而不是让一个普通问题听起来更复杂。如果一个术语无法帮助我们说明对象、规则、证据或责任边界，就应该回到具体业务场景，来得到更充分的理解。
