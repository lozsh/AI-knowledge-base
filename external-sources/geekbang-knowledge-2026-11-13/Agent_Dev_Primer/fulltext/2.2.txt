这篇文章写于 2023 年，距今三年，里面那个「三重境界」的分层框架今天依然站得住。有一点提前说明：文中的第二重「API 调用者」，在 2023 年是走在前列的位置，但放到今天，会调 API 只是起点。这门课带你在这一层再往前走——把一次调用，变成有记忆、有工具、有知识、会自己规划的 Agent 服务。

从 ChatGPT 的火爆开始，AI 这个已经存在了好几十年的东西终于一步一步地走进了普通程序员的日常工作。不同的程序员涉及到 AI 的程度不同，这里我将程序员在工作中使用 AI 分成了三个境界：

作为用户的程序员
作为 API 调用者的程序员
作为模型调教者的程序员
用户

作为用户的程序员，应该是最常见的。程序员本身就是一个对新技术比较敏感的群体，所以，像 ChatGPT 这样的新应用，很多人都会在第一时间尝试使用。程序员会如何使用 ChatGPT 呢？

最初接触时，我们会和其他人一样，只把 ChatGPT 当做一个聊天机器人。但是，作为一个专业人士，我们应该很快就会了解到提示词的概念，也应该应该知道提示词更好的写法。

一个好的提示词要符合下面的公式：

提示词=定义角色+背景信息+任务目标+输出要求

作为 ChatGPT 的技术基础，大语言模型（Large Language Model，简称 LLM）做的主要工作是基于上下文信息推断下一段要输出的内容，也就是说，信息越充分，推断出来的内容越精准，反之，则内容越通用。所以，当我们给 ChatGPT 足够的信息，它就会越来越接近我们希望达到的目标。比如，同样是回答医学问题，如果让 ChatGPT 扮演医生的角色，那么它输出的内容就会与诊断治疗相关，而如果让它扮演医学论文写作者的角色，那么它生成的内容就会更加专业。

事实上，这个公式不仅仅适用于普通用户，作为更高级的玩法，它也是是适用的。比如，许多 AI Agent 也是依赖于写出适当的提示词完成的。

有了对于提示词结构的了解，我们就能更好地利用 ChatGPT 去完成自己的目标，也就是进入到程序员的专业领域。

程序员常见的利用 ChatGPT 的方式有

让 ChatGPT 协助解决问题
利用 ChatGPT 学习相应的知识

原本，搜索引擎在程序员的工作中扮演着重要的角色：

在程序中遇到异常，就扔给搜索引擎
遇到没用过的工具或框架，扔给搜索引擎
一段代码该怎么写，扔给搜索引擎
……

当 ChatGPT 出现后，搜索引擎的很大一部分工作被替代了。如果说扔给搜索引擎之后，我们还要做人工筛选，扔给 ChatGPT 很容易直接得到答案。面对 AI 的应答。我们要做的是，识别真伪。程序员的工作识别真伪最容易，就是代码能否运行成功。当然，在解决一些具体问题上，有比 ChatGPT 更好的选择，比如，Github Copilot[1]，它甚至可以帮我们写代码。

利用 ChatGPT 学习，尤其是经典知识的学习是很方便的。比如，我要学习 Python，我完全可以告诉 ChatGPT 我是一个经验丰富的程序员，让他帮我规划一条学习路线。这样，它就会避免让我从基础知识开始学。我甚至可以有针对性地问一些我希望了解的话题，比如，Python 项目做自动化有哪些选择。几个问题下来，我就会某个领域有一个初步的了解。

至此，AI 算是开始进入了一个程序员的工作环节。不过，作为一个有追求的程序员，我们可以再进一步了。

API 调用者

在大多数人眼里，ChatGPT 是一个聊天机器人的面貌呈现于使人面前，实际上，它是 GPT 这个大语言模型的一个应用，而 GPT 本身就是作为一个基础设施打造的，所以，GPT 的标准用法就是调用 API。

在 ChatGPT 火爆之后，最早的一批出现的 AI 应用就是复刻 ChatGPT，这几乎是调用 API 最简单的方式。用程序员的话说，就是给 API 加上一些聊天历史：GPT API 本身是无状态的，所以，它不会保留对话历史，要想让 GPT 看上去有一些智商，就需要把聊天的历史作为请求的一部分传给 GPT。

随着人们对于 GPT 能力认识的加深，紧接着就出现了一批用好提示词就能做出的应用，比如，让 GPT 总结文本的内容、续写文字、翻译文字等等。这些应用甚至不用考虑聊天历史，只要直接调用 API，传入相应的提示词即可。

在度过了最初的兴奋，人们发现开始意识到 GPT 并非无所不知。一个典型的问题是，它知道的内容是通用的，换言之，它并不了解特定的知识。虽然 GPT 的 API 提供了微调接口，让我们可以训练出属于自己的 GPT，但对于普通人来说，他们并不会直接调用 API，而能够调用 API 接口的程序员，又不会轻易地把数据交给别人。所以，一个常见的解决方案就是引入向量数据库。

具体做法就是，把训练素材做向量化，存储到本地的向量数据库中。调用 API 之前，先在向量数据库中进行检索，再把检索到的内容结合到请求里，让 GPT 能够根据这些内容进行回答，这样一来，回答就是根据训练素材来的，看上去，我们就拥有了专属于自己的 GPT。这种做法在行业里有个名字：RAG（Retrieval-augmented generation，检索增强生成），其核心是通过引入一个信息检索的组件，在不微调模型的情况下，对检索进行增强。这种方案同样催生出一大批的 AI 应用。

基于 LLM 的应用不断产生，一个将所有这些统一起来的框架诞生了，这就是大名鼎鼎的 LangChain。LangChain 提供了 LLM 应用开发所需的组件，以及一些预制好的应用模版。有了 LangChain，今天的开发者要想开发一个应用比起之前容易许多，其中的一些组件已经成为了行业里事实标准，换言之，它为 LLM 应用开发提供了原语（Primitive）。

如果说最初的 AI 应用几乎都是围绕 LLM 本身能力构建的，在基础设施不变的情况下，程序员开始进行了更多的探索，一个叫 AI Agent 的方向开始逐渐兴起。

一些经过验证的能力本身会下沉到作为基础设施的大模型层面，比如，OpenAI 就可以通过让用户上传文件了做 RAG，实现自己的 GPT。当然，作为基础设施，在具体做法上会有所差异，减少了应用与大模型之间的交互，执行效率上会得到提升。

无论是直接调用 LLM 的 API，还是调用 LangChain 封装的原语，程序员们正在积极地推动着 AI 应用的落地，但所有这些能力一定还是在 LLM 本身的能力范围之内做事情，模型的局限也就成了 AI 应用的局限，想要突破这层限制，就需要再进一步，到达模型本身。

模型调教者

大语言模型与的核心在于大。之前，AI 模型之所以很长一段时间无法突破，很大程度上是不够大。如果不是 OpenAI 出手，谁也想不到「大」到一定规模之后，会产生如此神奇的效果。所以，很多大厂也纷纷入局，训练自己的模型。

但「大」也同样意味着其它的问题，首当其冲的就是资金投入。因为模型很大，所以，训练一次的成本就是少则百万，多则千万，还是美元。这也就决定了这不是小玩家可以随便入局的赛道。即便是舍得投入，也并不一定会有良好的效果。

回到程序员的视角，如果不在资金雄厚且舍得投入的公司，训练大模型必然不是普通程序员的选项，一个现实的选项是模型微调。

LLM 自身的一个限制是有很多东西它不知道，前面说过，RAG 在一定程度上解决了这个问题，但这种做法的准确性不太理想，更好的做法就是基于大模型进行微调，也就是把训练素材喂给模型。之所以叫微调，因为相对于模型整体的素材量，我们提供的素材量可以说是微不足道。

但如果微调是基于像 GPT 这样的模型，就意味着我们需要把数据提供给 OpenAI，这也是很多人宁愿用效果差一些的向量数据库，也不愿意去做模型微调的原因。显然，更多的人需要是一个能够在本地微调的大模型。于是，就出现了一个新的赛道：能够在本地微调的大模型。

如果说以 OpenAI 为首的厂商选择了成为 AI 时代的 iOS，提供强大而封闭的模型，那能成为 AI 时代的 Android 显然也是一个不错的选择，虽然能力略逊一筹，但胜在可定制性上。于是，我们看到的不同厂商的选择：

认为自己有能力直接挣钱的，选择走提供服务的路线；
认为开放更重要的，选择了走公开模型的路线。

其实，真正的问题出现在选择了一个大模型之后，并不是那些具体的操作，而是微调本身。想要获得良好的微调效果，就需要准备良好的数据。行业里有句名言「垃圾进，垃圾出（Garbage in Garbage out）」，而准备良好的训练素材是一件费时费力的工作。

如果只是把原始素材直接扔给模型，效果不见得会比 RAG 好。你现在应该明白了，之所以微调能够取得比 RAG 更好地效果，完全是因为大量的精心准备。所以有人调侃「人工智能是有多少人工才有多少智能」。

不过，相比于训练一个模型，微调一个模型的成本要低很多，所以，如果面对特定场景，从工程的角度看，微调一个模型对大多数团队来说，是一条更可行的路。

小结

这里所谓的「三重境界」，只是不同的 AI 使用方法，没有境界之间有优劣之分。一个程序员要完成好自己的工作，三重境界可能会在不同的阶段接触到。

如果说，现阶段有什么能力是最重要的，那就是写好提示词。无论是自己使用 AI，还是要开发 AI 应用，关键点都是提示词。一些眼花缭乱的 AI 应用背后都是提示词。一个学习方式就是打开 LangChain 的源码，找到那些提示词模板，了解不同的功能是如何实现。

虽然软件开发领域常常被人认为是高速发展的，新技术层出不穷，但作为一个在行业里沉浸二十多年的老兵，我认为，真正的需要认真学习和理解的东西并不多，今天的 AI 绝对算一个。每次新技术的出现，就是一个抹平高手与新手之间差距的机会，如今，在 AI 面前，我们又站到了同一起跑线上。
