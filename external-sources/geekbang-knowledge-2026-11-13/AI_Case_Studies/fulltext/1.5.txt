一句话成果：把逐个应用查用量、算配额、写命令的工作拆成可复用流程，一轮调整后，目标节点组日均节点数下降 46%。
案例简介

我新到一家 SaaS 平台公司做 SRE，负责生产 K8s 集群的资源与成本，涉及数千个应用。集群当时“装得满、用得少”：按 request 看装箱率超过 90%，真实 CPU 利用率却只有 10%。我用 Claude Code、Skills、Prometheus MCP 和只读 kubectl 搭了一条资源优化流水线，把取数、筛选、出方案、生成命令分开，再由人评审、灰度执行并验证。AI 负责编排和解释，计算规则放进脚本，生产变更由人控制。

以前怎样调资源

原来要在 Grafana 或命令行里逐个应用查用量，凭经验判断 request、limit 和 HPA 应该怎样调整，再手写 kubectl patch。应用一多，查询、计算和命令之间就很难保持一致。

一次调整上百个应用，一轮要花半天甚至更久。大部分时间消耗在重复查询和整理上，还容易漏查或算错。
筛选条件也经常变：只看某个节点组、排除核心应用，或者只看副本数大于 3 的应用。过去每换一组条件，都要重新整理数据或修改查询和处理逻辑，讨论方案的成本很高。
调整之后缺少系统性回看，配置又会随业务变化重新膨胀；HPA 震荡、卡在最大副本等问题，也只能偶然发现。问题不只是这次能否把 request 调小，而是能否反复跑同一条分析和验证流程。
这一轮优化具体怎样做

准备阶段，我让 Claude Code 参与编写 Skill 和配套脚本。Prometheus MCP 提供监控数据，kubectl 用只读账号检查现状；执行变更时，由人工切换到有权限的账号。这里没有让 Agent 直接取得生产写权限。

第一步，取数与判断分开。

resource-metrics-fetch 按 1 分钟粒度拉取各 Deployment 的数据，包括 P95 与均值用量、request/limit、Pod 数、HPA 阈值、优先级和节点组，输出 CSV。先留下同一批基础数据，后面改条件时不必把慢查询再跑一遍。

第二步，用自然语言缩小候选范围。

我可以提出“只看某节点组、用量低于 request 30% 的非核心应用”等条件，由 k8s-resource-filter 处理筛选。输出是候选清单，还不是执行清单；哪些应用可以进入这一轮，需要结合优先级和业务约束评审。

第三步，按固定规则形成方案。

k8s-resource-adjust 根据资源配额规则和目标利用率计算新的 request、HPA 配置及预期 Pod 数，生成方案表。规则写在脚本里，模型负责解释方案，避免同一份输入因为模型措辞变化而得到不同计算结果。

request 和 HPA 需要一起看。按 CPU 利用率伸缩时，利用率与 CPU request 有关；request 下调，可能改变相同负载下的伸缩行为。因此，“request 下降多少”不能直接等同于“节点就能减少多少”，还要检查副本变化和实际资源需求。

第四步，评审后生成变更和回滚命令。

k8s-resource-generate 为方案生成 kubectl patch，并附对应 rollback 命令。人核对目标集群、命名空间、应用和变更值后，再进入执行阶段。命令能生成，不代表已经具备执行条件。

第五步，分级灰度并回看。

先低用量应用，再普通应用，核心应用最后。每批执行后，AI 根据变更清单检查 Pod 就绪、重启、HPA、request 生效和流量情况，人判断是否继续下一批。变更清单也成为验证范围，避免改完一批后只看整组平均值，漏掉个别应用异常。

结果是什么，口径怎样理解

这一轮调整后，目标节点组日均节点数下降 46%。扣除调整前已有的自然下降趋势后，我估算约九成节点降幅与本轮调整有关。这是趋势扣除后的归因估算，不是有对照组的因果实验，也不能把 46% 直接写成公司总云账单的降幅。

我还做了一次交叉核对：按 request 下调量折算的节点数，与监控实测下降量偏差小于 5%。两种口径接近，支持这一轮调整确实释放了资源；但它不能单独证明所有业务场景下都没有性能影响，仍要以灰度后的应用与流量检查为准。

分析环节从小时级缩到分钟级，是这条流水线带来的直接变化。这里指取数、筛选和形成方案的分析环节，不把尚未明确计入的人工评审、灰度观察和回滚验证时间一并算作“分钟级完成”。

相比一次性降配，更可复用的变化是筛选条件能在对话里调整，基础数据不用重复抓取，方案和命令也能对应起来。它让多看几轮方案变得容易，同时把生产执行留在明确的人工检查点。

这条流水线踩过什么坑

最初把所有工作塞进一个大 Skill，取数慢，筛选和方案却要反复改，每次重跑都浪费时间。拆成取数、筛选、出方案等阶段后，慢的部分只跑一次，需要讨论的部分可以快速重来。阶段之间保留 CSV 和方案表，也更方便复核。

另一条经验是，计算规则必须落到脚本。AI 可以理解筛选意图、组织工具和解释结果，但不能靠对话临时心算配额。为了让别人复现，规则、输入数据和输出方案都需要能对应，而不能只剩下一段“建议下调”的文字。

批量调整还必须有分级灰度和回滚准备。低用量只是进入评审的线索，不是可以无条件降配的证明。遇到业务约束不清、监控样本不足或灰度结果异常时，应由人暂停处理，先补足判断依据，再决定是否继续。

如果你也想做类似的事情，可以从哪里开始？

先选一个节点组，导出一批非核心应用的用量、request/limit、Pod 数和 HPA 配置，只做分析，不急着生成生产变更。把“取数”和“按条件筛选”跑通后，选几项人工核算，确认监控口径和脚本计算一致。

再把资源配额规则写成可复核脚本，输出候选方案、对应 patch 和 rollback。先在测试环境核对命令，再挑少量应用灰度；每批观察什么、什么情况下停止，提前写进执行清单，避免执行到一半才临时讨论。

对我来说，AI 的价值是把原来分散的查询、筛选、计算和命令生成串起来。规则决定方案是否一致，人工评审与灰度验证决定方案能否进入生产，两者缺一不可。
