一句话成果：持续用于真实排查后，长链路问题平均定位时间由个人估算的半天缩至半小时以内；一次陌生扩缩容组件故障，原先预计 2 天定位，实际半天拿到根因。
我做成了什么？

我负责 SaaS 平台稳定性，日常需要轮值 oncall。过去采用“人在 kubectl、Grafana、日志平台等系统之间来回切换”的方式，主要问题是链路长、系统多、跨云厂商没有统一入口，几千个业务应用的配置没人全都熟，一个长链路问题平均要耗半天。

从 2026 年 3 月开始，我尝试用 Claude Code 加 MCP 把 Prometheus、EKS、ClickHouse 日志、Cloudflare、飞书等系统接进来，并把排查 SOP 写成 Skill，让 Agent 代替人去跨系统取证据、对代码、查配置。经过半年多、几十次真实排查的使用，目前的结果是长链路问题平均定位时间缩到 0.5 小时以内，陌生组件的配置分析从人工半天缩到十几分钟；其中仍需人工完成的是根因判断、变更执行和对业务影响的评估。

为什么需要改变？

这项任务由谁完成，多久一次：SRE 轮值 oncall，告警群或业务方随时抛问题，平均每天都有需要跨系统排查的事。

原来的流程：

收到问题后先猜方向，打开 Grafana 翻几张看板，再 kubectl describe / kubectl logs 逐个看 Pod。
去日志平台按时间段捞日志，去 Cloudflare 后台查边缘侧有没有异常。
涉及组件行为的问题，要去翻组件的参数、ConfigMap，再对着官方文档或源码猜它为什么这么做。
有些还要拉业务团队、DBA 一起看代码和数据库。

最麻烦的一步：不是某一个系统难查，而是线索散在五六个系统里，没有统一入口。会有不同的云厂商，会经过 Cloudflare、自研外部网关、应用内部网关、两千多个应用、代理层、公共中间件，再到 HPA / KEDA / Cluster Autoscaler 这些平台组件。每一层都有自己的查询方式和口径，人要在脑子里把它们拼成一条时间线。更要命的是对不熟的组件没办法快速建立认知：一个平时不碰的扩缩容组件出了问题，光是把它的几十个启动参数、默认值和实际配置对一遍，就要半天。

一次具体任务：一个不太熟悉的平台组件故障引发了单个集群 30% 节点异常。按经验估计，要读组件文档、对线上配置、捞故障时段的日志、再看源码确认行为，至少 2 天才能给出可信的根因。

不解决的影响：故障定位慢直接拉长 MTTR；排查依赖少数几个熟悉全链路的老人，新人上 oncall 只能转派；每次排查的思路留在聊天记录里，下次同类问题还是从头来。

具体怎样把 AI 用进去？
先搭好“眼睛”和“规矩”：接入全部系统，再把 SOP 写成 Skill

这一部分做在排查之前，是后面所有案例的基础。

接入层（MCP + CLI），全部用只读账号：

规矩层（CLAUDE.md）：精简且必须的内容，如不同云环境等特定认证，说明基础设施等不同如何做处理，一些内部特定信息如何做关联，Agent 每次对话自动读到，不用人反复交代，也不会连错环境。

SOP 层（Skill）：把排查方法固化成 Skill 和配套脚本，目前 16 个。和问题定位直接相关的有：

故障分层排查定位规范：把一次请求经过的链路分成 L0～L7 七层加观测、变更两条贯穿层，每层用黄金四指标判“请求到我这一层是否正常进、正常出”，排查顺序自上而下二分，目标 5 分钟确定坏在哪一层，15 分钟定位到组件。
巡检流程：一条命令拉出集群 86 项健康快照，和 1 小时前、7 天前对比给红黄绿结论，红黄项自动下钻到节点组 / HPA / Pod / 服务。

护栏：所有 MCP 和账号只读，settings 里禁止写操作，生产集群的变更只允许人审核后经封装预定义的工具做变更操作。Agent 可以放开查，但不能直接改东西。

一次有代表性的排查：陌生扩缩容组件引发集群异常

下面按发生顺序写，每一步都交代输入、操作、输出、人工处理、下一步。

第一步：定影响面。
先准备了告警群里的原始消息和大致时间段，交给 Claude Code，要求它按分层规范先确定“坏在哪一层”。它调用 stability-watch 和 Prometheus MCP，给出的结果是：入口链路 RED 指标正常，异常集中在 L6 容器平台层，节点组的节点数和 Pending Pod 数在故障时段明显偏离 7 天基线。确认了这个方向和告警现象一致，排除了应用发布和边缘侧的嫌疑，于是让它往平台组件下钻。

第二步：把陌生组件的配置一次性读透。
Agent 根据组件名，列出这个组件在线上的全部启动参数、ConfigMap 和相关 CRD 配置，并和官方默认值逐项对比，标出被显式修改过的项。它通过 EKS MCP / kubectl 读到 Deployment 的 args 和 ConfigMap，用十几分钟整理出一张“参数 → 线上值 → 默认值 → 作用”的表。发现其中几个参数的组合和我们对它的预期不一致，出现少量节点异常的时候，自动扩缩容就不工作了。一个组件意外异常时，整个集群失去自愈能力。于是把这几项标记为重点，进入下一步。这一步人工做至少要半天，因为要边查文档边对配置。

第三步：读组件源码，确认它在这组配置下到底会怎么做。
Agent 拉取组件对应版本的源码，围绕上一步标出的参数，找到解析和使用这些参数的代码路径，解释在当前配置组合下的实际行为。并指出了会打出的日志关键字。

第四步：用故障时段的日志反过来验证。
Agent 按上一步给出的日志关键字，捞故障时段这个组件的日志，看代码里的那条异常分支有没有真的被走到。它从组件日志里匹配到了对应的记录，时间点和集群异常开始的时间吻合。到这里证据链闭合：配置冲突 → 代码分支 → 故障时段日志 → 集群现象。

第五步：还原现场做配置验证。
在非生产环境按线上配置还原了这个组件，由 Agent 生成对照用的两组配置和观察指标，人来执行和观察。结果是按线上配置能复现异常，改掉冲突项后恢复预期行为。

第六步：输出报告。
Agent 把以上证据链整理成一份带参数表、代码位置、日志片段、验证结果和修改建议的文档，我补充了业务影响和变更计划后上传飞书知识库。整个过程半天，原本的预期是 2 天。

如何判断效果？

补充说明：

这不是一次尝试，是持续使用。从 2026 年上半年至今，本仓库已沉淀 16 个 Skill，排查类报告（OOM 分析、Pod 重启、CDN 性能审计、CA 行为分析、5xx 错误、ingress 路由异常等）持续积累。
没有全链路经验的人也能用同一套 Skill 和提示词走完排查，因为口径、账号、分层规则都在 CLAUDE.md 和 Skill 里，不在人脑子里。
哪里不好用，我踩过的坑？
最初的方法为什么没奏效：直接问 Agent “为什么异常”。
第一版没有分层规范，直接把现象丢给 Agent，它会同时查很多东西，给出一个覆盖面很广但没有重点的回答，看起来像结论，其实是猜测。改成“先定层再下钻”之后才稳定。教训是：SOP 要先写给 AI，再让 AI 用。
AI 出过的错：数据口径错，PromQL 语法完全正确。
用 rate[1d] 算日均 QPS，Pod 重建导致计数器重置，结果虚高 2～6 倍；request 没按 Pod phase 过滤，已完成 Job 被计入，装箱率算出 143%。这类错误靠“看起来不合理”的数字发现，比如装箱率超过 100%。处理方式是每个坑都写回 Skill 或 CLAUDE.md，让它变成 AI 下次的默认行为。
为了稳定使用加的约束。
全部账号只读，settings 禁写；生产变更只允许人审核后执行生成好的命令。
CLAUDE.md 记录集群与认证方式的对应关系，不写 AI 会猜，还可能连错环境。
判定逻辑写进脚本不交给模型自由发挥，保证同一个问题两次跑结果一致。
仍选择人工处理的情况。

涉及业务语义判断的问题、生产变更，Agent 给证据链和方案，人做决定。

如果你也想做类似的事情，可以从哪里开始？

这个方法适合负责多系统、长链路线上环境的工程师，在各系统有可查询的 API 或 CLI、且能申请到账号的条件下使用。开始前需要准备：Claude Code、各系统的只读凭证、一份写清集群与账号对应关系的 CLAUDE.md。第一次尝试，建议先拿“某个 Pod 重启了，查原因”这样的小任务练习：接一个 Prometheus MCP 和只读 kubectl 就够，跑通后把这条路径写成第一个 Skill。遇到需要进节点或容器、需要业务判断、需要变更生产的情况时，需要人工介入；系统没有可编程接口的，暂时不适用。

一个可直接执行的起点顺序：

配 Prometheus MCP 和只读 kubectl，写 CLAUDE.md 里的集群账号表。
用一次真实的小问题（Pod 重启、HPA 卡顶）走一遍交互式排查。
把这次排查的步骤、PromQL、口径坑写成 SKILL.md。
下一次同类问题直接用 Skill 触发，看是否不需要人补充上下文。
跑通后再接日志、边缘、协作工具，补分层排查规范。
最后想分享的话

Agent 在排查里最有价值的不是“它比人懂”，而是它能不知疲倦地把五六个系统的证据拉到同一条时间线上，并且每一步都留痕。人该做的是定方向、挑可疑项、判断证据链有没有闭合。“AI 负责调查，人负责判断”，这个分工定下来，新人和老人用的就是同一套流程。
