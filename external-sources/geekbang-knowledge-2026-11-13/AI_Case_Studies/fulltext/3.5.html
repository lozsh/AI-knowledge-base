案例名称

文章生产线：Claude Code 写作 skill + 自研 publisher-agent 桌面 App，实现技术文章“写作 → 分发 → 排期 → 审核监控”全链路自动化。

案例简介

我是产品人 + SRE 背景的个人技术写作者，在掘金/知乎双平台维护 7 个专栏（FDE 九辩、K8s 深入理解、云原生踩坑实录、SRE 转型路线、SRE 图谱平台全栈实践、R2R × Jev、分布式不难懂）。

写作环节早已和 Claude Code 协作顺畅，但分发环节仍是纯手工：每篇文章要登录后台、填标题摘要、选分类/标签/专栏、制作上传封面、设定时发布、事后盯审核状态，单篇 10 分钟起步，忙起来就断更，断更直接影响专栏的读者粘性。

我用 Claude Code 写作 skill + 自研 publisher-agent 桌面 App（Tauri 2.0 + Rust 核心）搭了一条文章生产线：写作层把惯例沉淀为 skill，分发层免浏览器直连掘金 API 自动发布，运维层用 SQLite 状态机 + 每小时心跳对账 + 自愈做监控。21 天管理 54 个条目、掘金侧 50+ 次全自动发布，全账号累计已发布 76 篇、日均 1.4 篇持续产出，全部零手工分发。

之前的老方案是什么，存在什么问题

写作早已和 Claude Code 协作顺畅，但分发环节纯手工仍然很繁琐，忙起来就断更。拆成四个具体问题：

  1. 发布操作重复繁琐：每篇 10+ 步手工操作；
  2. 没有排期机制：断更风险高；
  3. 平台审核是黑盒：被拒了无法当天发现，错过修改窗口；
  4. “哪些已发、哪些待发、哪些被拒”全凭记忆：零可观测性。

本质是把内容当一个一个项目在做，而不是当持续运转的服务在做。这里缺的正是 SRE 眼里的自动化、排程、监控与自愈。

是怎么用 AI 解决的，具体过程是什么（以及这中间有哪些坑）

三层架构，各层独立可用、组合成生产线：

  1. 写作层（Claude Code skill）：把写作惯例沉淀为可复用 skill（article-pipeline）：选题 → 大纲 → 成稿 → 修订的流程固化；并把掘金高阅读量文章的标题模式、结构节奏分析结论写进惯例，让数据反哺写作。人机分工明确：人管选题与观点，机器管重复劳动。
  2. 分发层（自研桌面 App）：publisher-agent，Tauri 2.0 壳 + Rust 核心，免浏览器直连掘金 API。链路：扫描本地 Markdown（frontmatter 声明元数据）→ 可视化编排（选篇/定时/专栏/标签/摘要）→ 自动创建草稿并发布 → 自动生成 192×128 封面并上传 → 专栏/分类/标签自动匹配。
  3. 运维层（SRE 实践）：SQLite 状态机（pending → publishing → in_review → live/rejected/held）、Windows 每小时心跳任务、审核状态自动对账、Cookie 过期自动转 held 并引导重新扫码（自愈）、防重发护栏（已发标题冻结 + 内容指纹去重 + 发布时间闸门）、51 个自动化测试守护核心逻辑。

过程中踩过的坑（踩坑与修复）：

  1. 中文标题按字节截断，切在汉字中间直接 panic 崩溃 → 全面改为字符级安全截断；
  2. 定时心跳与“立即发布”并发执行，状态互相覆盖“全乱套” → 引入跨进程文件锁；
  3. 特定词汇组合（如招聘类词×金额表述）触发内容审核拒绝，相似内容重投会被更快拒绝 → 沉淀预检规则，发布前对标题/摘要自检；
  4. Cookie 中途失效，条目卡死在中间态 → 引入 held 状态 + 自动治愈流程；
  5. 早期 Python 版依赖本机环境，换机即失效 → 核心逻辑重写为 Rust，状态收进 %APPDATA% 下的 SQLite，App 完全自包含，零环境依赖；
  6. 浏览器自动化有边界：Webview 内嵌 Chrome 方案失败，知乎接口反自动化强 → 诚实降级：掘金全自动，知乎保留“一键半自动”，不硬造全自动假象。

与旧办法相比，新办法的结果如何（数据对比）

（数据来自数据库 + 掘金创作者中心实测，非估算）

  • 生产端：21 天（9/18–10/9）状态机管理 54 个条目，掘金侧 50+ 次全自动发布；全账号累计已发布 76 篇、创作第 56 天——日均 1.4 篇的持续产出，全部零手工分发。
  • 专栏矩阵（全部由该工作流创建并维护）：7 个专栏 62 篇——FDE 九辩（11）、K8s 深入理解（14）、云原生踩坑实录（12）、SRE 转型路线（9）、SRE 图谱平台全栈实践（8）、R2R × Jev：判断之后的治理（5）、分布式不难懂（3）；专栏文章数与逐篇 API 核对结果完全吻合。
  • 传播端（掘金数据看板 10/9 读数）：文章展现 60,287 次、阅读 2,150 次、点赞 34、评论 11、收藏 19。
  • 单篇明细（API 核对 62 篇）：Top3 为《消息队列选型决策树》127 读、《云原生 SRE 巡检图》105 读、《FDE 人才定级手册》97 读；Top10 合计约 820 读、占总阅读 37%，多系列铺量的长尾结构清晰。
  • 可审计：494 条事件流水，每次状态迁移可回溯。
  • 单篇分发操作从 10+ 分钟 → 0 分钟（加入编排即完成）；
  • 审核状态从“想起来才看”→ 每小时自动对账，被拒当天可见；
  • 断更风险消除：一次编排多日排期，心跳自动执行——10 月 9 日当晚心跳仍在自动发文。

意外收获：写作 skill 与发布 App 形成双向闭环——发布侧经验（过审标题、高阅读结构）回写进写作惯例。

通过这个 AI 落地案例，我的收获有哪些

  1. Agent 工程的核心是状态机而非提示词：把“发布一篇”建模成显式状态机后，每种异常都有了挂靠点；
  2. 防重发比发布本身更重要：平台风控不可控，护栏（标题冻结、指纹去重）是敢让系统无人值守的根基；
  3. 诚实降级好过硬造全自动：明确声明半自动边界，反而让全自动部分更可信；
  4. 人的判断留在选题与观点，机器接管重复：这条线划清楚，人机协作才顺畅；
  5. SRE 方法论（排程、对账、自愈、自检）适用于任何“要持续运转的个人系统”：个人开发者也配拥有生产级运维。
