案例名称

LightGitPad：用 AI 协作开发的轻量代码工程与 Git 记录管理桌面工具，把「工程文件、代码、Git 改动和历史」放进一个窗口，配合 Claude Code / Codex 等 AI 编程助手使用。

案例简介

我在使用 Claude Code、Codex 等 AI 编程助手开发软件时发现一个实际问题：开发越来越多地在聊天里完成，助手能改文件并解释结果，但我仍然需要亲眼确认工程结构、代码内容、哪些文件被改过、具体改了哪几行。为了核对一次改动就打开 IDE，负担比较重；轻量文本编辑器适合看单个文件，却缺少完整的工程和 Git 视图。我把这个日常痛点转化为一个具体产品需求，再用 AI 协作开发 LightGitPad（github.com/felixlwang/LightGitPad）：把工程文件、代码、Git 改动和历史放进一个轻量桌面窗口，让人更容易检查 AI 的工作结果。已形成支持 Windows 和 macOS 的可运行桌面工具，具备工程文件树、多标签代码阅读与编辑、左右对照 Git 差异、路径历史和 Markdown 预览等能力。

之前的老方案是什么，存在什么问题

针对查看工程和核对改动的需求，原有方式主要是打开 IDE，或在文件管理器、轻量文本编辑器和 Git 工具之间来回切换：先找文件，再读代码，再查差异和历史。这些工具各有用途，但只为了看一眼工程和改动，需要维护多个窗口和上下文；单文件编辑器也难以把工程结构、当前差异和提交记录连起来看。

是怎么用 AI 解决的，具体过程是什么（以及这中间有哪些坑）

工具：Claude Code、Codex 这类能够直接读取和修改工程文件的 AI 编程助手。整体分工：我提出真实使用场景、确定范围并验收结果；AI 辅助分析方案、实现代码、排查问题和整理说明。步骤：

  1. 先把目标说具体：重点解决工程浏览、代码阅读、Git 差异和历史查看，明确产品的轻量定位；
  2. 把需求拆成可检查的功能：逐项迭代文件树、文本编辑器、差异视图、历史视图和 Markdown 预览等能力；
  3. AI 修改后核对实际文件和 Git 差异，再通过构建、必要的测试和界面检查确认行为；有问题就带着具体证据反馈，再继续修正；
  4. 把运行、安装和使用方法写成用户能看懂的说明，形成可交付的 Windows 和 macOS 桌面工具。

最关键的一步：把「助手说完成」转化成「人能检查的结果」——需求、实际改动和验收行为要对得上，发布等外部操作另行明确授权。LightGitPad 本身不调用 AI 服务，而是用 AI 协作开发出来、帮助人核对 AI 改动的配套工具。

过程中踩过的坑：

  • 最需要警惕的是把 AI 的完成说明当成验收结果：代码能编译，不等于界面行为和用户需求都正确；要回到实际文件、差异和操作结果逐项核对。
  • 把范围和权限写清楚：功能取舍、允许修改的路径、提交和发布的边界，都要让助手知道。尤其多人或多个会话一起工作时，要划清写入范围，避免相互覆盖；Git 提交也要核对具体文件和改动，不能把无关内容一起带进去。

与旧办法相比，新办法的结果如何（数据对比）

  • 具体成果：形成 LightGitPad 这个可运行的桌面工具，支持 Windows 和 macOS，已具备工程文件树、多标签代码阅读与编辑、左右对照 Git 差异、路径历史和 Markdown 预览等能力。
  • 工作方式变化：需求和反馈可以在对话中组织，AI 承担一部分实现与排查工作，人把精力放在范围判断和实际验收上；核对 AI 改动时，可以在一个窗口里查看工程、代码和 Git 记录，减少为看一眼结果而切换多种工具的步骤。
  • 一个可核实的产品指标：项目说明记录了 Windows v0.2.15 打包版打开工程时，程序自身私有内存约 30 MB——这个数字说明轻量目标的实现情况，不代表 AI 带来的效率提升比例。

通过这个 AI 落地案例，我的收获有哪些

  1. 从真实而具体的痛点开始：把「AI 改完要亲眼核对」这个日常痛点做成产品需求，工具一出生就有人用。
  2. 有工具或功能需求，可直接交由 AI 开发实现：过去若需要特定能力，往往要耗费大量精力寻找替代方案；如今借助 AI，不仅效率极高，产出成果也更贴合自身要求。
  3. 产品取舍、证据判断和最终验收仍需要人负责：AI 可以加快实现，但范围、权限、提交边界这些判断不能全交给助手——尤其多会话协作时，写入范围不划清就会互相覆盖。
