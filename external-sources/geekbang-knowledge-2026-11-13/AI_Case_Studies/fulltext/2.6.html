案例名称

桌面 AI 伙伴“栖伴”（QIBAN）开发实践：验证门禁 + 多智能体对抗审查 + 真机验收三道验证关，让 AI 生成代码敢合入主线。

案例简介

我是产品 + SRE 背景的独立开发者，业余时间开发桌面 AI 伙伴产品“栖伴”（QIBAN）：Windows 桌宠，React + TypeScript + Tauri 2 + Rust，功能含语音对话（录音 → 识别 → 流式分句 → 逐句合成 → 口型→ 打断）、本地记忆、手机配对。

团队就是我自己 + AI 编程智能体（Claude Code），一个人做通常需要小团队的事：Rust 后端、前端、测试、真机验收、发布。当前规模 8280 行 Rust、3390 行前端、2073 行测试、1565 行 IPC 契约，128 个提交。核心实践是把 AI 从写代码的工具升级为开发流程本身，用“验证门禁（每个 commit）+ 多智能体对抗审查（每个 PR）+ 真机验收（合并后）”三道验证关层层把关：以最近语音功能批为例，10-07 一天合入 7 个语音 PR，10-09 脚本化真机验收 8 用例全绿，全程一人 review。

之前的老方案是什么，存在什么问题

写代码早已不是瓶颈，验证才是：AI 生成代码的速度远超个人逐行审查的能力，但没有验证纪律的 AI 代码不敢合入主线。具体有三个问题。

  1. mock 测试会撒谎：浏览器测试里的 mock 对象与真机环境行为不一致（本项目有具体案例：真机 WebView2 的注入对象不可写，mock 是普通可写对象——这类差异 mock 自己永远测不出），“测试全绿”不等于“真机能跑”；
  2. 个人开发没有第二双眼睛：传统代码评审在这套流程里不存在，需要一个替代品；
  3. AI 审查 AI 可能共模：两个模型互相点头不构成证据——审查结论本身也要被验证。

是怎么用 AI 解决的，具体过程是什么（以及这中间有哪些坑）

三道验证关层层递进：

  1. 验证门禁（每个 commit）：全套脚本化、AI 自己跑自己修到绿——Rust 侧 cargo fmt / clippy -D warnings / cargo test（197 个测试），前端 npm run check（类型+单元）+ Playwright 全套（55 个浏览器用例，约 15 秒），外加文档结构校验 verify:docs。门禁不绿不进下一步。
  2. 多智能体对抗审查（每个 PR）：合并前用 workflow 编排多个审查智能体分维度找问题（生命周期时序 / 行为矩阵完整性 / 测试真实性），每个发现再派独立的「反驳者」智能体验证——反驳不掉才算真问题。防御性代码必须过 mutation 验证：临时删掉它 → 测试必须变红，才算被真正钉住。最近一次审查（PR #51）：7 个智能体、4 个发现、全部确认成立。
  3. 真机验收（合并后）：CDP 远程调试连打包后的 Windows exe + 本机 HTTP fixture（零真实凭据）+ 合成音频流替代真实麦克风 + 全新一次性 profile。验收脚本断言：raw WAV 走 IPC 字节级一致、无 Authorization 头、设备轨道全部释放、无 blob 泄漏、打断发生在传输层（fixture 服务端观测到连接 abort）。8 用例可重复执行。

安全设计同步内建：密钥只由 Rust 从 Windows 凭据管理器读取、永不跨 IPC、公开仓库零密钥。

过程中踩过的坑：

  1. AI 辅助开发的瓶颈从「生成」移到了「验证」：门禁 + 对抗审查 + 真机验收，是让 AI 产出敢合入主线的三件套——缺一个都会退化成「看起来很快、其实不敢用」；
  2. AI 审查 AI 是有效的，但必须结构化：维度分工、独立反驳、mutation 验证三层缺一不可；不然就是两个模型互相点头；
  3. mock 全绿不等于真机能跑：观察与断言要尽量打到真实边界（传输层连接 abort 比页面侧“已取消”字符串是强得多的证据）。

与旧办法相比，新办法的结果如何（数据对比）

（以最近的语音功能批为例，全部数字可溯源到主线 git）

  • 交付速度：10-07 一天合入 7 个语音 PR（含桌宠语音全链 T11 与口型 T12，晚间三个 PR 间隔仅 16 分钟）；10-09 脚本化真机验收 8 用例全绿；同日用户人工听感反馈（“切焦点停止朗读”）当天定位、过对抗审查、修复合入——从编码到验收全绿两天，反馈修复当天。
  • 质量证据：每 PR 有对抗审查记录（最近一次 7 agents / 4 findings 全确认）；回归有 mutation 验证（baseline 0 红 → 摘防御各精确 1 红）；真机有可重复验收脚本（result.json + 32 条 IPC 命令流 wire 留痕 + 服务端连接 abort 观测）。
  • 全程一人 review：AI 承担编码与大部分排查，人承担问题定义（“解决什么”）、产品语义拍板（如“失焦该不该停止朗读”）与最终判断。

通过这个 AI 落地案例，我的收获有哪些

  1. 验证纪律是 AI 产出的合入许可证：没有三道验证关，AI 写代码再快也不敢合并；有了它们，单人团队也能保持接近生产级的质量。
  2. 对抗审查必须结构化：维度分工 + 独立反驳 + mutation 验证三层，才能避免“两个模型互相点头”的共模失败。
  3. 人的价值上移了：写代码的时间占比大幅下降，但问题定义、产品语义取舍、诚实声明能力边界（哪些验证过、哪些没有）反而更关键——AI 不会替你拍板，也不该替你拍板。
  4. 坑就是案例：mock 与真机的差异、sed 的贪婪匹配、effect 竞态——失败比成功更有参考价值，也都沉淀成了交付记录和自动化测试。
