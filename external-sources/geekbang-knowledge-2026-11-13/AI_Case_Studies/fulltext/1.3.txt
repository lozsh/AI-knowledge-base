一句话成果：「别把 AI 当搜索引擎，把它当执行者——让它在业务链路里一步步取证，比给它一个更聪明的 prompt 重要得多」
案例名称

「问题排查小助手」：用 AI Agent 打通研发线上问题排查全链路，让排查经验一键沉淀、自动复用。

案例简介

我在研发团队，负责线上问题排查。

日常最常见的场景是：客服或运营甩过来一条反馈「这个页面打不开 / 这个订单查不到」，附一个 URL 和问题现象，我要去定位根因——这个 URL 属于几十个微服务里的哪个项目？对应日志在哪里？是不是配置错了？是不是某台机器有问题？

我们系统链路上有多套内部平台（项目定位、SLS 日志、配置中心、机器信息），排查一个问题要把这几套系统挨个走一遍。我把 AI 大模型（可切换 DeepSeek / 通义千问）接到这些内部系统上，做了「问题排查小助手」，让它代替人去查、去分析，并把每次排查结论一键沉淀成结构化案例，通过 RAG 复用。

之前的老方案是什么，存在什么问题

之前是纯人肉排查，全靠「问老人 + 翻平台 + 凭经验猜」：

先认项目：拿到 URL 先看域名和路径，猜是几个可能的服务；猜不出来就在群里喊「谁知道 xxx 这个接口是哪个服务的？」，等老同事回。
再找日志：登日志平台，选环境、选时间范围、填关键字搜，关键字不对就换词再搜，来回试。
查配置和机器：日志看不出结论，再去配置中心对照配置、看机器状态，又是一套新平台。
自己分析根因：信息都在脑子里，靠经验判断，最后在群里口头同步结论。
结束即结束：问题解决了就翻篇，过程不落文档，最多在聊天记录里留几句。

这套方式的问题：

慢，且大部分时间不是花在思考上，一个问题动辄几十分钟甚至半天，大头是机械查找动作。
强依赖个人经验，新人几乎没法独立排查，老人脑子里有「URL → 服务 → 日志在哪查」的映射表，老人一休假问题就卡住。
排查质量不稳定，关键字没试对、时间范围选错，就可能漏掉根因，得出「没找到异常」的错误结论。
上下文切换成本极高，同时开 N 个平台+聊天窗口，信息靠人脑拼接，容易丢信息。
经验零沉淀，排查完没人写 wiki，「写完即埋」，下个人从头走一遍。
高峰期响应不了，能排查的人就那几个，得排队等。
如何用 AI 解决

工具与技术：LangChain4j + Spring Boot 3.5（后端编排）、大模型可切换设计（DeepSeek / 通义千问 qwen-max，改环境变量秒切）、MCP 工具接入（把内部系统封装成 project-finder 定位项目 / sls-logs 查日志 / config 查配置 / nodes 查机器）、DashScope text-embedding-v4 做 RAG 检索、Vue 3 + Vite 前端 SSE 流式输出。

整体思路：不是让 AI「答」，而是让 AI「查」。 大模型本身不知道内部线上情况，光靠聊天只能给出通用猜测；真正有价值的是把 AI 变成能操作内部系统的「执行者」。

下面是关键步骤：

入口极简：用户只需输入「URL + 问题现象 + 发生时间/环境」，不填任何技术字段。
工具化内部系统（最关键一步）：通过 MCP 把项目定位、日志、配置、机器查询封装成标准工具暴露给模型，AI 才从「只能聊天」变成「能动手查」。
让模型自主编排排查链路：不写死流程，靠 system prompt 约束排查顺序和边界，由模型判断该调哪个工具、要不要追加查证，遇到非常规问题也能自己调整策略。
过程流式可见：每次工具调用、查到什么、中间结论都实时推给前端，用户能看到它在干活，出问题时一眼看出卡在哪——这是建立信任的前提。
一键沉淀 + RAG 复用：排查结束点一下「保存到知识库」，自动生成结构化案例（问题现象/定位过程/根因/结论）；后续同类问题 RAG 先检索历史案例，命中就直接给出上次的根因。
多供应商可切换 + 降级设计：供应商不稳定时可秒切；embedding 不可用时 RAG 降级为空结果，对话主链路不受影响。

过程中踩过的坑

SSE 流式输出被 Nginx 缓冲，页面一直转圈（排查类场景工具调用接近分钟级，加上缓冲用户以为卡死）

处理方式：反向代理配 proxy_buffering off、proxy_cache off，proxy_read_timeout / proxy_send_timeout 调到 600s。凡是流式 AI 应用走反向代理，这两条是必查项。

JDK 版本坑

处理方式：编译报「未结束的字符串文字」，实为 shell 默认使用 Java 8，项目用了 text block/record 需要 JDK 21。AI 相关框架普遍要求高版本 JDK，部署前先确认运行环境。

RAG 依赖的外部 API Key 没配会拖垮主链路

处理方式：embedding 不可用时降级为空结果 + 明确提示，保证对话主链路始终可用。AI 应用里每个外部依赖都要有降级路径。

内网排查场景主动关掉 web-search

处理方式：开着外网搜索，模型会拿公开资料「补充」内网问题的结论，反而干扰判断。内网场景要让模型只基于内部工具的证据说话。

黑盒等待 = 没人敢用

处理方式：早期版本只给最终结论，中间几十秒转圈，同事用完一次就不来了；改成每步工具调用、中间结论实时流式展示后使用率才上来。过程可见不是锦上添花，是信任的前提。

沉淀功能超过一步就没人用

处理方式：一开始想让同事手工填案例模板几乎没人填；改成排查完点一下自动生成结构化案例，沉淀才能跑起来。

与旧办法相比，新办法的结果如何（数据对比）
排查会话：已产生 20 条完整排查会话记录（系统自动留存，真实使用 20 次以上，不是 Demo）。
知识沉淀：从 0 到 4 个结构化案例（之前 wiki 几乎没人写），包括「接口无社群渠道幂等 → 同家庭重复创建学生」（AI 顺着日志查出的真实代码缺陷）、「内部交易号订单查询」「学生列表权限过滤逻辑」等。
使用门槛：排查入口从「N 个内部平台 + 找人确认」降到「1 个输入框 + 3 个字段」（URL + 现象 + 时间/环境）。
排查耗时：从原来的约 30～60 分钟/一个问题降到 5～10 分钟，人效提升约 70%～80%（这几个数字是体感估算，不是按统一口径的统计）。

变化描述（无硬数据但很明显）：新人能独立排查、不再卡在起步；排查质量变稳定（工具调用和排查顺序标准化，很少再出现「关键字没试对所以没找到异常」的假阴性）；经验终于能留下（同类问题第二次出现基本秒级给出结论）；排查过程可见、可追溯；不再强依赖个别人，高峰期不用排队等「会查的人」。

通过这个 AI 落地案例，我的收获有哪些

先打通工具，再谈模型和 prompt：内部系统接不进来，AI 就只是「懂技术术语的聊天窗口」，落地价值为零；工具打通之后，同样的模型立刻能干活。选型顺序应该是：哪些系统能被 AI 调用 → 如何工具化 → 再选模型和写 prompt。

别把 AI 当搜索引擎，把它当执行者：让 AI 出结论容易，让它按业务链路一步步取证、并基于证据说话才难。system prompt 里要严格约束排查边界和「没有证据不许下结论」，否则幻觉会直接变成错误的排查结论，比不用 AI 还糟。

不要把命运绑在单一模型上：模型供应商做成环境变量可切换，任一供应商限流、涨价、不稳定，改一个环境变量就能切走。

密钥管理从第一天就规范：AI 应用天然接触大量内部系统凭据，配置文件不进 git、权限设 600、走环境变量注入。
