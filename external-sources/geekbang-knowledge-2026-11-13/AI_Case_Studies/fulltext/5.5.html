一句话成果：把“人盯屏”换成“模型初筛、人复核”：单卡 3 秒解析 20 路 CCTV 画面，人流、拥堵、推搡等异常自动提醒值班人员，误报收敛、响应提速，全程数据不出域、不改存量设备。

先用一段话说清楚，我做成了什么

我是某大型维安领域公司的算法工程师，日常需要为承担公共服务的国央企客户研发数十路摄像头的实时异常监控方案。

过去采用“外包人力轮巡盯屏＋人工定期巡逻”的方式，主要问题是后半夜注意力衰减、异常发现和上报链路太长，小事件容易拖成大事故。

从去年开始，团队尝试用本地部署的视觉决策模型辅助完成数十路摄像头的实时异常判断。

经过两版方案迭代与现场试点，目前的结果是：单卡可在三秒内解析二十路画面，人流骤增、拥堵推搡、打架追逐等疑似事件能自动提醒值班人员，响应速度和误报情况都有改善；其中仍需人工完成的是报警复核、现场处置，以及少量长尾场景的兜底。

原来怎么做，为什么值得改变？

先说背景。团队在一家大型安全服务企业的业务组负责 CCTV 方向，集团希望我们部门实验并引入各种 AI 技术，为承担公共服务的国央企客户提供更有竞争力的服务。客户也同意“希望引入视觉 AI 做实时监控提醒”后，这件事落到了我们组。

以其中一个试点客户为例：他们在火车站、汽车站和人群密集的广场部署了数十路摄像头，要实时监控人流量突然变大、人群拥堵推搡、追逐打闹甚至打架抢劫等治安事件，也要盯住车辆容易拥堵的路段。

这项工作过去由外包人力完成：值班团队 7×24 小时轮巡盯住数十路画面，另有人定期巡逻关键路口和摄像头死角。最麻烦的环节有两个。

  • 一是“人盯屏幕”的稳定性。一个人同时盯几十路画面，连续值守几个小时难免精力不集中，后半夜尤其严重——而治安事件恰好多发生在后半夜。比如某个人流通道夜间出现人群聚集推搡，值班员可能正在处理另一路画面，等注意到时已过去几分钟。
  • 二是“发现—上报—处置”的链路太长。值班员看到异常后要用对讲或电话通知巡逻人员，沟通不畅就会延迟响应。小情况遏制不及时，就可能升级成重大事故，这是客户最担心的。

客户也尝试过自己引入 AI：本地部署的小模型跑得快但结果不稳定；大模型识别准，但推理慢、对硬件要求高，要满足实时就得投巨资升级方案。

此外还有两条硬约束：合规上数据不能出域、不能用外部模型；现场不接受对存量设备和网络做大规模改造，能用的只有有限的本地算力。

这两条约束叠加“数十路、实时”的要求，是方案设计的全部前提。

我们具体怎样把 AI 用进去？

我们选了一个有代表性的点位推进：在不换设备、数据不出域的前提下，为某枢纽站点的数十路存量摄像头做出“能实时提醒、误报可接受”的方案，分六步推进。

第一步：先用微调小模型当“报警器”，摸清单模型路线的边界。

第一版方案，我先准备了一个微调过的轻量视觉模型，交给我们自己的推理服务，要求它对单路画面做异常检测、发现疑似情况就提醒值班人员。它给出的结果是：速度够快，单摄像头勉强能实时，但误报非常多。

我发现问题的根源不在模型精度，而在单角度摄像头容易被遮挡、信息残缺——值班人员被无效报警反复打扰，反而开始麻木。于是我放弃“换更准的模型”，确认要换思路，进入下一步。

第二步：转向视觉决策模型，先给候选模型办一场“入场考试”。

我先准备了一个由几百张图像组成的评测数据集，覆盖不同人数规模、打架、推搡、拥堵、车辆滞留等场景，交给候选的视觉语言模型（VLM）逐个跑测，要求它们既看得清画面、又认得出目标现象，且参数量小于 9B——现场只给得起显存 24GB 的单卡。它给出的结果是：大部分候选被淘汰，有的视觉能力差，画面里明明有人群推搡却视而不见；有的看得清，但对“打架”“推搡”这类现象识别很弱。

我发现“能对话的模型”不等于“能看监控的模型”，于是把通过初筛的模型针对特定任务做后训练，再部署到客户环境测试，进入下一步。

第三步：设计“一次调用、多题联答”的提问方式。

我先梳理出值班场景真正关心的问题清单，交给决策模型，要求它对每张画面一次回答多道题目，并输出带置信度的 JSON。以下是我们实际使用的一版提示词（脱敏）：

【输入】一张 CCTV 画面截图（单帧）。

【请回答以下问题，并输出 JSON】
1.（choice）画面中的人数区间：
   A. 20人以下　B. 20–40　C. 40–60　D. 60–80　E. 80–100　F. 100人以上
2.（bool）是否存在打架斗殴？true / false
3.（bool）是否存在推搡或拥挤？true / false
4.（bool）是否存在追逐打闹？true / false
5.（bool）是否存在车辆拥堵或滞留？true / false

【输出示意】
{
  “count_range”: “B”, “count_confidence”: 0.92,
  “fight”: false, “fight_confidence”: 0.97,
  “push”: true,  “push_confidence”: 0.61,
  “chase”: false, “chase_confidence”: 0.95,
  “vehicle_jam”: false, “vehicle_jam_confidence”: 0.90
}

它给出的结果是：人数区间判断相当稳定，但“推搡”和“拥堵”在低清画面里容易互相混淆。

我发现把两类现象合在一起问会互相干扰，于是人工拆成两道独立的判断题；像上例中“推搡”置信度只有 0.61 的低置信结果不直接报警，转给第五步兜底复核。这样每路画面一次推理就能同时拿到人流量分级和行为判断，批量解析成为可能。

第四步：用多角度交叉验证压制误报。

我先准备了同点位多角度摄像头的画面关联关系，交给决策模型的复核流程，要求它在正面角度报出异常后，自动调用其他角度做二次取证。它给出的结果是：其他角度都没有类似结果的报警被降级或不推送，误报进一步收敛。

我发现这一步本质上是把“单角度信息不全”的短板从模型层面转移到流程层面解决，于是固化为标准动作，再进入下一步。

第五步：给长尾场景配兜底

我先准备了一个此前训练好的常规视觉模型常驻内存，交给兜底链路，要求它每 3～5 秒对全部画面抽帧探测一次；决策模型置信度低于阈值时，也把画面转给它复核。它给出的结果是：长尾场景（严重遮挡、罕见行为）有了第二道防线。

我发现决策模型的软肋是单步推理、“想得浅”，单靠它兜不住所有情况，于是保留了这条旁路；同时我们仍在收集更大的数据集，尝试基于 MOE（混合专家）架构的决策模型进一步提高可靠度。

AI 与人工的分工如下（脱敏流程示意）：

[数十路存量摄像头]
        │
        ▼
┌────────────────────────────────────────┐
│ 决策模型批量推理（单卡，秒级/轮）              │
│ 每路输出：人数区间 ＋ 行为判断 ＋ 置信度        │
└──────┬─────────────────────────────────┘
       ├─ 无异常 ───────────────→ 不打扰值班人员
       ├─ 异常 且 置信度 ≥ 阈值
       │      └→ 同点位其他角度交叉复核 ──→ 推送报警
       └─ 异常 且 置信度 < 阈值
              └→ 常驻常规视觉模型兜底复核 ──→ 推送报警
                                        │
                                        ▼
                      【人工】值班员复核确认 → 通知巡逻处置
旁路兜底：常规视觉模型每 3～5 秒抽帧探测全部画面
运维看板：健康指示灯/图标 ← 模型与宿主机心跳状态

第六步：把“系统活着”本身也纳入设计。

我先复盘了模型在生产环境中崩溃的事故，交给运维环节一个朴素的要求：让值班人员一眼能看出系统是否正常。它给出的结果是在现场加了健康指示灯/图标，并培训现场人员：指示灯不亮时，要更依赖人工盯屏和巡逻。

我发现最危险的不是模型答错，而是模型“不在场”却没人知道——崩溃后没有任何警报，值班人员会误以为“一直没情况发生”，这种假安全比误报更致命。

有没有效果，我是怎么判断的？

先坦白：这是客户环境中小范围试点的持续运行；没有做严格的对照实验，也没有“误报率下降百分之多少”这类精确数字。判断依据有三个。

  • 一是前后两版方案的对比。比较基于同一批存量摄像头、同一套值班流程，前后任务难度和质量要求基本一致。V1（微调小模型报警器）误报频发，值班人员开始忽略报警；V2（决策模型＋多角度复核＋兜底）上线后无效打扰明显收敛，值班人员的反馈是“打扰少了，报警更值得看一眼”。
  • 二是响应速度。现场单卡环境中，二十路画面三秒内完成一轮解析，基本达到“秒级发现”的目标。要说明的是：这是纯推理时间，不包含人工复核——报警后的人工确认并没有省掉，我们的目标始终是“把人的注意力从盯屏转移到确认”，而不是取消人。
  • 三是选型阶段的批量测试。几百张图、多个候选模型逐个跑完对比，谁能看清画面、谁对特定现象识别弱，排序依据非常明确。

需要诚实说明：以上主要依据是试点运行观察和值班人员反馈；误报次数、平均响应时长等指标仍在持续收集，样本量还小，结论只能算初步成立。

哪里不好用，我踩过什么坑？

第一个坑是最初的方法没有奏效。

小模型报警器勉强能实时，但单角度遮挡加上模型能力受限，误报多到值班人员开始麻木。这个坑教会我：报警系统最常见的失败不是“漏了大事件”，而是“报得太勤，没人再信”。

第二个坑是对“决策模型”的盲目信任。

我一度以为“能对话的模型就能看监控”，实测才发现并非如此。发现问题靠的就是那套几百张图的评测集——它在部署前淘汰了大部分候选模型。此后我们固定下“先评测、再后训练、后部署”的动作，每引入新模型第一件事就是跑评测集。

第三个坑是崩溃静默。

模型在生产环境崩溃过，宿主机上还有别的程序竞争资源；崩溃后没有任何报警，值班人员会误以为“没有情况发生”。目前的应对是健康指示灯加现场培训，但坦白说这仍依赖人员主动留意；把它升级成心跳丢失自动告警，是我们下一步要做的。

还有一些情况仍由人工处理：高风险事件（疑似打架、抢劫）即使模型报警，也必须由安保力量现场确认后升级处置；需要连续行为判断或严重遮挡的场景，主要靠常规模型探测和人工巡逻兜底。

如果你也想做类似的事情，可以从哪里开始？

这个方法适合有存量摄像头、数据不能出域、算力有限（单卡级别）的安防或运维团队，在需要“发现异常、提醒人工”而不是“自动处置”的条件下使用。

开始前需要准备三样东西：一份写清楚“要模型回答什么”的问题清单、一个几百张图规模且覆盖目标场景的评测集、一个随时待命的常规小模型做兜底。

第一次尝试，建议先拿“单摄像头人数区间统计”这种单问题、容易验证的小任务练习，跑通后再加行为判断题，然后是多角度复核和置信度兜底。遇到高风险事件、大范围遮挡、夜间低照度画面等情况时，需要人工介入，或者暂时不适用——先去积累数据，而不是硬上模型。

最后，我想分享给大家的话

做了两版方案后，我最大的体会是：AI 落地的难点往往不在“模型能不能做到”，而在“把什么交给模型、把什么留给人”。我们做的监控只是很小的一块——从车流车道、低空到工厂流水线，依托 CCTV 和视觉判断模型的机会还有很多，但每个场景都需要小心探索，几乎不可能有哪一项技术覆盖所有场景。

我的另一条经验是：模型是死的，场景是活的。能力最强的模型未必适配我们的场景，挑一个基础能力、硬件开销和响应速度都“够用”的模型，针对特定场景做适配，往往才是更合理的方案。
