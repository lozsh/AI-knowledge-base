从一条失败的代码修改说起

假设团队给 AI 编码助手下达了一个任务：为订单服务增加“取消原因”字段，并同步修改接口、领域模型和相关测试。

任务描述本身并不复杂。AI 检索到接口文档和历史 PR，修改了 DTO、数据库迁移脚本与服务层代码，执行测试后创建了一个 PR。表面上看，整个过程顺利完成。

但代码进入评审后，问题出现了。评审者发现取消原因应当是一个受限枚举，而不是自由文本。进一步追查才知道，AI 检索到了两份关于取消原因的文档，其中较旧的一份排在前面，模型据此生成了实现。单元测试没有覆盖这个约束，CI 也因此放行。

这时，团队真正需要回答的问题并不是“模型这次为什么答错了”，而是：

  • 这次修改依据了哪一版需求和接口契约。

  • AI 检索到了哪些知识片段，为什么选择了其中一份。

  • 模型、Prompt、工具调用和代码改动之间如何关联。

  • 测试为什么没有捕获这个问题。

  • 如果换一版模型、知识库或 Prompt，这类问题是否会再次发生。

  • 这次交付到底花了多少时间和成本。

这些问题共同指向一件事：LLMOps 可观测性关注的对象，不应只是一条模型请求，而应是一次完整的研发交付。

模型调用只是其中一个节点。对后端工程师而言，真正有价值的观测能力，是在交付出现偏差时，能够还原它的因果链。

一次模型调用成功，并不意味着交付成功

传统服务的可观测性，通常围绕请求展开。一个 HTTP 请求进入网关，经过服务、数据库和消息队列，最终返回响应。只要链路足够完整，工程师就能定位延迟、错误和资源瓶颈。

AI 研发场景的复杂之处在于，请求并不直接等于结果。

一次 AI 代码任务往往会经历需求理解、知识检索、模型推理、工具调用、文件修改、测试执行、PR 创建和人工评审等阶段。模型返回了正确格式的文本，甚至成功调用了工具，都只能说明局部动作完成了。代码是否符合规格，是否通过质量门禁，是否被评审者接受，才决定这次任务是否形成有效交付。

因此，平台不能只记录“调用了哪个模型、花了多少 Token”。这类数据对账单分析有帮助，但很难解释一次失败。

如果某个任务的首轮 CI 通过率突然下降，原因可能来自很多地方：

  • 模型版本更新后更倾向于修改较多文件。

  • 知识库中某类文档过期，检索结果发生偏移。

  • Prompt 模板改变了工具调用顺序。

  • 代码执行环境缺少依赖。

  • 测试本身没有覆盖规格约束。

  • 任务描述过于模糊，人工也会产生不同理解。

把这些问题都归结为“模型不稳定”，既无法定位，也无法改进。LLMOps 可观测性存在的意义，就是把模糊的印象转化为可追溯的工程事实。

一次 AI 交付，应该留下哪些事实

回到订单服务的例子。要解释这次错误，系统至少需要保留六类信息。

任务与规格

AI 接到的不是一句自然语言，而是一个研发任务。任务应有明确的身份，包括任务 ID、目标仓库、目标分支、代码基线、需求来源和规格版本。

其中，规格版本尤其重要。很多团队把需求写在 Jira、飞书文档、接口平台和代码注释中，AI 会从多个入口获取上下文。如果没有记录此次执行到底采用了哪一版规格，后续即使发现实现错误，也很难判断错误发生在需求、检索还是代码生成阶段。

对平台来说，任务不是模型调用的附属字段。它应当是整条链路的起点。

检索到的证据

RAG 场景中，模型并不是凭空生成代码。它会依据检索到的接口文档、架构规范、历史案例和代码片段做判断。

因此，观测系统需要记录证据的来源，而不只是最终拼接出来的 Prompt。一次检索至少应保留文档 ID、文档版本、分片 ID、排序位置、相关性分数和检索时间。对于敏感内容，可以保存摘要、哈希或受权限控制的引用，不必把原文无差别写入日志。

这样做不是为了复盘时逐字审查模型，而是为了回答一个更实际的问题：这段代码的依据是什么。

当团队发现 AI 总是在某个领域犯相似错误，首先该检查的通常是知识来源是否冲突、文档是否失效、检索是否覆盖了正确范围，而不是急于更换模型。

模型与提示词版本

模型调用本身仍然要记录，只是它不应成为唯一视角。

一次调用需要能够关联模型提供方、模型名称、模型版本、推理参数、Prompt 模板版本、上下文长度、输入输出 Token、缓存命中情况、响应状态和耗时。对于支持工具调用的模型，还应记录模型请求了什么工具，以及工具返回的结果是否被模型用于后续推理。

Prompt 也应被视为可演进的工程资产。很多团队会在优化过程中调整系统提示词、工具描述或上下文拼接策略。若这些变化没有版本化，后续看到质量波动时，很容易陷入猜测。

模型版本、Prompt 版本、知识库版本与工具版本共同构成一次运行的执行画像。把它们关联起来，才能比较两次结果的差异。

工具执行与代码改动

对 AI 编码任务来说，真正影响代码库的通常不是模型文本，而是工具执行。

例如，AI 读取了哪些文件，修改了哪些路径，执行了哪些命令，命令返回了什么错误，是否创建了分支，最终产生了哪些 diff。这些信息需要进入同一条任务链路。

这里有一个常见误区：只保存最终生成的代码片段，却没有保存执行过程。这样一来，团队知道 AI 最后改了什么，却不知道它中途是否尝试过错误的方案，是否因为测试失败进行了修复，是否读取了不应访问的文件。

工具日志不必无限保留，也不应包含密钥、用户数据等敏感内容。但关键的命令、退出码、文件范围、标准错误摘要和代码变更摘要，应该能够在任务详情中还原出来。

验证过程

研发交付的质量，最终要由验证来判断。

AI 生成的代码应进入现有质量链路，包括单元测试、集成测试、静态检查、安全扫描、契约测试和 CI 门禁。观测系统需要记录每一项验证的开始时间、结果、失败类型和报告地址，并将其与本次任务关联。

订单服务的例子里，如果契约测试明确检查取消原因只能取枚举值，那么问题会在 PR 前被发现。若测试没有覆盖，平台也应该能够让团队看见：这次交付的风险不是模型调用失败，而是规格约束没有进入验证体系。

这也是 AI 研发平台与聊天工具最本质的差别。前者需要对结果负责，后者只需要对回复负责。

交付结果与人工决策

最后还需要记录任务的归宿。

PR 是否创建，是否被合并，评审者提出了什么问题，是否发生人工接管，是否回滚，是否重新执行，以及最终消耗了多少成本。这些结果不能只作为旁路数据存在，它们应当回写到同一条运行记录中。

人工评审并不是 AI 自动化链路之外的例外。对于企业研发来说，它本身就是质量信号。一个任务虽然通过 CI，但连续被评审者要求重构，说明平台的“成功”定义过于乐观。

统一关联 ID，是链路能够成立的前提

许多团队已经有模型日志、检索日志和 CI 日志，但它们分散在不同系统中。排查问题时，工程师需要在日志平台、模型平台、代码平台和流水线系统之间反复跳转。

问题往往不在于缺少数据，而在于缺少关联。

一个实际可用的做法，是在任务创建时生成统一的 task_run_id，并把它传播到编排器、RAG 服务、模型调用、工具执行、代码仓库和 CI 流水线中。模型的一次调用可以有自己的 span_id，工具执行也可以有自己的执行 ID，但它们都应回到同一个任务运行 ID。

当 AI 创建 PR 后，CI 系统可以从 PR 标签、提交信息或流水线参数中继承这个 ID。人工评审、重新运行和回滚等动作，也可以继续关联到原始任务或建立清晰的因果关系。

这样设计之后，一次失败不再只是几条孤立日志，而是一条可以阅读的运行轨迹：

需求版本确定后，系统检索到了哪些证据，模型如何调用工具，代码在哪一步改变，验证为什么失败，工程师后来又如何接管。

对于后端工程师而言，这种关联比单独增加一个模型调用看板更有价值。因为绝大部分问题都发生在系统边界处，而不是发生在某个字段本身。

Metrics、Trace 与日志，各自解决不同问题

OpenTelemetry 将可观测性信号划分为 Metrics、Traces 和 Logs。这个划分同样适用于 AI 研发平台，但三类信号承担的职责需要分清，它们并不是彼此替代的关系。放到 AI 交付场景里，可以理解为三个不同的观察角度。

Metrics 适合看趋势。比如某个仓库近两周的任务完成率、CI 首次通过率、人工接管率、平均执行时长、单位任务 Token 消耗和成本分布。它们能帮助平台负责人发现异常，但通常不能直接解释异常。

Trace 适合看一次任务的路径。当某个 PR 出现问题时，工程师应能顺着 Trace 回看：任务从哪里开始，检索了什么，经过了哪些模型调用，执行了哪些工具，在哪个验证环节失败。Trace 的价值在于表达因果和时序。

Logs 适合保留证据。模型或工具的错误信息、测试失败摘要、权限拒绝记录、CI 标准错误输出，都属于定位问题时不可缺少的细节。

Google SRE 对监控系统提出过延迟、流量、错误和饱和度等基础观察维度。这些维度对于 AI 平台依然重要，例如模型调用延迟、队列堆积、工具执行失败率和并发容量。

不过，AI 研发平台还有一层传统服务很少直接面对的问题：交付质量。模型服务没有报错，并不代表代码正确。因此，平台指标还需要补充任务完成率、验证通过率、PR 合并率、人工接管率和评审后返工率等结果指标。

这类指标也不能被简单当作模型评分。PR 合并率受任务难度、团队评审标准和仓库质量基线影响。它们更适合用于发现趋势，再回到具体 Trace 中找原因。

版本关联，比单看 Token 更重要

Token 是 AI 平台最容易采集的数据之一，因此也最容易被过度关注。

Token 确实值得监控。它影响成本、延迟和上下文利用率。一个任务的输入 Token 突然翻倍，可能意味着检索召回范围过大，或者 Prompt 拼接出现了重复内容。输出 Token 异常增加，也可能意味着模型在循环调用工具时没有及时收敛。

但 Token 本身不能说明质量。

两个任务花费相同的 Token，其中一个通过了测试并被合并，另一个却因规格理解错误被打回，它们的工程价值完全不同。一个更贵但能减少人工返工的模型调用，也未必比一个廉价但经常需要人工修正的调用更差。

因此，更合理的观察单位是“任务结果与资源消耗的组合”。平台应能回答：

  • 某类任务的平均成本是多少。

  • 成本上升时，首轮验证通过率是否同时提升。

  • 切换模型或 Prompt 后，人工接管率是否下降。

  • 某个知识库版本上线后，是否减少了重复错误。

  • 某个仓库是否因上下文过大而产生明显的低效调用。

要回答这些问题，版本关联是必要条件。模型、Prompt、知识库、工具、评估集和代码基线不能各自独立演进。每一次运行都应明确自己使用了哪些版本，评估结果也应绑定到对应的执行画像。

OpenTelemetry 的生成式 AI 语义约定提供了模型调用、请求参数、Token 使用和响应等通用语义。它的价值不在于让所有团队使用同一套字段，而在于帮助平台把模型调用放入可关联、可比较的运行上下文中。

不要把观测系统做成另一个日志仓库

很多可观测性项目的失败，并不是因为技术选型有问题，而是记录了太多无法支持决策的数据。

第一种常见情况是，只采集模型 API 的请求与响应。这样能看见模型输出，却看不见它依赖的证据、执行的工具和最终的验证结果。模型日志很完整，交付链路仍然是断的。

第二种情况是，只建立成本看板。成本当然需要治理，但单独看成本容易把团队带向错误目标。平台把上下文压缩得很激进，Token 降下来了，却让模型失去了关键规格信息，返工成本反而上升。

第三种情况是，保留了所有原始 Prompt 和响应，却没有做数据分类和脱敏。研发任务中可能包含源代码、内部接口、客户信息和访问令牌。可观测性系统本身也应受到权限控制，默认记录元数据和必要摘要，对敏感原文采用最小化留存与按需访问。

第四种情况是，所有质量问题都用一个成功率指标概括。一次任务失败，可能是检索没有找到正确知识，也可能是工具权限不足，或是 CI 环境异常。把不同性质的失败混在一起，指标即使变化，也很难指导改进。

好的观测系统不会要求工程师阅读更多日志。它应该帮助团队更快判断，当前应该修模型、修知识、修工具，还是修验证流程。

一个适合企业试点的最小闭环

企业在起步阶段，没有必要先建设覆盖所有智能体、所有仓库和所有模型的复杂平台。更可行的方式，是选择一类边界清楚的任务，例如接口变更生成、测试失败修复，或基于规格创建后端模块骨架。

这个最小闭环需要做到几件事。

首先，为每次任务分配统一运行 ID，并贯穿任务编排、模型调用、工具执行与 CI。没有这条主线，后续数据很难组织。

其次，记录任务、规格、检索证据、执行画像、代码变更和验证结果。字段可以从简，但关联关系不能缺失。

再次，把成本放回结果语境中观察。任务详情页上同时展示耗时、Token、工具执行次数、测试结果、PR 状态和人工接管情况，通常比单独建设多个看板更容易形成判断。

最后，挑选一批稳定的典型任务作为评估集。在模型、Prompt 或知识库变更前后，比较同一批任务的验证通过率、改动范围、成本和人工介入情况。这样，平台的每次优化才有可验证的依据。

OpenAI 的 Agents SDK 也将一次运行表示为由 Trace 和 Span 组成的层级结构，其中模型调用、工具调用和交接都可以成为可追踪节点。其 Tracing 文档反映了一个值得借鉴的思路：观测应当跟随工作流，而不是停留在单次模型请求上。

结语

AI 研发平台最难的部分，通常不是接入一个模型，也不是搭建一块成本看板。真正困难的是建立一套能够解释交付结果的记录体系。

当一次 AI 代码任务被合并或被打回，团队应当知道它依据了什么规格和知识，经历了哪些模型与工具行为，在哪个质量环节通过或失败，最终投入了多少资源。这样的链路，才能让平台的改进从经验判断走向证据判断。

LLMOps 可观测性的价值，不在于让团队拥有更多数据，而在于让每一次失败都可解释，让每一次优化都可归因，让 AI 真正进入既有的软件工程治理体系。
